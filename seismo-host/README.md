# 自作センサーの受け手

**読者は自作地震計を組んで動かす人。** センサーが LAN へ流す波形を受け取り、
計測震度相当を出すためのプログラム。**このアプリ本体のビルドには含まれない。**

センサー側は [`firmware/`](../firmware/README.md)。送られてくるパケットの形も
そちらに書いてある。

**この文書が説明するのは「どう作ったか」。** 何を作るかを定めた要件は
[REQUIREMENTS.md](REQUIREMENTS.md)（§1〜§19）にあり、**節ごとの進み具合の表もあちらが持つ**。

## いまある部分

| 置き場所 | すること |
|---|---|
| `src/protocol/` | パケットを読む。壊れた中身を落とし、**落とした理由を数えられる形で返す** |
| `src/timebase/` | 届いたパケットを「途切れていない一続き」へ組み直し、時間軸を当てはめる |
| `src/intensity/` | 届いたサンプルから計測震度相当（強震モニタと同じリアルタイム震度）を一定の刻みで出す |
| `src/receiver/` | UDP を待ち受け、上の 3 つへ順に通す。生のパケットを残し（時間ごとの miniSEED 3）、結果を HTTP で配り、**換算が正しいかを自分で診る**のもここ。基板がどこに置かれているか（観測点）と、その履歴を持つ設定（StationXML）を読み書きするのもここ |
| `src/detection/` | 観測点の合成波形から揺れを切り出し、気象庁の地震情報と照らし合わせて記録する（→「地震検出」） |
| `main.ts` | 常駐プロセスの入口 |
| `bench/` | 地震検出の評価台。過去の生データを流し直し、気象庁の地震と突き合わせて数える（→「地震検出」の「評価台」） |

**保存した波形は読み返せる** —— 生データ（センサー単独の RAW 値）も観測点の合成波形も、
管理コンソールの「波形の記録」タブで全期間を見られる（→「保存した波形を読み返す」）。PWA の地震カードが
使う合成波形の口は別にある（→「過ぎた合成波形を読み返す」）。**まだ無いもの**: 複数台を 1 本へまとめる処理
（§7）で残っているのは**異常センサー検出だけ** —— 差分から「このセンサーがおかしい」を
自動で判定する仕組みで、閾値が未設計（合成・差分そのものは実装済み。
→「複数センサーの波形合成（§7）」）。**残りの全体像は
[REQUIREMENTS.md](REQUIREMENTS.md) の「進み具合」を見ること。**

## 読み取り（`src/protocol/`）

**例外を投げない。** 相手はネットワークで、壊れた入力は異常ではなく日常
（途中で切れる・別のプログラムが同じ口へ投げる）。投げる形にすると受信の繰り返しを
守るために呼び出し側が毎回囲うことになり、しかも**何件どんな理由で落ちたかを
数えられなくなる**。

落とす理由は 7 つに分けてある。**原因ごとに手当てが違うので分けている** ——
「先頭行が JSON として読めない」は別のプログラムが同じ口へ投げている疑い、
「宣言された件数と行数が合わない」は途中で切れた疑い、というように。

版 1 と版 2 の両方を読む。**蓄えた記録は実装より長生きする**ので、古い形を
読めなくすることはできない。版 1 は基板の MAC を名乗らないため、識別子には
名前を使い、`name:` を前置して出どころを残す。

**名乗られた時刻は「有限であること」だけでは通さない。** 時刻として表せない大きさの値
（`1e20` など）は有限の数なので素通りする。出す側も範囲を見て投げない形にしてあるので
**通しても落ちはしない** —— ただし下流に残るのは「時刻不正」という印だけで、
**どの欄が壊れていたのかも、何件届いたのかも辿れない**。ここで落とせば理由が付いて
1 件として数えられる。**「いまに近いか」では弾かない** —— 昔の記録を流し直す使い方が
あるので、縛るのは「時刻として表せること」だけにとどめる。

## 区間の組み立て（`src/timebase/`）

### 繋いではいけない切れ目

**失われた時間を詰めて繋ぐと、そこに段差ができる。** 計測震度のフィルタは段差を
強い揺れとして読むので、繋いだ結果は「静止しているのに揺れた」という形で出る。

| 理由 | いつ |
|---|---|
| `seq-gap` | 通し番号が飛んだ（パケットが届かなかった） |
| `overflow` | センサーの中でサンプルが失われた |
| `seq-reset` | 基板が再起動した |
| `config-changed` | 軸・周波数・換算が変わった |
| `stream-start` | その基板・センサーを初めて受けた |
| `timebase-jump` | **通し番号は続いているのに、名乗る時刻が飛んだ**（下記「時間軸」） |

前 2 つは、記録を後から解析する側と同じ規則。

### 並び替えと再起動の見分け

UDP なので、パケットは**遅れて届く・二度届く**ことがある。一方、基板が再起動すると
**通し番号が 0 へ戻る**。版 1 は起動ごとの識別子を持たないので、どちらも
「番号が戻ったパケット」として同じ顔で現れる。

**戻り幅では見分けられない。** 起動から間もない基板が落ちると、番号はまだ大きく
戻れないので、戻り幅で測ると再起動を並び替えと読む。

**見分けるのは時刻の辻褄。** 遅れて届いただけなら、その番号にふさわしい過去の時刻を
名乗る。再起動なら合わない —— 時計が合っていれば未来へ飛び、合う前なら大きく過去へ
飛ぶ。どちらの向きも同じ判定で捕まる。

**遅れて届いたものは繋ぎ直さず、数えて捨てる。** 挿し込む形にすると、下流が
「一度渡したより古いサンプル」を受け取ることになる。

何を足場に時刻を比べるかは、実測を根拠に選んである（`segmenter.ts` の
`TIMEBASE_CONSISTENCY_MS` のコメント）。

### 時間軸

パケットは 1 つにつき 1 つしか時刻の目印を持たない。その値は FIFO を抜き出した
瞬間の揺れをそのまま含むので、**直線を通して均す**。別々の区間が同じ絶対時刻の上に
乗るのはこのため。

時刻が unix ミリ秒という大きな値で入ってくるため、当てはめは**桁落ちしない書き方**を
選んである（理由は `lineFit.ts` のコメント）。

アンカーが足りないときと、当てはめた間隔が公称から 1 割以上離れたときは公称値へ倒し、
**倒したことを隠さない**（`nominalReason`）。

### 時計が合う前のパケットを、同じ区間へ繋がない

**基板が時計が合う前から送りうる。** ファームの `configTime()` は SNTP の応答を待たない
ので、最初の数秒は `gettimeofday()` が**起動からの経過＝1970 年**を返す。同期が済むと
時刻だけが 1.79 兆ミリ秒ぶん飛ぶ —— **通し番号は続き、設定も変わらず、あふれも無い。**

**基板の側でも送らないようにした**（2026-10-01。`firmware/README.md`「時計が合う前は
送らない」）。**それでもこの判定は外さない** —— 受け手は**どの版のファームが焼かれているかを
選べない**。焼き直していない基板はいまも同期前から送るし、送るのは自作の基板だけとも
限らない。**入口で守るものを、送り手の躾に置き換えない。**

**ここで切らないと、両方のエポックのアンカーが 1 本の直線に乗る。** 傾きが桁ごと外れて
公称値へ倒れ、足場には最初のアンカー（＝1970 年の側）が残る。**区間は当てはめをやり直さない
ので、その区間は二度と絶対時刻を持たない。**

だから**番号がぴったり続いているときだけ時刻の辻褄を見て、`TIMEBASE_CONSISTENCY_MS` を
超えたら切る**（`timebase-jump`）。**番号が飛んでいる側ではわざと見ない** —— 予測に使う
間隔は公称値で、欠落が長いほどずれが積み上がる（5 分ぶんで 210 ms）。落ちたことを
時計の話にすると、切れ目の理由が診断の手掛かりにならない。

**足場がエポックとして成り立つかも検算する**（`epochPlausible`。2020-01-01 より前なら偽）。
**倒した経路と当てはめが通った経路の両方**で見る —— アンカーが全部同期前に揃った区間は
傾きが公称どおりなので当てはめを通ってしまい、切片だけが 1970 年になる。**値そのものは
捨てずに渡す**（捨てると「届いていない」と見分けが付かなくなる）。

**成り立たない区間は毎分の要約で再掲する**（`timebase-epoch` の警告）。`/status` の
`segments[]` にも出るが、**生の JSON を読み比べる人にしか見えない** ——
`firstSampleMs` の数値を並べても、読む側が引き算をするまで異常に見えない。

> 2026-10-01 の実機。**9 本のうち 8 本の足場が 1970 年に居座っていた。** 時間で重なる
> センサー対が 36 組すべてゼロになり、**合成が 1 つも組めなくなっていた**（`uncoveredFusions`
> が 9361・`lastMemberCountMax` が 1）。震度は単独へ落ちて出続けるので、外からは
> 「動いている」ようにしか見えなかった。唯一正常だった 1 本は、同期の後に作り直された区間。

## 計測震度相当（`src/intensity/`）

**方式は強震モニタと同じリアルタイム震度。** 功刀ほか（2008）「震度のリアルタイム演算法」
（地震 2, 60, 243-252）と、そのフィルタを改良した功刀ほか（2013）「震度のリアルタイム演算に
用いられる近似フィルタの改良」（地震 2, 65, 223-230）の手順をそのまま使う。

- 気象庁の周期補正フィルタを、時間領域の近似フィルタ（2 次 6 段＋ゲイン）で置き換えて、
  届いた順に掛ける
- 3 成分を合成した振幅に対して、**サンプルが届くたびに直近 60 秒で 0.3 秒の判定**を行い、
  気象庁と同じ式で震度へ直す

**値は最大に達してから約 60 秒下がらない。** 揺れが止んでも、その揺れが判定の窓に残っている
間は保たれる。強震モニタの実データでも、最大値は 60〜63 秒保たれてから落ちる（2026-10-04 に
大地震 4 本・上位 12 観測点で確かめた）。

**気象庁の計測震度とは別の量。** あちらは記録全体へ周波数領域のフィルタを当てる。近似フィルタは
位相がずれるので、論文の検証（453,357 波）で差の標準偏差は 0.0272、99% 以上が 0.1 以内。
**時系列の最大値が計測震度に対応する。**

> 2026-10-04 まではこの方式ではなく、気象庁の手順をそのまま直近 20 秒の窓へ 1 秒ごとに当てていた
> （2 秒先読みして出していた）。強震モニタの値と並べるには物差しが違うため置き換えた。

### 計算そのものはここに無い

近似フィルタと判定はこのリポジトリのアプリ側（`src/utils/knet/realtimeIntensity.ts`）が持って
いるので、**それを呼ぶ**。ここが受け持つのは**区間の位置の突き合わせと、いつ答えを出すか**だけ。
K-NET の取り込み（`src/utils/knet/buildEventResultFromZip.ts`）も同じ計算を呼ぶので、
自作地震計と K-NET の値は同じ物差しで並ぶ。

写し取れば同じ数字が出るのは書いた日だけで、片方だけ直した日から静かに離れていく。
刻みをサンプル数へ直す丸め方や、0.3 秒の継続時間を測る位置も、同じ理由で両方が
同じ関数を呼ぶ。

### 答えは遅れずに出る

近似フィルタは未来のサンプルを見ないので、刻み（1 秒）の位置まで届いたその回に答えが出る。
区間を締めるときも出し残しは無い。

### 重力は最初の 1 秒の平均で引く

生の値には重力がそのまま乗る（机に置いた基板で約 1009 gal）。近似フィルタは直流を通さないが、
素で渡すと**立ち上がりの段差が強い揺れとして出て、60 秒の窓に入ったまま 1 分間居座る**。
だから区間の最初の 1 秒を溜め、その平均を差し引いてからフィルタへ通す。

**1 サンプルで推定しない。** そのサンプルのノイズが段差になる —— 実記録（ある有感地震の
前後）で試したとき、区間の頭だけ 0.89（平常時は 0.36）が 60 秒居座った。
1 秒の平均にすると 0.19 まで下がった。

基準線を補正済みの波形（K-NET など）では、引く量はほぼ 0 で害は無い。

### サンプリング周波数の下限

近似フィルタはサンプリング周波数が低いと発散する（論文は約 77 Hz 未満で発散すると報告している。
こちらの係数で確かめると 70 Hz では発散し、77 Hz では安定だった）。**作る時点で係数を確かめて
止める** —— 発散した出力は有限のまま大きくなるので、震度だけ見ていると揺れの大きな地震と
区別が付かない。止めた理由は `stream-rejected` として状態の口に出る。

### 実時間で回る

毎秒 100 回で、1 点（1 秒ぶん）あたり **0.05〜0.12 ms**。120 秒ぶんを 50 サンプルずつ流して
1 点あたりで割った値で、**測ったのは作業 PC 1 台だけ**なので機種で動く（2026-10-04）。
かつての方式（窓 20 秒の周波数領域フィルタ）は同じ測り方で 19.8 ms だった。

### 渡し方の約束

**例外を投げるのは呼び出し側の誤りに対してだけ** —— 3 成分の長さが違う・締めたあとに
渡した・有限でない値が混じっている。正しく換算した値がこうなることは無い（範囲の外は
換算の側が落とす）。**受け止めて続けてはいけない。**

**投げたときは何も溜め込んでいない。** 受け取った中身を先に全部確かめてから触るので、
成分ごとに溜まった数がずれたまま残ることは無い。

**投げたあと、同じ流れへ続きを渡してはいけない。** 渡さなかったぶんだけ位置が実際より
手前に留まるので、以後の答えは時刻のずれた値になる。

**作り直すときは、組み立ての側の区間も一緒に閉じること。** 震度の側だけ作り直すと、
組み立ての側は区間が続いていると見なしたまま次のパケットに区間の途中の位置を名乗らせ、
0 から始まる新しい流れと永久に噛み合わない —— その基板の震度が、本物の切れ目が来るまで
出なくなる。**両方を 1 つの操作で閉じる配線は、受信層を作るときの宿題。**

**その約束は文面ではなく位置で確かめる。** 渡すときに「区間の先頭から数えた位置」を
一緒に渡してもらい、待っている位置と突き合わせる。飛ばして渡せばその場で止まる。

区間が途切れたかどうかを決めるのは組み立ての側だけれど、**あちらはサンプルの中身を
見ていない**ので、ここで弾いたパケットを「連続」として受理してしまう。だから位置の
確認はこちらにも要る。一方で「一度壊れたら以後いっさい受け付けない」という覚えは
持たない —— 止めた側にそれを解く手立てが無く、その基板の震度が黙って戻らなくなる。

## 受信（`src/receiver/`）

UDP を待ち受け、届いたパケットを読み取り → 組み立て → 震度の順に通す。

### 動かす

```bash
npm run seismo-host
SEISMO_UDP_PORT=50505 SEISMO_UDP_ADDRESS=0.0.0.0 npm run seismo-host
```

ポートの既定は 50505（センサー側の送り先と同じ）。**打ち間違えた値では起動しない** ——
黙って既定へ倒すと、基板は送っているのに届かない状態が理由も分からず続く。

出口は 4 つ。**標準出力**へ震度が 1 行ずつ出て、落としたもの・区間の切れ目もその場で出る
（落とした件数の要約は 1 分ごとと終了時）。**生のパケットはファイルへ残る**（下記）。
残る 2 つは HTTP（下記「状態と押し出しの口」）。

### 常時動かす機へ配る

**配り先は git リポジトリとは限らない。** 開発機とは別の常時起動の機で動かす場合、
リポジトリから**ファイルをコピーしただけ**の置き場所になっていることがある
（`.git` を持たない）。そこでは `git pull` が効かないので、送り直す。

**送るのは実装だけ。**

| 送る | 送らない（配り先にしかない） |
|---|---|
| `seismo-host/main.ts` | `seismo-host/config/stations.xml` — 観測点の設定（履歴も兼ねる） |
| `seismo-host/src/` | `seismo-host/data/` — 生のパケット・合成波形・揺れの記録・波形の要約 |

**ディレクトリごと送らないこと。** 手元にも同名の `config/stations.xml`（開発用）が
あるので、`seismo-host/` を丸ごと上書きすると**配り先の観測点設定と、その履歴が開発用で潰れる**。

```bash
scp seismo-host/main.ts <配り先>:<置き場所>/seismo-host/main.ts
scp -r seismo-host/src <配り先>:<置き場所>/seismo-host/
```

**共有しているものも送る。** ホストはリポジトリ本体側の次のファイルを読む。配り先に無い・古いと、
起動時に読み込みが解決できずホストごと止まる。

| ファイル | 読む部分 |
|---|---|
| `src/utils/knet/realtimeIntensity.ts`・`src/utils/knet/intensityCommon.ts`・`src/utils/knet/seismicIntensity.ts`・`src/utils/knet/fft.ts` | 計測震度相当・地震 1 件ぶんの震度（`seismicIntensity.ts` は `fft.ts` を読む）・波形の要約の PSD（`fft.ts`） |
| `src/utils/geo.ts`・`src/utils/travelTime.ts`・`src/data/jma2001TravelTime.ts` | 地震検出（地震情報との照合）・波形の記録へ重ねる P・S |
| `src/utils/dmdataApiKey.ts`・`scripts/hypocenterDailyRecord.ts` | 波形の記録へ重ねる地震の一覧（DMDATA の API キーの形の確かめ・気象庁の震源リストの読み取り） |

```bash
scp src/utils/knet/realtimeIntensity.ts src/utils/knet/intensityCommon.ts src/utils/knet/seismicIntensity.ts src/utils/knet/fft.ts <配り先>:<置き場所>/src/utils/knet/
scp src/utils/geo.ts src/utils/travelTime.ts src/utils/dmdataApiKey.ts <配り先>:<置き場所>/src/utils/
scp src/data/jma2001TravelTime.ts <配り先>:<置き場所>/src/data/
scp scripts/hypocenterDailyRecord.ts <配り先>:<置き場所>/scripts/
```

読み込み先が増えたかは `grep -rhnE "from '(\.\./)+(src|scripts)/" seismo-host/src seismo-host/main.ts` で数え直す
（テストのファイルが読むものは送らなくてよい）。
`package.json` の依存が変わったときは配り先で `npm install` も要る。

**Windows の配り先へ ssh で起動するときは `cmd.exe /c '…'` と包む** ——
向こうのシェルが PowerShell だと `&&` を「有効なステートメント区切りではありません」と
言って落ちる。**値の直後（`&&` の前）に空白を入れない** —— `cmd.exe` の `set` は行末までを
値として採るので、`set VAR=値 && …` と書くと**値の末尾に空白が混ざる**。

```bash
ssh <配り先> "cmd.exe /c 'cd /d <置き場所> && set SEISMO_ADMIN_TOKEN=<値>&& set SEISMO_ADMIN_ALLOWED_HOSTS=<host:port>&& set SEISMO_ADMIN_ALLOWED_ORIGINS=<origin>&& npm run seismo-host >> seismo-host.log 2>&1'"
```

**ログは追記にする（`>>`）。** `>` だと起動のたびに前回のログが消え、落ちる直前に何が
起きていたかを調べる手立てが無くなる。ホストは起動のたびに `[host] 起動した（pid …・日時）`、
正常に終わると `[host] 正常に終了した（日時）` を書くので、どこから今回の分かはそこで分かる。
**前回が正常に終わらなかったことは、次の起動が自分で書く**（下の「止まった・落とされたことを残す」）。

**止めるときは、止める口を叩く**（サービスで動かしているなら `Stop-Service`。→ 下の「Windows で常駐させる」）。`Stop-Process` や `process.kill` は SIGINT のハンドラを
呼ばずにプロセスを落とすので締めくくりが走らず、**miniSEED が溜めていた波形（最長 5 秒ぶん）と
受信の記録（最長 30 秒ぶん）が書かれずに消える。** 認証つきの `POST /api/shutdown`（下の「止める合図」）を叩けば、
締めくくりを走らせてから自分で終わる。**`<配り先>:50506` は起動時の
`SEISMO_ADMIN_ALLOWED_HOSTS` に含めた値と同じ形にする**（違うと `host-not-allowed` の 403）。

```bash
curl -X POST -H "Authorization: Bearer <トークン>" -H "Origin: <許したオリジン>" http://<配り先>:50506/api/shutdown
```

`{"status":"closing"}` が返る。終わったかは、`seismo-host` を含む node のプロセスが消えたことと、
ログの最後の `[host] 正常に終了した` で確かめる。**2 分たっても残っていたら木ごと止める** ——
`npm run seismo-host` → `tsx` の CLI → 実体の node → `esbuild` と 4 段になるので、いちばん上だけ
止めても残る。

**入れ替わったかは `/status` で確かめる。** プロセスは読み込み済みのコードで走り続けるので、
ファイルを置いただけでは変わらない。再起動してから購読の粒度を見る ——
`stream.subscribers[].wave` が `'station'` のような**文字列**なら新しい版、
`true` / `false` の**真偽値**なら `?wave=` に粒度を足す前の版。

> 止めている間は UDP を受けない。**基板は送り続けるので、その秒数ぶんの生データが欠ける。**

### Windows で常駐させる（サービス）

**常時動かす機では、Windows のサービスとして動かす。** 求めるのは 2 つ ——
電源が入ったら誰もサインインしなくても動き出すこと、**再起動（Windows Update の自動再起動を含む）の前に
締めくくりを走らせてから止まること**。後者が無いと、再起動のたびに miniSEED の溜め（最長 5 秒）と
受信の記録（最長 30 秒）が消える。

ラッパーは [WinSW](https://github.com/winsw/winsw) の **v3.0.0-alpha.11**（プレリリース）を使う。
Windows がシャットダウン・再起動の前にサービスへ送る通知は 2 つあり、ラッパーの版で受けられるものが違う
（版ごとの受け方は WinSW のソースで確かめた。通知そのものの仕様は下の Microsoft Learn）。

| 版 | 受ける通知 | Windows が待つ長さ |
|---|---|---|
| v2.12.0（安定版） | 普通の停止通知（`SERVICE_CONTROL_SHUTDOWN`）だけ | `HKLM\SYSTEM\CurrentControlSet\Control` の `WaitToKillServiceTimeout`。**実際に配った機では 5000 ミリ秒（5 秒）だった**。ホストの締めくくりは実測 1〜2 秒だが、Windows Update の再起動のようにディスクが混む場面で収まるかは確かめていない |
| v3.0.0-alpha.11 | 止まる前の通知（`SERVICE_CONTROL_PRESHUTDOWN`）だけ（`<preshutdown>true</preshutdown>` のとき） | サービスが止まるか、サービスごとに決めた期限（下の設定では 1 分）が来るまで。ほかのサービスが止まり始める前に走る |

（通知の順序と待ち方は Microsoft Learn の [Service Control Handler Function](https://learn.microsoft.com/en-us/windows/win32/services/service-control-handler-function)）

**v3 は普通の停止通知を受け付けない**（`CanShutdown` を立てていない）。止まる前の通知の登録が外れていると、
**締めくくりの機会は 1 つも無く、再起動で強制終了される**。登録したら「登録・止める・起動する」の表の方法で必ず確かめること。

**タスクスケジューラで動かさない。** 再起動のとき、タスクのプロセスが締めくくりの前に落とされない保証を
資料で確かめられなかった（落とされる順序を書いた資料が見つからない）。

#### 置くもの

配り先の `<置き場所>` の直下に、WinSW の実行ファイルと設定の XML を**同じ名前で**置く
（WinSW は自分と同じ名前の XML を読む）。トークンを書くので、**XML は配り先にしか置かない**。

- `seismo-host-service.exe` —— 配布物の `WinSW-x64.exe` を改名したもの。署名は付いていない。
  2026-10-07 に取得したものの SHA-256 は `a2daa6a33a9c2b791ae31d9092e7935c339d1e03e89bfb747618ce2f4e819e20`。
  一致しなければ使わない（取得し直して、配布元が差し替わっていないかを確かめる）
- `seismo-host-service.xml`

```xml
<service>
  <id>seismo-host</id>
  <name>seismo-host</name>
  <description>self-built seismometer host (realtime-earthquake-viewer)</description>

  <executable>C:\Windows\System32\cmd.exe</executable>
  <arguments>/d /c ""C:\Program Files\nodejs\node.exe" --import tsx seismo-host/main.ts >> seismo-host.log 2>&amp;1"</arguments>
  <workingdirectory><置き場所></workingdirectory>

  <env name="SEISMO_ADMIN_TOKEN" value="<値>"/>
  <env name="SEISMO_ADMIN_ALLOWED_HOSTS" value="<host:port>"/>
  <env name="SEISMO_ADMIN_ALLOWED_ORIGINS" value="<origin>"/>

  <startmode>Automatic</startmode>
  <preshutdown>true</preshutdown>
  <preshutdownTimeout>1 min</preshutdownTimeout>
  <stoptimeout>30 sec</stoptimeout>

  <onfailure action="restart" delay="1 min"/>
  <resetfailure>1 hour</resetfailure>

  <logpath><置き場所>\service-logs</logpath>
  <log mode="append"/>
</service>
```

- **`cmd.exe` を挟むのは、ログを 1 本のファイルへ追記するため。** WinSW は標準出力と標準エラーを
  別々のファイル（`.out.log` と `.err.log`）にしか書けず、2 本に割れると前後関係が読めなくなる。
  `service-logs\` に残るのは WinSW 自身のログ
- **`npm run` を挟まない**（`node --import tsx` で node 1 本にする）。止めるときの Ctrl+C で締めくくりを
  走らせるのが node 1 つになり、npm・tsx の CLI を挟んだ多段の木を気にしなくてよくなる。配った機の Node 24・tsx 4.23 で動いた
- **動かすアカウントは既定の LocalSystem**（パスワードを登録しない）。`<置き場所>` に SYSTEM の書き込み権限が
  要る（ユーザーのホームの下なら既定で付いている）。ホストは管理用の口（`/api/*`）を開けているので、
  そこに穴があれば最も強い権限を渡すことになる —— それを避けたいなら `<serviceaccount>` で普通のアカウントを指定する
- 異常終了（終了コードが 0 でない）なら 1 分後に起動し直す。**止める口で終わらせたときは終了コードが 0 なので
  起動し直さない**

#### 登録・止める・起動する

管理者の PowerShell で、`<置き場所>` から:

```powershell
.\seismo-host-service.exe install
.\seismo-host-service.exe start
```

| したいこと | すること |
|---|---|
| 止める | `Stop-Service -Name seismo-host`。WinSW が Ctrl+C を送り、ホストは SIGINT で締めくくりを走らせて終わる（ログに `[udp] SIGINT を受けたので締めます` → `[host] 正常に終了した`）。30 秒たっても残っていれば WinSW が強制終了する |
| 起動する | `Start-Service -Name seismo-host` |
| 配り直す | 送る → ハッシュを照合する → `Stop-Service` → `Start-Service` → `/status` で確かめる（上の「入れ替わったか」） |
| 止まる前の通知を受けるか確かめる（登録したら必ず） | `sc.exe query seismo-host` の `STATE` に `ACCEPTS_PRESHUTDOWN` が出る。期限は `HKLM\SYSTEM\CurrentControlSet\Services\seismo-host` の `PreshutdownTimeout`（ミリ秒） |

止める口（`POST /api/shutdown`）で止めてもよい。その場合サービスは止まったままになるので、`Start-Service` で起こす。

**実機の再起動で確かめた**（2026-10-08）。再起動の操作から 13 秒後に `[host] 正常に終了した`、
Windows が起動した 16 秒後にサービスが `[host] 起動した` を書き、止まっていた約 1 分の分は
基板の溜めから取り戻して欠けは 0 だった。

#### 高速スタートアップのまま「シャットダウン」したとき

**再起動とは振る舞いが違う。** Windows の高速スタートアップ（既定で有効）は再起動には効かず、
「シャットダウン」にだけ効く。そのときはユーザーのセッションだけを閉じ、**カーネル・ドライバ・サービスは
止めずに休止状態として保存し、次に電源を入れたときに元へ戻す**
（[Delivering a great startup and shutdown experience](https://learn.microsoft.com/windows-hardware/test/weg/delivering-a-great-startup-and-shutdown-experience)・
[Fast startup causes hibernation or shutdown to fail](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/fast-startup-causes-system-hibernation-shutdown-fail)）。
サービスに届くのは電源の通知だけで、止まる前の通知は届かない
（[Suspend Services Duration](https://learn.microsoft.com/windows-hardware/test/assessments/suspend-services-duration)）。

ホストもサービスとして保存される側に入るので、**止まらないし、起動し直しもしない**。メモリごと保存されるので
溜めている波形も消えず、電源を入れ直すと止まった時点の続きから動く。**戻ったあとに時刻の飛んだ状態から
問題なく続けられるか（基板からの取り戻し・押し出しの張り直し）は、まだ確かめていない。**

**高速スタートアップは切らない。** 再起動には効かないので、切っても再起動の振る舞いは変わらず、
シャットダウン後の起動が遅くなるだけ。その代わり、**シャットダウンから電源を入れ直したら `/status` で
センサーが届いているかを確かめる**（届いていなければ `Stop-Service`・`Start-Service` で起こし直す）。

### 重力を引くのはここで決める

計算の側は既定値を置いていない（通す側に選ばせる作り）。**その選ぶ側がここ** ——
自作センサーの生の値には重力が乗ると分かっているので、窓ごとに平均を引くほうへ固定する。

### 換算を、組み立てより先に済ませる

カウント値を加速度へ直すのは、組み立てへ渡す**前**。逆にすると、範囲の外で捨てるパケットを
組み立てが受理してしまい、**あちらの位置だけが進む。** そうなると以後どのパケットも
震度側が待っている位置と噛み合わず、その基板の震度が本物の切れ目まで出なくなる。

### 閉じるときは、組み立てと震度を 1 つの操作で

`closeStream` が唯一の口。片方だけ閉じると、組み立ては区間が続いていると見なしたまま
次のパケットに**区間の途中の位置**を名乗らせるので、0 から数え直す新しい流し込みとは
永久に噛み合わない。

### 時刻の根拠が崩れたら、そのことも一緒に返す

名乗られた時刻が通し番号の進みと合わない基板では、組み立ての側が当てはめを捨てて公称の
間隔へ倒す。**倒れている間の時刻は正常時とまったく同じ形をしている**ので、印を付けずに
渡すと「時刻の根拠が崩れたまま震度だけが普通に出続ける」ことになる。震度 1 つずつに
その印（`timebaseNominalReason`）を載せる。

**区間の状態で代用しない** —— あれは「いまの当てはめ」なので、倒れていた間に出した値が
後から当てはめが効いて健全に見える。

### 組み立てと震度を繋ぐ部分は、数えない・記録しない

1 パケットごとに何が起きたかを返すだけで、件数の集計も記録の出力も持たない。出す先
（標準出力・状態の口）は上の層が決める。**ただし「返さない」ことはしない** ——
返さなかったものは、そこで起きた異常がどこにも現れないことを意味する。

### 数える表は 2 つに分ける

読み取りに失敗したパケットは、どの基板から来たのか判らない（ヘッダが読めていないのだから
当然）。だから**送信元アドレスの表**と**基板の表**を別に持つ。1 つへ寄せると「不明」という
巨大な行ができて、どの送り手が壊れているのか辿れなくなる。逆に、読み取りを通ったあとの
ものをアドレスで数えるのも違う —— アドレスは割り当て直しで変わるので、同じ基板が別の行に
分かれる。

**届いた件数と通した件数も数える。** 「落とした 40 件」は、届いたのが 50 件なのか 5 万件
なのかで意味が正反対になる。

**覚えられる相手の数には上限がある**（表ごとに 64）。名前もアドレスも送られてきた値なので、
際限なく増える形にはできない。達したあとは「その他」の行へ合算する —— 内訳は失うが
**合計は正しいまま**になる。

### 送信元ごとに、受け取る速度の上限を掛ける

1 台あたり毎秒 10 パケット（300 ms ごとに吸い出し、そのたびセンサーの数だけ送る。
実機 3 台を 20 秒見ても同じ値だった）に対して、既定は毎秒 100・瞬間 200 まで。**この値はセンサーの数と吸い出しの間隔で動く**ので、上限をそこへ
張り付かせない —— 張り付かせると、センサーを 1 つ足しただけで本物のデータが落ちる。
**読み取りより前に掛ける** —— あとに置くと、落とすと決めたパケットの中身を先に読むことに
なり、いちばん抑えたい場面で仕事が減らない。

**止まるのは「壊れた送り手が同じアドレスから撃ち続ける」形だけ。** 送信元アドレスは
詐称できるので、これは悪意ある相手を止める仕組みではない。名前や MAC の許可制にしないのも
同じ理由で、設置のたびに書き換える運用になるのに詐称した相手には効かない。**守っているのは
「1 つの送り手の暴走で受け手全体が潰れないこと」。**

覚えられる送信元の数にも上限（64）があり、達したら最も古い枠を捨てる。**数える側とは逆向き**
——あちらは合計を守るために合算するが、こちらは**正規の基板を落とさない**ことを守る。
新しい相手を断る作りにすると、詐称した相手で枠を埋めるだけで本物の基板を締め出せてしまう。

### 基板へ「届いた」と返す

**基板は送る側なので、自分の送信が届いているかを自分では知れない。** ESP32 は Wi-Fi が
切れて戻ったあと、ソケットが無効なまま「送れた」と言い続けることがある（2026-09-30 に
1 枚が 5 日間その状態だった）。そこで、読み取れたパケットのヘッダに `"ack":1` があれば、
**送り元のアドレスとポートへ `seismo-ack <MAC>` の 1 行を返す。** 返事が途絶えたときに
基板がどう立て直すかは [`firmware/README.md`](../firmware/README.md)「届いたかをホストに訊く」。

**その基板の分に取り戻し待ちの欠けがあれば、行の末尾へ ` gap=<センサー>:<番号>,…` を付ける**
（センサーごとの、いちばん古い欠けの始まり。下記「届かなかった分を基板へ取りに行く」の帳面から引く）。基板はこれを見て、
返事が途絶えていなくても送った分をフラッシュへ書き出し始める。電子レンジのような干渉では
返事がまばらに届くので、基板の「8 秒途絶えた」が立たず、取りに行く前にメモリの輪（約 30 秒）
から消えていた（2026-10-06、取り戻せたのは約 14%）。欠けを知っているのはホストだけなので、こちらから言う。

- **見つけた直後から載せる**（取りに行くまでの待ちの間も）。遅れて届いただけなら次の返事で消える
- **いまの起動の分だけ載せる。** 前の起動の分は基板のメモリの輪にもう無い
- **諦める年齢（20 分）を過ぎた欠けは載せない**
- 名前が英数字・`-`・`_` だけでできていない（16 文字を超える）センサーは載せず、載せるのは 4 件まで（基板の受け取りの入れ物に収める）
- **欠けを引き出せなくても `gap=` 無しで返す**（返事を止めると基板が立て直しを始める）
- **`gap=` を読めるのは、`gap=` を読むファーム（`seismo-node.ino` の `parseGapField` を持つ版）から。** 古いファームは行を 1 文字違わず照合するので、
  `gap=` 付きの返事を受けると返事が途絶えたと取り違える。**配るときは基板を先に焼く**

- **返すのは読み取りに成功したものだけ。** 読めなかったものに返すと、基板は「届いた」と
  思い込んだまま壊れた形を送り続ける
- **読み取れた直後に返す。** 震度や区間の処理より前に置いてあるので、そちらが例外を
  投げても返事は出る —— 後ろに置くと、ホストの不具合を基板が「送れていない」と取り違えて
  繋ぎ直しと再起動を始める。**欠けの帳面への記録（下記「届かなかった分を基板へ取りに行く」）だけは返事より先に置く** —— そのパケットで
  見つかった欠けを、同じ回の返事の `gap=` に載せるため。帳面への記録は数と範囲を覚えるだけで投げない
- **求めていない送り手には返さない**（`ack` の欄が無い古いファーム・版 1）。返事を読まない
  相手へ投げても、向こうの受信バッファに溜まるだけ
- **基板ごとに 1 秒に 1 回まで。** 1 台が 1 秒に 10 パケット前後を送るので、1 件ずつ返すと
  同じ数の返事を撒くことになる。基板が立て直しを始めるのは 15 秒返事が無いときなので、
  1 秒に 1 回でも桁が 1 つ以上余る
- **受けたのと同じソケットから返す。** 基板は送るのに使ったソケットでしか返事を待たない
  （送り元のポートは基板が開き直すたびに変わる）
- **返せなかったら数えるだけ**で、受信は止めない。数は `GET /status` の `acks` に出る。
  このうち `failures` だけは、毎分の要約の「基板へ返事を返せず」にも出る
  - `sent` / `failures` / `throttled` / `lastError` —— 返せた数・返せなかった数・間隔の内側で返さなかった数（多いのが正常）・最後の失敗の理由
  - `withGaps` —— `sent` のうち `gap=` を載せて返せた数。干渉の間に増えていれば、基板へ書き出しを頼めている
  - `gapLookupFailures` —— 欠けの帳面を引く処理そのものが失敗し、`gap=` 無しで返した回数（**0 のままが正常**）
  - `gapEntriesRejected` —— 名前や番号が載せられない形だったので外した欠けの数（**0 のままが正常**。増えていればその欠けは基板へ知らされていない）
- **速度の上限（前節）で落としたパケットには返さない**（読む前に落とすので、返事を
  求めているかも分からない）。1 台が上限に張り付くと、その基板は返事の途絶と読んで
  立て直しを始める。上限は普段の 10 倍に置いてあるので、張り付くのは送り手が暴走した
  ときだけ —— そのときは基板の立て直し（再起動を含む）がむしろ効く側に回る。
  **どちらが起きたかは別々の場所に出る**ので、基板の `ack_level` が上がっていたら
  ホストの `tally.sources` の `rateLimited` も見ること

**診断のために返事を止められる。** `SEISMO_ACK=off` で起動すると 1 つも返さない
（`acks.enabled` が `false` になり、起動時に警告が 1 行出る）。**基板が立て直しの段を
上げるかを、実機で確かめるためのもの** —— 止めている間、返事を受けたことのある基板は
15 秒ごとに UDP の作り直し → Wi-Fi の繋ぎ直し → 再起動と進む。`on` / `off` 以外の値では
起動しない（打ち間違えたまま返事が出続けると、「止めたのに段が上がらない」を基板の
不具合として追いかけることになる）。

### 割り当てた基板が届いていないことを知らせる

**来ないパケットは、どこにも数えられない。** 数え上げも間引きの行も、届いたものから
作るので、基板が黙ると何も起きないだけになる。センサーの生存（`GET /status` の `sensors[]`）も
**一度でも届いたセンサーしか載らない**ので、ホストを起動してから一度も届かない基板は
一覧に現れず、管理コンソールのカードも「受信中のセンサー 3 / 3」と全部生きているように見える。
基板は時計が合うまで 1 件も送らない（[`firmware/README.md`](../firmware/README.md)「時計が合う前は送らない」）ので、
SNTP に届かない基板はまさにこの形になる。

そこで、**観測点の設定に割り当てた基板（「来るはずのもの」）と、実際に届いたものを突き合わせる**
（`src/receiver/assignedReception.ts`）。

| 様子 | いつ |
|---|---|
| `live` | 60 秒以内にどれかのセンサーから届いている |
| `silent` | 最後に届いてから 60 秒を超えた、または割り当ててから 60 秒を過ぎても一度も届かない |
| `waiting` | 割り当ててからまだ 60 秒経っておらず、一度も届いていない（判断を保留する） |

- **60 秒は管理コンソールの「途絶」の札と同じ値**（同じ定数を読む）。基板が自分で立て直して
  いる最中（返事が 15 秒来ないと段を上げ、最後は再起動する）も、60 秒を超えれば `silent` に出る ——
  そのあいだ実際に黙っているので
- **猶予の起点は「割り当てが設定に現れた時刻」。** 起動時の割り当てはホストの起動から、
  稼働中に管理コンソールで足した基板は足した時刻から数える。足した瞬間に「届いていない」と
  言い出すと、登録のたびに誤報になる
- **設定の `sensors[]` に名前を書いた有効なセンサーは、1 個ずつも見る。** 1 枚の基板に
  3 個ぶら下がっていて 1 個だけ黙ることがあり、基板単位では気づけない。`sensorId` の書き間違いも
  ここに「届いていないセンサー」として出る。**名前を書いていないセンサーと無効にしたセンサーは
  見ない**（何個ぶら下がっているかを設定は約束しないし、壊れて外したものを数え続けても直しようがない）。
  基板そのものの判定には無効化を効かせない
- **センサーを個別に言うのは基板が届いているときだけ。** 基板ごと黙っていれば、その旨の 1 行だけ

**出る場所は 3 つ。**

- **`GET /status` の `assignedBoards`** —— 割り当てた基板を設定の並びで全部（未受信も含む）。
  各行に `state`・最後に届いた時刻・名前を書いたセンサーの様子
- **毎分の要約のあとの警告** —— 基板 1 枚（センサー 1 個）につき 1 行。例:
  `[station] 観測点に割り当てた基板が届いていない: mac:020000000003（観測点 garage・最後に届いてから 95 秒）`。
  黙っている間は**ほぼ毎分**出続ける（間引きの間隔が要約と同じ 60 秒なので、たいていの要約で
  出る。タイマーの揺らぎで 1 回飛ぶことはある）。
  間引きは 1 枚ごとに掛かるので、**新しく黙った基板はほかの基板の様子に関わらずすぐ出る**。
  届くようになったら `[station] 届くようになった: …` を 1 行出す（警告が出なくなったのが
  直ったからだと、行で分かるように）
- **管理コンソールの稼働状況タブ** —— 警告欄と、カード「割り当てた基板 N / M」。警告欄の
  1 枚ぶんの言い回しはログと同じで、複数あれば 1 つの文にまとめて並べる。カードの分母は
  設定に割り当てた基板の数なので、一度も届かない基板もここで欠けて見える。**一度も届いて
  いない基板は、割り当ててから 60 秒経つまで分子に入らず、警告も出ない**（送り続けている
  基板は、ホストを再起動した直後でも届いた時点で分子に入る）

### 基板の時計がずれていることを知らせる

**基板の時計は、合っているように見えて黙ってずれることがある。** 2026-10-01 のファームは
ソフトウェアの再起動のあと時計を合わせ直しておらず（[`firmware/README.md`](../firmware/README.md)
「時計が合う前は送らない」）、3 枚の時計が 22 時間で 0.5〜1.3 秒遅れた。パケットも震度も
出続けたので、**観測点の合成が毎回いちばん遅れた基板を欠くようになるまで気づけなかった**
（合成は顔ぶれが揃うのを**データの時刻**で最大 600 ms 待つので、時計のずれがそのまま待ちを食う）。

そこで、**届いたパケットからホストの側で時計のずれを測る**（`src/receiver/boardClock.ts`）。
受け取った時刻から、パケットの末尾のサンプルが名乗る時刻を引き、**基板ごとに 60 秒の窓で
いちばん小さい値**を取る。基板は FIFO を抜いた瞬間の時刻から逆算して名乗るので、時計が
合っていればこの差は「届くまでの時間」（実機で数〜数十 ms）だけになる。正なら基板が遅れている。
**ホストの時計が合っていることを前提にする**（ずれているのがホストなら、全基板が同じだけ
ずれて見える）。

**100 ms を超えたら知らせる。** 合成の待ちのうち基板どうしの到着差に充ててあるのは 200 ms で、
2 枚が逆向きにずれても収まるよう、その半分を 1 枚あたりの許容にした。**黙った基板は知らせない**
—— そちらは上の「届いていない」が同じ 60 秒の物差しで持つ。

**出る場所は 3 つ。**

- **`GET /status` の `boardClocks`** —— 基板ごとの `offsetMs`（ずれ）・`windowEndMs`（その窓を
  閉じた時刻）・`packets`（窓で測った数）・`lastPacketMs`（最後に受け取った時刻）。
  **その基板が届き始めてから**最初の 60 秒は `offsetMs` が `null`（ホストの起動時刻とは関係しない）
- **毎分の要約のあとの警告** —— 基板 1 枚につき 1 行。例:
  `[clock] mac:020000000001 の時計がホストより 1301 ms 遅れている（許容 100 ms。…）`
- **管理コンソールの稼働状況タブの警告欄** —— 判定はログと同じ。複数あれば 1 つの文にまとめて並べる

### 止まった・落とされたことを残す

**ホストが止まっている間は、ホスト自身は何も書けない。** 2026-10-02 13:41 にはホストと同じ機械で
重い処理（GPU を使う道具の起動）が走り、ホストが約 45 秒止まった。ログには 1 行も残らず、毎分の要約が
「直近 75 秒」と名乗ったことと、番号の飛びから逆算するしかなかった。基板の返事も止まるので、
基板 2 枚は立て直しの段を上げて自分で再起動した。そこで 3 つを置いている。

- **受信バッファを 8 MB へ広げる**（`udpReceiver.ts`）。止まっている間に届いた UDP は OS が
  ここに抱え、あふれた分は黙って捨てられる。既定の 64 KB は基板 3 枚（毎秒約 22 KB）の
  約 3 秒ぶんしか無いが、8 MB なら約 6 分ぶん抱えられ、動き出してから順に処理できる。
  実際の大きさは起動時の `[udp] 受信バッファ …` の行と `GET /status` の `udpRecvBuffer` に出る。
  **OS が小さく抑えたら警告になる**（Linux は `rmem_max` で頭打ちにする）
- **止まった区間を測る**（`loopStall.ts`）。250 ms ごとに刻みを置き、刻みが予定より
  1 秒以上遅れたら、止まり明けに `[stall] ホストの処理が 45.3 秒止まっていた（… に再開）…` を出す。
  回数・累計・最長・直近は `GET /status` の `loopStalls`、この 1 分の回数は毎分の要約の
  「処理が 1 秒以上止まった」に出る。**測るのは単調時計**なので、OS が時刻を合わせ直しただけでは鳴らない
- **稼働の印を置く**（`hostLifeMark.ts`）。起動で `data/host-running.json` を書き、毎分の要約で
  「最後に生きていた時刻」を進め、正常に終わったら消す。**印が残ったまま次に起動したら、
  前回は終了の記録を残せずに止まった**ので、起動時に
  `[host] 前回のホスト（pid …）は終了の記録を残さずに止まっていた（起動 …・最後に生きていたのは …）` を出す。
  `Stop-Process`・PC の再起動（サービスで動かしていない場合）・電源断のいずれでも、止まった時刻を 1 分の幅で絞れる。
  **配り直しで `Stop-Process` を使うと、次の起動では毎回この行が出る**（強制終了なので正しい）

**実機で 50 秒止めて確かめた**（2026-10-02。プロセスを `NtSuspendProcess` で一時停止）。再開した直後に
`[stall] ホストの処理が 50.3 秒止まっていた` が出て、止まりをまたいだ 88 秒の窓で 390 件、次の 60 秒の窓で
1095 件が届いた（どちらも 1 枚あたり。148 秒で約 1480 件 ＝ 毎分 600 件の割合どおり）。番号の飛びは 0、基板は 3 枚とも
再起動しなかった —— 止まっている間の分は受信バッファが抱え、再開後にまとめて処理された。

止まっている間の分は、受信バッファに収まらなかったぶんだけ届かない。届かなかった分は、
次節の仕組みで基板から取り戻す。

### 届かなかった分を基板へ取りに行く

**欠けを知っているのはホストだけ。** 基板は自分の送ったものが届いたかを知らない ——
`endPacket()` は届いていなくても真を返し、ホストの返事は「生きている」を 1 秒に 1 回
知らせるだけで、どのまとまりを受けたかは言わない。そこで基板は送った分を手元に残し
（メモリに直近約 30 秒、返事が 8 秒途絶えている間はフラッシュにも約 11 分。
[`firmware/README.md`](../firmware/README.md)「届かなかった分を残しておく」）、
**ホストが通し番号の欠けを覚えて、基板の `GET /backlog` へ取りに行く。**

- **欠けは流れごとに数える**（`src/receiver/backlogBook.ts`）。流れは「基板 × 起動 ID ×
  センサー」で、基板が再起動すると番号は 0 へ戻るので別の流れになる。区間の組み立て
  （`segmenter.ts`）とは別に数える —— あちらはあふれや時刻の跳びでも区間を切るが、
  こちらが知りたいのは番号の抜けだけ
- **見つけてから 2 秒待って取りに行く。** UDP は順序を保証しないので、入れ替わって遅れて
  届くだけのものを先に待つ。遅れて届けば欠けは埋まり、取りに行かない
- **1 枚の基板には 1 度に 1 件、古い順に訊く**（`src/receiver/backlogFetcher.ts`）。基板は応答を
  作っている間センサーの吸い出しも止まるので、重ねて訊くと待たせる時間が足し算になる。訊く合間は
  基板ごとに 250 ms、1 回の答えは 30 まとまりまで
- **別の基板へは並行して訊く。** 止まるのは答えている基板だけなので、1 枚が時間切れになるのを
  ほかの基板が待つ理由が無い
- **同じセンサーの近い欠けは 1 回で訊く**（900 サンプル＝30 まとまりまで。基板が 1 回に返せる数に
  揃えてある）。干渉では欠けが
  1 まとまりずつ散らばるので、1 件ずつ訊くと取りに行く速さが欠けのできる速さに負ける。間に挟まる
  受信済みのまとまりも基板は返すが、生データへは書かない（同じまとまりを二度入れない）
- **取り戻した分は生データの保存にだけ書く。** 震度・観測点の合成・押し出し・時計のずれの
  推定・速度の上限のどれにも通さない —— どれも「いま届いたもの」を前提に組んであり、
  数十秒〜数分前のまとまりを混ぜると、区間が切れたり時計が遅れて見えたりする。
  **画面に出たものは取り戻せないが、後から読み返す記録は埋まる**。レコードには取り戻した印が
  付く（下記「生のパケットを miniSEED 3 で時間ごとに残す」）。合成波形の控え（`GET /waves`）は、
  取り戻し終えてから生データを読み直して作り直す（下記「取り戻した区間は作り直す」）
- **欠けから外すのは、生データへ書き終えた分だけ。** 取り戻した分は溜めずにまとまりごとに書き、
  ディスクが書き終えたと知らせるまで待つ。書けなかったまとまり（流し口を開けない・書き出しが
  追いつかない・ディスクが一杯や I/O エラーで書き込みが失敗した・3 秒待っても知らせが来ない）は
  欠けに残して、下の間隔で訊き直す。基板がまだ抱えていれば取り直せる。1 まとまりでも書けなければ、
  同じ答えの残りは書かずに欠けへ残す（詰まったディスクへ書き続けても同じく書けない）。届いた分は
  取り直せないので、待たずに溜めてから書く
- **3 秒待ちきれなかった書き込みは、決着するまで次を訊かない。** 待ちきれなくても書き込み自体は
  裏で続くので、訊き直して同じまとまりを書くと、遅れて書き終えた分と生データに 2 度残る。
  遅れて書き終えたら、その時点で欠けから外す。遅れて失敗したら欠けに残り、決着した後で訊き直す。
  **知らせが来ないまま詰まっている間は、全ての基板の取り戻しを止める**（詰まっているのはディスクの
  側なので、別の基板へ訊いても同じく書けない）。止めている間は、待ち始めた時刻を `GET /status` に出し、
  毎分の要約にも `warn` で 1 行出す（下記）。詰まったのが過去の時の本だけなら、届いた分の保存は
  失わないので、ほかの数え上げには現れない
- **終了するときは、待ちきれなかった書き込みをもう 3 秒待つ**（基板ごとにいま訊いている分と合わせて最大 6 秒。並行して訊いているので、基板の数では伸びない）。
  その間に書き終えた分は欠けから外れる。それを過ぎた分は欠けに残ったまま帳面へ書き戻され、次の起動で
  訊き直す（下の「再起動をまたぐ」と同じく、同じまとまりの波形が 2 度入りうる）。このあと生データを
  閉じると新しい書き込みを断るので、遅れて波形を書き終えても受信の記録は書けない
- **取りに行って失敗したら（繋がらない・時間切れ 3 秒・読めない答え・生データへ書けない）、見つけてから
  25 秒の間は 1 秒で訊き直す。** 基板のメモリには直近約 30 秒しか残らないので、待ちを伸ばしている
  うちに上書きされる。**25 秒を過ぎたら、過ぎてからの失敗の数で 5 秒から倍々に、60 秒を上限に空ける**
  （その頃にはフラッシュにしか残っていない）。見つけてから 20 分を過ぎても取り戻せない欠けは諦める ——
  基板が抱えていられるのはそれより短い
- **ホストの再起動をまたぐ。** 欠けと「何番まで受けたか」を `data/backlog-book.json` へ 5 秒ごとと
  終了時に書き、次の起動で読み戻す。ホストが止まっていた間の分こそ取り戻したいのに、止まる前に
  何番まで受けたかを覚えていなければ、起動後の最初のパケットを見ても抜けたのか分からない。
  書く間隔のぶん、持ち越した番号は古いので、**同じまとまりが生データに 2 度入ることがある**
  （中身が同じなので、`bid`・`sid`・`q` の組で見分けられる）
- **基板が再起動して新しい起動 ID が現れたら、前の起動の流れは片付ける。** ただし欠けが
  残っていれば残す（基板はフラッシュに前の起動の分を持っていることがあり、取りに行く先を
  そこから引く）。**時間では忘れない** —— 黙っていた時間で忘れる形にすると、Wi-Fi が長く落ちて
  戻ったとき、その間の欠けを 1 つも見つけられない

**取り戻せなかった理由は 5 つに分けて数える**（手当てが違うので）。

| 理由 | 意味 |
|---|---|
| 基板が再起動していた | 基板が 410 を返した（メモリにもフラッシュにもその起動の分が無い） |
| 基板がもう抱えていない | 基板の輪が上書きした |
| 基板に取り戻しの口が無い | 取り戻しより古いファーム（404）か、輪を確保できなかった基板（503） |
| 何度訊いても答えが無かった | 見つけてから 20 分を過ぎた |
| 欠けが多すぎて古いものから捨てた | 抱える欠けの数が 1 万件を超えた |

**出る場所は 3 つ。**

- **`GET /status` の `backlog`** —— 抱えている欠けの数とサンプル数、取り戻したサンプル数、
  理由ごとの取り戻せなかったサンプル数、訊いた回数、理由ごとの失敗の回数、答えに混ざった
  使えないまとまりの数（読めない・別の流れを名乗る）、生データへ書けずに欠けへ残したまとまりの数
  （`unsavedPackets`）、書き終わりを待っていて取り戻しを止めているならその待ち始めた時刻
  （`unsettledWriteSinceMs`。止めていなければ `null`）
- **1 件ずつの行**（間引きあり）。例:
  `[backlog] mac:020000000001|34b6e78f|i2c0-68 基板から 600 サンプル（20 まとまり）を取り戻した`。
  取り戻せなかった・取りに行けなかった・使えないまとまりが混ざった・生データへ書けなかった、は `warn` で出る
- **毎分の要約** —— 取り戻したサンプル数、理由ごとの取り戻せなかったサンプル数、理由ごとの
  取りに行けなかった回数、使えないまとまりの数、生データへ書けなかったまとまりの数。**諦めた・捨てたは帳面の中で起きて 1 行も
  出ない**ので、ここでしか数えられない。書き終わりを待っていて取り戻しを止めている間は、毎回
  `[backlog] 取り戻したまとまりの書き終わりを待っていて、取り戻しを止めている（N 秒）` を `warn` で出す。
  N は待ち始めてからの経過で、止まっている間は出るたびに伸びる（止まっている間はほかの数が増えないので、
  「取り戻すものが無い」と見分けるための行）

**実機で確かめた**（2026-10-03、基板 3 枚・センサー 9 個）。

- **ホストを 5 分 18 秒止めた**（プロセスを終了し、同じコマンドで起動し直した）。起動し直したホストは
  帳面から 9 本すべての流れの欠け（計 33 万 4624 サンプル・1 本あたり約 6 分ぶん）を見つけ、
  378 回の問い合わせで約 3 分かけて**全部を基板のフラッシュから取り戻した**。取り戻せなかった分・
  取りに行けなかった回数・使えないまとまりはどれも 0。基板が答えている間も、どのセンサーも
  サンプルを落とさなかった（基板自身の状態ページ `http://192.0.2.<41|42|45>/` の `overflow` が 0 のまま。
[`firmware/README.md`](../firmware/README.md)「動いているか見る」）。生データには取り戻した印の付いた
  記録が取り戻した数だけ入った（当時の生データは 1 行 1 パケットの形式で、印は `"via":"backlog"`。
  いまは miniSEED のレコードの拡張ヘッダの `"r":1`）
- **ホストを 50 秒一時停止した**（`NtSuspendProcess`。上記「止まった・落とされたことを残す」と同じ条件を、
  取り戻しの側から見直した）。止まっている間の分は受信バッファが
  すべて抱え、欠けは 0 —— 取りに行くものが無く、届いた分を欠けと取り違えることもなかった。
  基板は 3 枚とも返事の途絶でフラッシュへ書き出し始め、戻ったら止め、再起動しなかった

**前回の帳面を読めなかったら**（形が合わない・権限が無い）、止まっていた間の欠けは取り戻さない
まま始まる。そのことは起動時と毎分の要約のあとに
`[backlog] 前回の欠けの帳面を読めなかった（…）。止まっていた間の欠けは取り戻さない` と出し続ける
（帳面は 5 秒後に今回の中身で書き直されるので、ファイルを見に行っても痕跡は残っていない）。

### 1 件ずつの行は見本、正確な数は表のほう

速度の上限を入れた以上、落ちたパケット 1 つにつき 1 行出す作りのままでは、上限いっぱいで
撃たれたとき毎秒 100 行が流れて他の警告が埋もれる。同じ（相手 × 理由）の行は初回だけ即座に
出し、以後は 60 秒に 1 度まで。**黙らせはしない**し、抑えた件数は次に出す行へ添える。

**枠は出来事の種類ごとに分ける**（種類ごと 64）。1 つの枠を全種類で分け合うと、送信元
アドレスを含む鍵（相手が決める値なので際限なく増える）が枠を食い尽くしたあとに初めて
起きた別種の異常 —— たとえば締めくくりの失敗 —— が共有の溢れ先へ合流して**一度も出ない
まま抑えられる**。いちばん注意が要る場面で、いちばん重要な報せが黙ることになる。
種類ごとに分けておけば「その種類で初めて」は必ず出る。

**溢れたあとは、同じ種類の 2 つ目以降が最大で 60 秒遅れて出る。** そこは受け入れている
—— 溢れた鍵を捨てて作り直す形にすると、捨てた鍵が毎回「初めて」に戻って 1 件ごとに
行が出る。件数そのものは表が常に正確に持つ。

要約は 1 分ごとと終了時。**何も届かなかった時間帯は、続く間 1 度だけ伝える** —— 毎分同じ
空の表を出すと記録が埋まるが、かといって黙ると**基板が全部黙ったことに気づけない**
（画面を持たない常駐プロセスでは、「何も起きていない」と「受信口が死んでいる」を
外から見分けられない）。

**数えたものは、状態の口だけでなく要約にも出す。** `GET /status` は見に来た人にしか
届かないので、そこにしか出ない数は**叩かない運用では再起動まで誰も気づけない**。
押し出しを切った理由のように 1 件ずつその場で記録するものは別として、それ以外
（数として出せなかった計測震度・センサーの生存の枠を捨てた数・切ったことを報せられ
なかった数）は毎分の要約へ載せる。**0 の行は出ないので、平時の見え方は変わらない。**

### 生のパケットを miniSEED 3 で時間ごとに残す

届いたパケットを **miniSEED 3**（FDSN —— 世界の地震観測網の連合 International Federation of Digital
Seismograph Networks —— が定める地震波形の形式）で残す（REQUIREMENTS.md §9）。
置き場所は `seismo-host/data/raw/<日>/raw-<日>T<時>.mseed3`（`SEISMO_RAW_DIR` で変えられる。
**Git には入らない**）。**日本時間の 1 時間に 1 本**で、時刻で頭出しできる —— 「12 時台を見たい」なら
12 時の 1 本だけを読めばよい。日本時間を選んだのは、このリポジトリが既に長期震源カタログで「1 日＝
日本時間の日」と決めているのと、突き合わせる相手（気象庁の電文）も日本時間だから。プロセスの時間帯
設定は読まない（読むと、別の機械へ移した日を境にファイル名だけが黙って 9 時間ずれる）。

**1 本で完結する。** 中身は 3 種類のレコードが届いた順に混ざって並ぶ。

| レコード | 識別子 | 中身 |
|---|---|---|
| 波形 | `FDSN:XX_<MAC の下位 8 桁>_<センサー ID>_H_N_<軸>` | Steim2 で詰めた整数のカウント値 |
| 受信の記録 | `FDSN:XX_<MAC の下位 8 桁>_<センサー ID>_L_O_G` | パケットの区切り・名乗った時刻・受け取った時刻・受付番号（テキスト） |
| ホストの受信の記録 | `FDSN:XX_HOST__L_O_G` | 波形へ入れられなかったパケットを中身ごと、理由つきで（テキスト） |

**書くのは速度の上限の後、読み取りの前。** 前に置くと壊れた送り手 1 台にディスクを埋められ、
後ろに置くと読めなかったパケットが消える。震度の処理より前にも置く —— 後ろだと、そちらで例外が出た
ときに生データが残らない。基板から取り戻した分（上記「届かなかった分を基板へ取りに行く」）も同じ口から
残り、レコードに取り戻した印が付く。

**古くなっても消さない。** 保持の判断は受け手が持たない —— ディスクが埋まる前に人が消す。

#### どの時の本へ入れるか

**波形の時刻で決める。** 基準はパケットの先頭の時刻で、1 つのパケットのサンプルと受信の記録は必ず同じ
時の本に入る —— そのぶん、本の末尾は正時を最大 1 パケット（0.3 秒）越えうる。基板から後で取り戻した分は、
過ぎた時の本を開き直して足す。時計が合う前の値（1970 年を名乗るもの）だけは受け取った時刻の時へ入れ、
レコードに「時刻が疑わしい」の印を立てる。読めなかったパケットは波形の時刻を持たないので、受け取った
時刻の時へ入れる。

#### 受信の記録（`LOG` チャンネル）

**miniSEED の波形だけではパケットごとの事実が残らない。** レコードが持つのは先頭の時刻と公称の刻みだけで、
そこから外挿した時刻は、パケットが名乗る時刻から 10 秒で ±20 ms ずれる（実測）。受け取った時刻も入らない。
そこで、地震計の世界でログに使う `LOG` チャンネルの慣例に倣い、センサーごとにテキストのレコードを並べる。

1 本は 1 つの流れ（届き方 × 起動 × センサー）の続いたパケットをまとめた JSON で、30 秒ぶんか 200 パケット
で切る（受け取ってから 30 秒経っても次が来なければ書き出す）。換算係数・型番・送信元などの固定の値が
変われば切る。パケットごとの値は、1 つ前のパケットからの差分で詰める（素の値で持つと嵩が 3 倍になる）
—— 番号の飛び・サンプル数・名乗った時刻の外挿からのずれ・受け取った時刻の差・受付番号の差・FIFO が
あふれた回数の増え。形は [`src/receiver/receptionLog.ts`](src/receiver/receptionLog.ts) の冒頭。

**受付番号は、ホストがデータグラムを受け付けた順の通し番号**（起動ごとに 0 から）。受け取った時刻は
ミリ秒までなので、同じミリ秒に届いた別のセンサーのパケットの順はそれだけでは決まらない —— そして
観測点の合成はその順でも結果が変わる。読み直す側は「受け取った時刻 → 受付番号」の順で並べれば、
実機が処理した順に戻せる。

**読めなかったパケット**（ヘッダが読めない・識別子を作れない・組み立てが退けた・内部の異常）は、
ホストの受信の記録へ **1 件 1 本**で、受け取った時刻・受付番号・送信元・理由・**中身を丸ごと**残す。
めったに起きず、起きたときは 1 件ずつ中身を見たいので、まとめない。

#### レコードの切り方

**波形は 1 本 512 バイトまで、溜めるのは 5 秒まで**（早いほう）。ほかに、番号の途切れ・刻みの変化・
時計が合う前と後の入れ替わり・正時の境目・名乗る時刻が外挿から 2 サンプルを超えてずれたとき・
隣り合う値の差が Steim2 で詰められないほど大きいとき（30 ビットを超える）にも切る。
**受け取ってから 5 秒経っても次のパケットが来ないときも、溜めた分を書き出す**（基板が黙った・
届くのが疎らなとき。`/status` の `cuts` では `idle`）。
**レコードの先頭時刻は、その頭にあたるパケットが名乗る時刻から取る。**

**取り戻した分と、遅れて届いた分は別のレコードにする。** 基板から後で取り戻した分は、いま届いて
いる分とは番号も時刻も離れている。また、番号がいまの続きより前へ戻るパケット（重なって届いた・
順序が入れ替わって届いた）を同じ並びへ入れると、そこでも次の正しいパケットでも切れてしまう。
どちらも捨てずに、別の並びとして残す。

**取り戻した分は溜めず、まとまりごとにその場で切る**（波形も受信の記録も。`cuts` では `recovered`）。
書き終えたかを 1 まとまりずつ確かめ、書けた分だけを欠けから外すため（上記「届かなかった分を基板へ取りに行く」）。
受信の記録は、そのまとまりの波形を全軸書けたときだけ書く —— 受信の記録だけが残ると、訊き直して
書けた波形とあわせて、読み直したときに同じまとまりが 2 回組み上がる。

**既知の限界: 一部の軸だけ書けて訊き直すと、書けていた軸の波形は 2 本残る**（2026-10-06 承認）。
書き込みの途中でディスクが失敗したときだけ起きる。このホストの読み手は重なった区間を 1 つにまとめるので、
組み上がるパケットは 1 つで中身も変わらない。外の道具（ObsPy など）で開くと、その軸のその区間が
重なって見える。再起動をまたいでまとまりごと 2 度入る形（上記「届かなかった分を基板へ取りに行く」）
より軽いので、書けた軸を覚えておく仕組みは置いていない。

**細かく切っても誤りは増えない。** 1 本ずつが自分の先頭値・末尾値・検査値（CRC-32C）を持ち、
前後に依らず元へ戻せる —— 書きかけで落ちたときに失うのは最後の 1 本だけになる。払う代償は嵩で、
1 本あたり約 100 バイトの見出しが付く（固定部 40・識別子 30・拡張ヘッダ 27 前後）。**強く揺れているほど早くディスクへ出る**（差分が大きいと
1 本に入るサンプルが減る）。

**識別子に観測点は入れない** —— 基板を移した日を境に同じ名前が別の場所を指すようになる。いつどの
観測点にあったかは、観測点の設定（StationXML。下記「観測点・基板・センサー校正の設定」）で引く。
**MAC を名乗らない版 1 の基板のパケットと、ロケーションコードの規則（英数字とハイフン・8 文字まで）に
収まらないセンサー ID のパケットは識別子を作れない**ので、ホストの受信の記録へ中身ごと残す。
そうした基板・センサーは観測点へ割り当てられない（設定の検証が受け付けない）。

**各波形レコードに、起動 ID と先頭サンプルの通し番号を拡張ヘッダとして入れる**（`{"Seismo":{"b":"63c9812e","q":123456}}`。
取り戻した分には `"r":1`、遅れて届いた分には `"l":1`）。受信の記録の番号とレコードのサンプルを、
番号で 1 件ずつ突き合わせられる。

#### 読み直す

[`src/receiver/mseedPacketReader.ts`](src/receiver/mseedPacketReader.ts) が、1 時間の本から届いたパケットを
組み立て直す —— 受信の記録の差分を足し直し、パケットの番号の範囲を波形から切り出す。**合わないものは
黙って捨てない**: 受信の記録にあるのにサンプルが揃わないパケット、読めない受信の記録、起動 ID と番号を
読めない波形のレコード、どのパケットにも属さないサンプル（落ちて最後の受信の記録を書けなかった区間 ——
区切りは戻せないが、波形そのものは失っていない）を数えて返す。検査値の合わないレコードは採らずに数え、その先を読み続ける。評価台（下記「地震検出」の
「評価台」）はこれで実機と同じ順・同じ区切りのパケットを流し直す。

#### 量

hostpc の 10/02 の 1 日ぶん（基板 3 枚・センサー 9 本・258 万パケット）を、この形へ写して測った。

| | 1 日の量 |
|---|---|
| 波形のレコード | 292 MB |
| 受信の記録 | 55 MB |
| 合計 | 347 MB |

書き込みはこれだけで、後から書き直すことはない。波形のレコードは、評価台（下記「地震検出」の「評価台」）
に使う 2026-09-28〜10-03 の 6 日分を同じ形へ写したとき、99.6% が 512 バイトまで埋まって切れていた
（`cuts` の `full`）。

#### 守り

**落ちない・黙らない。** 受信層の本題は震度なので、書けなくなっても落ちない。抱えたまま書き出せていない
量が 1 本 8 MB を超えたら捨てて数え、流し口が壊れたら 5 秒置いて開き直す（詰まったディスクを毎パケット
叩かないため）。2 分書かなかった本は閉じる。**置き場所を作れないときだけは起動しない** —— 黙って保存
せずに走るのがいちばん悪い。基板は送っていて震度も出ていて、生だけが残っていない状態は外から気づけない。

締めくくりでは溜めていた波形（最長 5 秒）と受信の記録（最長 30 秒）を書き出してから閉じる（上限 30 秒）。
**締めくくりが走らない止まり方（強制終了・停電・PC の再起動）では、その分が残らない。**
配り直しのように意図して止めるときは止める口を使う（→「常時動かす機へ配る」）。**`fsync` は掛けていない**
（合成波形の保存と同じ）—— 書いた直後の停電で失いうるのは、OS が書き出していなかった分。

**状態は `/status` の `mseed` に出る。**

| 欄 | 意味 |
|---|---|
| `recordsWritten` | 書き出せた波形のレコードの本数。**増え続けていれば保存が動いている** |
| `packetsLogged` | 受信の記録を書き出せたパケットの数 |
| `unreadableWritten` | 中身ごと残した、波形へ入れられなかったパケットの件数 |
| `lostRecords` | 書き出せずに失ったレコードの本数（流し口が開くのを待っている間に来た分・抱えた量が上限を超えて捨てた分を含む） |
| `writeErrors`・`lastWriteError` | 流し口が壊れた回数と、最後の理由。開き直しの間隔ごとにしか増えないので、失った量は `lostRecords` で見る |
| `badTimes` | どの時の本へ入れるかを時刻から決められなかった件数 |
| `internalErrors`・`lastInternalError` | 組み立て・書き出しで想定外の例外を受け止めた回数（**0 が正常**。受信は止めず、そのパケットは中身ごと残す） |
| `openBooks`・`slowClose` | 開いている本の数と、締めくくりを上限で打ち切ったか |
| `pendingSamples`・`bufferedPackets` | まだレコードにしていないサンプルの数と、受信の記録をまだ書き出していないパケットの数 |
| `cuts` | 波形のレコードを切った理由ごとの本数 |

失った件数・流し口の異常・想定外の例外は毎分の要約にも出る。管理コンソールの「稼働状況」にも出る。

### 状態と押し出しの口

HTTP で開く。`/status`・`/stream` は**読むだけ**、`/api/*` は**設定・履歴・管理操作**
（認証が要る。次の節「`/api/*` の認証」参照）。

```bash
SEISMO_HTTP_PORT=50506 SEISMO_HTTP_ADDRESS=0.0.0.0 npm run seismo-host
```

| 口 | 中身 | 宛先 |
|---|---|---|
| `GET /status` | いまの様子を JSON で | **運用者** |
| `GET /stream` | 計測震度を押し出す（SSE）。`?wave=` で波形も付く（下記） | **地震ビューアー**・**管理コンソール** |
| `GET /waves` | 過ぎた合成波形を時刻の範囲で返す（下記） | **地震ビューアー** |
| `GET /events` | 検出した揺れの記録を時刻の範囲で返す（→「地震検出」） | **地震ビューアー** |
| `GET /quake-intensity` | 地震 1 件ぶんの区間の最大リアルタイム震度と計測震度を返す（下記） | **地震ビューアー** |
| `GET /healthz` | `{"ok":true}` だけを返す。**中身を組み立てない**（ホストの処理が回っているかの確かめ。[`firmware/README.md`](../firmware/README.md)「届いたかをホストに訊く」） | **基板** |
| `/api/*` | 設定・履歴・管理操作（要認証） | **管理コンソール** |

**宛先が違うので口を分けている。** 揺れたかどうかを見に来る人と、機材を運用する人は別で、
機材の様子はビューアーへ出さない。

**波形は頼んだぶんだけ押す。** `?wave=` で粒度を選ぶ。

| `?wave=` | 届く波形 | 通信量 | 宛先 |
|---|---|---|---|
| （付けない） | なし | — | 震度だけを見る端末 |
| `station` | 観測点の合成だけ（`station-wave`） | 毎秒およそ 15 KB | 合成 1 本だけを描く端末 |
| `1`・`all` | センサー単独（`wave`）も | 毎秒およそ 80 KB | センサーごとに見分けたい端末 |

通信量は**実機の実測値**（センサー 9 本・観測点 1 つ）で、台数が変われば変わる。比較のため、
震度は毎秒 2.5 KB 前後。**桁が 2 つ違う**ので、波形だけを選り分ける意味がある。

**知らない値は「なし」として扱う。** `?wave=true` のような打ち間違いが「全部」へ倒れると、
頼んでいない端末へ毎秒 65 KB が流れ出す。**知らない値を受けたことは記録に 1 行残す**ので、
繋いだのに波形が来ないときはログを見ればよい（いま何を受けているかは `GET /status` の
`stream.subscribers[].wave` にも出る）。

**粒度を分けてあるのは、宛先の必要が違うから。** `?wave=1` を使っているのは
**管理コンソールの波形タブ**——センサーごとに据え付けを見分けるのが仕事なので、9 本ぶんが要る。
いっぽう**地震ビューアー側は観測点の合成 1 本**（震度と同じ出どころ）しか描かない予定で、
そこにセンサー単独の 65 KB を流す意味が無い。**受け手が捨てる形では通信量は減らない。**

**`?wave=station` を使うのは地震ビューアー**（#261 段 4 で実装済み。地図の下端に合成波形を描く）。

**センサー単独の波形（`wave`）は、地面の 3 成分を解けるかで形が 2 つある**（2 本の軸からは
東・北・上の 3 成分が決まらない）。 3 軸のセンサーは
`gal` に東・北・上の 3 本を載せる。2 軸のセンサーは `gal` を `null` にし、`axes` に軸ごとの
**測る向き**（地面で見た長さ 1 の向き `direction`）とその向きの値（`gal`）を `channels` と同じ並びで
載せる。3 軸のセンサーへ両方を載せないのは、同じ情報で通信量が倍になるため。

**観測点の合成（`station-wave`）の `gal`・`dcGal` には、成分ごとに `null` が混ざりうる。** 有効な
センサーの測る向きが 3 方向へ散っていない間、解けない成分だけを欠けにして残りを出す
（→「複数センサーの波形合成（§7）」の「軸を 1 本ずつの観測として解く」）。受け手は `null` を
「その成分の値が無い」として扱い、まとまりごと捨てない。

**センサー対の差分はこの梯子の外にある。** `?diffStation=` ほか 5 欄で頼んだ 1 組だけが届き、
**毎秒およそ 7 KB**（同じ実機の実測）。全ペアは 36 組あるので、まとめて流せば
**毎秒およそ 240 KB** —— 梯子へ載せず 1 組ずつ選ばせているのはこのため
（→「複数センサーの波形合成（§7）」）。

**センサーごとのずれ（`station-residual`）も梯子の外にある。** `?residualStation=` ほか 3 欄で
頼んだ 1 台だけへ届く。中身は 1 台ぶんの軸の値と測る向きなので、差分の 1 組と同じ桁と見込んでいるが、
実機ではまだ測っていない。

**通信量の数字はこの節が単一情報源。** 他の節とコード内のコメントはここを参照する。

配るのは計測震度がまさに食べたサンプルそのもの（換算済み・校正済み。
校正の適用順は「観測点・基板・センサー校正の設定」を見ること）で、
**生のカウント値は配らない** —— 受け手が換算し直す形にすると換算の経路が 2 本になり、
片方だけずれても画面では気づけない。

**溜めない。** 受け手が遅ければそのぶんは捨てて数える。送り手（基板）はこちらの都合で
止まってくれないので、溜める作りはメモリが膨らむ方向にしか倒れない。詰まったままの購読は
30 秒で切る（生データの締めくくりに掛かる上限とは別のもの）—— **測るのは経過時間で、捨てた件数ではない**（震度は購読の種類に
よらず毎秒 9 件が流れ、センサー単独の波形を取る購読にはそこへ毎秒 33 件が積まれる。件数で切ると同じ「30 秒」が
購読の種類で 4 倍以上ずれる）。

**`/status`・`/stream` の横断の許しは `*` で開いている。** 読み取り専用で、出るのは家の揺れの
計測震度と機材の健全性だけ。繋ぎ先（配信中のページ・開発用のサーバー・別の端末のブラウザ）は
増えるので、列挙する形にすると増えるたびにこちら側を書き換える運用になる。**`/api/*` は
書き込みを伴うので事情が違い、次の節のとおり Origin を列挙する。**

**`SEISMO_HTTP_PORT` も打ち間違えた値では起動しない。** 受信口と同じ理由で、黙って既定へ
倒すと「別のポートで待ち受けている」状態が画面にも記録にも現れない。

### 過ぎた合成波形を読み返す（`GET /waves`）

**押し出しは「いま」しか運ばない。** 繋ぐ前のぶんも、切れていた間のぶんも流れてこない。
時刻の範囲を指定して後から取れる口がこれ。

```
GET /waves?station=<観測点ID>&from=<unix ミリ秒>&to=<unix ミリ秒>[&columns=<列数>]
```

| 引数 | |
|---|---|
| `station` | 観測点の識別子（観測点の設定の `stationId`）。必須 |
| `from`・`to` | 範囲（unix ミリ秒の 10 進整数）。必須 |
| `columns` | 指定すると**列ごとの上下の端**へ落として返す。省くとサンプルのまま |

**範囲には上限がある。** 列で返すなら **10 分**、サンプルのままなら **2 分**。
この口は認証を持たない（下記）ので、ここが唯一の歯止め —— 上限が無いと 1 回の
問い合わせでディスクを何時間ぶんも舐めさせられる。サンプルのほうが狭いのは、
10 分ぶんを素で返すと JSON が数 MB になるため。

**落とすのはこちらの仕事。** 10 分ぶんの生の値は 3 軸で 18 万個あり、描く側が使うのは
列ごとの上下だけ。送ってから捨てる形は通信量が丸ごと無駄になる。**点は間引かない** ——
「n 個おきに 1 点」にすると、いちばん見たいピークが確率的に消える。

**応答には「読めなかった量」を必ず添える**（`skippedBytes`・`filesMissing`・`filesFailed`）。
これが無いと、受け手からは**揺れていなかったのか記録が無いのかが同じ空の配列に見える**。
サンプルのまま返すときは、**数でない値（JSON では `null`）が届かなかった区間**を表す ——
埋めない（埋めるとそこだけ時間の縮んだ絵になる）。

**`/status`・`/stream` と同じく認証を持たない。** 宛先は地震ビューアーで、あちらは管理用の
トークンを持たない（持たせるべきでもない）。出るのは `/stream` が既に押し出しているのと
同じ合成波形なので、公開の程度は変わらない —— 違うのは「過去をまとめて取れる」ことだけ。

#### 置き場所と入れ物

| | 生データ（`data/raw/`） | 合成波形（`data/wave/`） |
|---|---|---|
| 中身 | 届いたパケットの波形と受信の記録（miniSEED 3） | 観測点ぶんの合成波形（`station-wave` と同じもの） |
| 切り方 | 時ごと | **時ごと** |
| 圧縮 | 波形は Steim2 で詰める（その外側では圧縮しない） | **しない** |
| 量（1 日） | 約 347 MB（センサー 9 本） | 観測点 1 つあたり約 120 MB（見積もり） |
| 読み返し | 口は無い | `GET /waves` |

生データの量は実機の 1 日ぶんを写して測ったもの（前節「量」）。合成波形は**見積もり** —— 3 軸 × 100 Hz ×
4 バイトに効いた本数の 1 バイトを足した嵩から。

**ファイル名が索引を兼ねる**（`wave-<観測点>-YYYY-MM-DDTHH.bin`。日本時間の時）。1 本 5 MB 弱
なので、問い合わせの範囲に触れるファイルだけを頭から走査すれば足りる。別に索引ファイルを
持つと、そこが指すバイト位置と実際に書けた量がずれる形（プロセスが落ちた・書き出しが詰まった）を
抱え込む。**圧縮しないのは、すると頭出しができなくなるから** —— この入れ物は `GET /waves` から
読み返されるために在る。

**まとまりはそのまま並べる。** 合成は観測点の目盛り（10 ms 固定・位置は絶対時刻）の上で
作ってある（下記「複数センサーの波形合成（§7）」）ので、届いたまま並べれば目盛りに乗る。
**入れ物の側で格子へ割り付け直さない** —— 割り付けの規則が 2 か所に分かれると、片方だけ
変えたときに偽の欠測が出る。

**消さない**（生データと同じ約束。ディスクが埋まる前に人が消す）。

**残さないものがある。** 目盛りの通し番号（`firstSampleIndex`）—— 時刻から引けるので、
波形を描くのに要らない。直流（重力）は**まとまりごとに 1 組の平均**だけ残す
（100 Hz で動くものではないので、0.3 秒の粒度で足りる。毎サンプル持つと入れ物が倍近くになる）。

**保存が動いているかは `/status` の `waveArchive` を見る。** `written` が増えていれば残っている。
`lostRecords`（書き損ね。**流し口を開けていない間に来たぶんも含む**）・`badChunks`（形にできず
捨てた）は別に数える —— 前者はディスクの話、後者は合成の側の話で、手当てが違う。
流し口が壊れた回数（`writeErrors`）は**開き直しの間隔ごとにしか増えない**ので、
失われた量は `lostRecords` のほうで見ること。

#### 取り戻した区間は作り直す

**ライブの合成には、取り戻した分が入っていない**（上記「届かなかった分を基板へ取りに行く」）。
そのままだと、干渉で欠けた区間の合成波形は効いたセンサーが減ったまま（または途切れたまま）控えに残る。
そこで取り戻した区間を観測点ごとに覚えておき、**生データを読み直して合成を作り直し、控えへ足す**
（`src/receiver/rewaveScheduler.ts`・`rewaveRunner.ts`・`stationRewave.ts`）。

- **いつ作り直すか。** 最後に取り戻してから 3 秒経ったら。干渉の最中は取り戻しが続けて届くので、それを
  1 件へまとめる。**取り戻しが続いて落ち着かなくても、最初に取り戻してから 10 秒で作り直す**。取り戻した
  範囲の前後には 2 秒の余白を足す
  - **観測点にまだ欠けが残っていても待たない**（2026-10-07 ユーザー承認）。以前は欠けが全部片付くまで最長 2 分
    待っていたが、電子レンジの干渉の最中は欠けが片付かず、合間に取り戻せた区間まで知らせが遅れて（2026-10-07 の
    試験で 1〜2 分）、PWA の下部の波形（直近 60 秒）から穴が先に流れ出ていた
  - 欠けの残る区間を先に作り直しても困らない。作り直しはライブの合成より劣らず（受け取った分と取り戻した分の
    両方から組む）、後でその欠けを取り戻せばその区間はもう一度作り直されて、読み返しは後から書いた方を採る
- **1 件は 3 分まで。** それより長い区間は頭から 3 分ずつ区切って順に回す。作り直しは 1 度に 1 件
- **作り方はライブと同じ部品で。** 区間の 60 秒前から 5 秒後までの生データ（ライブで届いた分・
  取り戻した分の両方）をデータの時刻の順に並べ、新しく作った補正と合成の部品へ流す。60 秒前から
  流すのは、直流（重力）の推定が 20 秒の窓を持つので、その 3 倍流して落ち着かせるため。ライブの合成の状態には触らない
- **設定はその区間の当時のものを使う。** 観測点の設定ファイル（`stations.xml`）の履歴から引く。
  起動の記録は設定を変えないので、ホストの再起動をまたいだ区間（止めていた間の欠け）も作り直せる
- **作り直した分には印を付けて足す。** 読み返しは、作り直した分と重なるライブの分を
  サンプル単位で削って返す（作り直し同士なら後から書いたほうを採る）。ライブの分はファイルからは消さず、
  読み返しの応答に出さないだけ
- **受信を止めない。** 3 分ぶん（9 センサー）を流すと手元の機械で 1 秒前後かかるので、256 パケットごとに
  受信へ順番を譲る
- **控えへ足し終えたら押し出しで知らせる**（`station-wave-revised`。作り直した範囲だけで、波形は載せない）。
  合成波形を頼んでいる相手（PWA の下部の波形・地震カード）が、自分の抱えている穴と重なるときだけ
  `GET /waves` を取り直す。一部のまとまりを書けなかったとき（下の表の「控えへ書けなかった分があった」）も
  知らせる —— 書けた分があれば、知らせないと受け手はそれを取りに来ない（書けた分が無くても、受け手が 1 度
  取り直して何も変わらないだけで済む）

**作り直さないとき**（理由ごとに数える）。

| 理由 | 意味 |
|---|---|
| 区間の中で観測点の設定が変わった | 区間の 60 秒前から 5 秒後までの間に設定を変えていた（変えて元へ戻した場合も含む）。合成の顔ぶれと重みは設定で決まり、1 回の作り直しでは 1 つの設定しか使えない |
| 観測点の設定の履歴を読めていない | 設定ファイルを読めずに空の設定で動いている（起動時に警告が出ている）。いまの設定で代わりに作ることはしない |
| 生データを書き終えられなかった | 書き手が溜めていた分を吐き出せなかった。欠けたまま作り直すと、ライブより欠けの多い波形でライブを覆ってしまう |
| 区間の生データが無い | その時間の生データのファイルが無い・読めない |
| 作り直した合成が無かった | 流しても区間に掛かる合成が 1 つも出なかった（センサーが 2 台に満たない等） |
| 控えへ書けなかった分があった | 作り直した分の一部を書けなかった |
| 作り直しの途中で想定外の例外が出た | こちらの不具合 |

**目盛りの位置はライブと一致する。** 合成は観測点の目盛り（絶対時刻で決まる 10 ms 刻み）の上で
作るので、作り直したまとまりの境目と目盛りは、ライブのものと同じ時刻に立つ（以前は駆動役の区間の
当てはめが刻みを決めていて、作り直すと継ぎ目が最大 ±5 ms ずれた）。**値はわずかに動きうる** ——
センサーごとの時間軸は区間の頭からの全アンカーで直線を当てはめるので、何時間も続いたライブの区間と
60 秒前から当てはめた作り直しとでは傾きがわずかに違い、目盛りの時刻へ補間する値もその分ずれる。

**出る場所は 3 つ。**

- **`GET /status` の `rewave`** —— 作り直しを待っている観測点の数（`waiting`）、いま作り直しているか
  （`running`）、作り直した件数（`jobs`）と足したまとまりの数（`chunks`）、作り直しで読んだ生データの
  壊れ（CRC が合わない・復号できない・中身を読めない記録）の数（`rawIssues`）、理由ごとの作り直さなかった
  件数（`skipped`）。併せて `waveArchive` の `revisedWritten`・`revisedLost` が、作り直した分を控えへ
  書けた数と書けなかった数
- **1 件ずつの行**（間引きあり）。例:
  `[rewave] station-1 の 21:44:00〜21:45:05 の合成波形を作り直した（14 まとまり・812 ms）`。
  作り直さなかったもの、読んだ生データに壊れがあったもの（作り直した分にもその欠けが残る）は `warn` で出る
- **毎分の要約** —— 作り直した件数、足したまとまりの数、読んだ生データの壊れの数、理由ごとの作り直さなかった件数

### 地震の区間の震度を返す（`GET /quake-intensity`）

地震カードに出す 2 つの震度を、`GET /waves` と同じ合成波形の控えから出す
（計算は `src/receiver/quakeIntensity.ts`、式はアプリと共有の `src/utils/knet/`）。

```
GET /quake-intensity?station=<観測点ID>&from=<unix ミリ秒>&to=<unix ミリ秒>
```

| 返す値 | |
|---|---|
| `maxRealtime`・`maxRealtimeAtMs` | 区間の中で出た最大のリアルタイム震度（押し出しと同じ方式・1 秒刻み）と、その時刻 |
| `realtimeSeries` | 区間の中の 1 秒ごとのリアルタイム震度（`{ atMs, value }` の並び・時刻順）。最大はここから取っている。**途切れた所は補わない**（時刻が飛ぶ）。値が出なかった刻みは `value: null`。地震ビューアーの詳細の窓が「震度の推移」に使う |
| `measured` | 計測震度（気象庁の手順を区間の波形全体へ 1 回当てた値）。出せなければ `null` |
| `measuredUnavailable` | `measured` が `null` の理由。`no-data`（記録が無い）・`gap`（区間の中で途切れている）・`not-covered`（区間の頭か終わりまで記録が無い）・`no-value`（値にならない） |
| `gapCount`・`invalidChunkCount`・`unsolvedChunkCount` | 区間の中の途切れの数と、値が壊れていて捨てたまとまりの数と、観測点の合成で解けなかった成分を含んでいたので捨てたまとまりの数（有効なセンサーの測る向きが 3 方向へ散っていない間に出る。壊れた値とは分けて数える） |
| `filesMissing` ほか | 読めなかった量（`GET /waves` と同じ欄） |

- **範囲は 10 分まで**（`GET /waves` の列と同じ上限・同じ守り）。読むのは区間の **60 秒前**から
  —— リアルタイム震度は直近 60 秒で判定するので、そこから通せば区間の頭も窓が埋まった値になる
- **当時押し出した値と同じになるとは限らない。** 押し出しの計算器は区間（`segmentId`）の頭から通し
  続けたもので、刻みの位置と直流の推定がずれる（合成波形は直流を引いてあるので、ずれは小さい）
- **途切れた波形を繋がない。** 時刻が飛んだところで計算器を作り直し、**区間の中に 1 か所でも途切れが
  あれば計測震度は出さない** —— 欠けた波形から出した値は小さく出るだけで、見た目では気づけない
- **計算は 10 分ぶんで 0.1 秒ほど**（2026-10-04 の実測）。受信のイベントループを止める長さではない
  （FFT を自前の実装にしたのはこのため。`fft-js` では 1 秒を超えていた）

### `/api/*` の認証

**設定の読み書き・履歴・管理操作は、`/status`・`/stream` とは別の守り方をする**
（REQUIREMENTS.md §11・§12）。**tailnet**（Tailscale が作る私設ネットワーク。参加する
端末どうしは Tailscale Serve を介さず直接通信できてしまう）経由でも無認証は不可——
tailnet に参加する他端末・アプリからの攻撃経路は残るため、ネットワーク層の絞り込みだけでは
防げない。トークン・`Host` ヘッダ照合・`Origin` 検査の 3 点を **AND** で見る
（`src/receiver/adminAuth.ts`）。

```bash
SEISMO_ADMIN_TOKEN="$(openssl rand -hex 32)" \
SEISMO_ADMIN_ALLOWED_ORIGINS=https://console.example.ts.net \
npm run seismo-host
```

**この例は `SEISMO_ADMIN_ALLOWED_HOSTS` を省略している**（＝下記の既定値のまま）。
Tailscale Serve 経由でアクセスする構成では、既定値が実際の `Host` ヘッダと一致しない
可能性がある（下記「`SEISMO_ADMIN_ALLOWED_HOSTS` の既定値は推測」を参照）——`host-not-allowed`
（403）に遭遇したら、実際に届いている `Host` の値で明示的に設定すること。

**トークンは高エントロピーな値にする。** `openssl rand -hex 32`（256 ビット）等で生成した
値を使うこと——短い・推測しやすいトークンは、下記の限界（Host・Origin は非ブラウザ攻撃者を
止めない）と重なると、実効的な防御がトークン 1 つに収斂する。

| 環境変数 | 役割 | 未設定時 |
|---|---|---|
| `SEISMO_ADMIN_TOKEN` | 共有トークン。`Authorization: Bearer <token>` で照合する | `/api/*` 自体が無効（`not-configured` で 503） |
| `SEISMO_ADMIN_ALLOWED_HOSTS` | 許可する `Host` ヘッダ（カンマ区切り） | `127.0.0.1:<port>`・`localhost:<port>` |
| `SEISMO_ADMIN_ALLOWED_ORIGINS` | 許可する `Origin`（カンマ区切り） | 空——運用者が明示するまで誰も通さない |

**`SEISMO_ADMIN_ALLOWED_HOSTS` の既定値は推測。** Tailscale Serve がバックエンドへ
プロキシする際、実際の `Host` ヘッダがどう届くかは未確認（REQUIREMENTS.md §13 の実測は
まだ）。実機で確認でき次第、既定値を見直す。それまでは環境変数で運用者が上書きできる。

**Host・Origin はブラウザ経由の攻撃**（CSRF——別サイトに開いたページから、利用者が気づかない
うちに書き込みリクエストを送らせる攻撃／DNS rebinding——外部のドメイン名を後から内部の
IP アドレスへ向け直し、ブラウザに社内・宅内の機器を叩かせる攻撃）**を防ぐもので、tailnet 上の
任意の端末・アプリ（非ブラウザのクライアント）に対しては偽装できてしまう**——`Host`・
`Origin` ヘッダは秘密ではなく、そのまま送り直せば通過する。この構成での実効的な防御は
**トークンだけ**だと理解しておくこと。3 点を見る理由は、tailnet を経由していても正規の
入口（想定した Host・Origin）を通らないアクセスを機械的に減らすため——完全な防御ではなく、
1 つの層が破られても即座に総当たりが成立しないための多層防御。判定順序も Origin・Host を
先に見てトークンを最後にする形にしてある——トークンの正誤だけを他の条件と切り離して
確認できる仕組みにしないため。

**認証に失敗したアクセスは記録へ出す**（`[admin] /api/* を拒否した（<理由>）`）。
`/status`・`/stream` の購読上限と同じ理由——見に来ない運用では、記録に出ない限り
総当たり・スキャンが進んでいても気づけない。**ただし理由が同じ失敗が続くと間引かれる**
（`src/receiver/logThrottle.ts`。既定は 60 秒に 1 回、抑制した件数を添えて再掲する）——
総当たりの最中でも新しい 1 行が必ず 60 秒以内に出るとは限らないが、抑制件数自体は失われない。

**認証の門を通ったあとに応じるのは、観測点・基板の設定と静止窓（次項）、止める合図（その次）だけ。** REQUIREMENTS.md §11
が挙げる残り 6 項目のうち、**サンプリング・フィルタは処理そのもの（§4・§5）は既に動いている
が、値を外から調整する設定口がまだ無い**。**STA/LTA・イベント検出の閾値・保存設定も同じで、
地震検出・イベント保存（→「地震検出」）は動いているが値はコードの定数**。通知設定は通知そのものが
無い。どれも書き込み口は無く、それ以外の経路は 404 を返す。

### `/api/stations`・`/api/boards`（観測点・基板の設定の読み書き）

管理コンソールから観測点（設置場所）・基板（MAC）の割り当てを読み書きする。
書き込みは**保存と同時に実行中のホストへ即座に反映される**——再起動は要らない
（設定ファイルを直接編集した場合との違いは下記「設定ファイルは StationXML 1 本」参照）。

| 口 | 中身 |
|---|---|
| `GET /api/stations` | 観測点の一覧。`{ stations: StationInfo[] }` |
| `PUT /api/stations/:stationId` | 観測点を作成・更新する（upsert）。ボディは `{ displayName, lat, lon }` |
| `DELETE /api/stations/:stationId` | 観測点を削除する。基板が割り当て済みなら `409 station-in-use` で拒む |
| `GET /api/boards` | 基板（観測点への割当・センサー校正値）の一覧。`{ boards: BoardEntry[] }` |
| `PUT /api/boards/:boardKey` | 基板を作成・更新する（upsert）。ボディは `{ stationId, sensors }`（下記「観測点・基板・センサー校正の設定」節の `sensors[]` 形式）。`stationId` が存在しなければ `400` |
| `DELETE /api/boards/:boardKey` | 基板の割当と校正値（`sensors[]`）を丸ごと削除する（観測点自体は消さない） |
| `GET /api/rest-windows` | センサーごとの静止窓（直近 30 分・校正前の軸ごとの平均とばらつき。`meanGal`・`sdGal` の本数はそのセンサーの軸の本数で、2 軸のセンサーなら 2 本）。`{ sensors: [{ boardKey, sensorId, stillSinceMs, windows: [{ fromMs, atMs, streamKey, sampleCount, meanGal, sdGal }] }] }`。`fromMs`・`atMs` は窓の始まりと終わり（続けて閉じた窓は前の窓の `atMs` から始まる）。`windows` は 6 面法と「鉛直を合わせる」の材料（下記「軸の向き・倍率・ゼロ点は 6 面で測る」「基板の傾き」）。`stillSinceMs` はいまの置き方で静止し始めた時刻（いま静止していなければ `null`）で、「鉛直を合わせる」だけが使う |

**`:stationId`・`:boardKey` は URL パスの値を正とする。** ボディに同名のフィールドが
入っていても無視する——URL が指す資源を書き換えるという REST の前提に合わせている。

**`PUT /api/boards/:boardKey` は全置換であって部分更新ではない。** 既存の基板を更新する
つもりでボディに `sensors` を含めずに送ると、その基板が持っていた校正値
（軸ごとの `vector`・`offset` と `noiseDensity`）は黙って空配列に置き換わる。`orientation`（基板の向き）を
省いたときは単位行列へ戻る——
更新するときは現在の値を含めて送ること（現在の値は `GET /api/boards` で読める）。

**書き込みはすべて `parseStationConfig`（下記「観測点・基板・センサー校正の設定」節の
検証ロジック）を通してから保存する。** 検証に失敗したら `400 invalid-config` を返し、
ディスクにも実行中の状態にも触れない。

### `POST /api/shutdown`（止める合図）

締めくくり（残りの震度を出し、生データ・miniSEED・合成波形・揺れの記録を書き出して閉じる。
全段と順序は `main.ts` の `closeHostCore`）を走らせてから、ホストが自分で終わる。**Windows で手で止めるなら、この口を使う** ——
`Stop-Process` も `process.kill` も SIGINT のハンドラを呼ばずに落とす。もう 1 つの経路はホストのコンソールへ
Ctrl+C を送ること（サービスとして動かしたときに WinSW がこれをする。→「Windows で常駐させる」）。

| 答え | 意味 |
|---|---|
| `202 {"status":"closing"}` | 締めくくりを始めた（始まるのは答えを返した後） |
| `202 {"status":"already-closing"}` | もう締めくくりの途中。2 度目は走らせない |
| `503 {"error":"not-ready"}` | 起動の途中で、まだ止める段取りが揃っていない |
| `405` | POST 以外。**GET では止めない**（リンクを開いただけ・先読みされただけで止まらないように） |
| 応答なし（繋がらない） | 締めくくりが進んで状態の口がもう閉じた。プロセスは終わったか、まもなく終わる |

**初めて受け付けたときだけ** `[admin] 止める合図を受けた（POST /api/shutdown）。締めくくりを始める`
をログへ書く（2 度目は `already-closing` を返すだけで、行は増えない）。終わりは `[host] 正常に終了した`。**次の起動が「終了の記録を残さずに止まっていた」と書いたら、この口を
通らずに落ちた**（→「止まった・落とされたことを残す」）。

### 管理コンソール本体（`GET /admin`）

`/api/stations`・`/api/boards`・`/status` を叩くブラウザ向けの画面（#313 段 C）。
バニラ TypeScript（`src/admin/`）を esbuild でバンドルし、ホストの起動時に一度だけ
メモリ上でビルドする（`src/receiver/adminConsoleAssets.ts`）——ディスクへは書き出さない。
起動のたびにソースの最新を配ることになり、成果物を git 管理するか `.gitignore` するかの
判断を丸ごと避けられる。

| 口 | 中身 |
|---|---|
| `GET /admin`・`GET /admin/` | 画面本体（HTML） |
| `GET /admin/app.js` | 画面のロジック（バンドル済み JS） |

**この経路自体は認証を持たない。** 見られても書き込みはできない——観測点・基板の編集は
画面内で管理トークンを入力させ（`localStorage` に保存）、以後の `/api/*` 呼び出しへ
`Authorization: Bearer` として付ける。同一オリジンで配信しているため、
`SEISMO_ADMIN_ALLOWED_ORIGINS` にこの画面のオリジンを別途足す必要は無い。

**同一オリジンの GET は `Origin` ヘッダを省略することがある。** 実機（Chrome）で確認した
——画面内から `fetch('/api/stations')` を呼ぶと、`mode: 'cors'` を指定しても `Origin` が
付かない（CORS 仕様上、同一オリジンのリクエストに `Origin` を要求しないため。偽装では
ない）。`checkAdminAuth`（上記「`/api/*` の認証」・`adminAuth.ts`）は `Origin` が
省略されているとき `Sec-Fetch-Site: same-origin` を代わりに見る——このヘッダはブラウザが
自動で付け、ページの JS からは書き換えられないため、`Origin` を省略した正当な同一オリジン
リクエストであることの証拠になる。**`Origin` が提示されているときは、`Sec-Fetch-Site` の
値によらず従来どおり許可リストと照合する**——迂回の抜け道にはしていない。

**`Sec-Fetch-Site` が Tailscale Serve 経由でも透過されるかは未確認。** 上記の確認は
dev サーバーへの直接アクセスでの実測（`SEISMO_ADMIN_ALLOWED_HOSTS` の既定値の
「未確認」と同種の限界）。リバースプロキシの類は `Sec-` 接頭辞のヘッダを保持しない
ことがあり、Fetch Metadata Request Headers 自体も対応が遅いブラウザ・組み込み
WebView では送信されない。透過されない環境では、管理コンソール自身が `/api/*` を
叩くたびに `origin-not-allowed` で失敗し続ける——実機（Tailscale Serve 経由）で
確認でき次第、この節を更新する。

**`/api/*` を試すときは、ページを開いた中から叩くこと。** 上の判定（`Origin` が
省略されたら `Sec-Fetch-Site` を見る）はブラウザがヘッダを付けることに乗っているので、
**ページに紐付かない HTTP クライアントからは 403 `origin-not-allowed` になる**。

| 叩き方 | 結果 |
|---|---|
| ブラウザでページを開いて、その中の `fetch` | 200 |
| ページを介さない HTTP クライアント（`curl`・Playwright の `request` 等） | 403 `origin-not-allowed` |

**自動化したブラウザでも通る**（上記のとおり自動化の有無は無関係）。Playwright の
Chromium で `/admin` を開き `page.evaluate(() => fetch('/api/stations', ...))` を
実行して 200 を確認した。人が開く Chrome でも同じ（実機で観測点タブの一覧が出た）。

> **403 の意味は狭い。** `Origin`・`Host` が噛み合っていないことだけを言っていて、
> **許可リストの設定ミスとも、トークンの正誤とも無関係。**
>
> - `Origin` が省略されたときの分岐は**許可リストを一切参照していない** ——
>   `Sec-Fetch-Site` が無いことだけで断っている。それでも画面には「このオリジンは
>   未許可（`SEISMO_ADMIN_ALLOWED_ORIGINS`）」が出て一覧が空になるので、**設定を
>   間違えたように見える**
> - **トークンは最後に見る**ので、403 の時点では一度も触っていない

`checkAdminAuth` の順序は `Origin`（または `Sec-Fetch-Site`）→ `Host` → トークン
（`adminAuth.ts`）。**この順序は意図的** —— トークンを先に判定すると、`Origin`・`Host` の
正誤に関係なくトークンだけを総当たりできるオラクルになる。

だから**切り分けも同じ順序で**。先に叩き方とヘッダを直し、そのうえで 401 が返るなら
初めてトークンを疑う（`missing-authorization` は未設定か `Bearer <token>` の形式でない・
`invalid-token` は値が違う）。ページを介さないクライアントから試すなら、
`Sec-Fetch-Site` を手で付ければ通る。

```bash
curl -H "Authorization: Bearer $SEISMO_ADMIN_TOKEN" \
     -H "Sec-Fetch-Site: same-origin" \
     http://127.0.0.1:50506/api/stations
```

**画面に含む機能**: 観測点・基板の作成・更新・削除（`/api/stations`・`/api/boards` の
薄いフロントエンド）と、稼働状況（`GET /status` を 5 秒ごとに読んで表示。センサーの
受信状況・観測点合成の震度・生データ保存状況等）、波形、揺れの記録、波形の記録（下記）。

**識別子は手で打たせない。** 打ち間違えても保存は通ってしまい、しかも気づく手掛かりが
残らないため。

- **基板の表は 1 つ。** 「声が届いている基板」（`GET /status` の `sensors[]` を基板単位へ
  畳んだもの）と「設定にある基板」（`/api/boards`）を同じ表に並べる。**分けると同じ基板が
  二度出るうえ、いちばん知りたい状態がどちらからも読めない**——「登録したのに声が届いて
  いない」は、声の一覧には現れず、設定の一覧は受信の様子を持たないため。行には受信の様子と
  割当先の観測点が並び、設定にまだ無い基板には「登録」ボタンが付く
- **「登録」を押すと、その基板が実際に名乗っているセンサー ID のカード**が既定の校正値で
  並ぶ。`sensorId` の取り違えはとくに重い——1 文字違うと校正値が 1 つも効かないまま
  既定値（単位行列・補正なし）で動き続け、`/status` の `calibrationConfigured` が
  `false` になるだけで警告もエラーも出ない
- **候補は `<datalist>` で添え、選択のみ（`<select>`）にはしない。** 基板は電源が入って
  送り始めるまで `/status` に現れないので、選択式にすると現地へ行く前に設定を用意して
  おく運用が潰れる。`/status` を取れなかったときも、候補が出ないだけで編集は続けられる
- **観測点 ID は空いている連番（`station-N`）を提案する。** `stationId` は登録後に変えられず
  （URL パスの値が正）、`PUT` は upsert なので、既にある ID を打つと稼働中の観測点が
  警告なく上書きされる。**一覧を取れていないときは提案しない**——既存を知らないまま
  連番を出すと、まさにその上書きを勧めることになる

**観測点の座標は現在地から入れられる。** ブラウザの位置情報を使い、小数 6 桁
（約 0.1 m）へ丸めて測位の誤差を添える。**使えるのは HTTPS か localhost だけ**で、
このホストはまだ素の HTTP で配信している（§13 の Tailscale Serve は方式を決めただけで
未実装）ため、**tailnet の IP で開いた画面では使えない**——`navigator.geolocation` 自体は
素の HTTP でも生えているので、確かめずにボタンを置くと「押しても何も起きない」だけに
なる。使えない接続ではボタンを押せなくし、URL が原因だと書いて出す。

**校正値は「センサーの軸ごと」と「基板ごと」の 2 段で持つ**（形は下記「観測点・基板・
センサー校正の設定」）。同じ基板に載ったセンサーは後から向きが変わらないので、軸がどの向きを
測るかは基板の座標で書き、地面に対する向き（鉛直・方角）は基板に 1 回だけ合わせる。

**`sensors[]` はセンサーごとのカードで編集する。** 常時表示するのは `sensorId`・`enabled` と、
軸ごとの表（「軸ごとの校正（基板の座標）」）。表は 1 行が軸 1 本で、「向き X・向き Y・向き Z」に
その軸が基板のどの向きを測るか（**長さが倍率** —— 1 gal の揺れで何 gal 読むか）、「ゼロ点（gal）」に
揺れていないときに読む値を入れる。単位を gal にしているのは、`calibration.ts` が換算済みの gal 値から
ゼロ点を引くため。`noiseDensity`（ノイズ密度）は詳細設定として折りたたんでいる。

- **カードの行数は、そのセンサーの軸の本数**（3 軸の MPU6050 なら 3 行、2 軸の IIS2ICLX なら 2 行）。
  基板の一覧で「登録」を押すと、ホストがそのセンサーから受け取った軸の本数（`GET /status` の
  `sensors[].axisCount`）でカードを作る。手で足すときは「3 軸のセンサーを追加」「2 軸のセンサーを
  追加」を使い分ける。**本数がパケットと合わないセンサーは震度も波形も出さない**（下記の設定の節）
- 本数を返さない古いホストに繋いだときは、3 軸として作る

センサーの追加・削除もこの画面から行い、保存時は表示中の全カードを読み直して送る
（`PUT` が全置換であることの手当て。上記「`/api/stations`・`/api/boards`」参照）。
**1 件でも入力が不正なら保存自体が止まる**——一部だけ保存すると、どのセンサーが
実際に保存されたか運用者が見た目から追えなくなるため。軸の向きが解けない形（3 本が 1 つの面に
寄っている・2 本が平行）も保存の前に止める。

**初めて据え付けるときは、先に下の「軸の向き・倍率・ゼロ点は 6 面で測る」を済ませる。** 傾きは
ゼロ点のずれと区別できないので、ゼロ点を入れる前に出した傾きはずれを抱え込む。

**基板の傾きは、静止しているときの重力から自動で出す。** 各センサーのカードには
「取り付けの傾き 15°（重力 980.7 gal・ばらつき 1.4 gal・42 秒前）」のように出る。これは保存済みの
設定で見たホストの診断（下記「換算が正しいかを自分で診る」）で、画面を開いた時点・保存した時点のもの。
カードの上の「基板の向き」で「鉛直を合わせる」を押すと、その傾きを打ち消す向きが基板の向き
（詳細設定の 9 マス。列が基板の X・Y・Z 軸で、東・北・上の成分）へ入る（保存するまでは効かない）。

- **押したときは、その場でホストへ静止窓を取り直して計算する。** 材料は 6 面法と同じ
  校正前の静止窓（`GET /api/rest-windows`）で、そこへ**カードにいま入っている**軸の向きと
  ゼロ点を掛けて重力を出す。だから保存の前でも後でも、何回押しても答えは同じ
  （2 回目は傾き 0°）。ホストが校正を通した後の値を使っていた頃は、その窓を閉じた時点の
  向きとカードのいまの向きが二重に掛かり、続けて押すと向きがずれていった（実機で約 140 度）
- **基板に載ったセンサーのうち、いまの置き方で静止しているものの全部の軸から、最小二乗で一緒に
  解く。** 同じ基板のセンサーは同じ向きで揺れるので、どの軸も同じ重力を測っていて、まとめれば
  1 個ぶんのずれに引きずられない。**2 軸のセンサーも入れる**（2026-10-10 から。1 個では重力の
  3 成分が決まらなくても、ほかの軸と一緒なら解ける —— IIS2ICLX だけの基板はこれでしか合わせられない）。
  3 軸のセンサー 1 個だけの基板では、前と同じ答えになる。静止している軸の向きが 3 方向へ散って
  いなければ押せない（「いまの置き方で静止しているセンサーの軸が 3 方向へ散っていない」と出る。
  散り具合の基準は観測点の合成と同じ）。静止しているのにカードの軸の本数が届いている値の本数と
  合わないセンサーしか無いときは、その本数の食い違いを挙げて押せない
- **読めないカード（打ちかけで ID が空など）が 1 枚でもあれば押せない**（2026-10-10 から）。押したときに
  全部のカードを読むので、飛ばして判じると「押せるのに押すと断られる」になる。ボタンには押したときと
  同じ理由（「2 番目のセンサー: …」）が出る
- **使うのは、いまの置き方で静止し始めてから閉じた窓だけ。** ホストは「いつから続けて
  静止しているか」を軸ごとのばらつきで見ていて（溜めかけの窓も含む）、置き直した直後・
  動かしている最中・波形が途絶えている間はその窓を使わない。置いてから 1 分ほど触らずに
  待てば押せるようになる

- **共通座標は ENU（X＝東・Y＝北・Z＝上）の右手系とする。** REQUIREMENTS.md §16 は
  「地理的な XYZ」としか定めていないので、ここで決めた。**Z が上向き正であることだけが
  本質**で、水平 2 軸の入れ替えは §7 の差分にも §6 の P/S 判定にも効かない
- **方角は手で入れる。空欄なら水平面を一切回さない。** 重力は鉛直まわりの回転について
  何も語らない（どちらを向けて置いても重力ベクトルは同じ）ため、自動では決まらない。
  分からないまま既定値で回すと、合っていた方角を黙って崩すことになる。入れるのは
  **基板の X 軸（軸ごとの表の「向き X」と同じ軸）をどちらへ向けたいか**で、「いまどちらを
  向いているか」ではない —— 実際に回るのはいまの向きとの差だけなので、**同じ値を
  入れ直して押しても動かない**（絶対の角を足す形にすると、押すたびに方角が崩れていく）
- **揺れている間・換算の倍率が合っていない間は提案しない。** 揺れている間はボタンを押せなくし、
  倍率が合っていないときは押したときに理由を出す。とくに倍率が狂っている窓で提案すると、**その狂いを基板の向きへ塗り込む**ことになる
  ——直すべきは軸の向きの長さ（倍率）か、その手前の基板が名乗る分解能。基板の向きは
  **純粋な回転しか受け付けない**ので、倍率のずれはそこへは入れられない
- **単体センサーの計測震度は変わらない。** 震度が見るのは 3 成分の合成の長さなので、
  回しても長さは変わらない。効くのは軸ごとの波形・複数センサーの合成（§7）・P/S 判定（§6）
- **ゼロ点と倍率は 1 つの姿勢からは出せない。** 1 つの姿勢の静止データからは
  未知数 3 に対して拘束が 1 つしか立たないため。下の「軸の向き・倍率・ゼロ点は 6 面で測る」で出す
- **先に 6 面法を済ませてから押す。** 水平軸のゼロ点がずれていると、
  1 つの姿勢ではそれが傾きと区別できず、**ずれを基板の向きへ塗り込む**

**軸の向き・倍率・ゼロ点は 6 面で測る**（6 面法）。基板の向きの欄の「6 面で測る（基板に載った全部の
センサー）」で、**基板に載った全部のセンサーの全部の軸を一緒に解く**（2026-10-10 から。前は 3 軸の
センサーのカードごとにあり、軸どうしを直交と見なしてゼロ点と倍率だけを出していた）。基板の X・Y・Z の
上向き・下向きの 6 方向それぞれで静止した窓を記録できたかが ✓ で並び、その後ろに「姿勢 7／9」のように
置いた姿勢の数と要る数が出る。揃って計算が通ると「6 面の結果を入れる」が押せ、全部のカードの軸の欄へ
向き（長さが倍率）とゼロ点が入る（保存するまで効かない。押せないときの理由は下）。

- **軸は 1 本ずつ自由な向きで解く**（2026-10-10 ユーザー承認）。軸どうしの直角のずれ（MPU6050 で
  ±2%）も、立てたセンサーのステーの角度のずれも、その軸の向きのずれとして出る。REQUIREMENTS.md §16 で
  未決だった「軸どうしの直角のずれまで直すか」は、これで「直す」に決まった。**直角を崩す向きはセンサー
  単体の計測震度もわずかに動かす**（3 成分の合成の長さが変わる）
- **基板の X・Y は、1 個目のセンサーの 1 本目・2 本目の軸**（2026-10-09 ユーザー承認）。全体をどう
  回しても式は同じだけ合うので、1 個目のセンサーの 1 本目を X、2 本目を X・Y の面に置いて決める。
  だから 1 個目のセンサーの 1 本目は X だけ、2 本目は X・Y だけの向きで入る
- **6 面だけでは足りない。違う向きの斜めの置き方が 3 回要る**（軸の本数に依らず 9 姿勢以上）。
  軸を自由に解くと、向きを歪める変換（`g' = T g`・`h' = T⁻ᵀ h`）でも同じだけ合う解が残り、
  6 面（X・Y・Z とその裏返し）はその自由度のうち 3 つしか消せない。たとえば台の辺に立てかけて、
  X と Y の間・Y と Z の間・Z と X の間へそれぞれ 45 度ほど傾けた 3 回。**同じ面の中に偏った斜め**
  （3 回とも Z のまわり、など）では 9 姿勢あっても解けず、「計算できなかった」と出る
- **手順。** 基板を机など固い平らな場所へ持っていき、6 方向と斜め 3 回へ順に置いて、それぞれ
  1 分以上触らない。✓ と姿勢の数は 10 秒ごとに取り直して付く（静止窓は 30 秒ごとに閉じるので、
  置いてから最大 40 秒ほどかかる）。入れて保存したら、元の場所へ据え直して「鉛直を合わせる」を
  押し直す
- **同じ姿勢かどうかは時間の重なりで決める。** センサーごとに途切れずに続いた静止窓を 1 つの
  「静止の続き」にまとめ、全部のセンサーの続きが時間で重なる区間を 1 つの姿勢とする（基板を動かせば
  全部のセンサーの窓が静止と言えなくなるので、続きはそこで切れる）。窓の始まりの時刻（`fromMs`）が
  要るので、この欄を返さない前の版のホストでは「静止窓に始まりの時刻が無い」と出る。同じ面へ置き直した
  姿勢は向きの近さ（25° 以内）で 1 つにまとめて数える。**まとめるのは数えるときだけで、解くときは区間ごとに
  別の姿勢として扱う** —— 値を平均して 1 つにすると、測り終えて据えた場所（＋Z から数度傾いた置き方）と
  ＋Z の面が混ざった実在しない姿勢ができ、ゼロ点が 0.5 gal ほどずれる（残差にはほとんど出ない）。
  ほかのセンサーと同時に静止した置き方が 1 つも無いセンサーがあれば、その名前を挙げて止まる（壊れたセンサーなら、そのカードを外してから測る）
- **2 軸のセンサーだけの基板では、先にカードへ大まかな取り付けの向きを入れる。** 2 軸のセンサーだけ
  では、データの上で鏡に映した解（基板の面に垂直な向きが逆）と区別が付かないので、カードの向きに合う
  側を採る（解き始める値にも使う）。立てて付けたセンサーが既定の向き（X・Y）のままだと向きが 3 方向へ
  散らず、「カードの軸の向きが 3 方向へ散っていない」と出る。3 軸のセンサーがあればチップの軸が
  右手系なので、カードの向きに関わらずそちらで決まる。**2 軸のセンサー 1 個だけの基板では使えない**
  （2 本の向きは 1 つの面にしか散らないので、カードの向きをどう入れても同じ理由で止まる）
- **材料はホストが覚えている直近 30 分の静止窓**（`GET /api/rest-windows`・認証が要る）。
  校正を掛ける**前**の軸ごとの平均で持つので、いまの軸の向き・ゼロ点・基板の向きに
  関わらず同じ値が出る。出る値も「いまの設定を置き換える値」で、上乗せではない。
  覚えはホストを立て直すと消え、センサーが 64 本を超えて古いものが押し出されたときも
  そのセンサーの分が消える（換算の自己診断と同じ上限）
- **静止の判定は軸ごとのばらつきで見る**（どの軸も 5 gal 未満）。換算の自己診断が使う
  3 軸合成のばらつきは、向きを変えても長さが変わらないので、**ゆっくり回している最中の窓も
  静止に見える** —— 2 つの向きが混ざった窓を当てはめに入れないため
- **置き方は数度傾いていてよい。** 姿勢ごとの重力の向きも未知数として「どの姿勢でも長さが 1 g」の
  条件で解くので、置いた向きの傾きはそこへ入る
- **押せないときは理由が出る。** 読めないカードがある（「鉛直を合わせる」と同じく、押したときと同じ理由が
  出る）・面が足りない・姿勢が足りない・ほかのセンサーと同時に静止していない
  センサーがある・カードの軸の本数が届いている値の本数と合わないセンサーがある（カードの本数の打ち間違い）・
  カードの向きが散っていない・計算できない・個体差の幅を超えた値が出た
  （倍率 0.5〜2 倍・ゼロ点 ±490 gal）・姿勢の間で辻褄が合わない（後述の残差が 1 g の 2% を超えた）
- **式が未知数より多ければ検算が付く。** 解いた向きとゼロ点で各姿勢の値を読み直し、実際に読んだ値から
  いちばん離れた量（残差）を出す。3 軸のセンサー 1 個の基板で 9 姿勢ちょうどなら式と未知数が同じ数で
  必ずぴったり解け、「検算なし」になる（10 姿勢目を置けば残差が出る）。軸が多い基板（IIS2ICLX 3 個など）は
  9 姿勢でも余りがあり、残差が出る。同じ面へ置き直した分は姿勢の数には入らないが式は足すので、
  「姿勢 9」でも残差が出ることがある
- **温度による動きは直らない。** ゼロ点は数日で 10〜17 gal 動いていた（実機）

**波形は「波形」タブでその場で見られる**（#313 段 C-6）。押し出しの口（`/stream?wave=1`）へ
繋ぎ、届いた波形を軸ごとに重ねて描く。**見るのは据え付けが正しいかどうか** ——
センサーが生きているか、ノイズはどの程度か、傾きを直した効果が出ているか。
揺れたかどうかを見に来る人向けのリアルタイム画面は地震ビューアー側の担当
（REQUIREMENTS.md §10 が宛先で分けている）。

- **遡れるのは、画面を開いてから受け取った分だけ**（既定で最大 5 分）。**画面にもそう書く** ——
  書かないと、遡れないことが不具合に見える。保存してある過去の波形は「波形の記録」タブで見る（下記）
- **縦軸は軸ごとに「各センサーの平均」を中心に据える。** 校正を通した後も重力は残るので、
  上向き軸は 980 gal 付近が定常値。0 を中心に描くと、**見たい数 gal の揺れが 980 の目盛りに
  埋もれる**。中心はセンサーごと・縦の幅は軸ごとに共通で、こうすると重力の乗り方が違う
  センサーどうしでも波の形を比べられる。**1 本に絞ったときだけ中心の値を数字で出す**
  （実機の 9 本では数字が並んで読めなかった）
- **開いたときに重ねるのは 3 本まで。** 実機は基板 3 枚 × センサー 3 個の 9 本で、
  **全部重ねると真っ黒な塊になって 1 本も読めない**。残りは一覧に並ぶので、印を付けて足す
- **1 列に複数のサンプルが入るときは上下の両端を描く**（平均や単純な間引きではなく）。
  揺れの大きさを見に来た画面で、いちばん見たい一瞬が落ちるため
- **区間が変わった所・時刻が飛んだ所は線で繋がない。** 繋ぐと、欠測が「そこだけ傾いた波形」
  として絵になる
- 操作は、見る幅（5 秒〜5 分。絵の上でのホイールでも段ごとに動く）・追従の停止とスクロール
  （絵を横へ引く）・重ねるセンサーの選び方・縦の幅（自動か固定）。**軸は 3 枚を常に並べる**
  （選んで隠す口は無い）
- **溜めた分が消えたら画面に出す。** 時刻が巻き戻って作り直したとき（基板の入れ替え・
  時計の飛び）と、刻みが細かくて件数の上限に達したとき。黙っていると「開いた直後で
  溜まりが少ない」のと区別が付かない
- **観測点の合成波形（§7）も同じ絵へ重ねられる。** 一覧には「観測点名（合成）」として並び、
  **混ざった本数**が付く（揃っていなければ `8〜9 本` のように幅で出る）。**幅が出ていても警めの色にはしない** —— 起動直後と設定を変えた直後はまだ届いていないセンサーがあるので必ず幅が出るし、**どこからが異常かの物差しは未設計**（[`REQUIREMENTS.md`](REQUIREMENTS.md) §7）。色を付けると立ち上がりのたびに警告が出て、#362 の本物の乱れ（1〜7 本を揺れ動く）と区別が付かなくなる。
  **合成は先着枠を使わず、開いた直後から必ず表示に入る** —— この画面で合成を見る目的は
  「平均した 1 本が単体より静かか」の確認なので、センサー 9 本の枠に埋もれては意味が無い
- **合成を作っている観測点では、センサー対の差分とセンサーごとのずれも重ねられる。** どちらも
  1 つだけ選ぶ（両方を流すと段が増えて、どちらを見ているか読めない）。差分は 3 軸のセンサーどうしの
  組だけ、ずれは 2 軸を含む全員が候補になる（→「複数センサーの波形合成（§7）」）。ずれは測る向きのまま、
  2 軸のセンサーと同じくセンサーごとの段へ描く
- **2 軸のセンサーは X・Y・Z の段に入れず、センサーごとの段へ測る向きのまま描く。** 2 本の軸から
  東・北・上は決まらないので、X・Y・Z の段へ混ぜると別の向きの揺れを同じ段に重ねることになる。
  段の見出しは「観測点名（基板 / センサー）（2 軸・測る向きのまま）」、凡例は軸ごとに「HN1 の向き: 東 +0.87・
  北 +0.50・上 0.00」（地面で見た長さ 1 の向きを小数第 2 位で）。線の色は軸ごと。測る向きや本数が
  変わったら（設定の書き換え・別の種類のセンサーへの挿し替え）、溜めた分を捨てて切れ目から描き直す
- **合成波形は直流を足し戻してから描く。** 押し出しで届く値は変動分（重力を落としたもの）だが、
  センサー単独は校正済み gal（重力込み）——そのまま重ねると縦の目盛りが 2 つの意味を持つ。
  足し戻せるように、落とした直流は `dcGal` として添えてある

**検出した揺れは「揺れの記録」タブで振り返れる**（#313）。下の「地震検出」が残した記録
（`GET /events`）を新しい順に並べ、行を押すとその区間の合成波形を読み返して描く
（`GET /waves`）。どちらも認証の要らない読み取りの口なので、トークンが無くても見られる。

- **一覧の上に「見張りの状態」を観測点ごとに 1 行出す。** 中身は 1 時間ごとのログ
  （下の「静かだっただけか、止まっているか」）と同じで、言い方も共有している
  （`src/detection/detectionWording.ts`）。**空の一覧だけでは「静かだった」と「検出が止まっている」を
  見分けられない**ので、一覧と並べて置く。比の最大は 24 時間ぶん覚えるが、ホストを起動して
  24 時間経っていなければ「07:35 からの比の最大」のように覚えている範囲の頭を書く
- **期間は 1 日・7 日・30 日・90 日のボタンか、日付で選ぶ**（既定 7 日。日付は日本時間で、終わりの日を含む）。
  **期間の広さに上限は無い**（2026-10-07 ユーザー承認）。ホストは新しいほうから 500 件で区切って返すので、
  選んだ期間に 500 件を超える記録があるときは（期間の長さではなく件数で決まる）、表の下に
  「新しいほうから N 件を出している」と「さらに古い記録を読む」が出る。
  「生活振動らしいものを隠す」で `local-like` だけを隠せる（既定は全部出す。ホストで除いてから 500 件を数える）
- **行を押すと、その行のすぐ下に区間の波形が開く**（2026-10-07 ユーザー承認）。もう一度押すか「閉じる」で畳み、
  別の行を押すとそちらの下へ移る。一覧が描き直されても開いたまま残り、期間や隠す指定を変えてその行が
  一覧から消えたら閉じる
- **開いている間は押し出しの `shake-event` で行を差し替える。** 照合待ちが地震へ変わるのを
  開き直さずに見られる。読み返しと押し出しが前後して届いても、版（`rev`）の大きいほうが残る
- **押し出しだけには頼らない。** 見張りの行と一緒に、直近 3 時間に始まった記録を 30 秒ごとに読み返す
  （照合は揺れが閉じてから最長 2 時間まで版を進めるので、その余裕を見た幅）。押し出しが切れていても
  一覧が追いつき、切れている間の揺れが黙って抜けることがない。ホストはファイル名
  （`<観測点>-<始まり>.json`）で範囲の外と分かる記録を開かないので、30 秒ごとに読み返しても月の記録を全部は読まない
- **読み返しに失敗したら、その理由を表の中に出す**（「この期間に記録した揺れは無い」とは書かない ——
  取れていないのか、無かったのかを取り違えるため）。選んだ期間をまだ一度も読めていなければ、30 秒ごとの
  読み返しは直近 3 時間ではなく期間全体を読み直し、それが読めるまで失敗の行を出したままにする
  （直近 3 時間だけ読めた時点で消すと、期間の残りが空のまま「揺れは無い」に見えるため）。
  「さらに古い記録を読む」が失敗したときだけは、表の中ではなくそのボタンの下に出す。読めていないのは
  表の末尾より古い分なので、もう一度押して読めれば消え、期間を選び直しても消える
- **読めなかった記録は件数で出す**（ホストが読めなかったファイルと、画面が読めない形の記録の合計）。
  黙って捨てると「揺れが無かった」と見分けが付かない。
  - 読み返し（`GET /events`）で読めなかった分は、30 秒ごとの読み返しが同じ範囲を見直して出てこなければ数えなくなる
    （一時的に読めなかっただけなら消える）。直近 3 時間より古いものは、期間を選び直すまで数えたまま残す
    （見直していないものを「直った」とはみなさない）
  - 押し出し（`shake-event`）で届いて読めなかった分は、タブを開いてからの累計で、開き直すまで減らない
  - 見張りの状態も、一部の観測点だけ読めなければ件数を添えて書き分ける
- **区間の波形は始まりの 10 秒前から終わりの 20 秒後まで**（最長 10 分）。3 段（X・Y・Z）に、
  始まり・終わり・S・P の縦線を引く（S・P は拾えたときだけ）。横軸は始まりからの秒。
  サンプルのまま返す口は 2 分までなので、**列ごとの上下の端（`columns`）で読み返す** —— 10 分まで描けて、
  ピークも消えない。記録が残っていなければ「この区間の波形は残っていない」、一部を読めなければ
  「読めなかった部分がある」と添える

### 保存した波形を読み返す（「波形の記録」タブ・`/api/records/*`）

**保存してある全センサー・全期間の波形を、管理コンソールの「波形の記録」タブで見られる**（#621。
2026-10-07 ユーザー依頼）。生データ（センサーごとの 3 軸）と観測点の合成波形のどちらでも、何週間ぶんの
俯瞰から 1 サンプルずつの点まで寄せられる。**見るのは運用者** —— 据え付け・受信・検出がどう働いていたかを
後から確かめるためのもので、地震ビューアー側の「イベント履歴」（REQUIREMENTS.md §10）の代わりではない。

**要約を前もって作る。** その場で読んで間引くと俯瞰が成り立たない —— 生データ 1 時間ぶん
（27 チャンネル・約 14.6 MB）の復号に作業 PC で 0.58 秒かかり、1 週間を見るたびに 100 秒払うことになる。
そこで元のファイル 1 本ごとに要約を作って残す（形式は `src/receiver/waveSummary.ts`）。

| 部分 | 中身 |
|---|---|
| `fine` | 1 秒ごとの本数・最小・最大・平均・ばらつき |
| `coarse` | 1 分ごとの同じ値と、1 秒より速い揺れの強さ（ノイズ。傾きや温度でゆっくり動く直流を含めないため別に持つ） |
| `psd` | 1 分ごとのパワースペクトル密度（Welch 法。0.1〜50 Hz を対数で 40 区画） |
| `reception.json` | 受信の記録の要約（生データの時だけ。取り戻した分・遅れて届いた分・時刻が疑わしい分・読めなかったパケット） |

- **置き場所は `seismo-host/data/summary/`**（`SEISMO_SUMMARY_DIR` で変えられる）。元のファイルの並びを写す
  （`raw/<日>/raw-<日>T<時>.<部分>.wsum`・`wave/wave-<札>-<日>T<時>.<部分>.wsum`）。**1 日 55 MB 前後**増える
  （生データぶん 2 MB/時・合成波形ぶん約 0.2 MB/時）。**消しても元のファイルから作り直せる**
- **逆に、元のファイルのほうを消すと、その要約も次の見回りで捨てる**（2026-10-08 ユーザー承認）。元を
  消すのはそのデータが要らない・誤っているときなので、要約だけ残すと「波形の記録」で選べるチャンネルと
  その期間（要約の置き場所から作る。下の `/api/records/channels`）に元の無い時が出続ける。ただし次のときは
  捨てない —— 元の置き場所を読み損ねた回と、要約の置き場所を読み損ねた回は**何も捨てない**。生データ・
  合成波形のうち**元が 1 本も見つからなかった側は、その側の要約だけ捨てない**（置き場所の付け替えや
  ドライブの外れで、作り直せない要約までまとめて失わないため）。捨てた本数は `/status` の `waveSummary.removed`、
  1 本ごとにログへ `[summary] 元のファイルが無くなった要約を捨てた: …` が出る。捨てられなかったとき
  （ファイルを掴まれている等）は `[summary] … の要約を捨てられず: …` が出て、次の見回りでまた試す
- **作るのは見回りの係**（`src/receiver/waveSummaryKeeper.ts`）。1 分ごとに元のファイルを数え上げ、要約が控えている
  元の大きさと今の大きさが違うもの（まだ無い・取り戻した分が後から足された）を作り直す。**新しい時から先に、
  1 回 30 本まで**。いまの時は 1 分おきに作り直す。作れなかったものは 10 分待ってから作り直す
- **作る処理は別スレッドで走る**（`src/receiver/waveSummaryWorkerRunner.ts`）。1 時間ぶんに 1.4 秒かかるので、
  受信と同じスレッドで回すと止まった秒数の見張り（1 秒）を越え、UDP の受信バッファも溢れうる
- **初めて動かしたときは、溜まっている過去の時を新しい順に作っていく。** 1 分に最大 30 本（生データと合成波形の
  時のファイルを合わせて）なので、溜まっている時のファイルが数百本あれば作り終えるまで十数分〜数十分かかる。
  その間に開いた範囲のうち要約がまだ無い時は、
  画面が「要約がまだ無い時」として挙げる（欠けとは描き分ける）
- 進み具合は `GET /status` の `waveSummary`（数えた元のファイル・最新の数・待っている数・作った累計・
  作れなかった回数・元が無くなって捨てた累計・最後の理由）

**読み返しの口**（`src/receiver/waveRecordsApi.ts`。どれも `GET`・認証が要る。上の「`/api/*` の認証」）。
`from`・`to` は unix ミリ秒（`to` は含まない）で、範囲は 400 日まで。

| 経路 | 返すもの |
|---|---|
| `/api/records/channels` | 保存してあるチャンネルの一覧（生データはセンサーごと、合成波形は観測点の札ごと） |
| `/api/records/envelope` | 列ごとの本数・最小・最大・平均・ばらつき・ノイズ（列は 4096 まで。広さで 1 分か 1 秒の要約を選ぶ） |
| `/api/records/samples` | 生のサンプル（10 分まで） |
| `/api/records/spectrum` | 範囲のスペクトル（10 分以内は生のサンプルから、それより広ければ 1 分ごとの PSD の平均） |
| `/api/records/spectrogram` | 列ごとのスペクトル（10 分以内は生のサンプルから約 6 秒ごと、それより広ければ 1 分ごとの PSD から） |
| `/api/records/reception` | 受信の記録の帯と読めなかったパケット |
| `/api/records/intensity` | 刻みごとのリアルタイム震度と計測震度（観測点の合成波形だけ・10 分まで。`station` は観測点の札） |
| `/api/records/quakes` | 気象庁の地震と、その観測点へ P・S が届く時刻（7 日まで。`station` は観測点 ID。下記） |

**画面を閉じた・操作して取り直したら、読むのをやめる。** 接続が切れたら読み手を途中で止め、応答は書かずに捨てる。
400 日の範囲を頼んだまま離れても、ホストが最後まで読み続けることはない。**気象庁の地震一覧（`quakes`）だけは
打ち切らない** —— 取った分は日ごとの控えに残り、次の要求がそれを読むので無駄にならない。

**画面の作り**（`src/admin/viewRecords.ts`。作りと文言は 2026-10-07・2026-10-08 ユーザー承認）。上から順に:

- **記録と期間の選択・全体の帯**（記録がある期間の全体。押すとその時刻へ寄る）・**範囲の操作**
  （全体・1 週〜10 秒の幅、送り、ホイール、ドラッグ）。一度に見られる幅は口と同じ 400 日までで、
  記録がそれより長ければ「全体」は新しい側の 400 日になる（全体の帯も同じ）
- **印の段** —— 受信（取り戻した分・遅れて届いた分・時刻が疑わしい分・読めなかったパケット）、
  気象庁の地震（発生時刻と P・S）、揺れの記録（区間と拾った P・S）
- **軸の合成**（見えている軸だけを合わせた 1 本。10 分以内）と**軸ごとの段**（縦の物差しは段で共通）
- **リアルタイム震度の推移**（観測点の合成波形・10 分以内）
- **ノイズ水準の推移・軸ごとのスペクトログラム・範囲のスペクトル**（dB は 0 dB = 1 (m/s²)²/Hz。
  スペクトルには Peterson（1993）の低ノイズ・高ノイズのモデルを破線で重ねる）
- **範囲が 10 分以内なら生のサンプル、それより広ければ要約の列**で描く。操作の最中は取り直さず、止まってから取る

**取れなかったものは画面に書く。** 要約がまだ無い時、地震一覧を取れなかった日とその理由、
発生時刻を秒まで寄せる材料を取れなかった日、読めなかった揺れの記録の件数 —— 黙って抜けると
「その時は何も無かった」に見える。

**気象庁の地震を重ねる**（`src/receiver/recordQuakes.ts`・`src/detection/quakeRefine.ts`）。地震情報の発生時刻は
分までしか無いので、そのまま P・S を引くと 60 秒幅の帯になって揺れの区間を覆ってしまう。秒を持つ出どころで寄せる
（2026-10-08 ユーザー承認）。外への通信は次の 3 つ。

| 先 | 取るもの | 回数 |
|---|---|---|
| P2PQuake `https://api.p2pquake.net/v2/jma/quake` | 地震情報（名前・規模・最大震度・分までの発生時刻） | 範囲の日をまとめて 1 本〜（100 件ごとに 1 本・6.5 秒おき） |
| 気象庁の震源リスト（日別・`https://www.data.jma.go.jp/eqev/data/daily_map`） | 0.1 秒までの発生時刻・震源・深さ（2 日前まで載る） | 地震のある日ごとに 1 本（1 秒おき） |
| DMDATA `https://api.dmdata.jp/v2/gd/eew` | 緊急地震速報の最終報の発生時刻（秒まで） | 震源リストで寄せられなかった日をまとめて 1 本〜。**`SEISMO_DMDATA_API_KEY` を置いたときだけ** |

- **初めて見る 7 日なら、P2PQuake へ 3 本前後と気象庁へ 7 本前後**（DMDATA は震源リストで寄せられなかった日があるときだけ）
- **日本時間の日ごとに控える**（`data/summary/quakes/`）。確定した日は二度と取りに行かない。確定していない日は
  10 分（震源リストは 1 日）まで控えを使い、取れなかった日は 5 分取り直さない。外へは 1 本ずつ順に投げる
- **`SEISMO_DMDATA_API_KEY` は任意。** 無ければ緊急地震速報では寄せず、震源リストに載る前（直近 2 日）の地震は
  分の幅の帯で出る。値は DMDATA.JP の API キー
- `SEISMO_QUAKE_FEED=0` なら、地震情報との照合（下の「地震検出」）と同じく、ここも外へ取りに行かない
- 届く時刻の求め方（走時表・深さが分からないときの幅）と、気象業務法上の位置づけは
  [`docs/forecast-computation-audit.md`](../docs/forecast-computation-audit.md) の 9

### 観測点・基板・センサー校正の設定（何をどこへ置いたか）

**基板が名乗るのは焼いても動かしても変わらない事実だけ。設置に由来する事実はホストが持つ。**
基板を別の部屋へ移せば観測点は変わるが `boardKey`（MAC）は変わらない —— 両方を持たないと
「去年のこの波形はどこで採ったか」が答えられなくなる。

**観測点（設置場所）と基板を分けて持つ**（REQUIREMENTS.md §15）。同じ観測点に複数の基板を
割り当てられる —— 複数台の統合（§7）の前提。設定の中身は次の形で、管理コンソールと `/api/*`
（前節）はこの形で受け渡す。

```json
{
  "stations": [
    { "stationId": "study", "displayName": "書斎", "lat": 35.6, "lon": 139.7 }
  ],
  "boards": [
    {
      "boardKey": "mac:020000000003",
      "stationId": "study",
      "orientation": [[1, 0, 0], [0, 1, 0], [0, 0, 1]],
      "sensors": [
        {
          "sensorId": "i2c0-68",
          "enabled": true,
          "axes": [
            { "vector": [1, 0, 0], "offset": 0 },
            { "vector": [0, 1, 0], "offset": 0 },
            { "vector": [0, 0, 1], "offset": 0 }
          ],
          "noiseDensity": 400
        },
        {
          "sensorId": "i2c0-6a",
          "axes": [
            { "vector": [1, 0, 0], "offset": 0 },
            { "vector": [0, 1, 0], "offset": 0 }
          ]
        }
      ]
    }
  ]
}
```

`stationId` は識別子（英数字を想定。PWA 側から観測点を指すときの鍵になる）、`displayName`
は画面に出す名前、`lat`/`lon` は PWA が地図へ出すための座標。

基板は `stationId` で観測点を指す —— **`stations[]` に無い `stationId` を指す基板があると、
設定ごと拒否する**（参照整合性。黙って未割当へ倒すと、書き間違いに気づけない）。

**校正は軸ごとと基板ごとの 2 段で持つ**（§15・§16）。式と、前の形からの写し方は
[`src/receiver/calibration.ts`](src/receiver/calibration.ts) 冒頭のコメントにある。

```
軸 j:   m_j − o_j = h_j · a_基板        m: 校正前の加速度（gal）  o: ゼロ点  h: 測る向き
基板:   a_地面 = B × a_基板             B: 基板の向き（基板の座標 → 東・北・上）
```

- **`axes[]`（センサーの軸ごと）** —— `vector` はその軸が**基板の座標で**測る向きで、**長さが倍率**
  （向きに沿って 1 gal 掛かったとき、校正前の値で何 gal 読むか）。`offset` はゼロ点（gal）。
  **並びはパケットの軸と同じ、本数も同じ**（2 か 3）。軸どうしが直交している必要は無いが、
  **解ける形でなければ設定ごと拒否する**（3 本なら 1 つの面に寄っていない、2 本なら平行でない）——
  解けない向きはその向きの揺れを消す値で、補正ではない
- **`orientation`（基板ごと）** —— 基板の向き。**列が基板の X・Y・Z 軸の向き**（東・北・上の成分）で、
  **純粋な回転しか受け付けない**（列の長さ 1・互いに直交・右手系）。倍率や直角のずれは各軸の
  `vector` が持つので、ここに入れる理由が無い。単位行列なら、基板の X・Y・Z が東・北・上を向いている
- `enabled`・`noiseDensity`（公称ノイズ密度・µg/√Hz。複数センサーの合成で重みに使う）

どれも省略できる。既定値は、`axes` が補正なしの 3 軸（基板の X・Y・Z をそのまま測る・倍率 1・
ゼロ点 0）、`orientation` が単位行列、`enabled` が有効、`noiseDensity` が null。**2 軸のセンサーは
`axes` を省けない** —— 省くと 3 軸の設定になり、届いた 2 軸のパケットと本数が合わない（下記）。
前の形の欄（`rotation`・`offset` の配列・`sensitivity`）は読まない（書いても黙って無視される）。

**省略できるのは各項目の値であって、`sensors[]` のエントリ自体ではない。** `sensorId` を
1 つも書かなければ校正は既定値で動き続けるが、**複数センサーの波形合成（§7）はそのセンサーを
合成グループに数えない**——同一観測点へ 2 台目の基板を割り当てても、両方（または片方）の
`sensors[]` が空のままなら、合成は沈黙して起動しない。校正の実測がまだでも、
`{ "sensorId": "i2c0-68" }` のように `sensorId` だけを書けば参加する（他の項目は既定値のまま）。
食い違いは起動時・定期要約のログに加え、`GET /status` の `ungroupedMultiBoardStations`
（`stationsWithMultipleBoards` と `SensorFusion.groupedStationIds` を `main.ts` が突き合わせた結果）
にも恒久的に出る——空配列なら乖離なし。ログをテールしない運用者は、こちらをポーリングして気づける。

**並び順も設定の一部。** 観測点の合成は、基板とセンサーの並びで基準にするセンサーを決める ——
並びを入れ替えると、合成の時間軸が変わる（実測で 15 ms）。

**読み取りへの適用は、カウント値を gal へ換算した直後・区間の組み立てより前。** ホストは基板の向きを
掛けて「地面の座標で各軸が測る向き」`w_j = B⁻ᵀ h_j` にしてから使う。**3 軸のセンサーはそこから
地面の 3 成分（東・北・上）を解き**、震度もセンサー単体の波形もこれで出す。**2 軸のセンサーは
1 台では 3 成分を解けないので、センサー単体の震度は出さない。** 軸ごとの値を「地面で見た測る向き
（`w_j` を長さ 1 にしたもの）」とその向きの gal（`(m_j − o_j) / |w_j|`）にして、センサー単体の波形
（押し出しの口と管理コンソールの「波形」タブ）・静止窓（6 面法の材料）・観測点の合成（軸 1 本ずつを
ほかの台と一緒に解く。→「複数センサーの波形合成（§7）」）へ流す。受信の記録と生データには 3 軸と
同じく残る。

**軸どうしが直交していない `vector` を入れると、計測震度そのものが変わりうる**（純粋な回転なら
3 成分の合成の長さは変わらないが、直角を崩す変換では変わる）。REQUIREMENTS.md §16 の
「軸どうしの直角のずれまで補正するか」は 2026-10-10 に「直す」と決まり、基板の 6 面法が軸ごとの
向きを直角に縛らずに解く（上記「軸の向き・倍率・ゼロ点は 6 面で測る」）。

**軸の本数がパケットと食い違うセンサーは、震度も波形も出さない**（どちらの本数で読んでも、どれかの
軸が別の軸の校正値で補正されるため）。食い違いは `GET /status` の `sensors[].axisMismatch`
（`{ configuredAxes, receivedAxes }`、食い違っていなければ `null`）に出て、管理コンソールの
「稼働状況」では校正の欄に「軸の本数が違う（設定 3 本・届いたのは 2 本）」と赤字で、震度の欄に
赤い「—」で出る。パケットごとに書き直すので、設定を直せば次のパケットで消える。
設定に書いていないセンサーは、届いた本数ぶんの補正なしの軸に基板の向きだけを掛けて使う。

**2 軸のセンサーの震度の欄は、本数が食い違っていなければ灰色の「2 軸」になる**（震度を出さないのが
正しい状態で、異常ではない）。

`enabled: false` のセンサーはこの適用より前で弾く —— 換算にも組み立てにも渡さず、震度・波形の
どちらも出さない（§15 の「有効/無効」を読み取りへ反映しないと、設定した意味が無い）。

**`boardKey` は正規化してから照合する。** `mac:` は 12 桁の 16 進数（実機は小文字固定で送る）
だけを受け、大文字が混じっていても小文字へ揃える。前後の空白も落とす。**観測点へ割り当てられるのは、
miniSEED と StationXML で名乗れる基板・センサーだけ** —— `boardKey` は `mac:` で始まるもの（MAC を
名乗らない版 1 の基板は割り当てられない）、`sensorId` は英数字とハイフンの 8 文字まで。名乗れない
基板の波形は生データに残せないので、観測点へ入れられる形にしない。**重複は名乗りの単位で見る** ——
`stationId`、MAC の下位 8 桁（局コード）、同じ基板の中の `sensorId`（大文字小文字を区別しない）の
どれか 1 つでも 2 回現れれば、その時点で設定ごと拒否する（どちらを採るか黙って決めない）。

`GET /status` の `sensors[]` には、この設定から引いた `station`（`stationId`・`displayName`・
`lat`・`lon`）が付く。設定に無い基板は `station: null`（未割当）のまま出す。

**`calibrationConfigured` は別の問い。** `station` が「どこに置いたか」を答えるのに対し、
こちらは「そのセンサーの校正値を書いたか」を答える —— **校正の適用側（§15・§16）は設定が無くても
既定値（補正なし）で動き続けるので、`resolveSensor` の返り値だけでは「設定と一致
したか」を見分けられない。** `sensorId` を打ち間違えても警告一つ出ずに既定値で動き続ける、
という穴をここで塞ぐ。観測点は割り当てたのに校正値を 1 件も書いていないセンサーは、
`station` が付いて `calibrationConfigured: false` のまま出る。

**`enabled` はさらに別の問い。** `sensors[]` には `isSensorEnabled` の値も付く ——
「意図して無効化したセンサー」と「軸数不一致等で本当に壊れているセンサー」は、`lastIntensity`
等が同じように凍結されるので**この欄が無いと見分けが付かない**。設定に無いセンサーは既定値
（`enabled: true`）のまま出る。設定の軸の向きが解けない形だったセンサー（設定の検証を通っていれば
起きない）は無効として出し、ログに 1 回警告を残す。

**`axisCount` はそのセンサーから最後に受け取ったパケットの軸の本数**（まだ 1 通も届いていなければ
`null`）。管理コンソールの「登録」が、これでカードの行数を決める。

#### 設定ファイルは StationXML 1 本（設定と履歴を兼ねる）

置き場所は `seismo-host/config/stations.xml`（`SEISMO_STATION_CONFIG` で変えられる）。**Git には
入らない** —— 設置場所（＝自宅の間取り）を書くので、生データと同じ理由。`stations.example.xml` は
形の見本で、写して使う必要は無い —— ファイルが無ければ空の設定で起動するので、観測点と基板は管理コンソールから足す。

**FDSN StationXML 1.2**（地震観測網が観測点のメタデータを持つ標準の形）で、生データの miniSEED と
対になる。生データは基板とセンサーで名乗り、しかも補正前の値なので、後から読み直すには「その時刻に
どの観測点にあって、どう補正していたか」が要る。StationXML はまさにそれを期間（epoch）ごとに持つ形で、
**終わりの無い期間が「いまの設定」、閉じた期間が履歴**になる。ホストは起動時にこれを読み、管理コンソールの
保存も同じファイルへ書く —— **実機が動かしている設定と、後から読み直す設定が同じファイル**なので、
食い違いようがない。形の細部は [`src/receiver/stationXml.ts`](src/receiver/stationXml.ts) の冒頭。

| StationXML | ここでの意味 |
|---|---|
| Network `XX` | この観測網（FDSN へ登録していない網の符号） |
| Station | 基板（局コードは MAC の下位 8 桁）。期間は観測点の情報が変わったところで区切る |
| Channel（ロケーション＝センサー ID・`HN1`〜`HN3`） | センサーの軸。期間は校正値が変わったところで区切る |
| `Azimuth`・`Dip` | そのチャンネルが地面で測っている向き（基板の向きを掛けた `w_j` の向き） |
| `Response`（2 段） | 倍率（`w_j` の長さ）とゼロ点。**入力と出力は gal**（地面の加速度から校正前の加速度まで）。カウントから gal への換算は生データの受信の記録が持つ |
| 拡張（名前空間 `urn:realtime-earthquake-viewer:seismo-host`） | 基板の正式な鍵・観測点の ID・センサー ID・有効かどうか・ノイズ密度、**ホストが使う値そのもの**（チャンネルごとの基板の座標での向き `seismo:Vector`、基板ごとの向き `seismo:Orientation`）、起動と設定の変更の記録 |

2 軸のセンサーは `HN1`・`HN2` の 2 本だけを持つ。**前の形（2026-10-09 まで。チャンネルごとに回転行列の列と
感度を持ち、応答が 3 段）のファイルも読める** —— 読むときに今の形へ写し（基板の向きは単位行列）、
次に書くときは今の形で書く。写した値はもとの変換と丸めの誤差（1e-15 ほど）しか違わないので、
期間は切れない。**同じ基板の中に前の形のチャンネルと基板の向き（`seismo:Orientation`）が両方あるファイルは
読めない** —— どちらの向きで読むか決まらないため（管理コンソールの保存では起きない。手で継ぎ合わせたときだけ）。

**元の値を拡張にも持つのは、方位・傾き・倍率から組み直すと元に戻らないから**（三角関数と逆行列を通すので、
実測で 8e-15 ほどずれる）。読み手（ホスト自身を含む）は拡張の値を使い、標準の欄はそこから
計算したもの。**両者が食い違うファイルは、どちらが正しいか決められないので読めないとして扱う。**
標準の道具（ObsPy など）は標準の欄を読む。標高と深さは設定に無いので 0、多項式の範囲の欄も 0 を書く。

**起動と設定の変更のたびに、記録を 1 つ足して丸ごと書き直す**（一時ファイルへ書いて `fsync` してから
名前を付け替える）。記録には時刻・契機（`startup`／`changed`）と、**その時点の観測点・基板・センサーの
並び**を持つ。並びは期間の形では持てないが、合成の基準を決める（上記）ので、過去の時刻で流し直すときに
当時の並びが要る。基板を割り当てていない観測点も、ここにしか置き場所が無い（Station＝基板なので）。
時計が戻っても、期間と記録の順は崩さない（前の記録の時刻へ寄せる。実際の時刻も残す）。

**割り当ては任意。** ファイルが無ければ空の設定で起動し、起動の記録を書くときにファイルができる
（観測点を知らないだけで、震度を出す仕事とは無関係）。**読めないとき**（XML として読めない・期間と
記録が食い違う・標準の欄と拡張が食い違う・中身が設定の検証を通らない）**は空の設定で動き、そのプロセスでは
書かない** —— 読めない理由が分からないまま書き直すと、読めなかった分の履歴がまるごと消える。管理コンソールからの
保存も、そのあいだは失敗として返す。理由は標準出力（`console.warn`）だけでなく `GET /status` の
`stationConfigWarning` にも出す —— 起動時にしか出ない警告は、運用者が見に来た時点でもう流れている。
書けなかった回数と最後の理由は `GET /status` の `stationHistory` と毎分の要約に出る。

**ファイルを直接編集した場合、変更はプロセスを再起動するまで反映されない**（起動時に一度だけ読む）。
ふつうは管理コンソール（`/api/*`）から変える —— 保存と同時に実行中のホストへ反映される（`main.ts` が
ランタイムの状態 —— `StationDirectory`・`SensorFusion` —— も差し替える）。直接編集するなら、
上の「標準の欄と拡張が食い違えば読めない」に注意すること（拡張の値だけを書き換えると読めなくなる）。

### 複数センサーの波形合成（§7）

**同じ観測点に複数の基板を割り当てたとき、その波形を混ぜる部品**（`src/receiver/sensorFusion.ts`
の `SensorFusion`）。**混ぜるのは直前の節（校正の設定）で校正（軸の向きとゼロ点・基板の向き）を
適用した後の波形（`WaveChunk`）であり、生のカウント値でも校正前の gal でもない。** 2 軸のセンサーも
混ぜる —— **センサーの軸 1 本を 1 つの観測として、目盛り 1 点ごとに地面の揺れ（東・北・上）を
最小二乗で解く**（下記「軸を 1 本ずつの観測として解く」）。3 軸のセンサーだけの観測点では、以前の
成分ごとの重み付き平均と同じ値になる。要件原文は単純平均 `a=(a1+a2)/2` と書いているが、
[`docs/implementation-plan.md`](../docs/implementation-plan.md) #93 の実測が「品種が混ざると
単純平均は床を悪化させる」ことを示しているので、**重みはノイズ分散の逆数**にする
（`1/noiseDensity²`）。ただし#93 は「それで床が下がると期待しないこと。本題は差分と
空間的な一致のほうで、合成による精度向上ではない」とも言っている。

**混ぜるのは直流（重力）を落とした変動分。** 各センサーから、そのセンサー自身の
移動平均（窓は 20 秒。`FUSION_DC_WINDOW_SEC`）を引いてから解く。落とした直流は
`FusedWaveChunk.dcGal` に添えてあるので、**足し戻せば「校正済み gal から解いた値」に
戻る**（情報は失われない）。理由は下記「顔ぶれの入れ替わりが段差になる」。

**顔ぶれが揃うのを待ってから合成する。** すぐ混ぜると、その瞬間に届いていた
センサーだけが混ざって顔ぶれが揺れる（下記「顔ぶれの入れ替わりが段差になる」）。
**待ちは時間では決めない** —— 揃った時点で出し、揃わないときだけ 0.6 秒で頭打ちにする
（下記「出すのは『顔ぶれが揃ったら』で、時間では決めない」）。合成の震度はこの待ちのぶん
単独センサーより遅れて出るが、判定は直近 60 秒で行うので、待ちの間に最大値を取り逃すことは無い。**揃えばノイズは実際に下がる**（実測値は
[`REQUIREMENTS.md`](REQUIREMENTS.md) §7 の注記枠が持つ）——#93 が「床が下がると
期待しないこと」と言うのは品種が混ざる場合で、**同一品種なら下がる**。

**観測点ぶんの計測震度・合成波形・差分は `main.ts` へ配線済み。**

| 何が | どこに出るか |
|---|---|
| 観測点ごとの震度 | `GET /status` の `stationIntensities`（直近の震度・締めくくり失敗・震度が出せない理由）と `GET /stream` の `station-reading`（PWA 向け） |
| **合成した波形**（`FusedWaveChunk`） | `GET /stream?wave=station`（または `?wave=1`）の `station-wave`。**波形を頼んだ相手だけへ行く**。成分ごとに `null`（解けない成分）がありうる |
| **合成した波形を作り直した範囲** | `GET /stream?wave=station`（または `?wave=1`）の `station-wave-revised`（`stationId`・`fromMs`・`toMs`）。下記「取り戻した区間は作り直す」 |
| **混ざった本数** | `GET /status` の `stationIntensities[].lastMemberCountMin` / `lastMemberCountMax`（目盛りに値を持っていた台の数）。**大きく揺れ動いていれば異常を疑う手掛かり**（同 §7 の #362）。判定の閾値は未設計 |
| **顔ぶれが揃わないまま切り上げた回数** | `GET /status` の `stationIntensities[].uncoveredFusions`。本数だけでは「生きているセンサーが恒常的に揃わない」と「割り当てが 2 台で本数が少ない」を見分けられないので別に数える（#374）。**起動直後と設定を変えた直後は増える**（まだ届いていないセンサーがある）ので、**0 でないこと自体は異常ではない** —— 見るのは**動き続けているか**。実機（9 センサー）の立ち上げ直後は **1 回**で、そこから 135 秒まで動かなかった。判定の閾値は未設計 |
| **差分の強さ**（`SensorPairDiff` の要約） | `GET /status` の `stationIntensities[].pairDiffs`（3 軸のセンサーどうしの対ごと・軸ごとの RMS） |
| **差分の時系列**（`SensorPairDiff` そのもの） | `GET /stream?diffStation=…`（5 欄）の `station-diff`。**頼んだ 1 組だけへ行く**（`?wave=` とは独立） |
| **ずれの強さ**（`SensorResidual` の要約） | `GET /status` の `stationIntensities[].residuals`（センサーごと・軸ごとの RMS と、その軸の測る向き） |
| **ずれの時系列**（`SensorResidual` そのもの） | `GET /stream?residualStation=…`（3 欄）の `station-residual`。**頼んだ 1 台だけへ行く**（`?wave=` とも差分とも独立） |
| **測る向きが足りず解けなかった目盛り** | 毎分の要約の「観測点の合成で測る向きが足りず解けなかった目盛り」。センサーが途中で止まって解けなくなった形を数える |
| **解けない向きのある観測点** | 起動時・設定を変えたとき・定期要約のログ（`[station] 観測点 … は有効なセンサーの測る向きが 3 方向へ散っていないので、…`）。設定の時点で、有効なセンサー全員の向きを束ねて判定する |

**設定を変えても、`stationIntensities` からその観測点は消えない。** 直近の値を覚えておく仕組み
（帳面。`src/receiver/stationHealth.ts`）は起動時に 1 度作るだけで、観測点を消しても・割り当てを
1 台へ減らして合成グループが無くなっても作り直さない——その行は最後の値を抱えたまま、
**ホストを入れ直すまで残る**。

管理コンソールでは、その行の受信欄が 60 秒で「途絶」の札に変わり、**同じ行の値（震度・混ざった
本数・差分の最大・ずれの最大）も赤くなる**。要約カードの「複数センサー合成の観測点」は
`生きている数 / 全体` で出るので、減らした後の数はそこで読める（#373）。

**震度の欄だけは「届いてはいるが震度を出せていない」間も赤くなる。** 合成波形は出ているのに
震度だけ出せない状態（`stationIntensities[].lastSkipReason` が立っている）では、混ざった本数と
差分は今の姿のまま震度だけが古い——しかも合成のまとまりは出続けるので、受信欄は「受信中」のまま。

**赤い行が「消した観測点」なのか「基板が黙った観測点」なのかは区別しない。** 消したのは
運用者自身なので、見分けを画面へ足さないと決めた。

**差分の時系列は「見たい 1 組を選んでから」出す。**
`GET /stream?diffStation=…&diffBoardA=…&diffSensorA=…&diffBoardB=…&diffSensorB=…` の
**5 欄で 1 組だけ**頼み、`station-diff` として届く（`?wave=` とは独立 —— 波形を頼まなくても
差分だけ来るし、`?wave=1` だけでは差分は来ない）。**全ペアをまとめて流す道は置いていない**
——量は上記「状態と押し出しの口」の表のとおりで、波形の梯子へ載せれば桁が変わる。
**どの対を選ぶかの材料が上の RMS** —— 一覧で当たりを付けてから時系列を見る。

- **基板の書き方は設定と同じ関数を通す**（`stationConfig.ts` の `normalizeBoardKey`）。
  別に書くと、大文字の MAC を揃え忘れた側だけが**「構文は正しいのに設定の値と永久に
  一致しない」**形になる（症状は「繋がっているのに何も届かない」だけ）
- **半端な指定でも接続は断らない。** 差分なしで繋いで 1 行残す ——
  **記録の合言葉は理由ごとに分ける**（欄が足りない・空・長すぎる・書式違い・
  同じセンサー）。固定にすると、60 秒のうちに違う理由で失敗した 2 件目が間引かれて残らない
- **向きは問わない。** A-B と B-A を同じ組として配る。符号の反転は届いた 1 件の
  `memberA`/`memberB` から分かる
- **頼んだ組は `GET /status` の `stream.subscribers[].diff` に出る。**
  届いていないとき、頼み方が悪いのか値が来ていないのかをここで切り分ける
- **欄を 5 つに分けたのは、繋ぐ文字を決められないから** ——`boardKey`・`sensorId` は
  無認証の UDP パケット由来で文字種の検証を持たない。向きを問わない理由も含め、
  設計の判断は `statusServer.ts` の `parseDiffParams` と `readingHub.ts` の
  `pairMatches` のコメントにある

**ずれの時系列も「見たい 1 台を選んでから」出す。**
`GET /stream?residualStation=…&residualBoard=…&residualSensor=…` の **3 欄で 1 台だけ**頼み、
`station-residual` として届く。基板の書き方・半端な指定でも接続は断らないこと・頼んだ台が
`GET /status` の `stream.subscribers[].residual` に出ることは、差分と同じ。

**異常センサー検出はまだ無い。** 差分 `d=(a1-a2)/2` とずれ（下記）の強さは出るが、そこから
「このセンサーがおかしい」と自動で判定する仕組みは持たない——要件原文（§7）が挙げる
用途（自己ノイズの推定・異常センサーの検出・一致度確認・coherence 解析・ロバスト平均）
のうち、いまここにあるのは元になる数値と、対ごとに比べられる形までで、閾値は未設計。

**設計判断（要件原文には無い）**:

- **観測点ごとに、センサーと無関係な時間の目盛りを 1 本持つ。** 刻みは 10 ms（100 Hz）に固定し、
  位置は絶対時刻で決める（`k` 番目の目盛りは `k × 10 ms`）。合成はこの目盛りの 1 点ずつについて、
  **その時刻の値を持っているセンサーの軸全部**から地面の揺れを解く（下記「軸を 1 本ずつの観測として
  解く」）。設計の経緯は
  [`docs/seismo-station-fusion-design.md`](../docs/seismo-station-fusion-design.md)
  - **刻みを固定するのは、PWA が刻みの揺らぎで波形を捨てないため。** センサーの刻みは基板ごとに
    揺らぐ（実機で 9.979〜10.018 ms）が、PWA の溜まりは刻みが 0.5% 動くと作り直す
  - **位置を絶対時刻で決めるのは、届き方で目盛りが変わらないため。** どの台が先に届いても、
    ホストを入れ直しても、生データから作り直しても（下記「取り戻した区間は作り直す」）、同じ時刻には
    同じ目盛りが立つ。まとまり（30 点・300 ms）の境目も絶対時刻で固定する
  - **以前は 1 台（いちばん静かな台）を「駆動役」に固定し、その到着だけで合成を進めていた。**
    その 1 台が欠けると、ほかの台が生きていても観測点の波形と震度が止まった —— 2026-10-07 の
    電子レンジの試験で、駆動役の基板の FIFO あふれが観測点の波形に穴を残した（ほかの 2 枚は
    データを持っていた）。新旧を同じ生データで比べた値は [`REQUIREMENTS.md`](REQUIREMENTS.md) §7 が持つ
  - **いちばん静かな台が値を決める度合いは変わらない。** 重みが雑音の分散の逆数なので、静かな
    1 台がいればその台がほぼ値を決める（#93 の「役割分担」は重みとして残る）。変わるのは、
    その 1 台が欠けた瞬間に残りで続けられることだけ
- **値は線形補間で引く。外へは延ばさない。** 目盛りを前後で挟む 2 サンプルが同じセンサーにあれば
  補間する（刻みの違う台 —— IIS2ICLX は 104 Hz —— が混ざっても揃う）。2 サンプルの間隔が刻みの
  1.5 倍を超えるなら、間に欠けがあるとして引かない
- **軸を 1 本ずつの観測として解く**（2026-10-09）。軸 j の値を `y_j = d_j · a`（`d_j` は地面で見た
  測る向き・長さ 1、`a` は地面の揺れ）と見て、目盛り 1 点ごとに `N = Σ w d_j d_jᵀ`・`b = Σ w d_j y_j`
  から `a = N⁻¹ b` を解く。重みは雑音の分散の逆数（申告が 1 つでも欠ければ全員 1）。直流も同じ解き方で
  `dcGal` を出す
  - **解けるかは向きだけで決める**（重みを入れない `G = Σ d_j d_jᵀ`）。雑音の申告の大小で、解けるかが
    変わらないように
  - **成分ごとに出すかを決める。** 1 軸で真っすぐ測ったときより雑音が 3 倍を超える成分は欠け（`null`）に
    し、**解けない向きに掛からない成分は出す** —— 上を測る台が止まって水平の台だけが残っても、東・北の
    波形は続く（2026-10-09 ユーザー承認）
  - **震度は、3 方向とも散っている目盛り（`G` のいちばん小さい固有値が 1/9 以上）でだけ流す。** どの向きへ
    揺れても雑音が 3 倍を超えないので、震度が雑音で押し上がらない。一部の成分だけ解けた範囲は別の
    まとまりとして出し、震度を流さない
  - **3 方向へ散っていない観測点は知らせる**（上の表の最後の 2 行）
- **本数は台で数える。** `memberCount` はその目盛りに値を持っていた台の数（3 軸のセンサーだけなら、
  以前の「3 成分のうち最も少ない成分の本数」と同じ値）。`axisMemberCount` は成分ごとに、その成分を
  自分の軸でじゅうぶんに測っている台の数（水平に置いた 2 軸の台は上の成分に数えない）。いまは誰も読まない
- **ずれは、その台を除いたほかの台で解いて比べる。** 除いて解いた揺れを、その台の測る向きへ写して
  測った値から引く（`r_j = y_j − d_j · â`。半分にはしない）。自分を含めて解くと、重みの大きい台ほど
  自分で値を決めてしまい、振れても 0 に近く出る。除くとその軸の向きを解けない目盛りでは `null`
  - **2 台だけがある向きを測っている観測点では、どちらがおかしいかを RMS だけでは見分けにくい**
    （振れた台ともう 1 台のずれが、ほぼ同じ大きさで逆向きに出る）
  - **ずれが静かなときも残り続けるなら、まず向きと校正を疑う**（基板の向き・軸の測る向き・6 面法の
    向き・倍率・ゼロ点）。切り分けの考え方は [`REQUIREMENTS.md`](REQUIREMENTS.md) §16 の注記枠にある
- **顔ぶれの入れ替わりが段差になる（実機で発覚・2026-09-28）。** まだ届いていない範囲は
  引けないので、**待たずに合成するとその瞬間に届いていたセンサーだけが混ざり、顔ぶれが
  サンプルごとに変わる。**
  センサー間の直流（実機では静止時の Z 軸が 662〜1200 gal に散っていた。感度が未校正）が
  揃っていないと、顔ぶれが 1 本入れ替わるたびに平均の直流が数十 gal 跳ぶ ——
  静止ノイズ 1.5 gal に対する段差が 100ms ごとに立ち、**周期補正フィルタがそれを
  計測震度として出す**（実機では合成が 4.36、単体が 1.12〜1.24。実測値は
  [`REQUIREMENTS.md`](REQUIREMENTS.md) §7 の表が持つ）。**当時は混ざる本数が状態の口に
  出ていなかった**ので、実機の到着の形を写した台の上で測った（台の作りは
  `sensorFusion.test.ts` の「直流の違う 3 本を時刻をずらして流しても、合成の震度が跳ばない」が引き継いでいる）。
  **本数はその後 `/status` へ出した**（#315。上記「複数センサーの波形合成（§7）」）。
  手当ては 2 つで、どちらも要る
  ——**混ぜる前に直流を落とす**（段差を作らせない）と、**ほかのセンサーの到着を待つ**
  （顔ぶれを揃える）。震度の計算側が引く直流では消えない
  ——あれは区間の最初の 1 秒の平均を引くだけで、途中で立つ段差はそのまま揺れとして通る
  （2026-09-28 当時は窓ごとに平均を引く方式だったが、同じく窓の中の段差は残った）
- **出すのは「顔ぶれが揃ったら」で、時間では決めない**（#374）。目盛りを 30 点（300 ms）の
  まとまりにして、**生きているセンサーが全員そのまとまりの末尾を越えるサンプルを届けた回**に
  出す。**時間で決め打つと必ず足りなくなる** —— 要る長さは「センサー間の到着差 ＋
  センサーのまとまり長」で、後者は基板の設定次第だから、定数へ焼いた時点で設定が変わると
  静かに足りなくなる。**実機では、到着差より長い待ちを置いてあったのに顔ぶれが揃わなかった**
  （当時の作りの実測値は [`REQUIREMENTS.md`](REQUIREMENTS.md) §7 の表が持つ）
- **「生きている」は、直近 5 秒以内に何か届けたセンサー**（`FUSION_LIVE_MS`）。止まった台を
  毎回待たない。**一度も届いていない台は、観測点に最初のデータが届いてから 5 秒の間だけ
  生きている扱い**にする —— 起動直後・設定を変えた直後に、遅れて届く台を待たずに出してしまわないため
- **揃わないまま待ち続けないための頭打ち。** 届いたデータの時刻がまとまりの末尾から 0.6 秒
  （根拠は同 §7 の表）を超えたら、その時点の顔ぶれで出す。**ここまで待つのは揃わないときだけ**で、
  揃っていれば上限に関わらず即出す。**待ちの計時は届いたデータの時刻で行い、壁時計を見ない** ——
  見ると、生データの読み返しで実際の経過時間に振られて同じ入力から違う合成が出る
- **一度出したまとまりより前に届いたサンプルは、ライブでは混ぜない。** 押し出した後の波形は
  書き換えられないので、遅れて届いた分は数えるだけにする（毎分の要約の「観測点の合成に
  間に合わず混ぜなかったサンプル」）。**埋め直しは作り直しの仕事**（下記「取り戻した区間は作り直す」）
- **ホストが受け取った時刻より 2 秒を超えて先を名乗るサンプルは混ぜない**（`FUSION_MAX_FUTURE_MS`）。
  目盛りは届いたデータの時刻で進むので、1 台の時計が先へ飛ぶと、ほかの台のまとまりが届く前に
  「出した後」になり、観測点ごと止まる。まだ測っていない未来の値は届きようがないので、先を名乗るのは
  時計の壊れた台だと断定できる。**物差しはホストの時計で、台どうしは比べない** —— 比べ合いでは、
  全員の時計が壊れたときにどれが正しいかを決められない。**線を狭く取るのは、線より手前の先回りも
  その幅だけ観測点を止めるから**（1 パケットでも目盛りがそこまで進む）。2 秒は、時計のずれの見張りが
  知らせる 100 ms の 20 倍。代わりに**ホストの時計が 2 秒以上遅れると全員の分を捨てる**（合成は出なく
  なるが、センサーごとの震度は出続ける）。**線の内側の先回り（待ちの 0.6 秒〜2 秒）は混ぜる**ので、
  その幅だけ目盛りが進み、ほかの台の分を遅れとして落とすことがある（その幅までの穴が空くが、それより
  長くは止まらない）。このときに増えるのは「間に合わず混ぜなかったサンプル」のほうで、先を名乗った数には出ない捨てた数を数える（毎分の要約の「観測点の合成で
  受け取った時刻より先を名乗って混ぜなかったサンプル」）。作り直し（rewave）も控えに残った受け取りの
  時刻で同じ判定をする（受け取りの時刻が残っていない古い控えだけは判定しない）
- **抱えたまま混ぜずに捨てたサンプルも数える**（毎分の要約の「観測点の合成で抱えたまま混ぜずに
  捨てたサンプル」）。1 台が抱えるのは 60 秒ぶんまでで、それを超えた古い側を落とす。抱える幅は
  ふだん数秒なので、**0 が正常** —— 増えていれば合成の前提が崩れている
- **データの無いまとまりは 1 つずつ回さない。** 全員の時刻が大きく飛んだとき（長い停電の後）は、
  次にサンプルのあるまとまりまで飛ぶ
- **震度の流し込みは、3 方向とも解けた目盛りが続いている間は 1 本を使い続ける。** 欠けたら
  （一部の成分だけ解けた目盛りも含む）そこで締め、次に 3 方向とも解けた目盛りから作り直す。位置は作り直した時点の目盛りを原点に数える
  （`IntensityStream.push()` は位置 0 から数えるため）。**どれか 1 台の区間（`segmentId`）が
  変わっても作り直さない** —— 以前は駆動役の基板が再起動・パケット落ちするたびに、観測点の
  震度が助走からやり直しになっていた
- **差分 `d=(a1-a2)/2` は 3 軸のセンサーどうしの全ペアの組み合わせに適用する。** 要件原文が
  定めるのは 2 台の式だけなので、3 台以上のグループでも新しい式は作らない。値は目盛りの上で取る。
  2 軸の台は 1 台で東・北・上を持たないので、成分ごとの差を作れない（2 軸を含めて比べるのは上の「ずれ」）
- **`enabled: false` のセンサーは合成グループに入れない。**
  そのセンサーはそもそも波形を作らない（`enabled` の適用は上記「読み取りへの適用」を参照）
  ので、混ぜても永久に届かない相方が残るだけ。**2 台しか割り当てていない観測点で、
  どちらか 1 台を無効化すると、その観測点の合成は丸ごと止まる**（残り 1 台では
  合成する相手が居なくなるため）

### 換算が正しいかを自分で診る

**1 件ずつの検査では届かない穴がある。** 読み取りの上限検査（上記「換算を、組み立てより先に
済ませる」）が見るのは「名乗るフルスケールを超えていないか」だけなので、**倍率が小さすぎる向きは
素通りする** —— 本物の強い揺れが弱く出るほうで、しかも出てくる値はすべて有限で範囲内。
同じ形の穴が平均引き（上記「重力を引くのはここで決める」）にもあり、誤って切ると静止していても
計測震度 4.48〜6.23 が出続ける。

**どちらも 1 パケットの中を見ても判らない。判るのは、静止した数十秒をまとめて見たときだけ。**
だから受信層が持つ。使うのは型番に依らない 2 つの事実。

1. **静止した基板の 3 軸合成は約 980 gal（1 g）。** 傾けても大きさは変わらないので、設置の向きを問わない
2. **合成のばらつきが小さいなら、計測震度も低いはず**

2 つ目は**静止した窓が 1 つでは言い切らない。** 震度は直近 60 秒の最大を保つ値なので、地震の揺れが
止んだ直後の静かな窓にも、揺れていた間の震度が残っている。そこで**続けて静止した窓が、窓 1 つ ＋
振り返りの 60 秒 ＋ 余裕 10 秒（フィルタの尾と震度が届くまでの遅れ）を覆うだけ揃ったときだけ**
突き合わせる。30 秒の窓なら 4 つ（120 秒）。

窓は**受け手の時計で 30 秒**。基板が名乗る時刻を使わない —— 診たいものの中にヘッダの名乗りが
含まれているのに、窓を区切る根拠まで同じ名乗りへ預けることになる。持つのは走和だけで、
窓のサンプルは溜めない。

**同じ窓から、取り付けの傾きも出す。** 上の 2 つは 3 軸**合成**しか見ないので向きを問わないが、
**軸ごとに分けた平均は、静止していれば重力ベクトルそのもの**で、そこから傾きが読める。
走和を軸ごとに持つだけで済み、静止しているかの判定（合成のばらつき）もここにしか無いので、
集めるのはこの 1 箇所にまとめている。使い道と、そこから何が決まって何が決まらないかは
上記「管理コンソール本体」と REQUIREMENTS.md §16。

**震度は止めない。** 診断が異常を指しても値は出し続け、数えて報せるだけ。桁の狂った値より
「震度が黙る」ほうが重い。

**見るのは桁だけ。** 許容は 1 g の **1/3〜3 倍**で、狭められないのは個体差のため（下記「分かっている
限界」）。大きすぎる向きは、名乗るフルスケールも一緒に大きくなければここへ届かない —— 静止時の
合成は重力が乗る 1 軸でほぼ決まるので、±2 g を名乗ったまま倍率だけ狂った値は上限検査
（2 × 980.665 × 1.05 ＝ 2059.4 gal）が 2.1 倍で先に落とす。この幅に掛かるのは 3 倍からなので、
**2 つの上限は重ならない**（`gravityCheck.test.ts` の「手前の上限検査との関係」が固定している）。

出す先は `GET /status` の `gravity`（センサーごとに、最後に閉じた窓 1 つぶん）と、毎分の要約・
終了時の締めくくり。**両方へ出す** —— `/status` は見に来た人にしか届かず、記録の行は間引きを通る。

**「判定が出ていない」ことも数える。** 窓は波形が届いたときにしか閉じないので、窓より短い間隔で
再起動を繰り返す基板は判定が一度も出ない。そのままだと一覧に現れず「まだ 30 秒たまっていない
だけ」と見分けが付かないので、**捨てた窓の数**（`restarts`）を別に出す。同じセンサーの軸の本数が
変わって覚えた静止窓を捨てたときも数える（`axisReshapes`）—— 6 面法の材料が黙って 0 へ戻ると、
「まだ揃っていない」だけに見える。

**2 軸のセンサーは静止窓だけを覚え、倍率の判定は出さない。** 判定は 3 成分の合成の大きさ（1 g）で
診るので、2 本の軸からは決まらない。静止しているかは軸ごとのばらつきで見る（3 軸の静止窓と同じ）。

**数は 1 つのまとまりで受け渡す。** 帳面が返すのは「センサーごとの直近の判定（`verdicts`）＋
起動してからの累計」で、状態の口も要約もそこから取る。**欄を 1 つずつ並べる形にすると、数を
足したときに渡し忘れる** —— 実際この機能は 4 巡続けてそれをやった（`restarts` を足したのに
状態の口へ出さず、直したら隣の 3 つに同じ穴が残っていた）。

## 地震検出（`src/detection/`）

観測点の合成波形から「平常時より強く揺れた区間」を切り出し、気象庁の地震情報と時刻を
照らし合わせて、**地震だったかどうかを揺れ 1 件ずつの記録に残す**（REQUIREMENTS §6・§9）。

```
合成波形 ─→ 引き金（区間を切る）─→ 区間が閉じたら P/S を拾う＋揺れ方を分ける ─→ 記録（版 1・照合待ち）
気象庁の地震情報 ──────────────────────────────────→ 時刻が合えば「地震」の版を足す
照合の期限（区間が閉じてから 15 分）───────────────→ 合わなければ揺れ方で決めた版を足す
```

### 見るのは観測点の合成波形

センサー 1 本・基板 1 枚では足りない。実機の記録で、ある M3.5 の地震 は合成では平常時の
5.3 倍になったが、センサー単体では 1.4 倍にしかならなかった（9 本を混ぜると無相関な
ノイズが約 1/3 になる。→「複数センサーの波形合成（§7）」）。**合成波形を押し出す・残すのと
同じ 1 本の流れから受ける**ので、検出に使った波形と画面に出る波形は食い違わない。

### 区間を切る（引き金）

地震計で広く使われる STA/LTA（短い時間の平均の強さ ÷ 長い時間の平均の強さ）を使う。平常時より
何倍強く揺れているかを、その場の雑音の大きさに合わせて測れる。値は `src/detection/quakeTrigger.ts` の
`TRIGGER_CONFIG_DEFAULT`。

| 項目 | 値 | 理由 |
|---|---|---|
| 見る帯域 | 水平動の 5〜10 Hz | 近い M3 級の S 波がこの帯に集まっていた（帯域で絞らないと 2.8 倍、絞ると 5.3 倍） |
| 比 | 時定数 1 秒で均した強さ ÷ 時定数 60 秒で均した強さ（振幅の比） | |
| 始める・閉じる | 2.5 倍を超えたら始め、1.5 倍を下回ったまま 5 秒戻らなければ閉じる | P と S の間の静かな数秒を 1 区間に繋ぐ |
| 長さの上限 | 180 秒 | 超えたら閉じて、平常時の基準を作り直す |
| 助走 | 起動・途切れの後 60 秒は引かない | 平常時の基準が落ち着くまで |

**区間の最中は平常時の基準を進めない。** 進めると、長い揺れの間に基準が持ち上がって比が
落ちていく。波形が 1 秒以上途切れたら、区間を閉じてフィルタと基準を作り直す。

### 揺れ方で分ける

区間の帯域ごとの強さを、5〜10 Hz の水平動に対する比で見る（値は `src/detection/eventClassifier.ts` の
`SHAKE_ENVELOPE_DEFAULT`）。枠に収まれば「地震らしい」、
外れれば「生活振動らしい」。**振幅そのものは見ない** —— 強い地震ほど大きいので、大きさで
弾くといちばん大事な揺れを落とす。

| 比（÷ 5〜10 Hz の水平動） | 地震らしい枠 |
|---|---|
| 上下動（5〜10 Hz） | 0.30〜0.65 |
| 水平動 0.5〜2 Hz | 0.40 以下 |
| 水平動 2〜5 Hz | 0.60 以下 |
| 水平動 10〜20 Hz | 0.80 以下 |
| 水平動 20〜45 Hz | 0.70 以下 |

**これは最終判定ではない。** 地震だと決めるのは下の照合で、揺れ方の分類が効くのは照合が
合わなかった揺れの扱いだけ。枠は実機の記録で気象庁の地震と一致した 6 件（
M2.8〜3.5）を囲んで置いた。外へ出る典型は、お掃除ロボット（上下動が
水平動の 0.12〜0.2 倍しか無い）と、基板を手で動かした揺れ（上下動と低い周波数が多い）。

### P 波・S 波を拾う

S は引き金の 6 秒前から 3 秒後までの水平動、P はその S の 1〜30 秒前の上下動（2〜8 Hz）から、
AIC（赤池情報量規準。静かな前半と揺れている後半の切れ目を統計的に探す）で立ち上がりを探す。
前後の強さの比（SNR）が 2 未満なら拾わない。値は `src/detection/phasePicker.ts` の
`PHASE_PICK_CONFIG_DEFAULT`、窓の切り出しは `src/detection/quakeDetector.ts` の `phaseWindowFrom`。

**P はほぼ拾えない。** 近い M3 級でも、P 波の立ち上がりは雑音の 0.5〜1.9 倍にしかならなかった
（実機で一致した 6 件）。拾えなかったときも、試した点の SNR は記録に残す。

**窓の中で波形が途切れていたら、途切れの後ろから窓を始め直す。** 詰めて繋ぐと S の時刻がずれ、
非有限値はフィルタを以後ずっと壊すので、どちらも跨がない。P を探す範囲は短くなるが、S を探す範囲
（引き金の 10 秒前から）が残っていれば拾う。**残っていなければ拾わない** —— 理由は記録の
`phaseWindow` に残る（`picked` 以外なら拾っていない。`gap`・`non-finite`・`no-data`（窓へ置ける
波形が 1 つも無い）・`failed`）。

### 気象庁の地震情報と照らし合わせる

**家の中の 1 か所の記録だけでは、M3 級の地震と生活振動を見分けきれない。** 実機の記録で、
引き金の強さ・上下動の割合・揺れの長さが、有感地震の一覧に無い揺れと M3 級の地震とで
重なっていた。いちばん確かな裏付けは、気象庁がその時刻に地震を出しているかどうか。

**地震情報は P2PQuake から受ける**（震源・震度に関する情報。code 551）。照合のための外への通信は 2 つだけ
（管理コンソールの「波形の記録」へ地震を重ねるための通信は別。上の「保存した波形を読み返す」）。

| 先 | 回数 |
|---|---|
| `wss://api.p2pquake.net/v2/ws` | 常時 1 本。切れたら 5 秒から倍々に間を空けて繋ぎ直す（5 分で頭打ち）。**間を 5 秒へ戻すのは、60 秒以上繋がってから切れたときだけ**（開いてはすぐ切れる状態で 5 秒ごとに繋ぎ直さないため） |
| `https://api.p2pquake.net/v2/history?codes=551&limit=50` | **繋がるたびに 1 回**（途切れていた間の地震情報を取り戻す）。繋ぎ直しが続いても 1 時間に十数回まで |

**時刻の合わせ方**（`src/detection/quakeMatch.ts`。期限と記憶の長さは `src/detection/shakeEventBook.ts`）。
地震情報の震源と観測点の位置から、JMA2001 走時表（予報円と同じ表。
`src/utils/travelTime.ts`）で P 波・S 波が届く時刻を引き、区間の始まりが「最も早い P の 5 秒前」
から「最も遅い S の 15 秒後」までに入れば一致とする。地震情報の発生時刻は分単位で届くので
その 1 分ぶん、深さが分からなければ 0〜100 km ぶん幅を広げる。

**判定は 5 段。** 記録の `verdict`。

| `verdict` | 意味 |
|---|---|
| `quake` | 気象庁の地震情報と時刻が合った |
| `pending` | 照合を待っている（区間が閉じてから 15 分） |
| `quake-like` | 照合できなかったが、揺れ方は地震の枠に収まる |
| `local-like` | 照合できず、揺れ方も枠の外 |
| `unchecked` | 照合の期限までの間に地震情報の受信が途切れていて、合わなかったとは言えない |

**期限を過ぎてから届いた地震情報でも、2 時間以内なら `quake` へ上書きする。** 同じ地震の続報で
規模・深さ・震源が変われば、その値でもう 1 版足す。

**受け取らない構成にもできる**（`SEISMO_QUAKE_FEED=0`。外へ繋げない端末向け）。そのときは
照合できたとは一度も言えないので、すべて `unchecked` に倒れる（起動時に 1 行警告する）。

### 記録

```
data/events/<YYYY-MM>/<id>.json   揺れ 1 件につき 1 本。中身はその揺れの最新の版
```

置き場所は `SEISMO_EVENT_DIR` で変えられる。どの月へ入れるかは揺れの始まり（日本時間）で決める。
`id` は `<観測点>-<区間の始まり>` で、照合の結果が出ると同じ `id` のまま `rev` が 1 つ進む ——
**そのたびに一時ファイルへ書いて `fsync` してから名前を付け替える**ので、書いている途中で落ちても
前の版が残る。古い版で新しい版を上書きしようとしたら、書かずに書き損ねとして数える。**波形は写さない**
（区間の時刻があれば、生データと合成波形から読み返せる）。1 本 1 KB ほど。項目の意味は
`src/detection/shakeEvent.ts`。

**基板どうしで揺れ方が揃っているか（REQUIREMENTS §8）はまだ見ていない。** いまの基板は 1 か所に
まとまっていて、足音も家じゅうの基板に同じように乗るので見分けの役に立たない。見ていないことを
`spatialConsistency: 'not-evaluated'` として値で残す。

**終了の合図で、開いている区間を閉じて記録する。** 照合は済まないので、照合待ちの版のまま残る
（次の起動は引き継がない）。

### 配る口

```
GET /events?from=<unix ミリ秒>&to=<unix ミリ秒>[&station=<観測点ID>][&limit=<1〜500>][&hide=local]
```

区間の始まりが `[from, to)` に入る揺れを、`id` ごとの最新版で返す。**範囲の広さに上限は無く、件数で区切る**
（2026-10-07 ユーザー承認）—— 新しいほうから `limit` 件（既定で上限の 500 件）まで返す。重さは範囲の広さではなく
範囲の中の記録の数で決まるので（1 件あたり約 1.2 ミリ秒・0.7 KB）、縛るなら件数で縛る。

- **区切ったら `truncated: true` と `coveredFromMs` を添える。** `[coveredFromMs, to)` に始まりが入る記録は漏れなく返したので、
  続きは `to=<coveredFromMs>` で読めばよい（境目の記録が 2 回出ることはあるが、同じ `id` なので受け手で揃う）。
  ファイル名の始まりは整数ミリ秒へ丸めた値なので、同じ始まり（±1 ミリ秒）の記録は区切りで分けない
- **新しい月から 1 か月ずつ一覧し、区切りに届いたらそれより古い月は一覧しない**（蓄積した年数で重くならない）
- `station` と `hide=local`（判定が `local-like` のものを除く）は**数える前に**掛ける
- **読めなかったファイルを必ず添える**（`unreadableFiles`。区切りより古くて開かなかったものは入らない）——
  無いと「揺れが無かった」と「記録が壊れていた」が同じ空の配列に見える。`/status`・`/waves` と同じく認証を持たない

**押し出しにも乗る**（`/stream` の `shake-event`）。版が 1 つ増えるたびに 1 件で、量が小さいので
**`?wave=` の指定に関わらず届く。**

**動いているかは `/status` の `detection` を見る。** `shakes`（記録した揺れ）・`pending`（照合待ち）・
`feed`（地震情報の受信。止めてあれば `null`）・`store`（書けた版と書き損ね）のほか、異常の
数え上げとして `failures`（**揺れを記録できなかった**）・`droppedChunks`・`phaseWindowsBroken`・
`phaseFailures`・`resets` を持つ。異常の数え上げと書き損ねは、地震情報の受信の数え上げ（繋ぎ直した・
履歴を取れなかった・読めなかった報）と一緒に**毎分の要約と終了時の累計にも出る**。

### 静かだっただけか、止まっているか

**揺れの記録が 0 件のまま続いても、それだけでは故障か静かなだけかが分からない。** 数え上げは
どれも 0 のまま動かない。そこで `/status` の `detection.triggers` に、観測点ごとの引き金の
いまの状態を出す（`src/detection/quakeTrigger.ts` の `TriggerHealth`）。下の表は見分けに使う欄だけで、
ほかに `stationId`・`inEvent`（揺れの区間を開いている）・`onRatio`（引き金の比）なども出る。

| 欄 | 意味 |
|---|---|
| `lastFedAtMs` | 検出器が最後に波形を使えた時刻（**ホストの時計**）。一度も無ければ `null` |
| `lastSampleMs` | その波形の時刻（**基板が名乗るデータの時刻**） |
| `armed` / `warmUntilMs` | 引き金を引ける状態か／助走が明ける時刻 |
| `baselineGal` | 平常時の揺れ（60 秒で均した強さの振幅・gal） |
| `ratio` | いまの比（平常時の何倍か）。引き金は `onRatio`（2.5 倍） |
| `peak24h` / `peakWindowFromMs` | 直近 24 時間（データの時刻・1 分単位）で比がいちばん大きかった時刻と値／その範囲の頭 |
| `droppedChunks` | その観測点で、刻みが読めず捨てた合成波形のまとまり。**届いているのに使えていない**形の手がかり。上の `detection.droppedChunks` は全観測点の累計で、設定から外した観測点の分も含むので、こちらを足し合わせても一致しないことがある |

止まって見える形は 4 つあり、どれもここで見分けられる。

| 形 | どう見えるか |
|---|---|
| 静かで、比が引き金に届かないだけ | `armed` で、`peak24h.ratio` が 2.5 倍未満 |
| 波形が来ない（有効なセンサーが 2 台に満たず合成が組まれない等） | `lastFedAtMs` が古いか `null`。**設定にある観測点は、検出器がまだ無くても載る** |
| 途切れが繰り返し、助走から抜けられない | `armed` が立たない |
| 平らな値しか来ない | `baselineGal` が 0 |

**「届いているか」はホストの時計で見る。** データの時刻で見ると、基板の時計が先へずれていると
最後のサンプルが「未来」になり、止まっても古くならない。比の最大は逆に、引き金と同じデータの時刻で引く。

**1 時間に 1 行、記録にも残す。** `/status` は直近 24 時間しか見せないので、それより前を遡って
調べるため。毎分の要約には載せない（観測点ごとに 1 行なので 1 日 1440 行ずつ伸びる）。

```
[detect] station-1 この 1 時間: 比の最大 1.59 倍（10:23）・平常時の揺れ 0.16 gal・見張り中
[detect] station-1 この 1 時間: 波形が届いていない（最後は 09:12）
```

時刻は日本時間。状態は `見張り中`・`助走中（あと N 秒）`・`揺れを記録中` のどれか。次の場合は警告として出る。

- 波形が 1 分以上使えていない
- 一度も波形が来ていない
- その 1 時間に引き金を引ける状態のサンプルが無い（`比の最大 なし`）

### 取りこぼした揺れを後から記録に起こす（`redetect.ts`）

**ホストの検出が見ていなかった区間の揺れを、保存してある合成波形から後で起こす道具。** 検出を入れる前の期間・
ホストを止めていた間・起動の助走の間がこれに当たる。ホストとは別のプロセスで、ホストの機械の上で手で叩く
（2026-10-07 ユーザー承認）。ホストを動かしたままでよい。

```bash
# 控えに残っている全期間・設定にある全観測点（配り先の <置き場所> の直下で）
npx tsx seismo-host/redetect.ts
# 範囲を絞る・書かずに件数だけ見る
npx tsx seismo-host/redetect.ts --from 2026-10-03T00:00:00+09:00 --to 2026-10-04T00:00:00+09:00 --dry-run
```

- **入力は合成波形の控え（`data/wave/`）。** ライブの検出器が受け取ったのと同じ波形で、読むだけ。
  範囲の 5 分前から流して助走させる（その間に始まった揺れは記録しない）
- **検出・記録の部品はライブと同じ**（`QuakeDetector`・`ShakeEventBook`・計測震度相当の `IntensityStream`）。
  起こした記録はライブの記録と同じ形で、出どころの印は持たせない（2026-10-07 ユーザー承認）。照合の期限（15 分）は
  流している波形の時刻で進め、書いた時刻（`writtenAtMs`）だけ実際に書いた時刻を入れる
- **既に記録がある揺れは書かない**（id は観測点と始まりの時刻なので、同じ揺れは同じ id になる）。ライブで書いた
  記録が優先される
- **照合に使う地震情報は、流す期間ぶんを P2PQuake の履歴（`/v2/jma/quake`）から先に取る。** 古い順に
  100 件ずつ、2 本目からは 6.5 秒空ける（上限は 10 回/分）。ページは 30 本まで。**取りきれた範囲だけ**合わなかった揺れを
  揺れ方で決め、それ以外は「照合できず」にする。取りきれなかったと数えるのは、取れなかった・ページの上限で切った・
  取った時刻の直前 30 分・読めなかった報の時刻から 30 分（時刻すら読めない報があれば全期間）
- 通信を出したくなければ `--quakes <保存した一覧.json>` で渡す。この場合、読めなかった報が 1 件でもあれば、
  渡した一覧の全期間を「照合できず」にする（一覧のどこが欠けているかを道具の側で確かめられないため）
- **観測点の位置とセンサーの顔ぶれは、その時刻に効いていた設定（`config/stations.xml` の履歴）から引く。**
  設定の記録より前の時刻は、最初の記録の設定で照らし、その回数を出す（記録が無いだけで、観測点が無かったわけではないため）
- 起こした記録は、揺れの記録タブを開き直すと出る（押し出しは無い）
- 最後に観測点ごとの件数を出す（書いた・既にあった・助走の間で記録しなかった・書けなかった版・判定の内訳）。控えは「ファイルの無い時」
  「開けなかった時」「途中で打ち切った時（バイト数）」を分けて出す（いま書いている時の末尾は数えない）
- **終了コードは、地震情報を取れなかった・書けなかった版がある・流し直しが途中で止まった・途中で例外を受け止めた・
  その時刻の設定を引けなかった（位置とセンサー無しで記録した）、のどれかがあれば 1。** 地震情報の取得の失敗は標準エラーへ出る。
  観測点は 1 つずつ別に流すので、1 つが途中で止まっても残りの観測点は最後まで流れる（止まった観測点は、名前つきで標準エラーへ出る）
- 限界が 3 つある。
  - 控えに同じ区間が 2 度入っているとき（取り戻した分から作り直した区間。#596）、いまの読み手は作り直しの印を
    見ないので、時刻で並べて先に来た方を採る
  - ホストがその瞬間に同じ揺れを書いていると、どちらの版が残るかは決まらない（どちらも同じ部品を通るので、
    中身はほぼ同じ）
  - 設定の記録が始まる前に観測点を移していた場合、記録より前の揺れは移した後の位置で照らされる。出るのは
    「最初の記録の設定で照らした」回数だけで、位置がずれていたかどうかは分からない

### 評価台

過去の生データを流し直し、気象庁の地震と突き合わせて数える（`bench/`）。**実機と同じ部品**
（`QuakeDetector`）を通すので、評価した値と実機の値は食い違わない。**通信を出さない** —— 地震の
一覧は先に取って渡す。中身は P2PQuake の地震情報（code 551）の配列で、`/v2/history?codes=551` か
`/v2/jma/quake` の応答をそのまま保存したもの（取る前にリクエスト数を見積もること）。

生データの置き場所には、実機の `seismo-host/data/raw/` から評価したい日のディレクトリ
（`<日>/raw-<日>T<時>.mseed3`。前後の日も、あれば一緒に）を、その直下に実機の `seismo-host/config/stations.xml`（当時の観測点の
設定。履歴も入っている。無いと止まる）を写しておく。設定を別の場所に置くなら `--stations` で指す。

```bash
# 合成波形の控えを 1 日ずつ作る（評価したい日の数だけ繰り返す。控えの無い日は評価で飛ばされる）
for day in 2026-09-28 2026-09-29 2026-09-30 2026-10-01 2026-10-02 2026-10-03; do
  npx tsx seismo-host/bench/build-station-cache.ts --day "$day" --station <観測点ID> --raw <生データの置き場所> --out <控えの置き場所>
done
# 控えを検出器へ流し、地震の一覧と突き合わせる（観測点の位置は省けない）
npx tsx seismo-host/bench/bench-detect.ts --days 2026-09-28,2026-09-29,2026-09-30,2026-10-01,2026-10-02,2026-10-03 --station <観測点ID> --lat <観測点の緯度> --lon <観測点の経度> --labels <地震の一覧.json> --cache <控えの置き場所> --radius 200
```

**`--station`・`--lat`・`--lon` は自分の観測点の値を渡す**（観測点の設定の `stationId` と座標）。
`--lat`・`--lon` は地震までの距離と走時を測る起点で、違う値だと照合の窓がずれる。設定の履歴に無い
`--station` を渡すと控えを作らずに止まる。控えは生データが変わっていなければ作り直さないので、
同じ日をやり直すなら `--force` を付ける。

日ごとに概要の 1 行（揺れの件数・地震と一致した数・一致しない揺れの内訳）と、範囲内の地震
1 件ずつの「当たり」か「取りこぼし」の行が出て、最後に合計が出る。`--events` を付けると
区間を 1 件ずつ出す。

2026-09-28〜10-03 の 6 日（自宅の観測点）で回した結果:

| 対象 | 結果 |
|---|---|
| 近い地震・M3.0 以上 | 5 件中 5 件を検出 |
| 近い地震・M2.8 | 5 件中 1 件 |
| それより小さい・遠い | 0 件（M2.0〜2.7 の 4 件と、遠い M3.2） |
| 地震と一致しない揺れ | 90 件（地震らしい 18・生活振動らしい 72） |

**「一致しない」の中には、有感にならなかった地震が混ざりうる**（P2PQuake の地震情報は震度 1
以上の地震にしか出ない）。そこで「地震らしい」18 件は、無感の地震まで載る気象庁の
[震源リスト](https://www.data.jma.go.jp/eqev/data/daily_map/)（2 日前の分まで公開される）とも
照らした。取りこぼさないよう、上の照合より窓を広く取った（走時表で、揺れの始まりが P の 10 秒前〜
S の 30 秒後に入る 500 km 以内の地震）。同じ照らし方で、有感の地震と一致した 6 件を照らすと 6 件とも
見つかる（M2.8〜3.6。この観測点での揺れの大きさは 1.62〜2.95 gal）。

**18 件とも地震ではなかった。** 15 件は時刻の合う地震が無い。残る 3 件は時刻だけ合う地震があったが、
規模に対して揺れが大きすぎる —— M1.9 で 2.8 gal、M0.4 で 2.1 gal、M0.8 で
13.8 gal。近い M3 級でも 2.95 gal 止まりなので、それより小さい地震で
同じかそれ以上の揺れは出ない。M1.9 は規模も小さく遠いので、なおさらその
地震の揺れではない。

**枠の中には生活振動が 1 日 3 件（6 日で 18 件）残る。** 枠は詰めず、見分けは気象庁の地震情報との照合に任せる。
「生活振動らしい」72 件は震源リストと照らしていない。

## 実測値の出どころ（静止時の震度相当・時刻のばらつき・計算時間・保存の嵩）

この文書が挙げる実測値は、**基板を実際に動かして取った記録から出している。生の波形は
版管理していない**ので、どれもリポジトリからは確かめ直せない —— 数字を出し直すには
記録を取り直すことになる。**量がその方針の理由**で、基板 3 枚で 1 日 347 MB になる。

記録は 2 本ある。**8 時間**のもの（静止時のノイズフロアと、時刻のばらつき 2.5〜4.7 ms）と、
**ある有感地震の前後**（重力を 1 秒の平均で引く根拠。上記「計測震度相当」）。1 点あたりの計算時間は
同じ基板で 120 秒ぶんを流して測った。

**自己診断のしきい値だけは別の記録から出している** —— 3 台 9 センサーを静止させて
**90 秒**（3 軸合成の平均と、軸ごとのばらつき）と**別に 30 秒の窓**（3 軸合成のばらつき）
の 2 通りを測った。**90 秒**の実測では合成が 0.670〜1.232 g に散り、軸ごとのばらつきは
1.06〜1.86 gal に揃っていた。**この 2 つが揃って初めて「倍率ではなく 0 点の個体差」と
言える**ので、片方だけでは足りない。**「静止しているか」を判定するしきい値は
30 秒の窓の実測から出している** —— 3 軸合成のばらつきは 1.39〜1.57 gal だったので、
その 3 倍を上限にした。

**生データの量は、実機のホストが 10/02 の 1 日に受け取ったものから出している**（基板 3 枚・
センサー 9 本・258 万パケット。値は上記「生のパケットを miniSEED 3 で時間ごとに残す」の「量」）。
その 1 日を受け取った順に流し直して miniSEED 3 を書き、大きさを測った。

## 分かっている限界

- **地震検出は P 波をほぼ拾えず、複数の観測点・基板の揃い方も見ていない。** 近い地震・大きな
  地震の揺れ方も確かめていない（→「地震検出」）

- **100 ms より短い中断は見分けられない。** 版 2 の起動 ID が焼かれれば鍵そのものが
  変わるので、この弱点は版 1 に限られる
- **一度も時計が合わない基板は、震度は出続けるが合成は永久に組めない。** 時刻は終始
  「辻褄が合う」ので区間は切れず（`timebase-jump` が起きない）、足場は 1970 年のまま
  居座る。他の区間と時間で重ならないので合成が組めず、**震度は相対的な計算なので
  単独で出続ける** —— 外からは「動いている」ようにしか見えない。気づく手掛かりは
  毎分の要約に出る `timebase-epoch` の警告だけ
- **足場が「未来すぎる」ことは検知していない。** 見ているのは下限（2020-01-01）だけ。
  破損したパケットが巨大な時刻を名乗った場合、上と同型の壊れ方をするが気づけない
- **一部だけが新しいパケットは丸ごと捨てる。** 継ぎ接ぎするより、落とすほうが安全
- **取り戻した 1 まとまりの一部の軸だけ書けて訊き直すと、書けていた軸の波形は 2 本残る。**
  このホストが読むとパケットは 1 つにまとまるが、外の道具では重なって見える
  （→「生のパケットを miniSEED 3 で時間ごとに残す」）
- **書き込みが詰まって知らせが来ないと、全ての基板の取り戻しが止まる。** 止まっていることは
  `/status` と毎分の要約に出る（→「届かなかった分を基板へ取りに行く」）
- **当てはめから外れ値を除く仕組みは無い。** 名乗られた時刻のばらつき（ミリ秒）は
  `residualRmsMs` に出るので、見張るのは読む側の仕事。**平常時の目安は数ミリ秒** ——
  実測は 2.5〜7.6 ms（前者は 8 時間・3 台の記録、後者は 2026-10-01 に実機の `/status` で
  見た値）
- **速度の上限は送信元アドレスを詐称されれば効かない。** 1 つずつ違うアドレスから撃たれると
  どの枠も満杯のまま使われるので上限には一度も掛からず、**枠を捨てた件数だけが動く。**
  その数は要約に出るが、止める手立ては無い
- **1 つのアドレスの裏に複数台がいると枠を分け合う。** 有線・無線の LAN で直につながる構成では
  起きないが、間に変換を挟めば起きうる。既定の上限（毎秒 100）は 1 台ぶん（毎秒 10）の
  10 倍なので、定常では 10 台まで収まる
- **記録の間引きに、重要なものを先へ回す手立ては無い。** 同じ種類の枠（64）を使い切ったあと、
  その種類の 2 つ目以降は最大 60 秒待たされる。**どれを急ぐかを指定できない**
- **「その他」へ合算した内訳は、あとから復元できない。** 何がそこへ混ざったのかは残らない
  （合計は正しいまま）
- **認証が無い。** 読み取り専用で LAN へ開く前提なので、繋げる人は誰でも震度・波形・機材の様子を読める。
  **書き込みの口は無い**ので、読まれること自体が唯一の危険
- **押し出しの購読には上限があり、達したら新しいほうを断る**（8 本）。古いほうを切る作りにすると、
  ブラウザの自動再接続で双方が延々と切り合う
- **合成した波形は `?wave=station` 以上を頼んだときだけ出る**（`station-wave` イベント。作り直した範囲の知らせ
  `station-wave-revised` も同じ）——
  震度だけを見に来た相手へ毎秒 15 KB を流す理由が無い。
  **差分の時系列は頼んだ 1 組だけ出る**（`?diffStation=` ほか 5 欄。`?wave=` とは独立で、
  全ペアを一度に受け取る道は無い。対ごとの強さは `GET /status` に出る。
  上記「複数センサーの波形合成」）
- **押し出しが壊れて切れた数は残るが、相手がただ閉じた回との区別はそれだけ。** どちらも購読者が
  1 つ減る点は同じなので、どの端末が落ちたかまでは追えない
- **書き出せない間に届いたパケットの中身は残らない。** 溜め込んで後から書く仕組みは持たない
- **書き出しが追いつかないときは捨てる**（抱えたまま 8 MB を超えた分）。際限なく抱えると
  メモリが膨らむので、失うほうを選んでいる
- **締めくくりは 30 秒で切り上げる。** 開いている本を閉じ終わるのをそれ以上待たない（待ち続けると、
  終了の合図を受けてもプロセスが終わらない）。**切り上げたときは、まだ書き出せていなかった分を
  失いうる** —— 切り上げたことは記録に出るが、その中身は残らない
- **書けたと返ってから失われる形は検知できない。** `fsync` を掛けていないので、
  ネットワーク越しのドライブなどで「書き込みは成功と返ったのに実際には残っていない」
  という失い方をしても、**件数は 0 のまま**になる
- **ディスクの空きを見張る仕組みは無い。** 埋まったら保存だけが止まり、止まったことは
  要約に出るが、**埋まりそうなことは事前に判らない**
- **終了の合図（SIGINT・SIGTERM）を実際に受けた確認は取れていない。** Windows には
  この仕組みが無く、外から送る手立てがない（止める口 `POST /api/shutdown` から締めくくりへ入り、
  最後まで走って終わることは実際に確かめてある）。**テストで固定してあるのは締めくくりの中身と順序**
  （`closeAll()` が残りの震度と待たせていた合成波形を出し、1 本の失敗で他を道連れにしないこと。
  受信口を閉じてから波形の保存を閉じるまでの順序は `main.ts` の `closeHostCore` が持つ）で、
  合図を受けてそこへ入るまでの配線は押さえていない
- **通知の口（`onError`）自身が投げた場合は受け止めない。** データグラムの受け手を囲うのは
  中身をこちらで決められないからで、通知の口は自分たちのコード。網を張るとその欠陥が
  静かになるので、落ちる側に倒してある
- **換算の自己診断が見るのは桁だけ。** 合成の平均は倍率だけでなく**センサーごとの 0 点のずれ**でも
  動くので、幅を狭めると個体差が警告に化ける —— 手元の MPU6050 9 個の実測は **0.670〜1.232 g**
  だった（`ugPerLsb` はどれも同じ値を名乗り、軸ごとのばらつきも揃っていたので、倍率ではなく
  0 点と感度の個体差）。**レンジの 2 倍の取り違えは捕まらない** —— その個体差と重なるので、
  捕まえにいくと正常な個体を毎分警告することになる
- **3 軸を名乗らないセンサーは、自己診断の一覧に現れない。** 波形を 1 つも受けない流れは覚えを
  作らないため、「まだ窓が閉じていない」のか「この構成では永久に診断されない」のかは
  `/status` の `gravity` だけでは見分けが付かない。震度が出ない理由のほうは
  `sensors[].lastSkipReason` に出る
- **診断の記録も間引きの枠を使う**（区分ごと 64）。1 つのセンサーが最大 3 つの鍵を使うので、
  台数が増えると他の記録より早く枠に届く。**溢れても数は無傷**で、劣化するのは 1 件ずつの行の粒度だけ
- **自己診断が投げても、同じパケットの後続の震度までは守れない。** 押し出しと標準出力より後ろへ
  置いてあるので**その読み自身は必ず出る**が、震度を出す繰り返しの中から呼んでいるため、
  そこで投げれば残りは止まる。**いまこの穴が開くことはない**（診断は値の比較しかしておらず、
  投げる経路を持たない）—— あとから検証や読み取りを足したときに備えた並びで、配る順番は
  `deliverReading` がテストで固定している
- **覚えていられる流れの数には上限がある**（64）。達すると、いちばん長く音沙汰の無い流れが
  閉じられる。**版 2 のファームは再起動のたびに別の流れとして現れる**ので枠は埋まっていく。
  閉じたことは記録に出るが、**古い流れを時間切れで手放す仕組みは無い**
- **換算の倍率が「小さすぎる」誤りは捕まえられない。** カウント値を加速度へ直すとき、
  センサー自身が名乗るフルスケールを超えた値は落とすので、桁が大きすぎる向き
  （静止している基板が強く揺れて見える）は止まる。**小さすぎる向きは素通りして、
  本物の強い揺れが弱く出る。** 同じ穴が「重力を引くかどうか」の取り違えにもあり、
  どちらも値は有限で範囲の中なのでどの検査にも掛からない。
  **捕まえるには静止しているときの重力（3 軸の合成が約 980 gal）と突き合わせる自己診断が
  要る** —— 窓と報告先が要るので受信層の担当

### 合成の顔ぶれが揃っているかを実機で測る

**まず `/status` の `uncoveredFusions` を見る。** 立ち上げ直後の数回を過ぎてから動かなければ
揃っている（実機の実測は上記の表）。**動き続けているなら**、下記の手順でまとまりの中の
位置を見る。

**`lastMemberCountMin`/`Max` だけでは足りない。** あれは直近のまとまりの
最小・最大なので、**まとまりの中のどこで欠けているかが出ない** —— #374 の症状
（末尾と先頭だけが決まって欠ける）はこれでは見えなかった。**押し出しから
`memberCount` の配列を集め、まとまりの中の位置ごとに数える**。

**`event:` 行が種別を持ち、`data:` は中身そのもの**（`kind` は入っていない。ここを
`data` の中に `kind` があると思って読むと 1 件も拾えない）。`station-wave` のフレームだけを
拾って `memberCount` を読む。**実際に動いた 1 行**（2026-09-30・この形で測った）:

```bash
curl -sN "http://<ホスト>:50506/stream?wave=station" | node -e "
require('readline').createInterface({ input: process.stdin }).on('line', (l) => {
  if (!l.startsWith('data:')) return
  const m = JSON.parse(l.slice(5)).memberCount
  if (m === undefined) return
  console.log('末尾3:', m.slice(-3).join(' '), '/ 先頭3:', m.slice(0, 3).join(' '))
})"
```

**`jq` ではなく node で書く。** この環境（Windows の Git Bash）と実機のどちらにも
`jq` が無く、**ホストは node で動いているので node は必ずある**。
`memberCount` を持つのは合成波形だけなので、種別を見ずに `data:` 行を拾っても
他の種別は `undefined` で落ちる（**選り分けたいなら `event:` 行を見ること**）。

見るのは 2 つ。

- **位置ごとの本数** —— 末尾から数えた位置・先頭から数えた位置で分けて数える。
  末尾が欠けるのは待ちが足りない形、先頭が欠けるのは抱えたサンプルを捨てすぎた形で、
  **原因が別なので混ぜて数えると切り分けられない**
- **センサーごとの到着の遅れと位相** —— `?wave=all` で単独の波形も取り、
  「受信した時刻 − そのまとまりのデータ終端」をセンサーごとに並べる。**この値の
  絶対値は基板と受信機の時計のずれを含むので使えない**（ずれの実測値と、測るたびに
  動くことは [`REQUIREMENTS.md`](REQUIREMENTS.md) §7 の注記枠）。**センサー間の差だけを読む**

**到着差が小さいときに測っても症状は出ない。** 要る待ちは「到着差 ＋ まとまり長」なので、
到着差が小さければ直す前の値でも足りることがある（#374 の 2 回の測定で到着差が
2 倍以上違った。実測値は同 §7 の表）。**再現しないことを「直っている」と読まないこと。**
