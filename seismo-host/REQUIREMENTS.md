## 1. システム全体の基本方針

ESP32 ＋ 加速度センサーで取得したデータを、常駐するホストアプリで集中処理する。

```
加速度センサー
    ↓
ESP32
    ↓ Wi-Fi
ホスト（常駐）
    ├─ データ受信
    ├─ 時刻整列
    ├─ 信号処理
    ├─ 地震 / P 波 / S 波判定
    ├─ データ保存
    ├─ センサー管理
    ├─ 設定管理
    └─ 押し出し / REST API
          ↓
    クライアント（PWA）
```

## 2. 基本設計思想

**ESP32 はできるだけ単純な「データ収集ノード」とする。** 地震判定のような高度な処理は
ESP32 では行わず、ホスト側で行う。

理由:

- アルゴリズムを後から変更しやすい
- フィルタ条件を変更できる
- P/S 波検出を改良できる
- 機械学習を後から追加できる
- 複数センサーをまとめて解析できる
- ESP32 のファームウェアを頻繁に更新しなくてよい
- 生データを後から再解析できる

## 3. ESP32 側の役割

- 加速度センサーから RAW データを取得する
- 約 100 Hz でサンプリングする
- 3 軸、または各センサーの全軸を取得する
- サンプルをある程度まとめてパケット化する
- Wi-Fi 経由でホストへ送る
- デバイス ID・シーケンス番号・時刻情報を付ける
- ファームウェア版数・センサー種類・稼働時間・Wi-Fi の電波強度・実サンプリングレート・
  再起動理由・OTA 状態を知らせる

**ESP32 側では原則として最終的な地震判定をしない。**

## 4. ホストアプリ

常駐させる。**クライアントが開いていなくても、受信・解析・保存を続ける**（→ §17）。
つまりクライアントは処理の主体ではなく、ホストの表示・操作の口として扱う。

### データ受信

- 複数の ESP32 から同時に受ける
- デバイス ID で識別する
- シーケンス番号で欠損を検出する
- サンプル時刻を管理する
- ESP32 どうしの時間を合わせる
- パケットロスを監視する

### センサーデータ処理

- RAW データを保存する
- 物理単位へ変換する
- オフセット・感度・軸方向・姿勢を補正する
- フィルタを掛ける
- 3 軸を合成する
- センサーを合成する（→ §7）
- 同型センサーを複数使ってノイズを下げる

### 信号解析

将来的に次を実装できる構造にする。

RMS / Peak / 周波数解析 / FFT・PSD / STA・LTA / P 波候補検出 / S 波候補検出 /
P・S の到達時刻 / S-P 時間 / 複数観測点の相関 / センサー間の coherence /
局所振動の判定 / 地震イベントの判定

## 5. 計測震度関連

気象庁の計測震度に相当する処理を実装する場合は、正式なアルゴリズムに沿う。

ただし自作なので、**正式な「気象庁震度」と誤認される表現は避ける**。画面では
「計測震度相当」「Calculated Intensity Equivalent」のような表現を使う。

**震度 1 未満も内部値として保持する**（+0.8・+0.2・−0.4・−1.0 など）。
ただし負の値を「震度 −1」のようには表現しない。

弱い地震については、加速度・PSD・SNR・P 波 SNR・P/S の到達時刻・計測震度相当値を使う。

## 6. 地震検出

**単純な加速度閾値だけにはしない。** 振幅 ＋ 周波数特性 ＋ STA/LTA ＋ P/S の特徴 ＋
複数観測点の相関を組み合わせる。

初期は従来型の DSP を中心にし、将来は機械学習によるイベント分類・P 波ピック・
S 波ピックを追加できる設計にする。

## 7. 複数センサー処理

**各センサーの RAW データは必ず個別に保存する。** 合成後のデータだけを保存しない。

同じ軸を複数のセンサーで測っている場合、合成値だけでなく**差分**も計算できるようにする。

```
差分  d = (a1 − a2) / 2
```

用途: センサー自己ノイズの推定・異常センサーの検出・センサー間の一致度確認・
coherence 解析・ロバスト平均。

> **合成の目的は「精度を上げること」ではない。** 原文は合成を単純平均 `a = (a1 + a2) / 2` と
> 書いているが、[`docs/implementation-plan.md`](../docs/implementation-plan.md) #93 の「難所」が
> 台数効果と品種混在時の悪化を測っていて、**逆数分散で重み付けしても良品単独から 0.004 段しか
> 改善しない**（この値と、単純平均がどれだけ悪化するかの導出はあちらにある）。だから #93 の
> 結論は「**平均ではなく役割分担**」 —— 最も低雑音の 1 台を最も静かな場所へ置いて基準器とし、
> 残りは分散して裏付けに使う。裏付けの軸は**振幅が空間的に揃っているか**（地震なら家じゅうが
> 同程度、足音なら 1 台だけ突出）。
>
> **合成を実装するなら、重みはノイズ分散の逆数にする** —— 単純平均は品種が混ざると床を
> 悪化させるため。ただし**それで床が下がると期待しないこと。この節の本題は差分と空間的な
> 一致のほうで、合成による精度向上ではない。**
>
> **合成するのは波形の段階で、計測震度を平均してはいけない**（対数量のため）。

## 8. 観測点間処理

複数の地点のセンサーをホスト側でまとめて解析する。

用途: 局所振動の除外・生活振動の識別・地震らしい共通信号の確認・建物応答の比較。

**住宅内程度の距離では、到達時間差による震源位置推定は目的としない。**
主目的は空間的な相関と局所ノイズの除去。

判別の軸は**振幅が空間的に揃っているか** —— 地震なら家じゅうが同程度に揺れ、
足音なら 1 台だけが突出する。

## 9. データ保存

### RAW データ

最低限、時刻・ESP32 の ID・センサー ID・センサー種類・各軸の RAW 値・シーケンス番号を残す。

**可能な限り元データを保持し、後から新しいアルゴリズムで再解析できるようにする。**

> **保存形式は miniSEED を採用する（2026-09-27 決定）。**
>
> いまの `src/receiver/rawStore.ts` は日ごとの追記型 NDJSON。**日単位の粗い絞り込みはできる**
> （`raw-YYYY-MM-DD.ndjson` でファイルが分かれる）が、**その日の中で特定の時刻へ頭出しする
> 索引は持たない** —— 読むにはその日のファイルを先頭から全部パースし直すしかない。「過去の
> 波形を見たり、複数センサーの波形を比べたりできるアプリにしたい」（→ §10 の地震ビューアー
> （リアルタイム画面・イベント履歴）。波形を持たない管理コンソールの話ではない）を満たすには
> 足りない。
>
> **ただし miniSEED 自体は時刻で頭出しする索引を規格として持たない。** レコードが連続して
> 並ぶだけなので、**時刻索引は別途自前で持つ**（保存のペイロード形式を決めることと、
> 頭出しの索引を設計することは別の話）。
>
> **選定の経緯**（なぜ自前二進形式ではなく miniSEED か・Node 側の実装をどう調達するか）は
> [`docs/implementation-plan.md`](../docs/implementation-plan.md) #93「保存形式で決まったこと」
> を参照。

### 処理済みデータ

必要に応じて、補正済み加速度・合成加速度・平均値・RMS・Peak・PSD・計測震度相当・
P/S の判定結果を保存する。

### イベント情報

地震候補のイベントごとに、開始時刻・終了時刻・P 波推定時刻・S 波推定時刻・S-P・
最大加速度・最大計測震度相当・P 波 SNR・観測したセンサー・観測した観測点・判定信頼度を
保存できる構造にする。

## 10. クライアント PWA

既存のリアルタイム地震ビューアー PWA へ統合する。クライアントは**表示・操作の口**として
使い、**解析処理そのものをクライアントに依存させない**。

### リアルタイム画面

各軸の波形・合成加速度・複数センサーの波形・複数観測点の波形・現在の加速度・
RMS・Peak・計測震度相当・P 波/S 波の状態。

### センサー一覧

ESP32 ごとに、オンライン/オフライン・デバイス名・デバイス ID・ファームウェア版数・
センサー種類・電波強度・サンプリングレート・パケットロス・稼働時間・最終受信時刻・OTA 状態。

### イベント履歴

過去のイベントについて、発生時刻・波形・最大加速度・計測震度相当・P 波・S 波・
P 波 SNR・観測点。

> **観測結果と機材の管理は別の場所に出す。** リアルタイム画面とイベント履歴（観測結果）は
> 地震ビューアーへ、センサー一覧（機材の管理）はホスト自身が配る管理コンソールへ。
> 宛先が違うため —— 片方は「揺れたかどうか」を見に来る人、もう片方は機材を運用する人。
> 管理側を公開中のビューアーへ入れると、一般利用者の画面が LAN 接続の制約を抱え込む。
> （同じ判断の詳細は [`docs/implementation-plan.md`](../docs/implementation-plan.md) #93）

## 11. 設定管理

**重要な設定値は、クライアントではなくホスト側を正として管理する。**
クライアントから変更要求を送り、ホストが保存・反映する。

対象: サンプリング関連・フィルタ・STA/LTA・イベント検出の閾値・センサー補正値・
センサー姿勢・観測点設定・保存設定・通知設定。

これにより、どのクライアントから繋いでも同じ設定を使える。

## 13. HTTPS/WSS

既存の PWA は HTTPS で配信されているため、LAN 内のホストへ素の HTTP で繋ぐと
ブラウザの混在コンテンツ制限に掛かる。**iOS 実機（Safari）で実際にブロックされることを
確認済み**。HTTPS 化すればこの制限自体は避けられるが、**実機ではそれだけで済まなかった**
（下記の決定枠）。HTTPS で繋げる方式を用意する。

> **方式は Tailscale Serve を採用する（2026-09-27 決定）。**
>
> iOS 実機（Safari）の実測で、**通常の Safari タブでは、正規の HTTPS 接続であっても失敗し
>（原因は未特定）、ホーム画面に追加した PWA（standalone 起動）からのみ繋がった**。そのため
> **PWA はホーム画面に追加して使う前提を置く**——このアプリ自体を PWA として設計している点と
> 矛盾しない。
>
> **選定の経緯・実測の詳細は** [`docs/implementation-plan.md`](../docs/implementation-plan.md) #93
> 「ブラウザから LAN の機器を叩けるか」を参照。

## 14. OTA アップデート

ESP32 は OTA アップデートに対応させる。

```
クライアント → ホスト → ESP32 → ファームウェアの取得 → 検証 → 書き込み → 再起動
```

ホスト側で、最新ファームウェア・ESP32 ごとの現在の版数・更新状態を管理する。
クライアントからは、更新の確認・開始・版数の確認・進捗の確認をできるようにする。

将来の安全機能: ファームウェアの署名と検証・更新失敗の検知・巻き戻し。
ESP-IDF のパーティション設計を使う。

## 15. センサー管理

ホスト側では次の階層で管理する。

```
ESP32
 └─ Sensor
      └─ Channel
```

例:

```
ESP32-A
 ├─ IIS2ICLX-1
 │   ├─ X
 │   └─ Z
 └─ IIS2ICLX-2
     ├─ Y
     └─ Z
```

各センサーについて、センサー ID・型番・接続先の ESP32・観測点・物理的な向き・
校正行列・オフセット・感度・有効/無効を設定できるようにする。

## 16. 座標変換

**センサーの物理的な向きと、地理的な XYZ を分離する。** 各センサーについて回転行列 R を
持ち、次で共通座標へ変換する。

```
a_world = R × a_sensor
```

これにより、3D プリント治具の角度が完全な 90° でなくても校正で補正できる。

> **計測震度には効かない** —— ただし **R が純粋な回転（軸どうしの直角を保つ変換）である限り**。
> 3 成分の合成は `sqrt(ns² + ew² + ud²)`（ベクトルの長さ。
> → [`src/utils/knet/seismicIntensity.ts`](../src/utils/knet/seismicIntensity.ts)）なので、
> 向きを変えても長さは変わらない。効くのは**軸ごとの波形・センサー間の差分（§7）・P/S 判定（§6）**。
> つまり §16 は §7 の前提であって、単体センサーの震度を出すだけなら要らない。
>
> **補正の対象が「取り付けの向き」なのか「軸どうしの直角のずれ」なのかは、まだ決まっていない。**
> 前者なら R は回転で上の話が成り立つが、後者まで直すなら R は長さを変える変換になり、
> **計測震度も動く**。実装に入る前に、どちらを直すのかを決めること。
>
> **見分けられる。** 向きだけを直す前提で始めて、§7 の差分を見ればよい —— 同じ揺れを受けている
> はずのセンサーどうしで差が残り続けるなら、向きを合わせきれていないか、軸どうしの直角が
> 崩れている。**静止時の重力は前者しか教えてくれない**ので（重力から決まるのは傾きの 2 軸だけ）、
> そこで切り分けが要る。
>
> **重力からは傾き（2 軸）しか決まらない。** 鉛直まわりの回転＝方位は決まらないので、
> 共通の直線に当てて物理的に揃えるか、既知の水平方向の揺れを与えて解くかのどちらかが要る。
> 方位が揃っていないと、§7 の差分が本物の揺れを部分的に打ち消す。

## 17. クライアントが切断されても動作する

**重要要件。** クライアントを閉じても、ESP32 からの受信・データ保存・地震検出・
P/S 判定・イベント生成・通知はすべて続く。

クライアントは再接続したとき、ホストから現在の状態を取得する。

## 19. 開発上とくに重要な原則

1. RAW データを捨てない
2. ESP32 側に解析ロジックを詰め込みすぎない
3. **ホストを処理の中心にする**
4. クライアントを閉じても観測を継続する
5. センサー固有の座標と共通座標を分離する
6. 個々のセンサーデータを保持してから合成する
7. アルゴリズムを後から変更できる構造にする
8. センサー・ESP32・観測点を固定数として実装しない
9. **設定の正本はホスト側に置く**
10. リアルタイム表示と、解析・保存処理を分離する
