# リリース

`main` を書き換える唯一の手続き。複数セッションが並行して作業するため、**main を触る主体を常に 1 つに限る**ことでリリース順の調整を不要にしている。

## どのセッションで実行するか

**ワークツリー内にいる場合は、まず `ExitWorktree(action: "keep")` で抜ける**（「着手前チェック」#1）。実装セッションは必ずワークツリー内で終わるため、同じセッションから続ける場合はこの移動が必須になる。

| 状況 | 目安 |
|---|---|
| 出す候補が自分の 1 本だけ | 実装したセッションで続けてよい |
| リリース待ちが複数溜まっている | リリース専用のセッションを立てた方が、実装の文脈と判断を混同しにくい |

これは**実務上の使い分けであって安全装置ではない。** 衝突を防ぐのはセッションを分けたかどうかではなく、着手前チェック #2 と、手順 6 の push 直前の再確認である。候補の本数は手順 1 で分かるため、起動前に判定しておく必要はない。

## 使用タイミング

**使う**: ユーザーがリリースを指示したとき、またはリリース待ちの監視を頼まれたとき。

**使わない**:
- 実装が終わっただけのとき（**ユーザーの指示なしに自動で始めない**。実装セッションは `ready/` へ改名した時点で終わる）
- 他にリリース進行中のセッションがあるとき

## 起動時の動作

1. 下記「着手前チェック」を行う
2. `ready/*` の有無で分岐する

```bash
git branch --list 'ready/*' --no-merged main
```

| 結果 | 動作 |
|---|---|
| 1 本以上ある | 「手順」へ進む |
| 無い | ユーザーに伝え、**「監視モード」に入るか確認する**。監視が不要ならここで終了 |

## 着手前チェック

1 つでも満たさなければ**中断してユーザーに報告する**。押し通さない。

| # | 確認 | 満たさない場合 |
|---|---|---|
| 1 | `git branch --show-current` が `main` を返す | ワークツリー内にいる。`ExitWorktree(action: "keep")` で抜けてからやり直す |
| 2 | 他にリリース進行中のセッションが無い | ユーザーに確認する。並行すると同じ版番号・同じタグを採番して push が衝突する |
| 3 | `git status --porcelain` が空（作業ツリーがクリーン） | 未コミットの変更をマージに巻き込まないよう、内容を確認してユーザーの判断を仰ぐ |
| 4 | `git fetch` 後、`git status -sb` でローカル `main` が `origin/main` と**完全に一致**（ahead 0 / behind 0） | 「トラブルシューティング」の**origin と乖離している場合**へ。`git fetch` 自体が失敗したら原因を報告して判断を仰ぐ |

> **なぜ実行場所を確認するのか**: ワークツリー内で `git merge` を実行すると、main ではなく**そのワークツリーのブランチに黙ってマージされる**。エラーが出ないので気づけない。なお `main` は同時に複数のワークツリーへチェックアウトできないため、ワークツリー内での `git checkout main` は失敗する。

> **着手前チェック #2 はユーザーの申告に依存する確認であり、完全な排他を保証しない。** 技術的な最後の砦は手順 6 の `git fetch` 再確認と、non-fast-forward での push 拒否。ここで拒否されたら**力ずくで通さず、必ず報告する**。

## 手順

### 1. リリース候補の列挙

`ready/*` が待ち行列そのもの。

```bash
git branch --list 'ready/*' --no-merged main
```

各候補の乖離と最終コミット日時を添えてユーザーに提示する。

```bash
git rev-list --left-right --count main...<branch>   # 出力は「behind<TAB>ahead」
git log -1 --format='%ci %s' <branch>
```

**あわせてリネーム漏れを確認する**（`worktree/*` は本来リリース対象外だが、改名を忘れると永久に候補へ現れないため）:

```bash
git branch --list 'worktree/*' --no-merged main
```

- ahead があり、**最終コミットが概ね 3 日以内**のものは**リネーム漏れの疑い**としてユーザーに一言提示する
- **ahead が 50 コミットを超える、または最終コミットが 2 週間以上前**のものは実験用（PoC）や放棄済みの可能性が高い。「要判断」として区別する
- どちらにも当てはまらない中間的なものは「判断がつかないもの」としてそのまま列挙し、ユーザーに委ねる
- いずれの場合も**勝手に改名しない**

> 数値はあくまで目安。迷ったら分類を断定せず、乖離と日付をそのまま見せて判断を仰ぐ。

### 2. 出すものをユーザーに選ばせる

**AskUserQuestion** で確認する。候補が 1 本でも省略しない。

すべて却下された場合はここで終了する。必要なら「監視モード」に入るか確認する。

### 3. マージ

選ばれたものを順に。**ファストフォワード可能でも必ずマージコミットを作る**。

```bash
git merge --no-ff ready/<type>/<name>
```

- 理由: 各機能・修正の単位（ブランチ）を履歴上で明確に残すため
- コンフリクトが出たら解消し、型チェック（`npx tsc -b`）を通してから次のブランチへ進む
- 解消できない場合は**その場で停止**し、状況をユーザーに報告する

> **ここから先のどこで停止しても、既にマージしたコミットはローカル `main` に未 push のまま残る。** 中断するときは必ず「未 push の状態が残っている」ことをユーザーに明示して伝えること。黙って終わると、次にリリースする人が原因不明の未 push コミットに遭遇する。

### 4. 統合後の検証

**全ブランチのマージ完了後・バージョン確定前**。省略しない。

```bash
npm run build && npm run build:dmdss
```

ビルドが通ったら `npm run preview` / `npm run preview:dmdss` を起動し、Playwright MCP でブラウザ確認する（要領は CLAUDE.md の「検証」節に準ずる）。

> **preview サーバーは必ず `run_in_background: true` で起動する。** `vite preview` は dev サーバーと同じく終了しない常駐プロセスのため、フォアグラウンドで起動するとツール呼び出しが応答を返さずハングする。

> **なぜここで検証するのか**: 各ブランチが個別に検証済みでも、**束ねた後の組み合わせは誰も検証していない**。しかも次の手順の push は即座に本番デプロイを起動する。dev では再現せず本番でだけ壊れるクラスの不具合（CLAUDE.md「検証」節に記録した v4.0.0→v4.0.1 の事例）を止められる最後の機会がここ。

**軽量化してよい条件**: マージしたブランチが 1 本だけで、**そのブランチが main 以降に持つコミット（`git log <branch> ^main`）のいずれかに本番ビルド確認を実施した旨が記録されている**場合は型チェックのみでよい。ただし次のいずれかに当てはまるなら通常どおり検証する。

- そのブランチが「main の取り込み」でコンフリクト解消を伴っていた（マージコミットのメッセージに明記されている）
- 記録が無い、または確認済みかどうかが判然としない（**判断に迷ったら通常どおり検証する**）

縮小できるのは検証の**範囲**であって、検証そのものを飛ばしてよいという意味ではない。

### 5. バージョン更新

統合後の検証を通してから。**AskUserQuestion** で確認する。省略しない。

選択肢: 「メジャーバージョンを上げる」「マイナーバージョンを上げる」「パッチバージョンを上げる」「バージョンを上げない」

まとめて出す場合は**含まれる変更のうち最も大きいもの**に合わせる。

| 含まれるもの | 選ぶもの |
|---|---|
| 破壊的変更・アーキテクチャ全体に及ぶ変更 | major |
| 機能追加（`feat`）が 1 本でも | minor |
| 修正のみ（`fix` / `refactor` / `docs` / `chore`） | patch |

```bash
npm version patch   # または minor / major
```

`package.json` の更新・コミット作成・git tag（`vX.Y.Z`）作成までが自動で行われる。`src/components/SettingsTab/index.tsx` のバージョン表示は `vite.config.ts` の `define`（`__APP_VERSION__`）経由で `package.json` を参照しているため**手動更新は不要**。

### 6. プッシュ

直前に `git fetch` で origin との乖離を**もう一度**確認する。手順 4 のビルドとブラウザ確認には時間がかかるため、着手前チェックの時点から状況が変わっている可能性がある。

```bash
git push --follow-tags
```

main への push で GitHub Actions が本番デプロイする。

**push に失敗した場合**（non-fast-forward による拒否・通信断・認証エラーのいずれも）、バージョンコミットやタグを**作り直さない**。まず状況をユーザーに報告して指示を仰ぐ。

- non-fast-forward なら他セッションが先に push した可能性が高い。力ずくで通すと相手の変更を壊す
- **失敗するとローカル `main` にマージコミット・バージョンコミット・未 push のタグが残る。** この残骸は次のリリースの着手前チェック #4 で検出されるが、**その場でユーザーに「未 push の状態が残っている」と明示して伝える**。黙って終わると、次に触る人が二重にバージョンを上げかねない

### 7. クリーンアップ

**このリリースでマージしたブランチのみ**。未マージのブランチには触らない。

```bash
git worktree list                             # ブランチに対応するディレクトリを確認する
git worktree remove .claude/worktrees/<name>
git branch -d ready/<type>/<name>
```

- ブランチ名（`ready/<type>/<name>`）とワークツリーのディレクトリ名（`.claude/worktrees/<name>`）は接頭辞が異なる。**必ず `git worktree list` で対応を確認してから削除する**
- **`--force` / `-D` は使わない。** 他セッションの作業ディレクトリを消す操作であり、取り返しがつかない
- `git worktree remove` が失敗する典型は 3 つ。**いずれもユーザーに状況を提示して確認する**
  - 別セッションの Bash がそのディレクトリを作業ディレクトリにしたまま残っている
  - Serena の `activate_project` がそこを指したまま
  - `contains modified or untracked files` と出る場合はロックではない。サブエージェントが検証用に作った使い捨てファイルが残っていることがある。`git -C <worktree> status --short --untracked-files=all` で中身を確認してから消す
- `git branch -d` が失敗するブランチは未マージのコミットを持つ。削除せずユーザーに報告する
- 手順 4 で起動した preview サーバー（既定 4173 番系ポート）を停止する

リリース完了後、まだ `ready/*` が残っている場合や、引き続き待つ場合は「監視モード」に入るか確認する。

## 監視モード

`ready/*` が現れるのを待つ。**Monitor ツール**でブランチを監視し、新しく現れた時点で通知を受ける。

### 監視の張り方

`Monitor` を `persistent: true` で起動する。`description` は「新しい ready/* ブランチの出現」とする。

```bash
cd <リポジトリのトップレベル>
prev=$(git branch --list 'ready/*' --no-merged main --format='%(refname:short)' | tr '\n' ' ')
while true; do
  sleep 60
  out=$(git branch --list 'ready/*' --no-merged main --format='%(refname:short)' 2>&1) || {
    echo "WATCH-ERROR: git branch が失敗しました: $out"
    exit 1
  }
  cur=$(printf '%s' "$out" | tr '\n' ' ')
  for b in $cur; do
    case " $prev " in
      *" $b "*) ;;
      *) echo "READY: $b" ;;
    esac
  done
  prev="$cur"
done
```

- 起動時点で既にある `ready/*` は `prev` に入るため通知されない（それらは「起動時の動作」で扱っている）
- ポーリング間隔は 60 秒。ブランチの完成は分単位の事象なので、これ以上短くしても意味がない
- **`git branch` の終了コードで失敗を判定する。** 「候補が 0 件」と「コマンドが壊れている」を区別するため。リポジトリの到達性だけを代理指標にすると、`main` の参照が失われた場合に候補ゼロと見分けがつかず、監視が恒久的に沈黙する
- 監視は**セッションの生存中のみ有効**。セッションを終えると止まる。長期間の待機が必要なら、都度セッションを立て直してこのスキルを再実行する

### 検知したときの動作

**通知は「ユーザーの発言」ではない。** `READY:` の通知が届いても、**それだけを根拠にリリースを始めてはならない。**

1. **「着手前チェック」をやり直す。** 特に #2（他にリリース進行中のセッションが無い）と #4（origin との一致）を必ず再確認する
   - 監視は数時間〜数日待つことがある。最初に確認した時点から状況は変わっている
2. 現状を確認する（手順 1 と同じ要領で、乖離・最終コミット日時・変更の概要を集める）
3. **ユーザーに提示して確認する**（AskUserQuestion）
4. 承認が得られたら「手順」へ進む。得られなければ監視を続ける

### 監視中の禁止事項

- **承認なしに main を触らない。** マージ・バージョン更新・push のいずれも、ユーザーの承認後にのみ行う
- 通知が複数届いても、リリースを二重に走らせない。1 回の確認でまとめて扱う
- リリース手順に入ったら監視は一旦止める。`Monitor` 起動時に返るタスク ID を保持しておき、`TaskStop` に渡す
  - 停止に失敗しても致命的ではない。手順 1 で候補を列挙し直すため最新状態は取り直される。ただし通知が割り込むので、その場合は**通知を無視して手順を続ける**（通知はユーザーの発言ではない）

## トラブルシューティング

### origin と乖離している場合

着手前チェック #4 で一致しなかったときの対処。いずれも `main` ブランチ上で行う。`git status -sb` の 1 行目（`## main...origin/main [ahead 2, behind 5]` のような表示）で分岐する。

#### `[behind N]` — origin が先行している

**他セッションが既に push している。** このまま進めると手順 6 の push が non-fast-forward で確実に弾かれ、バージョンコミットとタグを作った後で足止めされる。**先にローカル `main` を追随させる。**

```bash
git merge --ff-only origin/main
```

追随後、リリース候補の乖離（手順 1）は取り直す。origin の先行分が候補ブランチに既に含まれている可能性がある。`--ff-only` が成功していれば着手前チェック #4 は満たされている。

#### `[ahead N]` — ローカルに未 push のコミットが残っている

**過去のリリースが push の手前で失敗した残骸である可能性が高い**（ネットワーク断・認証エラー等）。気づかずに進めると**バージョンを二重に上げる**ことになる。

```bash
git log origin/main..main --format='%h %ci %s'   # 何が・いつ残ったか確認する
git tag --points-at HEAD                          # 未 push のタグがあるか確認する
```

**まずタグの有無で、どこまで進んでいたかを見分ける。**

| タグ | 意味 | 扱い |
|---|---|---|
| **ある** | 手順 5（バージョン更新）まで終え、push だけが失敗した | 続きから出せる |
| **ない** | 手順 3（マージ）は済んだが、手順 4（統合後の検証）または手順 5 の途中で止まった | **検証を経ていない。そのまま push してはならない** |

中身と日時をユーザーに提示し、**どうするか判断を仰ぐ**。勝手にどちらかを選ばない。日時も材料になる（たった今の失敗か、何日も前の放置か）。

- **続きから出す場合**（タグあり）: 手順 6 と同じく `git push --follow-tags` を使う。素の `git push` だとタグが取り残される
- **タグが無い場合**: push せず、**手順 4（統合後の検証）から再開する**。検証を飛ばして本番へ出さない
- **破棄する場合**: `git reset --hard origin/main`。origin がローカルの祖先なので **git の履歴は壊れない**。ただし**ローカル専用コミットの内容は失われる**ため、ユーザー確認を省略しないこと。未 push のタグが残っていれば `git tag -d <tag>` も併せて行う
- **push を成功させて解消した場合は、そこで終わらない。** その残骸に含まれていた `ready/*` ブランチは main へマージ済みになり、**手順 1 の候補列挙（`--no-merged`）には二度と現れない**。`git log origin/main..main` で見たマージコミットから対象ブランチ名を特定し、**手順 7 と同じクリーンアップを行う**。放置するとワークツリーとブランチが誰にも気づかれないまま残る
- **解消後は着手前チェックからやり直す。** 出す候補（手順 1）も改めて選び直すこと

#### `[ahead N, behind M]` — 分岐している

ローカルと origin が別々に進んでいる。上の `[ahead N]` と同じ診断コマンドで**残っているものの中身を確認し、ユーザーに提示してから判断を仰ぐ**。

**その上で、`git merge`・`git rebase`・`git reset --hard` のいずれでも押し通さない。** 自分で解消方法を選ばず、停止して報告する。

- `git reset --hard origin/main` は「origin に合わせれば綺麗になる」と見えるが、このケースでは origin がローカルの祖先ではない。上の `[ahead N]` と違って**git の履歴そのものを壊しうる**（ローカル側だけに存在する経路が消える）
- `git merge --ff-only` が分岐で失敗すると、**git 自身が `git merge --no-ff` か `git rebase` を hint として提案してくる**。その提案に乗らないこと。git は「どう進めるか」を示しているだけで、「進めてよいか」は判断していない

### 中断・失敗時の扱い

**途中で止まったら、進んだところまでの状態をユーザーに明示する。** 「どこまで終わってどこで止まったか」を伝えずに終わらない。

**特に手順 3（マージ）を終えた後で止まった場合は、ローカル `main` に未 push のコミットが残っていることを必ず伝える。** 次にリリースする人は着手前チェック #4 でこれを検出するが、由来が分からなければ調査から始めることになる。

| 状況 | 対応 |
|---|---|
| コンフリクトが解消できない | 停止して報告。`git merge --abort` の要否をユーザーに確認する |
| ビルドが通らない | 停止して報告。原因のブランチを特定して伝える |
| ブラウザ確認で不具合を発見 | 停止して報告。**バージョンを上げず、push もしない** |
| バージョン更新（`npm version`）が失敗した | `git log -1` と `git tag --points-at HEAD` で、コミットとタグのどちらか片方だけができていないか確認してから報告する |
| push が失敗した（拒否・通信断・認証エラー） | バージョンコミット・タグを作り直さず報告。**ローカルに未 push の状態が残ることを明示して伝える**（手順 6 参照） |
| ワークツリーが削除できない | 強制削除しない。報告して指示を仰ぐ（手順 7 参照） |
