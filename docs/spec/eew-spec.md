# EEW（緊急地震速報）仕様書

> 本書は**現在の実装が EEW をどう処理するか**をまとめた仕様書。実コードと食い違う場合は実コードを正とする。
> 関連: [`data-sources-spec.md`](data-sources-spec.md) の EEW 電文受信、[`audio-tts-spec.md`](audio-tts-spec.md) の EEW 音・読み上げ、
> [`map-rendering-spec.md`](map-rendering-spec.md) の EEW 地図レイヤー。

## 1. 概要

緊急地震速報を受信・統合・表示するモジュール群。以下の役割を持つ:

- 電文の統合（同一 eventId の続報を最新報でまとめる）
- レベル判定（予報 / 警報 / 特別警報）
- 予報円の描画（P 波・S 波の地表到達円）
- 自動解除（一定時刻経過で無音・即消去）
- 誤報取消の処理（明示的な取消電文＝音・通知・読み上げを伴う）
- 仮定震源要素（震源未確定）の扱い

## 2. データフロー

```
[電文経路]
  DMDATA WebSocket / REST 履歴 (VXSE45)  ───────┐
  P2PQuake WebSocket (code=556)  ────────────────┴── enqueueEvent（eventQueue へ時刻順に積む）
  Yahoo hypoInfo（1Hz ポーリング・standard 版のみ）── handleEvent を直接呼ぶ（キュー非経由）
                                                            │
                                                            ↓
        [useEarthquakes] handleEvent (eventQueue から時刻順にディスパッチ)
                                                            ↓
                                          activeEEWs: Map<eventId, EEWAlert>
                                                            ↓
                                            ├─→ useLiveEventHandler
                                            │      音・通知・タブ切替・読み上げ・カメラフィット
                                            │
                                            ├─→ useEewLayerData
                                            │      地図の予想震度塗り・LPGM 区域塗り・震源マーカー
                                            │
                                            ├─→ usePsWaveCalc
                                            │      P 波・S 波地表到達円（100ms 更新）
                                            │
                                            ├─→ useSWaveCountdown
                                            │      S 波到達カウントダウン
                                            │
                                            └─→ RealtimeTab EEWCard
                                                   カード表示（見出し・震度・M・深さ等）
```

図の 3 経路が揃って動くことはない。DMDATA と、それ以外の 2 経路（P2PQuake・Yahoo hypoInfo）が
バリアントで排他的に入れ替わる（内訳は次節の表）。Yahoo hypoInfo の直接呼び出しは
`src/App.tsx` が `onEEWEvent` に渡す `injectEvent`（実体は `handleEvent`）による。

## 3. 電文経路・バリアント差・名称

3 系統の電文源がある:

| 経路 | バリアント | severity | condition | 長周期 lgIntTo | 使い方 |
|---|---|---|---|---|---|
| DMDATA WS/REST | DMDSS | 電文値（Warning/Forecast） | 電文値（`'仮定震源要素'` あり） | あり | 主系 |
| P2PQuake WS | standard | 電文に無いが `convertEvent` で一律 `'Warning'` 付与 | 数値/文字列 | なし | 主系（DMDSS 版は不使用） |
| Yahoo hypoInfo | standard | 震度からの推定（`>= 5弱 ? 'Warning' : 'Forecast'`） | 常に空（運ぶ欄が無い） | なし | 補完的に検知（DMDSS 版は不使用） |

P2PQuake の 556 で severity が付与される仕組みは [`data-sources-spec.md`](data-sources-spec.md) §3
を参照（電文仕様と付与ロジックはそちらに一本化）。

**Yahoo hypoInfo を DMDSS 版で使わない仕組み**: `src/App.tsx` が `useKyoshinRealtime` に渡す
`onEEWEvent` を DMDSS 版では `undefined` にしている。通知先が無いとき `useKyoshinRealtime` は
差分の基準（直前の hypoInfo）だけ進めてイベントを捨てるため、DMDSS 版では Yahoo 由来の EEW が
状態へ入る経路そのものが存在しない。**リアルタイム震度は両バリアントとも Yahoo を使う**
（強震モニタのフレームに hypoInfo は載ってくるが、EEW としては読まない）という点に注意。
クロック較正の主経路は別の時刻サービスに移っており、Yahoo は取得に失敗した周期のフォールバックとして
両バリアントで使う（[`data-sources-spec.md`](data-sources-spec.md) §4「クロック同期」）。

**enrichEEW（`useEarthquakes.ts`・standard 版のみ）**: Yahoo hypoInfo で先に検知した EEW に、後着の P2PQuake で
より正確な `areas` / `condition` / `hypocenter` を上書きする。severity は upgrade only（既存 `'Warning'` は
維持、`Forecast/Unknown` から `'Warning'` への格上げのみ許可）。Warning への格上げ時は `onLiveEvent` に
enriched オブジェクトを渡して `useLiveEventHandler` 側の音・通知・タブ切替のレベル再評価をトリガーする
（Yahoo 弱推定＋P2PQuake 後着で無音になる事象の解消）。ただし現状は次の課題が残る:
- Yahoo 続報が「新しい報」として `activeEEWs` を丸ごと上書きすると、enrichEEW で入れた `areas` /
  `earthquake.condition` / `earthquake.hypocenter` が揮発する（`case 'eew'` のマージ側では severity だけを
  upgrade only で保持）
  - `condition` が揮発すると仮定震源要素の判定（§5）が false に戻るため、**地図の震源×印の点滅が
    「穏やか」と「強い」の間を行き来する**。原因は揮発の側にあり、点滅の出し分けでは直せない

### 電文の名称と表示・読み上げ

DMDATA 経路で受けるのは 1 種類だけ。

| 電文種別 | `Control/Title` | 備考 |
|---|---|---|
| VXSE45 | 緊急地震速報（地震動予報） | 長周期地震動階級を含む（[DMDATA の電文一覧](https://dmdata.jp/docs/telegrams/ew09040/)）。**警報に該当するかは電文内の `isWarning` が示す**ため、VXSE45 でも警報相当になりうる |

VXSE43（警報）と旧形式の VXSE44（予報）を扱わない理由は [`data-sources-spec.md`](data-sources-spec.md)
§2「EEW は VXSE45 だけを受ける」を参照。

> **区分を決めているのは severity（`computeSingleEEWLevel`）で、電文種別ではない。**
> `severity` は「`headType` が VXSE43」または「区域の `Category/Kind/Name` が『緊急地震速報（警報）』」
> から導く（`dmdataParser.ts` の `parseEEWFromXml`）。
> VXSE43 は受信しないため実際に立つのは後者だけだが、パーサは渡された種別を電文どおりに解釈する
> （種別の絞り込みは呼び出し側の責務）。「電文種別＝区分」と読み替えると、`isWarning` が立った
> VXSE45 を予報級と誤って扱うことになる。

**呼び方は電文の名称から借りる。** 予報級を「地震動予報」と呼ぶのは、その内容を運ぶ VXSE45 の名称が
「緊急地震速報（地震動予報）」だから。予報級を「緊急地震速報（〜）」の器に入れると
「緊急地震速報（地震動予報）」と二重になるため、器ごと分ける。区分の名前は `eewKindLabel`
（`src/utils/eew.ts`）が単一情報源。

| 表示箇所 | 予報級 | 警報級 | 特別警報の条件を満たす場合 |
|---|---|---|---|
| リアルタイムタブのカード見出し | 地震動予報 | 緊急地震速報（警報） | 緊急地震速報（特別警報） |
| 地図のポップアップ（震源・区域） | 地震動予報 | 警報 | 警報 |
| ブラウザ通知の見出し | 地震動予報 | 緊急地震速報 警報 | 緊急地震速報 特別警報 |
| ウィンドウタイトル | 地震動予報 … | 緊急地震速報 … | 緊急地震速報 … |
| 電文ログ | EEW地震動予報 | EEW警報 | EEW警報 |

**地図のポップアップの行は、震源と区域で判定の軸が違う。** 震源×印（`EewEpicentersGL`）は電文の
`severity` を見るが、区域塗り（`EewRegionFillGL`）は**区域ごとの `kindCode`** を見る（下の
§4「区域の種別コード」）。同じ警報級の電文でも、予想震度 5 弱未満の区域は予報域なので、
その区域のポップアップだけ「地震動予報」と出る。表は 1 行にまとめているが同じ基準ではない。

電文ログの列だけは**電文種別（`headType`）から引く**（`TelegramTab` の `HEAD_TYPE_LABEL`）。
電文そのものの記録なのでそれが正しい。ただし `isWarning` が立った VXSE45 は severity では警報相当
なのに、ログには `EEW地震動予報` と出る。**ログの列と他の列は別の軸で決まっている**ことに注意。

> **ウィンドウタイトルの変更は外部への破壊的変更。** タイトルは AutoHotKey 等の外部監視向けの
> 文字列（[`audio-tts-spec.md`](audio-tts-spec.md) §1・§5）なので、「緊急地震速報」で文字一致
> させている仕組みは予報級を拾えなくなる。予報級も拾うなら監視側に「地震動予報」を足すこと。

**「緊急地震速報（予報）」も気象庁の公式な用語**（情報の名称としての呼び方）だが、電文の名称に
合わせる方を採っている。ここに書いたのは**表示**の理由。読み上げには「音声だけで区分が判別できる
ようにする」という固有の理由が加わるため、そちらは [`audio-tts-spec.md`](audio-tts-spec.md) §6 にある。

### 真偽値は電文の形から復元する（`parseEEWFromXml`）

電文には「取消か」「最終報か」「警報級か」を表す真偽値が無い。DMDATA の JSON 変換はこれらを
`body` のフラグとして持つが、**XML では別の形で現れる**ので読み替える（実電文 24 通で対応を
確かめた。予報級 14・警報級 6・仮定震源要素 1・取消 1・取消前 2）。

| 意味 | XML での現れ方 |
|---|---|
| 取消 | `Head/InfoType` が「取消」 |
| 最終報 | `Body/NextAdvisory` に最終報の文言、**または取消** |
| 警報級 | 区域の `Category/Kind/Name` が「緊急地震速報（警報）」 |

**取消は最終報として扱う。** 実電文の取消は `Body` に `Text` しか持たず `NextAdvisory` が無い
（2026-03-07 の取消で確認）。文言だけを見ると最終報にならず、自動解除の扱いが変わる。

**`Condition` は要素の位置で意味が変わる。** `Earthquake` 直下は震源の状態（「仮定震源要素」）、
`Pref/Area` 直下は区域の状態（「既に主要動到達と推測」）。子孫から拾うと、警報級の電文で区域側の
文言が震源の `condition` に化け、**仮定震源要素の判定が誤って立つ**（§5 の抑制が丸ごと発動し、
震源・規模が画面と読み上げから消える）。

上限を定めない予想震度（`<To>over</To>`）は XML でも同じ語で現れる（扱いは §4「上限を定めない
予想震度の扱い」）。

**震源要素が「全要素とも不明」と書かれた電文（`description="震源要素不明"`）は捨てない。**
震源の位置は「不明」のセンチネル（`-200`）へ倒し、予想震度と対象区域はそのまま出す ——
予報円は描けなくても、伝えるべきことが残っている。**位置を使う側は `hasKnownEpicenter` を通すこと**
（`Number.isFinite` だけではセンチネルをすり抜ける）。判定の作り、すり抜けたときに壊れる箇所、
書式が壊れた電文と分ける理由は [quake-spec.md](quake-spec.md) §5「震源要素不明の電文は捨てない」
（地震情報と EEW の単一情報源。津波と長周期は震源の座標を読まないので関与しない）。

### 震源要素の精度（`Hypocenter/Accuracy`）

震源・深さ・マグニチュードをどう決めたかが属性に入る（電文解説資料 Ⅱ.21 1-4-2）。
**実電文 405 通（2026-06〜09）すべてに入っている。** 本文はどれも `"NaN"` 固定で、意味は
属性にしかない（`NumberOfMagnitudeCalculation` だけ本文に数値）。

| 属性 | 意味 |
|---|---|
| `Epicenter@rank` / `Depth@rank` | 1＝P波／S波レベル超え、IPF法（1点）、または仮定震源要素／2＝IPF法（2点）／3＝IPF法（3点／4点）／4＝IPF法（5点以上）／5・6＝防災科研システム／7・8＝EPOS |
| `Epicenter@rank2` | **9＝推定震源とマグニチュードはこれ以降変化しない** |
| `MagnitudeCalculation@rank` | 2＝防災科研システム／3＝全点P相／4＝P相／全相混在／5＝全点全相／6＝EPOS／8＝P波／S波レベル超え、または仮定震源要素 |
| `NumberOfMagnitudeCalculation` | Ｍ計算に使った観測点数（**5 は「5点以上」**） |

**数字は画面に出さず、資料の語をそのまま出す。**「ランク4」では何も伝わらないので意味へ直すが、
**言い換えはしない** —— 「IPF法（5点以上）」を「精度が高い」と要約すると、資料と突き合わせ
られなくなるうえ、こちらが評価を足したことになる。対応表は `utils/eew.ts` が単一情報源。

**括弧書きも落とさない。** 資料は 7・8 を「EPOS（海域〔観測網外〕）」「EPOS（内陸〔観測網内〕）」
と書いており、この括弧が**観測網の外か内か**を言っている。「EPOS（海域）」まで縮めると、
何と対比しているのかが画面から読めなくなる（縮めていた版があった）。

**`rank2` が 9 でも「最終報」とは書かない。** 資料は同じ注で「PLUM 法により予測震度が今後
変化する可能性はある」と断っている —— 震源が決まっても予想震度は動きうる。

**`rank` が 1 は「単独点で決めた」ことを電文が直接言っている。** `earthquake.condition`
（仮定震源要素）とは別の事実で、仮定震源要素でなくても 1 点なら立つ。

深さの精度（`Depth@rank`）は震央と同じ表を引く。**同じ値なら 1 行にまとめる**（同じ文字列を
2 行並べても情報は増えない）。語がそのままでは通じないので、**説明はホバーへ逃がす**
（設定タブと同じ `DescriptionTip`）—— 「言い換えない」と「説明しない」は別のこと。

> **実測では、深さが単独の行になったことはない。** 購読分類 `eew.forecast` のアーカイブ
> 全 7,995 通（2026-05-01〜09-11）のうち `Accuracy` を持つ 4,798 通を数えると、震央と深さの
> ランクが食い違った電文は 0 件だった（内訳は rank=4 が 4,526 通・3 が 136・1 が 100・2 が 36。
> **5〜8（防災科研システム・EPOS）は 1 件も無い**）。つまり画面には常に「震源」1 行として
> 出ており、2 行に割れる分岐は運用では通っていない。**分岐を消す理由にはしない** ——
> 気象庁が別々のランクを送れる形で定めている以上、食い違った報が来たときに深さの精度が
> 黙って消えるほうが重い。
>
> **上の「405 通」とは別の調査で、どちらも結論は同じ。** あちらは EEW の要素を横断して
> 数えた標本で、`LandOrSea`（404/405）や `Appendix`（318/405）の件数もその標本から出ている
> （`src/types/earthquake.ts`）。こちらは `Accuracy` だけを見るために**アーカイブに入っていた
> XML 電文をすべて数えた件数**で、`Accuracy` を持たない配信試験（VXSE42）3,197 通を
> 除いた残りにあたる。件数が桁違いなのは母数の取り方の違いによる。

**見出しも資料の語を使う。** 資料はこの要素群を `Accuracy`【**精度情報**】と呼び、下位を
「震央位置の精度値」「深さの精度値」「マグニチュードの精度値」と呼んでいる（Ⅱ.21 1-4-2）。
**合わせるのはブロックの見出しだけ**で、行のラベルは短いまま（「震源」「震央」「深さ」「Ｍ」）
—— 見出しは要素群全体の呼び名、行のラベルはその中のどれを指すかの札で、担う粒度が違う。
見出しは単独では何の精度か読み取りにくいが、**アプリが言い換えを作るよりホバーの説明で
補うほうが、資料と突き合わせられる**（「震源の決め方」と書いていた版があった）。

**電文の運用種別（`Control/Status`）も読む。** 訓練・試験の報にカードで印を出す。
地震情報・津波情報と共通の仕組みで、単一情報源は
[quake-spec.md](quake-spec.md) §5「電文の運用種別」。

### 最大予測値の変化（`Intensity/Forecast/Appendix`）

**気象庁が「変わったか」と「なぜ変わったか」を直接言っている**（解説資料 Ⅱ.21 2-1-4）。
アプリは続報どうしを比べて変化を推定しているが、それは代理指標で、電文はこちらを正としている。

- `MaxIntChange` / `MaxLgIntChange` … 0＝ほとんど変化なし／1＝1.0 以上大きくなった／2＝1.0 以上小さくなった
- `MaxIntChangeReason` … 0＝変化なし／1＝主としてＭが変化（1.0 以上）／2＝主として震央位置が変化（10.0km 以上）／3＝Ｍと震央位置の複合／4＝震源の深さが変化（30.0km 以上）／**9＝PLUM 法による予測により変化**

**「1.0 以上」は計測震度の差**で、画面に出している震度階級の差とは別物。「階級が 1 つ上がった」と
読み替えないこと。文は `eewForecastChangeText` が組む（変化が無い報・読めない報では空を返す）。

#### 帯を出し続ける長さは、報の状態と切り離してある

ここでいう**帯**は、カードの震源名の下に出るこの一文（`eewForecastChangeText` の戻り値）のこと。
**出す先は画面だけ** —— 読み上げ・ブラウザ通知・共有カードには載せていない。`Appendix` が
入るのは DMDATA の XML 経路だけなので、standard 版では帯そのものが出ない。

**気象庁はこの変化を 1 通しか言わない。** 第 1 報を除くほぼ全通が `Appendix` を持つが、
変化が無い報は値を 0 にして送ってくる —— 要素が消えるのではなく、値だけが戻る。
続報は数秒間隔で届くため、報の状態をそのまま描くと帯は 1 秒ほどで消えて誰も読めない。

そこで表示の寿命はカード側が持つ（`RealtimeTab` の `useHeldForecastChange`）。
変化を立てた報から最低 `EEW_FORECAST_CHANGE_HOLD_MS`（10 秒）は出し続け、その間に
変化なしの報が来ても消さない。

| 決めごと | 理由 |
|---|---|
| 保持するかどうかは**「変化を伝える値か」**で判定する（`eewForecastChangeText` が非空を返すか） | `Appendix` の有無で見ると、変化なしの続報を「新しい値」として採ってしまい保持が効かない |
| **新しい変化が来たら差し替えて計時し直す** | 保持は「変化なしの報で消さない」ためのもので、気象庁が言い直したものを抑えるためではない |
| 計時をやり直す契機は**報番号** | 同じ文言が離れた報で再び立つ形があるので文言だけでは 2 度目を拾えない。一方で `eew` オブジェクトの参照は「新しい報が届いた」ことの**代理値にすぎない** —— 報の到着以外でも EEW は作り直される（standard 版の区域・震源要素の注ぎ足し、取消の適用） |
| 取消の報では出さない | 取り下げた予想について「大きくなりました」と並べても意味がない。**隠しているのは `useHeldForecastChange` が戻り値を決めるときの `cancelledAt` 判定そのもの** —— 取消電文は `Appendix` を持たないが、状態更新は取消を `{ ...表示中の EEW, cancelledAt }` の形で当てるため、**直前の報の値がそのまま残る** |
| 長さは**実時計**で測る | 画面に出ている時間は利用者が読むのに要る時間。リプレイの再生時計（電文の失効に使っているもの）には乗せていない |

10 秒という値は「変化が続いている間、帯が途切れないこと」から決めた。効くのは
**別の文言へ差し替わるまでの間隔**で、実電文（2026-06-01〜09-06 の `eew.forecast`
アーカイブ・334 イベント）で変化を立てた 55 通を数えると次のとおり。

| 測ったもの | 実測 |
|---|---|
| 別の文言へ差し替わるまで | 33 通・最大 9 秒 |
| 同じ文言が再び立つまで | 5 通・最大 4 秒 |
| 実際に出た文言 | 4 種（「大きくなりました」28／「小さくなりました」18／「大きくなりました（PLUM法による予測で変わったため）」5／「大きくなりました（マグニチュードが変わったため）」4） |

10 秒あればどちらも覆う。上限の側は、EEW のカード自体が最終報から 60 秒以上出ている
（`calcEEWCancelTime` の下限）ことに対して十分短いこと。

> **次の報が来るまでの間隔（中央 1 秒・最大 10 秒。うち 35 通が次報で値 0 に戻る）は、
> この値を決めていない。** 変化なしの報では帯を消さないので、報が何秒後に来るかは関係がない。
> 最大値が 10 秒と一致しているのは偶然で、根拠にしていない。

> **読み上げの安定待ちはこの値へ載せ替えていない。** あそこは実地震で調整した経路で、
> しかも階級インデックス差で測っている。載せ替えるなら実データでの検証を伴う別の作業にする。

### 内陸判定・短縮用震央地名

`LandOrSea`（値域は「内陸」「海域」の 2 つだけ）は震源名の横に添える —— 海域なら津波を
思い浮かべる手がかりになる。仮定震源要素のときは地名自体が震源の推定位置ではないので添えない。
`ReduceName`（「青森県東方沖」に対する「青森東方沖」）は気象庁が用意した短い呼び方。
**読んで持ってはいるが、現状どの画面にも出していない** —— 通常の震央地名が収まらない場所が
いまのところ無いため。置き換えではなく、幅が足りない場所ができたときの代替として持っている。
対になる `ReduceCode`・震央地名のコード（`Area/Code`）も読むが、画面に出すのは名前のほう
（コードの扱いは [`quake-spec.md`](quake-spec.md) §8「電文のコード値は読むが、画面には出さない」）。

### 固定付加文（`Comments/WarningComment/Text`）

避難行動の呼びかけなどの定型文。`warningComment` として持ち、
**画面にだけ出す**。

**入るのは警報級の報だけ。** 購読分類 `eew.forecast` のアーカイブ全 7,995 通
（2026-05-01〜09-11）を数えると、付加文があったのは警報級の 380 通（VXSE44・VXSE45 各 190）
だけで、**予報級 7,615 通は 1 件も無い**（うち 3,197 通は毎正時の配信試験 VXSE42）。文言も
コード `0201`「強い揺れに警戒してください。」の 1 種類だけ。購読対象外の `eew.warning`
（VXSE43）も同じ期間で 23 通すべてに入っていたが、こちらはアプリへ届かない（→
[`data-sources-spec.md`](data-sources-spec.md) §2）ので上の数には含めていない
（VXSE43 は警報を出した日にしか生成されず、この 133 日のうちアーカイブがあったのは 16 日分）。

**置き場所は予想値のバナー群（予想最大震度・推定長周期地震動）の直後。** 電文が言う唯一の
行動指示なので、カードの末尾に置くと対象地域や到達の一覧の下に埋もれる。震度と長周期の
バナーは対になっているため、その間には割り込ませない。大きさは本文と同じかそれ以上にし、
**色は区分に追随させる**（上の実測から予報級のカードでは出ないが、予報級に別の付加文が
入ったときに警戒色で断定しないため）。

**コードはあるのに原文が無い電文は記録する**（`readCommentText`。→ [`quake-spec.md`](quake-spec.md)
§8「固定付加文（その他）」）。原文を画面に出す経路で、ここだけ検査を通していなかった。

**読み上げには載せない。** EEW の読み上げは秒を争うため、定型文を挟むと肝心の震度・地域が
遅れる（読み上げの優先順位は [`audio-tts-spec.md`](audio-tts-spec.md) §6）。取消電文では出さない
—— そのときの本文は付加文ではなく取消の理由なので、`Comments` の下に限って拾う。

**取消かどうかは `cancelledAt` で見る。** `cancelled` は受け取った電文そのものが取消報かを
表すフラグで、**画面が持つ EEW には伝わらない** —— 状態更新は取消を
`{ ...表示中の EEW, cancelledAt }` の形で当てるため、`cancelled` は取消前の値のまま残る
（上の「帯を出し続ける長さ」と同じ罠）。`!eew.cancelled` で判定していた版があり、
常に真で素通りしていた（実際に隠していたのは取消オーバーレイ）。

## 4. レベル判定（`computeSingleEEWLevel`）

`src/utils/eew.ts` の `computeSingleEEWLevel(eew)` が単一情報源。判定は 3 段階の直列条件で行う:

1. `severity !== 'Warning'` → `0`（予報）で早期 return（P2PQuake の予報電文・Yahoo severity が Forecast のケース）
2. 特別警報判定（下記 OR 条件のいずれか）→ `2`
3. 上記に該当しない（severity === 'Warning' かつ特別警報の条件を満たさない）→ `1`（警報）

**特別警報の判定条件**（OR）:
- `eewMaxScale(eew) >= 55`（震度 6 弱以上。震度が取れないときは `0` になるため自然に対象外になる。
  値の決まり方は下記のフォールバック規則を参照）
- `eewMaxLpgmClass(eew) >= 4`（長周期地震動階級 4 以上）

気象庁の実基準に合わせた OR 条件。長周期地震動階級は DMDATA 電文（VXSE45）にのみ載るため、
standard 版では `eewMaxLpgmClass` が常に 0 になり震度のみでレベルが決まる。

> **「特別警報」は表示に使い、読み上げには使わない。** 位置づけ自体は公式で、気象庁は震度 6 弱以上
> または長周期地震動階級 4 以上を予想した緊急地震速報（警報）を特別警報としている。ただし
> 「これらの特別警報は名称に『特別警報』は用いず、従来どおりの名称で発表します」とも明示している
> （[津波・火山・地震（地震動）に関する特別警報の発表基準](https://www.jma.go.jp/jma/kishou/know/tokubetsu-keiho/kizyun-jikazan.html)）。
> そのためレベル 2 は色分け・ブラウザ通知のタイトル・通知音の選択には使うが、**音声では「警報」と読む**
> （[audio-tts-spec.md](audio-tts-spec.md) §6）。重さは値そのもの（「予想最大震度6弱。」）で伝える。

`eewMaxScale`・`eewMaxLpgmClass` は**地域別 `areas[].scaleTo` / `areas[].lgIntTo` の最大を優先**し、
**`areas` が空または最大が 0 のときのみ**電文全体の `forecastMaxScale` / `forecastMaxLpgmClass` に
フォールバックする（大きい方を取るのではない）。震度未確定の `-1`（`IntensityScale` のセンチネル）は
`Math.max` の初期値 0 に丸められるため、全地域が未確定の場合もこのフォールバック経路に入る。
**`condition === '仮定震源要素'` を理由に値を捨てない。** 気象庁が最大予測震度を発表しないのは
「観測点 1 点による震度予測」と「深さ 150km 超（PLUM 法による 2 点以上の震度予測がある場合を除く）」の
2 つで、該当すれば電文にそもそも値が入らない。受信側で潰す必要はなく、潰すと発表済みの値を落とす
（詳細は §5）。

> **区域が空でも電文全体の値が載ることがある。** 気象庁が区域を列挙するのは震度 4 以上を予測した
> 予報区だけなので、震度 3 以下の予想は区域が空のまま `ForecastInt` だけが載る。かつてはそこを
> `condition` で潰しており、実データで取りこぼしが出ていた（件数は §5）。

`eewMaxScale` は `scaleTo` が震度階級（`IntensityScale`）の値でない地域を最大値の計算から除外する。
そのため P2PQuake の `scaleTo = 99`（「〜程度以上」）は、この判定に届く前に
`convertEvent` が同じ地域の `scaleFrom` へ置き換えている（[`data-sources-spec.md`](data-sources-spec.md) §3）。
置き換えないと「震度 7 程度以上」という最も強い予想が丸ごと無視され、警報止まりになる。

### 上限を定めない予想の扱い（震度・長周期地震動階級）

予想震度は上限が定まらないことがある（DMDATA は `to: "over"`・P2PQuake は `scaleTo: 99`）。
受け口で下限側の階級へ寄せ、上限が定まらないことをフラグで持ち越す。**電文上の表れと寄せ方は
[`data-sources-spec.md`](data-sources-spec.md) §8 が単一情報源。**
ここではその値を EEW 側がどう使うかだけを書く。

**長周期地震動階級も同じ形で来る。** 電文解説資料（Ⅱ.21 2-1-3-2）の値域は
`"0"/"1"/"2"/"3"/"4"/"over"/"不明"` で、事例も「最大予測長周期地震動階級が階級 3 程度以上の
場合」として `<From>3</From><To>over</To>` を示す。**震度側だけ対応して長周期側を忘れると、
`parseInt("over")` が `NaN` になって予測が丸ごと消える**（実際にそうなっていた）。
読み取りは `parseForecastInt`（震度）と `parseForecastLgInt`（長周期）に分けてある。

- **判定は下限で行う。** `computeSingleEEWLevel`（特別警報）・区域塗りの色・地図のカメラ追従は
  すべて階級値だけを見る。フラグを判定に混ぜない
- **語は「程度以上」。気象庁の表現に合わせる。** 電文解説資料は `To` の値域を
  「over:～程度以上」と定め、事例も「震度 5 弱程度以上」「階級 3 程度以上」と書いている。
  付け方は `getIntensityLabelWithApproxAbove()`（震度）と
  `getLpgmClassLabelWithApproxAbove()`（長周期）に集約する
- **「以上」（`getIntensityLabelWithOrAbove`）と混同しない。** そちらは「5弱以上・未入電」専用で、
  電文の値そのものが `震度５弱以上未入電`。**気象庁が「程度」を付けていない**ので付けない。
  以前は 1 つの関数を両方に使い回しており、片方に揃えるともう片方が気象庁の表記から外れる
  状態だった（→ [`quake-spec.md`](quake-spec.md) §4「震度5弱以上未入電」）
- 集約は `src/utils/eew.ts` の `eewMaxScaleInfo()` が `{ scale, orAbove }`、
  `eewMaxLpgmClassInfo()` が `{ cls, over }` で返す。`eewMaxScale()` / `eewMaxLpgmClass()` は
  値だけを返す薄いラッパ
  （**カードのバナーだけは例外**で、語を本体より小さく添えるため自前で組む）
- **比較に「程度以上」を含める。震度と長周期で対称にすること。** 上限が定まらなくなる向き
  （「階級3」→「階級3程度以上」）は**もっと強いかもしれないという安全側の変化**なので、
  数値だけで比べると据え置きと誤判定して**無音で消える**。門は 2 つあり、**両方**に要る。
  - 安定待ちの比較（`EEWLpgmStabilityCycle` が `{ cls, over }` を持つ）
  - 既読との比較（`isForecastLpgmHigher`。震度側の `isForecastScaleHigher` と同じ形）
- **語は確定値と一緒に持ち回る。** 現在の報から引き直さない —— 確定値は安定待ちを経ているため
  現在の報と食い違いうる。引き直すと別の値に語を貼り付ける（`eewIntensityText` の `lpgmOver` 引数）
- 語を出す箇所: EEW カードのバナー・ウィンドウタイトル・ブラウザ通知・読み上げ・区域塗りの
  ポップアップ（ホバー時のバッジを含む）・**震源×印のポップアップ**。
  **新たに予想震度を出す箇所を作ったらここに追記する**
- **読み上げの「上がったか」の比較にも入れる。** 階級値だけで比べると、同じ階級のまま上限が
  定まらなくなった変化（「震度4」→「震度4以上」）を据え置きと見て黙ってしまう。判定は
  `src/utils/eew.ts` の `isForecastScaleHigher()` に集約する
  （[`audio-tts-spec.md`](audio-tts-spec.md) §6）
- 「以上」の集約規則: 最大の階級を与えた区域を基準にする。同じ階級の区域が複数あって片方だけが
  「以上」なら「以上」を採る（強い側の表現を残す）。最大でない区域の「以上」は拾わない

### 区域の種別コード（`areas[].kindCode`）

電文の区域が持つ種別。気象庁「地震火山関連コード表」の表 12（緊急地震速報種別）の値をそのまま使う
（DMDATA の `regions[].kind.code`）。**レベル判定には使わない**（`computeSingleEEWLevel` は
`severity` と予想震度・長周期階級だけを見る）。区域の話なのでこの節に置くが、判定には関与しない。
使うのは「警報域か予報域か」の表示の出し分け。

| コード | 種別 | 主要動 |
|---|---|---|
| `00` / `01` / `09` | 緊急地震速報（**予報**） | 未到達と予測 / 既に到達と予測 / 到達予想なし（PLUM 法。→ §5） |
| `10` / `11` / `19` | 緊急地震速報（**警報**） | 同順 |

- 警報域の判定は `10` / `11` / `19` の 3 値。**判定は `isEewWarningKindCode` の 1 か所に置く**
  （`src/utils/eewKind.ts`）。使う側は 3 つある —— 電文が警報級かどうか（`severity`）、
  `RealtimeTab` の「警報:」「予報:」欄の振り分け、区域塗りの濃さ（`EewRegionFillGL` が
  警報域を `fillOpacity` 0.55・予報域を 0.3 で塗る）。**同じ 3 値を書き分けると、
  片方だけ直したときに静かにずれる**
- **判定に使うのはコードで、名前（`Kind/Name`）ではない。** どちらも同じ事実を表すが、名前は
  表記が変われば一致しなくなる。名前を見るのは、**コード表に無い値が来たとき**だけ —— 警報を
  取りこぼさないよう安全側へ倒し、読めなかったコードを記録に残す
- 警報が発表されるのは予想震度 5 弱以上の区域。震度 4 以下の区域は同じ電文の中でも予報域になる
- `kindCode` が空の電文もある（`RealtimeTab` は全区域が空なら「警報/予報」に分けず「対象:」表示へ落ちる）
- **区域が電文に載る条件**: 最大予測震度 4 以上**または**最大予測長周期地震動階級 3 以上
  （eew-information スキーマ）。震度 3 以下で長周期も 3 未満の区域は電文に現れない
- 合成テストデータもこの節の規則に従う（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7「実電文の形に合わせる」）

### 主要動が届いたかどうか（`areas[].arrived`）

上の表の「主要動」の列は、**電文がもう 1 つ別の形でも伝えてくる**。区域の `Condition`
（値は「既に主要動到達と推測」の 1 つだけ。電文解説資料 Ⅱ.21 2-1-5-3-7）。

| 伝え方 | DMDATA | P2PQuake |
|---|---|---|
| 種別コードの下 1 桁（`01` / `11`） | 読む | **読む** |
| 区域の `Condition` | 読む（→ `EEWRegion.arrived`） | 配信されない |

**判定は `isEewAreaArrived`（`src/utils/eew.ts`）の 1 か所に置く。** どちらかが立てば到達済みとして
扱う —— 片方しか無い電文が来ても取りこぼさないため。**`arrived` を直接見ないこと**：
`Condition` を配信するのは DMDATA だけなので、そちらだけを見ると standard 版で到達済みの区域が
「時刻も印も持たない区域」に落ちて画面から黙って消える。

**片方しか無いことを異常として記録しない。** 資料が排他だと定めているのは `Condition` と
`ArrivalTime` のあいだ（同 2-1-5-3-6）だけで、**コードと `Condition` が必ず同時に出るとは
書いていない**。手元の実電文で両方そろっている例は数えるほどしかなく、そこから「常にそろう」と
決めるのは標本が薄い。鳴らすようにすると正常な電文でログが埋まり、本物の異常が沈む。

記録するのは `Condition` の値が資料の定める 1 つ（「既に主要動到達と推測」）から外れたときだけ
——そちらは値域が定まっているので、外れれば確かに異常。

### 到達予測時刻は種別によって意味が変わる（`areas[].arrivalTime`）

同じ要素に 3 通りの状態が入る。**時刻の有無だけで絞ると、性質の違うものが 1 つの列に並ぶ。**

| 区域の状態 | 電文 | `RealtimeTab` の「主要動の到達（予測）」欄 |
|---|---|---|
| まだ到達していない | `ArrivalTime`（到達予測時刻） | 時刻（**秒まで**） |
| 既に到達したと推測 | 時刻は出ず、上記の 2 通りで伝わる | 「到達済みと推測」 |
| PLUM 法（`09` / `19`） | `ArrivalTime`（**その震度を初めて予測した時刻**＝過去） | 「到達時刻は不明」 |

- **PLUM 法の時刻を「到達予想」として出さない。** 周辺の観測点で実際に観測された揺れから震度を
  出す手法で走時を計算しないため、値は到達の予測ではない（同 2-1-5-3-6）。並べると、既に過ぎた
  時刻をこれから来るものとして読ませる。判定は `isEewPlumKindCode`
- 並びは時系列のとおり（到達済み → PLUM 法 → 到達予測時刻順）。上位 6 件までで、残りは「他N地域」
- **この欄だけ秒まで出す。** 電文は秒の値まで持っており、区域ごとの差は数秒。時:分に丸めると
  隣り合う区域の到達順が潰れる。津波の時刻表示（分単位で発表される）が `HH:MM` なのとは
  意図的に揃えていない
- **見出しに「予測」を残す。** 3 通りとも気象庁の予測・推測で、確定した事実ではない。中立な
  見出し（「主要動の到達」）にすると、時刻の行だけが断り書きを持たないまま確定時刻の顔をする ——
  他の 2 通りは「推測」「不明」と語の中に断りがある。**意味の違いは `DescriptionTip` で
  ホバーへ逃がす**（同じカードの「精度情報」と同じ流儀）。PLUM 法という手法の名前も
  そちらに置き、行には状態そのもの（「到達時刻は不明」）を書く

### 想定外の値に対する実行時ガード

`eewMaxScale` は震度スケール外の値を、`eewMaxLpgmClass` は 1〜4 以外の階級を採用しない
（`isValidIntensityScale()` / `isValidLpgmClass()`）。型（`IntensityScale` / `LpgmClass`）で
宣言してはいるが、実地震シナリオ JSON のように型検査が及ばない経路があるため実行時にも弾く。
これが無いと、壊れた入力の値がそのまま `>= 55` / `>= 4` の比較を通って特別警報へ誤昇格する。
**特別警報は震度と長周期地震動階級の OR 判定なので、片方だけ守っても誤昇格は防げない。**

両関数を経由しない参照経路にも同じガードを通している:

- **地図の区域塗り**（`useEewLayerData`）は `areas[]` を直接集計する（震度区域・長周期区域の両方）。
  とくに長周期側は `getLpgmClassLabel()` がフォールバックを持たなかったため、弾かないと
  「階級99」のような値がそのまま地図ラベルに出ていた（現在は同関数も「階級不明」へ落とす）。

一方、**読み上げ**（`ttsText.ts`）は震度・長周期階級のどちらも両関数を経由する。音声には色の
フォールバックのような逃げ場が無く、不正値がそのまま声に出てしまうため。

> かつては階級だけが `forecastMaxLpgmClass` を直接参照しており、両関数が持つ「地域別予想を優先」の
> ガードが読み上げにだけ効いていなかった。**同種の値を扱う経路は、片方だけ生フィールドを読まないこと。**

**震度を伝えられない報では階級も出さない。** 判定は `eew.ts` の `canPresentLpgmClass` で、
**カードの階級バッジ（`RealtimeTab`）・読み上げ（`eewIntensityText`）・第 2 フェーズの言い直し
（`useLiveEventHandler` の震度据え置き分岐）の 3 経路が同じ述語を共有する**（片方だけに置くと画面と
音声が食い違う）。気象庁の電文では最大予測震度が必須要素で、長周期地震動階級のほうが任意——つまり
**「震度なし・階級あり」という電文は作れない**。到達したら電文の異常なので、読み上げ経路が
`log.warn` で記録を残す。深さ 150km 超では階級のほうが先に落ちる（震度と違い PLUM 法による例外規定を持たないため）。
そのまま読むと「予想震度なし。予想最大階級3。」という矛盾した発話になるので、震度が取れないときは
階級句ごと省く。

> かつてここには「深発地震で長周期階級だけが載る電文が実在するかは未確認」と書いてあった。
> 電文仕様を確認した結果**仕様上ありえない**と判明し、実データ（2024 年能登 1/1〜1/3）でも深さ 150km 超の
> 13 報すべてが階級を持たなかった。仮定震源要素の 72 報も同様に 0 件で、こちらは PLUM 法が長周期階級を
> 予測しないため。

## 5. 仮定震源要素（震源未確定）の扱い

電文の `condition === '仮定震源要素'` は「**震源要素が推定できず、PLUM 法による震度予測だけが有効**」な
状態を指す。震源が決まらないので、気象庁は PLUM 法でトリガー条件を最初に満たした観測点の**直下 10km・
M1.0** を仮の震源として電文に書く。震央地名もその観測点の所在地であって、震源の推定位置ではない。
（定義と固定値の出典: 気象庁「[緊急地震速報に関する情報のコード電文解説資料](https://www.data.jma.go.jp/suishin/shiyou/pdf/no40202)」・
[配信資料に関する技術情報第 566 号](https://www.data.jma.go.jp/suishin/jyouhou/pdf/566.pdf) 別添資料 1）

（**PLUM 法** = 周辺観測点で実際に観測されたリアルタイム震度から予想震度を算出する手法。震源要素を
使わないため、揺れが観測された瞬間から数秒で予報を出せる。詳細は
[`kyoshin-detection-spec.md`](kyoshin-detection-spec.md) 参照）

> **「単独観測点処理」と同義ではない。** 定義に観測点の数は含まれておらず、PLUM が何点鳴っていても
> 震源要素が推定できなければ仮定震源要素になる。電文の「震央の確からしさ」でも *IPF 法（1 点）* と
> *仮定震源要素* は並列に列挙された別物で、前者は「1 点で震源を決めた」、後者は「決められなかった」。
> 実データ（2024 年能登 1/1〜1/3）では仮定震源要素 72 報のうち **50 報が最大予測震度を持っていた**
> ——気象庁は観測点 1 点による震度予測では値を出さないので、これらは PLUM が 2 点以上鳴っている報。
>
> 呼び方が意味を持つのは**予想震度が付いていない報の理由を述べるとき**だけ。**気象庁のいう
> 「観測点 1 点による震度予測」とは、PLUM 法が 1 地点でしかトリガーしていない状態を指す**——
> 仮定震源要素で値が載っていない報がちょうどそれにあたるので、画面・読み上げとも「単独点処理のため」
> と言える（判定は `eewNoForecastReason`）。PLUM が 2 点以上なら値が載り、`eewMaxScale` が拾うので
> この経路へは来ない。
>
> **警報級の仮定震源要素も実在する**（同期間で 9 報）。「震源が決まらない＝軽い地震」ではない。
>
> **かつては仮定震源要素というだけで予想震度・長周期階級を 0 にしていた。** 同期間で区域を持たない
> 25 報が「予想震度なし」に落ちており、いずれも電文には「震度 3 以上」が載っていた（§4 の
> フォールバック規則を参照）。

以下の**複数箇所で連動して非表示化する**（片方だけ直すと非対称になる）。数を書くと列挙漏れがドリフトしやすいため、
新たに `condition` を参照する箇所を追加したときは必ずこのリストに追記する:

- **予報円を出さない** — `src/hooks/usePsWaveCalc.ts` の `computeEewCircle`（`condition === '仮定震源要素'` で早期 return）。
  震源が仮の値であることに加え、**気象庁は PLUM 法による予測の報で主要動の到達予測時刻を出さない**
  （PLUM は震源を使わないため猶予時間を算出できず、受信端末向けのガイドラインも「まもなく到達」等の
  表現を推奨している）。予報円は猶予時間の図示なので、描けば根拠のない秒数を見せることになる
- **カードで M・深さを隠す** — `src/components/RealtimeTab/index.tsx` の EEW カード内表示条件
- **カードの震源名に「（震源未確定）」を添える** — 同じく `RealtimeTab`。地名は最初に揺れを捉えた
  観測点の所在地であって震源の推定位置ではないため、M・深さを伏せるだけでは断定して見える
- **共有カードの見出しで M を出さない** — `src/utils/shareCardContent.ts` の `kyoshinContent`
  （[`share-card-spec.md`](share-card-spec.md) §3）。**画面より強い理由がある**——共有された画像は
  後から訂正できない。予想震度は区域ごとの発表値なので、そちらは隠さない
- **地図の震源×印を控えめに描く** — `src/hooks/useEewLayerData.ts` で `EewEpicenter.isAssumed` フラグ生成 →
  `src/components/Map/EewEpicentersGL.tsx` が不透明度（`crossOpacity`）と点滅の振幅（`EEW_BLINK.assumed`・
  0.9 ↔ 0.45。確定震源は `EEW_BLINK.confirmed` で 1 ↔ 0.1）の両方を弱める。
  **不透明度だけで弱めない**のは、この 2 つが乗算されるため（[`map-rendering-spec.md`](map-rendering-spec.md)
  §16）。下げるだけでは点滅の谷で×印が消える。引き換えに、**仮定が確定より薄いのは濃い側だけ**になり、
  点滅の谷ではどのモードでも仮定の方が濃くなる（確定の方が谷が深いため）。積の下限は
  `src/components/Map/EewEpicentersGL.test.ts` が固定している
- **地図の震源に深さを採らない** — 同じく `EewEpicentersGL.tsx`。確定震源は電文の深さへ置くが、
  仮定震源要素は地表（深さ 0）に置く。M・深さを画面から隠すのと同じ扱いで、**採ると確定していない
  数値を立体で断定して見せることになる**。深さ 0 では柄の長さが 0 になり、震央の印もレイヤー側の
  判定で自動的に消える（[`map-rendering-spec.md`](map-rendering-spec.md) §16）
- **検知エンジンの EEW 連動緩和判定** — `src/App.tsx` の `hasActiveNonAssumedEEW`
- **区域への S 波到達推定の震源に採らない** — `src/hooks/useEewLayerData.ts` の `eewAreaFills` が
  `EewAreaFill.origin` を作るときに除外する。M・深さが仮定値（実データでは M1・深さ 10km 固定）なので
  走時を解いても根拠のない秒数になる。除外の結果 `origin` が null になった区域では、区域塗りの
  ポップアップが S 波到達の行を出さない（`EewRegionFillGL` の `arrivalRowHtml`）。
  ただし**同じ階級を確定震源の EEW も与えているなら、そちらの震源で埋める**（出せる根拠があるなら使う）
- **揺れ検知の基準震源選定** — `src/hooks/useKyoshinAlerts.ts` の `extractEewInfo`
- **予想震度が出ない理由の判定** — `src/utils/eew.ts` の `eewNoForecastReason`。読み上げの文言
  （`src/utils/ttsText.ts` の `noForecastText`）と、予想震度の確定を待つかどうかの判断
  （`src/hooks/useLiveEventHandler.ts` の第 2 フェーズ）はどちらもこれを通す。分類と待ちの決まりは
  [audio-tts-spec.md](audio-tts-spec.md) §4・§6 が単一情報源。**読み上げ側が `condition` を直接見るのは
  やめたので、この関数だけを直せばよい**
- **`condition`/`hypocenter` の明示マージ** — `src/hooks/useEarthquakes.ts` の `enrichEEW`（§3 参照。standard 版で、後着の P2PQuake が明示的に上書きし、Yahoo 由来の誤った `condition` が残り続けないようにする。ここが崩れると下流の全判定が破綻する）

**バリアント差の非対称**: Yahoo hypoInfo は `condition` に相当するフィールドを持たず**空を返す**ため、
standard 版で Yahoo hypoInfo が先に仮定震源要素の EEW を検知した場合、後続の P2PQuake で
上書きされるまでの間は「確定震源として表示」される。既知の限界（実運用時の確認をユーザーに委ねる）。

> **空にしているのは「判らない」を表すため。** かつてここは `'以上'` という**電文に存在しない値**を
> 返していた。判定は `=== '仮定震源要素'` しか見ないので挙動には出ず、何を意味するのかも辿れない
> 値が残っていた。電文の値域は「仮定震源要素」の 1 つだけで、該当しなければ要素ごと出ない
> （電文解説資料 Ⅱ.21 1-2。実電文 26 通の実測でも空か「仮定震源要素」の 2 つだけ）。

## 6. 予報円（P 波・S 波）

**`src/hooks/usePsWaveCalc.ts`** が単一情報源。2 層速度モデル（地殻＋マントル・Pn/Sn 屈折波）で
自前計算する。**標準版・DMDSS 版で共通**。

- 入力: `EEWAlert.earthquake.hypocenter`（lat/lng/depth/magnitude）と `originTime`
- 更新頻度: 100ms（`UPDATE_INTERVAL_MS`）で `setInterval`
- 停止条件: `activeEEWs.length === 0` または `isFinal:true` かつ計算不能
- 出力: `PsWaveCircle[]`（各 EEW に対する現時点の P 波・S 波半径）

### 距離はすべて球で解く

**地表は曲がっている。** アプリの距離計算は `utils/geo.ts` の `EARTH_RADIUS_KM`（6371km）を
単一情報源とし、地表距離は `haversineKm`（大円）、地表距離と深さの組は
`hypocentralDistanceKm` / `surfaceDistanceKm`（球の弦）で解く。

**「√(地表距離² + 深さ²)」は使わない。** 平らな直角三角形で解くと、震央から離れるほど地表の点が
震源から見て「下がって」いくぶんを取りこぼす。浅い地震では 0.1% 未満だが、深発地震で遠方を見ると
効く（地表 800km・深さ 700km で 3.3%）。

**屈折波（Pn/Sn）の距離も換算する。** 屈折波はモホ面（半径 R−33km の球面）を伝わるので、同じ角度でも
地表のほうが弧が長い（`MOHO_TO_SURFACE` = 1.0052）。ここを換算しないと、直達波だけ球・屈折波だけ
平面という混在が残る。

予報円の頂点も同じ球で解く（`components/Map/gl/psWaveRing.ts` の `ringVertex`。震央から方位 θ へ
距離 km だけ大円上を進んだ点）。**円の外接矩形（カメラ追従）・破線の本数も同じ関数を通す**——
別々の近似で出すと、円と矩形・円と破線がわずかにずれる。

**外接矩形の東西端は「真東・真西へ半径ぶん進んだ点」ではない**（`ringBounds`）。大円は東へ進むと
赤道側へ曲がるので、最も東へ届くのは方位 90 度より少し極寄りの点になる。経度の最大差は
`asin(sin(Δ) / cos(緯度))`（Δ は角距離）で、総当たりの探索と一致することを確認済み。方位 90 度で
代用すると緯度 40 度・半径 800km で 5.8km、緯度 80 度・半径 300km で 60km 過小になる。
南北端のほうは方位 0・180 の点で厳密に正しい（そこで緯度の変化率が 0 になるため）。

**シェーダー側は単精度**なので、TypeScript 側（倍精度）と完全には一致しない。同じ式を単精度で解いて
突き合わせた実測では、ずれは半径によらず 30〜320m（半径 1km でも 171m 出るので、式の桁落ちではなく
三角関数の実装誤差が支配的）。円の半径に対して 0.04〜0.6% で、zoom 10 でも 3px 程度。

平面（Mercator）投影で表示しているときは、地面の上で正しい円でも画面上では北側が大きくなる
（半径 400km で 4%）。これは図法そのものの性質で、円の作り方では消せない。消すには円が波の到達位置を
表さなくなるのを受け入れるしかないので、消さない（[`map-rendering-spec.md`](map-rendering-spec.md) §6）。

震源深さは `Math.max(0, depth ?? 0)` でクランプする。深さ不明（`-1` センチネル）が来ると 0 に落ちて
「ごく浅い」として計算される点は既知の課題（`depth < 0` で「深さ不明・円を出さない」分岐が望ましい）。

**既知の限界（EEW-5）**: `depth > MOHO_KM`（33km）の分岐は「マントル速度で直達波」のみを
計算しており、地殻区間を経由する屈折波（本来は Snell 則で扱うべき）を考慮しない。結果として:

- 走時を **相対誤差 約 19%（一定）** で過小評価する（例: 震源直上 R=0 で約 2 秒、R=100km で約 5.6 秒、
  R=300km で約 15.9 秒。絶対値は距離に比例して拡大するが相対誤差は距離非依存）
- `depth=MOHO_KM` 前後で分岐境界の不連続ジャンプが生じる

正しい修正には Snell 則ベースの traveltime 再設計が必要で、`computeSWaveTravelTimeSec` と対にリファクタする
大きな作業になるためスコープ外とした（単純な max 比較で 2 区間走時を代替する案は代数的に無効と判明済み）。

## 7. 自動解除（`calcEEWCancelTime`）

**明示的な取消電文が来ない限り**、EEW は一定時間経過後に**無音・即消去**される（キャンセルオーバーレイなし）。
計算式は**司・翠川式**（震源からの距離に応じて震度がどれだけ減衰するかを近似する経験式・地震工学で広く使われる）
から**有感半径**（震度 1 以上が届くと推定される距離）を二分探索で逆算し、そこまで S 波が届く時間 + 30 秒を
自動解除時刻とする。最終報から最低
60 秒（`MIN_CANCEL_SEC`）は表示を保つ。詳細は `src/utils/eew.ts` の `calcEEWCancelTime` /
`calcEEWAutoCancelSec` / `calcFeltRadiusKm`（二分探索）参照。

再生（テスト時刻設定 →
[`settings-pwa-spec.md`](settings-pwa-spec.md) §6）中も同じ猶予が効く。解除の予約は再生時計の
時間軸で評価するため、最終報を受けた直後に消えることはない（→ 同 §6「再生中も予約は発火時刻を待つ」）。

## 8. 誤報取消（明示的な取消電文）

DMDATA・P2PQuake で明示的な取消電文（`cancelled: true`）が来た場合、自動解除と異なり以下を伴う。

**取消は `isFinal` も立つ**（§3。そのイベントの打ち切りだから）。ただし消費側はどこでも
`cancelled` を先に見て分岐するので、`isFinal` の値で取消の扱いが変わることはない。

- `eewCancel` 音の再生（`hadKey=true` のみ。二重鳴り防止）
- ブラウザ通知（`hadKey` 有無を問わず発火。tag=`eew-cancel-${key}` で自動上書きされるため二重にならない）
- VOICEVOX 読み上げ（`hadKey=true` のみ。二重鳴り防止）
- カードに「誤報として取り消されました」表示（10 秒間）

`useLiveEventHandler.ts` の EEW 分岐で「`event.expired` フラグの有無」で自動解除と誤報取消を区別する。
`hadKey` は「このセッションで `activeEEWLevelsRef` に既に登録されていた eventId か」を表す:

- **hadKey=true**: 画面に表示中の EEW を取り消す通常経路 → 音・通知・読み上げの全てを発火
- **hadKey=false**: 既に自動解除済みの後に本物の誤報取消が遅延到達したケース、または P2PQuake WS と Yahoo の両方から cancel が来た場合の 2 回目 → 通知のみ発火（音・読み上げは二重鳴り防止のためスキップ）

**取消しの理由（`Body/Text`）を読む**（`EEWAlert.cancelText`）。取消電文は `Body` に `Text` しか
持たず、そこに気象庁が書いた取り消しの概要が入る。**地震情報・津波情報とまったく同じ構造**なので
3 種別で扱いを揃える —— 片方だけ拾うと、同じ事象なのに種別によって理由が出たり出なかったりする。
**リアルタイムタブの EEW カードの取消オーバーレイ**に定型文の下へ添え、読み上げも定型文の後ろに
続ける。長い本文は読み上げを切って画面へ委ねる（[audio-tts-spec.md](audio-tts-spec.md) §4）。
`activeEEWs` の更新は表示中の EEW を土台にするので、**取消電文だけが持つ項目は名指しで移すこと**
（落とし穴の詳細は [quake-spec.md](quake-spec.md) §8「取消しの理由は電文にしかない」）。

**取消電文は予想を持たない**: `dmdataParser` は取消（`isCanceled`）のとき震源座標を 0 にし、
`forecastMaxScale` / `forecastMaxLpgmClass` を入れない。区域も空。表示側は `activeEEWs` の
直前の確定状態を保つため取消電文の中身を使わないが、通知文・読み上げは `hypocenter.name` と
`issue.time` を読むのでこの 2 つは残る。合成テストデータも同じ形を作る
（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7「実電文の形に合わせる」）。

## 9. 音・タブ切替・通知の連動

`useLiveEventHandler.ts` の EEW 分岐が主。以下を発火する:

- **音**: `selectEEWSoundType(isNew, levelUpgraded, currentLevel, isFinal)` で種別決定 →
  `playAlertSound(type)`。種別: `eewSpecial` / `eew` / `eewForecast` / `eewUpdate` / `eewFinal` / `eewCancel`
- **通知**: `showBrowserNotification(...)` で OS 通知
- **読み上げ**: `speakWithVoicevox(eewAlertToText(...))`
- **自動タブ切替**: 新規・レベルアップ・誤報取消は最上位の優先度で realtime を確保し、続報は
  それより 1 段低い優先度で要求する。**新規・レベルアップ・誤報取消が確保している 15 秒間は、
  地震情報・長周期地震動情報・津波がタブを奪えない。続報が確保している間は、読み上げが無効な
  端末では電文の受信に越えられる**（優先順位の全体像は [`audio-tts-spec.md`](audio-tts-spec.md)
  §6「自動タブ切替の優先順位」）。続報は手動選択より弱いため、ユーザーが自分で別タブを選んだ
  直後は realtime へ戻らない。ただし新規・レベルアップは手動選択より強く、必ず realtime を
  取り戻す。EEW のレベル（特別警報級か否か）はタブの奪い合いに関与しない
- **カメラフィット**: `FitToEEWGL` が発火。第一報は S 波円（円が無ければ震源）へ寄り、以降は
  予想の区域塗りまで含めた範囲を追う。追従の主な起点は EEW 電文と予報円の更新で、区域塗りの範囲
  （`useEewLayerData` の `eewFitPositions`）は発報中の追従にのみ加わる。kyoshin モード限定。
  詳細・モード限定の理由は [`map-rendering-spec.md`](map-rendering-spec.md) §6（後段「既知の限界（MAP-5）」）参照

**音種別の優先順位**（`selectEEWSoundType` の判定順）:
1. **新規発報またはレベル格上げ**（`isNew || levelUpgraded`）→ `currentLevel` に応じて
   `eewSpecial`（特別警報）／`eew`（警報）／`eewForecast`（予報）。**`isFinal` より優先**するため、
   最終報で震度・長周期階級が上がって levelUpgraded=true になる最重要ケースでも警戒音を鳴らす。
2. **続報の最終報**（`!isNew && !levelUpgraded && isFinal`）→ `eewFinal`（穏やかな終了音）
3. **通常続報**（上記のいずれでもない）→ `eewUpdate`

ただし現状は続報時の音・読み上げの多重発火防止に弱い箇所がある（`useLiveEventHandler.ts` 内の
5 箇所の setTimeout が未追跡）。

## 10. `activeEEWs` の状態遷移

```
[受信]              [enrichEEW / handleEvent]         [状態]
  ├─ 新規 EEW      →  activeEEWs.set(key, eew)      →  active
  ├─ 続報          →  activeEEWs.set(key, newEew)   →  active（上書き）
  ├─ 古い報        →  何もしない（報番号で棄却）    →  active（現状維持）
  ├─ enrich        →  既存に areas/condition/hypocenter マージ
  ├─ 誤報取消      →  cancelledAt セット・10 秒後 purge
  └─ 自動解除      →  時刻到達で activeEEWs.delete(key)（無音）
```

### 古い報で退行させない

**続報は丸ごと上書きするため、順序が入れ替わると内容が古い側へ戻る。** 表示中の報より報番号が
小さい報は適用しない。

順序が入れ替わりうるのは、EEW が**同じ秒に複数の報を出す**ため（能登本震の実配信では 46 報中
13 報が同一秒）。キューは電文の時刻でしか並べ替えず（`enqueueEvent`）、その時刻は秒精度しかない。
加えて WebSocket の受信は body の展開（gunzip）を待たずに次へ進むため、同じ秒に届いた報は展開の
完了順で処理されうる。

判定で守ること。

- **入口（`handleEvent` の先頭）で捨てる。** 読み上げ・ウィンドウタイトルへの通知と自動解除の予約は
  状態更新の外で走るため、状態更新の直前で弾いても間に合わない。**地図・カードだけが新しい報を保ち、
  読み上げとタイトルが古い報で上書きされる**——揃って退行するより始末が悪い
- **入口の判定は「受理した報番号の台帳」で行う（表示中の状態を見ない）。** キューのディスパッチャは
  1 ティックの中で `handleEvent` を連続で呼び、その間 React の状態はレンダー待ちで進まない。状態を
  見ると直前に受理した報を見落として素通しする。表示が終わった EEW の分は掃除する（残すと伸び続ける）
- **状態更新側にも判定を置く。** ただし比べる相手は違い、こちらは表示中の値（`isStaleEewReport`）。
  状態の整合性を守る二重化で、通知の保護は台帳が担う
- **報番号を持たない経路では判定しない。** P2PQuake は `issue.serial` が欠けることがあり、欠けた側を
  0 とみなすと正しい報まで捨てる。数値化は `eewSerial`（`utils/eew.ts`）に委ねる
- **同じ報番号の再送は棄却しない。** 訂正報も同じ番号で届きうるため、内容の異同にかかわらず通す
- **取消・失効・テスト報は判定を通さない。** ここで弾くと誤報を消せなくなる
- **捨てたことを記録する。** 判定が誤り続けるとその EEW は以降更新されない。痕跡が無いと原因に
  辿り着けないため入口で `log.debug` に残す

> P2PQuake 補完経路（`enrichEEW`）も**同じ台帳で判定し、受理したら台帳と報番号の両方を進める**。
> この経路はキューを通らず WebSocket から直接呼ばれるため、台帳を共有しないと `handleEvent` 側の
> 受理と入れ違いになる。中身だけ注入して報番号を据え置くと、格納した EEW の報番号が内容の
> 新しさを表さなくなる。

**この判定が守らない範囲。**

- **取消のあとに来る、より大きい報番号の非取消報。** 報番号だけを見るため、取消済みのエントリが
  書き戻されうる（気象庁の運用では取消が最終報のため実際には起きない）
- **報番号の系列が経路をまたいで一致すること**を前提にしている。standard 版は Yahoo hypoInfo の
  `reportNum` と P2PQuake の `issue.serial` が同じ `eventId` に合流しうるが、どちらも気象庁の
  報番号に由来するという前提を置いている
- **報番号を持たない報を挟んだ直後は精度が落ちる。** その報で内容が進んでも台帳は前の値のままなので、
  次に来る報を古い台帳と比べることになる（DMDATA 経路は `serial` が常に埋まるため、起こるとすれば
  P2PQuake 経路に限られる）

キーは `eew.issue?.eventId ?? eew.id` を統一パターンで使う。**地図の震源×印の差分更新キー
（`EewEpicenter.id`）も同じ式を使う。** `eew.id` は報番号込み（DMDATA は
`dmdata-eew-<eventId>-<serial>`・P2PQuake は報ごとに変わるレコード ID）なので、これを直接キーに
すると続報ごとにマーカーを作り直し、点滅が止まってポップアップも閉じる
（理由と対策は [`map-rendering-spec.md`](map-rendering-spec.md) §10）。

`issue.eventId` は DMDATA・P2PQuake のどちらの経路も持つ。Yahoo 強震モニタの hypoInfo 経路
（standard 版の補完）も持ち、`id` 自体にも報番号を含まない。**つまりフォールバックの `?? eew.id` は
防御用で、実データでは通らない。**
