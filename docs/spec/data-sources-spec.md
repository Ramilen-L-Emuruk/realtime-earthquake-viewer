# データソース仕様書

> 本書は**アプリが使用する外部データソースと接続の仕組み**をまとめた仕様書。
> 実コードと食い違う場合は実コードを正とする。

## 1. 概要

3 系統のデータソースを扱う:

- **DMDATA.JP**（DMDSS 版・要 API キー） — 地震情報・EEW・津波情報の主系
- **P2PQuake API v2**（標準版・認証不要） — 地震情報・EEW・津波情報の主系
- **Yahoo!天気・災害 リアルタイム震度**（両バリアント共通） — 強震モニタデータ。EEW 補完は標準版のみ

さらに以下も外部・準外部データとして扱う（「オプショナル」は設定で表示を切り替えられるもの）:

- 気象庁 予報区等 GIS データ（都道府県・一次細分区域の境界／津波予報区の海岸線）
- 気象庁 震度観測点一覧表（震度観測点の座標＋所属区域のテーブル）
- 気象庁 地震月報（カタログ編）震源データ／震源リスト（長期震源カタログ）
- GEBCO 海底地形タイル（背景・オプショナル）
- 産総研 活断層データベース（オプショナル）
- PB2002 プレート境界（オプショナル）

## 2. DMDATA.JP（DMDSS 版）

### エンドポイント

- WebSocket: `wss://ws.api.dmdata.jp/v2/socket`
- REST: `https://api.dmdata.jp/v2/*`

### 認証

Basic 認証（`Authorization: Basic base64(apiKey:)`）。API キーはユーザーが設定タブで入力し、
`localStorage` に平文保存する（BYOK / Bring Your Own Key 方式）。ビルド時にキーが埋め込まれることはない。

例外は開発時のみ。DMDSS 版の dev サーバーではリポジトリ直下の `.env.local` の値が設定タブの初期値として
入る（本番ビルドには渡らず、`localStorage` にも保存しない）。条件は
[`settings-pwa-spec.md`](settings-pwa-spec.md) §6「dev サーバーでの API キー自動投入」を参照。

設定欄は 1 文字ごとに保存するが、**通信を起こす側へ渡す値は 800ms のデバウンスを挟む**
（`App.tsx` の `API_KEY_DEBOUNCE_MS`）。手入力・修正のたびに未完成のキーで接続と履歴取得を
やり直すと、そのすべてが 401/403 で失敗して無駄なリクエストとログを生むため。リプレイ機能だけは
ユーザーがボタンを押した時点でしか通信しないので、生の値をそのまま使う。

**キーに使える文字**: 印字可能 ASCII（`!` 〜 `~`）のみ。空白・制御文字・全角や日本語は受け付けない
（`isValidDmdataApiKey`）。キーの書式そのものを当てにいくのではなく、**Basic 認証ヘッダに載せられるか
だけ**を見ている。実在のキーはピリオドを含むため、英数だけに絞ると正規のキーを弾く。

使えない文字が入っている間は**通信を起こさない**。設定タブは入力欄を赤枠にして理由を表示し、接続状態は
「APIキーが不正」になる。地震タブにも同じ理由が出る。**入力欄の値は書き換えない**（貼り付けたキーが
黙って変わると「合っているのに繋がらない」状態になる）。WebSocket はこれを 401/403 と同じ非回復扱いに
して再接続しない。

**未設定と「使えない文字」は言い分ける**（`dmdataApiKeyProblem` が `'missing'` / `'invalid'` を返し、
文言の選び方は `dmdataApiKeyMessage` に集約する）。原因も対処も違う——未設定はまだ入れていない状態
（入れれば直る）で、不正は入れた値が載せられない状態（どこが悪いか分からないと詰まる）。同じ文で
知らせると、一度も入力していない人に「使用できない文字が含まれています」と告げ、入れた覚えのない
文字を探させることになる。

ライブ取得（`useEarthquakes`）とヒートマップ（`useQuakeHeatmap`）は**未設定を手前で弾いて黙って
取得しない**（利用者が選んだ状態なので知らせる必要がない）。リプレイと履歴の追加読み込みだけは
事前に弾かず、ヘッダを組む時点の例外（`authHeader`）に任せる。**このうち未設定の文言が実際に
ユーザーへ出るのはリプレイだけ**——理由が設定タブに出る。追加読み込みは他の取得失敗と同じくログだけで、
画面には「増えなかった」ようにしか見えない。

> この判定が無かった頃に何が起きていたかは §11 改訂履歴（2026-08-21）に記録している。

`DecompressionStream('gzip')` で復号してから `dmdataParser.ts` で内部型に変換する。

#### EEW は VXSE45 だけを受ける

購読分類は `eew.forecast` と `telegram.earthquake` の 2 つ。VXSE43 だけを含む分類 `eew.warning`
は購読しない。分類と種別の集合はどちらもライブ（WebSocket）とリプレイ（アーカイブ要求）で共有する
（`dmdataTelegramPayload.ts` の `CLASSIFICATIONS` / `EEW_TYPES`）。**片方の経路にだけ足すと、同じ
電文が経路によって届いたり届かなかったりする。**

**VXSE43 を受けない理由**は 2 つ。

- **遅れて届く複製が、新しい予想を上書きするため。** VXSE43 は対応する VXSE45 の警報報と同じ内容が
  同時か数秒遅れて届き、予想震度の区域はその時点の VXSE45 の部分集合にしかならない。表示中の EEW は
  `eventId` だけで束ねられ、後から届いた報で丸ごと置き換わるため、古い内容で区域塗りが削られる
- **報番号の系列が別。** VXSE43 の第 1 報が VXSE45 の第 2 報に対応するなど独立しており、混ぜると
  同じ地震に番号の異なる報が並ぶ

失うものは無い。警報級の判定は VXSE45 の `body.isWarning` が同時か先に立てるため、表示・音・読み上げは
変わらない（区分を決めるのは電文種別ではなく `severity`。[eew-spec.md](eew-spec.md) §3）。

> **識別のしかたは地震カードと同じだが、統合のしかたは違う。** `eventId` 等の識別子で 1 件へ束ねる
> 考え方は [quake-spec.md](quake-spec.md) §6.1 と同じでも、地震カードが速報→詳細報と情報を積み上げる
> のに対し、EEW は新着報が既存を丸ごと置き換える（`severity` だけ upgrade only）。

> 2024/1/1 の能登半島地震（本震）の実配信で確認した実害: VXSE45 が 76 区域を出した直後に
> VXSE43 の第 3 報（40 区域）が届き、**区域塗りが 76 から 40 へ落ち、報番号も #30 から #3 へ
> 巻き戻っていた**。リプレイ経路は元から VXSE43 を取り込んでいなかったため、この壊れ方は
> ライブでしか起きず、テストシナリオでは再現しなかった。

リプレイ経路には**そもそも VXSE43 が現れない**。アーカイブ経路が要求する分類
（`eew.forecast,telegram.earthquake`）を展開しても VXSE43 は 1 通も入っておらず（2024-01-01 と
2026-07-28・07-29・08-21・08-22 の 5 日で確認）、当日経路が EEW を引く `/v2/gd/eew` も VXSE45 しか
返さない。VXSE43 を得るには分類 `eew.warning` を明示して取得する必要がある。

**購読していない VXSE43 が届いた場合は記録する。** `log.warn`（連続発報で溢れないよう間引く）と
電文ログの両方に残す。取り込まないことと、届いたのに気づけないことは別だからで、届くとすれば
配信分類の変わり目にあたる。一方 **VXSE44 は購読中の `eew.forecast` に日常的に含まれる**ため、
警告は出さず電文ログにだけ残す（廃止予定の旧形式で、同時刻の VXSE45 より区域が少ない）。

> **この判断が置いている前提**: 「警報級を示す `isWarning` は VXSE45 でも VXSE43 と同時か先に立つ」。
> 実配信の観測に基づくもので、破れた場合は警報級の電文を購読していないぶん受信すらできない。
> 上の記録はその検知を兼ねる。

#### 南海トラフ関連の 3 種別（VYSE50 / VYSE51 / VYSE52）

種別ごとに役割が違い、**臨時情報と解説情報は別物として扱う**。

| | VYSE50 | VYSE51 | VYSE52 |
|---|---|---|---|
| 情報名 | 南海トラフ地震臨時情報 | 南海トラフ地震関連解説情報 | 同左 |
| 内部型 | `JMANankai` | `JMANankaiCommentary` | `JMANankaiCommentary` |
| 段階を持つか | 持つ（調査中／巨大地震注意／巨大地震警戒／調査終了） | 持たない | 持たない |
| 発表の頻度 | 異常な現象が観測されたときのみ | 臨時情報の発表期間中、毎日 | 平常時に毎月 1 回 |
| `InfoSerial`（地震関連情報番号コード） | 調査中 `111` / 巨大地震注意 `130`（**実装では使わない**） | 臨時解説 `210` | 定例解説 `200` |

段階の判定には **`Head/Title`（情報名）の括弧内キーワード**を使う。例:
`南海トラフ地震臨時情報（巨大地震注意）`。

> **`Head/InfoKind` は判定に使えない。** 実電文では段階に関わらず「南海トラフ地震に関連する情報」で
> 固定されており、括弧内キーワードを含まない。かつてここを見ていたため、「巨大地震注意」が
> 「調査中」と表示され、さらに翌日以降の解説情報が臨時情報の段階を上書きしていた。
>
> `InfoSerial` のコードでも判定できそうに見えるが、**臨時情報側では使っていない**。コード表が
> 公開されておらず、実電文で確認できたのは上表の 4 値だけで、巨大地震警戒・調査終了は過去に一度も
> 発表されていないためコードが不明（表の `111` / `130` は実電文から読み取った値だが、参考情報として
> 載せているだけで実装は参照しない）。情報名は気象庁の資料で定義されているため `Head/Title` の方が
> 確実。解説情報側の `210` / `200` は臨時解説と定例解説の区別に**実際に使っている**（表示するバッジと
> 読み上げの文面がこれで変わる）。

解説情報は解除電文を持たない。帯は**発表から 7 日**で自動的に畳み、閉じるボタンでも消せる
（帯の仕様は [architecture-spec.md](architecture-spec.md) §4、音と読み上げの設定は
[settings-pwa-spec.md](settings-pwa-spec.md) §2）。

取消電文（`InfoType=取消`）は `cancelled` を立てて返し、**表示中の帯を消す**（音と読み上げは
起こさない）。実電文では一度も発表されていないが、他種別のパーサと扱いを揃えている。

> **取消を `null` で表さないこと。** パースできなかった場合と区別できなくなり、「解析失敗」の
> 警告が正常な取消のたびに出るうえ、帯を消す経路にも乗せられない。

電文の同一性は `EventID` と `Serial` の組で決まる。実電文で確認した挙動:

| | `EventID` | `Serial` |
|---|---|---|
| 臨時情報（VYSE50） | 電文ごとに変わる（発表日時） | 空 |
| 臨時解説（VYSE51） | **一連の期間で固定**（2024 年 8 月に取得できた 6 通すべて同一） | 号数（取得できた 6 通は 1〜5 と 7。第 6 号はアーカイブに欠落） |
| 定例解説（VYSE52） | 電文ごとに変わる（発表日時） | 空 |

臨時解説は `EventID` だけでは号を区別できない。閉じるボタンは電文 id（`EventID` と `Serial` から
組み立てる）で判定するため、`Serial` を落とすと第 1 号を閉じただけで以降の号すべてが出なくなる。

### WebSocket 接続（`src/services/dmdata.ts`）

- 自動再接続（指数バックオフ、`RECONNECT_BASE_MS=3000`、`RECONNECT_MAX_MS=30000`）
- `type: 'ping'` を受けたら `pong` を返す
- `stopped` / `authError` 以外は close 時に自動再接続
- 認証失敗（401/403）時は `authError` で停止。キーに使えない文字が入っている場合も同じ扱いで停止する（§2 認証）
- ping ウォッチドッグ: 最終受信から `PING_WATCHDOG_MS=90000` 経過で自発 close → 再接続（半開通信対策）
- 非回復系 close code: 保守的に `1008`（Policy Violation）のみ `authError` 相当に停止。`4xxx` は DMDATA v2 の公式仕様の裏取りが取れておらず、通常の再接続対象に含める（実運用ログで意味が判明したら個別に列挙する）
- `reconnectAttempt` のリセットは `start` 受信後 `STABLE_CONNECTION_MS=15000` 継続で行う（フラッピングでバックオフが効かなくなるのを防ぐため）

### REST 履歴取得（`fetchDmdataEarthquakes` 等）

起動時に過去 24 時間の主要電文を取得してカードに反映する。ページング（`nextToken`）に対応。

### 震源カタログ（`fetchDmdataGdEarthquakes`）

地震活動ヒートマップのデータ源。`GET /v2/gd/earthquake`（`gd.earthquake` スコープが必要）から
直近 30 日分の震源を取得する。標準版の `fetchJmaQuakeHistory`（P2PQuake）に相当するが、
**震度が観測されなかった地震も含む震源カタログ**である点が異なる。新しい順に返るため、
期間外に達した時点でページングを打ち切る。スコープが契約に含まれない場合は 403 で例外になり、
ヒートマップは非表示のままになる（画面上のエラー表示は無い）。コンソールには認証エラーとして
`console.error` が 1 行、続けて取得失敗として `console.warn` が 1 行出る。

キーに使えない文字が入っている場合は取得を試みず、`console.warn` を 1 行残す。この経路は画面に
エラーを出さないため、記録を落とすと「ヒートマップだけ出ない」理由に辿り着けなくなる。

**取得できないときも、キャッシュがあれば表示を保つ**（止まるのは新規取得だけ。鮮度は見ない）。
403 と文字種違反のどちらも同じ扱いで、上記の「非表示のまま」になるのはキャッシュが無いときだけ。
キーの入力中は一時的に文字種違反を通るため、ここで捨てると直している最中に表示が消える。

**座標の粒度**: このカタログが返す緯度経度は **0.1 度（約 11km）刻み**。これは気象庁の震源決定が
その程度しか当たらないという意味ではなく、**公表時の丸め**である。実際、顕著な地震の震源要素更新
（VXSE61）の電文には度単位の座標に加えて**度分単位（0.1 分 ≈ 185m 刻み）の座標**も入っている
（実電文で確認: `+40.2+142.4-40000/` と `+4012.4+14222.0-41000/` が併記される）。一方、通常の
震源・震度情報（VXSE53）は 0.1 度の座標のみを持つ。

ヒートマップがこの精密な値を使えない理由は 2 つ。VXSE61 は顕著な地震にしか発表されないことと、
震源カタログ API が 0.1 度の値しか返さないこと（1 ヶ月分を電文から個別に集めるのはリクエスト数が
現実的でない）。したがって**カタログから得られる粒度は 0.1 度が上限**で、地図側もそれに合わせて
ぼかす（[map-rendering-spec.md](map-rendering-spec.md) §14）。これより細かく描くと格子状の点描になり、
配信された座標より細かい位置が分かっているように見えてしまう。

粒度は**両バリアント共通**（どちらも気象庁の発表値が出所）。2026-08-18 の実データで、DMDSS 版
（震源カタログ）は 696 点中 695 点・ユニークな座標 139 個、標準版（P2PQuake）は 697 点すべて・
ユニークな座標 138 個が 0.1 度グリッド上だった。

**欠測項目の扱い**: このカタログには**震源が決まっていない地震**が混ざる（震度速報だけが発表され、
震源・震度情報がまだ出ていない段階のもの）。該当項目は `hypocenter` も `originTime` も持たず、
`eventId`・`arrivalTime`・`maxInt` だけを返す。地図に置く座標も時刻も無いため、該当する項目を
1 件ずつ個別に除いて取得を続ける。座標の値だけが読めない項目も同じく除く（API 仕様変更への防御。
実データでは未観測）。捨てた件数は理由の内訳付きで警告ログに 1 行出す（標準版の `warnField` /
`warnMissing` と同じ「既定の扱いに落とすことは許すが黙っては通さない」方針）。

ただし**捨てた項目があるのに 1 件も残らなかった場合は例外**にする。空の結果を正常とみなすと、
呼び出し側がそれをキャッシュして、直前まで表示していたヒートマップを消したまま TTL の間
そのままにしてしまうため。期間内に地震が本当に無くて 0 件だった場合とは区別する（捨てた項目が
0 件なら例外にしない）。判定を「全滅」に限っているのは、大地震の直後は震源未確定の項目が
一時的に増えるからで、割合で切ると最も見たいときにヒートマップが消えることになる。

### 試験報（VXSE42）

設定タブの「試験報を受信（検証用）」を有効にすると、毎正時に配信される配信テスト電文も受信できる。
実地震を待たずにリアルタイム受信経路を検証できる（受信した試験 EEW は通常の発報と同様に表示される）。

## 3. P2PQuake API v2（標準版）

### エンドポイント

| 用途 | エンドポイント |
|---|---|
| リアルタイム受信 | `wss://api.p2pquake.net/v2/ws` |

### convertEvent の検証と日本語化

`src/services/p2pquake.ts` の `convertEvent` が、受信した生 JSON を検証しながら内部型へ組み立てる。
**内部型に宣言されたフィールドだけを明示的に詰め直す**ため、API 固有のフィールド
（`comments` / `earthquake.foreignTsunami` / `hypocenter.reduceName` / `timestamp` 等）は落ちる。
生データは電文ログ（`TelegramLogEntry.rawBody`）に残るので調査には困らない。

英語の enum で来るフィールドは日本語化する:

- `issue.type`: `ScalePrompt` → `震度速報` 等
- `issue.correct`: `None` → `なし`、`Unknown` → `訂正`、`ScaleOnly` → `震度のみ訂正`、`DestinationOnly` → `震源を訂正`、`ScaleAndDestination` → `震度・震源を訂正`（`Correction` というキーは存在しない）
- `earthquake.domesticTsunami`: `None` → `なし`、`Watch` → `注意報`、`Warning` → `警報等` 等（`DOMESTIC_TSUNAMI_MAP` が扱う値ドメインは `None` / `Unknown` / `Checking` / `SeaFloor`（`海面変動の可能性`） / `NonEffective`（`若干の海面変動`） / `Watch`（`注意報`） / `Warning`（`警報等`） / `MajorWarning`（`警報等`） の 8 種。津波電文 code=552 側の等級（`areas[].grade`）はこのマップを通さず別扱い）

いずれのマップも、未知の値は既定値に格下げしたうえで警告を残す（`issue.type` → `その他`、
`issue.correct` → `なし`、`domesticTsunami` → `不明`）。

**不正値の扱い**: 基本はフィールド単位で既定値・センチネルに落として通し、電文ごと捨てるのは
同一性が壊れる場合だけに限る。

| 対象 | 挙動 |
|---|---|
| `code` が 551/552/556 以外・ペイロードが非オブジェクト | 電文を破棄（設計どおりの読み飛ばし） |
| `id` の欠落、`time` / `earthquake.time`（551）の欠落 | 電文を破棄。イベントの同一性キー・キューの並び順キーになるため |
| `points[]` / `areas[]` の壊れた要素 | その要素だけ落とし、電文は残す |
| 震度が階級外の値 | `-1`（不明）へ格下げ |
| 座標・深さ・規模が数値でない | P2PQuake が「不明」に使うセンチネル（座標 `-200` / 深さ `-1` / 規模 `-1`）へ。座標と深さは DMDATA 経路とも同じ値だが、規模だけは異なる（DMDATA 経路は `NaN`）。いずれも `hasMagnitude()` が「不明」として弾く |
| 津波の `areas[].grade` が未知 | `Unknown` へ格下げ |

**震度値の正規化**: API 仕様の値域は内部型 `IntensityScale` より広いため、以下を寄せる。
いずれも API 上は正規値なので警告は出さない。

| API の値 | 意味 | 内部での扱い |
|---|---|---|
| `46` | 震度 5 弱以上と推定されるが震度情報を入手していない | `45`（5 弱） |
| `0` | 震度 0 | `-1`（不明）。EEW のレベル判定はどちらでも結果が変わらない |
| `99` | 〜程度以上 | 同じ地域の `scaleFrom`（＋「以上」フラグ。DMDATA の `to: "over"` と同義 → §8） |

`46` と `0` の読み替えは震度を持つ全フィールド（`points[].scale` / `earthquake.maxScale` /
`areas[].scaleFrom` / `areas[].scaleTo`）に共通で適用する。仕様上 `46` は `points[].scale` に、
`0` は EEW の `scaleFrom` / `scaleTo` にしか現れないが、どのフィールドに来ても同じ意味に読める値なので
区別していない。`99` は `areas[].scaleTo` 専用（`scaleFrom` とセットで初めて意味を成すため）。

`scaleTo = 99` をそのまま通すと階級外の値になり、`eewMaxScale()` の実行時ガードがその地域を
丸ごと無視する。最も強い「震度 7 程度以上」が特別警報に上がらなくなるため、下限の `scaleFrom` を
上限として採用する。失われる「以上」は `scaleToOrAbove` フラグで持ち越す（→ §8）。

**severity の付与**: code=556（EEW）は P2PQuake API v2 のペイロードに severity フィールドを持たないが、
JMA 仕様上ここで配信される 556 は全て警報級であるため `convertEvent` が `severity: 'Warning'` を
明示付与する（付与しないと後段の `computeSingleEEWLevel` が予報扱いに落とし警報音・特別警報表示が
発火しない）。

**既知の情報粒度制約（QUAKE-6・TSU-5A）**: 実データ検証で確認済み。DMDSS の DMDATA と比較して以下が API 仕様
上の制約として存在する（詳細は [`quake-spec.md`](quake-spec.md) §4・[`tsunami-spec.md`](tsunami-spec.md) §3）:
- **地震情報**: `DetailScale`（観測点のみ）と `ScalePrompt`（区域のみ）が別電文で送られる。1 電文に
  両方を含めないため、標準版では県内の区域粒度内訳（一次細分区域ごとの震度差）を出せない
- **津波情報**: `validDateTime` フィールドが**そもそも存在しない**。標準版では
  `useEarthquakes` の TSU-1 経路（validDateTime による自動失効予約）が発火せず、
  解除電文 (`cancelled=true`) が届くまで表示され続ける。異例の障害で解除電文が届かない場合の
  フェイルセーフとして、`useEarthquakes` は 24h タイマーで自動非表示にする（TSU-5A）

### WebSocket 再接続

- 成功時にカウンタリセット
- エラー・不正メッセージのログ出力なし（既知の課題）

## 4. Yahoo リアルタイム震度（両バリアント共通）

### エンドポイント

- 観測点リスト: `https://weather-kyoshin.west.edge.storage-yahoo.jp/SiteList/sitelist_<siteConfigId>.json`（**west 固定**・`src/services/kyoshin.ts:21-22` の `SITELIST_BASE`）
- リアルタイム震度: `https://weather-kyoshin.<region>.edge.storage-yahoo.jp/RealTimeData/yyyyMMdd/yyyyMMddHHmmss.json`
- リアルタイム震度の `<region>` は west / east（west を優先、失敗時 east にフォールバック。SiteList は west のみ）

### 認証

不要。

### データ

- **観測点リスト**: 約 1725 点の緯度経度＋観測点情報（年に数回更新される・`siteConfigId` で判別）
- **リアルタイム震度**: 1 秒毎の JSON。`realTimeData.intensity` 文字列（1 文字＝1 観測点、`charCodeAt(0)-100` が index 0〜20）
- **震源情報（hypoInfo）**: EEW 相当の情報（震源・M・calcintensity 等）を含む場合がある

`fetchRealtimeIntensity` は `res.ok` に加えて `realTimeData` の存在、`realTimeData.intensity` が
非空の文字列であることを検証する（フィールド欠落・型不一致・空文字は次エッジ／リトライへフォールバック）。
`calcintensityToScale` は「空文字・null/undefined」（震度未確定の想定内）以外の未知コードで `log.warn` を出す
（silent に severity=Forecast 格下げを防ぐ）。
`useKyoshinRealtime` の `applyFrame` は try/catch で例外を隔離し、ローカルバグと fetch 失敗を分けて扱う。

### 取得と再生の分離

1 時点ぶんの観測データ（1 秒ぶんの全観測点の震度＋データ時刻＋hypoInfo）を **フレーム** と呼ぶ。
フレームは「供給元 → 時刻順キュー → 画面反映」の 3 段で流れる。

| 段 | 実装 | 役割 |
|---|---|---|
| 供給元 | [`src/services/kyoshinSource.ts`](../../src/services/kyoshinSource.ts)・[`src/services/kyoshinLocalArchiveSource.ts`](../../src/services/kyoshinLocalArchiveSource.ts) | どこからデータを持ってくるか。Yahoo のライブ／過去リプレイ／ローカル限定アーカイブ（後述）の 3 実装。リトライ・スケジューリングと、クロック同期の起動／停止（ライブ限定）もここ |
| キュー | [`src/utils/kyoshinFrameQueue.ts`](../../src/utils/kyoshinFrameQueue.ts) | フレームをデータ時刻順に並べ、アプリ時計が追いついた時点で放出する |
| 反映 | [`src/hooks/useKyoshinRealtime.ts`](../../src/hooks/useKyoshinRealtime.ts) | 放出されたフレームを画面の状態へ入れる。観測点リストの追随取得と hypoInfo 差分もここ |

分離の目的は取得ペースと表示ペースを切り離すこと。Yahoo は 1 秒 1 リクエストなので両者が一致するが、
「フレーム列が一度にまとまって手に入る」供給元は、まとめて投入して時刻に沿って流す必要がある。
`KyoshinSource` を実装すれば下流は変更なしで載る。この形で実装済みなのが
[`kyoshinLocalArchiveSource.ts`](../../src/services/kyoshinLocalArchiveSource.ts)（NIED K-NET/KiK-net
実波形由来のローカル限定アーカイブ。再配布禁止のためアプリには同梱せず、実行者本人が
`scripts/capture-kyoshin-waveform.ts` で生成する、または設定タブでNIEDのZIPを直接インポート
した場合のみ再生できる。後者はIndexedDB（[`kyoshinImportDb.ts`](../../src/utils/kyoshinImportDb.ts)）
を先にチェックし、無ければ前者の静的ファイルへフォールバックする。詳細は
[`settings-pwa-spec.md`](settings-pwa-spec.md) §6「NIED K-NET/KiK-netの実波形由来のデータ
（ローカル限定・リアルタイム震度）」）。

放出は**到来した最新 1 件のみ**を採り、間は捨てて `log.warn` に残す（1Hz の観測フレームは最新の状態だけが
意味を持つため。到来分を全件処理する電文側のキューとは意味論が逆）。反映は**データ時刻の順に限る**
（`applyFrame` の単調性ガード）。供給元が時計の後退をまたぐと古いデータ時刻のフレームを積みうるため、
そのまま入れると表示が巻き戻り、検知エンジンにも後退したデータ時刻が渡る。順序の判定に使うのは
取得を要求した時刻であり、表示に使う `dataTime` 文字列とは独立（応答のパースに依存させないため）。

`siteConfigId` 切替時（年数回）: `fetchSiteList` は Promise キャッシュを持つが、失敗した Promise は
キャッシュから削除して再試行可能にする。`useKyoshinRealtime` は `currentSitesKeyRef` の更新を
取得成功後に行い、失敗時は ref を据え置いて次のフレームで再試行させる（失敗は `log.warn` で通知。
毎フレーム再試行するため、記録は観測点集合ごとに一度に絞る）。
`sites`／`indices` の状態にはそれぞれの `siteConfigId` を紐付けて公開し、`useKyoshinDetectorV2` は
`sitesSiteConfigId !== indicesSiteConfigId` のフレームを step() 呼び出しからスキップする（切替直後の
「新 indices・旧 sites」で `frame.sites[i]` アクセスが `TypeError` になる恒久停止と、点数が偶然一致
した年切替で座標と震度が位置ベースで誤ペアリングされる検知エンジン内部の不整合を防ぐ）。
検知エンジン外の下流経路（地図描画・RealtimeTab・派生ビュー `deriveKyoshinView` ／
`filterSubThresholdIndices`）も同じ `sites[i]`／`indices[i]` の位置対応で消費するため、`src/App.tsx` で
`sitesSiteConfigId === indicesSiteConfigId` の条件を満たさない期間は空配列にゲートして通す。
sitelist の非同期取得が完了した次フレームで元の実データに戻る（非表示時間はネットワーク往復 1 回分）。
step 内例外も try/catch でログ出力の上、次フレームへ復帰する。**同じ `siteConfigId` なのに件数が食い違う
フレームも step() へ通さない**（上流データの異常。検知が丸ごと止まるため、間引いた上で記録に残す）。

このゲートが守るのは `sites` と `indices` の対応まで。**検知エンジンの結果を位置で使う値には別の確認が要る**
——`filterSubThresholdIndices` が使う慢性ノイズ床は effect 経由で 1 レンダー遅れて届くため、ゲートを通過した
直後は「新しい観測点 × 古い床」が並びうる。床がどの観測点配列に対して計算されたかを参照で照合してから使う
（詳細は [kyoshin-detection-spec.md](kyoshin-detection-spec.md) の「震度0ドット表示フィルタ」）。**検知結果を
位置で消費する経路を新しく足すときは、同じ照合が要らないかを確かめること。**

**残る既知の課題**（発生頻度・切替頻度から今回のスコープ外）:
- 並行 `fetchSiteList` 呼び出しの順序保証がない（1 回目の応答が 2 回目より遅れると `sites`／`sitesSiteConfigId`
  を古い内容へ巻き戻す可能性）
- sitelist 取得失敗時のリトライに上限・バックオフがない（Yahoo 側で `siteConfigId` の URL が恒久的に
  無効になった場合、毎フレーム無制限に再試行する）。恒久的に失敗しても「更新停止」の表示は出ない
  （震度と時刻は更新され続けるため、エラー無しのまま観測点が地図に出ない状態になりうる）

### index → 震度の変換

`indexToValue(index) = -3.0 + index * 0.5`（0.5 刻み量子化、index 6 = 震度 0 = value 0.0）。
`index = -1` は欠測センチネル（公式 CSS が裏付け）。

**欠測は 1〜2 秒で復帰する瞬断が多く、強く揺れている観測点でも起きる。** 表示側は欠測を描かないため、
そのままでは強い揺れのバッジが 1 秒だけ消える。このため**表示に使うインデックスだけ**、欠測点を直前値で
短時間保持する（保持の範囲・時間・見せ方は
[`kyoshin-detection-spec.md`](kyoshin-detection-spec.md) §8。検知エンジンには生値を渡す）。

### クロック同期（`startClockSync`）

アプリ時計（`serverNow()`）をサーバー時刻へ較正する。起動と停止はライブの供給元の開始・終了に紐づく
（リプレイ中は起動しない。アーカイブの時刻とサーバーの現在時刻は無関係なため）。30 秒ごとに 1 周期。

1 周期の流れ:

1. **主経路**: 外部の時刻サービスから時刻を取り、`feedServerSample` へ渡す（1 リクエスト。往復時間の実測は §9）
2. **フォールバック**: 主経路が**失敗したときだけ**、Yahoo の 403→200 境界から較正する
3. どちらも失敗し続けて 5 分を超えたら記録に残す

**順序が逆だと意味が変わる。** Yahoo を先に走らせて両方を `feedServerSample` へ供給すると、精度の
良い側にもう一方のバイアスが EMA 経由で割り込み、どちらか単独より悪くなる。加えて Yahoo 方式は
1 周期あたり十数リクエスト（うち数件は意図的な 403）を要するため、主経路が使える環境ではそれを避ける。

なお**この排他は周期単位**で、時間をまたぐ混在は防いでいない。主経路が間欠的に失敗する環境では、
フォールバックが挿さった周期のバイアスが EMA に混ざり、収束する数分の間だけ残る（自己修正するため
恒久的な誤りにはならない）。

#### 主経路: 外部の時刻サービス（`akamaiClock.ts`）

- 取得先は `https://time.akamai.com/?iso&ms`。応答は ISO8601 の平文 1 行。**このクエリは dash.js
  （DASH Industry Forum の標準プレイヤー）の既定の時刻同期先**であり、Akamai がブラウザからの
  クロック同期用途で供給していることを承知して運用している
  （[dash.js のクロック同期ドキュメント](https://dashif.org/dash.js/pages/usage/clock-sync.html)・2026-08-20 確認）
- **返る時刻は応答生成時点のもの。往復の中点ではなく応答到着時点を基準に**現在時刻へ換算する。
  中点を使うと -RTT/2 の系統誤差がそのまま乗る
- **`?ms` が効かないと応答が秒単位に丸まり、精度だけが静かに劣化する**（エラーにはならない）。
  URL がこのクエリを保っていることをテストで固定するだけでなく、**応答が小数秒とタイムゾーンの
  両方を持つことを実行時にも検査する**（欠けていれば棄却して記録に残す）。タイムゾーンを見るのは、
  オフセットが無い日時を `Date.parse` がローカル時刻として解釈し、数時間ずれた値が妥当範囲内として
  通ってしまうため
- このエンドポイントには送信値を返すエコーが無く、古い応答を掴んでも気づけない。代わりに
  **単調時計で見て前回サンプルより戻っていないこと**を検査する（中間装置のキャッシュ対策）
- 失敗したときだけ警告を出し、**棄却理由を併記する**（`network` なら回線の問題、`parse-invalid`
  などならサービス側の形式変更）。理由を落とすと、較正が止まった原因を切り分ける手段が残らない
- **取得が重なったら後から来た方を見送る**（`skipped`）。逆行検出の基準をモジュール単位で持つため、
  同時に走ると応答の到着順が入れ替わって正当な応答を誤棄却しうる。**見送りは失敗ではないので
  フォールバックへ落ちない**（落とすと、重なっただけで Yahoo の未登録秒を撃つことになる）

> **NICT（情報通信研究機構）の日本標準時は使わない。** HTTP/HTTPS による時刻配信が 2022-03-31 に
> 公式終了しているため（経緯と根拠は §11 の 2026-08-20）。

#### フォールバック: Yahoo の 403→200 境界（`syncClockOnce`）

Yahoo は未登録秒には 403 を返す（登録遅延約 1.5 秒）。この 403 → 200 遷移を捉えて時刻を較正する。
**主経路が失敗した周期でのみ走る。**

- guessSec の前後 `[-4, +2]` の探索窓で 200 になる境界を検出。連続失敗のたびに窓を指数的に
  広げる（上限 ±60 秒）ため、壁時計が数秒ずれていても追いつける
- 検出した境界を `feedServerSample` に渡して EMA 較正（`clock.ts`）
- `isRegistered` は `200` → `true`（登録済み）、`403/404` → `false`（未登録）、
  `5xx`/`429`/その他 → `null`（判定不能）の三値を返し、`null` のサンプルは較正基準に採用しない
  （CDN の一時的な障害を「未登録→登録」遷移と誤認して `feedServerSample` を汚染し、時計が
  じわじわ狂うのを防ぐ）
- フロンティアが見つかっても打ち切り時間内に flip を観測できないことがある（開始時点で既に登録済み・
  判定の取得に失敗）。以前はこの経路が無音で、較正が止まっていても古い K が残り続けて気づけなかった
  ため、5 分間隔で警告を出す。**間引きは理由ごとに独立して行う**（1 つにまとめると、最初に鳴った
  理由が残りを 5 分間隠して真の原因を取り違える）

**この経路の既知の限界**: 落ち着き先がセッションごとに数百 ms ずれる。`REG_DELAY_MS` は登録遅延の
実測 p50 で、実際の遅延は CDN の応答によって変わるため。定数の調整では消せない（実測は §11 の
2026-08-20）。**主経路をこちらから移した理由がこれ。**

#### 較正が止まったことの検知

較正済みの基準値（§5 の `K`）は最後に成功したサンプルを保持し続けるため、両経路が失敗し続けても
`serverNow()` は古い値を返し、未較正警告（`clock.ts`・一度も較正できていないときだけ出る）も鳴らない。
**一度でも成功していると、止まったことに気づけない。** 最後の較正から 5 分（周期 10 回分）を超えたら
警告を出す。

### EEW 補完（`hypoInfoItemToEEW`）

Yahoo の `hypoInfo.items` を EEW 型に変換して P2PQuake と統合する。**この経路は標準版のみ**
（DMDSS 版は DMDATA の EEW 電文を主系とし、Yahoo 由来の EEW は使わない。詳細は
[`eew-spec.md`](eew-spec.md) §3）。
`condition` に相当するフィールドが無いため常に `'以上'` を返す（single-point PLUM 検知の判別不能・
既知の限界。**PLUM 法** の詳細は [`eew-spec.md`](eew-spec.md) §5 参照）。severity は震度からの
ヒューリスティック推定（`scaleNum >= 45 ? 'Warning' : 'Forecast'`）。

## 5. クロック同期（`src/utils/clock.ts`）

**壁時計は絶対値として信用しない**。以下の時刻は `serverNow()` で取得する:

- EEW P/S 波円計算
- EEW 自動解除タイミング
- 津波 `validDateTime` の期限判定
- Yahoo 取得ラグ計算
- 実地震テストシナリオの時刻シフト

### 実装

- `serverNow(): number` — サーバー基準の epoch ms を返す
- 内部で `K = trueServerEpoch - performance.now()` を保持
- Yahoo クロック較正から `feedServerSample(trueServerEpoch)` で K を EMA 更新（α = 0.2）
- 未較正時（K = null）は `Date.now()` にフォールバック
- 診断用に現在のオフセット（`getServerClockOffsetMs`）と最終較正からの経過時間
  （`getServerClockSampleAgeMs`）を公開する。K は最後に成功したサンプルを保持し続けるため、
  値だけでは「新しい較正」と「止まった古い較正」を区別できない

### 既知の課題

- `feedServerSample` に外れ値検知なし（初回サンプルは無条件採用）
- EMA（α = 0.2）の収束に数分かかる。加えて Yahoo 較正側の落ち着き先がセッションごとに
  数百 ms ずれる（上記「フォールバック: Yahoo の 403→200 境界」）。**主経路が一貫して使える環境では
  影響しない。** ただし主経路が間欠的に失敗する環境では、フォールバックが挿さった周期のバイアスが
  EMA に混ざり、収束する数分の間だけ残る（排他は周期単位のため、時間をまたぐ混在は防いでいない）

## 6. 生成データ（`public/data/`）

事前生成された座標・境界データ。地図は常時表示されるため、地図が使うものは表示モード（地震／津波／
リアルタイム震度）に関わらず地図の初回表示時にまとめて要求する。読み上げ辞書とテストシナリオ一覧は
アプリ起動時、シナリオ本体は再生時に取得する。いずれも一度取得したらキャッシュする。

| ファイル | 生成スクリプト | 用途 |
|---|---|---|
| `station-coords.json` | `scripts/build-station-coords.mjs` | 震度観測点の座標＋所属区域 |
| `tsunami-zones.json` | `scripts/build-tsunami-zones.mjs` | 津波予報区の海岸線 |
| `tsunami-obs-coords.json` | 手動整備 | 津波観測点座標 |
| `prefectures.json` | `scripts/build-prefectures.mjs` | 都道府県境界 |
| `subregions.json` | `scripts/build-subregions.mjs` | 一次細分区域境界（**一次細分区域** の定義は [`quake-spec.md`](quake-spec.md) §1 参照） |
| `active-faults.json` | `scripts/build-active-faults.mjs` | 全国活断層線 |
| `plate-boundaries.json` | `scripts/build-plate-boundaries.mjs` | プレート境界線（全球・52 プレート） |
| `tts-phrase-break-dict.json` | 手動整備 | 読み上げ用の句区切り辞書 |
| `test-scenarios/index.json` | 手動 or `capture-test-scenario.ts` | 実地震テストシナリオ一覧（本体は .gitignore） |
| `hypocenter/*.json` | `scripts/build-hypocenter-catalog.ts` | 長期震源カタログ（統計解析用・→ 下記） |

**取得に失敗したとき**: そのデータを使う表示だけを諦めて動作を続ける（何が欠けるかは各仕様書を参照）。
失敗は `console` に残し、次に要求されたときに取得し直す（自動リトライは持たない）。

**失敗なのは通信だけではない。** 200 が返っても中身が空・想定外の形なら失敗として扱う（県境・
一次細分区域・観測点座標・津波予報区の 4 つ。`prefectures.ts` / `subregions.ts` / `stationCoords.ts` /
`tsunamiZones.ts`）。ビルドや配信が壊れて `{}` や `[]` が返ると、そのままでは「取得成功・0 件」として
通ってしまう。何が画面から消えるか・代替表示があるかはデータごとに異なる
（[`map-rendering-spec.md`](map-rendering-spec.md) §4・§5、[`quake-spec.md`](quake-spec.md) §7.2・§7.3、
[`tsunami-spec.md`](tsunami-spec.md) §7 を参照）。

**この検分は取得の中（`fetchJsonWithTimeout` の `validate`）で行っている。** 取得が終わってから
呼び出し側で確かめる形にすると、その時点で取得関数は成功として数え終わっており、下記の取得状況の
表示に計上されない——だから中で呼ぶ。新しいローダーを足すときも同じ場所へ渡すこと。

見る深さはデータごとに違う（観測点座標だけは `stations` と `areas` の有無まで確かめる）。共通するのは
**中身の妥当性までは検証しない**という点で、一部のキーだけが壊れている配信は素通りする。

**取得状況の表示**: 地図左上（更新時刻の下）に `MapDataStatus` を出す。取得が 3 秒以上続いたら
「データを取得中…」、失敗したまま取り直せていないデータがあれば
「データの一部を取得できませんでした（N 件）／再読み込みで取得し直します」を表示する。
失敗があるときは取得中より優先し、両方は出さない。正常時は何も出さない（通常は 1 秒ほどで
揃うため、その間の表示はちらつきにしかならない）。何が取れなかったかの詳細は `console` 側に
あり、画面には件数だけを出す。取り直しに成功すれば表示は消える。

対象は**地図の見た目に関わるデータだけ**。読み上げの句区切り辞書・実地震テストシナリオ・長期震源カタログは
地図に影響せず、それぞれ音声・設定タブ・統計表示の側に固有の表示があるため数えない
（`fetchJsonWithTimeout` の `trackStatus: false`）。**`trackStatus: false` を新しく足すときはこの列挙も直すこと。**

**タイムアウト**: 応答もエラーも返らない回線で待ち続けないよう、取得は 60 秒で打ち切って上記の
失敗として扱う（`src/utils/fetchJson.ts`）。これらは初回表示時にまとめて要求されるため、1 本ずつ
ではなく合計サイズ（gzip 後 約 1.7MB）を基準にした値で、低速回線での正常な取得を切らないことを
優先している。読み上げの句区切り辞書だけは読み上げ本体が取得を待つため、これより大幅に短い専用の値を使う
（[`audio-tts-spec.md`](audio-tts-spec.md) の「辞書（読み仮名の補正）」節）。

### 長期震源カタログ（`public/data/hypocenter/`）

**「震源カタログ」タブが点群として描く**（見せ方は [`map-rendering-spec.md`](map-rendering-spec.md)
§16「長期震源カタログの点群」）。あわせて統計解析の土台でもある。b 値（規模別の発生頻度の傾き）・
静穏化（地震活動が一時的に減ること）・余震域の
広がり・同じ地点の過去の地震・深さ方向の断面といった、**長い期間と多くの件数が要る**用途を
想定している（個々の項目は [`implementation-plan.md`](../implementation-plan.md) の
4・9・12・15・17・20 を参照）。気象庁の震源データを加工したもので、**1919 年から 2 日前まで・
M2.0 以上の約 102 万件**（31MB・年ごとに 108 ファイル）を収録する。

#### カタログは自分の限界を 2 つ持っている

**この 2 つを見ないと、データは静かに嘘をつく。** どちらも索引（`index.json`）が持つ。

**1. `coveredThroughMs` —— データの終端。** 気象庁の「震源リスト」は 2 日前までしか載らないため、
直近の数日は必ず欠ける。週次更新（後述）を回しても尾は最大 9 日残る。
**「まだ取っていない」と「地震が無かった」は、格子の濃淡では区別できない。** 終端より先は
「未取得」として描くこと。

**2. `completeness` —— 期間ごとの完全性。** 収録は M2.0 以上だが、**M2.0 の取りこぼしが無いのは
1997 年以降だけ。** 年間件数をマグニチュード別に実測すると、M5 以上は 1919 年から横ばいなのに
M2 以上は 46 倍に増えている —— **増えたのは地震ではなく観測網。**

| 期間 | M2+/年 | M3+/年 | M4+/年 | M5+/年 | 完全と言える下限 |
|---|---|---|---|---|---|
| 1919〜1950 | 505 | 482 | 322 | 111 | **M5.0** |
| 1951〜1960 | 326 | 323 | 239 | 96 | M5.0 |
| 1961〜1966 | 1,062 | 1,031 | 522 | 119 | **M4.5** |
| 1967〜1982 | 1,456 | 1,132 | 621 | 139 | M4.5 |
| 1983（例） | 4,823 | 3,061 | 1,014 | 204 | **M3.5** |
| 2010（例） | 23,224 | 6,305 | 1,441 | 187 | **M2.0** |

件数を数える機能（日別回数・b 値・静穏化）は `completeMinMagnitude(index, 描く期間の最も古い年)`
で閾値を上げること。同じ濃淡で 1919 年から描くと「昔は地震が少なかった」という嘘になる。
使わなくてよいのは**その期間の完全性下限より上の M だけを扱う**場合（M5 以上を並べるだけ等）。

**これは「時代」の話で、「場所」の話ではない。** 同じ 1997 年以降でも、観測点が密な陸域は M1 まで
拾えるのに対し、海域は M2 台でも取りこぼす。**地域別に件数を比べる機能（b 値マップ・静穏化）は、
`completeness` を満たしただけでは足りない** —— 観測網の密度分布が地震活動の分布として出てくる。
地域ごとの完全性下限をデータから推定するか、比較の対象を同じ観測条件の領域に限ること。

読む側が知っておく必要のある細かい約束（日ごとに数えるときの日付境界・最大震度のコード表と
その落とし穴）は、消費する側のコード `src/utils/hypocenterCatalog.ts` の型定義に併記してある。

#### 取得元が 2 つある

| 期間 | 取得元 | 年ファイルの `quality` |
|---|---|---|
| 1919〜2023 | [地震月報（カタログ編）震源データ](https://www.data.jma.go.jp/eqev/data/bulletin/hypo.html)（ZIP） | `final`（確定値） |
| 2024〜2 日前 | [震源リスト](https://www.data.jma.go.jp/eqev/data/daily_map/)（日別 HTML） | `preliminary`（速報値） |

確定値は精査を経てから収録されるため構造的に遅れる。生成は**年 ZIP を先に試し、404 なら日別へ
落ちる** —— 気象庁が 2024 年の確定値を公開した週に、回すだけで自動的に入れ替わる。切り替えを
手で管理する箇所は作っていない。404 以外の失敗（一時障害・ZIP 破損）では落とさず、生成を
失敗させる（確定値が公開済みの年を速報値へ格下げしないため）。

ZIP の配布単位は年ごとではない。1919〜1982 年は 4 つのまとめファイル（1919-1950 / 1951-1960 /
1961-1966 / 1967-1982）、1997 年だけ 10 月の処理方法改訂を境に 2 ファイルに割れている。

#### 直近 30 日のヒートマップとは母集団が違う

あちらは DMDATA / P2PQuake から取る「いま」のデータ（→ §2「震源カタログ」）。
**1 日あたりの件数が 10 倍以上違う**ため、繋いで日別回数や統計に使わない。

| | 長期カタログ | ヒートマップ |
|---|---|---|
| 期間 | 1919〜2 日前 | 直近 30 日 |
| 母集団 | M2.0 以上の全地震（**近年は 1 日あたり約 88 件**。2009〜2023 年の平均） | 震度を観測した地震のみ（**1 日あたり 6〜7 件**） |
| 更新 | 週 1 回（後述） | 6 時間ごと（ライブ受信も反映） |
| 座標の精度 | 0.01 分（約 18m）—— 気象庁が決めた値そのまま | **0.1 度（約 11km）** —— API・電文がこの刻みで返す（→ §2） |

#### 週次更新

[`update-hypocenter-catalog.yml`](../../.github/workflows/update-hypocenter-catalog.yml) が毎週
`--from 2024` を回し、差分をコミットして main へ push する。

- **main へ直接 push する。** 「main を書き換えるのはリリース手続きの中だけ」という原則
  （CLAUDE.md「リリース」節）の唯一の例外。その原則はバージョン番号の競合とマージ順の混乱を
  防ぐためのもので、**データのみ・版上げなし・マージなし**のこのコミットはどちらの危険も持たない
- 日別ページはワークフローのキャッシュに残す。**無いと毎回 966 日ぶん（約 70MB）を取り直す**
- テストを通してから push する。生成が異常を検知すれば exit 1 で止まり、壊れたデータは本番へ出ない
- **格納単位を変えたときは全年を作り直すこと。** 週次更新は 2024 年以降しか生成しないため、
  作り直さなかった年が古い単位のまま残る。索引を組み直すときに検知し、その年を索引から除いて
  exit 1 にする（ワークフローは後続の commit / push へ進まない）
- 頻度を上げても意味が無い。気象庁側が 2 日前までなので、日 1 回にしても尾は 2 日のまま縮まらない

#### 年別に分かれている

1 ファイルにまとめると 31MB になるため年ごとに分けてある。用途に応じて必要な年だけ読める
（時計盤なら 1 年、b 値なら 10 年）。**月別には分けない** —— 週次更新で書き換わるのは当年
ファイルだけで、内容は末尾への追記なので git の差分圧縮がよく効く（788KB の年ファイルを
52 回更新して `.git` の増分は 438KB）。

**索引は出力ディレクトリの実態から作る。** 今回生成した年だけで書くと、範囲を絞って 1 年を
作り直した瞬間に**他の年が索引から消える**（ファイルは残るのに読めなくなる）。索引に無いが
ファイルが在る年はファイルから拾うので、壊れた索引からも回復できる。M の下限を変えて
一部だけ作り直そうとしたときは警告を出す（索引が持つ下限と中身がずれるため）。

年ファイルは**列で持つ**（`{"t":[...],"lat":[...],...}`）。1 件 1 オブジェクトに展開すると
100 万件でメモリを大きく食うため、ローダ（`src/utils/hypocenterCatalog.ts`）は TypedArray へ
移してから返す。値は整数へ直して格納し、**単位は年ファイル自身が持つ**（索引にも同じ値が
あるが、読んだファイル側を信じる方が桁がずれない）。時刻の起点（`startMs`）も年ファイルが
持つ——読む側に日本時間の知識を要求しないため。

##### 格納単位は元データの刻みに合わせる

| 列 | 元データの最も細かい刻み | 格納単位 | ファイルが持つ項目 |
|---|---|---|---|
| 時刻 | 0.01 秒 | 1/100 秒 | `timeScale` |
| 緯度経度 | 0.01 分 | 1/6000 度 ＝ 0.01 分 | `coordScale` |
| 深さ | 0.01km | 0.01km | `depthScale` |
| M | 0.1 | 0.1 | `magScale` |

**小数部の桁数は取得元と年代で変わる。** 確定値は年代によって秒・緯度経度の分・深さの桁数が
異なり（**年の途中で変わることもある**ので、年の範囲では区切れない）、日別ページ由来の年は
深さが整数 km になる。単位は**最も細かい箇所**に合わせる —— 粗い箇所の値も同じ格子に乗るので、
どの年も丸めずに格納できる。

**選ぶ基準は「元データの値を復元できること」。** 「震源の決定精度より細かいから十分」では
決めない —— 緯度経度の刻み 0.01 分は 1/6000 度なので、10 進で切った単位（1/10000 度など）とは
噛み合わない。1/6000 度の値が 1/10000 度の格子に乗るのは 3 の倍数のときだけで、**3 件に 2 件は
丸め誤差が乗る**（データによらず決まる比率。実測でも 66〜67%）。深さと秒も同じで、0.1km・1 秒で
格納すると細かい箇所が持っている桁が失われる（深さは小数第 2 位、秒は小数第 1 位から）。

**噛み合っていなくても生成は成功する。** 格納は `Math.round(値 × 単位)` なので、例外も NaN も
出さずに丸めた値が書かれ、「読めない行」としても現れない。そのため生成のたびに
`scripts/hypocenterScale.ts` の検査（`countUnrepresentable`）で全レコードを突き合わせ、
**単位で表せない値が 1 件でもあれば exit 1 で止める**。上流が刻みを細かくしたときに気づける
唯一の経路がここ。単位の定義もこのモジュールが単一情報源。

**単位の混在を検知するのは生成側だけ。** 読み取り側は年ファイル自身が持つ単位をそのまま信じて
読むので、**年ごとに単位が違っても何も言わずに読める**（単位が欠けている・正の整数でない場合
だけ失敗する）。作り直し忘れた年を捕まえられるのは、生成が索引を組み直すとき
（`findScaleMismatch`）に限られる。

最大震度は**疎な 2 列**（`intIdx` / `intCode`）で持つ。有感は M2.0 以上の 11.9% しかないため（確定値の 1919〜2023 年で。速報値の年を含めた全期間では 10.9%）、
全件ぶんの列にすると 9 割が無駄になる。速報値の年（日別経路）は震度欄が無いので空。

#### 読み取りで踏んだ罠

パーサが 2 つある。**読み方が正反対なので取り違えると静かに壊れる。**

| | 年 ZIP（`scripts/hypocenterRecord.ts`） | 日別 HTML（`scripts/hypocenterDailyRecord.ts`） |
|---|---|---|
| 文字コード | latin1（震央地名が Shift-JIS で入りうる） | UTF-8 |
| 切り方 | **バイト**位置の固定幅 | **正規表現** |

**年 ZIP 側**

- **実ファイルは改行区切り。** [仕様書](https://www.data.jma.go.jp/eqev/data/bulletin/data/format/hypfmt_j.html)は
  「96 バイト固定長」と書いているが、96 バイトずつ切ると 1 バイトずつずれていく
- **数値欄の小数部の桁数が年代で変わる。** 桁が 1 つ少ない年は緯度分を `474 `（= 47.4 分）と
  書く。空白を無視して `474 / 100` と読むと 4.74 分になり、**緯度が 78km ずれる**。秒・経度分・
  深さも同じ規則。**桁数は年の範囲で区切れない** —— 1 桁の年もあれば 2 桁の年もあり
  （1983・1990・1993 年は全件が 1 桁）、年の途中で切り替わる年もある。**範囲で判定せず、
  末尾の空白の有無で読むこと**（`parseTrailingBlankDecimal`）
- **深さ欄に仕様外の形がある**（`   0 ` と `  0 4`）。**値を推測せず捨てる** —— 前者は
  0〜9 のすべてが現れるので「0km の別表記」ではなく桁の解釈が変わっており、0.7km と 7km の
  どちらなのかがデータからは決まらない。全期間で 90 件（年ごとの内訳は
  `hypocenterRecord.ts` の `parseTrailingBlankDecimal`）
- **最大震度の欄は震度の値と震度でない分類が混在する。** `1`〜`7`・`A`〜`D` が震度、`F`（有感地震）・
  `X`（付近有感）・`L`・`S`・`M`・`R`（最大有感距離による顕著度）は震度スケール上の値ではない。
  **数値へ写せるのは前者だけ**（コード表は `hypocenterRecord.ts`）
- 採るのは気象庁が決定した震源（レコード種別 `J`）だけ。海外の震源（`U`）は南緯・西経を
  `- 7` のように書くなど体裁も違うが、そもそも対象外になる
- M は暗黙の小数点（`45` = 4.5）。負の M は符号化されるが、M2.0 以上しか採らないので範囲外
- 1919〜1950 年に**秒欄が空白の記録が 18 件**ある。捨てずに採るが、その秒は 0 で埋めている
  （時刻は分までしか意味を持たない）

**日別 HTML 側**

- **空白区切りに見えて空白では割れない。** 分が 1 桁の座標は `137° 8.0'E` のように中に空白が
  入るため、`split(/\s+/)` すると列がずれて深さと M を取り違える
- 位置を決め打たず正規表現にしている。スクレイピングした表なので、**気象庁が列幅を変えたときに
  黙って誤読するより落ちてほしい**ため
- **1 日 0 件は障害として扱う。** 日本で 1 日の地震が 0 件になることは無い（966 日の実測で
  最小 391 件／平均 742 件）。`<pre>` はあるが中身が空という応答を恒久キャッシュすると、その日は二度と
  取り直されないまま「地震が無かった」ことになる
- M 欄の `-` は未決定（1 日あたり 5〜165 件）。位置と時刻は読めるので捨てない

#### 異常を検知する仕組み

**「捨てた」「読めなかった」を `console.log` で終わらせない。** 検知しても生成の成否に繋がらな
ければ、壊れたデータは黙って本番へ出る（週次更新の CI は終了コードしか見ていない）。次のいずれ
かで生成が失敗する。

- 既知の地震との照合が合わない（下記）
- 深さ欄が読めない行が 1 年で **3%** を超えた（実測の最大は 1967 年の 1.741%）
- **深さ以外の理由で読めない行が 1 件でもあった**（実測 0 件。出たら形式が変わったということ）
- **J レコードがあるのに 1 件も採れなかった** —— M 欄だけが壊れると震源 3 要素は読めるため、
  「読めない行」は増えず**件数 0 という形でしか現れない**
- 年欄が数字でない `J` レコードがあった（実測 0 件。どの年にも振り分けられず黙って消えるため）
- 年を 1 つでも取得できなかった
- 既にある年ファイルが読めなかった（ファイルは残るのに索引から消える経路）

> 深さ欄の閾値だけ「1 件でも失敗」にしていないのは、**理由が判っていて実測の幅も判っている**
> ため。理由を分けずに 1 つの比率で見ると、既知の変則を抑えようとして本物の信号まで黙らせる。

**照合は取得経路ごとに置く。** 経路によって文字コードも切り方も違うため、1 つでは他の経路の
壊れを捕まえられない。

| 取得元 | 照合する地震 |
|---|---|
| まとめ ZIP 1919-1950 | 1923 関東大震災（M7.9） |
| まとめ ZIP 1951-1960 | 1952 十勝沖地震（M8.2） |
| まとめ ZIP 1961-1966 | 1964 新潟地震（M7.5） |
| まとめ ZIP 1967-1982 | 1968 十勝沖地震（M7.9） |
| 年 ZIP（1997 の分割ファイル） | 1997 鹿児島県北西部地震（M6.6） |
| 年 ZIP | 2011 東北地方太平洋沖地震（M9.0） |
| 日別 震源リスト | 2024 能登半島地震（M7.6） |

照合のログには**実際に読んだ取得元**を出す（期待と食い違ったことに気づけるように）。
時刻の完全一致では引かない —— 速報値と確定値で発生時刻が 0.1 秒単位で動きうるため、
最も近いものを採る。範囲を絞って生成したときは、**照合していない経路を名指しで出す**
（「照合済み」と思い込まないため）。

## 7. リプレイ機能

### 「テスト時刻設定」

設定タブで日時を指定して過去を再生する機能。再生の仕組みは共通で、**当時の電文をどこから
取ってくるかがバリアントで変わる**。

バリアント別に何が再生されるか、取得の詳細（日付単位の取得・キャッシュ・取りこぼしの扱い）、
再生中にライブ接続を止める理由は [`settings-pwa-spec.md`](settings-pwa-spec.md) §6
「テスト時刻設定」に集約している。

本書が受け持つのはデータ源としての制約だけ。**standard 版のリプレイで EEW を取得できないのは、
P2PQuake に緊急地震速報（code 556）を過去日付で引く口が無いため**（`/jma` 配下に無く、
`/history` は日付指定できないうえ 1 週間以上前を辿れない）。強震モニタの震源情報から EEW を
検出する経路はリプレイ中も働くため、当時発表された EEW 自体は画面に出る。

`useTestScenarios.ts` が管理。両バリアント共通で動作する。詳細は

## 8. 震度スケール

| 値 | 震度 |
|---|---|
| 10 | 1 |
| 20 | 2 |
| 30 | 3 |
| 40 | 4 |
| 45 | 5弱 |
| 50 | 5強 |
| 55 | 6弱 |
| 60 | 6強 |
| 70 | 7 |

センチネル値:
- `-1` — 震度算出不能・不明
- `-200` — 位置不明（震度速報の震源座標フォールバック）

内部型 `IntensityScale` は上表と `-1` だけを取る。P2PQuake API はこれより広い値域（`0` / `46` / `99`）を
返すため、`convertEvent` が受け口で上表の値に寄せる。読み替えの一覧は §3「震度値の正規化」を参照。

### 上限を定めない予想震度（「〜以上」）

EEW の予想震度は範囲（下限・上限）で配信され、**上限が定まらないことがある**。どちらの経路でも
意味は同じで、内部では**下限側の階級**を採り、「以上」であることは別のフラグで持ち越す。

| 経路 | 電文上の表れ | 例 |
|---|---|---|
| DMDATA | `forecastMaxInt: { from, to }` の `to` が `"over"` | `{ from: "4", to: "over" }` = 震度4以上 |
| P2PQuake | `areas[].scaleTo` が `99` | `scaleFrom: 70` / `scaleTo: 99` = 震度7程度以上 |

- 内部型では `EEWRegion.scaleTo` に下限の値を入れ、`EEWRegion.scaleToOrAbove` を立てる
  （電文全体の値は `EEWAlert.forecastMaxScale` と `forecastMaxScaleOrAbove`）
- **上限を階級値に写さないこと。** `"over"` を震度7として読むと、下限しか決まっていない報が
  最大震度7として扱われる。単独観測点処理の初報がこの形を取るため実害があった
  （2024/1/1 16:18 の余震の初報が「石川県能登 震度4以上」→ 震度7として区域塗り・カード・
  ウィンドウタイトル・読み上げに出ていた）
- 下限が不明（`-1`）のときは「以上」を立てない（「不明以上」は意味を成さない）
- **受け取った値を EEW 側でどう使うか**（判定に混ぜない・語を出す箇所）は
  [`eew-spec.md`](eew-spec.md) §4「上限を定めない予想震度の扱い」を参照

  **なぜ移したか**: Yahoo 方式のばらつき（理由は §4「フォールバック」）を実測したところ、落ち着き先が
  セッションごとに **-10ms 台から -500ms 台まで**動いた（standard / DMDSS の両バリアントで同じ傾向）。
  効くのは主に予想円の半径計算（`serverNow() - originTime`）で、300ms のずれは S 波で 1km 強に相当する。

  **取得先の選定**: 当初は NICT（情報通信研究機構）の日本標準時 JSON で実装したが、**NICT の
  HTTP/HTTPS 時刻配信は 2022-03-31 に公式終了**しており NTP への移行が要請されていることが分かった
  （[NTP への一元化のお知らせ](https://jjy.nict.go.jp/httphttps-index.html)・2026-08-20 確認。
  アクセス増による負荷が終了理由の一つ）。旧エンドポイント `ntp-a1.nict.go.jp/cgi-bin/json` は実際に
  404 を返す。JST Clock の表示用ページが使う難読化ホストは今も応答するが、運営者が明示的に止めた
  経路を残存バックエンド経由で叩くことになるため取り下げた。

  **切り替え前に並走計測で確かめたこと**（アプリ時計へ供給せず差分だけ記録する段を挟んだ）:

  | 比較 | 結果 |
  |---|---|
  | 壁時計 − サーバー時刻（応答到着を基準に換算） | RTT と無相関（傾き 0.01 以下） |
  | 壁時計 − サーバー時刻（中点を基準に換算） | RTT に対する傾き -0.5。RTT に比例して誤差が増える |

  これで換算の基準（§4「主経路」）が決まった。NICT・Akamai どちらでも同じ傾きが出たため（NICT 側は
  差し替え前の実装での実測で、コードは残していない）、この種のエンドポイント全般に当てはまると
  考えられる。**最初の実装は中点を使っており、並走計測がこの誤りを露出させた。** そのまま供給して
  いれば、精度を上げるつもりで現行より悪いものを出していた。

  取得ターゲット秒の余裕は `FETCH_OFFSET_MS − (1000 + REG_DELAY_MS) − ずれ` で決まる（現状の定数では
  1800 − 1480 = 320ms が基準）。観測されたずれの範囲では常に正だったため `FETCH_OFFSET_MS` の調整は
  不要と判断し、切り替え後の実測でも取得は全件 200 を維持した。

  副作用として**意図的な 403 が出なくなった**（主経路が使える環境では 1 周期 1 リクエストで済む）。
  あわせて、これまで無音だった「flip を観測できず較正を見送った」経路に理由ごと独立した警告を追加し、
  較正の鮮度を返す `getServerClockSampleAgeMs` を `clock.ts` に足して、両経路が失敗し続けたときに
