# 地震情報仕様書

> 本書は**現在の実装が地震情報をどう処理するか**をまとめた仕様書。実コードと食い違う場合は実コードを正とする。
> 関連: [`data-sources-spec.md`](data-sources-spec.md) の電文受信、[`map-rendering-spec.md`](map-rendering-spec.md) の地図描画。

## 1. 概要

地震情報（震度速報・震源情報・各地の震度）を受信・表示するモジュール群。以下を扱う:

- 電文パース（DMDATA JSON / XML、P2PQuake JSON）
- 同一 eventId の続報統合（速報 → 詳細報の順で情報を上書き）
- 地図の表示: 観測点別震度ドット・区域別震度塗り・観測点から補間した震度の面・震源マーカー
- ズームレベルによる集約表示切替（詳細 ↔ 区域）
- 訂正・取消の表示

### 用語: 「一次細分区域」

気象庁が定める地震情報用の地域区分単位。都道府県より細かく、市区町村より粗い（1 都道府県あたり数個〜十数個。全国で約 380 区域）。震度速報・各地の震度で「宮城県南部」「岩手県沿岸北部」のように区域名で震度が発表される。境界データは `public/data/subregions.json`、区域名↔観測点の紐付けは `public/data/station-coords.json` の `areas` で管理する。本仕様書と関連仕様書（[`map-rendering-spec.md`](map-rendering-spec.md) 等）では単に「区域」と略すことがある。


## 3. 電文種別

| 種別 | DMDATA | P2PQuake | 内容 |
|---|---|---|---|
| 震度速報 | VXSE51 | ScalePrompt | 震源未確定・区域別震度のみ |
| 震源情報 | VXSE52 | Destination | 震源のみ・震度なし |
| 各地の震度 | VXSE53 | ScaleAndDestination（DetailScale） | 震源＋観測点・区域震度 |
| 遠地地震 | VXSE53（電文標題が「遠地地震に関する情報」・下記参照） | Foreign | 国外の規模の大きな地震。国内で震度を観測しないため観測点・区域震度なし |
| 訂正 | VXSE61 | — | 顕著な地震の震源要素更新 |
| 取消 | — | — | 誤発表の取消 |

**発表元（`issue.source`）** は編集官署 → 発表官署の順で解決する（JSON は
`editorialOffice ?? publishingOffice`、XML は `Control/EditorialOffice` → `Control/PublishingOffice`。
実電文では編集官署が「気象庁本庁」・発表官署が「気象庁」なので、解決順で値が変わる）。
**両経路で同じ順序にすること。** ただし現状この値を表示・読み上げ・通知に使っている箇所は無い。

### 遠地地震に関する情報

国外で規模の大きな地震が発生したときに、日本への津波の影響とあわせて発表される情報。
**電文種別コードは各地の震度と同じ VXSE53** で、以下の性質を持つ。

- **識別は `Head/Title`（JSON は `title`）の値が「遠地地震に関する情報」かどうかで行う**。
  気象庁 XML は配信制御用の `Control` と情報本体の `Head` がそれぞれ `Title` を持つが、
  `Control/Title` は「震源・震度に関する情報」のままなので、そちらを見ても通常の地震情報と
  区別できない（両パーサとも `resolveIssueType` でこの規則を通す）。
  P2PQuake（標準版）は `Foreign` という専用の種別で届くため、この見分けは不要
- **取消報も同じ規則で判定する**。取消のマッチングは eventId と `issue.type` の一致で行うため（§6）、
  取消報だけ `'震源・震度情報'` になると既存カードと一致せず、取消音は鳴るのにカードが消えない
- **国内震度を伴わない**: `maxScale` は常に `-1`、`points` は空
- **深さ不明の報が多い**: `depth` が `{value: null, condition: "不明"}`（XML は座標文字列の深さフィールドごと欠落）で
  届き、パーサは `-1` センチネルに落とす。`0`（ごく浅い）と区別して扱うこと
- **震源名は詳細震央地名を採る**: 震央地名（「中米」）ではなく `detailed.name`（「メキシコ、チアパス州沿岸」）。
  この優先順位は遠地地震専用の分岐ではなく全電文共通のフォールバックだが、遠地地震は震央地名が粗いため特に効く
- **続報がある**: 同一 eventId で serial 2・3 と続くことがある（津波観測値の追記など）
- **「最低表示震度」フィルタの対象外**: 国内震度を持たない情報を震度で絞り込む意味がないため、
  設定値に関わらず一覧に表示する（`App.tsx` の `filteredEarthquakes`）

#### 津波の付加文（固定と自由の 2 種類）

**付加文**は、気象庁が電文に添える文のこと。2 種類あり、役割が違う。

| 種類 | 電文上の位置 | 中身 | 保持先 |
|---|---|---|---|
| 固定付加文 | `comments.forecast`（XML は `Comments/ForecastComment`） | 津波区分ごとの定型文と番号（付加文コード） | `JMAQuake.forecastText` |
| 自由付加文 | `comments.free`（XML は `Comments/FreeFormComment`） | 電文ごとに書き起こされる本文 | `JMAQuake.freeText` |

どちらも DMDATA 経路でのみ配信される。P2PQuake（標準版）では `undefined` となり、
津波の一文は従来どおり区分から起こす。

##### 固定付加文 — 021x 系だけでは足りない

通常の地震情報は 021x 系のコードで足りるが、遠地地震は 022x 系（0221・0222・0226・0228）と
023x 系（0229・0230）を併用する。

| コード | 意味 | `domesticTsunami` への反映 |
|---|---|---|
| 0211〜0217 | 日本国内への影響（警報発表中・海面変動・心配なし 等） | する |
| 0229 | 日本への津波の有無については現在調査中 | する（`'調査中'`） |
| 0230 | この地震による日本への津波の影響はありません | する（`'なし'`） |
| 0221 / 0222 / 0226 / 0228 | 太平洋の広域・太平洋・震源の近傍で津波発生の可能性／規模による一般論 | **しない**（日本国内への影響区分ではないため） |

区分（`domesticTsunami`）への丸め込みでは意味が落ちるため、**原文を `forecastText` に保持**し、
読み上げではこちらを優先する（`ttsText.earthquakeToText`）。

表のどれにも当てはまらないコードが届いたら警告を出す（電文構造の変化に気づくため）。判定は
**既知のコードを取り除いて残ったもの**で行うこと。「1 つでも既知なら黙る」形にすると、022x 系が
頻出する遠地地震で、それと同居した新しいコードを丸ごと見逃す。

##### 自由付加文 — 続報で動くのはこちら

固定付加文は区分ごとの定型文なので、**区分が変わらない限り続報でも一字も変わらない**。
実際に更新されるのは自由付加文の側で、次のような内容が入る。

- 潮位変化の観測状況（「現在、海外および国内の観測点で有意な潮位変化は観測されていません」）
- 観測された津波の高さの一覧（**全角スペースで整形された表**）
- 次報の発表予定時刻
- 精査後のモーメントマグニチュード（VXSE61）

このため `freeText` は**改行と空白をそのまま保持する**（前後の空白だけ落とす）。1 行へ整形すると
表の列が崩れる。表示側も `whitespace-pre-wrap` で受けること。**読み上げには載せない**
（表を音声にできないため。[audio-tts-spec.md](audio-tts-spec.md) §4）。

自由付加文は遠地地震専用ではなく、国内地震にも付く（例:「なお、茨城県から沖縄県地方にかけての
太平洋側を中心に津波注意報を発表中です。」）。

**VXSE61 の自由付加文は定型文だけのことが多い**（直近 12 件のうち 11 件が
「度単位の震源要素は、津波情報等を引き続き発表する場合に使用されます。」のみ。残る 1 件は
精査後の Mw が添えられていた）。それでもそのまま出す。
理由: 定型文を文字列の一致で取り除く実装は、気象庁が文言を一字変えただけで静かに効かなくなる。

**VXSE61 は必ず持つ**ため、統合（`quakeMerge.mergeQuakeInto`）では**その報が持っていればそれを、
無ければ既存を残す**。土台が切り替わる分岐が 3 つあり、**書き漏らした分岐からだけ静かに抜け落ちる**。

| 分岐 | 土台 | 採る側 |
|---|---|---|
| VXSE61 を受け取ったとき | 既存カード | `incoming`（VXSE61） |
| VXSE61 のカードへ後から震度電文が届いたとき | 震度電文 | `existing`（VXSE61） |
| 震度を伴わない後続電文（震源情報等）で震度を補完するとき | 後続電文 | `incoming` → 無ければ `existing` |

2 つ目を落とすと VXSE61 が伝える精査後の Mw が**震度が確定した瞬間に消え**、3 つ目を落とすと
「津波注意報を発表中です」のような状況説明が後続の震源情報で消える。

## 4. points 構造（バリアント・経路差）

`JMAQuake.points` には観測点（`isArea:false`）と一次細分区域（`isArea:true`）が混在しうる。
**区域の点は区域内観測点の重心**（`station-coords.json` の `areas`）であって観測値の位置ではないため、
**ドット描画には使わない**。

| 経路 | 震度速報 | 詳細報 |
|---|---|---|
| DMDSS: WebSocket JSON（`parseIntensityPoints`） | 区域のみ | **区域＋観測点** |
| DMDSS: REST XML（`parseEarthquakeFromXml`） | 区域のみ | 区域＋観測点 |
| 標準版: P2PQuake | 区域のみ（ScalePrompt） | **観測点のみ**（DetailScale は区域を落とす） |

**QUAKE-6 の既知の制約（P2PQuake API 仕様上）**: 実データ検証（`api.p2pquake.net/v2/history?codes=551`）で確認
した通り、P2PQuake API は**観測点電文（DetailScale）と区域速報電文（ScalePrompt）を別々に送信**する仕様に
なっており、両者を 1 電文で束ねる仕組みがない。よって標準版では:
- **DetailScale**（詳細な震度情報・観測点別）: `points[].isArea: false` のみ（区域なし）
- **ScalePrompt**（震度速報・区域別）: `points[].isArea: true` のみ（観測点なし）

いずれも `pref` は非空で届く（P2PQuake の JSON 構造上の仕様）。`EarthquakeCard` は「pref 非空を都道府県
ロールアップ点として扱う」設計なので、DetailScale 時のカードは「都道府県別最大震度」だけを並べる。

**電文に区域が無くても、観測点から所属区域は逆引きできる。** 座標テーブル（`station-coords.json`）が
観測点ごとに一次細分区域を持つため。地図の区域塗り（`useQuakeLayerData`）と読み上げ
（→ [audio-tts-spec.md](audio-tts-spec.md) §4「地域名の粒度」）はこの逆引きで、標準版でも区域粒度を出す。
**カードだけが都道府県粒度に留まっている**のは、区域にすると行数が倍以上に増えて縦に伸びすぎるため
（2026-08 時点の実測で、能登半島地震の本震が 45 行 → 107 行）。情報が取れないからではなく、表示量の判断。

**P2PQuake 経路の points 検証**: `convertEvent` は `addr`（観測点名・区域名）が空の要素だけを落とし、
地震そのものは残す。`addr` は一覧・地図いずれの表示にも要る識別子だが、1 点の欠陥で地震全体を
捨てる理由にはならないため。`pref` は空でも落とさない（上の識別規則で意味を持つ）。
震度（`scale`）が階級外なら `-1`（不明）に格下げする。ただし `46`（「震度 5 弱以上と推定されるが
震度情報を入手していない」）は API 仕様上の正規値なので、下限の `45` として扱う
（詳細は [`data-sources-spec.md`](data-sources-spec.md) §3）。

**識別規則**（**DMDSS 経路限定**）: DMDATA JSON / XML 経路の points について `pref` の有無で
「点の役割」を識別する。P2PQuake 経路は上記の通り常に `pref` 非空で届くため、この規則の対象外。
- 区域は必ず `pref: ''` で積む（`isArea: true`）
- 観測点も `pref: ''` で積む（`isArea: false`）。DMDSS の JSON 経路と XML 経路の両方で統一（QUAKE-2）
- **都道府県ロールアップ点**を `pref: '<都道府県名>', addr: '<都道府県名>', isArea: true` で追加する。
  情報源は JSON 経路が `intensity.prefectures[]`、XML 経路が `Pref` 直下の `MaxInt`（実電文の
  `<Pref><Name>石川県</Name><Code>17</Code><MaxInt>5+</MaxInt>` に相当）。
  `EarthquakeCard.prefGroups` は `pref` が非空かどうかだけを見るため `isArea` の値は表示には
  影響しないが、点の役割は「区域や観測点ではない集約値」なので `true` で積む
  - XML 側は `xmlChild`（直下限定）で `MaxInt` を取る。`xmlQ`（子孫検索）にすると、`Pref` 直下に
    `MaxInt` を持たない電文で配下 `Area` の値を都道府県の代表値として拾ってしまう

合成テストデータ（地震テストボタン）も DMDSS ではこの形を作る
（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7「実電文の形に合わせる」）。

**QUAKE-2 の対応（2026-08-13）**: 以前は XML 経路（`parseEarthquakeFromXml`）が観測点に `pref: prefName` を
積んでおり JSON 経路と非対称だった。`EarthquakeCard.prefGroups` は「pref 非空＝都道府県ロールアップ点」
前提で処理するため、XML 経路のみ「観測点値」を都道府県別最大震度と誤解して区域最大震度を上書きしていた。
現在は XML 側も `pref: ''` に統一済み。

**都道府県ロールアップ点の欠落（2026-09-04 に解消）**: 上の QUAKE-2 で観測点の `pref` は揃えたが、
`Pref` 直下の `MaxInt` を読む処理が XML 経路に無く、**都道府県ロールアップ点そのものが落ちていた**。
`EarthquakeCard.prefGroups` は pref 付きの点が無いと区域点からの逆引き集計に落ち、それは
「同一都道府県内の全区域が同じ震度で揃っている」ときだけ 1 行にまとめる。区域ごとに震度が違う県では
気象庁発表の代表値と粒度・数値が変わっていた。XML 経路が通るのは REST 履歴取得（起動時の初期表示と
「もっと見る」）なので、**同じ地震でも履歴で読み込まれたかライブで受信したかで内訳が変わっていた**。

**pref 逆引きが必要な派生データ**: `pref` が空でも `station-coords.json` の逆引き（`buildAreaPrefIndex` /
`buildStationPrefIndex`）で都道府県は復元可能。以下の派生データは pref が空でも都道府県を再構築する:
- `useQuakeLayerData.intensityMarkers` — 地図に置く観測点マーカーの色・位置
- `useQuakeLayerData.prefIntensities` — 震源ポップアップの都道府県別最大震度
- `ttsText.regionNamesForScale` — 読み上げの地域名。区域の点が無い電文では観測点から
  一次細分区域を逆引きし（`lookupStationRegion`。地図の区域塗りと同じ関数）、区域が引けないときだけ
  都道府県名へ落とす（→ [audio-tts-spec.md](audio-tts-spec.md) §4「地域名の粒度」）

## 5. 震源未確定（震度速報）の扱い

- VXSE51（震度速報）は震源が未確定のため `Earthquake` 要素・`body.earthquake` を**持たない**
- 座標は `-200`（位置不明センチネル）、発生時刻は `TargetDateTime`（JSON は `data.targetDateTime`）を使う
- 両パーサとも震源なしを許容する分岐がある
- 表示側は `EarthquakeCard.hasLocation`（lat > -200）で震源系の表示を切り分ける
- **EventID も暫定値**で、震源決定後の情報と別採番になることがある（§6.1）

## 6. 続報マージ（`quakeMerge.mergeQuakeInto`）

同一イベントの電文が来た場合、時刻順で 1 枚のカードに統合する。

- 速報 → 詳細報の順で情報が積み重なる（震度速報の後に詳細報が来れば震源・観測点情報が追加される）
- VXSE61（震源要素更新）は既存カードの震源情報のみを更新
- 取消は既存カードを削除

### 6.1 同一イベントの判定（`sameQuakeEntry`）

統合・カード選択・ブラウザ通知の重複抑止は、すべてこの判定（または一度確定した `eventKey` の
一致）を根拠にする。優先順は次のとおり。

1. **`eventKey`（安定キー）** — 双方が統合済みカードならこれだけで判定する
2. **eventId（14 桁数字）** — DMDATA 経路。`extractQuakeEventId` が電文 ID から抽出する
   （ただし食い違ったときに 3 へ落ちる例外がある。下記「暫定 EventID の採り直し」）
   - **見るのは `id` 文字列で、`eventId` フィールドではない。** カードは両方を持つが、この判定も
     `coalesceByEventId` も `id` から抜く
   - フィールドを直接読むのは 2 箇所。`TsunamiTab` が津波バナーから原因地震カードへのリンクを
     作る箇所（取消済みカードを除外するので影響しない）と、`testScenarioReplay` の
     `remapAppEvent`（リプレイの ID 再採番）。**後者はフィールドが無いと `id` を無変換で返す**ため、
     欠けている報だけシナリオ内でキーが揃わない
   - フィールドは全経路・全種別（取消電文を含む）で埋める。**片方だけ持たない状態を作らない**。
     XML 経路と取消電文で欠けていたのを 2026-09-04 に揃えた
3. **発生時刻 ＋ 震源名 ＋ 区域の重なり** — eventId が無い（P2PQuake 経路）か、
   あっても根拠にできない場合（下記の暫定 EventID）

`eventKey` は `mergeQuakeInto` が統合のたびに既存カードから引き継ぐため、**続報で電文 ID が変わっても
カードのキーは変わらない**。DMDATA 経路では eventId、P2PQuake 経路では初報の発生時刻とレコード ID から作る。

キーの材料が欠けた電文は、統合先を誤って別々の地震を 1 枚に潰す。そのため P2PQuake 経路の
`convertEvent` は、`id` と `earthquake.time` のどちらかが空の 551 を**電文ごと破棄**する
（どちらも API 仕様上の必須フィールドなので、欠けていれば壊れた電文と判断してよい）。
なお破棄条件はこれで全部ではない — 電文トップレベルの `time` も同じく破棄対象で、
そちらは同一性ではなく表示キューの並び順キーが理由。全条件は
[`data-sources-spec.md`](data-sources-spec.md) §3 の表に一覧がある。

3 の震源名を見るのは、**P2PQuake の発生時刻が分単位（秒は常に `00`）**で、同じ分に起きた別々の地震が
同じ時刻文字列になるため。震源名が両方判明していて食い違う場合のみ別イベントとする。
震度速報は震源が未確定で震源名が空なので判定に使わず、震源を伴う続報と合流する。
震源名が変わりうる電文（訂正報と、震源要素を差し替える VXSE61「顕著な地震の震源要素更新のお知らせ」）は、
食い違いを別イベントの根拠にしない。

#### 暫定 EventID の採り直し

**eventId が食い違っても、それだけでは別イベントとしない。** 震源が未確定の電文（震度速報）の
EventID は震源が決まると採り直されることがある（**観測から読み取れる規則**で、気象庁の公表仕様として
裏を取ったものではない。暫定値は検知時刻、確定後は震源時刻に見える）。
実例として 2026-08-24 04:05 の熊本県天草・芦北地方の地震では、震度速報が `20260824040519`、
震源情報以降が `20260824040526` だった（震度速報は気象庁本庁、震源情報は大阪管区気象台の発表で、
官署の引き継ぎに伴って採り直されている）。**どちらかが震源未確定のときだけ** eventId の一致を
要求せず、発生時刻・震源名・区域の照合へ落とす。震源が判明している電文どうしは従来どおり eventId
だけで分離する（同じ分の別々の地震を取り違えないため）。

発生時刻で照合できるのは、震度速報が `TargetDateTime`、以降が `ArrivalTime` を `earthquake.time` に
使っていて、同じ地震なら同じ値になるため（震源時刻 `OriginTime` とは 1 分ずれることがあるので採らない）。

**救済は「震源未確定の電文 × 震源が判明した電文」の組に限る。** 同じ地震の震度速報どうしは同じ
EventID を共有するため（2026-08-23 22:45 の 2 通で確認）、**両方が震源未確定なら別々の地震**として
扱う。ここを緩めると、同じ区域を揺らした別々の地震が 1 枚に潰れる。

**数えるのは一次細分区域だけ。** §4 のとおり DMDATA の JSON 経路（ライブ）は都道府県を
`{ pref: 名前, addr: 名前, isArea: true }` としても足すため、`isArea` だけで絞ると県名が混ざる。
県は区域より粗く、同じ県の別々の区域で起きた 2 つの地震が「重なる」ことになってしまう。除き方は
読み上げ側（`ttsText.ts`）と同じく `p.isArea && p.addr !== p.pref`。

**区域の重なり（§4 の `isArea: true`）の使い方は、経路によって強さが違う。**

| 経路 | 区域の使い方 | 理由 |
|---|---|---|
| eventId が食い違う（暫定 ID の採り直し） | **重なることを合流の条件にする** | 発生時刻の一致だけで合流させると、同じ分に起きた別の地震の震源情報（VXSE52 は区域を持たない）が震度速報のカードを乗っ取り、**揺れていない地域の震度が別の震源に貼り付く** |
| eventId が無い（P2PQuake） | 1 つも重ならなければ別イベントとする（緩い） | この経路は eventId による分離が最初から無い。合流に区域を必須にすると、区域を持たない通常の続報まで分かれてしまう |

**合流を厳しくした分は、あとで畳んで帳尻を合わせる。** 震度速報のカード（暫定 ID）が震度を伴う
続報（DMDATA なら VXSE53 の震源・震度情報、P2PQuake なら各地の震度情報）を取り込むと、そのカードの
eventId は確定 ID に変わる。すると先に届いていた震源情報のカード（同じ確定 ID）と重複するため、
`coalesceByEventId` が **eventId だけを見て** 1 枚に畳む。`eventKey` は続報で不変にするため引き継ぐ
値なので、この重複には気づけない。履歴・ライブの両経路で同じ関数を通し、畳んだことは `log.info`
で記録する（無音だと、畳まれたのか元々重複していないのかを実運用で区別できない）。

**取消表示中（`cancelledAt`）のカードは畳まない。** `mergeQuakeInto` は置換時に `cancelledAt` を
引き継がず `id` も入れ替えるため、畳むと 10 秒後の purge 予約（`id` で対象を引く・§6.2）が空振りし、
取り消したはずのカードが居座る。

**一致するカードが 2 枚あるときは、先に立った方（発表時刻が古い方。同値なら `id` 順）を既存として
選ぶ**（`findExistingQuakeCard`）。暫定 ID のカードと確定 ID のカードが同時に一致する瞬間があり、
後から立った方を選ぶと統合後の `eventKey` が入れ替わる。`eventKey` はブラウザ通知の重複抑止に使う値
なので、入れ替わると**同じ地震の通知が二度出る**。

> **限界**: 同じ発生時刻の別々の地震を常に分離できるわけではない。
> - **震源名が同じ場合**（P2PQuake 経路） — 分離できず 1 枚のカードに統合される
> - **暫定 ID のカードと震源情報（VXSE52）は、その場では合流しない** — VXSE52 は区域を持たず、
>   合流の条件（区域の重なり）を満たせないため。震度を伴う続報（VXSE53）が届いて畳まれるまでの間、
>   ライブでは 2 枚に見える（実測で 04:08 → 04:09 の約 1 分）。履歴の取得では 3 通が
>   そろうため最初から 1 枚になる
> - **区域を持たない電文（VXSE52・VXSE61・訂正報）が先に割り込む場合** — それらは確定 ID 側の
>   カードだけを更新し、暫定 ID のカードとは合流できない。震度を伴う続報（VXSE53）が届いた時点で
>   1 枚に収束し、割り込んだ震源要素更新の内容も残る（`quakeMerge.test.ts` で固定）
> - **震源要素更新（VXSE61）のカードが残っている間** — この電文は震源名の変更を許す扱いなので、
>   その間は震源名の食い違いを別イベントの根拠にできず、同じ分の別の地震の報を吸収しうる
> - **区域が部分的にしか重ならない場合** — 「1 つも重ならなければ別」という基準は推移的でない。
>   A と C が重なり、B と C も重なるが A と B は重ならない、という 3 つ組がありうる。どのカードへ
>   吸収させるかは経路で選び方が違う（履歴は配列の先頭から、ライブは発表時刻の古い方）が、
>   いずれも電文の到着順に左右される
>
> **DMDATA 経路も無縁ではない。** eventId があっても、震度速報の暫定 ID が採り直された場合は
> 上と同じ照合へ落ちる（上記 04:05 の実例）。そもそも同じ分に別々の地震が発表されること自体がまれで、実例として
> 確認できているのは 2026-08-15 06:58 の「群馬県南部 × インドネシア、フローレス」（震源名が
> 異なるため分離できるケース）。この実例は `quakeMerge.test.ts` に回帰テストとして固定している。

### 6.2 取消のマッチング（`useEarthquakes.ts`）

**取消電文は eventId でのみ照合する。** パーサは取消を種別によらず震源名・発生時刻とも空で作るため、
§6.1 の内容照合（発生時刻・震源名・区域）の材料を持たない。`sameQuakeEntry` はこの電文を
「震源未確定」の扱いから明示的に外しており、eventId が採り直された取消はどのカードにも当たらない
（その場合は `log.warn('[quake] 取消電文に対応するカードが見つからず無視した', …)` が残る）。

取消電文は **同一イベント（`sameQuakeEntry`）かつ `issue.type` が一致する**カードを対象に
`cancelledAt` を付け、10 秒後に消す。`issue.type` まで見るのは、同一イベントで種別の異なる電文が
並ぶため。この一致条件があるので、パーサは取消電文でも通常報と同じ規則で `issue.type` を決める
必要がある（§3 の遠地地震を参照）。

#### 取消の後に届いた報

**正常な運用では起きない。** 取消は「その情報を取り下げる」意味で、取り下げた地震について続報は
出ない。それでも届いたなら異常が 2 通りあり、**取消電文の発表時刻で切り分ける**（判定は
`quakeMerge.ts` の `isRetractedQuakeReport`）。

| | 何が起きたか | 扱い |
|---|---|---|
| 到着順の入れ替わり | 取消と**同時刻以前に発表された**報が遅れて届いた。当日ぶんの REST 経路・リプレイでは順序が入れ替わりうる（同じ分のタイは呼び出し側の入力順に委ねているため） | **捨てる**（取り下げ済みの内容） |
| 同一性の誤認識 | 別の地震の報が `sameQuakeEntry` で同一と判定された（§6.1 の限界） | **別カードとして立てる**。取消済みカードには触らない |

- **同じ発表時刻なら取り下げ側へ倒す。** `time` は分精度なので前後を決められない。取消を尊重する
  方が安全。発表時刻が空の報も同じ扱い
- **種別（`issue.type`）まで一致を要求する。** 取消の適用側も種別まで見て絞っている（遠地地震の
  取消報が「震源・震度情報」のカードを巻き込まないようにするため。上記参照）。**適用側が絞ったものを
  参照側で広げてはいけない**——報を落とす判定は結果が画面に出ないぶん見つけにくい
- **取消済みカードは既存カードの候補から外す。** 選ぶと `mergeQuakeInto` が置換して `cancelledAt` が
  落ち、さらに `id` も入れ替わるため 10 秒後の purge 予約（`id` で対象を引く）が空振りし、取り消した
  はずの地震が居座る。**この規則は 2 箇所に別々の実装で置いてある**——ライブ経路は
  `findExistingQuakeCard`、履歴経路は `mergeQuakeHistory` 内の照合（前者はカードを返し後者は添字を
  必要とするため関数を共有できない）。**片方だけ直すと規則がずれる**
- **ライブ経路は取消済みカードを差し替えの対象から外す**（`useEarthquakes.ts` が `coalesceByEventId`
  へ渡す配列で `cancelledAt` 付きを残す）。落とすと 10 秒表示を待たずに消え、purge 予約も空振りする
- **取消を見た事実は台帳（`quakeRetractionsRef`）に持ち、両経路で共有する。** カードの `cancelledAt`
  を見るだけでは足りない——取消済みカードは 10 秒後に purge されるため、それを過ぎて届いた古い報を
  弾けない。順序の入れ替わりを拾うのが目的なのに 10 秒で記憶が消えては用を成さない。履歴経路は
  カードごと消すので、そちらの取消も同じ台帳へ集める
  - 台帳は件数に上限を置き**古いものから**落とす（判定は毎回全件を走査するため）。向きを取り違えると
    「直近の取消を忘れて古い取消を覚え続ける」形になり、取り消した地震が復活する側へ倒れる
  - **リプレイの開始・リセットでは空にする。** 時間軸が変わるため、前の軸で見た取消の発表時刻と
    新しい軸の報を比べると正常な報を取り下げ済みと誤判定する
  - **台帳への記録は `setState` の外（受信の入口）で行う。** 更新関数は再実行されうるため、中に
    置くと同じ記録が二重に積まれ、上限の実効容量が縮む。EEW の台帳（`acceptedEewSerialRef`）と
    同じ置き方
  - 取消がどのカードに効くかの判定は `isQuakeCancelTarget` に集約する。台帳への記録（入口）と
    取消の適用（`setState` の中）で同じ述語を使うため。書き写すと記録と適用の範囲が静かにずれる
- **`mergeQuakeHistory` には台帳を渡す。** `base` に取消表示中のカードが含まれる呼び出し
  （「もっと見る」は画面のカード群を渡す）では、その取消はバッチの中に無いため渡さないと照合できない
- 記録に何を入れるかで照合の精度が変わる（選び方は `quakeRetractionOf` の説明を参照）
- **この扱い全体が DMDATA 経路（DMDSS 版）限定。** P2PQuake の地震情報（code 551）は `cancelled` を
  配信せず、パーサ（`p2pquake.ts` の `parseQuake`）もこのフィールドを設定しないため、標準版では
  取消の分岐に一度も入らない（台帳は常に空のまま）。標準版で正常な報が取り下げられる心配は無い

**訂正の扱い**:
- XML パーサ（`parseEarthquakeFromXml`）は `InfoType === '訂正'` を判定して `correct: '訂正'` を設定
- JSON パーサ（`parseEarthquake`）も `infoType === '訂正'` を判定して同じく設定する（旧実装は `'なし'` 固定で
  訂正バッジが出なかった。`dmdataParser.test.ts` に回帰テストあり）
- P2PQuake 経路（`convertEvent`）は `CORRECT_TYPE_MAP` で日本語化

### 6.3 据え置き判定（`mergeQuakeInto` の据え置き）

`sameQuakeEntry` が同一イベントと判定した後、`mergeQuakeInto` は「新しく届いた電文（incoming）で
既存カード（existing）を上書きするか、据え置くか」を判定する。既存が実震度を持つ・未取消のときだけ
働く（震度なし・取消表示中のカードは常に上書きされる）。

- **既存が VXSE61（顕著な地震の震源要素更新のお知らせ）とマージ済みの完成カードなら、時刻・種別を
  問わず絶対的に据え置く。** VXSE61 は「震源要素が確定した」という強い意味を持つ電文で、その後に
  届く通常電文（震度速報の再送等）で覆されるべきではないため
- **incoming が実震度を持つ電文（震度速報・震源・震度情報・各地の震度）なら、発表時刻（`time`）で
  判定する。** `issue.type` の優先度は見ない。**同じ発表時刻の続報は種別を問わず常に受け入れる**
- **incoming が震度を持たない電文（震源情報等）なら、`issue.type` の優先度表
  （`QUAKE_ISSUE_PRIORITY`）で判定する**（各地の震度情報 > 震源・震度情報 > 震源情報 >
  震度速報 > 遠地地震・その他。顕著な地震の震源要素更新＝ VXSE61 はこの比較には現れない。
  既存が VXSE61 なら 1 つ上の絶対据え置きルールで先に処理されるため）

**時刻を主軸にしているのは、気象庁が震度速報を複数回発表することがあるため**（能登 2024/1/1
16:06〜16:08 の実データで確認）。震度速報の間に震度を持たない震源情報が挟まると、既存カードの
`issue.type` が「震源情報」（震度速報より優先度が高い）に変わる。そこへ種別優先度だけで判定すると、
時系列的には後から届いた正しい震度速報の続報が「優先度が低い」という理由だけで無視され、新しく
増えた区域（新潟県佐渡等）が地図・カードに反映されなくなる不具合があった（2026-08 修正）。

**`time` は分単位までしか精度が無い**（気象庁電文の `ReportDateTime` 由来）。同じ分に複数種別の
電文が発表されることが実データでも確認されており、`mergeQuakeInto` は「同じ分の続報は種別を
問わず受け入れる」設計にしている。この判定が正しく働くのは、`mergeQuakeInto` が時系列順に
逐次呼ばれる前提（ライブ経路は受信順、`mergeQuakeHistory` は `time` 昇順ソート済み）が
成り立っているときに限る。

**`time` の比較は文字列の辞書順で行う（`Date` を経由しない）。** これが時系列順と一致するのは、
existing/incoming が同じ書式・同じタイムゾーンオフセットで揃っているときだけ。DMDATA 経路
（`dmdataParser.ts`）は ISO 8601 + 固定オフセット（例: `+09:00`）、P2PQuake 経路（`p2pquake.ts`）
はスラッシュ区切りでオフセット無し（例: `2026/01/02 15:04:05`）と書式が異なる。今のところ実害が
無いのは、standard 版は P2PQuake のみ・DMDSS 版は DMDATA のみとビルドバリアントごとにデータ
ソースが単一だから。両方を 1 つの `mergeQuakeInto` 呼び出し系列に混ぜる変更をするなら、先に
`time` を `Date` ベースの比較に置き換えること。

**既知の限界（DMDATA 履歴経路）**: `mergeQuakeHistory` は安定ソートで畳み込むため、同じ分に
詳しい電文（各地の震度情報等）と粗い電文（震度速報等）が混在すると、入力配列の相対順序が
そのまま結果に効く——詳しい方が先・粗い方が後だと、粗い方が詳しい方を上書きしてしまう
（`quakeMerge.test.ts` に既知の限界として固定）。これを避けるため、`fetchDmdataEarthquakes`
は取得した電文を常に「速報→詳細」（VXSE51→52→53→61）の順に結合する。呼び出し側で結合順序を
変える場合はこの前提を崩さないこと。

**`sameQuakeEntry` の誤認識に対する保険**: incoming が実震度を持つ場合は種別優先度を見ないため、
`sameQuakeEntry` が別の地震を同一イベントと誤認識すると（§6.1 の「限界」を参照。P2PQuake 経路や
暫定 EventID の採り直しで起こりうる）、無関係な電文が正しいカードを上書きしうる。この上書きが
「種別優先度としては本来据え置き相当だった」場合は `log.info` で記録する（無音だと、地震カードの
内容が急に後退したときに原因を辿れない）。

### 6.4 置換時の項目の引き継ぎ

据え置き判定（§6.3）が「上書きする」と決めた後、`mergeQuakeInto` は incoming を土台にしつつ、
**incoming に載っていない項目を既存カードから補う**。補うのは 2 方向あり、対になっている。

| incoming が持たないもの | 該当する電文 | 既存カードから補うもの |
|---|---|---|
| 震度 | 震源情報（VXSE52）等 | `maxScale`・`points`・自由付加文 |
| 震源 | 震度速報（VXSE51） | `hypocenter`（震源名・座標・深さ・M） |

震源を補う側の判定には `isHypocenterPending`（震源名が空かどうか）を使う。震源名の空判定を
書き写さないこと——同じ事実を別の言葉で表すと、片方だけが変わったときに範囲がずれる。

**震度速報の津波区分（`domesticTsunami`）と固定付加文は採らず、既存カードの判断を残す。**
震度速報はこれらを自前で持っているが、**その報の判断を表していない**。種別に付く定型文で、
実データではこうなっていた（能登 2024/1/1 の前震）。

| 到着 | 種別 | 津波区分 | 固定付加文 |
|---|---|---|---|
| 16:08:32 | 震源情報 | `なし` | この地震による津波の心配はありません。 |
| 16:08:42 | 震度速報 | `調査中` | 今後の情報に注意してください。 |

気象庁が「なし」と判断した 10 秒後の報が `調査中` のまま届く。判断が更新されていないのではなく、
震度速報の付加文コード（0217）が種別に紐づいて動かないだけ。採ると、確定した安全表示が続報の
たびに `調査中` へ戻る（`formatDomesticTsunami` は `なし` を緑・`調査中` を灰で出す）。津波警報の
発表中に震度速報の続報が届けば、同じ経路で `警報等` を `調査中` へ格下げしうる。

- **読み上げ側は既に同じ扱いをしている**（`ttsText.ts` の「震度速報では呼ばないこと」）。画面表示側
  にだけ無かったので揃えた
- 既存が `不明`（判断がまだ無い）のときは震度速報の値を使う。イベントの初報が震度速報のときは
  そもそも既存カードが無いため、`調査中` がそのまま出る
- **判定は `issue.type` で行う。** `isHypocenterPending`（震源名の空判定）を流用しないこと
- 震度速報以外の続報は津波区分を普通に置き換える。実際の判断を運ぶ電文なので、値が軽くなる方向
  （`注意報` → `なし`）でも従う

> これは上の「値の取り下げには従う」だけでは足りないことを示す 3 つ目の型——**種別に付く定型文**。
> 電文が値を持っていても、それがその報の判断でなければ採らない。

#### 補う／補わないの分かれ目

**補ってよいのは「その電文種別が構造的に持たないフィールド」だけ。**
**同じ種別・同じフィールドの中で値が消えた場合は補ってはいけない。**

| 消え方・値の性質 | 例 | 扱い | 誤ると何が起きるか |
|---|---|---|---|
| **構造的欠落** | 震度速報は `Earthquake` 要素を持たない（§5） | 前報から**補う** | 確定した震源が続報で消える |
| **値の取り下げ** | 続報の震度が前報より下がる | **そのまま従う** | 気象庁が下げた値を高いまま表示し続ける |
| **種別に付く定型文** | 震度速報の津波区分（下記） | **採らず既存を残す** | 確定した判断が定型文で上書きされる |

震源が構造的欠落の側だと言える根拠: 気象庁が確定した震源を取り下げるときは訂正報
（`issue.correct`）か VXSE61 を出す。震度速報の続報が「震源が未確定に戻った」を意味することはない。

**取消表示中（`cancelledAt`）のカードからは補わない。** 取消は「その報の内容が誤りだった」という
意味なので、取り下げられた内容を新しいカードへ持ち込まない。ただし本来は取消済みカードが
`existing` として選ばれること自体を止めるのが筋で、そちらは `findExistingQuakeCard` が担う
（§6.2「取消の後に届いた報」）。ここと震度補完側の判定は、その入口が変わっても不変条件が
保たれるようにする二重の防御。震度補完側にはこの判定が無い（取消済みカードの震度・自由付加文を
引き継ぐ）が、入口で止まるため到達しない。

**震源側には震度側のようなキャッシュが無い。** `useEarthquakes.ts` は震度速報の震度を
`quakeIntensityCacheRef` に控えて後続の震源情報へ補うが、震源にはこれに当たる控えが無いため、
対象カードが消えた後（取消の 10 秒後 purge 等）に震度速報の続報が届くと震源は付かない。

> この原則は `mergeQuakeInto` 以外のマージにも当てはまる。EEW の続報マージ
> （`useEarthquakes.ts` の `'eew'` ケース。`severity` だけを引き上げ専用にし、他は incoming で
> 置き換える）では、続報でマグニチュードが下がると予想長周期地震動階級が電文から消えることが
> ある（能登 2024/1/1 前震の第 12 報で確認）。これは値の取り下げなので保持しない——保持すると、
> 階級 4 の地震では気象庁の推定が支えなくなった後も特別警報を維持してしまう
> （[`eew-spec.md`](eew-spec.md) §4）。

#### 実例（能登 2024/1/1・前震）

震源を補わないと、確定した震源が続報で丸ごと消える。

| 到着 | `time` | 種別 | 震源 | 震度 |
|---|---|---|---|---|
| 16:07:42 | 16:07 | 震度速報 | なし（座標 `-200`・深さ `-1`・M なし） | 震度5強・区域 5 件 |
| 16:08:32 | 16:08 | 震源情報 | 石川県能登地方・深さ10km・M5.7 | なし |
| 16:08:42 | 16:08 | 震度速報 | なし | 震度5強・区域 6 件 |

`time`（`ReportDateTime` 由来）は分精度なので、**後の 2 通が同じ 16:08 に並ぶ**。据え置き判定は
同じ分の続報を受け入れるため（§6.3）、最後の震度速報が震源情報を置き換える。補完が無いと
震源名・座標・深さ・M が失われ、座標が `-200` に戻るため地図の震源マーカーとカードの位置表示
（`EarthquakeCard.hasLocation`）も落ちる。

この地震では 16:10:05 の震源・震度情報（VXSE53）が震源を持つため、そこで表示は回復する。
**症状が出るのは約 83 秒の窓に限られ、リロードでも再現しない**——履歴経路
（`mergeQuakeHistory`）は電文を「速報→詳細」の順に結合するため、同じ分のタイでは震源情報が
後着になる（§6.3 の「既知の限界」）。ライブ・リプレイでのみ現れる。

## 7. 地図描画の切替（区域集約と観測点表示）

`useQuakeLayerData` の `stationMarkers` と `intensityMarkers`:

- `stationMarkers`（`isArea:false` のみ）: `QuakeIntensityPointsGL` の入力。観測点ごとの震度ドット
- `intensityMarkers`（全点）: カメラフィットのフォールバック専用（描画には使わない）

### 7.1 ズームによる集約の切替

区域データ（`subregions.json`）が読めていることが前提。読めていない場合は §7.2 が優先し、
以下の条件に関わらず観測点個別表示になる。

- ズームが集約閾値（自動フィットの寄り上限と同値。基準ペイン・短辺 800px では概ね 7.0 相当）以下
  → 区域集約表示
- それより深いズーム → 観測点個別表示
- **観測点が 0 件の電文（震度速報等）** → ズームに関わらず区域集約を維持
  （拡大しても増える情報が無いうえ、区域重心をドットにすると「その地点の観測値」に見えてしまうため）

判定は `useQuakeLayerData.aggregateByRegion` の OR 条件。LPGM 表示中が対象外になるのは
**3 番目（観測点 0 件による維持）だけ**で、ズームによる切替と §7.2 のフォールバックは LPGM にも
同じように効く（3 番目だけを外すのは、選択中の quake と表示中の LPGM が別イベントのことがあるため）。

### 7.2 区域データ取得失敗時のフォールバック

取得失敗が確定すると、ズーム・観測点数に関わらず観測点個別表示へ切り替える（§7.1 の
どの条件よりも優先する）。塗る区域ポリゴンが 1 件も作れないうえ、区域塗りと観測点ドットは
排他で切り替わるため、集約を維持したままだと地図から震度が消えてしまうため。

**限界**: このフォールバックは観測点ドットで震度を描くものなので、観測点を持たない電文
（震度速報）には代替表示が無い。震度速報は震源も未確定（§5）で震源マーカーすら出ないため、
**地図は空白になる**（震度は一覧カードにのみ出る）。緊急地震速報の予想震度も区域単位でしか
表現できないため同様に地図へ出ない。

**復帰**: 区域データは震度・EEW の予想震度・ベースマップの境界線・区域名ラベルがそれぞれ
要求し、失敗しても次の要求で再取得される。震度側の要求は地図の初期化前、ベースマップ側は
初期化後に走るため、震度側が先に失敗してもベースマップ側の再取得が成功すれば区域集約に戻る
（EEW の予想震度塗りも同じ仕組みで復帰する）。

通信がハングして応答もエラーも返らない場合も、取得は時間切れで打ち切られて失敗として確定する
ため、上記のフォールバックとログはそのまま働く（生成データ全般に共通。タイムアウト値は
[`data-sources-spec.md`](data-sources-spec.md) §6 参照）。

利用者に向けては、取得に失敗した件数を地図左上に出す
（[`data-sources-spec.md`](data-sources-spec.md) §6「取得状況の表示」）。

失敗時の `console` 出力は、震度側が `error`（「観測点ドットで代替」の旨）で 1 度だけ。
ベースマップの境界線・区域名ラベル側の警告は
[`map-rendering-spec.md`](map-rendering-spec.md) §4・§5 を参照。

集約閾値は自動フィットの寄り上限（`gl/camera.ts` の `fitMaxZoom`）と**同値でなければならない**。
自動フィットの着地点が常にこの閾値以下＝必ず区域集約になる、という前提に描画側が依存しているため。

寄り上限は地図ペインの寸法で変わる（[map-rendering-spec.md](map-rendering-spec.md) §6「寄り上限と閾値の
単位」）ので、この閾値も定数として持てない。`JapanMapGL` が寄り上限と同じ関数から取った値を
`useQuakeLayerData` へ渡し、ペインが変わるたび取り直す。**独自の値を置いてはならない**——大きな画面
（寄り上限が 7 を超える）で「フィットしたのに震度塗りにならない」が静かに起きる。

### 7.3 座標テーブル取得失敗時の挙動

観測点の緯度経度は `station-coords.json` から引く。取得に失敗すると観測点ドットは 1 つも描けず、
§7.1 の「観測点 0 件」条件が成立してズームに関わらず区域集約が維持される。

このとき地図に何が残るかは電文次第。区域塗りは電文が持つ区域名から引くため座標テーブルに依存せず、
**区域を持つ電文なら残る**（§4 のとおり DMDSS の詳細報は「区域＋観測点」、震度速報は区域のみ）。
一方、**標準版（P2PQuake）の詳細報は観測点のみで区域を持たない**ため、この経路では地図から震度が
消える（震度は一覧カードには出る）。

**区域データも同時に失敗している場合**は §7.2 が優先されるため区域集約自体が無効になり、
ドットも区域塗りも出ない（地図に震度は何も残らない）。どちらも同じ配信元から取得するので、
ホスティング側の障害では同時に落ちうる。

地震カードの都道府県別内訳も、点が都道府県を持たない経路（DMDSS の REST 履歴。§4 の識別規則）では
区域名から都道府県を引けず空になる。都道府県付きで届く経路（DMDSS の WebSocket・標準版）は影響を受けない。

区域データと同じく、他の呼び出し元（地震カード・EEW の都道府県補完）の再取得が成功すれば復帰する。
緊急地震速報の地域名に付ける都道府県の補完も同じ仕組みで復帰する（補完用の索引は接続中に届く
すべての EEW に使い回されるため、一度の失敗で固定されると影響が長く残る）。

失敗は `console.error` に「観測点ドットが描けない」旨で 1 度だけ出力される（EEW の都道府県補完側は
影響が異なるため別途 `warn`）。§7.2 と同じく、通信がハングした場合も時間切れで打ち切られて
失敗として確定するため、上記の挙動とログはそのまま働く。

## 8. カード表示（`EarthquakeCard`）

主な要素:
- 見出し: 「震度速報」「震源に関する情報」「各地の震度に関する情報」「遠地地震」等（`formatIssueType`）
- 震源情報: 座標・深さ・マグニチュード（震源確定時のみ）
- 最大震度・津波の見通し
- `prefGroups`: 都道府県ごとに集約した震度リスト
- 訂正バッジ（`correct !== 'なし'` のとき）

**値が不明なときの表示**: 深さ・マグニチュードは `formatters.ts` の `hasDepth` / `hasMagnitude` で
判定し、不明なら数値の代わりに「不明」を出す（色バッジも不明色になる）。パーサが渡す不明の値は
深さが `-1`、規模が `-1`（P2PQuake 経路）または `NaN`（DMDATA 経路）。同じ判定関数を読み上げ
（[audio-tts-spec.md](audio-tts-spec.md) §4）でも使うため、カードと読み上げで食い違わない。
遠地地震は震度を伴わないため最大震度欄は「?」になる。

**`prefGroups` の集約規則**（`src/components/EarthquakeTab/EarthquakeCard.tsx` の `prefGroups`）:
- ここでの「集約」は `§7 地図描画のズーム集約`（一次細分区域単位）とは別軸で、**カード表示専用に都道府県単位で集約**する処理
- 「pref 非空＝都道府県ロールアップ点」「pref 空＝一次細分区域点」の 2 経路に分けて処理
- 都道府県内で震度が割れているケースは区域単位で個別表示
- 全区域が同一震度の場合は都道府県単位でまとめて表示

**QUAKE-4（解決済み）**: 以前は `EarthquakeTab` の React `key` が続報のたびに変わって
`EarthquakeCard` がリマウントし、`isSelected` の副作用（scrollIntoView）が毎回発火して
ユーザーの手動スクロールを妨害していた。現在は `key` も選択判定も §6.1 の `eventKey` に
統一している。`eventKey` は続報でも変わらないため、この問題は両バリアントで解消している。

## 9. 地図レイヤー

### QuakeIntensityPointsGL（観測点ドット）
- 各観測点を「震度ラベル付きの丸バッジ」として描画
- ラベルは Canvas2D で事前ラスタライズした icon-image を map.addImage で登録
- ホバーで観測点名と震度、クリックで所属区域と震源距離まで表示

### QuakeRegionFillGL（区域塗り）
- 一次細分区域ごとの最大震度で塗り分け（fill+line）
- 区域中心に震度バッジ（icon-image・symbol レイヤー）
- 2026-08-10 のコミット 55dcc42 で HTML Marker から icon-image に移行済み

### QuakeIntensitySurfaceGL（震度の面）

観測点の震度を補間して「揺れの広がりの形」を面で敷く。点の背景であって、観測点バッジは面の上に残る。
**描き方（補間・陸クリップ・解像度・描けないときの扱い）は
[`map-rendering-spec.md`](map-rendering-spec.md) §17 が単一情報源。** ここには出す条件だけを書く。

**区域塗りとは排他。** 面と観測点ドットは同じ式（`mode === 'quake' && !aggregateByRegion &&
!lpgmActive`）を使い、区域塗りはその否定（`aggregateByRegion`）を使う。3 つが対になっているので、
**どれか 1 つの式だけを変えると排他が崩れる**。区域塗りは気象庁が発表した区域ごとの最大震度そのもので、
面は観測点からの推定なので、同じ画面に置くとどちらが発表値でどちらが推定かが混ざる。

**渡すのは `stationMarkers`**（§7）。区域の代表点（`isArea: true`）は区域の最大震度であって、その
座標の観測値ではないため、補間に混ぜない。

**寄っても面は消さない。** 視野が観測点の間隔（10〜20km）を下回ると面はほぼ単色になり読み取れる情報は
無くなるが、そこで消すと操作の途中で唐突に面が失われる。害が出るのは海への漏れのほうで、それは
陸クリップで塞いである。

**「観測点はあるのに 1 件も使える値が無い」はバリアントで起こりやすさが違う。** この状態は面を出さずに
記録する（[`map-rendering-spec.md`](map-rendering-spec.md) §17）が、DMDSS 版では構造的に起こらない——
DMDATA 経路のパーサは階級を読めなかった観測点を `points` に積まないため、`stationMarkers` へ届く点は
必ず階級表の値を持つ。標準版は「震度0」を `-1`（不明）へ寄せて残す（§4）ので、そこだけが到達しうる。

### HypocenterDepthGL（震源マーカー）
- 震源の × 印 + 震央の印 + その間を結ぶ柄 + ポップアップ
- **深さを持つ点として地下へ描く**（`gl/depthPointLayer.ts` のカスタムレイヤー）。DOM マーカーは
  地表にしか置けないため、2026-08-29 に `EpicenterGL`（`maplibregl.Marker` 実装）から移した
- クリック判定はカラーピッキング。カスタムレイヤーは `queryRenderedFeatures` にヒットしないため
  （詳細は [`map-rendering-spec.md`](map-rendering-spec.md) §16「深さを持つ点」）
