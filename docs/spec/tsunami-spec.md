# 津波情報仕様書

> 本書は**現在の実装が津波情報をどう処理するか**をまとめた仕様書。実コードと食い違う場合は実コードを正とする。
> 関連: [`data-sources-spec.md`](data-sources-spec.md) の津波電文受信、[`audio-tts-spec.md`](audio-tts-spec.md) の津波音・読み上げ。
> 読み上げには優先順位があり、津波は緊急地震速報より後・地震情報より先に読まれる（[`audio-tts-spec.md`](audio-tts-spec.md) §6）。

## 1. 概要

大津波警報・津波警報・津波注意報・津波予報を受信・表示するモジュール群。以下を扱う:

- 電文パース（DMDATA は XML、P2PQuake は JSON）
- 区域別の警報等級の統合
- 観測情報（津波観測点の波高・到達時刻）のマージ
- 解除・取消・期限切れの 3 経路の出し分け（DMDSS 版のみ完全対応）
- 海岸線描画（対象海域を色分け）
- カード表示（区域グループ・観測情報）

## 2. データフロー

```
[電文]
  DMDATA WS / REST (VTSE41/51/52) ──┐
  P2PQuake WS (code=552)  ───────────┴── parseTsunamiFromXml / convertEvent
                                                   ↓
                                            JMATsunami 型
                                                   ↓
                                    useEarthquakes.ts の handleEvent（tsunami ケース）
                                                   ↓
                                          state.tsunamis: JMATsunami[]（実質 1 件スロット）
                                                   ↓
                        ┌────────────┴────────────┐
                        ↓                          ↓
              useTsunamiLayerData          TsunamiTab
              （海岸線・観測バー）        （カード表示）
                        ↓
              TsunamiLinesGL / TsunamiObsBarsGL
```

## 3. 3 経路の解除フロー

津波が消える経路は 3 種類ある。`JMATsunami.cancelReason` で区別する（型: `'lifted' | 'retracted' | 'expired'`）。
**3 経路とも同じ流れを通る**: `cancelledAt` セット → 10 秒間の解除表示 → `purge-cancelled-tsunami` で消去。

| cancelReason | 電文条件 | 検出箇所 | 表示文言 |
|---|---|---|---|
| `lifted`（解除） | `InfoType === '発表'` かつ区域が消える | `dmdataParser.ts` の `areas.length === 0` フォールバック | 「解除されました」 |
| `retracted`（取消） | `InfoType === '取消'` | `dmdataParser.ts` の InfoType 判定 | 「取り消されました」 |
| `expired`（期限切れ） | `validDateTime` の満了 | `useEarthquakes.ts` がタイマー予約 | 「有効期間終了」 |

**表示文言の単一情報源**: `src/components/TsunamiTab/index.tsx` の `CANCEL_REASON_LABEL`（3 経路 + undefined フォールバック）。
新しい cancelReason を追加する場合はここと型定義（`src/types/earthquake.ts`）を同時に更新する。

### バリアント差

- **DMDSS 版**: 3 経路すべて出し分け可能（DMDATA 電文が `InfoType` と `ValidDateTime` を持つため）
- **standard 版**: P2PQuake API v2 スキーマに `InfoType`・`ValidDateTime` に相当するフィールドが**無い**ため、
  `cancelReason` は常に `undefined`。`CANCEL_REASON_LABEL` のフォールバックで常に「解除」表示になる

**`validDateTime` が付く条件**（気象庁仕様）: 「津波予報（若干の海面変動）のみ発表の場合」または
「警報・注意報解除後に予報のみが残る場合」の 2 パターンのみ。警報・注意報が 1 区域でも残っている間は付与されない。

### TSU-5A: standard 版の 24h フェイルセーフ（2026-08-14）

P2PQuake API 仕様上 `validDateTime` が届かないため、通常の TSU-1 経路（validDateTime 満了の
`expired` 予約）は standard 版では発火しない。津波は明示的な解除電文（`cancelled=true`）で消えるのが
正常経路だが、解除電文が届かない例外ケース（P2PQuake API 障害等）に備えて、`useEarthquakes.ts` は
**standard 版で validDateTime を持たない tsunami に対して 24h 後の `expired` 予約を積む**フェイルセーフを備える。

- 実行条件: `!isDmdss && !tsunami.cancelled && !tsunami.validDateTime`
- 予約時刻: 現在時刻から 24 時間後（リプレイの初期状態を再現する場合だけは基準が変わる。後述）
  （気象庁の実運用で警報・注意報が 24h を超えて継続することは稀。
  ただし 2011 年東日本大震災級の広域災害では大津波警報が半日以上継続した実例がある。24h を超える
  例外的な長時間継続警報の途中で表示が消える場合は、次の続報受信で予約が積み直されるため実害は
  限定的だが、意図されたフェイルセーフの限界として認識する）

**purge/insert の分岐**:
- purge（`cancelReason='expired'` 既存予約の全除去）は「これから insert する場合」または
  「明示解除電文（`cancelled=true`）を受信した場合」のみ実行する
- DMDSS で `validDateTime` を持たない非キャンセル電文（VTSE51②/VTSE52 の**観測のみ続報**）は
  正規パターン。この経路では purge も insert もスキップして既存の TSU-1 予約を温存する
  （消すと期限切れによる自動失効が二度と起きなくなる）
- 明示解除電文でも purge を実行するのは、TSU-5A の 24h 予約を「解決済み津波」に対して
  発火させないため
- P2PQuake は eventId が無く id も続報ごとに変わるため、`cancelReason='expired'` な予約は
  id/eventId 一致条件を課さず全除去する（TSU-3「常に 1 件スロット」で管理されるため 1 件残せば充分）

**時刻軸の扱い**: TSU-1（`validDateTime` 由来）は電文の**絶対時刻**、TSU-5A の 24h フェイルセーフは
`getTimeRef` 起点の**相対時刻**（`now + 24h`）。どちらの予約も、再生中でも発火時刻をそのまま待つ
（再生中の時刻軸の扱いと、かつて発火時刻を潰していた `clampToNow` の経緯は
[`settings-pwa-spec.md`](settings-pwa-spec.md) §6「再生中も予約は発火時刻を待つ」が単一情報源）。

**リプレイの初期状態を再現するときだけ基準が変わる**: リプレイは開始時刻より前に発表された電文を
まとめて「いま」流し直す（初期状態の再現。`silent` 付きで注入される）。ここで受信時刻を基準にすると、
20 時間前に出ていた津波が再生開始からさらに 24 時間残り、実際の失効タイミングとずれる。この経路
だけは**電文の発表時刻**を基準に 24h を数える。

遡り幅（24 時間）の境目では、発表から 24 時間を過ぎた電文が紛れることがある。その場合は予約を
未来に置けないため、**その場で失効させる**（`silent` 注入なので音は鳴らない）。未来の予約しか
積まない作りだと、こうした津波は失効予約を持たないまま画面に残り、再生中はライブ更新も
止まっているので消す手段が無くなる。

**既知の適用漏れ**: TSU-5A は `handleEvent` 経由でのみ発火する。初回ロード時の履歴取得
（`fetchHistory([552], 10)`）は `handleEvent` を経由せず直接 `setState` するため、フェイルセーフが
仕掛けられない。「ページを開いた瞬間に standard 版で有効な津波警報が既に存在し、以後一切続報が
来ない」というレアケースで、次のライブ tsunami 受信までフェイルセーフが働かない。実運用では
リロードするか続報を受信すれば救済される。

### 有効期限は報ではなく津波に付く

**`validDateTime` は「その報が持つ値」ではなく「その津波に定められた期限」として扱う。** 気象庁は
期限が決まった報で一度だけ ValidDateTime を載せ、以後の続報には載せない。実電文の並び（DMDATA の
archive API から取得して確認）:

| 地震 | 期限を伝えた報 | その次の報 | 解除電文 |
|---|---|---|---|
| 2024 年能登半島地震 | 01/02 10:00 VTSE41（`2024-01-02T17:00+09:00`） | 01/02 10:03 VTSE51 は持たない | 出ない |
| 2024 年日向灘地震 | 08/08 13:00 VTSE41（`2024-08-09T10:00+09:00`） | 08/08 13:02 VTSE51 は持たない | 出ない |

どちらも「警報・注意報が解除されて予報のみが残った」段階で期限が付き、直後の詳細報は持たない。
**予報のみの津波に解除電文は出ない**ため、期限を落とすとその津波を消す手段が無くなる。

引き継ぐ箇所は 3 つある。**1 つでも漏らすと「失効しない津波」ができる。**

| 場所 | 実装 |
|---|---|
| 同一イベントの続報でカードを上書きするとき | `useEarthquakes.ts` の `sameEvent` 分岐 |
| 履歴からの復元（初回ロード・リロード。バリアント共通） | `withInheritedTsunamiFacts`（`utils/tsunami.ts`）。載せるのは最新 1 報だけなので、同一イベントの過去報から拾う |
| リプレイの初期状態 | `resolveTsunamiPreWindowStates`（`services/dmdataReplay.ts`）。下記 |

**リプレイの初期状態は報ではなくイベント単位で有効性を決める。** 報ごとに「期限が過ぎているか」を
見ると、期限を伝えた報だけが捨てられ、期限を持たない最後の報が生き残る（能登で 01/02 17:00〜
01/03 10:03 のあいだを開始点にすると、期限切れの津波予報が消えないまま画面に残っていた）。
解除も同じで、解除報だけを捨てるとそれより前の発表報が残り、解除済みの津波が復活する。

- 判定は `eventId` でまとめたグループごとに行い、有効なら**全報を時刻順に流す**（EEW のように
  最新 1 報へ畳まない。津波は観測のみの続報が前報の区域を引き継ぎ、観測点はマージされるため）
- 期限を持たない報には、そのグループで最後に伝えられた期限を持たせる（持たせないと最後の報で
  失効の予約が積まれない）
- **解除による足切りは `eventId` を持つ電文にしか適用しない。** 識別子が無ければ「どの津波の解除か」を
  決められず、時刻の前後だけで落とすと、同じ 24 時間に無関係な津波が 2 つあったときに解除された側の
  時刻でまだ発表中の側まで消える。識別子の無い経路（standard 版）では解除報ごと全報を流し、照合は
  §5 の `isCancelForCurrentTsunami` に委ねる（解除の表示が 10 秒挟まる点だけが「載せない」場合との違い）

**引き継げるのは同じ取得結果に含まれる報だけ。** 履歴の取得は電文種別ごとに件数上限（10 件）が
あるため、期限を伝えた報がそれより古い位置に押し出されていると引き継げない。その場合は「予報のみ
なのに期限が無い」状態になるので、`log.warn` で記録だけ残す（画面には痕跡が出ない）。

**日時として読めない期限は採らない。** 電文を読む時点で捨て（`readTelegramDateTime`）、消費側でも
判定を `latestValidDateTime` 1 箇所に集約する（上の 3 箇所ともこの関数を通す）。**入口で捨てるのは、
時間帯を明示していない期限を消費側では捕まえられないため**（→
[`data-sources-spec.md`](data-sources-spec.md) §2「日時は 2 つの層で確かめる」）。
読めない値を残すと、その津波は「期限を持つ」顔をしたまま
以後の比較（`new Date(壊れた値) <= now` 等）がすべて偽に倒れる。表示を続ける側にも、失効の予約を
積まない側にも同時に倒れるため、消す手段の無い津波が黙って出来上がる。捨てるときは記録を残す
（画面には痕跡が出ない）。同じ理由で、失効予約に Invalid Date を積まないこと。イベントキュー自身も
積む時点で弾くが（`EventQueue.push`）、そちらは呼び出し規約の違反として `error` に残る。
**電文が期限を持たないのは正常**なので、津波側で判定して `warn` に留める。

**standard 版（P2PQuake）はこの節の対象外**（期限が届かないため。上記 TSU-5A）。ただし P2PQuake は
津波予報（`Forecast`）の区域を配信しないので、予報のみになった時点で区域が空になり**解除として届く**
——期限を知らなくても津波は消える。能登では 01/02 10:00 の電文がこれに当たる（P2PQuake の
`/v2/jma/tsunami` で確認。`cancelled: true`・区域 0 件）。

## 4. 電文パース

### DMDATA XML（`parseTsunamiFromXml`）

ライブ（WebSocket）・REST 履歴・リプレイのいずれもこの 1 本を通る。

- `src/services/dmdataParser.ts` の `parseTsunamiFromXml` 関数
- `tsunami.forecasts` から区域別の等級・波高・到達時刻を抽出
- `tsunami.observations` から観測情報を抽出
- 未知の Kind/Code は `Unknown` → 除外される（現状は既知コードが固定のため実害は限定的）
- `kind.lastKind.code` を区域ごとの**前回の等級**（`lastGrade`）として読む（`parseLastKindGrade`）。
  コードが無い区域・**未知のコード**は undefined にして判定から外す ―― `Unknown` として採ると
  「前回は津波なし」＝「新たに発表されました」という別内容の文に化けるため、未知コードでは警告を
  残す（現在の等級側が安全側の `Warning` へ倒して警告するのと同じ思想）。既知の解除コード
  （00/50/60）は「前回は津波なし」で正しい（新規発表の第一報がこの形）。用途は §10「区域単位で
  等級が動いた報」
- 予想波高が「巨大」「高い」のとき（数値化できない表記）は `jmx_eb:TsunamiHeight` の
  **`description` 属性**から読む。`condition` ではない（§9「数値にならない予想波高」）
- **原因地震（`Earthquake`）は全件読む**（`sourceEarthquakes`）。短い間に起きた地震がまとめて
  1 通で発表されることがあり、1 件目だけ読むと残りの震源が画面から消える。名前を読めないものは
  落とす（画面に出しようがないため）
  - **同一性の判定に使うのは 1 件目だけ**（`sourceEarthquakes[0]`）。`isTsunamiNewFire` は
    `eventId` が両側で欠けるとき、この 1 件目の `originTime` で代替判定する（§11「自動タブ切替」）。
    **2 件目以降は続報で増減する**ので同一性の鍵にならない
  - **続報のマージ（`mergeTsunamiReports`。§5「続報で前報から引き継ぐもの」）はこの値を
    前報から引き継がない** ので、原因地震を
    持たない報が来れば震源の行は消える。**ただし実電文にその形は無い** —— アーカイブ全期間
    （2020-11-18〜2026-09-12）の津波電文 434 通（訓練を除く）は、VTSE41 / VTSE51 / VTSE52 の
    どれも 1 通残らず原因地震を持っていた。引き継ぎを足すかどうかは、**その形の電文を観測してから**
    決めればよい（無い形に備えて引き継ぐと、気象庁が取り下げた震源を出し続ける側へ倒れる）
- 規模が数値で求まらないとき、気象庁は `jmx_eb:Magnitude` の本文を空にして `condition="不明"` を
  立て、**`description` に理由を書く**（「Ｍ８を超える巨大地震」）。`condition` は「不明」固定なので、
  それだけでは「観測が足りず不明」と「M8 を超えていて速報できない」を見分けられない。
  `magnitudeCondition` として持ち、震源の欄に出す（§9「数値にならない予想波高」と同じ場面で起きる）
- **沖合の観測から導いた沿岸への推定**（`Estimation`。VTSE52 のみ）を `estimations` として読む。
  構造は `Forecast` と同じで、`Item` ごとに津波予報区と `FirstHeight` / `MaxHeight` を持つ。
  沖合の観測点は沿岸より先に津波を捉えるため、**まだ到達していない沿岸**の到達予想と高さが入る。
  **観測値でも気象庁の発表値でもない**ので、カードでは沖合観測の実測の下に区切って並べる
- **推定の `FirstHeight/Condition`（「早いところでは既に津波到達と推定」）は到達時刻と併存する。**
  解説資料 Ⅱ.13 1-2-2-2 は Condition を常に記載し、第1波を明瞭に観測した沿岸にだけ ArrivalTime を
  足すと定めている（事例１は両方を持つ）。**「時刻を出せないときの代わり」ではない** ―― 時刻が
  あるときに隠すと、**時刻を出せる沿岸ほど注意喚起が落ちる**。カードでは時刻の下の行に出す
- **推定の `MaxHeight/Condition`（「推定中」「重要」）を読む**（`parseTsunamiEstimationCondition`）。
  「推定中」は `DateTime` と `jmx_eb:TsunamiHeight` に**代わって**出るため（Ⅱ.13 1-2-2-3）、
  読まないと `maxHeight` が作れず**波高欄が空のまま**になる。値が無い理由がこのフラグにしか残らない
- **区域の予想波高にも `MaxHeight/Condition`＝「重要」がある**（Ⅱ.11 1-1-2-4）。
  `TsunamiArea.forecastHeightImportant` として読む。**観測・推定の「重要」とは意味が違う**ので
  語を分ける（下記「「重要」の基準は電文で違う」）
- **原因地震の震源名は詳細震央地名（`DetailedName`）を優先する**（地震情報側と同じ規則）。
  国外の地震では `Name` が「中米」のように粗く、`DetailedName` に「メキシコ、チアパス州沿岸」が入る。
  津波側だけ粗い名前を出していた
- **原因地震は地震カードへも貸す。** 津波警報を伴う地震では、この震源が**地震情報より数分早く**
  届く（2024-01-01 の能登半島地震の本震は、津波警報が 16:12・地震情報が 16:16。規模の更新も
  16:22 と 16:24 で 2 分早い）。震源を持たない震度速報のカードと読み上げがこの値を借りる。
  借りる条件・契機・出どころの示し方は
  [`quake-spec.md`](quake-spec.md) §5「震源・津波区分を津波電文から借りる」が単一情報源で、ここへ写さない
- **震央補助表現（`NameFromMark`）と震源決定機関（`Source`）を読む**（Ⅱ.13 2-3-1-4 / 2-3-2）。
  前者は「御前崎の北東４０ｋｍ付近」のように震央地名より具体的に場所が分かり、日本近海で津波警報・
  注意報を発表した地震にだけ付く。後者は「ＰＴＷＣ」「ＵＳＧＳ」等で、**気象庁以外の機関が決めた
  震源要素を採用したことを示す** —— 誰が決めた値かは、値そのものと同じくらい重要
- **震源の位置要素は長周期地震動観測情報と同じ読み手を通す**（`readHypocenterAreaDetail`）。
  座標（緯度経度・深さ）・震央地名コード・震央補助表現の材料（`MarkCode` / `Direction` / `Distance`）が
  対象。**経路ごとに書き分けない** —— かつては長周期と津波が別々に読んでおり、津波だけ座標と
  材料が落ちていた。震央補助表現の文そのものは読んでいたため、**画面からは欠けに見えなかった**。
  深さは津波カードの震源の行に出す。遠地地震による津波では対応する地震情報が発表されないことがあり、
  **震源の深さがこの電文にしか無い**
  - **深さの `0` は「ごく浅い」という有効値、`-1` が「読めなかった」の目印**（`parseJmaCoord` が
    読めないとき `-1` を返す）。有限だからと通すと、深さ 1km 未満と区別が付かない値が入る
  - **地震情報（VXSE61）はこの読み手の座標を通らない** —— `Coordinate` を 2 つ持ち、度分の側を
    選び直す必要があるため（[`quake-spec.md`](quake-spec.md) §8）。座標以外の補助要素は 3 経路で共有する
- **地震発現時刻（`Earthquake/ArrivalTime`）を、地震発生時刻（`OriginTime`）とは別に持つ**（Ⅱ.11 2-2）。
  前者は観測点が地震を検知した時刻で、国外の地震で発現時刻が不明なときは発生時刻の値が入る。
  **実電文では両者が 1 分ずれる**（2026-04-20 三陸沖 M7.4 の VTSE41 で発生 16:52 / 発現 16:53、
  2026-07-03 宮古島北西沖 M6.4 で 13:04 / 13:05）。ずれるのは**電文の 1 割強**で、**規模が大きいほど・
  震源が深いほど**分の境界をまたぐ（発生から観測点が検知するまでの時間が長くなるため）。
  遠地地震ではずれない —— 発現時刻が不明なら発生時刻の値が入る、という上の規定どおり
- **画面と読み上げに出すのは発現時刻**（`sourceEarthquakeTime`。無ければ発生時刻へ落ちる）。
  地震情報側（`parseEarthquakeFromXml`）と同じ規則で、**揃えないと同じ地震が経路によって
  別の時刻で出る**。**地震単位**で数えると、地震情報と津波の両方が立った地震の 6 件に 1 件ほどが
  この形になる（電文単位の 1 割強とは母集団が違う）。
  **根拠は気象庁自身の文**。ずれた電文のうち見出し文・本文へ時刻を書いていたものは**すべて
  発現時刻**で、発生時刻を書いたものは 1 通も無かった。津波電文自身もそうしている ——
  「［海面変動の見通し］ ２０日１６時５３分に発生した三陸沖を震源とする地震の津波注意報は、……」
  （2026-04-20 の VTSE41。発生は 16:52 で、**書かれている 16:53 は発現時刻**）。
  つまり気象庁の言う「◯時◯分に発生した地震」は発現時刻を指しており、カードのラベル「発生」と
  値はここで噛み合う。
  - **同じ規則を 3 箇所が個別に実装している。** 津波カードは `sourceEarthquakeTime`
    （`utils/tsunami.ts`）、地震情報は `parseEarthquakeFromXml` の中、長周期地震動観測情報の
    読み上げは `lpgmToText`（`utils/ttsText.ts`）の中。**1 つの関数へ集約していない**ので、
    規則を変えるときは 3 箇所とも見ること（1 箇所へ寄せるなら、電文をパースする層と
    読み上げ文を組む層をまたぐ置き場所を先に決める必要がある）
  **緊急地震速報だけは発生時刻のまま** —— あちらは両方とも秒値まで有効（Ⅱ.21）で、**実測では
  全報がずれていた**（1 日分・VXSE45 の 91 通で一致 0 通・ずれ 1〜18 秒）。気象庁は緊急地震速報の
  本文に時刻を書かないためこの節の根拠（どちらを本文へ書くか）が当てられず、代わりに**あの値が
  予報円や自動解除の起点でもある**ことが決め手になっている。判断と実測は
  [`eew-spec.md`](eew-spec.md) §3「地震の時刻は発生時刻を出す」
- **`originTime` の中身は入れ替えないこと** —— `isTsunamiNewFire` が、電文の識別子が両側
  そろっていないときにこの値へ落ちて同一性を判定しており、差し替えると続報が別の津波として立つ。
  **上で選ぶのは「持っている 2 つのうちどちらを出すか」だけ**で、持っている値は変えない。
  **`isTsunamiContinuation` は `originTime` を見ていない**ので、この注意の対象外
- **マグニチュードの種別（`jmx_eb:Magnitude@type`）を読む。** `Mj` は気象庁マグニチュード、`M` は
  気象庁以外の機関が決めた値で、実電文では遠地地震による津波（`Source` を伴う電文）に `M` が現れる。
  **画面には出さない** —— 気象庁自身も本文では「Ｍ７．６」としか書かないため、種別を添えると
  発表より詳しい顔になる。電文が述べている事実として持つだけ
- **自由付加文（`Comments/FreeFormComment`）を読んでカードに出す。** 電文種別ごとの定型文
  （`warningComments`）と違い電文ごとに書き起こされる本文で、「［予想される津波の高さの解説］……」の
  ような表が入る。**地震情報・長周期地震動観測情報では読んで画面に出していたのに、津波だけ
  落ちていた。** 全角スペースの整形が入るため改行と空白をそのまま保つ（表示側は `whitespace-pre-wrap`）
- **第1波の `Revise`（「追加」／「更新」）を読む。** 最大波側（`MaxHeight/Revise`）は読んでいたのに
  第1波だけ落ちており、「追加」か「更新」かを値の変化から推し量るしかなかった。
  **新規／更新の言い分け（読み上げ）には使わないこと** —— 理由は §6「「観測中」のまま津波警報相当」
  の `maxHeightRevise` に同じ
- **最大波の観測時刻（`MaxHeight/DateTime`）を読んで観測点の行に出す**（§9「最大波の観測時刻」）
- **沖合の潮位観測点は特殊観測機器の名称（`Station/Sensor`）を持つ**（Ⅱ.13 1-1-2-2）。
  「ＧＮＳＳ波浪計」「水圧計」で、測っているものが違う。電文の語をそのまま出す
- **`Body/Text` は発表報でも入る。** 電文解説資料は「自由文形式で追加的に情報を記載する。
  **例えば**情報形態が"取消"の場合に取消しの概要等を記載する」と定めており、取消はあくまで例。
  かつては取消のときだけ拾っており、**例を定義として読んでいた**。
  **津波予報（若干の海面変動）では区域に波高も到達時刻も付かないため、いつ来ていつまで続くかが
  この文にしか無い**：

      若干の海面変動が予想される時刻は、早い沿岸で０２日１０時３０分頃です。
      　これらの沿岸では今後１日程度は若干の海面変動が継続する可能性が高いと考えられます。

  付加文 2 種（`warningComments` / `freeText`）とも別物で、同じ電文に 4 つとも入りうる。
  カードでは付加文より先に出す —— あちらは電文種別ごとの定型文（§5）と解説で、こちらはその報固有の内容。

  **続報でも消えないよう、報を跨いで引き継ぐ。** 気象庁は毎報には載せず、実電文では VTSE41 の
  半数に入るだけで続報の VTSE51/52 には 1 通も無い。引き継ぎは**有効期限と同じ 2 経路**で揃える
  ——続報の上書き（`useEarthquakes`）と履歴からの復元（`withInheritedTsunamiFacts`）。
  **片方だけに足すと、ライブ受信では出るのにリロードすると消える。**
- **取消電文では同じ `Body/Text` が取消しの概要になる。** 気象庁が書いた取り消しの理由で、
  アプリの定型文（`CANCEL_REASON_LABEL`）とは別物 —— なぜ取り消したのかはここにしか無い。
  **`Comments` ではなく `Body` 直下**（取消電文に付加文は出現しない）
- **`parseTsunamiFromXml` は電文種別（`headType`）を受け取る。** 沖合（VTSE52）と沿岸（VTSE51）で
  「重要」の基準が違うため、観測点に `offshore` を立てて持ち回す。**`districtCode` の有無で
  代用しないこと** ―― 沖合の観測点が津波予報区に属さないため結果的に一致するが、それは電文が
  区域名を空にしている副作用にすぎない

**区域を読めなかった結果を「正式解除」と取り違えないこと。** この経路は名前を読めない区域を捨てる。
気象庁は全解除のとき区域を電文から落とすため、**捨てた結果 0 件になったものまで解除と解釈すると、
電文の構造が変わったときに「津波警報が解除されました」という事実と逆の内容を発表する**（無言で
消えるより重い）。

**電文の区域を 3 つに分けて判定する。**

| 区分 | 条件 | 意味 |
|---|---|---|
| 有効 | `areas` へ積んだ | その区域に等級が出ている |
| 解除済み | 解除コード（00/50/60）が読めた（**名前の可否を問わない**） | その区域は解除された |
| 解除と言えない | 名前が読めず、解除コードでもない | まだ有効かもしれない（等級が現役と読めたものと、未知コードで分からないものの両方が入る。どちらも「解除ではない」側なので分けない） |

**解除と断定してよいのは、「解除と言えない」区域が 1 つも無いときだけ。** そこには等級が現役のまま
名前だけ壊れた区域が入りうるので、解除として通すと**まだ津波予報・注意報が出ている区域について
「解除されました」と伝える**ことになる。**他の区域に解除コードがあることは、その区域の解除を
意味するだけで、こちらについては何も保証しない。**

- 区域が電文から丸ごと消える通常の全解除は、有効 0・「解除と言えない」0 でここを通る
- 有効が 1 件でもあれば通常の津波として扱う（一部の区域だけ読めない場合は、読めた区域で成立させる）。
  読めなかった区域があった事実は、解除・非解除のどちらでも記録する
- **「解除済み」の区域のうち名前が読めたものは捨てずに `cancelledAreas` へ積む。** 有効な区域が
  残っている報では、そこが「この区域は解除された」と伝える唯一の手がかりになる
  （→ §10「解除された区域」）

**等級は `Kind/Code` で読む。`Kind/Name`・`LastKind/Name` は読まない。** どちらも同じ事実
（いまその区域に何が出ているか）を書いたもので、コードが識別子・名前がその表示。両方を読むと
1 つの事実に 2 つの出所ができ、食い違ったときに決め手が無い。アプリは等級から自前の語を組み立てて
おり（カード・読み上げで同じ語を使う）、電文の名前をそのまま出す場所も無い。

**コード体系の定義（`CodeDefine/Type`・その `@xpath` 属性）は読まない。** これは「この位置の
`Code` は津波予報区のコード表です」と電文自身が名乗る宣言で、パーサーはどの位置の `Code` が
何のコードかを実装として持っている。読んでも分岐する先が無い。

**潮位観測点のコード（`Station/Code`）は観測情報でも読む。** 予想区域の観測点では読んでいたので
扱いを揃えた。引き当ては名前で行うため画面には出さず、名前を読めなかった観測点を記録に残すのに使う。

### 観測状況を確定した時刻（`Head/TargetDateTime`）

**観測情報（VTSE51・VTSE52）でのみ読む。** この要素は種別で意味が変わり（電文解説資料 Ⅰ.（ⅱ）3）、
観測情報では「いつ時点の観測状況か」を表す。津波警報・注意報・予報（VTSE41）は観測情報ではないので
読まない。

**発表時刻とは別物で、さかのぼる。** 実電文で測ると次のとおり。

| 種別 | 発表時刻との差 |
|---|---|
| VTSE52（沖合の津波観測） | 60〜360 秒 |
| VTSE51（津波情報） | 0〜120 秒 |
| VTSE41（津波警報・注意報・予報） | 0 秒 |

最大 6 分前の値を「いまの高さ」として見せると誤解を招くので、カードの見出しに
「観測 ◯◯ 時点」を添える。**発表時刻と同じ分なら出さない** —— 同じ数字が 2 つ並ぶだけで、
「観測値は発表より前の時点のもの」という肝心の意味が薄れる（0 秒差の報も普通にある）。

**続報では前報の値を残す**（`useEarthquakes.ts`）。入るのは観測情報だけなので、**引き継がないと**
間に等級の発表が挟まった瞬間に消える。観測点そのものは `mergeTsunamiObservations` で残るため、
時点だけ落とすと表示が出たり消えたりする。

**引き継いだ結果、名乗り（`infoName`）と観測時点の出所が別の報になることがある。** 前者は
最新の報の値、後者は前報から残った値だから。等級の発表が最後に来れば「大津波警報・津波警報・
津波注意報」と名乗る報が前の観測情報の時点を持つ —— **これは正常な状態**で、電文 1 通の中身が
矛盾しているわけではない。

**`Head` 直下に限る。** 同名要素が他の位置に現れた電文で取り違えないため。

**日時として読めない値は捨てる**（`readObservationDateTime`）。表示は `formatTime` を通るが、
あちらは `new Date(...)` の結果を確かめずに時分を取り出すため、読めない値が届くと画面に
`NaN:NaN` と出る —— 例外もログも出ない。

確かめるのは **2 つ**で、発表時刻（`readReportDateTime`）と揃える。

1. `Date.parse` が有限値を返すか
2. **時間帯を明示しているか**（末尾が `Z` か `±HH:MM`）

2 が要るのは、`Date.parse` がオフセット無しの `2026-01-01T12:00:00` を**実行環境のローカル時刻**
として解釈し、**有限値を返す**から —— 1 だけでは素通りする。このアプリは利用者のブラウザで動くので、
同じ電文が端末ごとに違う時刻として画面に出る。

> **`parseTsunamiFromXml` は戻り値を 4 箇所で組み立てる。** 通常の発表報のほかに、取消・全解除・
> **「`Forecast` を持たない観測のみ」**の早期 return がある。ヘッダ部の項目を足すときは
> **観測のみの分岐を必ず含めること** —— VTSE52 と VTSE51 の観測のみ続報はそこを通るので、
> 落とすと**観測時点が最も効く電文で一度も出ない**。しかも続報のマージは `?? current` で
> 前報へ倒れるため、画面には古い時点が残るか何も出ないだけで、異常として現れない
> （2026-09-09 の敵対的レビューが実測で検出した）。

### 電文が名乗る情報名（`Head/Title`）

**`Control/Title` とは別物。** あちらは種別の固定名で、津波では末尾に記号が付く（「津波情報a」）。
こちらは**その報が何を出しているか**を表し、報ごとに変わる。

| 種別 | `Head/Title` の実例 |
|---|---|
| VTSE41 | 津波予報／津波注意報・津波予報／大津波警報・津波警報・津波注意報 |
| VTSE51 | 津波観測に関する情報／各地の満潮時刻・津波到達予想時刻に関する情報 |

**VTSE51 は性質の違う 2 つを同じ種別コードで送る。** 実装はこれを電文の構造
（`Forecast` / `Observation` の有無）で見分けており、判定に `Head/Title` は使わない。
ただし**種別コードだけでは利用者にどちらか分からない**ので、カードの行動指示の下に控えめに出す。

読み取りは `readInfoName`（`services/dmdataParser.ts`）に集約する。地震情報の遠地地震判別
（`resolveIssueType`）も同じヘルパーを通る —— 同じ要素を複数の経路が別々に読むと必ず片方が遅れる。

**緊急地震速報と長周期地震動観測情報では読むが画面に出さない。** 前者は画面の見出しを電文の区分
（`severity`）から組み立てており（[`eew-spec.md`](eew-spec.md) §3）並べると語が二重になる。
後者は実電文 8 通すべてが「長周期地震動に関する観測情報」の 1 種類で、出しても情報が増えない。

### P2PQuake（`convertEvent`）
- `src/services/p2pquake.ts` の code=552 分岐
- `JMATsunami` 型に変換（`InfoType` / `ValidDateTime` は付与されない）
- 津波の等級（`areas[].grade`）は英語のまま（`MajorWarning` / `Warning` / `Watch` / `Forecast`）で内部型に流れ、`useLiveEventHandler.ts` 等の分岐で直接 `grade === 'MajorWarning'` として判定される（`DOMESTIC_TSUNAMI_MAP` は地震情報 code=551 の `earthquake.domesticTsunami` 用で、津波の等級には使われない）。`TsunamiGrade` にない値は `Unknown` に格下げして警告を残す
- 予想波高（`areas[].maxHeight`）は「巨大」「高い」のとき数値表現が付かない。`value` を持たなくても
  `description` だけで区域行を描けるよう、`maxHeight` ごと落とすことはしない
- 区域名（`areas[].name`）が無い要素はその区域だけ落とす（海岸線データとの突き合わせキーのため）。
  解除電文は `cancelled: true` かつ `areas` が空配列で届くので、空自体は正常として通す

## 5. 状態管理（`useEarthquakes.ts` の tsunami ケース）

- `state.tsunamis: JMATsunami[]` は**実質 1 件スロット**（別 eventId の津波が来ると無警告で置換）
- 新規・非キャンセル: `sameEvent` なら更新、そうでなければ配列を丸ごと置換
- キャンセル（3 経路のいずれか）: `cancelledAt: now` と `cancelReason` をセット、10 秒後に purge をキューイング
- 期限切れ検出: `validDateTime` を見て、未来なら expired キャンセルを予約（期限は報ではなく津波に付く事実として引き継ぐ。§3「有効期限は報ではなく津波に付く」）

### 続報で前報から引き継ぐもの

続報のカードは**新しい報を土台に組み立てる**ので、新報が持たない項目は明示的に引き継がないと
落ちる。落ちても例外もログも出ず、次の報で戻ることさえあるため、画面を見ていても気づけない。

**規則の置き場所は `mergeTsunamiReports`（`utils/tsunami.ts`）1 箇所。** ライブ受信
（`useEarthquakes` の tsunami ケース）も履歴からの復元（`withInheritedTsunamiFacts`）も
この関数を通る。後者は古い報から順に畳み直すだけで、規則そのものは持たない。

> **規則を 2 箇所に書くと必ずずれる。** かつては両方が同じ引き継ぎを各自で書いており、
> 「同じものをここでも引き継ぐこと」と説明文で戒めるだけだった。結果、項目を足すたびに
> 片方へ入れ忘れ、**ライブ受信では出るのにリロードすると消える**という形の欠落が
> 繰り返し見つかった（レビュー 3 巡で別々の項目が 3 回）。**新しく引き継ぐ項目を足すときは、
> `mergeTsunamiReports` と下の表だけを直す。**

引き継ぐかどうかは項目ごとに違う。**「新報が持っていない」の意味が項目で違う**からで、
次の 4 つに分かれる。

| 引き継ぎ方 | 項目 | 理由 |
|---|---|---|
| 新報が持たなければ前報（`?? current`） | `bodyText` / `observationDateTime` / `freeText` / `validDateTime` / `estimations` | 特定の種別の電文にしか入らない。挟まった別種別の報で消える |
| キー単位でマージ | 観測点（`observations`） | 観測点ごとに upsert（§6）。**沿岸と沖合は別の観測点集合**で、実電文では沿岸 19 点・沖合 9 点が完全に分かれていた。最新報だけを採ると片方が丸ごと消える |
| 主題ごとに束ねる | 固定付加文（`warningComments`） | 種別ごとに**別の話**をする。上書きし合うと最後の報の注記しか残らない |
| 新報が正。ただし一部だけ継ぐ | 区域（`areas`） | 顔ぶれと等級は新報が正。区域の中の潮位観測点だけ条件付きで継ぐ |
| 新報が正（区域と同じ分かれ目） | 解除された区域（`cancelledAreas`） | 区域を伝えている報が来たら、その報が載せなくなった解除は消す。気象庁が言い続けている間だけ出す形なら、寿命をアプリ側で決めずに済む（実電文では解除の次の報にも同じ区域が載る）。区域を伝えていない報で消すと、一部解除の直後に観測情報が 1 通届いただけで「解除」の枠が消える |
| 引き継がない | `infoName` | その報が何を出しているかの名乗り。引き継ぐと、満潮時刻の報を見ているのに「津波警報・津波注意報・津波予報」と名乗る |

**沿岸への推定（`estimations`）を落とさないこと。** 入るのは沖合の津波観測（VTSE52）だけで、
実電文では最後の VTSE52 のあとに津波情報が 20 通以上続く。引き継がないと次の報が届いた瞬間に
推定が消えるが、**その推定を導いた沖合の実測はマージで残る**ので、画面には「実測はあるのに
そこから導いた推定だけ無い」という食い違いが出る。VTSE52 は推定を累積で全件載せるので、
区域単位のマージではなく最新の報のものを丸ごと採る。

**手当てが要る経路は 2 つで、3 つ目は要らない。** 有効期限は「続報の上書き・履歴からの復元・
リプレイの初期状態」の 3 箇所そろえる規約になっているが（§3「有効期限は報ではなく津波に付く」）、
ここで挙げた項目は**最初の 2 つだけ**でよい。リプレイの初期状態（`dmdataReplay.ts` の
`filterPreWindowEvents`）は最新 1 報へ畳まず**全報を順に流す**作りで、流れた報はライブ受信と
同じ経路を通るため、引き継ぎがそのまま効く。有効期限だけが特別扱いなのは、**再生を始める前に
「その津波が既に終わっているか」を決める必要がある**から —— 報を跨ぐ事実のうち、判定に先立って
要るのはこれだけ。新しく引き継ぐ項目を足すときも、同じ理由でリプレイ側は触らなくてよい。

#### 区域の潮位観測点（`mergeTsunamiAreas`）

**区域そのものをキー単位で upsert してはいけない。** 実電文では津波警報等（VTSE41）も
津波情報（VTSE51）も**区域一覧を毎回全量で載せ**、一部解除は「区域が電文から消える」形で届く
（2026-04-20 三陸沖の実電文で 13 → 17 → 14 → 8 と推移し、VTSE41 と直後の VTSE51 は
常に同じ顔ぶれだった）。upsert にすると、消えた区域が前報から復活して解除済みの等級を出し続ける。

一方 `stations`（満潮時刻・津波到達予想時刻）を運ぶのは VTSE51 だけで、VTSE41 は区域一覧しか
持たない。新報の区域をそのまま採ると、**警報が届いた瞬間に満潮時刻が画面から消える**
（実電文では次の満潮情報まで 24 秒欠けていた）。そこで区域コード・区域名で前報を引き当てて継ぐ。

**継ぐかどうかは電文種別で決める。中身では決められない。**「新報の区域に観測点が無い」には
2 通りある。

| 形 | 意味 | 扱い |
|---|---|---|
| 運ばない種別だから無い（VTSE41） | その報は観測点を載せる種別ではない | **継ぐ** |
| 運ぶ種別なのに無い（VTSE51） | 気象庁が発表をやめた | **継がない** |

後者は等級が津波予報まで下がったときに実際に起きる（実電文では 14:45 に全区域が津波予報へ
落ちた時点で、VTSE41 も VTSE51 も観測点を 1 件も載せなくなった）。一律に継ぐと、解除間際の
画面に古い到達予想時刻が残る。判定材料は `JMATsunami.carriesForecastStations` で、パーサーが
電文種別から立てる（`TsunamiObservation.offshore` と同じやり方）。種別を判定できない経路
（P2PQuake）は安全側＝継ぐ。

**判定は報の単位で、区域の単位ではない。** 「等級が現役のまま、その区域だけ観測点が落ちた」
という形があれば報単位の判定では取りこぼすが、実電文 31 通を区域ごとに並べて数えたところ、
**観測点が 0 件へ落ちた遷移 8 件はすべて等級の降格（津波注意報 → 津波予報）に伴うもの**で、
等級が変わらないまま落ちた区域は 1 件も無かった。警報・注意報なのに観測点を持たない区域も
1 件も無い（津波予報の区域は最初から持たない）。

**「等級が変わらないまま観測点が落ちたら継ぐ」という条件は置かない。** 上の数え上げは
相関が 100% だったが、**等級は「その種別が観測点を運ぶか」の代理値**でしかなく、機構は種別の
側にある。実際、津波警報等は区域を増やしながら等級を動かすために出る報なので（実電文では
13 → 17 の報がまさにそれ）、等級の変化を条件にすると**主経路でこの引き継ぎが外れる**。
条件を増やすと誤ったときの倒れ方も変わる —— 「消える」から「古い到達予想時刻が永久に残る」へ、
つまり気づきにくい側へ倒れる。等級を条件にするなら、実例を見てからにする。

#### 固定付加文は主題ごとに束ねる（`mergeTsunamiWarningComments`）

固定付加文（`Comments/WarningComment`）は**電文種別ごとに別の話をする**。同じ地震の連続報から
拾った実例（2026-04-20 三陸沖）:

| 種別 | 主題 | 内容 |
|---|---|---|
| VTSE41 津波警報等 | 等級に対する行動の呼びかけ | 「ただちに避難してください。＜津波警報＞…」 |
| VTSE51 満潮時刻 | 満潮との重なり | 「津波と満潮が重なると、津波はより高くなりますので…」 |
| VTSE51 津波観測 | 観測値の読み方 | 「場所によっては、観測した津波の高さよりさらに大きな津波が到達しているおそれがあります。」 |
| VTSE52 沖合観測 | 沖合と沿岸の差 | 「沖合での観測値であり、沿岸では津波はさらに高くなります。」 |

1 つの枠を報どうしで奪い合わせると、最後に届いた報の注記しか残らない。実際、津波警報の
**避難の呼びかけが 1 分後の満潮時刻の報で消えていた**。そこで主題の鍵を添えて配列で持ち、
`observations` と同じく同じ鍵は置き換え・別の鍵は追加する。

**鍵は電文種別。ただし VTSE51 だけは情報名（`Head/Title`）も含める** —— 気象庁はこの種別で
「各地の満潮時刻・津波到達予想時刻に関する情報」と「津波観測に関する情報」を名乗り分けており、
付加文の中身も別物だから（§4「電文が名乗る情報名」）。**他の種別で情報名を鍵に含めない**のは、
津波警報等の情報名が等級とともに変わるため（実電文で「津波警報・津波注意報・津波予報」→
「津波注意報・津波予報」→「津波予報」と 3 回変わった）。含めると、解除済みの等級の避難呼びかけが
別の鍵として画面に残る。

並びは到着順ではなく主題の固定順（`WARNING_COMMENT_ORDER`）。途中から受信を始めたとき
（アーカイブ再生・起動が遅れた場合）でも、いちばん重い等級の呼びかけが先頭に来るようにする。
**表に無い鍵は末尾へ回して落とさない** —— 気象庁が情報名を増やしても消えない。

**古くなった主題を落とす仕組みは置いていない。** いちど現れた満潮・観測・沖合の注記は、
津波が解除されるまでカードに残る。実電文では気象庁が等級の降下に合わせて注記そのものを
書き換えて送り続けており（津波情報の注記は解除間際に「現在、大津波警報・津波警報・津波注意報を
発表している沿岸はありません。」へ変わる）、残った注記が現状と食い違う形は観測できなかった。
沖合の注記だけは発表が途絶えた後も残るが、**その注記が説明している沖合の観測値もカードに
残り続ける**ので、指しているものは消えていない。失効の規則を足すのは、食い違う実例を
見つけてからにする。

> **文面のほうが実装より正しいこともある。** この節の「区域を伝えていない報では前報の区域を
> 残す」は、履歴からの復元では実装されていなかった —— コメントが「ライブ側と同じ扱い」と
> 書いていたのに、実装だけが追いついていなかった。レビューの観点は「矛盾しているのは実装か文面かを
> 見分ける」だが、**文面が正しくて実装が遅れている側**もある。食い違いを見つけたら、どちらが
> 事実かを実電文と実装の両方から決めること。文面を実装に合わせて書き下げると、直すべきものが消える。

**引き継げなかったことの記録も置いていない。** 有効期限には「期限を伝えた報を取得できていない
可能性」の警告があるが（`useEarthquakes`）、観測点と固定付加文は**持たないのが正常な状態**が
ふつうにある（津波予報の区域は観測点を持たない／途中から受信を始めれば等級の呼びかけは無い）。
同じ形の警告を置くと平常時に鳴り続ける。

> 付加文が何段も並ぶことになるので、カードのどこに置くかは別途見直す（現状は区域一覧・
> 観測点一覧より下）。

### 解除電文と表示中の津波の照合

解除電文が「いま表示している津波のもの」かを判定する規則（`isCancelForCurrentTsunami`）。

**カードの状態更新と、観測点の記憶を落とす判断（§10）の両方でこの規則を使う。** 片方だけが
照合すると、カードは解除に切り替わったのに観測点の既読だけが残る（あるいはその逆）。

> **照合の相手はそれぞれ違う。** カード側は自分が持つ表示中の津波を見るが、記憶側は**自分が
> 受信した直前の津波**を見る。記憶側が App の表示中リストを見ると、同一 tick（React の 1 回の
> レンダー・状態更新サイクル）に複数の電文がまとめて捌けたとき——アーカイブ再生の追いつき、
> 長時間バックグラウンド後の復帰——に取り残された古い値と照合し、届いたばかりの津波への解除を
> 「別イベントの解除」と誤判定する。この「直前の津波」も、観測点の記憶と同じくリセット・
> リプレイ復元の対象に含める。

- **双方が `eventId` を持つときだけ厳密に照合する**。別 eventId の解除は無視する（報番号が違っても
  同一イベントなら解除できるよう、`id` 全体ではなく `eventId` で見る）
- **どちらかが `eventId` を持たない場合は、発表時刻の前後だけで足切りする**。表示中の津波より古い
  発表時刻の解除は「別イベントの遅延到達」とみなして無視し、それ以外は受け入れる。1 件スロットのため、
  同一性を確かめられないまま受け入れると別イベントの遅い解除で現在の津波が消えてしまう。
  時刻が読めないときは足切りしない（解除を落とす方が害が大きい）

> かつては `eventId` が無い場合に `id` の完全一致を求めていた。しかし standard 版（P2PQuake）の
> `code=552` は `eventId` を持たず、`id` は電文ごとの文書 ID（`str(raw.id)`）なので**発表電文と解除電文で
> 必ず異なる**。このため standard 版では実運用の解除が常に捨てられ、音・読み上げ・タブ切替だけが
> 「解除」と伝えてカードは TSU-5A の 24h フェイルセーフまで残っていた（`handleEvent` は state 更新の
> 成否に関わらず `onLiveEvent` を呼ぶため、音と表示が食い違う）。
> 長く気づかれなかったのは、テストボタンが解除電文に発表電文と同じ `id` を使い回しており、
> **テストデータの側が実運用と違っていたために `id` 照合が成立していた**ため
> （→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7「実電文の形に合わせる」）。

**既知の課題**:
- expired 予約が同一 eventId の後続更新で取り消されず、10 秒表示が早期打ち切りされる可能性
- `purge-cancelled-tsunami` アクションが識別子を持たないため、連続キャンセルのレースで前の解除表示が
  早期消去される可能性

## 6. 観測情報のマージ（`mergeTsunamiObservations`）

`src/utils/tsunami.ts` の関数。津波観測点の連続電文で、同一観測点の観測値を最新に更新する。
区域と固定付加文のマージは別（§5「続報で前報から引き継ぐもの」）。

- キーは `${o.districtCode ?? o.districtName ?? ''}|${o.name}`（区域コード or 区域名 と観測点名を `|` で連結。同じ区域内の複数観測点を区別するため）
- 同一キーで既存があれば更新、なければ追加
- `over` フラグは `description` 属性の文言に「以上」が含まれるかで立てる（XML には真偽値に
  相当する属性が無いため）。属性の形を確かめた範囲と、この判定が空振りしうる条件は
  下記「観測波高の「以上」」に集約する
  - standard 版（P2PQuake）は観測点データ自体を持たないため、この節の内容は DMDSS 版限定

### 観測波高の「以上」

気象庁は、観測施設の観測可能な範囲を超えた観測値・機器が被災した観測値を「○m以上」の形で
発表する。電文にはこれを表す真偽値が無く、`description` 属性（気象庁が組んだ表示文字列。
全角で「０．５ｍ」等）の文言に「以上」が含まれるかで印を立てる。

**「以上」という語彙は、この地震の電文で確認できている。** 2024 年能登半島地震の津波電文 56 通
（下記 §10 と同じ集合。01/01 16:12〜01/02 10:03 発表・取消は 0 通）のうち、観測点を運ぶ津波情報
（VTSE51）49 通に含まれる `TsunamiHeight` 要素 2104 個を走査したところ、46 個が「以上」を含んで
いた。すべて輪島港の `description="１．２ｍ以上"` で、01/01 16:35 の報から以後の全報に現れる。
表記は `${value}ｍ以上`（全角）で、判定が見ている語彙と一致する。**確かめたのはこの地震だけ。**
別の表記（「〇m超」等）を観測したことはないが、他の地震で別の形が使われていないことまでは
確かめていない。

**値は据え置きのまま、`over` だけが後から付く。** 輪島港は 01/01 16:29 の報で「１．２ｍ」、
16:35 の報で「１．２ｍ以上」となり、`jmx_eb:TsunamiHeight` の本文はどちらも 1.2 のまま動かない
（`MaxHeight/Revise` も付かない）。潮位計が振り切れて真の波高が読めなくなった、といういちばん
見せたい変化が、数値の上では何も動かない形で届く。したがって:

- **「変化したか」を数値の等値比較で判定しないこと。** `over` を値と別に見るのは 3 経路とも共通だが、
  **問いの向きは同じではない**
  - 読み上げ（`hasObservedHeightRisen`）とカードのバッジ・自動スクロール（`updatedObs552` の判定）は
    「**深刻になったか**」を問うので、`over` が**付いた**ときだけ通す
  - 地図のカメラ追従（`hasObservedHeightChanged`）は「**動いたか**」を問うので、`over` が外れる向きも
    通す（下方修正でもその観測点を見せ直す）。**外れる向きは上記の走査では観測していない。**
    起きれば「真の波高が判った」という同じ値打ちの更新にあたるので、通す側へ倒してある
  - 値だけを見ていたころは、読み上げが「１．２メートル以上」と言い観測棒が点滅する一方で、
    地図だけがその観測点へ寄らなかった
- 実機で確かめる入口は設定タブの「変化の小さい続報テスト」（2 通目）。値が変わらない形なので
  「値の変化で判定する」仕組みでは作れず、テストボタンにしか無い

**この表記が示すのは真の波高の「下限」だけで、上限は無い。** 2011 年の東北地方太平洋沖地震では
潮位計がこの形で飽和・被災し、発表値を大きく上回る津波が実際に来ていた。したがって:

- **並び順では値の大小より `over` を先に見る**（`compareObservedHeightDesc`）。「8.5m以上」を
  「9.0m」の下に置くと、より深刻でありうる観測を過小評価してしまう。この規則はカードの区域の
  並び（`sortAreasForCardDisplay`）と読み上げの観測点の選抜
  （[`audio-tts-spec.md`](audio-tts-spec.md) §4）で共有する
  - 値が小さい `over` も確定値の大きな観測より上に来るが、観測可能範囲がそこまで小さい潮位計は
    無いため実運用では起きない
- **表示文字列は `overSuffixedHeight` を通す。** カード・地図のツールチップ・読み上げの 3 経路
  すべてで通すこと（片方だけだと地図には「以上」が出てカードには出ない食い違いになる）。
  `description` は既に「以上」を含むため記号や語を重ねると「>8.5m以上」になる。この関数は
  含まないときだけ補う
  - **観測点の `description` は数値だけで組む。** 電文の波高には「上昇中」を表す属性が付くことが
    あるが、それを表示文字列へ入れると数値が消える（画面と読み上げが「上昇中」しか示さなくなる）。
    水位が上昇中であることは観測状態として別に持つ（下記「観測状態」）
  - **数字を含まない `description` には補わない。** 数値化されない語（「巨大」「高い」）が入るのは
    区域の予想波高で、そちらは `over` を持たないため現状ここへは来ない。経路が増えたときの
    歯止めとして残してある（機械的に繋ぐと「巨大以上」という読めない語になる）
  - この数字の判定は**全角も数える**。電文由来の文字列がそのまま入る経路では全角が来うる。
    ASCII だけを見るとその表記で「以上」が黙って落ちる
- **波高が数値として読めなければ観測値ごと落ちる**（`height` が `undefined` になり `over` も消える）。
  表示・並び順・読み上げのどこにも痕跡が残らないため、`over` が立っていた場合だけ警告を出す
- **`description` が空の観測点は、波高の数値から表示文字列を組む**（予想波高側と同じ扱い）。
  表示・読み上げは `description` しか見ないため、空のまま通すと利用者から波高が消える
  （カードの数値・地図の観測棒のツールチップ・読み上げの数値部分がすべて空になる）。
  あわせて「以上」を判定する手がかりが無くなったことを記録に残す —— XML 経路では
  `description` が `over` の唯一の情報源なので、黙って落とすと「以上」が通常値として扱われる
- **アプリ側で言い換えない。** 「○m超」「測定限界」等に置き換えると、気象庁の発表・報道と
  食い違って利用者が別の情報と受け取る

### 波高の表示文字列は半角へ揃える

気象庁の原文は全角（`description="０．２ｍ未満"` / `"８．５ｍ以上"`）。XML 経路はこれを
**数字・小数点・単位だけ半角へ直して**渡す（`dmdataParser` の `toHalfWidthHeightDesc`）。
前後の空白も落とす（実電文に先頭が全角空白の `　１ｍ` があった）。

- **半角にする理由。** 画面と読み上げはずっと半角で出してきた。全角のまま通すと、数値が
  読み取りにくくなるうえ、`description` を持たない電文で数値から組む表記（`${value}m`）と
  同じ画面に全角と半角が混ざる
- **「未満」「以上」「超」「巨大」といった語は残す。** 数値だけで組み直すと、津波予報
  （若干の海面変動）の `０．２ｍ未満` が `0.2m` に化けて意味が変わる。数字を含まない
  `巨大` `高い` はそのまま通る
- **`over` の判定と記録は生の属性値を見る。** 半角へ直した文字列は表示に使うだけで、
  「電文が何と言ったか」を判定から見えなくしない

### 観測状態（欠測・微弱・観測中・重要・上昇中）

気象庁は 2025-07-24 から、障害等で観測できていない観測点を**欠測**として発表している。それ以前は
観測できない地点の情報が発表されず、「津波が無い」のか「測定できていない」のかを区別できなかった。

**「まだ値が出ていない（観測中）」と「もう観測できない（欠測）」を、波高の有無で見分けてはいけない。**
どちらも数値を持たないため、`height` の有無で振り分けると欠測の観測点が「到達確認・波高は観測中」
として扱われる ―― 気象庁がこの運用変更で解消しようとした取り違えを、アプリ側で作り直すことになる。
見分けは `isObservationMissing`（`src/utils/tsunami.ts`）だけを通す。

電文での表れ方（気象庁「地震火山関連 XML 電文解説資料」Ⅱ.12）:

| 語 | 出る場所 | 意味 |
|---|---|---|
| 欠測 | `FirstHeight/Condition`・`MaxHeight/Condition` | その項目のデータが得られていない |
| 第１波識別不能 | `FirstHeight/Condition` | 津波は観測したが第1波の到達時刻が不明瞭 |
| 微弱 | `MaxHeight/Condition` | 津波注意報の区域で、観測した最大波が非常に小さい |
| 観測中 | `MaxHeight/Condition` | 予想される高さに比べ十分小さく、数値を発表していない |
| 重要 | `MaxHeight/Condition` | これまでの最大波が基準を超えた（**基準は電文で違う**。下記） |
| 上昇中 | 波高の要素の属性 | 水位が上昇中 |

読み取りで外せない点:

- **`Condition` は複数の内容を全角スペースで併記する。** 「重要 欠測」「微弱 欠測」「観測中 欠測」の
  事例がある。文字列の完全一致では読み取れないので、分割して照合する
  （`parseTsunamiObservationCondition`）。**排他の値として持たないこと**
- **欠測は波高の数値と同時に来る。** そのときの数値は「これまでの最大波の高さ」＝欠測になる前に
  観測できた値で、以後は観測できていない。**捨ててはいけない**（大津波警報の基準を超えた値が
  「重要」と併記されることもある）。表示・読み上げでは「これまでに観測した値」であることを添える
- **DMDATA の JSON はこれを 2 つに分けて配る**（`condition` と `status`）。呼び出し側で空白を挟んで
  繋ぎ、XML と同じ読み取りへ渡す（経路ごとに判定を書き分けない）
- **アプリ独自に前の値を持ち回さない。** 欠測になった観測点の波高を画面に残し続けると、観測できて
  いない値を発表し続ける形になり、危険を過小に見せる（2024 年能登半島地震では地盤隆起で観測不能に
  なった観測点があった）。残すのは電文がその報で載せてきた値だけ

画面での見せ方:

- カードのバッジは**併記する**（`observationBadges`）。実測／到達確認と欠測は同時に成り立つため、
  1 つの欄に押し込むとどちらかが消える。「重要」は語のままでは伝わらないので意味の側を書く
  （下記「「重要」の基準は電文で違う」）
- **「到達確認」を第1波が欠測の観測点に付けない**（到達したかどうかも判っていない）。一方
  **第１波識別不能には付ける** ―― 気象庁の定義は「津波を観測したものの到達時刻が不明瞭」で、
  到達そのものは確定している。時刻の欄には理由を出す（`observationArrivalFallbackText`）
- 波高の欄（`observationHeightText`）は数値／微弱／観測中のいずれか。**値を持たない欠測のときだけ
  空**にする（バッジが既に言っているため）。数値を持つ欠測ではその数値を出す ―― 前段のとおり、
  それは欠測になる前に観測できた値で捨ててはいけない。**「観測中」を欠測へ流用しない** ――
  値が出る見込みだと読める
- 地図の印は到達確認と**別**にする（§8「欠測マーカー」）

読み上げでの扱いは [`audio-tts-spec.md`](audio-tts-spec.md) §4「欠測は到達確認と別の文で伝える」。

### 取消しの理由は電文にしかない

取消電文（`InfoType` = 取消）の `Body/Text` には、気象庁が書いた取り消しの概要が入る。
アプリの定型文（「この津波情報は誤って発表されたため取り消されました」）は**何が起きたか**しか
言っておらず、**なぜ取り消したのか**はこの本文にしか無い。バナー・取消オーバーレイ・読み上げの
3 つに出す（読み上げの上限は [audio-tts-spec.md](audio-tts-spec.md) §4）。

**地震情報・EEW とまったく同じ構造**で、状態更新の落とし穴も共通
（→ [quake-spec.md](quake-spec.md) §8「取消しの理由は電文にしかない」）。津波は
`{ ...既存, cancelledAt, cancelReason }` の形で書かれていたため、`cancelText` が黙って落ちていた。

### 「観測中」のまま津波警報相当

沖合の潮位観測点は、大津波警報の区域に対応していて沿岸で推定される高さが 3m 超に届かないとき、
`Condition` を「観測中」にしたまま数値を出さない。そのとき **`Revise` に「更新」と書くことで、
津波警報に相当する津波（1m 超）を観測していることを示す**（電文解説資料 Ⅱ.13 1-1-2-2-2）。

**この信号は値の変化からは導けない。** 「観測中」の中身は変わりようがない（`DateTime` も高さも
出ない）ので、アプリの「値が変わったら更新」という代理指標では原理的に捉えられない。電文が
直接言っているもの（`TsunamiObservation.maxHeightRevise`）を読むしかない。判定は
`isWarningLevelWhileObserving`、画面はバッジ「津波警報相当を観測」（**「〜の基準超」と同じ形にしない** —— 上の「重要」の 2 つは実測値が基準を超えた事実で、意味の階層が違う。同じ行に並ぶため、形を揃えると「弱いほうの基準だけ超えた」と読める）、読み上げは専用の文
（[audio-tts-spec.md](audio-tts-spec.md) §4「「観測中」のまま津波警報相当は別の文で伝える」）。

**沿岸の観測点には当てない。** 同じ「観測中」でも、資料が注意を書いているのは沖合の側だけ。
仕組みとしては沿岸でも成り立ちそうに見えるが、電文が定めていないことを先回りして読むと、
**気象庁が言っていない警告をアプリが作る**ことになる。

**`Revise` を新規／更新の言い分けに使わないこと。** 読み上げの境界は「前に声にした波高があるか」
で、`Revise` が言っているのは「気象庁が何を発表したか」。別の軸なので混ぜると、読み上げが割り込みで
鳴らなかった観測点を「更新」として扱う。

### 「重要」の基準は電文で違う

気象庁は「重要」を 4 つの場所に付けるが、**どれも基準が違う**。語のまま「重要」と出しても何が重要
なのか伝わらないので意味の側を書くが、そのとき基準を混ぜると、実際より軽い／重い印象を与える。

| 出所 | 解説資料 | 基準 | 画面に出す語 |
|---|---|---|---|
| 沿岸の潮位観測点（VTSE51） | Ⅱ.12 1-2-2-2 | 大津波警報のみ | 大津波警報の基準超 |
| 沖合の潮位観測点（VTSE52） | Ⅱ.13 1-1-2-2-2 | 大津波警報・津波警報 | 大津波警報・津波警報の基準超 |
| 沿岸への推定（VTSE52） | Ⅱ.13 1-2-2-3 | 大津波警報・津波警報 | 大津波警報・津波警報の基準超 |
| 区域の予想波高（VTSE41/51） | Ⅱ.11 1-1-2-4 | **意味が違う** | 予想の高さを数値で発表・引き上げ |

上 3 つは `importantBadgeText(offshore)` が引き受ける（沿岸か沖合かは `TsunamiObservation.offshore`）。
**4 つ目だけは別物** ―― 実際に観測・推定した高さではなく、**大津波警報の区域で予想波高が初めて
数値になった、または上方修正された**ことを指す（`forecastHeightImportantBadge`）。同じ語で出すと
取り違える。**「更新」とだけ書かないこと** ―― この印は引き下げでは付かないので、方向が伝わらない
語では赤い色と釣り合わない。逆に「引き上げ」だけにすると、「巨大」から「10m超」へ数値になった
だけの報まで「高さが上がった」と言うことになる。

## 7. 区域と海岸線

- 電文の区域コード（`areas[].code`）に対応する海岸線ライン座標を `public/data/tsunami-zones.json` から引く
- ソースは気象庁 予報区等 GIS データ（`Ichihai1415/JMA-GIS-GeoJSON`）
- 生成スクリプト: `scripts/build-tsunami-zones.mjs`

**取得に失敗したとき**: 海岸線は描かれない。このデータでしか描けないため代替表示は無く、
警報・注意報の範囲が地図から消える（観測点の波高バーは別データなので残り、カード・一覧にも
影響しない）。海岸線の座標はカメラの自動フィット対象でもあるため、対象海域への自動フィットも
効かなくなり、観測点の位置または日本全体の表示に落ちる（[`map-rendering-spec.md`](map-rendering-spec.md) §6）。

本データを要求するのは海岸線描画の 1 箇所だけなので、区域データ（[`quake-spec.md`](quake-spec.md) §7.2）
のような再取得による復帰も起きず、ページを再読み込みするまで戻らない。失敗は `console.error` に
「海岸線が出ない」旨で出力される。

### 描画（`TsunamiLinesGL`）

- 等級ごとの色・線幅は `src/utils/tsunamiStyle.ts` で定義
- 大津波警報（紫）・警報（赤）・注意報（橙）・予報（シアン）で色分け
- 点滅アニメーション: `requestAnimationFrame` で `line-opacity` を周期変化
- MapLibre の paint プロパティは既定で 300ms トランジションが付くため、`line-opacity-transition:
  { duration: 0 }` を明示的に設定して点滅の途切れを防ぐ

## 8. 観測点バー（`TsunamiObsBarsGL`）

- 各津波観測点に「実測波高を高さで表した棒」を地図上に立てる
- 高さは波高に比例（5m で上限に達する線形。下限 8px・上限 400px でクランプ）。
  地図アイコン倍率を掛ける範囲は [`settings-pwa-spec.md`](settings-pwa-spec.md) §2
- 座標は `public/data/tsunami-obs-coords.json` から引く。ここに無い観測点は棒が立たない
  （カード側には実測値が出るため、地図と一覧で見え方が食い違う）
- ツールチップの波高は `overSuffixedHeight` を通す（「以上」の扱いは §6「観測波高の「以上」」）。
  **棒の高さは `value` だけで決まり「以上」を区別しない**（飽和値までしか伸びない）
- 色は気象庁の津波観測階級で 4 段。段と色は
  [`Map/gl/tsunamiObsBarStyle.ts`](../../src/components/Map/gl/tsunamiObsBarStyle.ts) が単一情報源で、
  **地図の凡例も同じ表を読む**。**等級の色（`utils/tsunamiStyle.ts`）とは別物**で、凡例では別の
  ブロックへ分けている（理由は [`map-rendering-spec.md`](map-rendering-spec.md) §20）
- 更新は観測点名をキーにした差分更新（HTML マーカーを使い回して中身だけ書き換える）。
  受信のたびに全マーカーを作り直すと、発報中の高頻度な更新で棒が一瞬消えてちらつく
- カメラがこのバーへ寄る条件と俯瞰への帰り方は [`map-rendering-spec.md`](map-rendering-spec.md) §6

### 白フチと影（`BAR_RING`）

**棒は必ず津波予報区の海岸線（`TsunamiLinesGL`）の上に立つ。** 観測点は海岸線上にあるため。そして
**両者の色は見分けが付かない**——津波警報の線と 1m 以上の棒は `#ef4444`、津波予報の線と 0.2m 未満の
棒は `#22d3ee` で**値まで同じ**。津波注意報の線（`#f59e0b`）と 0.2m 以上の棒（`#f97316`）は値は違うが、
並べても区別できない。どちらも気象庁の配色（等級色と観測階級色）なので**色は動かせず、輪郭で分けるしかない**。
海岸線が入り組んだところでは太線（注意報 4px〜大津波警報 6px ×倍率）が折り返して塊になるため、
輪郭が無いと棒の根元がどこから始まっているか読めなくなる。

**丸バッジの家族**（震度観測点・揺れ検知点・到達確認マーカー・欠測マーカー）は「塗り＋白フチ＋影」を
共有しており、**この地図で観測棒だけがそれを持っていなかった**。下記の寸法はその家族へ揃えたもの。

- **フチは外側へ引く。** 内側だと色の芯が `BAR_WIDTH` から細り、波高が持つ色の面積が減る
  （等倍で 6px → 3px）。外側なら芯は `BAR_WIDTH` のまま保たれる
- **太さは `BAR_FOOT` の半分。** 等倍では外形（`BAR_WIDTH + 2 * BAR_RING`）が脚の幅
  （`BAR_WIDTH + BAR_FOOT`）と一致し、**足元の専有幅が変わらない**。到達確認マーカーの直径も
  同じ 9px なので、地図に並ぶ 3 つの印（棒・到達確認・欠測）の足元がそろう
- **倍率で太らせないが、細らせる。** 太らせないのは枠線・影を装飾のヘアラインとして扱う方針
  （[`settings-pwa-spec.md`](settings-pwa-spec.md) §2「主な項目の補足」）。細らせる理由と、芯の取り分を
  外形の 2/3 に保つ考え方は下記「到達確認マーカー」と同じ（あちらが `MIN_CORE_RATIO` を持つ）
- **下端にはフチを引かない。** 脚に接する辺で、白線が入ると棒と台座が分断されて見える
- **画面では 1px へ丸められる。** ブラウザは `border-width` を整数のデバイスピクセルへ丸めるため、
  等倍・`devicePixelRatio` 1 の端末では実測 1px（外形は `box-sizing: border-box` なので指定どおり
  9px のまま。丸めが効くのはフチと芯の配分だけ）。共有カードの描き直しは丸めを受けないので 1.5px で
  描き、**この 0.5px は画面と画像で一致しない**。到達確認マーカーも同じ値・同じ書き方で以前から
  同じ丸めを受けている。整数へ寄せると上記「外形と脚の幅が一致する」関係が崩れるので、一致を選んだ
- **影は津波の 3 つの印で定数を共有する**（`BADGE_SHADOW_COLOR` / `BADGE_SHADOW_BLUR`）。棒・到達確認・
  欠測がそれぞれ画面の DOM と共有カードの描き直しで使うので、定数にしないと同じ数値が 6 箇所へ散る。
  震度観測点・揺れ検知点・長周期地震動の印は同じ値を各ファイルのリテラルで持っている——あちらは
  WebGL のアイコンを焼く側で経路が違い、寄せるなら丸バッジの家族をまとめて扱う別の作業になる
- **共有カードの描き直しは、寸法が壊れた棒を 1 本まるごと弾いて記録する**（`isDrawableBar`）。あちらは
  「芯とフチを重ねない」ために外形と芯のパスを自分で組むので、芯を抜けなければ**外形が白一色で
  塗られ、波高の色が消えたまま画像に残る**。輪郭だけが消えた場合も同色の海岸線に溶けるだけで、
  **どちらも正常な描画に見えてしまう**。非有限値は大小の比較では素通りする（`NaN <= 0` は偽）ため
  先に確かめる。画面側（DOM）は `border` が要素の内側に収まるので壊れても「細い棒」にしかならず、
  上流の保証（`useTsunamiLayerData` が `OBS_MIN_PX` でクランプし、波高の数値が読めない観測点は棒に
  しない）に委ねている

### 到達確認マーカー（`TsunamiArrivalMarkersGL`）

**波高がまだ出ていない観測点**（気象庁電文の `MaxHeight` に数値が無く、到達時刻だけがある状態。
カードの「到達確認 / 観測中」に対応）を、棒とは別の印で表す。

- **棒と到達確認マーカーは排他。** 振り分けは `height` の有無だけで、値が付いた観測点は
  マーカーから消えて棒へ移る（`useTsunamiLayerData`）
- **形はこの地図が既に持っている丸バッジに合わせる。** 塗り丸＋白フチ＋影という作りは震度観測点と
  揺れ検知点が共通で使っており、ここで新しい形を作ると地図の語彙が 1 つ増える。大きさは地図アイコン
  倍率だけで決まる（観測点ごとに変わらない）。白フチと影は倍率に連動させない
  （[`settings-pwa-spec.md`](settings-pwa-spec.md) §2「主な項目の補足」）
- **寸法は観測棒から導く。** 直径を台座の幅（`BAR_WIDTH + BAR_FOOT`）に合わせると、海岸線に並んだ
  ときの足元の専有幅が棒と一致する。白フチを内側に引けば、残る灰色の芯が棒の本体幅（`BAR_WIDTH`）と
  等しくなる。**単独の数字で決めない**——棒より大きくなり、値を持たない印のほうが目立つ（実機で
  一度そうなった）。この 2 つの関係はテストで固定してある
- **白フチは太らせないが、細らせる。** 倍率で太らせないのは上記のとおりだが、下限 0.5 倍では直径が
  4.5px まで縮み、太さを保ったまま内側へ引くと灰色の芯が 1.5px しか残らない。印が「ほぼ白い丸」に
  なり、色が担っていた合図が消える。**芯が直径の 2/3 を割り込むならフチを細くする**（等倍がちょうど
  この比なので、細くなるのは等倍を下回る倍率だけ）
- **共有カードでは芯とフチを重ねずに描く。** 塗り丸の上へフチを重ねると、フチの帯だけ 2 回合成されて
  実効の濃さが上がる（0.9 → 0.99）。画面側は 1 つの要素へまとめて不透明度を掛けるため芯もフチも
  0.9 で、重ねると画像だけフチが濃くなる
- **不透明度は中の要素に置く。** マーカーの根の要素の `opacity` は `maplibregl.Marker` が自前で
  管理するため上書きされる（[`map-rendering-spec.md`](map-rendering-spec.md) §10）。観測棒と同じく、
  根はレイアウトだけを持ち、中の要素が見た目を持つ
- **高さを持つ形にしない。** 観測棒の形を借りると、固定の高さでも「小さな波高」に読まれる
- **色は気象庁の観測階級色（紫・赤・オレンジ・シアン）から外し、無彩色にする。** 階級色を借りると、
  値が出ていないのに波高の大小を伝えることになる。この地図が「意味のある量が無い」に使っている灰と
  同値だが、**定数は共有しない**（あちらは震度0 の色で、意味が違うものを束ねると片方の都合で
  もう片方が黙って変わる）
- **薄くしない。** この地図で不透明度を下げるのは「示している値が古い・確定していない」意味
  （欠測ホールド中の点・EEW の仮定震源要素）。到達確認は到達した事実も場所も確定していて、
  判っていないのは波高だけなので、薄くすると観測そのものを疑わせる。値が無いことは色が担う
- 座標は棒と同じ `tsunami-obs-coords.json` から引く。**ここに無い観測点はどちらの印も出せない**。
  この取りこぼしは名前ごとに 1 度だけ記録する（座標表は気象庁のコード表にある観測点を全件
  埋めているが、観測点が新設されて再生成が追いついていなければ引けない名前が出る。黙って消すと、
  カードには出るのに地図にだけ現れない理由が残らない）
- カメラがこのマーカーへ寄る条件は [`map-rendering-spec.md`](map-rendering-spec.md) §6
- **波高が無いことを理由にこの印を落とさない。** カード（「到達確認」のバッジと緑の左罫）も
  読み上げ（「◯◯で到達を確認しました。最大波高は観測中です」）も同じ観測点を扱っているため、
  地図だけが落とすと、声が到達を告げているのに画面が動かない、という食い違いが生まれる

### 欠測マーカー

観測データが欠測となっている観測点（§6「観測状態」）に置く印。**到達確認マーカーとは別の一覧・
別の印にする**（`missingMarkers`）。到達確認は「到達した事実は確定していて波高だけがこれから」の
意味なので、観測そのものが届いていない観測点を混ぜると印の意味が壊れ、津波が来ていないことの
保証のように読める。

- **寸法は到達確認マーカーと共有する**（`arrivalMetrics`）。海岸線に並ぶ印どうしで大きさが違うと、
  大きい方が重要だと読めてしまう。違えてあるのは色と、中央の横棒だけ
- 色は**無彩色にしない**（`TSUNAMI_MISSING_COLOR`）。この画面で灰色は「意味のある量が無い」に
  使っており、欠測は量が無いのではなく観測が届いていない状態。等級色も借りない（波高を観測した
  ように読める）
- 中央の横棒は「値が無い」を表す記号。**下限を置く** ―― 割合だけで決めると倍率 1 で 3.7×1.2px に
  なり、拡大しないと横棒があること自体が判らない（実測で確認した）
- **これまでに観測できた波高がある欠測は観測棒も出る。** 量は棒が、観測できていないことはこの印が
  伝える。棒の足元に重なるため、共有カードへ描き直すときは棒より後（手前）に描く
- カメラの寄り先にも含める（到達確認と同じ理由。観測できなくなった場所は津波が無いことの保証に
  ならない）
- 座標は到達確認マーカーと同じ表から引く。**そこに無い観測点はこの印も出せない**（取りこぼしの
  記録も共通。上記「到達確認マーカー」と同じ扱い）

## 9. カード表示（`TsunamiTab`）

以下の順序で表示:
1. 見出し（大津波警報・警報・注意報・予報のいずれか）
2. 区域リスト（同一階級内で予想波高が同じ区域はグルーピング）。前回の等級から動いた区域には
   その移り変わりを添える（§10「区域単位で等級が動いた報」）
3. 観測情報（区域コードが一致する観測点は該当区域の直下に、それ以外は別カードにフォールバック）
4. キャンセル時は `cancelReason` に応じた見出しに切り替え（10 秒間）

### 気象庁が書いた文は、行動指示の行から開く

電文の本文（`bodyText`）と付加文 2 種（`warningComments` / `freeText`）は、**バナーの行動指示の行を
タップして開く**。カードの末尾には置かない。

> **末尾に置くと事実上いつも見えない。** 区域と観測点が並ぶ実運用ではスクロールの最下部に埋もれる
> —— 区域 5・観測点 11 のテストデータでも、モバイルの上下分割（画面 390×740）で **7.2 画面分**下だった。
> 実電文はさらに多い（2026-04-20 三陸沖で区域 17・潮位観測点 28・観測 28 件）。いちばん重い避難の
> 呼びかけがいちばん見えない、という逆転が起きていた。

**行動指示の行には、気象庁の避難行動の文の 1 行目を出す**（`evacuationActionLine`）。これまでは
アプリが書いた文（「海岸・河川から直ちに離れてください」）だけを出していたが、公式の文があるなら
そちらが正しい（→ CLAUDE.md「利用者へ出す語を気象庁の表現と揃える」）。

**採るのは 1 行目が文として完結しているときだけ。** 実電文では報によって 1 行目の形が変わる。

| 実電文（2024-01-01 能登半島地震） | 1 行目 | 画面 |
|---|---|---|
| 16:12 | 「ただちに避難してください。」 | 気象庁の文を出す |
| 20:30 | 「＜津波警報＞」 | アプリの文へ戻る |

小見出しをそのまま行動指示の位置に出すと、何をすべきか伝わらない。境目は当日の VTSE41 を
全通走査して求めた（1 行目の形が変わるのは 20:30 の報）。

**どちらの形になるかを等級から当てにいかないこと。** 上の 2 通はどちらも最高等級が津波警報で、
それでも形が違う。2026-04-20 三陸沖（最高等級は津波警報）は前者の形だった。**等級と形は
対応していない**ので、行そのものを見る。

**この行が読むのは、続報のマージが引き継いだ固定付加文**（§5「続報で前報から引き継ぐもの」）。
固定付加文は主題の鍵ごとに新しい報の内容で置き換わるので、VTSE41 を持つ報が届けば行動指示の行も
一緒に入れ替わる。**裏を返せば、等級を動かしながら VTSE41 の固定付加文を持たない報があれば、
前報の文が残り続ける。** アーカイブにある 2024-01-01 以降の VTSE41 全 91 通を走査した範囲では
その形は 1 通も無かった（**数えたのは VTSE41 型の電文だけ**で、他の種別が等級を動かす経路は
この数に入っていない）。ただし、この行の正しさが引き継ぎの前提に依っている。
**崩れたら記録する** —— 等級が動いた報にこの付加文が無ければ警告を出す
（`mergeTsunamiReports` が呼ぶ `warnIfActionLineGoesStale`）。
画面には何の痕跡も出ず、古い等級への呼びかけが最も目立つ位置に残り続けるため。

**バナーへ行を足さない。** バナーは sticky なので、足した分だけ区域一覧の居場所が恒久的に減る。
モバイルの上下分割（画面 390×740）で測ると、津波パネルは 342px でそのうちバナーが 182px（53%）。
本文を別の行として足したときは残りが 91px まで落ち、等級の見出しすら入らなかった。だから既にある
行に入口の役目を持たせる。**この節の数値がパネル高さの単一情報源**で、コード側のコメントは
ここを参照するだけにしてある（同じ値を 2 箇所に書くとずれる）。

**開いた中身はバナーの下へ重ねる。流し込まない。** 流し込むとバナーが伸びて後ろの区域一覧が
押し下がり、読むつもりで開いただけで見ていた場所が動く。重ねれば高さは変わらない。
**高さの上限はパネルの実寸から引く**（パネル − バナー）。画面の高さ（`vh`）で切ると、上下分割で
パネルが画面の一部しか占めないときに下へはみ出す（上の測定のとおり、パネルは画面の半分以下）。
上限を超えた分はこの中でスクロールする。**「狭くても最低これだけは出す」という下限は置かない** ——
床の方が残りより大きくなれば、はみ出させないという目的そのものを裏切る（実測: パネルを縮めると
残りは 53px まで落ちるので、120px の床があった頃はそこで 67px はみ出していた）。

**代わりに、出す場所が無いときは開かせない。** パネルを縮めるとバナーだけで埋まり、面の高さは
0 になる。開くと矢印が変わるだけで中身は 1 行も見えず、理由も出ない —— 押せる見た目だけ与えない
という点で、取消し表示中の扱いと同じ。境目は本文 2 行ぶん。

> **寸法の判断はコンポーネントの外へ置く**（`overlayHeight.ts`）。描画の中に書くと
> `ResizeObserver` を差し替えないと動かせず、テストで押さえられない。実際、押さえられないまま
> 同じ計算に 3 巡続けて指摘が出た（床を足す → 床が残りを超える → 床を外す）。

> **測るのは callback ref で。`useEffect` + `[]` では張り直されない。** 津波が無い間は
> 「津波情報はありません」で早期 return しており、測る対象の要素が存在しない。効果は空振りして
> 終わり、津波が届いても依存が変わらないので二度と走らない —— 高さが 0 のまま上限が付かず、
> 開いた付加文がパネルの外まで伸びる（実際にそうなった）。

**開いたまま等級が動いたら閉じる。** 重ねた面は下の区域一覧を覆うので、開けっ放しだと発表・
引き上げ・一部解除が届いても利用者の目に入らない。**ただし報ごとには閉じない** —— 満潮時刻や
観測の続報は数分おきに届き（2026-04-20 三陸沖で 41 通）、そのたびに閉じると読んでいる途中で
毎回消える。閉じる契機は「津波の識別子」と「区域ごとの等級」の組が変わったときだけにする。

> **その組の前回値は state で持つ。ref をレンダー中に書き換えない。** React は描いた結果を捨てて
> 描き直すことがあり、**捨てられたレンダーでも ref の書き換えだけは残る**。次のレンダーでは
> 「組は変わっていない」と見えて閉じそこねる（実機で等級が動いても開いたままになった）。
> state なら捨てられたレンダーの更新も一緒に捨てられる。**閉じる操作自体もエフェクトで行う** ——
> 開閉の状態を持つフックの setter は「手で操作した」という意味を持つため、
> レンダー中に呼ぶと捨てられたレンダーでもフック内部の印だけが書き換わる。

**取消し・解除の表示中は入口にしない。** その間は中身を出さないので、押せる見た目だけ与えると
何も起きない理由が分からない（観測点の行と同じ考え方・§9「観測点の行・区域名をクリックしたときの寄り先」）。

> **入口はバナーの内側にあり、バナー自身もクリックできる**（対応する地震カードへ移動する）。
> 入れ子になった操作要素は支援技術に正しく伝わらないが、バナーの外へ出すと行が増えて区域一覧の
> 居場所が減るため、ここでは入れ子のままにしている。地震カードの震度一覧も同じ制約を抱えている
> （→ [`quake-spec.md`](quake-spec.md) §8「震度一覧は 4 段の入れ子」）。既知の限界として記す。

**中身に小見出しは付けない。** 読めば何の話か分かる文ばかりで、名前を足すと読む量が増えるだけ。
区切り線で分ける。並びは本文 → 固定付加文（主題順・§5）→ 自由付加文。

### 区域の到達状況

`Forecast/Item/FirstHeight` は**その区域にいつ津波が来るか**を伝える。取りうる形は 4 つ。

| 形 | 意味 | 出る等級 |
|---|---|---|
| 要素そのものが無い | 到達を語らない | 津波予報（若干の海面変動）と解除**だけ** |
| `ArrivalTime` のみ | これから来る | 注意報・警報・大津波警報 |
| `ArrivalTime` ＋ `Condition` = 「ただちに津波来襲と予測」 | これから来る（間近） | 同上 |
| `Condition` のみ =「津波到達中と推測」「第１波の到達を確認」 | もう来ている | 同上 |

上の表は**電文の形**。解除された区域はパーサーが `areas` から除くので（→ §4「DMDATA XML」）、
アプリの状態として「要素そのものが無い」形で残るのは津波予報の区域だけ。

**`ArrivalTime` と `Condition` は排他ではない。ただし併存するのは「ただちに津波来襲と予測」だけ。**
到達済みを表す 2 値が時刻を持たないのは、予想する対象がもう無いから。併存する側の時刻は
**必ず未来**（実配信では発表の 2〜10 分後）。

**注意報以上は `FirstHeight` を必ず持つ。** 要素ごと無いのは津波予報と解除。予想波高
（`MaxHeight`）も、`FirstHeight` を持つ区域には必ず付く。

区域の中の地点（`Forecast/Item/Station`）の到達予想も**必ず未来**で、波高か到達時刻が届いた
地点からは消える（満潮時刻だけが残る）。区域が到達済みでも、まだ来ていない地点の到達予想は残る。
**欠測の地点だけは残ることがある** —— 到達そのものを観測できていないので、予想を取り下げる
理由が無い。ただし**その値は画面に出ない**: カードは同じ名前の観測点があれば予報の行を出さず
（§9「観測点の並び順」の行のマージ）、観測点の行が拾うのは満潮時刻だけ。

#### バッジ

3 値は**意味が違う**。同じ文言で出すと、これから来るのか既に来たのかが読み取れない。

| 電文の値 | バッジ | 意味 |
|---|---|---|
| ただちに津波来襲と予測 | まもなく到達 | これから来る予測 |
| 津波到達中と推測 | 到達中 | いま来ている推測 |
| 第１波の到達を確認 | 第1波到達 | 実際に到達した事実 |

- **表に無い文言はバッジにしない**（本文へそのまま出す）。気象庁が語を増やしたとき、知らない語を
  赤いバッジで強調してしまわないため
- **その区域に観測点の行があれば出さない**（`badgeSuppressed`。観測点の行で代替できる）。
  条件は**行があるかどうかだけ**で、波高が届いているかは見ない —— 欠測しか無い区域でも抑制する。
  下の「実測との関係」が扱う「波高の実測がある区域」とは範囲が違う
- P2PQuake も 3 値をそのまま配信する。ただし真偽値の `immediate` は「ただちに津波来襲と予測」と
  1 対 1 ではなく、「津波到達中と推測」でも真になる（第１波の到達を確認では偽）。**どちらか一方で
  判定しない** —— 2023 年 11 月より前のデータは `firstHeight` 自体を持たず、真偽値しか残らない

#### 実測との関係

**波高の実測がある区域は、津波予報か到達済みの状態でしか現れない。**

- 沿岸観測点に波高の実測がある区域は、`FirstHeight` を持たない（津波予報）か、`Condition` が
  「第１波の到達を確認」のどちらか。「ただちに津波来襲と予測」「津波到達中と推測」の区域に
  波高の実測は無い。**津波予報の側は 1 割強を占める** —— 等級が下がっても観測は続くので、
  「到達を語らない区域に実測がある」のは異常ではない
- 「津波到達中と推測」の区域に観測点が現れることはあるが、**すべて欠測**（波高も到達時刻も無い）。
  来ているのに捉えられていない状態で、区域の `Condition` と食い違わない
- 実測が `Condition` より先に届くことも無い。`Condition` が先に「到達済み」へ変わるか、同じ報で揃う

**沖合観測点はこの話の外。** `Observation/Item/Area` が空で、区域に紐づかない（→ §4）。沖合から
沿岸を推定した `Estimation` 側の到達状況は値域も別で、「早いところでは既に津波到達と推定」の
1 値だけ（→ §9「沿岸への推定の行」）。

#### 遷移

4 つの形は**到達の段階に沿って進む**。

1. 区域が電文に初めて現れるときは「要素なし」（津波予報）か「時刻のみ」（注意報以上の発表）が
   ほとんど。稀に「到達中」「時刻＋ただちに来襲」から始まる（発表の時点で既に来ている）
2. 「時刻＋ただちに来襲」は**必ず通る段ではない**。「時刻のみ」から直接「到達中」「第１波の到達を
   確認」へ進む方が多い
3. 「到達中」→「第１波の到達を確認」と進み、解除で「要素なし」へ戻る。**第１波の到達を確認しない
   まま「要素なし」へ戻ることもある**（等級が津波予報まで下がった場合）
4. **戻る向きもある** —— 「到達中」から「時刻のみ」「時刻＋ただちに来襲」へ戻るのは、等級が
   変わって第一波の到達予想が引き直されたとき（`FirstHeight/Revise` = 更新）

> **確かめた範囲**（この節全体の根拠）: DMDATA アーカイブの全期間（2020-11-18〜2026-09-11）にある津波電文 634 通
> （VTSE41/51/52・通常 434・訓練 200）、`Forecast/Item` の区域延べ 19,906。上の規則はいずれも

### 観測点の行・区域名をクリックしたときの寄り先

観測点の行をクリックすると地図がその観測点へ寄る（実装は `FocusObsGL`）。**実測・到達確認の
どちらの行も対象**で、区域に紐づく行（`TsunamiAreaRow`）と沖合観測の行（`TsunamiObservationRow`）で
条件を揃える。

**着地の深さは地震カードの一覧と同じものを使う**（`focusMaxZoom`。→
[`quake-spec.md`](quake-spec.md) §8「一覧の行をクリックしたときの寄り先」）。どちらも「1 点を指す
行を押した」という同じ操作で、一覧によって深さが違う理由が無い。自動フィットの寄り上限では、
細い観測棒が隣の点と見分けが付かない。

**ただし押した観測点を選んだ状態にはしない。** 地震カードの一覧では寄り先の吹き出しを開くが、
津波の観測棒・到達確認・欠測は地図の描画物ではなく画面に重ねた要素で、**ホバーでだけ出る
吹き出し**を自前で持っている。クリックの調停役（`gl/popupRegistry.ts`）に登録されていないため、
同じ仕組みでは開けない。

押せるかどうかは「地図がその観測点へ寄れるか」＝**座標表に名前があるか**で決める。座標表に無い
観測点は地図に印が出ず、`FocusObsGL` も寄せ先を見つけられずに何もしない。押せる見た目だけ与えると、
利用者からは動かない理由が分からない。

**区域名も押せる。** 寄り先はその予報区の海岸線（`tsunami-zones.json`）の外接矩形で、経路は地震
カードの一覧と同じ（`FocusTargetGL`。→ [`quake-spec.md`](quake-spec.md) §8「一覧の行をクリック
したときの寄り先」）。押せるかどうかを寄り先の有無で決めるのは観測点と同じ規律。

- **行全体ではなく区域名だけ**を当たり判定にする。この行は観測点の一覧を抱えているため
- **解除された区域には与えない**（`TsunamiCancelledCard`）。海岸線が地図に描かれておらず、
  寄っても何も無い場所を見せることになる
- **寄せたら俯瞰へ帰る猶予を数え直す**（観測点のクリックと同じ。帰還そのものは
  → [`map-rendering-spec.md`](map-rendering-spec.md) §6「津波追従の目標範囲」）。ただし
  **猶予を張るのは津波モードのときだけ**で、要求そのものは
  モードに関わらず消費する —— 寄せ先の入れ物は地震カードと共有しているので、モードを見ないと
  地震タブでの操作が津波の帰還を遅らせるが、消費まで止めると今度は地震タブで押した要求が
  津波タブへ移った瞬間に猶予を延ばす

### 予想波高の有無

**判定は `tsunami.ts` の `hasForecastHeight` に一本化する。** 見るのは `maxHeight` オブジェクトの
有無ではなく `description`（表示・読み上げに使う文字列）の中身。

- 電文の解析は数値が取れれば `maxHeight` を作るため、値が 0 で条件（「巨大」等）も無いときに
  `description` が空文字のオブジェクトが残る
- オブジェクトの有無で判定すると、カードは「波高なし」として扱うのに読み上げは「波高あり」として
  扱い、**その区域が波高の文にも波高なしの文にも入らない**（黙って落ちる）
- **`maxHeight` を作る条件は経路で違う。** DMDATA（`dmdataParser.ts`）は数値か `description` の
  どちらかがあれば作るので、値だけで条件が無い区域には `description` が空のオブジェクトが残る。
  P2PQuake（`p2pquake.ts`。§4「P2PQuake（`convertEvent`）」）は `description` が空なら作らない。
  **同じ中身の区域でも経路によってオブジェクトの有無が変わる**ため、両経路を揃えるには
  `description` を見るしかない

波高が無い区域はカードでは波高見出しを持たないグループに入り、読み上げでは「〇〇にも津波警報が
発表されています。」の形で別の文に挙げる（[`audio-tts-spec.md`](audio-tts-spec.md) §4）。
**波高が無いこと自体は異常ではない** — 警報が先に出て波高が後続報で付くことがある。

### 沿岸への推定の行

沖合の観測から導いた沿岸への推定（`Estimation`。§4）は、沖合観測の実測の下に区切って並べる。
**気象庁が推定したもの**であってアプリの計算ではないことを見出しに書く。

1 行は 2 段。

- 上段: 区域名／「重要」のバッジ／波高／到達予想時刻
- 下段: 到達についての説明（「早いところでは既に津波到達と推定」）

**説明を上段の時刻と入れ替えないこと。** 電文はこの 2 つを併存させる（§4）ので、時刻があるときに
説明を隠すと**時刻を出せる沿岸ほど注意喚起が落ちる**。

波高の欄（`estimationHeightText`）は数値、無ければ「推定中」。**空欄にしない** —— 値が無いのが
気象庁の判断（予想される高さに比べ十分小さい）なのか読み落としなのか、画面から区別できなくなる。

### 数値にならない予想波高（「巨大」「高い」）

M8 を超える地震では規模を速報できないため、気象庁は**大津波警報・津波警報の第一報で高さを
「巨大」「高い」と発表し**、`jmx_eb:TsunamiHeight` の本文を `NaN` にして `description` 属性に
その語を入れる。同じ電文では原因地震の規模も「Ｍ８を超える巨大地震」になる（§4）。

> **語が入るのは `description`。`condition` ではない。** 電文解説資料の事例はこの形。
>
> ```xml
> <jmx_eb:TsunamiHeight type="津波の高さ" unit="m" condition="不明"
>   description="巨大">NaN</jmx_eb:TsunamiHeight>
> ```
>
> `condition` は**固定値「不明」**で、定性的表現は `description` に入り、本文は `NaN` になる。
> **`condition` を表示文字列のフォールバックに使わないこと** —— 解説資料いわく「定性的表現が
> ない津波注意報や津波予報の場合は、@description は空属性となる」ので、そこへ落ちると波高として
> **「不明」と表示・読み上げする**（実際にそうなっていた）。数値も語も無ければ波高は持たせない。
>
> なお令和6年能登半島地震（2024-01-01〜03）の津波電文 56 通にこの形は現れなかった（M7.6 で
> 「巨大」を使う条件に当たらないため）。**実物での確認は解説資料の事例に拠っている。**

**数値が無いことを理由に落とさない。** 落とすと、**最も重大な場面で波高が 1 つも画面に出ない**。
`description` の組み立ては 2 段で、上から順に採る。

1. `description` 属性（気象庁が組んだ表示文字列。定性的表現もここに入る）
2. 本文の数値から組む（`${value}m`。属性が空のときの保険）

**ここへ 3 段目として `condition` を足さないこと。** 上の囲みのとおり固定値「不明」なので、落ちると
波高として「不明」と出る。**予想・観測・沿岸への推定の 3 経路すべてでこの 2 段に揃える** ——
かつて推定側だけが 3 段で、同じ電文の予想側と推定側で波高の出方が変わりうる状態だった。

数値が読めなければ `value` は持たせない（0 や NaN で埋めると波高の比較や並べ替えが狂う）。
読み上げは語を補う（`NON_NUMERIC_HEIGHT_PHRASE`。→ [`audio-tts-spec.md`](audio-tts-spec.md) §4）。

### 区域の並び順

並べ替えは `tsunami.ts` の `groupAreasForCardDisplay` / `sortAreasForCardDisplay`。予想波高が
**連続して一致する**区域を 1 グループにまとめ（離れた位置にある同じ波高は別グループ）、グループの
中を実測波高の深刻な順（`compareObservedHeightDesc`）に並べる。実測を持たない区域はグループ内の
後ろへ回す。**この「深刻な順」は単純な値の降順ではない** ―― 「○m以上」は値の大小より先に見る
（§6「観測波高の「以上」」）。

**この並びは読み上げの区域列挙とも共有する**（揃える理由は
[`audio-tts-spec.md`](audio-tts-spec.md) §4「津波の区域の並び順」）。カード専用の関数ではないので
`TsunamiTab` ではなく `tsunami.ts` に置いている。

#### 等級をまたぐ順が要るとき

`sortAreasForCardDisplay` が決めるのは**1 つの等級の中**の並びだけ。カードが等級ごとに分かれて
いるためで、等級が混ざった一覧をそのまま渡すと、波高の見出しで等級をまたいで束ねてしまい、
注意報の区域が警報より上に来る。

区域を「カードで上から見える順」に通しで並べたいときは `sortAreasAcrossGradesForCardDisplay` を
使う。**上位から何件かだけを採る用途で効いてくる** ―― ブラウザ通知の本文（先頭 5 件）と、
受信時スクロールの送り先（先頭の 1 件）がそれにあたる。

#### 並べ替えに渡す材料はカードと同じものにする

区域の並びは「その区域で最も深刻な実測波高」で決まるため、**渡す観測点が違えば並びも変わる**。
カードはマージ済みの全観測点で並んでいるので、そこから並びを引く側もすべて同じ材料を使う。

材料を組み立てるのは `useLiveEventHandler` の `tsunamiCardOrderBasis`。区域と観測点の 2 つを返し、
4 経路がそれを共有する ―― 読み上げ・ブラウザ通知の本文・受信時スクロールの送り先・区域単位で
等級が動いた報（§10「区域単位で等級が動いた報」。ここで作った並びは読み上げと寄せ先の**両方**が
そのまま使うので、前の 3 つとは別に材料を渡す）。電文の `areas` / `observations` を直接使わないこと。

**この 4 つを数え上げている場所は 2 つ**（`tsunamiCardOrderBasis` の宣言箇所・この節）。
**経路を増減するときは両方とも直す。** これ以外の場所 ――
材料の重要さを説く `isTsunamiContinuation`（`tsunami.ts`）や、`tsunamiCardOrderBasis` を呼ぶ側の
コメントなど ―― では経路を列挙せず、宣言箇所を参照させる。散らすと、経路が増えたときに一部だけ
古い数が残る（実際に 3 ファイルで残っていた）。

- **区域**: 電文が持たなければ（観測情報の続報）画面が出している津波から引く
- **観測点**: 画面が出している津波の観測点とマージする
- **引き継ぐ条件はカードと同じ述語**（`tsunami.ts` の `isTsunamiContinuation`）。同じ `eventId` を
  双方が持ち、表示中が解除表示に入っていないときだけ引き継ぐ。カードの状態更新
  （`useEarthquakes`）と同じ関数を使うので、片方だけが引き継ぎを断つことがない

**等級を切り替える報（大津波警報 → 警報 → 注意報）で最も大きくずれる。** その形の電文は観測点を
ほとんど載せないため、電文の分だけで並べると読み上げが電文順へ戻る。2024/01/01 20:30 の切替で
実際に起きた。

> `eventId` を持たない経路（P2PQuake の 552）では引き継ぎが起きない。カードも同じ条件で
> 蓄積しないため、材料は電文単体で一致する。

### 最大波の観測時刻

**波高の数値だけでは、それがいつの観測値かが分からない。** 続報で値が変わらないとき、観測し直して
同じだったのか前の値が据え置かれているのかを読み取れる唯一の手がかりが `MaxHeight/DateTime`。
観測点の行の時刻欄に、第1波の到達時刻と並べて出す（実体は `tsunami.ts` の
`observationMaxHeightTimeText`）。

- **語を冠する**（「最大波 HH:MM」）。同じ行に 2 つの時刻が並ぶため、裸の時刻を足すとどちらが
  どちらか分からなくなる
- **波高を出していない行では出さない。** 時刻だけが残ると、値の無い観測点が何かを観測したように
  見える。「観測中」「微弱」ではこの要素ごと出現しない（Ⅱ.12 1-2-2-2）
- **区域に紐づく行と沖合観測の行は別コンポーネント**なので、**両方に同じ述語を通す**
  （観測点の行のクリック可否と同じ理由。下記「観測点の行・区域名をクリックしたときの寄り先」）

### どの項目が動いたかを文字色で示す

観測点の行の左端には更新の印（3px の縦線）が付く。緑＝その地点が初めて出た・黄＝既にあった地点が
更新された。**しかしこれは「この地点で何かあった」までしか言わない** —— 最大波の時刻しか動いて
いない報では、縦線が黄色く光るのに**行の中身は 1 ドットも変わらない**。

そこで**動いた項目だけを、縦線と同じ色で塗る**（`ObsUpdateMark` の `fields`）。縦線が「この地点で
何かあった」、文字色が「この項目よ」の 2 段構え。

- **色は縦線と共有する**（`UPDATE_MARK_COLOR`）。同じ出来事を指す印なので、色を分けると読み手が
  2 つの語彙を覚えることになる。地震カードの欄の印とも同じ語彙だが、**あちらは値の肩に点を置く**
  （欄が横に並び、津波区分は文字そのものが区分の色なので文字色では揃えられないため）
- **対象は第1波・最大波の観測時刻・波高の 3 つ。**
- **区域に紐づく行では、波高の既定の文字色を白にする。** 以前は等級の色（`GradeStyle.heightColor`）で
  塗っており、そのせいで波高だけ印の対象から外していた。**等級は等級カードの枠と見出しが示しているので、
  波高の数字で繰り返す必要がない** —— 白にしたことで、動いた報だけ印の色へ変えられるようになった。
  **沖合の行は元から等級の色を持たない**（無彩色）ので、そのまま印を当てられる
- **沖合の観測点の行にも出す。** 津波予報区に紐づかない観測点（`unmatched`）は別のコンポーネントで
  描くので、判定が作った印を渡し忘れると**そこだけ縦線も項目の色も出ない**（実際にそうなっていた）。
  読み上げは沿岸と同じように読むため、声が名指しした観測点を画面が示せなくなる。
  **実機で確かめる入口は設定タブの「変化の小さい続報テスト」（5 通目）** —— 沖合の観測点を載せるのは
  沖合の津波観測に関する情報（VTSE52）だけなので、その 1 通を足すまで**実機に出す手段が無かった**
- **満潮時刻は対象外。** 2024-01-01〜02 の VTSE51 全 49 報で満潮時刻が動いたのは 2 報だけで、しかも
  動くときは 41/52 点が一斉に動く（前の満潮を過ぎて次の満潮へ進んだ形）。印としての選別力が無い
- **区切りの全角空白は色を当てる範囲の外に置く。** 中へ入れると、動いた項目の手前の空白まで
  塗られて色の帯が項目からずれる
- **寿命は縦線と共有**（`TSUNAMI_BADGE_TTL_MS`）。出どころが同じ `obsUpdateStatus` なので、同じ
  出来事を指す 2 つの印が別々に消えることはない
- 判定は**画面用の記憶**と突き合わせる（`changedObservationFields`）。読み上げ用の記憶（声にした分
  だけ進む）を渡すと、上位の読み上げに待たされて見送られた報でも画面には届いているのに印が出ない
- **波高は「深刻になったか」で見る**（`hasObservedHeightRisen`）。記憶が高水位マーク式なのと対で、
  下方修正では印を付けない。向きを問わず拾うのは地図のカメラだけ（→ §6「観測波高の「以上」」）
- **初出も印を付ける。** 最大波の観測時刻だけは判定が `hasMaxHeightTimeAdvanced` を通り、あれは
  電文が「更新した」と言っていること（`MaxHeight/Revise`）を要求するので、**観測点が初めて現れた報では
  必ず偽になる**（初報の電文は `Revise` を持たない）。そのまま印の判定に使っていたころは、
  **行の縦線も波高も第1波も緑なのに最大波の観測時刻だけ白**という中途半端な画になっていた
  （読み上げはその時刻を読んでいる）。**`hasMaxHeightTimeAdvanced` 自体は変えないこと** ——
  あれは読み上げ・地図のカメラ・バッジが共有する「更新されたか」の述語で、初出まで真にすると
  初めて現れた観測点について「最大波の観測時刻が更新されました」と読む
- **等級が動いた報でも、動いたものだけに印を付ける。** その報には値が 1 つも変わっていない観測点が
  同梱されうる。全件を無条件に「初出」で押していたころは、何も変わっていない行に
  「最新の情報で初めて出た値です」という案内が付いていた。**ただし新規発報では絞らない** ——
  判定は「別の津波へ移った報か、観測点の記憶がまだ空か」で見る（**等級で見ない** —— 等級の記憶は
  区域を持たない観測情報では進まないのに観測点の記憶はその報でも埋まるので、進行中の津波へ
  途中から接続した直後に正当な継続を初出と扱う）。
  観測点の記憶は**津波をまたいで残る**ので（落とすのは表示中の津波への解除とリプレイのリセットだけ）、
  前の津波で見た同名の観測点が前より低い波高で現れると「動いていない」と判定される。
  **縦線だけでなく項目の色も同じ規律で決める** —— 新規発報では前値を渡さずに判定する。
  縦線の色（`status`）だけを「初出」にしても、項目の色は同じ記憶との比較から出るので、
  **行は緑なのに値が白い**という中途半端な行になる（初出の印を入れた意味が津波を跨ぐと消える）
- **波高を持たない観測点（到達確認・欠測）を「名前の新しさ」だけで絞らない。** 一度でも載った名前は
  記憶に入るので、名前だけで見ると**二度目以降は何が変わっても印が付かない**。実際に起きるのは
  第1波の訂正と、到達確認だけだった地点に到達時刻が付く形で、**読み上げは両方とも名指しして読む**。
  新旧の別はこの群だけ「名前を見たか」で決める（波高の記憶には一度も入らないため）
- **欠測へ転じたことは、いまも印にできない。** 画面用の記憶は高水位マーク式で値を消さないため、
  「前の報では観測できていた」と「欠測のまま続いている」を見分けられない（名前の有無で判定すると
  欠測の間ずっと毎報光る）。欠測のバッジ自体は出るので情報は落ちないが、縦線の合図は付かない
- **地図のカメラも第1波の訂正で寄る。** 波高（`hasObservedHeightChanged`）と最大波の観測時刻
  （`hasMaxHeightTimeAdvanced`）に、第1波の鍵（`firstWaveSpokenKey`）の比較を並べる。カードの文字色も
  読み上げもその観測点を名指しするのに、**カメラだけが第1波を見ていなかった**。到達時刻が読めない報では
  鍵を組めないので「動いた」とみなさない —— `null !== undefined` が真になるため、素の比較だと
  その観測点へ毎報寄り直す
- **バッジ・自動スクロールの対象と同じ判定から出す。** 別々に書いていた頃は、読み上げが名指しした
  観測点のバッジが点滅せずカードもそこへスクロールしない食い違いを 2 度作り込んだ（最大波の
  観測時刻・第1波の訂正）

### 実測の到達時刻が無い行に添える到達予想

観測点の行は、同じ名前の**予報の観測点**（`TsunamiArea.stations`）と実測（`TsunamiObservation`）を
1 行へ畳んで出す。**実測の到達時刻を出せていない行には、予報側が持っている到達予想を
「到達予想 HH:MM」として添える。**

添えないと、到達を観測できていない地点で時刻の欄が空になり、**まだ来ていないのか、来たのに
観測できなかったのかが画面から読み取れない**。

- **条件は「実測の到達時刻を出せない」こと**（整形の結果が空。値が無い場合と、値はあっても
  日時として読めない場合の両方）で、観測状態では絞らない。**生の `obs.arrivalTime` の有無で
  書かない** —— 読めない値は真になるので、時刻を出せないのに到達予想が添わない。
  **理由の語（「到達時刻不明」）を出す `observationArrivalFallbackText` も同じ述語にする** ——
  片方だけ整形の結果で見ると、到達予想は出るのに理由の語が出ない形でずれる。
  実配信でこの値が残るのは欠測の地点だけだが（DMDATA アーカイブ 2020-11-18〜2026-09-11 の
  津波電文 634 通。予報と観測の両方に載る観測点 8,857 件のうち、欠測 153 件中の 17 件のみで、
  実測の波高がある 8,034 件・到達時刻だけの 472 件・第1波識別不能 198 件ではいずれも 0 件）、
  **観測状態の名前で条件を書くと、別の状態で届いたときに黙って落とす**
- **語は 3 箇所で揃える** —— 区域の行・実測の行・予報だけの行。同じ `TsunamiStation.arrivalTime` を
  実測のエントリの有無で「到達予想」「到達」と呼び分けると、上下に並んだとき片方が確定した事実に
  見える。**「予測」のバッジがあっても足りない** —— 時刻の語が違えば、別の性質の値として読まれる
- **画面にだけ出す。** 読み上げは欠測を到達確認と別の文で伝えており
  （[`audio-tts-spec.md`](audio-tts-spec.md) §4「欠測は到達確認と別の文で伝える」）、そこへ予報の値を
  混ぜると到達を確認したように聞こえる。地図の到達確認マーカーにも出さない —— 到達していないので
  印を置く根拠が無い
- **名前が一致しないことは記録しない。** 観測点を運ぶのは VTSE51 だけなので、**その津波でまだ一度も
  VTSE51 を受けていない間は `stations` が空**（一度受けた後は続報へ引き継ぐ → §5「続報で前報から
  引き継ぐもの」）。等級の発表が先に届く実運用ではこれが普通の状態で、「1 件も一致しない」を異常
  として鳴らすと正常な受信で記録が埋まる
- **時刻の欄は区切りを前置きしない。** 空になりうる要素が並ぶため、前置きすると先頭が空のときに
  字下げだけが残る。要素が 1 つも無ければ欄ごと出さない
- **出るのは DMDSS 版だけ。** 予報の観測点（`TsunamiArea.stations`）を埋めるのは DMDATA XML の
  経路だけで、P2PQuake はこの要素を配信しない（→ §4「区域の潮位観測点」）

「到達時刻不明」（第1波識別不能）の行と並ぶことは仕組みの上ではありうる。到達そのものは確定して
いて時刻だけが読めない状態なので矛盾はしないが、上記の欠測 153 件の内訳では 0 件。

### 観測点の並び順

区域と同じ理由で、**観測点の並びも読み上げと共有する**。実体は `tsunami.ts` の
`sortObservationsForCardDisplay` で、カードの入れ子をそのまま辿る。

1. 等級カード（`GRADES_IN_CARD_ORDER` = 大津波警報 → 警報 → 注意報 → 予報 → 不明）
2. 予想波高の見出しごとのグループ
3. グループ内の区域（上記「区域の並び順」）
4. 区域内は電文の並び
5. どの区域にも紐づかない観測点（沖合の観測点。カードでは「沖合観測」の別カード）

**等級カードの順を並べる定数もカードと共有する。** カード側に独自の配列を置くと、等級を増やした
ときに片方だけ漏れる。

#### 観測点は「選抜」と「並び」を分ける

観測情報の読み上げは、**どの観測点を読むかを波高の深刻な順で選び、どの順で読むかを
`sortObservationsForCardDisplay`（上記）で決める**。この 2 つを混ぜてはいけない。

- 選抜を深刻な順にするのは、件数上限（5 件）で「○m以上」の観測点を落とさないため（§6）
- 並びをカードに揃えるのは、追従スクロールがカード上を往復しないため

深刻な順のまま読むと、カードの位置と読む順が無関係になる。カードは等級と区域でまとまっていて、
区域の並びは**その区域の最大波高**で決まるのに対し、読み上げは**観測点ごとの波高**で並ぶため、
同じ区域の小さな値が離れた位置で読まれる。2024/01/01 の実電文を再生すると、観測点が広域に散った
続報で画面が上下に往復した。

読み上げ側は「渡された並びをそのまま読む」だけで、並べ替えは呼び出し側
（`useLiveEventHandler`）が行う。渡す材料の作り方は上記「並べ替えに渡す材料はカードと同じものに
する」を参照。

> **限界**: 「画面が出している津波」は描画のたびに更新されるため、電文が 1 度の処理でまとめて
> さばかれたときは 2 件目以降が 1 件分古い状態を基準にする。並びがカードと少しずれるだけで、
> 読み上げる観測点も新規・更新の言い分けも変わらない。

### スクロールの自動制御

3 つの駆動がある。読み上げが有効なときは受信時のものが追従を待つ（声と画面を一致させる側に
任せる）。**ただし待ちには上限があり、追従が受け持たなければ受信時のものが動く** ―― 塞ぐと
VOICEVOX が未起動の端末でカードが一切動かなくなる。詳細は
[`audio-tts-spec.md`](audio-tts-spec.md) §6。

| 駆動 | いつ動くか | 動き |
|---|---|---|
| 自動で見せたとき | **他のタブから**津波タブへ自動で切り替わったとき（**既定の状態への復帰もここに含む**。下記） | カードの先頭へ戻す（一瞬で移す）。手動で開いたとき・手で動かした直後は動かさない。**最も弱く**、同じ受信で下の 2 つが動くなら上書きされる |
| 受信時（`focusedDistrict`） | 電文の受信時に 1 回（読み上げが有効なら、追従が受け持たなかったときだけ） | 変更区域が視野に収まればまとめて見せ、収まらなければ波高最大の区域を視野の上端へ。**寄せ先が無い受信の扱いは下記** |
| 読み上げ追従 | 読み上げの進行に合わせて（読み上げが有効なときだけ） | 読んでいる箇所が視野内なら動かさず、外に出たときだけ送る（詳細は [`audio-tts-spec.md`](audio-tts-spec.md) §6「読み上げに合わせたカードの追従」） |

#### 寄せ先が無い受信

区域を 1 つも挙げられない受信がある。**そのうち先頭へ戻すのは、カードの中身が入れ替わって
前の位置に意味が無くなったものだけ**（`FocusedDistrict.resetToTop`）。

| 受信 | 動き |
|---|---|
| 解除 | 先頭へ戻す（カードの中身が消える） |
| 新規発報・等級が変わった報（観測点を伴わないもの） | 先頭へ戻す（最上位の区域群が入れ替わる） |
| **各地の満潮時刻・津波到達予想時刻に関する情報** | **動かさない** |
| **実質変化なしの続報**（中身が前報と同じ再送。満潮時刻の報と同じ枝を通る） | **動かさない** |
| **沖合の津波観測に関する情報** | **動かさない** |

後ろの 3 つを動かさないのは、**寄せ先が作れないことと、位置を捨ててよいことが別の事実**だから。
満潮時刻の報は区域も観測点も動かさないので「変化なし」として扱われ、沖合の観測情報は新しい
観測点を持つのに沖合の観測点が津波予報区を持たないため寄せ先の一覧が空になる。どちらも
先頭へ戻すと**直前の報や読み上げが合わせた位置を捨てる**（実電文での実測は §14 改訂履歴の
2026-09-11 の項）。しかもこの経路は読み上げを待つ猶予を飛ばすため、喋っている最中でも引き剥がす。

**両者を同じ値（区域の一覧が空）で表さないこと。** 兼ねさせると、寄せ先を作れなかっただけの
受信が「先頭へ戻せ」として扱われる。判断は受信の種類ごとに決め、**既定値を置かない**
（経路を足したときの決め忘れを型検査で捕まえる）。

#### 既定の状態への復帰

アイドル復帰・EEW 全解除・揺れ検知終了・揺れの可能性の失効は、いずれも既定タブへ戻す操作
（`revertToDefaultTab`）。**これらは受信ではないので、上の 3 駆動のうち「自動で見せたとき」
1 本だけで扱う。**

**先頭へ戻すのは、津波タブ以外から連れ戻されたときだけ。** 判定は `shouldResetTsunamiScroll`
に集約してある。津波優先の設定（`tsunamiPriorityDefault`）では津波の発表中に既定タブが津波に
なるため、**津波タブを見ている最中も無操作のたびに復帰が通る**。そこで先頭へ戻すと、読んでいる
位置が設定の秒数ごとに捨てられる。

**先頭へ戻す要求を別経路から出さないこと。** 条件が片方にしか掛からない形になり、津波タブを
見ている最中の復帰で位置が捨てられる（実測は §14 改訂履歴の 2026-09-12 の項）。

**手で動かした直後（30 秒）は、タブが変わる復帰でも先頭へ戻らない。** 「自動で見せたとき」の
駆動が手操作の保持を尊重するため。触った位置を残す方を採る。

なお復帰では**変更区域の記憶（`focusedDistrict`）に触らない**。この記憶から行ごとに算出する
`isChanged` / `isTop` は次の受信でスクロール先を決めるためだけのもので、行の見た目には使わない。
次に `focusedDistrict` が変われば全区域の行が登録し直されるため、復帰の時点で消す必要はない。

## 10. 音・通知・読み上げの連動

`useLiveEventHandler.ts` の tsunami 分岐で発火する。

| 状態 | 音種別 | 通知 | 読み上げ |
|---|---|---|---|
| 大津波警報の新規発表 | `tsunamiMajor` | あり | あり |
| 津波警報の新規発表 | `tsunami` | あり | あり |
| 津波注意報の新規発表 | `tsunamiWatch` | あり | あり |
| 津波予報の新規発表 | `tsunamiForecast` | あり | あり |
| 続報（レベル変化なし） | 抑制（読み上げのみ） | 抑制 | あり |
| 解除・取消・期限切れ | `tsunamiCancel`（cancelReason の 3 種を単一音で区別せず伝える） | 抑制 | あり |

音・TTS は `spokenTsunamiCancelEventIdsRef`（`useLiveEventHandler.ts`）で **eventId 単位** に
重複発火を抑止する。P2PQuake WS と DMDATA WS から同一 eventId で cancel が届いた 2 回目、
または合成 expired タイマーが同一 eventId に複数積み上がった 2 回目以降は握り潰す。
ページリロード直後の初回解除は Set が空のため正常に発火する。

### 等級を伝えていない電文（区域が空）

DMDATA には、区域を持たず観測点だけを載せた続報がある（VTSE51②・VTSE52。§3 の表記に揃える）。この電文は
**等級の比較から外し、観測点更新として扱う**（`isTsunamiObservationOnly`）。

区域が無いと最大等級は `Unknown`（最下位）になるため、発表中の警報と比べると必ず「降格」に
見える。降格の読み上げは区域が空だと全解除の文言へフォールバックするので、**警報の発表中に
「津波警報等は全て解除されました」と読み上げていた**（2026-08-21 に修正）。等級を伝えていない
だけで観測値は載っているため、観測点更新として読むのが正しい。

この判定は音の種別・読み上げ・観測の追跡（読み上げ無効時のタブ移動を含む）の 3 か所で使う。
**同じ判定に揃えること。** 片方だけずらすと「読み上げはするのに画面が動かない」が生まれる。
実装では音の種別を決めるときに 1 度だけ判定し（`tsunamiIsObservationUpdate`）、読み上げ側はそれを
使う。

### 区域単位で等級が動いた報（一部解除・一部引き上げ）

**一部解除は多くの場合、区域の削除ではなく等級の降格として届く。** 解除された区域は「津波注意報
→ 津波予報（若干の海面変動）」への降格として電文に残り、前回その区域に出ていた等級は
`Category/LastKind`（JSON では `kind.lastKind`）が伝える。2024 年能登半島地震の一部解除 3 通は
いずれもこの形だった。

**ただし、その津波予報区でもう何も発表しないときは解除コードが付く。** `Kind/Code` が 00/50/60 の
区域で、降格ではなく等級そのものが無くなる。この区域は `areas` には入らず
`JMATsunami.cancelledAreas` が持つ（→ 下記「解除された区域」）。

2024 年能登半島地震 01/02 02:30 の VTSE41（見出しは「津波注意報を一部解除しました。」）:

| 区域 | 今回の等級 | 前回の等級 |
|---|---|---|
| 石川県能登ほか 19 区域 | 62 津波注意報 | 62 津波注意報 |
| 福岡県日本海沿岸・佐賀県北部 | 72 津波予報（若干の海面変動） | **62 津波注意報** |
| 北海道太平洋沿岸中部ほか 4 区域 | 71 津波予報（若干の海面変動） | 71 津波予報（若干の海面変動） |

**他の区域に注意報が残る限り、電文全体の最上位等級は動かない。** そのため `tsunamiMaxGrade` の
比較だけでは変化を捉えられず、この報は観測情報の続報と同じ枠へ落ちていた。観測波高の更新が
無ければ読み上げ文が空になるため、**受信音だけが鳴って解除がどこにも現れなかった**
（2026-09-01 に修正）。

区域ごとの前回の等級は `TsunamiArea.lastGrade` に持ち、`tsunamiAreaGradeChanges` が「どこから
どこへ動いたか」の組にまとめる。**前報との差分は取らない** ―― 電文が自ら述べている事実なので、
報の到着順が入れ替わっても部分再送でも結果が変わらない。

- 並びは**引き上げの組を先、引き下げの組を後**に置き、それぞれの中は遷移先の等級が重い順。
  聞き手が取るべき行動が重くなる側を先に伝えるため
- 組の中の区域の並びはカードに揃える。渡す観測点は §9「並べ替えに渡す材料はカードと同じものに
  する」の材料から取る（一部解除の電文は観測点をほとんど載せないため、電文の分だけで並べると
  カードと逆転する）
- 等級の重さの比較は `isTsunamiGradeRaised` に閉じる（読み上げの動詞・並び順・カードの表示が
  すべてこの向きで決まるので、呼び出し側で比べ直すと等級を増やしたときに片方だけ漏れる）
- `areas` の中の `Unknown` の区域は返さない。**これは「等級を読めなかった」の意味**で、解除とは
  別の事実（下記「解除された区域」）。どちらの向きにも文を作れない

#### 解除された区域

**`Kind/Code` が解除コード（00/50/60）の区域は `areas` に入らない。** もう等級が出ていないため、
入れると地図の海岸線・全体の最上位等級・通知の本文・寄せ先といった「発表中の区域」を読む経路が
まとめて解除済みの区域を拾う。代わりに `JMATsunami.cancelledAreas` が持ち、`grade` は
`'Unknown'`（この報の時点で等級が無い）・`lastGrade` に解除前の等級が入る。

**混ぜずに別の入れ物へ置くのは、読み忘れたときの症状が軽いから。** `areas` に混ぜると、除外を
書き忘れた経路が解除済みの区域を発表中として描く（事実と逆）。別にしておけば、読み忘れの症状は
「この機能が効かない」に留まる。**`TsunamiGrade` へ解除を表す値を足さない**のも同じ理由で、
`areas.filter(...)` の類は型検査に掛からない。

`tsunamiAreaGradeChanges` はこの区域も等級変化の組として返す。遷移先は `TsunamiGrade` に無い値
`TSUNAMI_GRADE_LIFTED` で、引き下げの組の中で最も軽い位置（`Unknown` より後ろ）に並ぶ。

- **絞り込みは `describableCancelledAreas` に集約する。** 落とすのは 2 つ ―― 前回も津波なし
  （`lastGrade` が `Unknown`。何も起きていない）と、前回の等級を読めなかったもの。読み上げと
  カードが別々に絞ると、声は伝えるのに画面に出ない形でずれる
- 前回の等級を読めなかった区域は**何から解除されたかを言えない**ので伝えようがない。画面にも
  音にも出ないため記録だけ残す（`warnUndescribableCancel`）。実電文では `LastKind` を欠く区域は
  観測できていない（走査した区域 19,906 件で 0 件）
- **全区域が解除コードなら従来どおり正式解除**（`cancelled: true` / `cancelReason: 'lifted'`）。
  そちらは `cancelledAreas` を持たない
- 解除された `Item` は `Area` と `Category` しか持たない（波高・到達時刻・潮位観測点は付かない）
- **ブラウザ通知の本文には入れない。** 見出しがいま発表中の等級なので、その下に解除された区域を
  並べると「まだ出ている」と読める。通知は「いま何が出ているか」を伝えるもので、区域ごとの
  移り変わりはカードと読み上げが担う。**決めていないのではなく、入れないと決めている**
- **「解除」の表示が消えるのは、区域を伝える続報がその区域を解除として読めなくなったとき。**
  寿命を電文に預ける形は「気象庁は解除した区域を続報にも載せ続ける」という観測に乗っているが、
  **確かめられたのは 1 事象だけ**なので、読めなくなったら記録を残す（`warnIfCancelStopsEchoing`）。
  画面にも音にも痕跡が出ないため、実運用で確かめる手がかりはそこにしか無い。**記録は原因を
  断定しない** —— 続報が載せなくなった場合と、載ってはいるが前回の等級を読めなくなった場合の
  両方がここへ来る（後者はパーサー側が別に記録する）
- DMDATA XML 経路のみ。P2PQuake は解除コードに相当する値を配信しない（下記「バリアント差」）

#### 読み上げ

**文の組み立て・読み上げの優先度・通知音の扱いは
[audio-tts-spec.md](audio-tts-spec.md) §4「区域単位で等級が動いた報は、動いた区域だけを読む」が
単一情報源。** この節が持つのは電文の判定（どの区域がどちらへ動いたか）と既読の管理で、
文の作り方は向こうに置く ―― 同じ言い回しを両方に書くと、変えたときに片方だけ直す事故になる。

読み上げ文を作るのは `tsunamiAreaGradeChangeToSegments`。渡すのは**既読を除いた組**
（下記「既読は「最後に声にした等級」で持つ」）。

#### 既読は「最後に声にした等級」で持つ

**`LastKind` は等級が動いた瞬間だけでなく、その後の続報にも同じ値が載り続ける。** 02:30 で
解除された 2 区域は、02:31・02:33 の続報でも「津波予報／前回は津波注意報」のまま届いた。
電文の事実だけで読み上げると同じ文を 3 回読む。

記録（`spokenAreaGradeRef`）は区域ごとに「等級の変化として最後に声にした等級」を持ち、今回の
等級と一致していれば読み終えたものとして落とす（`selectUnspokenAreaGradeChanges`）。等級が
さらに動けば値が変わるので、もう一度読む。

- **進めるのは発話を始める瞬間だけ**（観測点の記憶と同じ規約。§10「読み上げた観測点の記憶は
  画面用と分ける」）。受信時に進めると、上位の読み上げに割り込まれて鳴らなかった変化が既読になる
- **読み上げが無効な端末だけは、タブを見せた時点で進める。** 声が出ないため発話の契機が無く、
  進めないと同じ変化を載せ続ける続報のたびに画面を奪う
- **専用の文を読んだ報だけに限らない。** 全体の等級が同時に動いた報では発表文・降格文が全区域を
  等級ごとに読み上げるので、動いた区域の「いまの等級」はそこで声になっている。限ってしまうと、
  次に全体が落ち着いた報で「〇〇から切り替えられました」を遅れて言い直す
- **ただし解除された区域はその例外。** 発表文・降格文が挙げるのは `areas` に居る区域だけなので、
  解除は専用の文を足したときにしか声にならない。読まなかった報では既読にしないこと
  （`speakableAreaChanges`）—— 等級を語れない電文（全区域が `Unknown`）がこれに当たる
- 解除・リセット・リプレイ復元では観測点の記憶と同じ 3 か所で落とす（§5「解除電文と表示中の
  津波の照合」）
- **リプレイを途中から始めるときは、開始時刻より前の変化を埋めること**（`restorePreWindowTracking`）。
  埋め忘れると、注入後の最初の続報が開始前に起きた解除を「いま起きた」ものとして読み上げる
  （観測点の記憶で防いでいるのと同型の穴）

#### 受信時スクロールとカードの表示

観測点が動いていない報でも、**等級が動いた区域へ寄せる**（`focusedDistrict`）。ここを「変化が
無い電文」の枝へ流すと画面は一番上へ戻り、何が変わったのか見えない。

カードでは区域名の下に「津波注意報から切り替え」「津波注意報から引き上げ」を出す。

- **出すのは直近の受信で動いた区域だけ**（`areaGradeChangedKeys`）。区域が持つ `lastGrade` だけを
  見て出すと、`LastKind` が続報にも載り続けるぶん何通も後まで「たった今切り替わった」ように
  見え続ける（読み上げは既読で 1 回に絞っているのに、画面だけ持続する非対称になる）。観測点の
  新規・更新バッジ（`obsUpdateStatus`）と同じく「今回分だけ」に置き換え、時間で消す
- **置き換えるのは、まだ声にしていない等級変化を持つ報のときだけ。** 津波の続報には等級について
  何も言っていないものがある —— 各地の満潮時刻・津波到達予想時刻に関する情報と津波観測に関する
  情報は、**区域一覧も `LastKind` も前報のまま載せて届く**。それらは `selectUnspokenAreaGradeChanges`
  が既読として全部落とすので、受信のたびに無条件で置き換えていたころは**等級が動いたことを伝える
  印が寿命を待たずに消えていた**（2024 年能登半島地震では、16:22 の引き上げの 30 秒後に満潮時刻の
  報が届いている）
- **消去のタイマーは観測点のバッジと分ける**（長さは共有＝`TSUNAMI_BADGE_TTL_MS`）。起点が違う
  ―― 観測点の印は受信のたびに置き換わるので「最後の受信」から、区域の印は等級が動いた報でだけ
  置き換わるので「その報」から数える。共有したままだと、等級を語らない続報が届くたびに張り直されて
  寿命が伸び続ける（津波が続いている間は数分おきに届くので、事実上消えなくなる）
- **別の津波へ切り替わったら落とす。** 印の鍵は区域コードだけで、どの津波のものかを持たない。
  津波予報区コードは固定なので、前の津波で動いた区域と同じコードが次の津波にも現れる。据え置く
  以上、ここで落とさないと前の津波の印が新しいカードへ持ち越される（解除を受けずに別の津波へ
  移る経路）。カードは「その区域がいま `lastGrade !== grade` か」も併せて見るので、これが無くても
  持ち越した印がそのまま画面に出るわけではない。**それでも落とす** —— 表示の正しさを別の判定に
  頼る形にすると、そちらの条件を緩めたときに前の津波の印が黙って出る。
  **切り替わったかの判定は、App が持つ表示中の津波ではなく自分が受信した直前の報で行う**
  （§5「解除電文と表示中の津波の照合」と同じ理由。表示中の津波は render 本体で代入されるため、
  同じ tick に複数の電文が捌けると tick 開始前の値に取り残される。そちらと比べると新しい津波の
  2 通目以降まで「新規発報」に見えて、1 通目が立てた印を消す）
- **等級が動いた報では置き換える（足し合わせない）。** 区域 A の印が残っているうちに区域 B だけが
  動いた報が来ると、A の印は消えて B の印になる。A の `lastGrade !== grade` はまだ成立しているが、
  この印が示すのは「直近の受信で動いた区域」なので前の報の分は持ち越さない。**置き換えること自体は
  この機能の初めからの挙動**で、上の 2 項が変えたのは置き換える契機（どの報で置き換えるか）だけ
- **前回が「津波なし」の区域には出さない** ―― 新規発表の報では全区域がそこから始まるため、
  全部の行に付いて意味を持たなくなる
- 等級の呼び名は読み上げと共有する（`TSUNAMI_GRADE_SHORT_LABEL`）

解除された区域は等級カードに居場所が無いので、**等級カードの後ろに無彩色の「解除」の枠**を置き、
区域名と「津波注意報を解除」の 1 行だけを並べる（`TsunamiCancelledCard`）。

- **等級カードの行（`TsunamiAreaRow`）を流用しない。** 波高・到達時刻・潮位観測点を描く前提で
  組んであるが、解除された区域はそのいずれも持たない
- **前回の等級は無条件に出す。** 等級カードの「〇〇から切り替え」は直近の受信で動いた区域だけに
  付くが、こちらは枠そのものが「この報で解除された区域」を意味するので絞る理由が無い
- 並べ替えは等級カードと同じ関数（`sortAreasForCardDisplay`）を通す。読み上げの並びと食い違うと
  追従スクロールがカード上を往復する
- 読み上げ追従と受信時スクロールの寄せ先になるよう、行は等級カードと同じ 2 つの登録
  （`registerRow` / `registerSpeechRow`）を通す。**カード自体は引き当て先にしない** ―― 等級カードが
  `grade:` の鍵を持つのは読み上げが等級を告げる箇所を指すためで、解除の読み上げは区域名しか指さない

#### 区域の顔ぶれが報ごとに変わること

**気象庁は津波予報区を報ごとに足し引きする。** 電文解説資料 Ⅱ.11 1-1-2．Item【津波の予測値
（津波予報区毎）】は「本情報で津波警報・注意報や津波予報（若干の海面変動）を発表している津波
予報区**及び津波警報・注意報を解除した津波予報区**について、発表状況を記載する。記載する津波
予報区の数に応じて、本要素が複数出現する」と定める。続く Ⅱ.11 1-1-2-2．Category（出現回数は
1 回）は「発表状況の状態遷移を表すために、一つ前の情報による発表状況を子要素 LastKind に記載
する」とし、挙げている事例はいずれも `LastKind = 津波なし(00)`。

**後から加わる区域は検出できている。** DMDATA のアーカイブ（`/v2/archive` の
`telegram.earthquake` 分類）のうち 2020-11-18〜2026-09-11 に存在する 2098 日ぶんの実測（地震電文
20,661 通のうち津波電文 634 通＝VTSE41 177・VTSE51 417・VTSE52 40。津波電文があったのは 105 日・
100 事象で、通常運用 434 通／訓練 200 通）。数えたのは **DMDATA XML 経路だけ**で、P2PQuake は
下記「バリアント差」のとおり構造的に検出できない。

以下はすべて**報の数**（区域の数ではない）。

| 数えたもの | 通常運用 | 訓練 |
|---|---|---|
| 前報に無い区域が現れた報 | 9 | 2 |
| 　うち等級変化を 1 件も拾えない（全体の最上位等級も動いていない） | **0** | **0** |
| 発表中の区域が残るのに解除コードで区域が落ちた報 | **2** | 25 |
| 　うち落ちた区域が前報では表示されていた | **1** | 8 |

- 加わった区域 126 件の `LastKind/Code` は**全件 `00`（津波なし）**だった。`parseLastKindGrade` が
  これを `Unknown` へ写すので `lastGrade` は埋まり、`tsunamiAreaGradeChanges` は「津波なし →
  注意報」の組として拾う（読み上げ文は `from === 'Unknown'` の分岐が担う）。区域 19,906 件のうち
  `LastKind` 要素を持たないものは 0 件
- **解除コードで落ちる側も実在する。** 通常運用の実例は 2025-12-09T06:20 の VTSE41（見出しは
  「津波注意報を解除しました。」）で、`青森県日本海沿岸` が `Kind/Code=60`（津波注意報解除）・
  `LastKind/Code=62`（津波注意報）として届いた。他の 7 区域は 62 → 72 の降格として電文に残るため、
  **降格として捕まえられるのは 7 区域だけ**で、解除された 1 区域は上記「解除された区域」が担う
- **同じ報で 13 区域が解除コード無しに消えている。** そちらは津波予報（`Kind/Code=71`）の区域で、
  予報には解除の概念が無く電文から外れるだけ。**この節の仕組みは扱わない** ―― 伝えようとすると
  前報との差分を取ることになり、「電文が自ら述べている事実だけを使う」という設計を崩す
- **解除コードの区域は続報にも載り続ける。** 06:22 の VTSE51（この事象の最終報）にも同じ形
  （`Kind/Code=60` / `LastKind/Code=62`）で入っていた。`LastKind` と同じ性質なので、既読の管理を
  通さないと同じ文を繰り返す

> 数え方: 区域を持つ報を `eventId` ごとに `Head/ReportDateTime` 昇順へ並べ、連続する 2 報の区域を
> `code ?? name` で突き合わせる。判定には実装の `parseTsunamiFromXml` と
> `tsunamiAreaGradeChanges` / `selectUnspokenAreaGradeChanges` をそのまま通した。観測点が動いたかは
> 読み上げの 4 述語（波高の上昇・欠測・観測中のまま警報相当・到達確認）を写して判定している。
> 解除後に同じ `eventId` で区域を持つ報が再び来た事象は標本中 0 件（並べ方が前報を取り違える形は
> 現れない）。
>
> **アーカイブが無い日が 26 日ある**（期間の暦日 2124 日に対し 2098 日）。その 26 日について
> P2PQuake（standard 版の取得元）の `jma/tsunami` を照会すると津波の発表は 1 日も無く、逆に
> P2PQuake が津波を配信した 24 日はすべて上の 105 日に含まれていた。**「アーカイブが無い日」と
> 「津波が無い日」は別物**なので、数を足すときはここも確かめること。

#### バリアント差

P2PQuake（standard 版）は `LastKind` に相当する項目を配信しない。`lastGrade` は常に undefined に
なり、この節の機能は **DMDSS 版のみ**で働く（解除経路と同じ非対称。§3「バリアント差」）。
**上の実測は DMDSS 版に対するもの**で、standard 版では区域が加わっても消えても等級変化としては
一度も検出されない。

### 観測情報と地震情報は互いに読み上げを切らない

等級が動いていない続報（観測点の波高更新・到達確認）は、**等級の発表より 1 段軽い扱いで読む**。
高い扱いのままだと、観測点の波高が 1 つ更新されるたびに地震情報の読み上げを途中で消していた。
あわせて「互いに切らない」相手として宣言しているため、逆に地震情報が観測情報を切ることもない。
詳細は [`audio-tts-spec.md`](audio-tts-spec.md) §6「内容が重ならない同格は互いに待つ（相互譲り）」。

引き下げ（警報 → 注意報）は等級が動いた報なので、新規・格上げと同じ扱いのまま（音だけは続報と
同じ更新音を鳴らす）。

### 読み上げた観測点の記憶は画面用と分ける

観測点の「もう伝えた」記憶は 2 つある。

| 記憶 | 用途 | 進めるタイミング |
|---|---|---|
| 画面用 | 観測点バッジ（新規／更新）・カードのスクロール先 | **受信時**（読み上げの有無に関わらず） |
| 読み上げ用 | 「更新があった観測点だけ読む」の差分 | **声に出す瞬間** |

**共有してはいけない。** 読み上げは待たされることがあり（上記のとおり地震情報と互いに待つ）、
待っている間に後続の電文へ置き換えられたり上位に切られたりする。受信時に既読にしてしまうと、
**一度も声に出ていない観測値がその観測点の既読になり、二度と読まれない**。分けておけば、鳴らな
かった分は次の電文で再び読み上げ対象に入る（実電文は既報の観測点も載せ続けるため、次の報で拾える）。

**既読にするのは「実際に声に出した分」だけ。** 電文に載っていても読まないものがある。

| 読まないもの | 理由 |
|---|---|
| 件数上限（5 件）で落ちた観測点 | 更新が多いときは波高の大きい順に絞る。絞り込みは読み上げ文の生成と同じ関数で行う（`selectObservationUpdatesToSpeak`） |
| 件数上限（5 件）で落ちた到達確認 | 到達確認も同じ上限で切る。絞り込みは読み上げ文の生成と共有する（`selectArrivalsToSpeak`） |
| 等級の発表に同梱された観測点の実測値 | 等級の発表で読むのは**区域の予想波高**。観測点は区域の並べ替えにしか使わない（到達確認だけは読む） |

**表示中の津波に向けた解除なら、観測点の記憶をすべて落とす**（波高と名前・画面用と読み上げ用の 4 つ）。
名前を残すと、前の津波で「観測中」（波高未確定）のまま終わった観測点は、次の津波で再び到達が
確認されても「新規到達」と見なされず、**到達を一度も伝えられない**。常時起動する使い方では
1 セッションで複数の津波をまたぐので実際に起こりうる。落とす範囲は画面用と読み上げ用で揃える
こと——片方だけ残すと「声は到達を伝えるのにバッジが付かない」（またはその逆）になる。

**別イベントの遅延到達した解除では何も落とさない。** 照合の規則はカードの状態更新と共有する
（§5「解除電文と表示中の津波の照合」）。津波は 1 件スロットなので、照合せずに落とすと進行中の
別の津波の既読が消え、その観測点が「新規」として読み直される。

**照合と落とす対象は分けて考えること。** 落とすのは記憶と画面の状態だけで、**音と読み上げは
照合せずに出す**（照合できない経路の解除を黙らせるより、解除を伝える方を優先する。理由は §5）。
そのぶん「解除を読み上げたのにバッジが消えない」食い違いは残る。

### 変化を伝えない続報

等級も観測波高も動かないまま届く報がある。従来はここで読み上げ文が空になり、**通知音だけが
鳴って何も伝わらなかった**。2024 年能登半島地震の 26 時間では、取消を除く津波電文 56 通のうち
7 通がこの形だった（満潮時刻の報 6 通と、最大波の観測時刻だけが動いた観測情報 1 通）。

| その報が載せているもの | 読む文 |
|---|---|
| 満潮時刻・到達状況（各地の満潮時刻・津波到達予想時刻に関する情報） | 見出し文 ＋ 変化の中身に応じた一文（下表） |
| 観測点（波高は据え置き・最大波の観測時刻だけ更新） | 「津波観測情報。◯◯、◯◯で、最大波の観測時刻が更新されました。」 |
| 観測点（何も動いていない） | 「津波観測情報。観測された波高に変わりはありません。」 |
| **区域一覧だけ**（観測点を運ばない報） | **読まない**（従来どおり黙る） |

**最後の行が要点。** 区域一覧だけを載せた報（津波警報等・VTSE41）が既読の等級変化しか持たない
とき、その電文は観測波高について何も述べていない。そこで「観測された波高に変わりはありません」
と言えば、**電文が言っていないことをアプリが言う**ことになる。言い切ってよい範囲は、その報が
載せている事実まで。

#### 満潮時刻の報が何を動かしたか

判定は `tideReportChange`。声にした満潮時刻・到達状況（`SpokenTideEntry`）と突き合わせる。

| 判定 | 条件 | 続く一文 |
|---|---|---|
| `first` | まだ一度も満潮時刻を声にしていない | （足さない。名乗りだけで意味が通る） |
| `tide` | 満潮時刻が動いた地点がある（初出の地点を含む） | 満潮時刻が更新されました。 |
| `arrival` | 満潮時刻は据え置きで、到達状況だけが動いた | 津波の到達状況が更新されました。 |
| `none` | どちらも動いていない | 内容に変わりはありません。 |

**`tide` と `arrival` を混ぜない。** 実配信の 6 通のうち 2 通（2024-01-01 20:30・01-02 02:31）は
**満潮時刻が 1 つも動かず到達状況だけが変わった報**だった。一括りに「満潮時刻が更新されました」
と読むと、気象庁が言っていないことを言うことになる。

**名乗りは気象庁の見出し文をそのまま使う**（「各地の満潮時刻と津波到達予想時刻をお知らせします。」）。
読めない電文では同じ文を定数から補う。**地点名も件数も読まない** —— 満潮時刻は 46〜52 地点ぶん
載るので読み切れず、件数を言っても聞き手にできることが増えない。

**この種別の判定は情報名で行う**（`isTideReport`）。津波情報（VTSE51）は「各地の満潮時刻・津波
到達予想時刻に関する情報」と「津波観測に関する情報」を名乗り分けるが、**どちらも区域の潮位
観測点を運ぶ**ので中身では見分けられない（能登では観測情報の側も 52 地点ぶんの満潮時刻を
載せていた）。満潮時刻を主題にしているのは前者だけ。

#### 最大波の観測時刻だけが更新された観測点

判定は `hasMaxHeightTimeChanged`。**電文が直接言っているもの**（`MaxHeight/Revise` = 更新）を
見る —— 時刻の比較だけで決めると、気象庁が更新と認めていない揺れまで拾う。

- **波高が上がった観測点は対象外**（そちらは波高の文が読む。二重に言わない）
- **欠測の観測点も対象外**（観測できていない地点に「最大波の観測時刻が更新されました」と言うと、
  いま観測できているように聞こえる）
- **波高は読まない**（前の報で既に声にした値を繰り返すだけになる）。言い直すと、値が上がったのか
  時刻だけが動いたのかを**聞き分けられなくなる** —— 群を分けている意味がそこにある
- **助詞は「へ」**（「23時26分へ更新されました」）。「に」だと「23時26分に更新した」とも読め、
  更新の時刻なのか更新後の観測時刻なのか紛れる。**これは観測情報の 3 つの群に共通する規律**で、
  波高の更新も第1波の訂正も「〜へ更新されました。」で閉じる
  （→ [`audio-tts-spec.md`](audio-tts-spec.md) §4「更新の着点は「へ」」）

##### 同じ報に波高の上昇が混じっても譲らない

かつては波高の文があるときこの群を落としていた（「時刻の更新の 21 回中 20 回が波高の上昇と同じ報で
起きるので、合流させると肝心の波高の話に脇道が付く」という判断）。**これは覆した。**

電文の波高は 0.1m 刻みなので、**実測が上がっても表示が動かない間は時刻だけが進む**。つまり
「時刻だけの更新」は**丸めの中で育っている**という事実を運んでいる。

2024-01-01 の VTSE51 全 38 通を観測点ごとに数えると、波高が同じまま最大波の観測時刻だけが動いたのは
**34 回**で、そのうち **28 回（82%）はその後に波高が階級をまたいで上がった**（下の「この形は珍しく
ない」が挙げる**延べ 44 のうち 01/01 ぶん**。あちらは 01/01〜01/02 の 2 日を数えている）。江差がその典型で、
`0.2m 18:11 → 0.2m 18:21 → 0.2m 18:36 → 0.2m 18:58 → 0.3m 19:45` と 4 回時刻だけが進んでから
階級をまたいでいる。**収束の印ではなく継続の印**なので落とさない。

- 譲るのをやめた後の件数は、2024-01-01 で 1 報あたり 1〜5 件（上限 5 件に触れる報は 0）。かつて
  8 件まで膨らんでいたのは、譲り続けて未読が積もっていたため
- **層も `tsunamiObs`（通常の観測情報と同じ）へ上げた。** 最下位に置いていたのは「伝える変化が無い報」
  だったからで、いまは新しい観測時刻という中身を読む —— 読み上げるものを持つ報を「何も切らない」層に
  置く理由は無い。最下位に残るのは満潮時刻の報と「観測された波高に変わりはありません」の 2 つだけ

記憶は波高（`spokenObsHeightRef`）とは別に持つ（`spokenObsMaxHeightTimeRef`）。同じ観測点に
ついて別々に起きうる事実なので、記憶も別にする。

**画面もこの報で動かす。** 対象はカードのバッジ・カードの自動スクロール・地図のカメラ追従の 3 つ。
波高が据え置きなので値だけを見る仕組みでは捉えられず、読み上げが「◯◯で、最大波の観測時刻が
更新されました」と名指ししているのに、画面がその観測点をどこにも示さない状態になっていた。

- 判定の本体は `hasMaxHeightTimeAdvanced`（`utils/tsunami.ts`）。読み上げ側の
  `hasMaxHeightTimeChanged` はこれに読み上げだけの条件（上記 3 つの対象外）を重ねる
- **画面用の記憶は読み上げ用と分ける**（`lastMaxObsTimeRef` / `spokenObsMaxHeightTimeRef`）。
  画面は受信した全観測点を常に最新へ進めるが、読み上げは**声にした分だけ**進める（待たされた末に
  見送られた観測点まで既読にすると、その更新は二度と読まれない）
- **画面用の記憶は波高の記憶とも分ける。** 波高は「上がったときだけ」更新するので、混ぜると
  波高が据え置きの報で時刻だけが取り残される
- この形は珍しくない。**上と同じ 56 通**のうち観測点を運ぶ津波情報（VTSE51）49 通を観測点ごとに
  数えると、**波高が据え置きのまま `MaxHeight/Revise` が「更新」になった観測点は延べ 44、21 通の報に
  またがる**（01/02 00:51 の舞鶴 0.4m・玄海町仮屋 0.1m など）。冒頭の「7 通」とは**数えている対象が
  違う** ―― あちらは読み上げ文が空になった報の数で、波高が上がった観測点が同じ報に混じっていれば
  そちらの文が出るため空にならない。それでも時刻だけが動いた観測点は画面に現れないままだった
- 「更新」以外の `Revise`（「追加」）では動かさない。同じ集合で「観測中」と併記された `Revise` が
  5 件あり、いずれも「追加」だった
- 実機で確かめる入口は設定タブの「変化の小さい続報テスト」（3 通目）

#### これらは何も切らない

読み上げの層は最下位（`SPEECH_PRIORITY.commentary`）。**満潮時刻の報は等級の発表の直後に届く**
—— 2024 年能登半島地震の 6 通はすべて 0〜60 秒後で、うち 2 通は同じ分だった。`normal` に置くと、
大津波警報の区域を読み上げている最中に「内容に変わりはありません」が 90 秒後に割り込んで切る。

**最大波の時刻だけが動いた報は、もうここに居ない**（上記「同じ報に波高の上昇が混じっても譲らない」）。
最下位に残るのは満潮時刻の報と「観測された波高に変わりはありません」の 2 つ。

**主題も 2 つとも別に持つ**（満潮時刻 = `tsunamiTide` ／ 静穏な観測情報 = `tsunamiObsQuiet`）。
到来順の裁き（`overtakenByLaterArrival`）は**優先度を見ずに、同じ主題の先発を取り下げる** ——
「同じ主題の中では優先度は常に等しい」という前提に立っているため。層の違うものを `tsunamiObs`
へ相乗りさせると、上位に待たされている実測の波高更新を、あとから届いた「変わりはありません」が
**声にならないまま握りつぶす**。等級の発表（`tsunami`）と観測情報（`tsunamiObs`）を分けたのと
同じ理由で、ここも分ける。

**そのぶん、待ちきれなければ黙る。** 等級の発表を読んでいる最中に届いた報は声にならないことが
ある —— そこで鳴っているものの方が重いので、これは受け入れている損失。黙った分は既読にならず、
次の報で機会が来る。

#### 記憶は 3 つの経路すべてで埋める

新しく持った記憶は 2 つ（`spokenTideRef` / `spokenObsMaxHeightTimeRef`）。**落とす場所**は解除・
リセット・リプレイ復元の 3 つ、**埋める場所**は発話を始める瞬間とリプレイの窓の手前の復元
（`restorePreWindowTracking`）。

- **窓の手前の復元を忘れると**、途中から再生を始めたとき、既に伝えた満潮時刻が「初報」として
  読み直される（`tideReportChange` は記録が空なら無条件に `first` を返す）
- **波高の文を読んだ観測点の時刻も記録する。** 記録しないと、次の静穏な報で同じ観測点が
  「最大波の観測時刻が更新されました」と読み直される（記録が無い＝変わった、と判定されるため）。
  波高の文は時刻そのものを読まないが、**その報で最大波が更新されたことは伝えている**
- **時刻の判定はその報自身が載せた観測点に限る**（`observationsInCardOrder` が既にそう絞っている
  —— カードの並びへ差し替えたあと、その報の観測点と**参照で**照合している）。カードの材料は前報から
  マージ済みなので（`mergeTsunamiObservations`）、混ざれば「この報は何も言っていないのに時刻が
  更新された」と読むことになる。**あの照合を名前や複製へ変えるなら、判定の側で絞り直すこと**

## 11. 自動タブ切替

tsunami タブへの強制切替は「**新規発報／grade 格上げ**」のときのみ発火する
（`useLiveEventHandler.ts` の tsunami 分岐）。判定は `src/utils/tsunami.ts` の
純関数 2 つに分離してテスト可能にしている:

| 判定 | 定義 | true の条件 |
|---|---|---|
| `isTsunamiNewFire(next, current)` | 新規発報か | `current` 無し／取消済み／`eventId` 相違、または `eventId` 欠落時に `sourceEarthquake.originTime` 相違（DMDATA XML の Earthquake 要素経由のフォールバック） |
| `isTsunamiGradeUpgrade(next, current)` | grade 格上げか | `MajorWarning > Warning > Watch > Forecast > Unknown` の順で `next > current` |

EEW の発表状況は判定に入れない（下記「優先度ルール」参照）。

**バリアント差**: DMDSS 版（DMDATA）は電文に 14 桁 `eventId` が常に付与されるため厳密判定が可能。
標準版（P2PQuake）の `code=552` は生 JSON に `eventId` を持たず、`earthquake` 相当のフィールド自体が
無いため `sourceEarthquake` も常に `undefined` になる。よって上表の `originTime` フォールバックは
**標準版では事実上常に不成立**し、保守的な続報扱い（別地震の新規津波でもタブが奪われない）が
デフォルト挙動になる。ユーザーは grade 格上げ検知か手動タブ切替で対応する必要がある。

タブ移動の入口は**読み上げの有無で分かれる**（規則の全体は
[`audio-tts-spec.md`](audio-tts-spec.md) §6「自動タブ切替の優先順位」が単一情報源）。

| 読み上げ | 何が tsunami タブへ移すか |
|---|---|
| 有効 | 読み上げの発話を投入する瞬間に `followSpeechTab('tsunami', …)`。**観測点更新（grade 不変の続報）でも、読み上げ文が組める続報なら移る**（変化のない続報は読み上げ文が空になり移らない） |
| 無効 | 受信の瞬間に `setActiveTabNonRealtime('tsunami')`。新規発報・grade 格上げのほか、**観測点更新でも移る**（判定は下記） |

読み上げが無効なときの観測点更新の判定は、`obsUpdateStatus` / `focusedDistrict` の更新で使っている
「観測が動いたか」をそのまま流用する（波高が伸びた観測点、または波高未確定で新たに到達した観測点が
1 つ以上あるか）。変化のない再送では動かない。**判定を増やさずに済むよう、意図的に同じ場所に
相乗りさせている**ので、この判定を動かすときはタブ移動にも影響することを意識すること。

読み上げが有効でも、`setActiveTabNonRealtime('tsunami')` は保険として残っている。読み上げ文が
組めない電文が「新規発報」と判定された場合に、tsunami タブへ一度も移らない事態を避けるため
（読み上げが無ければ追従も発火しない）。いま残っているのは「区域はあるのに、その等級がすべて
未知コードで判定できない」という異常な形だけ。区域を持たない続報は観測点更新として読み上げるので、
この保険には掛からない（§10「等級を伝えていない電文」）。

`title.showTsunamiTitle()` は続報でも呼ぶのでタイトルバッジは維持される。

**優先度ルール**（tsunami × EEW の同時発報時）:

- **EEW が realtime を確保していても、津波の読み上げの番が来れば tsunami タブへ移る**（読み上げ
  追従どうしは保持を見ないため。声が津波を読んでいる間は津波を見せる）。EEW のレベル（予報／
  警報／特別警報）は判定に関与しない
- **移ったあと、EEW の続報では realtime へ引き戻されない。** EEW の続報は他の情報が確保している
  画面を奪わない規則があるため（これが無いと数秒ごとに画面が往復する）。EEW の新規発報・
  レベルアップ・誤報取消は引き戻す
- 読み上げが無効な端末でも、EEW 続報が確保している画面は越えて tsunami へ移る。越えられないのは
  新規発報・レベルアップ・誤報取消が張った 15 秒だけ（詳細は
  [`audio-tts-spec.md`](audio-tts-spec.md) §6「自動タブ切替の優先順位」）
- 解除・取消・失効も同様にタブを奪う。**タブ切替・解除音・読み上げ**は `alreadySpoken`
  （eventId 単位の重複抑止）を条件とし、**タイトルの `endTsunamiTitleWindow()` と状態リセット**
  （観測バッジ・保持していた最大波高・スクロール位置）は無条件に実行する
- ただし操作も情報の更新も途切れると、自動復帰（設定の「自動復帰までの時間」= `idleRevertSec`。
  [`settings-pwa-spec.md`](settings-pwa-spec.md) §2）が働く。これはタブの種類を問わない共通の
  仕組みで、EEW 発報中・揺れ検知中であれば realtime タブを維持する（tsunami タブも例外ではなく、
  津波発表中でも realtime へ移る）。**津波受信の瞬間に tsunami を見せることと、その後どのタブに
  落ち着くかは別の仕組みが決めている**
