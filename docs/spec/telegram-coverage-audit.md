# 電文の網羅性を点検する

> 本書は**気象庁の電文解説資料が定義する要素と、実装が実際に読んでいる要素を突き合わせる**ための手引き。
> 読者は、この点検を続ける人と、「この値、電文には載っているのに画面に出ていないのでは」と疑った人。
> **本書と実装が食い違う場合は実コードを正とする。**
> 関連: [`data-sources-spec.md`](data-sources-spec.md)（電文の受信経路）、
> [`quake-spec.md`](quake-spec.md) / [`tsunami-spec.md`](tsunami-spec.md) / [`eew-spec.md`](eew-spec.md)（読んだ値の使い道）。

## 1. 何を数えているか

「読んだ」の定義は **`textContent` を取ったか、`getAttribute` を呼んだか**の 1 つだけ。
要素の名前を比べただけ（`localName` の参照）は数えない —— XML を走査するヘルパーは
全子孫の名前を見て回るので、数えると電文の全要素が「読んだ」ことになる。

数え上げには 2 つの母集団がある。**どちらか一方に乗り換えず、和を取ること。**

| 母集団 | 見つかるもの | 見えないもの |
|---|---|---|
| 実電文（手元のサンプル） | 実際に届く形。資料が書き漏らした要素も出る | サンプルに現れなかった条件付きの要素 |
| 解説資料 | 条件付きの要素（失効時刻・仮定震源要素の欄など） | 資料に載っていない実運用の形 |

乗り換えると、片方だけが見つけていた分が黙って落ちる。

## 2. 測り方

計測台は [`src/services/dmdataCoverage.probe.test.ts`](../../src/services/dmdataCoverage.probe.test.ts)。
実電文を本物のパーサーへ流し、取り出した要素・属性を記録する。**環境変数を渡したときだけ動く**ので、
通常の `npm test` は汚さない。

**静的解析（ソースの文字列からアクセサ呼び出しを推し量る方法）は使わない。** 敵対的レビュー
4 巡で毎巡新しい取りこぼしが出て収束しなかった —— **JavaScript の書き方が増えるたびに穴が開く**
構造だったため。どんな書き方で漏れたかは計測台の冒頭コメントに並べてある。
静的解析の結果は、いまは**実測との突き合わせ**にだけ使う（実測で通らなかった経路と、
静的側の誤りを見分けるため）。

スクリプトは [`scripts/telegram-audit/`](../../scripts/telegram-audit/) にある。
**入力の 2 つはリポジトリに入っていない**ので、測る人が手元へ揃える。

- **実電文のサンプル** —— `fetch-samples.mjs` が DMDATA のアーカイブから集める
  （`npm run capture-scenario` と同じ API キーを使う）。配信元の利用規約により
  **リポジトリへは入れられない**
- **解説資料のテキスト** —— 気象庁が配る PDF をテキスト化し、`eq_manual.txt` の名前で置く。
  資料の再配布にあたるため**リポジトリへは入れられない**（手順は下記）

置き場所は環境変数 `TELEGRAM_AUDIT_DIR` で渡す。実電文はその下の `telegram-cache/` に置くか、
`TELEGRAM_CACHE` で別に指す。計測の生データ（`dynamic-coverage.json`）と突き合わせの出力
（`triage-result.txt`）も同じディレクトリを使う。

### アーカイブは一度取れば控えから読む

アーカイブ（日ごとの `.tar.gz`）の取得は [`archive-cache.mjs`](../../scripts/telegram-audit/archive-cache.mjs)
の 1 本に集約してある。**なぜ控えるのか・配信元の上限がいくつかは
[`data-sources-spec.md`](data-sources-spec.md) §2「リクエスト数を抑える」が単一情報源**で、
ここに書くのは監査スクリプトを走らせる人が知る必要のあることだけ。

**この棚卸しのスクリプトだけが通るのではない。** テストデータの生成スクリプト
（`npm run build-test-quake` ほか）も同じ口を通り、**同じ控えを読む** —— 監査が既に取った日は
生成側でもリクエストが出ないし、逆も同じ。

- **控えの場所は `.claude/dmdata-archive-cache/`**（`.gitignore` 済み。`DMDATA_ARCHIVE_CACHE` で
  変更できる）。アーカイブは 1 日分を締めたあとに生成される不変のファイルなので、**2 回目以降の
  走査はリクエストを 1 件も出さない**（実測: 同じ範囲の 2 回目が「控えから 2 件 / 取得 0 件」）
- **ワークツリーで走らせると控えもそのワークツリー内に作られる。** 使い捨てのワークツリーで
  初回の走査をやり直したくなければ、`DMDATA_ARCHIVE_CACHE` でメインの checkout 側を指す
- 控えの名前には一覧が示す id を含めるので、**上流がアーカイブを作り直せば自動で取り直す**。
  解けない控えは捨てて取り直す（黙って消さず記録を出す）
- **初回の全期間走査は数時間かかる。** 取得の間隔を配信元の上限に合わせて直列に空けるため。
  `fetch-quake-times.mjs` の `CONCURRENCY` は控えから読む分の並列度で、ネットワークへ出る
  ところは待たされる。控えが埋まれば次からは待たない
- **一覧のページ送りには上限（20 ページ ＝ 2000 件）がある。** 達したら例外にし、下の
  「取得できなかった範囲」へレンジ単位で載せる。**黙って切ると、走査できなかった期間が
  「アーカイブが無かった」に化けて集計へ混ざる** —— このスクリプトは網羅性を主張するために
  使うので、そこは失敗として数える。出たら範囲の指定を疑うこと（正常な範囲はここに触れない）
- **走査できなかった範囲は最後に必ず出る**（標準エラーへ「取得・解析できなかったものがあります」）。
  そこは「見ていない」のであって「無い」のではない。**0 件という結論を出すときは、この行が
  出ていないことを確かめること**（2026-09-11 に走査先を間違えて誤った 0 件結論を出した前例がある。
  → CLAUDE.md「調査レビュー」）
  - 数えるのは**範囲**の件数で、日数ではない。一覧の取得に失敗した分は
    `2026-01-01~2026-01-02（一覧）` のようにレンジ単位で 1 件になる（**1 件が複数日を覆いうる**）
  - 標準出力の JSON にも、中間成果物にも、下流のレポートにも同じ印が載る。あわせて
    終了コードも非 0 になる。運び方は下記「取りこぼしは印として下流へ運ぶ」

```bash
# 0. 実電文のサンプルを集める（初回だけ。API キーは DMDATA_API_KEY か .env.local から読む）
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/fetch-samples.mjs

# 1. 実電文を本物のパーサーへ流し、読んだ要素・属性を記録する
TELEGRAM_CACHE=<作業ディレクトリ>/telegram-cache \
  COVERAGE_OUT=<作業ディレクトリ>/dynamic-coverage.json \
  npx vitest run src/services/dmdataCoverage.probe.test.ts

# 2. その記録と解説資料を突き合わせ、種別ごとに未読を並べる
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/triage.mjs
```

**計測の出力先（`COVERAGE_OUT`）は `TELEGRAM_AUDIT_DIR/dynamic-coverage.json` に揃えること。**
揃っていないと 2 が生データを見つけられない。

`header-survey.mjs` は計測を要らない。実電文だけ渡せば動く。

```bash
node scripts/telegram-audit/header-survey.mjs <実電文のディレクトリ>
```

| スクリプト | すること |
|---|---|
| `fetch-samples.mjs` | 実電文のサンプルを DMDATA のアーカイブから集める |
| `triage.mjs` | 計測結果と資料を突き合わせ、種別ごとに未読を並べる |
| `header-survey.mjs` | 実装を通さず、`Control` と `Head` の中身を種別ごとに並べる。判定を経由しないので `triage.mjs` とは独立に動く（ただし集計の分母は収集の結果に左右されるので、札は読む） |
| `where-defined.mjs` | 資料が同じ要素名を**どこで何回定義しているか**を並べる。未読を仕分けるときに通す（下記） |
| `coverage-core.mjs`・`read-model.mjs`・`handled.mjs` | `triage.mjs` が使う判定（置き場所の解決と対象種別は `fetch-samples.mjs` も借りる）。**同じ判定を複数のスクリプトに持たせない**（片方だけ直すと数字が食い違い、どちらが正しいか分からなくなる） |
| `archive-cache.mjs` | アーカイブの取得・ローカルの控え。**アーカイブを取るスクリプトが必ず通る**（この棚卸しの 3 本と、テストデータの生成スクリプト 3 本。上記「アーカイブは一度取れば控えから読む」）。取得の間隔は下記 `lib/rateGate.mjs`、取りこぼしの記録は `lib/incompleteness.mjs` に任せる。**生成スクリプト用の実行の定型**（`runArchiveScript`）も持つ —— 本体を包んで、取得の実測値と取りこぼしの印を成功・失敗のどちらでも出す。**この棚卸しの 3 本はこれを通らない**（トップレベルで処理する形で、包む本体を持たないため。末尾で 2 つを並べて呼ぶ同じ規約を別の形で満たしている） |
| `collection-mark.mjs` | 実電文サンプルの収集が完遂したかを伝える札の置き場所と読み方。**収集の成果物は `telegram-cache/` に並ぶファイルそのもので、そこへ印を載せられない**ため別に置く（下記「取りこぼしは印として下流へ運ぶ」） |

次の 3 本は `scripts/lib/` にある（`telegram-audit/` の外）。**この棚卸し専用ではなく、生成スクリプトも使う**ため。

| モジュール | すること |
|---|---|
| `lib/rateGate.mjs` | 取得の間隔を守る門（`gate`）。**取得元ごとに `kind` を分ける**汎用の仕組みで、`archive-cache.mjs`・`fetch-p2p-history.mjs`・`lib/stationSource.mjs` が同じものを通る。**待つ前に枠を予約する**（`await` の後に書き込むと並列呼び出しが一斉に発火する）。元は `archive-cache.mjs` の中にあり、DMDATA 専用に見えて他から使われていなかった |
| `lib/incompleteness.mjs` | 「取得・解析できなかった」という印を、スクリプトのあいだで運ぶ（下記「取りこぼしは印として下流へ運ぶ」） |
| `lib/repo-root.mjs` | リポジトリの根のパスだけを持つ。`coverage-core.mjs` は import した時点で `TELEGRAM_AUDIT_DIR` を要求するため、**根だけが必要なモジュールをそちらへ依存させない**ために分けてある |

### 取りこぼしは印として下流へ運ぶ

これらのスクリプトの出力は「この種別は 0 件だった」という**網羅性の主張の根拠**になる。
だから「集めたが 0 件」と「集められなかった」を区別できない形で残してはいけない。

**引き継ぎは読み取りの副作用にしてある。** 中間成果物（JSON）を `readArtifact` で読むと、
そのファイルが持つ印はその場で呼び出し側の台帳へ入り、`writeArtifact` / `markResult` で
自動的に出ていく。**引き継ぎのコードを各スクリプトへ書かない** —— 書く形にすると、
パイプラインにホップが増えるたびに同じ手当てが要り、1 つ書き忘れればそこで印が消える。

| 使う関数 | いつ |
|---|---|
| `noteIncomplete(源, 事実)` | 自分が取りこぼしたとき。源ごとに 1 行へ畳まれる（件数が増えても行数は増えない） |
| `readArtifact(パス, { source })` | 中間成果物を読むとき。**読んだ時点で引き継がれる**。`optional` を立てるとファイルが無くても印にしない（無いのが普通の入力用） |
| `writeArtifact(パス, データ)` | 中間成果物を書くとき。印は `_incomplete` としてトップレベルに載る |
| `markResult(結果)` | 標準出力の JSON が結果そのもののとき |
| `checkpoint()` | **1 つのプロセスが独立した成果物を複数書くとき**。`writeArtifact` の `since` へ渡すと、その後に積まれた分だけが印になる |
| `incompletenessBanner(体裁)` | 人が読むレポート（`.md` / `.txt`）の頭に断りを入れるとき |
| `reportIncompleteness(見出し)` | 終わりに標準エラーへ出す。**戻り値を見て呼び出し側が exit code を立てる** |

守っている決まりは 3 つ。

- **ファイルには取りこぼしが無くても印の欄を書く。** 欄が無いことを「完全」ではなく
  「この仕組みを通っていない＝不明」と読ませるため。手元に残った古い中間ファイルが
  黙って「完全に集めた」に化けるのを防ぐ
- **標準出力には、取りこぼしが無ければ何も足さない。** あちらは別のスクリプトが読み、
  こちらは人が読む。**前提が違うので扱いも分ける**
- **1 つのプロセスが独立した成果物を複数書くときは、区間で区切る**（`checkpoint()`）。
  台帳はプロセスごとに 1 本なので、区切らないと**完璧に走査できた分の成果物にも
  別の分の取りこぼしが載る**。下流はそれを読んで「このレポートのどの節も『無い』の根拠に
  するな」と出すので、事実に反する警告になる —— **事実に反する警告は、本物の警告を軽く見せる**。
  いまの対象は `fetch-quake-times.mjs`（分類ごとに `meta.json` を書き、下流は分類ごとに読む）
- **迂回できないようにする。** ヘルパーを作っても、素の `fs` で読み書きする経路を 1 本
  足せばそこで印が消える。[`scripts/incompletenessPropagation.test.ts`](../../scripts/incompletenessPropagation.test.ts)
  が `npm test` で**ファイルの読み書きを 1 件残らず数え上げ、理由付きの許可と突き合わせる**。
  新しい読み書きを足すと必ず落ちるので、書いた人は「ヘルパーを通す」か「中間成果物ではない
  理由を書く」かを選ぶことになる
  - **「怪しい書き方を探す」形にはしない。** 最初はそう書いたが、変数へ入れる・複数行に
    分ける・非同期版を使う、のどれでも素通りした。§2 冒頭が `triage.mjs` について書いている
    「JavaScript の書き方が増えるたびに穴が開く構造」と同じ形になっていた

**ファイルの山には印を載せられない。** 実電文サンプルの収集（`fetch-samples.mjs` /
`fetch-rare-samples.mjs`）の成果物は `telegram-cache/` に並ぶ XML と二進のファイルそのもので、
JSON ではない。そこで `collection-mark.mjs` が定める札を別に置き、
入力に使う側（計測台・`triage.mjs`・`testdata-shapes.mjs`・`header-survey.mjs`）が読む。

- **成功したときも札を書く**（上の 1 つ目と同じ理由）
- **走査を始める前に古い札を消す。** 残すと、今回の収集が途中で落ちたときに**前回成功した
  ときの札が今回の成果物に対する「完了報告」として読まれる**
- **札は「1 回の収集」ごとに分ける。** スクリプト単位では足りない ——
  `fetch-rare-samples.mjs` は対象（`eew` / `ixac41` / `type:VXSE60`）を変えて複数回走らせる
  設計なので、対象で分けないと最後に走らせた 1 回の成否しか残らない

`where-defined.mjs` も計測を要らない。解説資料のテキストだけで動く。

```bash
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/where-defined.mjs        # 定義が 2 箇所以上ある要素を全部
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/where-defined.mjs Revise  # 名前を指定
```

**未読を仕分けるときは、名前ごとにこれを通すこと。** `triage.mjs` の一覧は要素名でまとめるため、
**同じ電文種別の中で階層が分かれている要素**は 1 行にしか見えず、片方だけ読んでいる状態が
一覧からは分からない（→ §5「同じ名前が資料の複数箇所で定義されている」）。

出力はこう読む。

```
Revise  （定義 5 箇所 / 2 章）  ★同じ章に複数の階層
    Ⅱ.33 2-1-3-2  情報の更新（都道府県）  [VXSE53]  5219 行目
```

- 章が分かれているだけなら、電文種別ごとに 1 つずつあるということ（普通の形）
- **`★` が付いたら要注意** —— 同じ電文種別の中で階層が分かれている。1 つ読んで満足すると残りを落とす
- 末尾の「対象 N 件」は並べた要素名の数（引数を渡さなければ、定義が 2 箇所以上あるものすべて）

**リポジトリの根はスクリプト自身の位置から導いている。** 絶対パスを書くと、別の作業場に置いた
古い実装を測ってしまう。

**サンプルの集め方には判断が入っている**（`fetch-samples.mjs` に理由付きで書いてある）。
種別ごとの上限で打ち切ること、**同じ事象の続報を採らない**こと（「最初の 8 通」だと 1 つの地震の
連続報で埋まり、区域構成も付加文も似通う）、南海トラフの解説情報だけは号数まで鍵に含めること
（`EventID` が固定のため事象で畳むと 1 通になる）、打ち切りは対象の種別だけで数えること
（全種別で数えると対象外が先に埋まって収集が途中で止まる）。**通数を増やすより先にここを読むこと。**

### 未読を作業対象から外す 2 つの篩

未読はそのままでは点検の役に立たない形で膨らむ。`triage.mjs` は 2 段で篩う。
**どちらも外した分を出力へ並べる** —— 黙って落とすと「読まないと決めた」と「読み落とした」を
区別できなくなる。

1. **§3 で決めてあるもの**（`coverage-core.mjs` の `DECIDED_PATHS`）。**要素と属性で同じ
   登録簿を通す** —— `Head/Headline/Information` のように配下ごと読まないと決めた枝は、
   要素も属性も同じ理由で外れる
2. **単位・型の宣言**（属性だけ）。値が 1 種類で、**かつその経路に必ず付いている**もの

**1 つ目の篩は無かった。** §3 の決定を参照する仕組みは `scanManual()` の中にしかなく
（`CHAPTER_I_SCOPE`・`HEADLINE_INFORMATION_ELEMENTS`）、効くのは**資料にしか現れないもの**の
数え上げだけ。実測で未読と出た側は要素も属性も §3 を見ておらず、決めてあるものを数え続けていた。

2 の条件を 2 つにしているのは、値の一様さだけでは宣言と言えないため。

- **付かないことがある属性は、値が固定でも出現そのものが情報を運ぶ。**
  `jmx_eb:Magnitude@condition` は資料が固定値「不明」と定めており値は永久に 1 種類だが、
  出るのは規模が不明のときだけ。値だけで落とすと「情報を持たない宣言」と誤る
- **数えるのは経路ごと。要素名でまとめない。** `jmx_eb:TsunamiHeight@condition` は予想側では
  「不明」、観測側では「上昇中」と、同じ名前でも枝によって値域が違う。合算すると片方の標本が
  無いだけで 1 種類に見える。要素の出現回数も枝で大きく違うので（`Code` は電文の多数の枝に
  出る）、比を取る分母も経路で揃える

**これで標本の厚みの限界が消えるわけではない。** 常に付いていて値も 1 種類だったものは、
資料が値を固定しているのか**この標本で 1 種類しか出なかっただけ**なのかを実測では区別できない。
出力に値と厚み（属性の出現回数／要素の出現回数）を添えてあるので、読む人が資料と突き合わせる。

**資料側の裏取りは「固定値」の語だけを探しても足りない。** 資料は同じことを別の言い回しでも
書く（`@type` に「参照すべきコード種別"震央地名"を記載する」・`@codeType` に「"固定付加文"を
記載する」）。属性名ごとに定義文を当たること。一方で**本文が値を固定していないもの**もある ——
長周期地震動の `@unit`・`@PeriodUnit` は本文が値に触れず、資料の**実例にしか**現れない。
実例は「その値が出る」ことしか示さないので、他の値が出ないことは資料からは言えない。

### 点検そのものが壊れていないかを見る（自己診断）

**この点検は読み落としを見つけるための道具なので、「何も検出しなかった」が「壊れていた」を
意味しうる。** `triage.mjs` は数字を出す前に 3 つを確かめ、引っかかったら報告の先頭と標準エラーへ
出す。

| 確かめること | 引っかかると何が起きていたか |
|---|---|
| 生データが**いまのパーサー**を測ったものか | 計測は失敗すると書き出さない（書き出しは完走後）ので、前回成功したときのファイルが残る。**実装を変えたのに古い計測で「問題なし」と報告する** |
| 計測台の経路を電文の走査側で引けるか | 経路を組む実装が 2 つある（`scanTelegrams` と計測台の `pathOf`）。ずれると値 0 種類として未読へ倒れ、件数が膨らんで点検が役に立たなくなる |
| §3 の登録項目が当たっているか | 経路の綴りを間違えても照合が当たらないだけで、エラーにも記録にもならない。**決めたつもりで効いていない**項目ができる |

**3 つ目は 0 件でなくてよい。** 標本にその形の電文が無いだけのこともある。「綴り違い」と
「標本に無い」のどちらかを確かめる合図として読む。

来歴（`__meta`。計測時刻・通数・パーサーの内容のハッシュ）は計測台が生データの先頭へ書く。
**電文種別と衝突しない鍵にしてある**ので、突き合わせ側の種別ごとのループは読み飛ばす。

### 解説資料のテキストを作る

気象庁が[技術資料のページ](https://xml.kishou.go.jp/tec_material.html)で配る「解説資料セット」に、
地震火山関連の解説資料が入っている。**`curl`・`unzip`・`pdftotext`（poppler）が要る** ——
Windows では既定で入っていないので、別途用意すること。

```bash
curl -sSL -o manual.zip "https://xml.kishou.go.jp/jmaxml_20260826_Manual(pdf).zip"
unzip -q manual.zip -d manual
pdftotext -enc UTF-8 -layout manual/<地震火山関連の PDF> <作業ディレクトリ>/eq_manual.txt
```

- **URL の日付は更新される。** 上のページで最新のものを確かめること
- **`unzip` は Shift-JIS のファイル名を壊す**ので、地震火山関連の PDF を名前で選べない。
  **サイズで見分ける** —— 5MB を超えるのはこれだけ（→ §5「道具の癖」）
- **`-layout` を付ける。** 付けても付けなくても拾える要素の数は同じだが、付けると行が細かくなる。
  `scanManual()` は**行ごとに章を割り当てる**ので、1 行に複数の章の内容が混ざらないほうがよい

`scanManual()`（`coverage-core.mjs`）が読むのは次の 2 つで、**どちらも全角**。変換で失われると
章の判定か要素の抽出が丸ごと空になる。

| 手掛かり | 形 | 使い道 |
|---|---|---|
| ページの柱 | `Ⅰ－1`・`Ⅱ.11－3` | その行がどの章か（＝どの電文種別か）を決める |
| 要素の定義 | `Kind【種類】` | 資料が定義している要素を拾う |

作れたかは数で確かめる。2026-09-09 時点の資料（令和 7 年 12 月版）では**柱 160・要素定義 509**。

```bash
grep -cE "(Ⅰ|Ⅱ\.[0-9]+)－[0-9]+" <作業ディレクトリ>/eq_manual.txt   # 柱
grep -oE "[A-Za-z_][A-Za-z0-9_:]*【" <作業ディレクトリ>/eq_manual.txt | wc -l   # 要素定義
```

**0 件なら変換で全角が落ちている。** その状態でも `triage.mjs` は動いてしまい、
「資料が何も定義していない」という結果を返す。

### テストデータを実電文と突き合わせる

**同じ作業ディレクトリを使う、別の突き合わせ。** 上は「電文の要素を実装が読んでいるか」を
測るが、こちらは**テストボタンのデータが実電文の形をしているか**を測る。テストボタンは実機で
挙動を確かめられる唯一の入口で、そこに無い形は一度も画面に出ない（→ CLAUDE.md「テストボタンは
実機確認の唯一の入口」）。放っておくと実装が仕様へ寄るぶんだけずれが広がる。

| スクリプト | 役割 |
|---|---|
| `fetch-p2p-history.mjs` | P2PQuake の公開 API から履歴を集める（**認証不要**）。standard 版が実際に受け取る形の標本 |
| `fetch-rare-samples.mjs` | `fetch-samples.mjs` が取りこぼす標本を名指しで集める（二進電文の IXAC41・頻度の低い種別・条件付きの要素を持つ EEW） |
| `testdata-shapes.mjs` | 実電文とテストデータを**本物のパーサー・本物のファクトリへ通し**、出来上がった内部型のプロパティ経路を記録する |
| `testdata-compare.mjs` | 突き合わせて A〜E の 5 表を書く |

**測るのは内部型のオブジェクトの経路**で、ソースの文字列ではない（理由は上と同じ）。
配列は `[]` に畳み、`undefined` は数えない。**型付き配列も配列として畳む** —— 畳まないと
推計震度分布図のセル列が添字ごとの経路になり、1 ファクトリで 5,097 経路に膨らむ。

**「standard 版で作れる項目」は 2 つの入力の和で決める。** 実測だけでは足りない ——
P2PQuake の 552（津波）は直近 600 件に 1 件も無いことがある。そこで `p2pquake.ts` /
`kyoshin.ts` のオブジェクトリテラルのキー（TypeScript の AST）も和に入れる。この 2 ファイルの
parse 関数は固定のキーを持つリテラルを返すだけなので、キーの集合が上限そのものになる。

- **照合は経路の全セグメントで行う。** リーフ名だけで照合すると、`estimations[].name` のように
  **P2PQuake には配列ごと存在しない構造**が、`name` が別の場所で使われているという理由だけで
  「作れる」と誤判定される（2026-09-10 の点検で津波 17 経路がこれで漏れていた）
- **それでも偽陽性は残る。** 別々の関数のキー名がたまたま同じ並びを作れば通る。リテラル照合で
  救われた経路は「作れないとは言い切れない」であって「作れる」の証明ではない

**標本 0 件を黙って飛ばさない。** 実電文が 1 通も無い種別は E 表へ明示する ——
「一致していた」と「見ていない」を混ぜると、それは網羅性の主張にならない。VXSE60（地震回数）は
2024-01-01〜2026-09-06 の全アーカイブを走査しても 0 件で、**配信実績が無い**（→
[`data-sources-spec.md`](data-sources-spec.md) §2）。突き合わせには気象庁公式のサンプル電文を使い、
標本の表にその旨を出す。

**実行手順はここにも書かない**（上と同じ理由。出力先を揃えて動かす必要があり、片方だけ書くと
食い違う）。入力の揃え方は上の節と同じで、`TELEGRAM_AUDIT_DIR` の下に
`testdata-shapes.json` と `testdata-report.md` が出る。

### 地震の時刻のずれを測る

**同じ作業ディレクトリを使う、3 つ目の突き合わせ。** 電文は地震の時刻を 2 つ持つ
（`OriginTime` = 地震発生時刻 / `ArrivalTime` = 地震発現時刻）。どちらを画面に出すかは
実電文から決めたもので（→ [`tsunami-spec.md`](tsunami-spec.md) §4）、その判断を測り直す道具。

| スクリプト | すること |
|---|---|
| `fetch-quake-times.mjs` | アーカイブを走査し、電文ごとの 2 つの時刻を JSONL へ抜き出す。**電文そのものは保存しない** |
| `compare-quake-times.mjs` | 集計する。ずれる割合・偏り・利用者の目に触れる形・気象庁自身がどちらを本文へ書いているか |

```bash
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/fetch-quake-times.mjs
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/compare-quake-times.mjs
```

**分類を指定できる。** 既定は `telegram.earthquake`（地震情報・津波・長周期）。緊急地震速報を
測るなら `CLASSIFICATIONS=eew.forecast,eew.warning` を渡す ——
**そちらは 1 日分（2024-11-26・VXSE45 の 91 通）を測って決着している**（→
[`eew-spec.md`](eew-spec.md) §3「地震の時刻は発生時刻を出す」）。**範囲を広げるのは幅の分布を
知りたいときだけでよい。** どちらを出すかの結論は幅ではなく、気象庁がどちらを地震の時刻として
示すかで決まっている。

**2 本で渡し方が違う。** `CLASSIFICATIONS` が効くのは `fetch-quake-times.mjs` だけで、
集計側は**第 1 引数にファイル名の幹**を受け取る（分類名の `.` を `-` にしたもの）。
集計側へ環境変数を渡しても無視され、既定の `telegram-earthquake.jsonl` を読む。

```bash
CLASSIFICATIONS=eew.forecast,eew.warning   TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/fetch-quake-times.mjs
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/compare-quake-times.mjs eew-forecast
TELEGRAM_AUDIT_DIR=<作業ディレクトリ> node scripts/telegram-audit/compare-quake-times.mjs eew-warning
```

**出力の 1 行目が `走査: <分類名>` を出す**ので、読む前にそこを見れば取り違えに気づける。

測るときの落とし穴が 5 つある。**どれも実際に踏んだ。**

- **情報名は `Head` 直下の `Title`。** 最初に現れる `<Title>` は `Control/Title`（種別の固定名）で、
  遠地地震を 1 件も判別できない（→ §5「名前が同じでも同じ場所とは限らない」）
- **気象庁の文は全角数字。** 半角で作った「0時13分」は全角の「０時１３分」に一致せず、照合が
  全件「どちらも無い」へ落ちる。`compare-quake-times.mjs` は**拾えた件数を検算として出す**ので、
  0 件なら照合そのものが壊れている（→ §5「検索が空振りしたことを『無い』の根拠にしない」）
- **訓練電文を混ぜない。** 同じ EventID の訓練電文が種別ごとに別の時刻を名乗るため、
  実運用のずれとして数えると桁が変わる
- **同じ内容が別の種別として対で届く。** 緊急地震速報は VXSE45 と、廃止予定の旧形式 VXSE44 が
  対で流れる。1 日分では **93 組すべてで地震の 2 つの時刻が完全に一致**していたので、両方を数えると
  母数がちょうど倍になる。**アプリがパーサーへ渡すのは VXSE45 だけ**（`src/services/dmdata.ts` の
  `DISPATCHED_WITHOUT_PARSER`）なので、アプリの挙動を論じる数値は VXSE45 で数える。**比率は倍に
  しても変わらないので、件数を見るまで気づけない**
- **同じタグ名が 1 電文に複数入る。** 気象庁の文を探すとき `<Text>` を 1 件だけ拾うと取りこぼす ——
  見出し文（`Head/Headline`）・固定付加文（`Comments/WarningComment`）・取消の本文（`Body/Text`）が
  同じタグ名で並ぶ。緊急地震速報の 1 日分（VXSE45）では 93 通のうち 26 通が 2 件以上を持っていた。
  **全出現を走査すること**（→ [`eew-spec.md`](eew-spec.md) §3「地震の時刻は発生時刻を出す」の
  「時刻を書いた報の数え方」）


## 3. 読まないと決めたもの

**「読めていない」と「読まないと決めた」は別の状態。** 計測はこの 2 つを区別しないので、
決めたものはここに書き出しておく。書かないと、次に測った人が同じ調査をやり直す。

| 要素 | 読まない理由 | 根拠の置き場所 |
|---|---|---|
| `Head/Headline/Information`（見出しの構造化） | 内容部（`Body`）の部分集合で、同じ事実を二重に読むことになる | [`quake-spec.md`](quake-spec.md) §8 |
| `CodeDefine/Type`・`Type@xpath` | 電文が自分のコード体系を説明する欄。値そのものは情報を持たない | [`tsunami-spec.md`](tsunami-spec.md) §4 |
| 津波の `Kind/Name`・`LastKind/Name` | 同じ事実をコードで読んでおり、名前は表示にも判定にも使わない | [`tsunami-spec.md`](tsunami-spec.md) §4 |
| `Hypocenter/Area/Coordinate@description` | 座標を読めなかったときの記録にだけ使う。正常な電文では通らない | `readHypocenterAreaDetail`（`src/services/dmdataParser.ts`）の説明 |
| `jmx_eb:Magnitude@condition` | 固定値「不明」で、出現は本文 `NaN` と同時。資料が両方を同時に定めているので同じ事実の別表現にすぎない。「Ｍ不明」と「Ｍ８を超える巨大地震」の別は `@description` でしか付かない | [`quake-spec.md`](quake-spec.md) §8（規模が数値にならない電文の説明） |
| `jmx_eb:Magnitude@description`（**緊急地震速報だけ**） | 資料の緊急地震速報の章は、不明のときの値を「M不明」しか定めておらず、アプリが出す「不明」と変わらない。「Ｍ８を超える巨大地震」を定めた一文は地震情報・津波の章にしかない。**資料が改訂されたら見直す** | 資料 Ⅱ.21 1-5（他の種別では条件付きで読んでいる） |
| 予想波高・沿岸への推定の `jmx_eb:TsunamiHeight@condition` | 固定値「不明」。定性的表現がない津波注意報・予報では `@description` が空属性になるため、表示文字列のフォールバックに使うと波高として「不明」と出る。**観測側の同名属性は「上昇中」が入るので読む** | [`tsunami-spec.md`](tsunami-spec.md) §9「数値にならない予想波高」 |
| 入れ物の要素（`Category`・`Comments` など） | 自分では値を持たず、子を個別に読んでいれば足りる | —— |

**ここに書くだけでなく、`coverage-core.mjs` の `DECIDED_PATHS` にも足すこと。**
そうしないと突き合わせが数え続ける（→ §2「未読を作業対象から外す 2 つの篩」）。
要素も属性も同じ登録簿を通る。

**入れ物の要素は一覧に残り続ける。** 「読んだ」の定義は §1 のとおり値を取り出したかどうかなので、
子だけを読んでいる親要素は必ず未読として挙がる（仕組みどおりの挙動で、除外漏れではない）。
`triage.mjs` は電文の構造から容器を判定して除くが、**それは実測の側だけ** —— 資料からの
数え上げには構造が無いため、こちらには残る。

## 4. 決まっていない判断

「直すには別の設計変更が要る」もの。着手する人はここから読むこと。

**いまは 1 件も無い。** 点検で挙がった未決はすべて決着し、扱いは各機能の仕様書へ移した
（下記の改訂履歴に、どれをどこへ移したかがある）。新しく「調べたが決められない」ものが出たら、
ここへ足す。**「まだ手を付けていない」と「見たうえで決められない」は分けて書くこと** ——
混ぜると、次に棚卸しする人が同じ調査をやり直す。

## 5. 読み落としの型

点検で見つかった漏れは、いくつかの型に収まる。**新しく電文を読むコードを書くときは、
この一覧を当ててみること。**

### 資料の読み方

- **「例えば」を定義として読まない。** 津波の本文（`Body/Text`）は資料に「例えば取消の場合に…」と
  書かれていたため、取消のときだけ拾っていた
- **値域を推測で書かない。** 「震度５弱以上未入電」を短縮形で書いていて実電文を 1 件も拾えなかった
- **「載っていない」と「読めなかった」を分ける。** 空の値を「未知のコード」に数えると、
  正常な形の電文すべてで警告が鳴り、本物の未知が埋もれる
- **章の範囲を手書きの行番号で切らない。** 資料の中にある機械的な手掛かり（見出し・柱・目次）から
  導く。手書きの範囲がひと章はみ出していて、アプリが受信すらしていない種別の要素を
  「未読」と数えていた

### 実装の形

- **同じ要素を複数の経路が別々に読んでいると、必ず片方が遅れる。** 判定は 1 箇所へ寄せる
- **引き継ぐ値を足したら、引き継ぎ経路を全部に足す。** 続報の統合は種別ごとに分岐があり、
  1 箇所だけ直しても通る
- **`{ ...既存, 一部 }` は任意フィールドを黙って落とす。** 型検査は通り、画面でしか分からない
- **型コメントが実装より先を主張していたら、直すのは文面。** ロジックを足しに行かない

### 調べ方

- **代理指標で網羅性を判定しない。** 推論をやめて実測できるなら実測する
- **値が 1 種類であることを「情報を持たない」の根拠にしない。** 資料が固定値と定めた属性は
  標本をいくら厚くしても 1 種類のままで、情報は値ではなく**出現そのもの**にある
  （`jmx_eb:Magnitude@condition` は規模が不明のときだけ出る）。
  同じ理由で、**値域の広さを枝をまたいで合算しない**（→ §2「未読を作業対象から外す 2 つの篩」）
- **落とす判断に、確かめていない道具を使わない。** 篩に使ったモデルが誤ると、本物の漏れが
  黙って消える。確信が持てないものは落とさず印を付ける
- **判定器そのものを検算する。** 答えの分かっている事実を 10〜20 件用意して当てる
- **名前が同じでも同じ場所とは限らない。** 入れ子になった同名要素で取り違える
- **同じ名前が資料の複数箇所で定義されている。** 数え上げが要素名でまとめると、**同じ電文種別の
  中で階層が分かれている要素**は 1 行にしか見えず、片方だけ読んでいても一覧からは分からない
  （実例: 震度の `Revise` は都道府県・地域・市町村の 3 階層にあり、市町村だけ落としていた）。
  仕分ける前に `where-defined.mjs` で定義の数を確かめる（→ §2）
- **同じ事実を電文が 2 通りで伝えてくることがある。** 片方だけ読むと、それを配信しない経路で
  取りこぼす（実例: 緊急地震速報の主要動到達は区域の `Condition` と種別コードの両方にあり、
  前者は DMDATA しか配信しない）。読み取り側で 1 つの値へ畳み、判定を 1 か所に置く
- **突き合わせを種別ごとに閉じる。** 文字列の有無だけで見ると、ある種別の要素を読むコードを
  足しただけで、**別の種別の同名要素まで「読んでいる」ことになる**
- **データの構造を見てから引く。** 観測点の座標表の鍵は都道府県名と観測点名の組で、
  観測点名だけでは 1 件も引けない
- **検索が空振りしたことを「無い」の根拠にしない。** 全角と半角・空白の入り方で外れる

### 書き方

- **数を書くなら、読む人が確かめられる形にする。** 手元のサンプルから出した割合・件数は、
  そのサンプルの性質を映しているだけで、読む人には裏が取れない。書かずに済むなら書かない
- **同じ説明を 3 箇所に書くと、直すとき 1 箇所が残る。** 単一情報源を決めて他は参照にする

### 道具の癖

電文の点検そのものではなく、**集計スクリプトや回帰テストを書くときに繰り返し踏んだもの**。
電文に固有の話ではないが、この作業では毎回出てくる。

- **Bash のヒアドキュメントはバックスラッシュを半分に潰す。** `\n` や `\s` を含むスクリプトは
  ファイルへ書いてから実行する
- **作業ツリーの改行は LF と CRLF が混ざる。** 複数行を照合する処理は読み込み後に揃える
- **JavaScript の `.replace()` は対象が無くても黙って素通りする。** テストの雛形を書き換えたつもりで
  元の電文を見たまま緑になる。置換が当たったことを機械的に確かめること
- **`unzip` は Shift-JIS のファイル名を壊す。** 気象庁の配布 ZIP はこれに当たり、展開した後は
  目的のファイルを名前で選べない。サイズで見分ける（→ §2「解説資料のテキストを作る」）
- **`pdftotext` は語の途中に改行を入れる。** 資料のテキストを行単位で `grep` すると、
  行末で割れた語が取りこぼされる（「固定値」が「固」と「定値」に割れ、数え上げが 1 件少なく
  出た）。**資料を対象に数えるときは、改行を除いた版でも数えて突き合わせること。**
  `scanManual()` の行単位の走査は要素定義（`Kind【種類】`）が 1 行に収まる前提で成り立っている

判断」も残っている。終わったのは**この 2 段だけ**。

**段に着手する前に必ず計測をやり直すこと** —— 前の段で読むようにした要素が未読の数に残っていると、

### ヘッダ段（2026-09-09 に完了）

`Control` と `Head` の未読要素を読む。**同じ要素名でも、読んでいる種別と読んでいない種別がある。**
実測の内訳は次のとおり。

| 要素 | 未読の種別 |
|---|---|
| `Control/Title`・`Head/InfoKind`・`Head/InfoKindVersion` | 13 種別すべて。読む経路が実装に無い |
| `Control/DateTime`・`Control/PublishingOffice` | 13 種別すべて。**ただし受け皿としての経路はある** —— 前者は発表時刻（`Head/ReportDateTime`）が空のとき、後者は編集官署が空のときに読む。手元のサンプルではどちらも主の要素が常に埋まっていて、一度も通らなかった |
| `Head/TargetDateTime` | 震度速報を除く 12 種別 |
| `Control/EditorialOffice` | 6 種別（緊急地震速報・長周期地震動・南海トラフ 3 種・後発地震）。**地震情報と津波では読んでいる** |
| `Head/Title` | 5 種別（津波 3 種・緊急地震速報・長周期地震動）。**地震情報では情報種別の判定に使い、南海トラフ 3 種と後発地震では情報名として画面に出している** |

**読むことと画面に出すことは別**で、出すのは利用者に意味のあるもの（情報名・発表官署）だけ。
スキーマの版番号は出さない。

着手前に実電文で測った事実:

- **いま画面に出している発表時刻は分単位に丸まっている。** `Control/DateTime` は秒値まで有効だが、
  `Head/ReportDateTime` は緊急地震速報系だけが秒値で、その他は分値まで（解説資料 Ⅰ.（ⅰ）2・
  Ⅰ.（ⅱ）2）。実装は `ReportDateTime` を先に読み `||` で落とすため `Control/DateTime` へ到達しない
- **最新の報を探すときに見るべきものを資料が名指ししている。** Ⅰ.（ⅱ）8 が「同一種別の情報における
  最新情報の検索にあたっては、本要素（`Serial`）ではなく管理部の発表時刻（`Control/DateTime`）を
  参照すること」と書いている。実装の続報判定・退行防止が何を鍵にしているか確かめること
- **`Control/Title` は画面に出せない。** 電文の種別名で、津波では末尾に記号が付く。利用者に見せる
  情報名は `Head/Title`
- **編集官署（`Control/EditorialOffice`）を同一性の鍵にしない。** システム障害時に切り替わる
  （Ⅰ.（ⅰ）4）。地震・津波の「独立した情報単位」の鍵は情報名称・運用種別・地震識別番号の組
  （（ⅲ）共通別紙ア）
- **`Head/TargetDateTime` は種別で意味が変わる**（Ⅰ.（ⅱ）3）。津波の観測値を発表する情報と
  沖合の津波観測に関する情報では**津波の観測状況を確定した時刻**で、実装はここを読んでいない
- **発表官署を読む経路が種別によって欠けている。** `parseIssueSourceFromXml` を呼ぶのは地震情報と
  津波だけ（§5「同じ要素を複数の経路が別々に読んでいると、必ず片方が遅れる」の型）。しかも
  読み取った値はどの画面からも使われていない

この段で決めたこと（2026-09-09 に決着）:

| 論点 | 結論 | 根拠の置き場所 |
|---|---|---|
| 発表時刻を秒精度へ上げるか | **上げない。** 代わりに受け皿の表記混在を塞いだ | [`quake-spec.md`](quake-spec.md) §6.3 |
| `Head/TargetDateTime` を観測情報で読むか | **読む。** VTSE51・VTSE52 のみ。カードに「観測 ◯◯ 時点」 | [`tsunami-spec.md`](tsunami-spec.md) §4 |
| 発表官署を画面に出すか | **出さない。** 実電文 135 通すべてで「気象庁」の 1 種類 | 下記 |
| 読み取り経路を全種別へ埋めるか消すか | **どちらもしない。** 出さないなら埋める理由が無く、消すと P2PQuake 経路（`issue.source`）へ波及する | 下記 |
| （追加）`Head/Title` を出すか | **津波だけ出す。** 緊急地震速報は語が二重になり、長周期は 1 種類で情報が増えない | [`tsunami-spec.md`](tsunami-spec.md) §4 |

**発表官署は情報を持たない。** 実電文 135 通で `Control/PublishingOffice` はすべて「気象庁」。
`Control/EditorialOffice` は「気象庁本庁」と「大阪管区気象台」の 2 値だが、これは障害時に
切り替わる内部の運用体制で、利用者にとって意味が無い。**読む経路は残す**（`issue.source` は
P2PQuake の JSON も持つフィールドで、型から消すと両経路を触ることになる）。

**この段で潰した穴。** `Head/ReportDateTime` が空のとき `Control/DateTime` へ落ちる受け皿で、
前者は JST・後者は UTC 表記のため、落ちた報だけ続報判定で永久に「古い」と判定される形に
なっていた。例外もログも出さない。手元のサンプルでは一度も通らなかったので、**計測だけでは
見つからない**——資料が「`Control/DateTime` を参照せよ」と書いている理由を追ったところで出てきた。

**このとき直したのは、当時この受け皿を持っていた 6 つのパーサーだけ。** 緊急地震速報は別の
パーサーで発表時刻を素読みしており、受け皿も検証も持たないまま残っていた（2026-09-13 に揃えた。
→ [`quake-spec.md`](quake-spec.md) §6.3）。**同じ性質の読み取りが何箇所あるかは、直す前に
数え上げること。**

  引き継いでおり、3 巡の敵対的レビューで 1 段ずつ下流へ同じ穴が再発した** —— 永続化する
  ファイルへ書いていない、下流が読んでいない、その先が読んでいない。どれも「動くけれど印だけが
  消える」形で、型検査もテストも通っていた。引き継ぎを `readArtifact` の副作用にしたので、
  呼び出し側は読むだけでよくなった。あわせて次の 5 つを直した（後ろ 2 つはこの作業の
  敵対的レビューが見つけたもので、**仕組みへ寄せても、その仕組みの中で同じ間違いはできる**）。
  - **実電文サンプルの収集の取りこぼしが、下流へ一切伝わっていなかった。** 成果物は
    `telegram-cache/` に並ぶファイルそのもので印を載せる場所が無く、途中で失敗しても
    計測台・`triage.mjs`・`testdata-shapes.mjs` からは「その種別は 0 件」としか見えなかった。
    `collection-mark.mjs` の札で伝えるようにした
  - **`fetch-quake-times.mjs` の取りこぼしは、集計側（`compare-quake-times.mjs`）で
    見出しに 1 行出るだけだった。** レポート全体を「無い」の根拠にしないという断りが無く、
    以降のどの節も正常時と同じ見た目で出ていた
  - **印の欄を持たないファイルを「完全」と読んでいた。** 書く側が取りこぼしの有無に
    かかわらず欄を置くようにし、欄が無いものは「この仕組みを通っていない＝不明」として扱う
  - **稀な種別の収集の札を対象（`eew` / `ixac41` / …）ごとに分けていなかった。** 後から
    走らせた対象の成否だけが残る形で、「1 枚を共有すると印が消える」はスクリプト間だけでなく
    **同じスクリプトの実行対象のあいだでも**成り立つ
  - **区間で区切らず、1 つの分類の取りこぼしが全分類のレポートへ波及していた。** 完璧に
    走査できた分類にまで「信用するな」と出ており、**事実に反する警告は本物の警告を軽く見せる**。
    `checkpoint()` で区切る形にした
