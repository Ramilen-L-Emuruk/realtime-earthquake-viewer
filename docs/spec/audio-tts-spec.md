# 音声・TTS 仕様書

> 本書は**現在の実装が通知音・読み上げ・ウィンドウタイトル・自動タブ切替をどう扱うか**をまとめた
> 仕様書。実コードと食い違う場合は実コードを正とする。
> **読み上げと自動タブ切替の優先順位の単一情報源は §6。** 緊急地震速報・津波・地震情報・揺れ検知が
> 画面と声を取り合う規則はすべてそこにある（他の仕様書からはそこを参照している）。

## 1. 概要

情報受信時にユーザーへ通知する 3 系統の副作用を扱う:

- **通知音**（`alertSound`）: Web Audio API で合成した種別別のアラート音
- **VOICEVOX 読み上げ**（`voicevox`）: ローカル VOICEVOX HTTP API 経由の音声合成（任意）
- **ウィンドウタイトル**（`useAlertTitle`）: ブラウザタブ / ウィンドウのタイトル書き換え（AutoHotKey 等の外部監視向け）

さらに以下も関連する:
- ブラウザ通知（`Notification` API）
- 自動タブ切替
- 自動カメラフィット

すべての発火は `src/hooks/useLiveEventHandler.ts` で一元的にディスパッチする。

## 2. 通知音（`alertSound`）

`src/utils/alertSound.ts`。Web Audio API の `OscillatorNode` + `GainNode` +
`ConvolverNode`（残響）で種別ごとの音を合成する。事前録音ファイルは持たない。

減衰する音は `decayTone()` を通す。**指数減衰は 0 に到達できないため 0.001 まで落として
から 0 へ落とし切って停止する。** 0.001 のまま停止すると段差が残り、無音区間にティックが
出る（1 つの音で 2〜6 本のオシレータが同時に切れるため −50 dBFS 前後まで積み上がる）。
この終端処理は `decayTone()` の 1 箇所に集約してあるので、ここを種別ごとに分岐させないこと。

### 音の種類

| 種別 | 用途 | 概要 |
|---|---|---|
| `eewSpecial` | EEW 特別警報 | 低音スイープ + 9 連打アラーム + ドローン（約 1.7s） |
| `eew` | EEW 警報 | 連打アラーム（短め） |
| `eewForecast` | EEW 予報 | 控えめなピンポン |
| `eewUpdate` | EEW 続報 | ダークピアノ F4 の単音（0.5 秒） |
| `eewFinal` | EEW 最終報（自動解除の直前は使わず、真の最終報用） | ダークピアノ F4→C4 の穏やかな 2 音 |
| `eewCancel` | EEW 誤報取消 | ダークピアノ 3 音 A4→F4→C4（降下） |
| `tsunamiMajor` | 大津波警報 | 5 回のダブルスイープ（約 3.85s） |
| `tsunami` | 津波警報 | 連続スイープ |
| `tsunamiWatch` | 津波注意報 | 短めのスイープ |
| `tsunamiForecast` | 津波予報（若干の海面変動） | 単音のチャイム |
| `tsunamiUpdate` | 津波観測情報の更新 | 小音量のティン音 |
| `tsunamiCancel` | 津波の解除・取消・期限切れ（cancelReason の 3 種は音では区別せず単一音で伝える） | ピアノ 2 音 G4→C4（下行完全 5 度の終止形。約 2.0 秒） |
| `earthquake` | 地震情報（震源・震度 / 各地の震度） | ピアノ上昇 4 音 E4→G#4→B4→E5 |
| `earthquakePrompt` | 地震情報（震度速報） | ピアノ上昇 3 音 G#4→B4→E5 |
| `earthquakeInfo` | 地震情報（震源情報・遠地地震・その他） | ピアノ 2 音 G4→B4（控えめ） |
| `kyoshin` | 揺れ検知（confirmed） | 打撃 2 音 + シマー高周波 |
| `kyoshinCandidate` | 揺れの候補（faint / likely） | 控えめな単発チャイム |
| `specialInfo` | 南海トラフ臨時情報・後発地震注意情報 | ピアノ A4×2 連打 → D5（上昇） |
| `specialInfoCommentary` | 南海トラフ関連解説情報 | ピアノ 2 音 D5→A4（下降・控えめ） |

> 解説情報に専用音を割り当てているのは、**平常時にも定期的に届く**ため（発表頻度は
> [data-sources-spec.md](data-sources-spec.md) §2）。段階の発表（`specialInfo`）と同じ音を鳴らすと、
> 実際に「巨大地震注意」が出たときに音で区別できなくなる。上昇（臨時情報）と下降（解説情報）で
> 向きを逆にして聞き分けられるようにしている。

### 発火 API

```ts
playAlertSound(type: AlertSoundType)
```

内部で `AudioContext` の取得・resume を行う。`getCtx()` はシングルトンで、モジュール変数
`_reverb`（`ConvolverNode`）と一緒に使い回される。

上表の各種別とは別に、S 波の到達直前に鳴らす専用の音がある（`AlertSoundType` には属さず、
`playCountdownBeep(second)` を直接呼ぶ）。残り 5 秒から 1 秒まで、1 秒ごとに 1 回鳴る。

残り秒数が減るほどパルスが速く・多くなる（ゲート周波数 8→20Hz、パルス数 2→6）。
残り 1 秒だけサブ低音と高音トーンを重ねて衝突感を出す。ホーム地点を設定していないと
S 波の到達時刻を計算できないため鳴らない。

### 質感の分け方 — 警報は乾き、情報は濡れ

残響の有無で分けると次の 3 分類になる（`darkAlarm` / `darkSweep` / `sweep` は
そもそも残響を送る仕組みを持たない別系統）。

| プリミティブ | 使う音 | 残響 |
|---|---|---|
| `pianoNote` | 地震情報・震度速報・遠地地震・南海トラフ 2 種・津波解除 | 全音に載せる（`PIANO_ROOM_WET`） |
| `darkPiano` | EEW 予報・続報・最終報・警報・誤報取消 | 呼び出し側が指定したときだけ（**予報のみ** 0.12 / 0.14） |
| `impact` / `ding` | 揺れ検知・震度更新音・津波観測情報の更新 | 載せない |

**EEW の警報級（`eew` / `eewSpecial`）と津波警報（`sweep`）は乾いたまま。** 警報として
硬い質感を保つためで、濡らすと甘くなり情報系との聞き分けも弱くなる。ここを情報系に
寄せないこと。EEW で残響を持つのは予報だけで、これは以前からの音作りをそのまま残している。

> `pianoNote`（8ms）・`darkPiano`（6ms）・`impact`（7ms）はアタックに広帯域ノイズを重ねて
> 「鍵盤を叩いた感じ」を出していたが、これが小型スピーカー（iPad・ノート PC 内蔵）で
> 「プチ」と聞こえる正体だった。1 秒おきに鳴る EEW 続報や 0.16 秒間隔で 4 音鳴る地震情報では
> 粒が並んで「プチプチ」になる。実機の聴き比べを経てこの 3 系統から廃し、情報系だけは
> 失ったアタックの厚みを上部倍音と残響で補っている。

### 音量制御

- `globalVolume`（0.0〜1.0）を `setSoundVolume(v)` で更新
- 各種別内の相対バランスは `PLAYERS[type]` 内でハードコード
- 音量 0 では `decayTone()` がノードを 1 つも作らない（終端の 0.001 ぶんすら鳴らさない）

### マスターチェーンとリミッター

`alertSound` の全音源と `voicevox` の TTS 発話は、個々の `.connect(ctx.destination)` ではなく
`getMasterInput(ctx)`（`alertSound.ts` から export）を経由し、
`GainNode → DynamicsCompressorNode → ctx.destination` の順で流れる。特別警報級 EEW
（`eewSpecial`）と大津波警報（`tsunamiMajor`）が同時発火した場合、または TTS 継続中に
警報音が重なった場合、素の加算合成では波形がクリップして警報音がノイズに埋もれるため、
compressor で合成音圧の暴走をリミッター的に抑える。パラメータは threshold=-6dB / knee=6 /
ratio=4 / attack=3ms / release=250ms（音楽制作のリミッター標準的な値）。

**単独再生でも threshold を超える音がある。** 複数音を重ねる種別は 1 種別だけで超えうる
（実測: 地震情報の 4 音は −3.1 dBFS。倍音構成を見直した後は −6.7 dBFS で threshold の
すぐ下に収まった）。「単独なら素通し」を前提にしないこと。

**生成直後の約 0.4 秒はアタックを強く潰す。** Chrome の `DynamicsCompressorNode` は
作りたての状態だと減衰が深く、実測で 8 dB 小さく鳴る。そのため最初の音を鳴らす瞬間に
マスターチェーンを作ると **1 発目だけ小さく鳴る**。`unlockAudio()`（ユーザー操作の時点で
呼ばれる）でマスターと残響をまとめて先に作り、発報までに定常へ落ち着かせている。
なおセッション最初のポインタ操作が試聴ボタンに直接当たった場合だけは 0.4 秒を確保できず、
その 1 回だけ小さく鳴る（設定タブを開く操作で先に解除されるため通常は起きない）。

### 既知の課題

- 優先度キュー（低優先度の音を高優先度中に抑制するシリアライズ）と重複再生の抑止（dedup）は
  未実装。マスターチェーンの compressor で合成音圧の暴走は防いでいるが、UX として「特別警報中は
  他の音を鳴らさない」「同一種別の呼び出しを短時間ガードする」等の能動的な制御は行っていない。
  dedup を種別単位で入れると、群発地震で連続する別イベントの警報音を誤って抑止してしまう
  リスクがあるため、実装するなら eventId 単位のキーで慎重に設計する必要がある
- `AudioContext.resume()` の Promise を await せずに `currentTime + 0.02` をスケジュール（iOS Safari で初回音がドロップしうる）。`unlockAudio()` だけは失敗を警告に残す
- このアプリには Error Boundary が無く、React 18 は捕捉されない例外でツリー全体をアンマウントする。
  通知音は `useEffect` やイベント処理から直に呼ばれるため、音の例外ひとつで画面全体が消えうる。
  暫定として `playAlertSound` / `playCountdownBeep` / `playKyoshinUpdateSound` が例外を外へ出さず
  `log.error` に残す契約にしてある（音だけを諦めて通知と読み上げは通す）。Error Boundary の設置は別課題
- `eewSpecial` の内部ゲイン合計が 1.0 を超え、単独でもクリップしうる（compressor で緩和される）

## 3. VOICEVOX 読み上げ（`voicevox`）

**VOICEVOX** は無料で配布されている音声合成ソフトウェア（[voicevox.hiroshiba.jp](https://voicevox.hiroshiba.jp/)）。
ユーザーが自分の PC 上で起動しておくと、その HTTP API に対してテキスト → 音声合成をリクエストできる。
本アプリは任意機能として組み込んでおり、VOICEVOX を起動していない場合は無音で失敗する。

`src/utils/voicevox.ts`。VOICEVOX ローカル HTTP API（デフォルト `http://localhost:50021`）を呼び出して
音声合成する。任意機能で、有効化はユーザー設定 `voicevoxEnabled` による。

### API 呼び出し

呼び出す順に:

- `POST /audio_query` — テキストからアクセント句を生成
- `POST /accent_phrases` — 句区切り辞書のカナ表記からアクセント句を作る（下記「辞書」節で使う）
- `POST /mora_data` — 繋ぎ合わせたアクセント句の音素長と音高を引き直す（下記「辞書」節で使う）
- `POST /synthesis` — アクセント句から WAV を合成

中の 2 つは辞書に該当する語を含むときだけ呼ぶ。

合成 WAV は `AudioContext.decodeAudioData` でデコードして `AudioBufferSourceNode` で再生する。

テキストは一度にまとめて合成せず、**句読点（`。、！？`）の直後で区切った塊（チャンク）ごとに**
合成する（`splitIntoChunks`）。最初のチャンクができた時点で再生を始め、鳴らしている間に次を
合成するため、長い文でも読み始めを待たせない。短すぎる塊（5 文字未満）は次と繋げる。
**区切り文字を持たない文はチャンクに割れず、その分だけ発話の切れ目も生まれない。**

### 鳴らす直前の見直し

呼び出し側は「鳴らしてよいかの判定」（`shouldStillPlay`）を渡せる。**チャンクを鳴らす直前**に呼び、
外れていればそのチャンク以降を鳴らさない。**鳴っている途中のチャンクは最後まで鳴らす**
（語の途中で切ると聞き取りを壊すため）。

必要なのは、文面を作った時刻と音が出る時刻がずれるから。合成の往復を待つ間にも、鳴らしている
間にも新しい電文は届く。判定は 2 か所で行う。

| 判定する場所 | 捉えるもの |
|---|---|
| チャンクを予約する直前 | 合成の往復を待つ間に古くなった場合 |
| 鳴り始めの直前（`PRE_START_CHECK_LEAD_SEC` = 0.05 秒前） | 鳴らしている間に古くなった場合 |

2 段にしているのは、チャンクを**前のチャンクの終わりに合わせて先に予約する**ため（切れ目を作らない
ための設計）。予約した時点だけで判定すると 1 チャンク分先の未来を判定することになる。

**判定そのものが失敗したときは鳴らす側に倒す**（記録は残す）。黙る判断を例外に委ねると、
緊急地震速報が無音のまま消える方に転ぶため。

渡しているのは EEW の読み上げだけで、見るものはフェーズで違う（→ §6。第 1 フェーズは誤報取消のみ、
第 2 フェーズは誤報取消と値の引き上げ）。渡さなければ従来どおり全チャンクを鳴らす。

### セッション管理

- モジュール変数 `activeSources: AudioBufferSourceNode[]` と `currentSessionId: number`
- `speakWithVoicevox(text)` を呼ぶたびに既存の再生を全 stop() し、`currentSessionId++` で新セッションに切替
- 同時に旧セッションの `AbortController` を abort し、進行中の合成リクエスト
  （`/audio_query`・`/synthesis`・`/accent_phrases`）も打ち切る。セッション ID だけでは
  in-flight のリクエストが完走して VOICEVOX の処理を占有し、新しい発話が待たされるため
- **単一グローバルセッション**なので、EEW / 地震 / 津波 / LPGM の全読み上げがこの単一セッションを共有する。
  つまり後から来た読み上げが再生中のものを打ち切る。**どれが打ち切ってよいかは優先度で決めている**
  （§6「読み上げの優先順位」）
- **先行合成（`prewarmVoicevox`）はこのセッションに関与しない**（詳細は
  §6「間を合成の時間に充てる（先行合成）」）

### 辞書（読み仮名の補正）

`src/utils/ttsPhraseBreakDict.ts` + `public/data/tts-phrase-break-dict.json` に地名・専門用語の
読み仮名エントリを持ち、`findPhraseBreakMatch` で該当箇所のアクセント句をキャッシュ済みのものと差し替える。

辞書はアプリ起動時に先読みする。読み上げ開始時にまだ取得できていなければ待つが、その待ちは
**5 秒**で打ち切る。生成データ共通の取得タイムアウト（[`data-sources-spec.md`](data-sources-spec.md) §6）
より大幅に短くしているのは、ここでの待ち時間がそのまま緊急地震速報の読み上げの遅れになるため。
辞書が無くても句区切りが効かないだけで読み上げ自体は成立する。

該当した地名の直後には短い間（`DICT_TRAILING_PAUSE` = 0.12 秒）を挟む。切れ目に間があると
「区切って言い直した」ように聞こえて自然なため。「大津波」「深発地震」のような一般用語
（辞書の `_terms`）は文中に溶け込む語なので対象外。

#### 繋ぎ目の引き直し

上記のとおり辞書該当語は前後と別々に VOICEVOX へ渡して繋ぎ合わせている（`buildAccentPhrases`）。
この渡し方だと前半が独立した 1 文として扱われ、その末尾（「震度5弱を」のように助詞で終わることが
多い）が文末と解釈される。結果として **母音がおよそ 2 倍に伸び、音高も下がりきる**。地名の直前の
助詞が間延びして聞こえたり、言い切ってから地名を言い直したように聞こえたりする原因。

そのため繋ぎ合わせた後に `POST /mora_data` へ通し、全体の文脈で長さと音高を引き直す
（`refineProsody`）。音高はアクセント句の `accent`（アクセント核＝音高が下がる位置）を手がかりに
引き直されるため、辞書がカナ表記で指定した読みとアクセント核は保たれる。

ただし `DICT_TRAILING_PAUSE` も引き直しの対象になり、読点相当の長さまで伸ばされてしまう。
そのため句と句の間（`pause_mora`）は、辞書由来・読点由来を問わずまとめて元の値へ戻している。
引き直しに失敗した場合は繋ぎ目が不自然なまま読み上げるだけで、読み上げ自体は止まらない
（失敗は `log.debug` に残る。ただし割り込みによる中断は記録しない）。実測値は `refineProsody` の
コメントに残してある。

### 話速

現状 `synthesizeChunk` 内で `query.speedScale = 1.2` を無条件に上書き（ユーザー設定なし）。

### 既知の課題

- 通常チャンクの音声合成に一切キャッシュがない（定型句「緊急地震速報。」等も毎回合成）
- 音声合成そのものの失敗パス（`synthesizeChunk` の `catch`）と `/accent_phrases` の取得失敗に
  ログがなく原因追跡ができない（辞書の取得失敗と `/mora_data` の引き直し失敗は `log.debug` に残る）

## 4. 読み上げテキスト生成（`ttsText`）

`src/utils/ttsText.ts`。イベント種別に応じた読み上げ文を生成する。

### 主要関数

- `eewAlertToText(eew, kind)` — EEW の切り出し。`kind` は `forecast`（「地震動予報、〇〇で地震。」）／`warning`（「緊急地震速報、〇〇で地震。」）／`hypocenterUpdate`（「震源を更新、〇〇で地震。」）
- `eewIntensityToText(eew, announceUpgrade)` — EEW の予想値（予想最大震度・予想最大階級）。`announceUpgrade` が真のとき「緊急地震速報に切り替わりました。」を前置きする（真にするのは予報→警報の格上げだけ。→ §6）
- `earthquakeToText(quake, opts, isNew)` — 地震情報（`isNew:false` で更新報の言い回しになる）
- `tsunamiToText(tsunami)` / `tsunamiCancelToText(cancelReason)` — 津波
- `lpgmToText(...)` — 長周期地震動
- `nankaiToText(...)` / `kohatsuToText(...)` — 南海トラフ臨時情報・後発地震
- `nankaiCommentaryToText(...)` — 南海トラフ関連解説情報。**本文は読まない**（1000 字を超えることが
  あるため）。種別（臨時解説／定例解説）と号数までを伝え、詳細は画面のバナーに委ねる

### 特殊な扱い

- **予想震度が出ない理由**: `eewNoForecastReason` が 3 通りに分ける（仮定震源要素＝単独点処理／
  深さ 150km 超の深発地震／それ以外）。**読み上げる文言と、値の確定を待つかどうかの判断が
  同じ判定を使う。** 前 2 つはその報に予想震度が載らないと判っているので待たない（→ §6）。
  待つ意味があるのは 3 つめだけ
- **仮定震源要素**: 上記のうち単独点処理のケース。震度に加えて長周期階級も句ごと省く。単独点処理では
  地域別予想が発表されないため、`eewMaxScale` / `eewMaxLpgmClass` がともに 0 を返すことによる。
  なお M・深さを隠すのはカード表示・地図マーカー側の扱いで、EEW の読み上げは元から M・深さに
  触れない（[eew-spec.md](eew-spec.md) §5）
- **震源深さ不明**: 深さ不明（負値）では**深さ句ごと省く**。`0` のみ「ごく浅い場所」と読む
- **マグニチュード不明**: 規模不明（`NaN`＝DMDATA 経路／負値＝P2PQuake 経路）ではマグニチュード句ごと省く
- 深さ・マグニチュードの判定は `formatters.ts` の共有関数 `hasDepth` / `hasMagnitude` で行う。カード表示
  （`formatDepth` / `formatMagnitude`）・色付け（`getDepthColor` / `getMagnitudeColor`）も同じ関数を使うため、
  カードが「不明」と出すものを読み上げが「ごく浅い」「M0.0」と言うような食い違いは起きない
- **地域列挙の助詞**: 階級ごとに地域を並べるとき、場所の助詞「で」は文末（述語の直前）にのみ置く。
  句ごとに付けると一文字の助詞が読点に挟まれ、読み上げが途切れて聞こえる（震度・長周期地震動階級で共通）
- **地域名・地点名の区切り**: 名前を並べるときは読点「、」で繋ぐ。中黒「・」は VOICEVOX が音にせず、
  句読点と違って合成の区切り（§3「API 呼び出し」）にもならないため、並べた名前が一続きに聞こえる
  （例:「山形県新潟県上中下越」）。辞書に載っている地名の直後には短い間が入るが
  （§3「辞書（読み仮名の補正）」）、載っていない区域名では入らないので、区切りをそれに頼れない。
  なお津波予報区名には「伊勢・三河湾」のように**名前自体に中黒を含むものがある**
  （`tsunami-zones.json` に 9 件）。連結にも中黒を使うと、名前の一部か区切りかが区別できなくなる。
  この読点への統一により、津波の観測・到達情報で予報区名と地点名がすべて同じ読点で並ぶ
  （「佐渡、佐渡市鷲崎、小木、…」）。**どこまでが予報区でどこからが地点かは音声では区別されない**が、
  中黒では地点名同士が一続きに潰れて個々の地名すら聞き取れなかったため、こちらを採っている
- **遠地地震**: 「遠地地震に関する情報。」と名乗り、**日付から読み上げる**（発表が発生の数十分後になり日付をまたぐため）。
  津波の一文は電文の付加文原文（`JMAQuake.forecastText`）を優先し、無い経路では津波区分から起こす
  （付加文コードの詳細は [quake-spec.md](quake-spec.md) §3）

### 地域列挙の範囲

どの階級まで・各階級で何地域まで読むかは、設定タブの 4 項目で決まる
（項目名と既定値は [settings-pwa-spec.md](settings-pwa-spec.md) §2「主な項目の補足」）。
実装では `ttsText.ts` の `TtsRegionOptions`（`intensityLevels` / `alwaysReadScale` /
`maxRegions` / `regionTolerance`）としてこの 4 項目を受け取る。

- 読む階級は「階数の範囲内」**または**「必ず読み上げる震度以上」を満たすもの
- 階数は**最大震度に加えて何階級下まで読むか**。`0` なら最大震度のみ、既定の `2` なら最大を含めて計 3 階級
- 階数で数えるのは**観測がある階級だけ**。観測 0 地域の階級は飛ばして次を数える
  （例: 階数 1 で 5 強・5 弱の観測が無ければ、6 弱 の次に読むのは 震度 4）。長周期地震動階級も同じ数え方
- 1 階級あたりの地域名は上限まで読む。ただし上限をわずかに超えるだけなら（許容超過の範囲内）省略せず
  全地域を読む。超えた場合は上限ちょうどで切り「ほか N 地域」と件数で伝える
- 上位の階級で読んだ地域名は、下位の階級では繰り返さない
- 「必ず読み上げる震度」は震度にのみ効く。長周期地震動階級（1〜4）は震度と別軸のため対象外

### 地域名の並び順

読み上げる地域名は**気象庁の標準順**（北から南。同じ県の区域が隣り合う）に並べる。震源からの距離順だと
同じ県の同じ震度でも間に他県が挟まり、聞いて位置を掴みにくいため。県内の区域も気象庁の並びに従い、
代表点の緯度では並べない（例: 新潟県は緯度と逆に 上越 → 中越 → 下越）。

- 順序の実体は座標テーブル（`station-coords.json`）の区域キー順で、生成元の気象庁 震度観測点一覧の
  並びをそのまま引き継いでいる。索引の構築は `stationCoords.ts` の `buildRegionOrderIndex`、
  並べ替えは `ttsText.ts` の `sortByRegionOrder`
- 索引に無い地域名（震度観測点を持たない区域）は末尾へ回す。区域の一覧（`subregions.json`）でも
  これらは末尾（沖縄県の後の北方領土・埋立地）に置かれるため、標準順と矛盾しない。座標テーブルが
  未読み込みのときは並べ替えない
- **上限で切るときに残す地域は震源に近い順で選ぶ**。「どれを読むか」（選抜）と「どの順で読むか」を
  分けているのは、地理順のまま先頭から切ると震源から遠い北側の地域が枠を占め、震源直近が
  「ほか N 地域」に潰されうるため
- **震源を持たない電文では距離で選べないので、地理順に整えてから切る**（座標テーブルが読み込めて
  いれば＝北から上限まで）。震度速報がこれにあたり、震源の緯度経度には位置不明センチネル `-200` が
  入る。0 だけを「震源なし」とみなすと、この電文で地球上に無い点からの距離を測ることになる
- 長周期地震動も同じ並び。こちらは電文に震源座標が無いため、選抜は常に電文の順序のまま

この節の挙動（震源の有無による選抜の切り替え・県内の並び・上限で切ったときの並び）は
`ttsRegionOrder.test.ts` が実配信データで検証する。順序の元になる「県ごとに連続している」
「北海道から沖縄県まで通る」という座標テーブル側の前提は `stationCoords.test.ts` が受け持つ。

## 6. ライブイベント連動（`useLiveEventHandler`）

`src/hooks/useLiveEventHandler.ts`。イベント種別ごとに音・通知・読み上げ・タブ切替・タイトルの発火を
一元的に扱う（約 500 行以上の巨大フック）。

### 発火順序（概念）

各イベントで以下が並行 or 逐次に発火する:

1. 音（`playAlertSound(type)`）
2. ブラウザ通知（`showBrowserNotification(...)`）
3. VOICEVOX 読み上げ（`setTimeout` で遅延投入。通知音と重ならないよう種別ごとに 500〜4200ms）
4. 自動タブ切替（`setActiveTabNonRealtime(tab)` or `setActiveTabRealtimeOnUpdate()`）
5. ウィンドウタイトル変更（`useAlertTitle`）
6. カメラ自動フィット（`FitTo*GL` 経由）

読み上げの遅延は、通知音が鳴り終わってから話し始めるための待ち時間。`TTS_DELAY_MS`
（`useLiveEventHandler.ts`）が種別ごとの値を持つが、**次の 6 種はこのテーブルを通らず
呼び出し箇所に直接書かれている**。

| 種別 | 遅延 |
|---|---|
| 地震情報の取消 | 1200ms |
| EEW 誤報取消 | 1200ms |
| 津波の解除・取消・期限切れ | 2400ms |
| 長周期地震動 | 1000ms |
| 南海トラフ臨時情報・後発地震注意情報 | 1500ms |
| 南海トラフ関連解説情報 | 1500ms（`NANKAI_COMMENTARY_TTS_DELAY_MS`） |

**通知音を作り変えたら、その種別の遅延も見直すこと。** 音が長くなれば読み上げと重なる。
津波の解除音はリバーブを効かせているぶん、乾音が止まったあとも残響が尾を引くため、
音の長さちょうどではなく余白を足してある。

見直しの基準は「尾がどこまで伸びたか」ではなく **読み上げが始まる瞬間に音がどれだけ
残っているか**（その音自身のピークとの比）。情報系の全音に残響を載せた際の実測値を残す。

| 種別（遅延） | 残響を載せる前 | 載せた後 |
|---|---|---|
| 地震情報（1000ms） | −30.0 dB | −26.1 dB |
| 震度速報（500ms） | −22.0 dB | −19.1 dB |
| 遠地地震（1700ms） | 無音 | −54.3 dB |
| 津波解除（2400ms） | −59.4 dB | −62.2 dB |

地震情報と震度速報は、もともと鳴っていた余韻が 3〜4 dB 増えた。遠地地震は無音から
−54.3 dB になったが可聴外。津波解除だけは逆に 2.8 dB 減っている（元から残響を持つ音で、
倍音構成の見直しで送出そのものが変わったため）。いずれも区分が変わる変化ではないため
遅延値は据え置いた。

次に音を作り変えるときは、この表と同じ測り方で比較すること（上の数値はこの変更時点の
実測で、音を変えれば当然変わる。**残す意味は「比較の起点」を git 履歴を掘らずに得られること**）。

#### 間を合成の時間に充てる（先行合成）

対象は**間を置く非 EEW の読み上げ**（上の表と `TTS_DELAY_MS` の経路）。EEW の発報は間を置かない
ので対象外。

**間のあいだに、最初のひと区切りの音声合成を済ませておく**（`prewarmVoicevox`）。合成は VOICEVOX へ
2 往復（`/audio_query` → `/synthesis`）するため LAN 越しで 150〜350ms かかり、待ってから合成を
始めると「音が鳴り終わってから声が出るまで」の空白になっていた（実測 244ms → 20〜33ms）。

- **進行中の読み上げには触らない。** 先行合成はセッションを確立せず、鳴っているものを止めない
  （止めると、間を置いている最中に前の読み上げが切れる）
- 使われなかった先行合成は、次の読み上げが始まるときに打ち切る。放っておくと VOICEVOX 側の
  直列処理を占有して、これから読む方が待たされる
- **ただし、これから使うものは打ち切りの対象から外すこと。** 外さないと、地震情報と長周期の
  ように電文がほぼ同時に届いたとき、**後から始まった読み上げが、先に始まった側がこれから使う
  先行合成を消す**（本番ビルドの実測で「最初の音まで」が 2.8 秒に達した回があった）
- 打ち切られていた・失敗していた場合は、再生側で合成し直す（無音にはしない）
- 間より合成が遅ければ効かない。そのときは従来どおり待つだけで、遅くはならない

#### 間を置く読み上げの予約は追跡する

対象は**間を置くすべての読み上げ**（`scheduleSpeech`）。先行合成の有無を問わず、EEW の誤報取消も
含む。

予約は、画面を閉じたときとリプレイを開始したときに取り消す。取り消さないと、状態をリセットした
後に古い予約が発火し、リセット済みなので待ち合わせにも掛からずそのまま割り込む（しかも記録が
残らない）。

#### EEW の発報は間を置かない

**EEW の発報（新規・続報）だけはこの仕組みの外にある。** 速報性を優先し、音の鳴り終わりを待たず
即座に震源を読み上げる（第 1 フェーズ）。予想値の読み上げ（第 2 フェーズ）がそれに続く。
EEW の音を作り変えても、ここに調整すべき遅延値は無い。

#### 第 1 フェーズ（切り出し）— 区分を名前で伝える

| 場面 | 読み上げ |
|---|---|
| 予報級（severity=Forecast）の発報 | 「地震動予報、〇〇で地震。」 |
| 警報級（severity=Warning）の発報 | 「緊急地震速報、〇〇で地震。」 |
| 続報での震源の大幅更新 | 「震源を更新、〇〇で地震。」（区分には触れない。既に伝えてある） |

区分の判定は severity、名前は電文の名称から借りている（**電文種別と区分は 1 対 1 ではない**。
根拠と表示側の対応表は [eew-spec.md](eew-spec.md) §3）。
**読み上げ固有の理由は「音声だけで区分が判別できること」。**
予報級まで「緊急地震速報」と読むと、一般に流れるのが警報だけであることから「警報が出た」と
聞こえ、実際より重く伝わる。

なおこれは気象庁の用語法からの意図的な逸脱。気象庁は「緊急地震速報」を警報と予報の両方を含む
上位の名前として使う。ここでは耳で区別が付くことを優先している。

鳴らしている途中で誤報取消が届いたときは、そこから先を鳴らさない（下記「第 2 フェーズ」の
「鳴っている間に上がったら」以降を参照）。**第 1 フェーズが見るのは誤報取消だけ**で、
予想値の変化では打ち切らない（震源名は値ではないため）。

#### 第 2 フェーズ（予想値）

| 場面 | 読み上げ |
|---|---|
| 初報に予想震度がある | 待たずに「予想最大震度〇〇。」（長周期階級があれば続けて「予想最大階級〇。」） |
| 初報に予想震度が無く、付かない理由がはっきりしている | 待たずに理由付きで読む（「単独点処理のため、予想震度なし。」／「深発地震のため、予想震度なし。」）。値が付いた続報が来たら引き上げとして言い直す |
| 初報に予想震度が無く、理由も判らない | 値が付いた続報の時点で読む。付かないまま 3 秒（`EEW_PHASE2_MAX_WAIT_MS`）経ったら「予想震度なし。」で打ち切る |
| 待っている最中に理由が判明した | 続報で深さが 150km 超に改められた等。待ちを打ち切って理由付きで読む（初報で判っていた場合と揃える） |
| 予報から警報へ格上げ | 予想値の手前に「緊急地震速報に切り替わりました。」を前置きする |
| 続報で震度・階級・区分が上がった | 初報と同じ形で言い直す。前の発話が終わった時点で、その瞬間の最新値を 1 回 |
| 続報で下がった | 読まない |

**予想値は毎回同じ形で読み、引き上げ専用の短句は持たない。** 「震度5強に引き上げ。」のような
差分の言い方は、基準にした値を実際に発話したかどうかに依存する。読み上げは割り込みや取消で
消えることがあるため、一度も声に出していない値からの引き上げを語る事故が起きる。

**格上げは遷移の言い方で述べ、初報から警報なら述べない。** 第 1 フェーズで「地震動予報、〇〇で
地震。」と伝えてあるので、聞き手は前の区分を知っており「何から何に変わったか」が通じる。ここを
「警報。」のような区分名だけにすると、値の前に単語が挟まるだけで変化が伝わらない。逆に初報から
警報なら切り出しで既に伝えており、重ねて言う意味がない（値を読み直すだけの報にも前置きが付くと
耳に障る。初期の実装では本震の 5 発話すべてに付いていた）。一度伝えた区分は下げず、severity が
揺れ戻しても「伝え済み」として扱う。

**「特別警報」は読み上げない。** 特別警報の条件を満たしていても、格上げとして読むのは予報→警報の
ときだけ。重さは値そのもの（「予想最大震度6弱。」）で伝える。表示・ブラウザ通知・通知音は内部の
重大度区分として 2 段階を保つ。理由（気象庁が発表時にこの名称を用いないこと）は
[eew-spec.md](eew-spec.md) §4 を参照。

**待つ対象は時間ではなく、値の確定と前の発話の完了。** 時間でデバウンスすると、続報が立て続けに
届く大地震ほど読み上げが遅れる（経緯は §10 参照）。

第 2 フェーズは第 1 フェーズの再生完了を待つため、その間に誤報取消が届くことがある。
**発話の直前に対象がまだ発表中かを確認している**（取り消された地震の予想震度を読み上げないため）。

**鳴っている間に上がったら、その先は鳴らさない。** 予想震度は数秒で書き換わる（2024/1/1 能登の
本震では 5弱 → 7 まで 7.5 秒、続報の間隔は 0.3〜2 秒）。文面はその時点の最新値から作るが、合成の
往復と発話そのもので数秒かかるため、鳴り終わる前に古くなる。そこで鳴らす直前に見直し、より高い
値の続報が届いていればそのチャンク以降を鳴らさない（仕組みは §3「鳴らす直前の見直し」）。
取りこぼしにはならない: 上がった続報を受けた時点で次の第 2 フェーズが予約されており、そちらが
最新値を読む。**値が下がっただけでは止めない**（読まない方針と揃える。下がったことを理由に
止めると、代わりに読むものが無く無音で終わる）。

取消による打ち切りは**誤報取消だけ**で、自動解除（発表の終わり）では鳴っているものを止めない。
内容が誤りだったわけではなく、また自動解除には取消の読み上げが無いため、途中で止めると
尻切れのまま何も説明されない。この扱いは第 1 フェーズ（震源）と共通。

### 読み上げの優先順位

`speakWithVoicevox` は待ち行列ではなく**割り込み**（既存の再生を stop し、進行中の合成を abort する。
§3「セッション管理」）。そのため EEW の読み上げは eventId をまたいで**全体で 1 本のチェーン**に繋ぎ、
前の発話が終わってから次を話す。

- **eventId ごとにチェーンを分けてはいけない。** EEW が同時多発すると（2024/1/1 能登では約 15 分間に
  6 件）互いの発話を途中で消し合い、どちらも尻切れになる
- 予約は eventId ごとに高々 1 件に畳む。解決した時点でその瞬間の最新値を読み直すため、続報のたびに
  積む必要が無い。**これがデバウンスの代わりになる**（連投中も沈黙せず、連呼にもならない）
- 既読の値（震度・階級・区分）を更新するのは**発話の直前だけ**。予約した時点で更新すると、
  取消で捨てられた発話や割り込みで消えた発話まで既読になる
- 直前の発話を待つ時間には上限を置く（`EEW_SPEECH_CHAIN_MAX_WAIT_MS` = 8 秒）。VOICEVOX への合成
  リクエストにタイムアウトが無く、応答が返らないと後続の EEW が永久に読まれなくなるため

#### 割り込みを許す条件

**割り込みを許すのは「自分の優先度が読み上げ中のものと同じか高いとき」だけ。** 低い側は相手が
読み終わるのを待つ。

**つまり同格どうしは新しい方が勝つ。** 震度速報の更新が古い震度速報を置き換えるのは正しい挙動で、
ここを待ち行列にすると最新の震度がいつまでも読まれない。以下の表で「同格にする／分ける」の
判断が何度も出てくるが、その拠り所はこの規則。

| 優先度 | 種別 |
|---|---|
| 最優先 | 緊急地震速報（同格どうしは上記のとおり直列化する） |
| 高 | 津波（発表・更新・解除）／南海トラフ臨時情報・後発地震注意情報 |
| 中 | 地震情報（`kind: 'quake'` の電文。震度速報・震源情報・遠地地震・取消などの**種別を問わず一律**）／長周期地震動情報 |
| 最下位 | 南海トラフ関連解説情報 |

南海トラフ臨時情報・後発地震注意情報を津波と同じ高に置いているのは、発表頻度が極端に低く、
聞き逃したときの損失が大きいため。

**長周期地震動情報を地震情報と同格にしているのは、長周期の方が新しい情報だから。** 同格どうしは
新しい方が勝つ規則なので、地震情報を読んでいる最中に長周期が届けば割り込んで読める。以前は
「地震のあとに出る事後情報だから軽い」として一段下に置いていたが、各地の震度（数千文字・読み切りに
2 分近く）の後ろへ回されて大幅に遅れていた。**内容が別軸（震度と長周期地震動階級）で、どちらも
その時点で最新の情報**なので、待たせるより割り込ませる方が実態に合う。

**南海トラフ関連解説情報は単独の最下位に置いている。** 臨時情報の発表期間中は解説情報が毎日
届くため、既存のどの層と同格にしても必ず何かを切ってしまう。

- 高（臨時情報と同格）にすると、同格は新しい方が勝つため、臨時情報の読み上げを追い出す
- 中（地震情報・長周期と同格）にすると、数千文字に達しうる地震情報の読み上げを毎日切る

同格を作らず最下位に置くことで「**解説情報は何も切らない**」を保証している。定型文が大半の
情報なので、待たされて上限（`HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS`）で諦めても損失は小さい。

**同格どうしは新しい方が勝つ。** 震度速報の更新が古い震度速報を置き換えるのは正しい挙動で、
ここを待ち行列にすると最新の震度がいつまでも読まれない。

**EEW が予想震度の確定を待っている間も、EEW は最優先のまま。** 初報に予想震度が無く理由も判らない
ときだけ、第 2 フェーズは最大 3 秒待つ（上の表）。この待機中を「空き」と見なすと、震源を読み終えた
直後の数秒に地震情報が滑り込み、待ち明けの第 2 フェーズに**必ず**切られる。能登 16:08 の震源情報が
これで残り 5.7 秒を残して消えていた（当時の上限は 6 秒）。

**待ちには上限を置く**（`HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS` = 90 秒）。長めなのは、津波の
本文が 60 秒近くに達することがあり、短い上限では読み上げを途中で切ってしまうため。この上限が
効くのは VOICEVOX が無応答のときだけで、その状況ではそもそも何も聞こえないため、長く取っても
失うものは無い。**上限に達して割り込んだときは記録を残す**（優先度の高い読み上げを消す判断なので、
黙って消すと事後に追えない。VOICEVOX が落ちていると毎回起こるため間引いて出す）。

なお 90 秒は**1 回の待ち合わせあたり**の上限。下記のとおり待ち直すことがあるため、1 件の読み上げが
待つ総時間はこれを超えうる（優先度の高い読み上げが立て続けに始まった場合）。

**待つ条件は毎周回で作り直す。** 一度きりの判定にすると、待っている間に始まった読み上げを
見落とし、待ち明けに読み始めた側が進行中の読み上げを後ろから切る。読み始める直前にも見直して、
必要なら待ち直す。

#### 優先度が無かったときに起きていたこと

いずれも 2024/1/1 能登半島地震の実電文（20 分・EEW 6 件・106 報）を再生し、発話の開始時刻と
推定所要時間から重なりを数えて確認したもの。優先度を入れる前は 12 件の割り込みのうち 3 件が
「軽い方が重い方を消す」向きだった（入れた後は 0 件）。

- EEW 第 1 報が地震情報に潰されていた。16:08 の EEW 第 1 報が、その 0.36 秒後に**読み上げの
  始まった**震源情報に消された。震源情報の電文自体は EEW より先に届いており、上の表の遅延を経て
  読み上げが始まる。**割り込みは電文の到来順では決まらない**
- 大津波警報が地震情報に潰されていた。大津波警報の読み上げが、その 30 秒後に始まった地震情報に
  残り 2.9 秒を残して消された
- 長周期地震動情報が震度速報・地震情報を潰していた。2 件とも発生し、消された残りはそれぞれ
  18.9 秒・23.6 秒

**逆向き（優先度の高い側が低い側を切る）は許す。** 緊急度どおりであり、また地震情報の本文は
数千文字に達することがあって（能登本震の地震情報は読み切りに 2 分近くかかる）、その後ろに
EEW や津波を並べると致命的に遅れる。

#### 到来順を守る — 追い越されたら取り下げる

**待つのは「重いものが先に届いた」ときだけ。** 自分の予約より**後に**届いた重い読み上げに
追い越された場合は、待たずに取り下げる（`speakNonEEWDelayed`）。

| 到来順 | 扱い |
|---|---|
| 重いものが先 → 軽いものが後 | 軽い側が**待って読む**（順序どおり） |
| 軽いものが先 → 重いものが後 | 軽い側を**取り下げる**（読まない） |

> 上の行にも例外がひとつ。待ちは `HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS`（90 秒）で打ち切られ、
> そのときは割り込んで読む（この節の上の「割り込みを許す条件」）。VOICEVOX が無応答のときだけ
> 起こる経路で、その状況ではどちらも聞こえていない。

待って読むと「後から来た方が先、先に来た方が後」と喋ることになり、聞いている側には順序が
入れ替わって聞こえる。**優先度に例外は設けない**ので、津波の予約が EEW に追い越された場合も
取り下げる（画面・通知音・バナーは残るので、発表そのものは伝わる）。

判定は予約した瞬間と発話の直前に `speechBlocker` を取って比べるだけ。「予約時は空いていたのに、
いまは塞がっている」が追い越しの印。取り下げるときは先行合成も破棄し、タブ追従も呼ばない
（画面は追い越した側に留まる）。

**この規則が及ぶのは、間が明けて判定を通るまでの一度だけ。** 境目は「間が明けたときに塞がって
いたか」の一点なので、同じ順序の電文でも間の長さ（0.5〜4.2 秒）とのタイミングで挙動が変わる。

判定を通ったあとの扱いは 2 つに分かれる。**混同しないこと。**

- **まだ声が出ていない（順番待ち）**: 取り下げも割り込みも起きない。待っている間にさらに重いものが
  積まれても**待ち時間が延びるだけ**（`waitForSpeechSlot` は毎周回で条件を作り直して待つ）。
  順序そのものは守られる——先に届いた重いものの後に読まれるため
- **すでに読み始めている**: ここから割り込みの側の話になり、重い方が軽い方を切る
  （上の「逆向きは許す」）

つまり「予約した時点で既に塞がっていた」電文は、EEW の続報が連投される場面では**読まれるまで
長く待つ**ことがある。順序は入れ替わらないので取り下げていないが、待ちの上限（90 秒）まで
届けば割り込んで読む。

### 自動タブ切替の優先順位

タブの奪い合いには **2 つの駆動が併走する**（`src/utils/tabPriority.ts`）。

| 駆動源 | いつ動くか | 順序を決めるもの |
|---|---|---|
| **読み上げ追従**（`speech`） | 読み上げの発話を投入する瞬間 | 読み上げ側の待ち行列（`waitForSpeechSlot` / `chainEEWSpeech`） |
| **保持機構**（`hold`） | 電文の受信時・ユーザー操作・アイドル復帰・揺れ検知 | 下の優先度表と 15 秒の保持 |

読み上げがある経路は追従で動き、**順序の判断を読み上げ側に預ける**。重い電文の読み上げ中に
届いた軽い電文は、その読み上げが終わって自分の番が来たときに初めて画面を取る。こうして声と
画面が食い違わなくなる。

**ただし待たされずに読めるなら、通知音と同じ瞬間に先出しする**（`speakNonEEWDelayed`）。
通知音と声が重ならないよう電文の種別ごとに間を置いているため（0.5〜4.2 秒）、その間ずっと画面が
前のタブに留まると「音が鳴ったのに何も変わらない」ように見える。先出しするかどうかは
「いま読み上げを始められるか」だけで決める（判定は `speechBlocker`。待ち合わせと**同じ条件を
共有する**こと。二重に書くと、片方だけ直したときに「待たされないと踏んで画面を動かしたのに、
実際には待たされる」形の食い違いになる）。

- 対象は**タブを持つ非 EEW の経路**（地震情報・津波・長周期・それぞれの取消）。EEW は受信の瞬間に
  要求しているので対象外、南海トラフ系はタブを持たないので対象外
- 先出ししたあとも、発話を投入する瞬間にもう一度同じ追従を出す。待っている間に別の情報が画面を
  取っていれば、自分の番が来た時点で取り戻せる
- **先出しには最小滞留時間の床を掛けない**（`preSpeechTab` と `followSpeechTab` の使い分け）。
  先出しは「これから読む予定」にすぎないので、床を消費させると後から実際に声が出る側の追従を弾く。
  実際に踏んだ形: 大津波警報（間 4.2 秒）で先出し → 直後の震度速報（間 0.5 秒）が床で弾かれ、
  **声が始まっても**画面が津波タブに留まった（地震情報を読む 3.7 秒間ずっと食い違う）
- 先出しの判断が外れること（間を置いている最中に EEW や津波が割り込む）はある。**巻き戻さない。**
  割り込んだ側が自分で画面を取るため、放っておけば正しい方へ落ち着く

> **EEW だけは例外で、受信の瞬間にも要求を出す**（`setActiveTabRealtimeUrgent` /
> `setActiveTabRealtimeOnUpdate`）。予想震度が上がらない続報では読み上げが黙るため、追従だけに
> 任せると realtime を取り戻す手段が無くなる。この 2 つも駆動源は `speech` にしてあるが、それは
> 「発話の投入時に動く」という意味ではなく、**他の読み上げ追従に弾かれないための指定**。
> 冗長に見えても消さないこと（消すと EEW の続報で realtime へ戻る経路が失われる）。

読み上げが無い経路は保持機構で動く。該当するのは、強震モニタの揺れ検知（読み上げを持たない）・
読み上げが無効な端末・読み上げ文が空になる場合（長周期や、観測に変化のない津波の再送）・
ユーザーの手動選択・アイドル復帰。

> 区域を持たない津波の続報は**観測点更新として読み上げる**ので、通常はこちらに来ない
> （[tsunami-spec.md](tsunami-spec.md) §10「等級を伝えていない電文」）。読み上げ文が空になるのは
> 観測に一切変化がない再送のときだけ。

> **声と画面が一致するのは読み上げが有効なときだけ。** 読み上げが無効な端末は優先度と保持だけで
> 裁くため、EEW 発表中に震度速報や津波が画面を取れない場面が残る（設定の既定値は読み上げ無効）。
> 読み上げを持たない経路には順序を決める仕組みが無いための構造的な制約で、直すなら「拒否した
> 要求を後から実行する」別の仕組みが必要になる。
>
> ただし**読み上げの設定に関わらず効く変更もある**ので、「無効なら何も変わらない」ではない。
> ①EEW の続報が他の情報の画面を奪わない抑制（津波タブ表示中に続報で引き戻されなくなる）
> ②アイドル復帰が揺れ検知中に張る重み（揺れ検知のあと津波が画面を取れるようになる）
> ③揺れ検知の保持が他の移動を妨げない（揺れ検知中に地震情報が届いたら画面が移る）
> ④津波の観測点更新でも画面が移る（従来は新規発報と格上げだけだった）
> ⑤特別情報の受信でパネルを一時的に開く挙動。

| 優先度 | 契機 |
|---|---|
| 6 | EEW の新規発報・レベルアップ・誤報取消 |
| 5 | ユーザーの手動選択（ナビの選択・津波カードから地震情報へのリンク） |
| 4 | EEW の続報 |
| 3 | 津波（新規発報・grade 格上げ・観測点更新・解除／取消／失効） |
| 2 | 強震モニタの揺れ検知 |
| 1 | 地震情報・長周期地震動情報 |

揺れ検知が地震情報より重いのは「いま揺れている」を示す情報だから。津波より軽いのは、津波が
避難行動を促す情報だから。**長周期地震動を地震情報と同格にしているのは読み上げ側と揃えるため**で、
どちらも移動先は地震情報タブなのでタブの奪い合いは起きない。

#### 受け付けるかの判定（`shouldAcceptAutoTab`）

上から順に見る。

1. **保持が切れていれば通す**（`TAB_HOLD_MS` = 15 秒）
2. **揺れ検知（2）の保持は、他の移動を妨げない。** 揺れ検知のあとに地震情報や津波が届くのは
   実際に起きた順序どおりで、そこで画面が留まる方が不自然。**読み上げの有無に関わらず**通す。
   優先度の値（2）は逆向き（揺れ検知が地震情報の保持を越えて realtime を取る）で意味を持つ
3. **EEW の続報（4）は、他の情報が確保している画面を奪わない。** 「非 realtime へ移ったあとは
   続報で引き戻さない」という片方向の抑制で、優先度の仕組みを入れる前の実装にあった考え方を
   駆動源の枠組みで作り直したもの（優先度の比較だけでは続報 4 ＞ 津波 3 で通ってしまう）。
   これが無いと、津波を読み上げて画面を移した直後に続報が届いて realtime へ戻り、数秒ごとに
   往復する。realtime を EEW 自身が確保している間（保持が EEW 由来）は素通りする
4. **追従どうしは保持を見ない。** 順序は読み上げ側が決めているので、タブ側で重ねて守ると
   「読み終えた電文の保持の残り」が次に読む電文を弾く（この二重防御が「喋っているのに画面が
   動かない」の正体だった）。
   **ここを「手動選択以外は全部突破」まで広げてはいけない**（広げると、区域を持たない津波電文で
   受信時要求に落としたフォールバックを長周期が即座に奪い、アイドル復帰が EEW 中に張った保持も
   地震情報だけで外れる）
5. それ以外は優先度を比較する（同格以上は通す。新しい情報が勝つ）。手動選択を突破できるのは
   EEW の新規発報・レベルアップ・誤報取消（6）だけ

> **揺れ検知中に地震情報や長周期が届くと、画面は earthquake タブへ移る**（読み上げの有無に
> 関わらず）。地図の内容は表示中のタブから決まるため、リアルタイム震度の観測点・検知点・予報円は
> 一時的に見えなくなる（[map-rendering-spec.md](map-rendering-spec.md) §3）。実際に起きた順序を
> そのまま見せる方針を採った結果で、検知そのもの（判定エンジン・通知音・検知カード）はタブに
> 関わらず動き続ける。揺れがレベルアップしたり別地点で検知されれば realtime へ戻る。

#### そのほかの決めごと

- **保持は「最後に動いた理由」で上書きする**（最大値を取らない）。EEW の新規発報（6）で確保した
  直後に続報（4）で動けば、保持も 4 に下がる。最大値を取ると、その EEW が終わるまで手動選択が
  奪われ続ける
- **追従には最小滞留時間がある**（`TAB_FOLLOW_MIN_DWELL_MS` = 1.5 秒）。VOICEVOX が起動して
  いない端末では合成が 1 つも通らず発話がほぼ即座に終わるため、床を置かないと声が出ないまま
  タブだけが激しく入れ替わる。**優先度が上がる追従は床を無視する**（声が切り替わっているのに
  画面が遅れないように）。床は追従だけに掛け、受信時の要求には掛けない
- **ユーザー操作とアイドル復帰は必ず通る。** どちらも `forceTab` を通り、保持を捨ててから
  張り直す。拒否できる形にすると次の 2 つが起きる。①ユーザー操作: 「押しても切り替わらない」
  （津波タブを見ている間に地震情報へのリンクを押す経路が該当した）②アイドル復帰: タイマーは
  一発限りで再スケジュールされないため**二度と復帰しない**。とくに設定「自動復帰までの時間」の
  15 秒は保持時間と一致するため、直前の手動操作と必ず衝突する
- **アイドル復帰が realtime に留まるときの重みは、留まる理由に合わせる**（`idleRevertPriority`）。
  EEW 発表中なら続報相当（4）、揺れ検知だけなら揺れ検知（2）。揺れ検知だけのときに EEW 相当を
  張ると優先度表（揺れ検知＜津波）が逆転し、津波警報や「別地点で揺れ検知」が画面を取れなくなる
- **生のタブ切替を使わないこと。** 優先度を通らない移動は、張るべき保持を張らないまま動く。
  実装では `setActiveTab` を呼べるのは `requestAutoTab` だけという不変条件にしてある
  （配り忘れを 3 箇所作り、いずれも「画面が奪われる」「復帰しない」という形で出た）
- 拒否したときもパネルの折りたたみは解除する（保持は「今見せるべきものを守る」ためで、情報を
  隠すためではない）
- **南海トラフ臨時情報・後発地震注意情報・関連解説情報はタブを持たない**ので自動タブ切替の
  対象外。地図に重ねた帯（`SpecialInfoBanner`）で伝えるため移動先が無い。代わりにパネルを
  一時的に開く挙動があり、詳細は [architecture-spec.md](architecture-spec.md) §4 が単一情報源
- **読み上げ中のアイドル復帰は別課題。** 各地の震度は読み切りに 2 分近くかかることがあり、
  その間に既定 30 秒のアイドル復帰が発火すると声と画面が食い違う。復帰を延期する変更は
  「二度と復帰しない端末」を作る危険があるため、この修正には含めていない

ログの読み方（成立・拒否はいずれも `console.debug`）。

| 文言 | 意味 |
|---|---|
| `タブ名を要求` | 判定に入る前（次の行を見るまで結果は分からない） |
| `→ タブ名 移動` | 成立して移動した |
| `→ タブ名 スキップ` | 優先度・抑制の判定で拒否された（理由が括弧内に出る） |
| `→ タブ名 追従を間引き` | 最小滞留時間の床で間引かれた |

追従は呼び出し元が名前付きの記録を持たないものがあるため、結果は `requestAutoTab` 側で残している。
要求の文言を「→ …移動」と分けているのは、1 行目だけを読んで「移動した」と誤読しないため。

### 設定連動

- `settings.soundEnabled` — アラート音の ON/OFF
- `settings.voicevoxEnabled` — 読み上げの ON/OFF（`soundEnabled` と独立）
- **ブラウザ通知は種別ごとに 3 つの独立トグル**:
  - `settings.notifyEEW` — 緊急地震速報の発報・昇格時のブラウザ通知 ON/OFF
  - `settings.notifyTsunami` — 津波注意報以上のブラウザ通知 ON/OFF
  - `settings.notifyDetection` — 強震モニタ揺れ検知時のブラウザ通知 ON/OFF
- `settings.notifyMinScale` — 通知の最低震度
- `settings.idleRevertSec` — **操作なし経過後**にデフォルトタブへ戻るまでの秒数（`0` で無効。「情報受信後の N 秒」ではなく「ユーザー操作が止まってからの N 秒」で判定）

### 解消済み

- **AUD-2**: EEW キャンセル電文が P2PQuake WS と Yahoo の両方から届いた場合の二重鳴り防止。`hadKey=true`（このセッションで表示中の EEW）のみで音・通知・読み上げを発火（`useLiveEventHandler.ts`）。2 経路が重なるのは standard 版限定だが、`hadKey` ガード自体は両バリアントで働く（[`eew-spec.md`](eew-spec.md) §3）
- **AUD-4**: 新しい読み上げの開始時に旧セッションの合成リクエストを `AbortController` で打ち切るようにした。セッション ID の更新だけでは in-flight のリクエストが完走して VOICEVOX を占有し、新規発話が待たされていた
- **AUD-6**: 津波の解除/取消/期限切れの通知音を追加（`playAlertSound('tsunamiCancel')`。音の内容は §2 の表を参照）
- **自動タブ切替の優先度**: 後から来たイベントが無条件にタブを奪う問題を解消した（§6「自動タブ切替の
  優先順位」）。EEW が確保した realtime を地震情報が即座に奪い、声は EEW を守るのに画面だけ取られて
  いた。EEW 誤報取消の 10 秒オーバーレイ中に無関係な地震情報でタブが即消える問題も同時に解消
- **AUD-7**: 読み上げは常に `voicevoxEnabled` 単独で判定するように統一。`soundEnabled` はアラート音のみに影響し、`voicevoxEnabled` の可否とは独立に動く
