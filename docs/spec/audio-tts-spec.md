# 音声・TTS 仕様書

> 本書は**現在の実装が通知音・読み上げ・ウィンドウタイトル・自動タブ切替をどう扱うか**をまとめた
> 仕様書。実コードと食い違う場合は実コードを正とする。
> **読み上げと自動タブ切替の優先順位の単一情報源は §6。** 緊急地震速報・津波・地震情報・揺れ検知が
> 画面と声を取り合う規則はすべてそこにある（他の仕様書からはそこを参照している）。

## 1. 概要

情報受信時にユーザーへ通知する 3 系統の副作用を扱う:

- **通知音**（`alertSound`）: Web Audio API で合成した種別別のアラート音
- **VOICEVOX 読み上げ**（`voicevox`）: ローカル VOICEVOX HTTP API 経由の音声合成（任意）
- **ウィンドウタイトル**（`useAlertTitle`）: ブラウザタブ / ウィンドウのタイトル書き換え（AutoHotKey 等の外部監視向け）

さらに以下も関連する:
- ブラウザ通知（`Notification` API）
- 自動タブ切替
- 自動カメラフィット

すべての発火は `src/hooks/useLiveEventHandler.ts` で一元的にディスパッチする。

## 2. 通知音（`alertSound`）

`src/utils/alertSound.ts`。Web Audio API の `OscillatorNode` + `GainNode` +
`BiquadFilterNode`（マリンバのみ）で種別ごとの音を合成する。事前録音ファイルは持たない。

減衰する音は `decayTone()` を通す。**指数減衰は 0 に到達できないため 0.001 まで落として
から 0 へ落とし切って停止する。** 0.001 のまま停止すると段差が残り、無音区間にティックが
出る（1 つの音で 2〜6 本のオシレータが同時に切れるため −50 dBFS 前後まで積み上がる）。
この終端処理は `decayTone()` の 1 箇所に集約してあるので、ここを種別ごとに分岐させないこと。

> この文書で音の大きさは **dBFS**（歪まずに出せる最大を 0 とした対数の目盛り）で書く。
> **必ず負の値で、0 に近いほど大きい。** −6 と −12 なら前者が 2 倍の振幅、6 dB ごとに 2 倍。

### 音の種類

| 種別 | 用途 | 概要 |
|---|---|---|
| `eewSpecial` | EEW 特別警報 | 警報アラーム 9 連打（Bb4/F4 交互）+ 58Hz の支え（約 1.15s） |
| `eew` | EEW 警報 | 警報アラーム Bb3 の 2 連（約 1.0s） |
| `eewForecast` | EEW 予報 | ダークピアノ 2 音 F4→A4（緩やか） |
| `eewUpdate` | EEW 続報 | ダークピアノ F4 の単音（0.5 秒） |
| `eewFinal` | EEW 最終報（自動解除の直前は使わず、真の最終報用） | ダークピアノ F4→C4 の穏やかな 2 音 |
| `eewCancel` | EEW 誤報取消 | ダークピアノ 3 音 A4→F4→C4（降下） |
| `tsunamiMajor` | 大津波警報 | 上昇スイープ 220→620Hz × 5 回（往復せず駆け上がる。約 1.9s） |
| `tsunami` | 津波警報 | 往復スイープ 260→560Hz × 3 回（約 2.4s） |
| `tsunamiWatch` | 津波注意報 | 往復スイープ 300→500Hz × 2 回（正弦波で穏やか。約 1.4s） |
| `tsunamiForecast` | 津波予報（若干の海面変動） | 往復スイープ 380→460Hz × 2 回（最も穏やか。約 1.6s） |
| `tsunamiUpdate` | 津波観測情報の更新 | 純音 2 音 F#4→C#5 |
| `tsunamiCancel` | 津波の解除・取消・期限切れ（cancelReason の 3 種は音では区別せず単一音で伝える） | 純音 2 音 G4→C4（下行完全 5 度の終止形。約 0.84 秒） |
| `earthquake` | 地震情報（震源・震度 / 各地の震度） | ピアノ上昇 4 音 E4→G#4→B4→E5 |
| `earthquakePrompt` | 地震情報（震度速報） | ピアノ上昇 3 音 G#4→B4→E5 |
| `earthquakeInfo` | 地震情報（震源情報・遠地地震・その他） | ピアノ 2 音 G4→B4 |
| `kyoshin` | 揺れ検知（confirmed） | マリンバ 2 音 C#6→A5（下行長 3 度） |
| `kyoshinCandidate` | 揺れの候補（faint / likely） | マリンバ単発 F#5（控えめ） |
| `specialInfo` | 南海トラフ臨時情報・後発地震注意情報 | 純音 A4×2 連打 → D5（上昇） |
| `specialInfoCommentary` | 南海トラフ関連解説情報 | 純音 2 音 D5→A4（下降・控えめ） |

> 解説情報に専用音を割り当てているのは、**平常時にも定期的に届く**ため（発表頻度は
> [data-sources-spec.md](data-sources-spec.md) §2）。段階の発表（`specialInfo`）と同じ音を鳴らすと、
> 実際に「巨大地震注意」が出たときに音で区別できなくなる。上昇（臨時情報）と下降（解説情報）で
> 向きを逆にして聞き分けられるようにしている。

### 発火 API

```ts
playAlertSound(type: AlertSoundType)
```

内部で `AudioContext` の取得・resume を行う。`getCtx()` はシングルトンで、
マスターチェーン（`_master`）と一緒に使い回される。

上表の各種別とは別に、S 波の到達直前に鳴らす専用の音がある（`AlertSoundType` には属さず、
`playCountdownBeep(second)` を直接呼ぶ）。残り 5 秒から 1 秒まで、1 秒ごとに 1 回鳴る。

残り秒数が減るほどパルスが速く・多くなる（ゲート周波数 8→20Hz、パルス数 2→6）。
残り 1 秒だけサブ低音 2 本と高音を重ねて衝突感を出す。ホーム地点を設定していないと
S 波の到達時刻を計算できないため鳴らない。

**音色は警報アラームに揃えてあるが、段階の作り方（ゲート周波数とパルス数）は別の話。**
5 段階の聞き分けはそちらが担っているので、質感を変えるときも触らないこと。

### 系統の分け方 — 7 つのプリミティブ

すべての通知音は次の 7 つのどれかで作る。**分け方の軸は知らせの性格**で、音色の好みではない。

| プリミティブ | 使う音 | 何を伝えるか | 作り方 |
|---|---|---|---|
| `pianoNote` | 地震情報・震度速報・遠地地震 | 地震そのものの確定情報 | ユニゾン 3 本＋非整数の上部倍音＋サブオクターブ |
| `darkPiano` | EEW 予報・続報・最終報・誤報取消 | EEW の穏やかな報 | ユニゾン 3 本＋整数倍音 2 本（情報系より狭い離調） |
| `darkAlarm` | EEW 警報・特別警報・S 波カウントダウン | 警報級の切迫 | 左右への振り分け＋サブオクターブ 2 段＋トランジェント |
| `sweep` | 津波 4 段階 | 津波の等級 | 左右への振り分け＋サブオクターブ 2 段 |
| `marimba` | 揺れ検知・その予兆 | 揺れを検知した | 木琴の共鳴比（1 : 4 : 10）＋ローパス |
| `warningBeep` | 震度更新音 | 揺れが強まっている | 矩形波 2 本を ±10 セント離調＋正弦の芯＋サブ＋ローパス |
| `ding` | 津波の観測更新・解除、南海トラフ 2 種 | 値が動いた・状況が変わった | 正弦＋第 2 倍音 |

**音を足すときはどれかに属させること。** 系統を固定しておくと、新しい種別を作るときに
「どんな音にするか」を毎回考えずに済み、利用者の側も系統で役割を推し量れる。

**ただし役割が既存のどれとも違うなら、系統を増やすほうが正しい。** 「揺れを検知した」（一度きりの
通知）と「揺れが強まっている」（進行中の警告）は別の知らせで、同じ系統に入れると片方が
役割を果たせなくなる。**歯止めの意味は「安易に増やすな」であって、役割の違いを無視しろでは
ない**（実例は §10 の 2026-08-30 の項）。

**フィルタを使うのは `marimba` と `warningBeep` だけ。** 前者は木の柔らかさ（板の共鳴が
高域を吸う）を、後者は連打で耳に刺さらないための頭打ちを作っている。

#### 残響は持たない（全系統）

情報系に広い残響（2.9 秒）、EEW の穏やかな音に短い残響（0.85 秒）を載せていたが、
**全廃した。** 連続して鳴る音では尾が重なって濁る——地震情報は 0.16 秒間隔の 4 音なので、
1 音ごとに付いた尾が積み上がって「うざったい」響きになっていた。

厚みはユニゾンと倍音が担っているため、外しても薄くはならない。副次的に、
`ConvolverNode` の生成（数秒ぶんのバッファ合成）とその失敗への備えが丸ごと不要になり、
`unlockAudio()` はマスターチェーンだけを先に作ればよくなっている。

**戻さないこと。** 音を「豊かにする」目的で残響を足すと、同じ濁りが再発する。

#### 厚みの作り方 — 1 本のオシレータでは電子音になる

音階を持つ音（`pianoNote` / `darkPiano`）は基音を **3 本のユニゾン**で鳴らす。実際の
ピアノは 1 音を複数の弦で鳴らしており、その張力差が生むうねりが「楽器らしさ」の正体に
なっている。1 本で出すとうねりが無く、シンセサイザーの音に寄る。

`pianoNote` はさらに**倍音を整数倍からわずかに外す**（インハーモニシティ）。弦は硬さを
持つため実際の倍音は整数倍より高いところに立ち、整数倍のまま重ねるとオルガンに寄る。
`darkPiano` は整数倍のまま——EEW は硬さを保つ判断。

警報系（`darkAlarm` / `sweep`）は**左右へ振り分ける**。同じ波形を ±7 セントずらして左右に
置くと、干渉によるうなりが生まれてサイレンらしい厚みが出る。**モノラルで鳴らすと薄くなる。**
`StereoPannerNode` を持たない環境ではマスターへ直結し、初回だけ記録する（音が消えるより
中央で鳴るほうがよいため。ただし黙って落とすと、退化したことを後から診断できない）。

残る 3 系統は別の作り方をする。

| 系統 | 厚みの作り方 |
|---|---|
| `marimba` | 木琴の共鳴比（1 : 4 : 10）。倍音が上へ大きく離れるので基音の周りが濁らない。板が高域を吸う柔らかさはローパスで作る |
| `warningBeep` | 矩形波 2 本を **±10 セント**ずらして重ねる。左右に振らず 1 点で鳴らすため、警報系より広い離調でうねりを作る。連打で耳に刺さらないよう基音の 8 倍でローパス |
| `ding` | 正弦と第 2 倍音だけ。**厚みを足さないことが役割**——値が動いたことを伝えるだけの音なので、主張させない |

> `pianoNote`（8ms）・`darkPiano`（6ms）・打撃音（7ms）はアタックに広帯域ノイズを重ねて
> 「鍵盤を叩いた感じ」を出していたが、これが小型スピーカー（iPad・ノート PC 内蔵）で
> 「プチ」と聞こえる正体だった。1 秒おきに鳴る EEW 続報や 0.16 秒間隔で 4 音鳴る地震情報では
> 粒が並んで「プチプチ」になる。実機の聴き比べを経てこの 3 系統から廃し、失った厚みは
> ユニゾンと上部倍音で補っている（→ 上記「厚みの作り方」）。

### 掃引の形の分け方 — 大津波警報だけ上がりっぱなし

津波の 4 段階は同じ `sweep()` で鳴らす。段階の差は波形（警報級は鋸波、注意報以下は正弦波）・
周波数・回数で付けていたが、**大津波警報と津波警報はそれだけでは聞き分けられなかった。**

掃引は音域を上下に動くため、周波数の範囲が近いと途中で互いの音域を通過する。旧構成
（大津波 200→500Hz × 5 回 / 津波 260→560Hz × 3 回）は開始が 60Hz 違うだけで、波形も
声部構成もほぼ同じだった。回数の違いは最後まで聴かなければ分からない。**避難を促す最上位の
警報が、冒頭の 1〜2 秒で判別できない状態だった。**

そこで**掃引の形そのものを変えた**。耳は音の高さより動きの向きで先に区別するため、
音域が重なっていても形が違えば別物として聞こえる。

| 段階 | 折り返し点（`peakAt`） | 形 | 1 周期 |
|---|---|---|---|
| 大津波警報 | 0.88 | 上がりきってから急に戻る | 0.34 秒 |
| 津波警報 | 0.55 | 上がって下がる往復 | 0.70 秒 |
| 津波注意報 | 0.55 | 同上 | 0.60 秒 |
| 津波予報 | 0.55 | 同上 | 0.70 秒 |

`peakAt` は「1 周期のうち最高音に達する位置」の比で、実装は**分岐ではなくこの 1 つの値**で
両方の形を表す（`sweep()` は元から「開始 → 最高音 → 開始」の 2 本の線で書かれており、
折り返し点が 0.55 に固定されていただけ）。分岐を増やすと、次に片方だけ直して食い違う。

**弁別を担っているのは折り返し点と 1 周期の長さの 2 つで、周波数ではない。** 大津波警報
（220→620Hz）は津波警報（260→560Hz）の音域を完全に含む。`alertSound.test.ts` の
「津波の段階は掃引の形で聞き分ける」がこの 2 つを固定しているので、**どちらかを揃える変更は
テストで止まる**。

### 音量制御

- `globalVolume`（0.0〜1.0）を `setSoundVolume(v)` で更新
- 1 つの音の中での声部のバランス（ユニゾンの配分・倍音の比など）は各プリミティブが持つ
- 音量 0 では `decayTone()` / `gateTone()` / `sweep()` がノードを 1 つも作らない
  （終端の 0.001 ぶんすら鳴らさない）。**0 は正当だが負値と NaN は必ず計算ミス**なので、
  同じ無言の早期 return に合流させず警告に残す

#### 種別ごとの音量は「系統 × 深刻度」で決める

**種別ごとの個別の値を書かないこと。** 音量は 2 つの定数の積だけで決まる。

| 定数 | 決めるもの | 値 |
|---|---|---|
| `BASE_GAIN` | 系統（プリミティブ）ごとの基準 | piano 0.23 / darkPiano 0.32 / darkAlarm 0.48 / sweep 0.70 / marimba 0.35 / beep 0.40 / ding 0.39 |
| `SEVERITY` | どれだけ急を要するか。**3 dB 刻みの 5 段** | critical 1.00 / warning 0.71 / caution 0.50 / info 0.35 / update 0.25 |

`BASE_GAIN` が系統ごとに違うのは、声部の本数と重なり方が違うため。**揃えるのは同じ系統の
中**であって、系統をまたいだ数値の一致ではない。値は実測（マスターチェーンのコンプレッサーを
通過したあとのピーク）が下表の目標へ落ちるように決めてある。

| 段 | 目標 | 種別 |
|---|---|---|
| `critical` | −5 dBFS | EEW 特別警報・大津波警報・S 波カウントダウンの残り 1 秒 |
| `warning` | −8 dBFS | EEW 警報・津波警報・震度更新音の震度7 |
| `caution` | −11 dBFS | EEW 予報・津波注意報・揺れ検知・S 波カウントダウンの刻み |
| `info` | −14 dBFS | 地震情報・震度速報・遠地地震・津波予報・南海トラフ臨時情報 |
| `update` | −17 dBFS | EEW 続報 / 最終報 / 誤報取消・津波の解除 / 観測更新・南海トラフ関連解説・揺れ検知の予兆・震度更新音の震度2以下 |

震度更新音は 8 段あり 3 dB 刻みでは表せないため、`BEEP_SEVERITY` が段を刻む。震度6弱までは
1 dB ずつ緩やかに上げ、**震度6強と震度7 では 2 dB ずつ開く**。勾配を作っているのは音量だけ
ではない——音数（2 → 8 音）と `deep`（震度5弱以上でサブオクターブが厚くなる）も効いており、
実測の勾配は端から端まで（震度2以下 → 震度7）で合計 10.5 dB。**`BEEP_PATTERNS` は音量を
持たない**（音数・間隔・長さだけ）。
段の割り当ては下記「震度更新音の段は気象庁の階級と対応させる」。

**同じ値を渡しても、鳴り方で音圧は変わる。** EEW 続報（1 音・−24.3 dBFS）と誤報取消
（3 音が 0.1 秒間隔で重なる・−12.2 dBFS）はどちらも `darkPiano × update` だが 12 dB 開く。
音数と重なりはその音の作りが決めるもので、音量の設定ではない。**揃えるために片方の値だけを
動かさないこと。** 手加減で帳尻を合わせる運用をやめるために、決め手をこの 2 つへ絞っている。

**S 波カウントダウンも同じ設計に載せてある。** ただし載せ替えで音は変えていない（従来の
6 つの値が、そのまま `darkAlarm × caution`（刻み）と `darkAlarm × critical`（残り 1 秒に
重ねる支え）の比で表せた）。残り 1 秒だけは声部が 4 本増えるため −2.5 dBFS で**アプリ中
いちばん大きい**。S 波到達の直前に鳴る音として意図したもの。

#### 震度更新音の段は気象庁の階級と対応させる

`playKyoshinUpdateSound(maxIndex)` は強震モニタのインデックス（0〜20）を `kyoshinLevel()` で
**8 段**へ落として鳴らす。

| 段 | 震度 | 音数 | 音程 | 音圧 |
|---|---|---|---|---|
| 0 | 0〜2 | 2 | A4 → D5 | −17.8 dBFS |
| 1 | 3 | 3 | D5 → F5 → G5 | −16.7 dBFS |
| 2 | 4 | 4 | D5 → F5 → G5 → A5 | −15.7 dBFS |
| 3 | 5弱 | 4 | 同上（`deep`） | −13.1 dBFS |
| 4 | 5強 | 5 | F5 ↔ C5 | −12.0 dBFS |
| 5 | 6弱 | 6 | G5 ↔ D5 | −10.8 dBFS |
| 6 | 6強 | 7 | A5 ↔ D5 | −9.3 dBFS |
| 7 | 7 | 8 | C6 ↔ C5 | −7.3 dBFS |

**まとめてよいのは震度0〜2 だけ。** この段は音を選ぶためのものではない——`useKyoshinAlerts`
が「段が上がったか」で**検知音・リアルタイムタブへの移動・地図の揺れフォーカス**の 3 つを
起動する判定にも使う。畳んだ範囲では揺れが悪化しても 3 つとも起きない。

**上位 3 段は音程で分ける。** 音数は 6〜8 音まで来ると 1 音の差が聞き取りにくく、音量の差も
隣どうしで 1〜2 dB しかない。**震度7 だけ 880Hz の外（C6 ↔ C5）へ出している**のはこのため。
440〜880Hz に収まる 6 音は震度4 の時点ですべて出そろっており、震度6弱（G5 ↔ D5）と
6強（A5 ↔ D5）はそれを 2 音ずつ反復しているだけで、震度7 へ新しく割り当てる音が残らない。

**1047Hz より上へは上げないこと。** この一族の音域は 659〜1318Hz から 2 度にわたって
下げられてきた経緯があり（§10 の 2026-08-29 と、同 08-30 の「系統を役割で分け直し」）、
最上段だけ 1047Hz へ戻したのが現状。ここから先は下げてきた意味が失われる。

### マスターチェーンとリミッター

`alertSound` の全音源と `voicevox` の TTS 発話は、個々の `.connect(ctx.destination)` ではなく
`getMasterInput(ctx)`（`alertSound.ts` から export）を経由し、
`GainNode → DynamicsCompressorNode → ctx.destination` の順で流れる。特別警報級 EEW
（`eewSpecial`）と大津波警報（`tsunamiMajor`）が同時発火した場合、または TTS 継続中に
警報音が重なった場合、素の加算合成では波形がクリップして警報音がノイズに埋もれるため、
compressor で合成音圧の暴走をリミッター的に抑える。パラメータは threshold=-6dB / knee=6 /
ratio=4 / attack=3ms / release=250ms（音楽制作のリミッター標準的な値）。

**単独再生でも threshold を超える音がある。** 複数音を重ねる種別は 1 種別だけで超えうる。
「単独なら素通し」を前提にしないこと。

実測（音量 1.0・compressor 通過後のピーク。全種別クリップなし）:

| 種別 | ピーク | 種別 | ピーク |
|---|---|---|---|
| S 波カウントダウン 残り1秒 | −2.5 dBFS | EEW 警報 | −9.0 dBFS |
| EEW 特別警報 | −4.0 dBFS | S 波カウントダウン 刻み | −9.0 dBFS |
| 大津波警報 | −4.0 dBFS | EEW 予報 | −9.9 dBFS |
| 震度更新音（震度7） | −7.3 dBFS | 津波注意報 | −10.9 dBFS |
| 津波警報 | −8.0 dBFS | 揺れ検知 | −11.1 dBFS |

以前は誤報取消・震度更新音・地震情報・震度速報が上位 4 つを占めており、深刻度と音圧の
順位が食い違っていた。上記「系統 × 深刻度」で組み直した結果、閾値（−6 dBFS）を超えるのは
最も重い 3 つだけになっている。連打で耳につくようなら、段ではなく `BEEP_SEVERITY` を見ること。

**生成直後の約 0.4 秒はアタックを強く潰す。** Chrome の `DynamicsCompressorNode` は
作りたての状態だと減衰が深く、実測で 8 dB 小さく鳴る。そのため最初の音を鳴らす瞬間に
マスターチェーンを作ると **1 発目だけ小さく鳴る**。`unlockAudio()`（ユーザー操作の時点で
呼ばれる）でマスターチェーンを先に作り、発報までに定常へ落ち着かせている。
なおセッション最初のポインタ操作が試聴ボタンに直接当たった場合だけは 0.4 秒を確保できず、
その 1 回だけ小さく鳴る（設定タブを開く操作で先に解除されるため通常は起きない）。

### 既知の課題

- 優先度キュー（低優先度の音を高優先度中に抑制するシリアライズ）と重複再生の抑止（dedup）は
  未実装。マスターチェーンの compressor で合成音圧の暴走は防いでいるが、UX として「特別警報中は
  他の音を鳴らさない」「同一種別の呼び出しを短時間ガードする」等の能動的な制御は行っていない。
  dedup を種別単位で入れると、群発地震で連続する別イベントの警報音を誤って抑止してしまう
  リスクがあるため、実装するなら eventId 単位のキーで慎重に設計する必要がある
- `AudioContext.resume()` の Promise を await せずに `currentTime + 0.02` をスケジュール（iOS Safari で初回音がドロップしうる）。**失敗はどの経路でも警告に残す**（`unlockAudio()` と、実際に毎回の発報で通る `playAlertSound` / `playCountdownBeep` / `playKyoshinUpdateSound` の 3 つ）。resume に失敗したまま鳴らすと全種別が無音になるため、記録が無いと原因を追えない
- このアプリには Error Boundary が無く、React 18 は捕捉されない例外でツリー全体をアンマウントする。
  通知音は `useEffect` やイベント処理から直に呼ばれるため、音の例外ひとつで画面全体が消えうる。
  暫定として `playAlertSound` / `playCountdownBeep` / `playKyoshinUpdateSound` が例外を外へ出さず
  `log.error` に残す契約にしてある（音だけを諦めて通知と読み上げは通す）。Error Boundary の設置は別課題
- `darkAlarm` の内部ゲイン合計が 1.0 を超える（声部を増やしたため約 1.4）。これを使う
  `eew` / `eewSpecial` は単独でもクリップしうるが、実測では compressor が吸収している（上記の表）

## 3. VOICEVOX 読み上げ（`voicevox`）

**VOICEVOX** は無料で配布されている音声合成ソフトウェア（[voicevox.hiroshiba.jp](https://voicevox.hiroshiba.jp/)）。
ユーザーが自分の PC 上で起動しておくと、その HTTP API に対してテキスト → 音声合成をリクエストできる。
本アプリは任意機能として組み込んでおり、VOICEVOX を起動していない場合は無音で失敗する。

`src/utils/voicevox.ts`。VOICEVOX ローカル HTTP API（デフォルト `http://localhost:50021`）を呼び出して
音声合成する。任意機能で、有効化はユーザー設定 `voicevoxEnabled` による。

### 接続先の確認

設定タブは接続先（`voicevoxUrl`）が生きているかを確かめ、結果を「接続状態」として出す
（表示の文言は [`settings-pwa-spec.md`](settings-pwa-spec.md) §2）。確認には 2 つの前置きがある。

- **入力が落ち着くまで待つ**（800ms・`VOICEVOX_URL_DEBOUNCE_MS`）。入力欄は 1 文字ごとに設定を
  保存するため、そのまま確認すると打鍵のたびに接続を試みる。しかも**入力途中の値でも接続は成立しうる**
  （ブラウザは裸の整数をアドレスと解釈するので、「192」と打つ途中の「1」が `0.0.0.1` になる）。
  DMDATA の APIキーが同じ理由で先にデバウンスされている（[`data-sources-spec.md`](data-sources-spec.md) §2）
- **URL として成立しない値では通信しない**（`isValidVoicevoxUrl`）。見るのは解析できること・
  スキームが http/https であること・ホスト名が空でないことだけで、ホスト名の中身には踏み込まない
  （LAN のホスト名・IPv4・IPv6 のいずれも来る）。スキームを書き忘れた `192.168.0.64:50021` のような
  入力を「起動していません」と誤診しないための判定であって、**入力途中の値を弾く役割は持たない**

末尾のスラッシュは連結する側で落とす（`apiBase`）。`http://localhost:50021/` は URL として正しいので
上の判定は通るが、そのまま繋ぐと `//version` になって VOICEVOX が 404 を返し、起動しているのに
「起動していません」と出る。合成の呼び出しも同じ関数を通す。

**設定タブの「試聴」も確認済み（待ったあと）の URL へ送る。** 画面に並ぶ話者はその URL から
取ってきたものなので、選べる相手と鳴らす相手を一致させる。入力欄の生の値を使うと、URL を
書き換えている最中に押したときだけ未確認の宛先へ飛んで無音に終わる。

### API 呼び出し

呼び出す順に:

- `POST /audio_query` — テキストからアクセント句を生成
- `POST /accent_phrases` — 句区切り辞書のカナ表記からアクセント句を作る（下記「辞書」節で使う）
- `POST /mora_data` — 繋ぎ合わせたアクセント句の音素長と音高を引き直す（下記「辞書」節で使う）
- `POST /synthesis` — アクセント句から WAV を合成

中の 2 つは辞書に該当する語を含むときだけ呼ぶ。

合成 WAV は `AudioContext.decodeAudioData` でデコードして `AudioBufferSourceNode` で再生する。

テキストは一度にまとめて合成せず、**句読点（`。、！？`）の直後で区切った塊（チャンク）ごとに**
合成する（`splitIntoChunks`）。最初のチャンクができた時点で再生を始め、鳴らしている間に次を
合成するため、長い文でも読み始めを待たせない。短すぎる塊（5 文字未満）は次と繋げる。
**区切り文字を持たない文はチャンクに割れず、その分だけ発話の切れ目も生まれない。**

#### チャンク末尾の句読点には間を足す

区切るのは句読点の**後ろ**なので、句読点は必ずチャンクの末尾に来る。**この位置の句読点は
そのままでは音にならない。** VOICEVOX は後ろに何も続かない句読点に間（`pause_mora`）を
付けないため（実測: 話者を変えても付かない。読点だけの文はアクセント句が 0 個で返る）、
チャンクを隙間なく詰めて鳴らすと句読点が消える。地名を読点で並べても一続きに聞こえる、
というのがこれで起きていた症状（→ §4「地域名・地点名の区切り」）。**同じ症状はチャンクの内側の
別の切れ目でも起きる**（→ 下記「分割で落ちた句読点を戻す」）。

そのため、**後続のチャンクがあるときだけ**末尾に間を足す（`CHUNK_BREAK_PAUSE`）。長さは
チャンク境界に元からある無音（合成の前後に入る各 0.1 秒）を差し引いて、文中の読点と同じ
間（0.27 秒）になるよう決めている。読点と句点で値を変えていないのは、VOICEVOX 自身が文中で
どちらにもほぼ同じ長さを与えるため。**最後のチャンクには足さない**（読み終わりに無音が伸び、
再生の完了を待っている次の読み上げがその分遅れる）。

値の検証は合成した WAV の無音区間を測って行っているが、この測り方は**次のチャンクの語頭の
子音に左右される**（鼻音のように立ち上がりが緩い語頭は無音が長めに出る）。そのため実測は
0.28 秒前後に散り、目標の 0.27 秒とは 0.01〜0.02 秒ずれる。定数自体も計算値 0.107 を
0.11 に丸めている。**この幅は測り方と丸めによるもので、狙いは文中の読点と同じ間**。

足すかどうかは合成を呼ぶ側が渡す。**入口は 4 つある**（先行合成・切り出し語の作り置き・
再生側の先頭チャンクの作り直し・再生中の次チャンクの先行合成）ので、渡し忘れると経路によって
間が入らなくなる。

**同じ句を作りうる入口どうしは、必ず同じ値を渡すこと。** 切り出し語の作り置きと、再生側の
先頭チャンクの作り直しは同じ句を合成する。作り置きの対象（`EEW_LEAD_PHRASES`）はすべて読点で
終わる 1 チャンク目で後ろに震源名が続くため、どちらも常に「後続あり」を渡す。片方が渡し忘れると
**どちらの経路が先にキャッシュを埋めたかで間が変わる**非決定的な不揃いになり、音は鳴るので
気づけない。`voicevox.test.ts` の「末尾の間は作り置きと合成し直しで一致する」が両者の一致を
固定している。

### 鳴らす直前の見直し

呼び出し側は「鳴らしてよいかの判定」（`shouldStillPlay`）を渡せる。**チャンクを鳴らす直前**に呼び、
外れていればそのチャンク以降を鳴らさない。**鳴っている途中のチャンクは最後まで鳴らす**
（語の途中で切ると聞き取りを壊すため）。

必要なのは、文面を作った時刻と音が出る時刻がずれるから。合成の往復を待つ間にも、鳴らしている
間にも新しい電文は届く。判定は 2 か所で行う。

| 判定する場所 | 捉えるもの |
|---|---|
| チャンクを予約する直前 | 合成の往復を待つ間に古くなった場合 |
| 鳴り始めの直前（`PRE_START_CHECK_LEAD_SEC` = 0.05 秒前） | 鳴らしている間に古くなった場合 |

2 段にしているのは、チャンクを**前のチャンクの終わりに合わせて先に予約する**ため（切れ目を作らない
ための設計）。予約した時点だけで判定すると 1 チャンク分先の未来を判定することになる。

**判定そのものが失敗したときは鳴らす側に倒す**（記録は残す）。黙る判断を例外に委ねると、
緊急地震速報が無音のまま消える方に転ぶため。

渡しているのは EEW の読み上げだけで、見るものはフェーズで違う（→ §6。第 1 フェーズは誤報取消のみ、
第 2 フェーズは誤報取消と値の引き上げ）。渡さなければ従来どおり全チャンクを鳴らす。

**語の途中でも止まる経路が別にある。** 予報から警報への言い直しは `stopSpeech()` で鳴っている音を
直接止める（→ §6「予報から警報へ上がったとき」）。この判定はチャンクの切れ目でしか働かないため、
区分の格上げのように待てないものには使えない。

### セッション管理

- モジュール変数 `activeSources: AudioBufferSourceNode[]` と `currentSessionId: number`
- `speakWithVoicevox(text)` を呼ぶたびに既存の再生を全 stop() し、`currentSessionId++` で新セッションに切替
- 同時に旧セッションの `AbortController` を abort し、進行中の合成リクエスト
  （`/audio_query`・`/synthesis`・`/accent_phrases`）も打ち切る。セッション ID だけでは
  in-flight のリクエストが完走して VOICEVOX の処理を占有し、新しい発話が待たされるため
- **単一グローバルセッション**なので、EEW / 地震 / 津波 / LPGM の全読み上げがこの単一セッションを共有する。
  つまり後から来た読み上げが再生中のものを打ち切る。**どれが打ち切ってよいかは優先度で決めている**
  （§6「読み上げの優先順位」）
- **先行合成（`prewarmVoicevox`）はこのセッションに関与しない**（詳細は
  §6「間を合成の時間に充てる（先行合成）」）

### 辞書（読み仮名の補正）

`src/utils/ttsPhraseBreakDict.ts` + `public/data/tts-phrase-break-dict.json` に地名・専門用語の
読み仮名エントリを持ち、`findPhraseBreakMatch` で該当箇所のアクセント句をキャッシュ済みのものと差し替える。

辞書はアプリ起動時に先読みする。読み上げ開始時にまだ取得できていなければ待つが、その待ちは
**5 秒**で打ち切る。生成データ共通の取得タイムアウト（[`data-sources-spec.md`](data-sources-spec.md) §6）
より大幅に短くしているのは、ここでの待ち時間がそのまま緊急地震速報の読み上げの遅れになるため。
辞書が無くても句区切りが効かないだけで読み上げ自体は成立する。

該当した地名の直後には短い間（`DICT_TRAILING_PAUSE` = 0.12 秒）を挟む。切れ目に間があると
「区切って言い直した」ように聞こえて自然なため。「大津波」「深発地震」のような一般用語
（辞書の `_terms`）は文中に溶け込む語なので対象外。**チャンク末尾の間（`CHUNK_BREAK_PAUSE`）と
値が近いが別物**で、あちらは「境界に元からある無音への足し分」、こちらは「間の全量」を表す。
辞書地名がチャンク末尾に来た場合は二重にせず、句読点ぶんの間に置き換える
（後続のチャンクがあるときだけ。発話の最後の語が辞書地名なら 0.12 秒がそのまま残る）。

#### 何を収録するか

収録するのは**誤読するものだけ**。標準的な漢字読みの地名は入れない（該当した語は前後と別々に
合成して繋ぎ直すため、エントリを増やすほどその経路と間の挿入が増える）。

正しい読みは気象庁防災情報XMLの個別コード表が持つふりがなを正解として使う
（[技術資料](https://xml.kishou.go.jp/tec_material.html) の「個別コード表」）。ふりがなが付いているのは
区域と観測点の類（一次細分区域・津波予報区・潮位観測点・震度観測点・長周期観測点など）で、
**震央地名と都道府県には付いていない**。その 2 つは読みを別に当たることになる。

**誤読は後ろに続く文字で反転する。** 単体で読ませて正しくても実運用で崩れることがあり、逆もある。
「長崎県西方」は「〜に津波注意報」なら「せいほう」と読むのに、読点で終わると「にしほう」になる。
「宮古」は読点なら正しく、「〜で10センチ」で「みやふる」になる。確かめるときは、読み上げ文が実際に
作る形（名前＋読点／名前＋「で」＋波高／名前＋「を震源とする」）で読ませること。

**1 件の報告はたいてい一族の一部**なので、報告された名前だけを直して終わらせない。全名称を突き合わせる
段取り（正解の出どころ・読ませる文脈・正規化・エントリの書き方）は
[`/tts-reading-audit` スキル](../../.claude/skills/tts-reading-audit/SKILL.md) に置いてある。

#### 単独語キー

辞書のキーは既定で部分一致するため、短いキーはより長い地名の一部にも当たる。そのままでは
**VOICEVOX が正しく読める長い地名を語中で切ってしまう**。津波予報区の「佐渡」がその例で、単独だと
「さわたり」と誤読されるのに、「新潟県佐渡」「佐渡市小木」は正しく読まれる。

そこで辞書の `_standalone` に列挙したキー（以下「単独語キー」）は、前後が漢字（と地名中で漢字を繋ぐ
「々〆〇ヶヵ」）でない位置に現れたときだけ一致させる。ひらがな・カタカナを境界として扱うのは、
読み上げ文では予報区名に助詞が直に付くため（「佐渡に津波注意報」「佐渡で10センチ」）。
長い側に専用エントリを置いて避ける手もある（「三宅島」に対する「三宅島阿古」）。

短いキーを単独語キーにするかは、**その語を含む長い地名を VOICEVOX が正しく読むか**で決まる（単体と複合を
それぞれ読ませて比べる）。正しく読むなら単独語キーにして切らない（「佐渡市小木」「呉市」はそのままで正しい）。
誤読するなら部分一致のままにしておく方が、切った結果として読みが救われる（「三角町」は「サンカクマチ」と
誤読されるので、「三角」を部分一致で拾って「ミスミ」と「マチ」に分ける方がまだ近い）。
2026-08-21 の棚卸しでは「呉」「竜飛」が単独語キー化の候補になったが、読み上げに出る名前を切っている実例が
無いため据え置いた。2026-08-22 には「宮古」「鳥羽」を単独語キーにした。どちらも単独では正しく読むのに
後ろに「で」が付くと崩れる側で（上記「何を収録するか」）、部分一致のままにすると専用エントリを持つ
「宮古島平良」や震度観測点名（「宮古市田老」「鳥羽市鳥羽」）を語中で切ってしまう。

単独語キーを増やすときは、**その語の直前に、区切り文字を挟まず別の辞書キーが並ぶ形が無いか**も確かめること
（この形だけ境界を判定できない。理由は `indexOfStandalone` のコメントを参照）。現状は読み上げ文が地名を
必ず読点で繋いでいるため起きていない。

#### 繋ぎ目の引き直し

上記のとおり辞書該当語は前後と別々に VOICEVOX へ渡して繋ぎ合わせている（`buildAccentPhrases`）。
この渡し方だと前半が独立した 1 文として扱われ、その末尾（「震度5弱を」のように助詞で終わることが
多い）が文末と解釈される。結果として **母音がおよそ 2 倍に伸び、音高も下がりきる**。地名の直前の
助詞が間延びして聞こえたり、言い切ってから地名を言い直したように聞こえたりする原因。

そのため繋ぎ合わせた後に `POST /mora_data` へ通し、全体の文脈で長さと音高を引き直す
（`refineProsody`）。音高はアクセント句の `accent`（アクセント核＝音高が下がる位置）を手がかりに
引き直されるため、辞書がカナ表記で指定した読みとアクセント核は保たれる。

ただし `DICT_TRAILING_PAUSE` も引き直しの対象になり、読点相当の長さまで伸ばされてしまう。
そのため句と句の間（`pause_mora`）は**原則まとめて元の値へ戻す**。例外は次項の「分割で落ちた
句読点」の位置だけで、そこは引き直された値こそが欲しい値になる。
引き直しに失敗した場合は繋ぎ目が不自然なまま読み上げるだけで、読み上げ自体は止まらない
（失敗は `log.debug` に残る。ただし割り込みによる中断は記録しない）。実測値は `refineProsody` の
コメントに残してある。

#### 分割で落ちた句読点を戻す

前後を別々に渡す以上、**切れ目に来た句読点も音にならない。** チャンク末尾と同じ理屈が、チャンクの
内側の切れ目にも当てはまる。読点で並べた名前の途中に辞書該当語があると、その手前（または直後）の
読点が消え、**名前が間なしで一続きに聞こえる**。地名でも一般用語でも同じで、辞書該当語の種類は
問わない。

そこで落ちた位置に種となる間（`SPLIT_PUNCT_PAUSE`）を置き、**長さは引き直しに決めてもらう**。
`POST /mora_data` は「間が置かれていない位置に間を作る」ことはしないが、**何か置いてあれば文脈から
正しい長さへ引き直す**（種の値が何であっても、分割しなかった場合と同じ長さになる）。種の値自体は
引き直しに失敗したときの受け皿にすぎず、文中の読点として不自然にならない範囲でやや短めを選んでいる
（受け皿が長すぎると、引き直しに失敗した回だけ間が伸びて次のチャンクを待たせる）。

置かない位置が 2 つある。

- **チャンクの末尾**。そこは `CHUNK_BREAK_PAUSE` の担当。ここで引き直しに任せると、最後のチャンクで
  読み終わりに長い無音が残り、再生の完了を待っている次の読み上げが遅れる
- **掛ける先の句が無いとき**（切れ目の手前から句が 1 つも返らなかった場合）。ただしこれは
  再帰の内側では起こらない ―― その位置は外側の呼び出しが既に処理している。残るのは
  **チャンク自体が句読点で始まる**場合だけで、それには読み上げ文に句読点が連続している必要がある。
  テストデータと実シナリオの読み上げ文を機械的に走査した限り、連続句読点は生じていない

置いた後にも歯止めが 1 つある。**種が句の並びの末尾に来た場合は、引き直された値を採らず種のまま残す。**
そこはチャンク末尾と同じ位置なので、引き直しに任せると長い無音が残る。種が末尾に来るのは切れ目の
後ろから句が 1 つも返らなかったときだけで通常は起こらないが、起きたときに黙って読み終わりを
伸ばさないための備え。

チャンク末尾の間（`CHUNK_BREAK_PAUSE`）とは**別の穴**であることに注意。あちらを直しても、
辞書該当語を含むチャンクの内側はこちらが直るまで間が消えたままだった。**同じ症状（読点で並べた
名前が一続きに聞こえる）に原因が 2 つある**ので、再発したときはどちらかを決めてから直すこと。

### 話速

現状 `synthesizeChunk` 内で `query.speedScale = 1.2` を無条件に上書き（ユーザー設定なし）。

### 既知の課題

- 通常チャンクの音声合成に一切キャッシュがない（定型句「緊急地震速報。」等も毎回合成）
- 音声合成そのものの失敗パス（`synthesizeChunk` の `catch`）と `/accent_phrases` の取得失敗に
  ログがなく原因追跡ができない（辞書の取得失敗と `/mora_data` の引き直し失敗は `log.debug` に残る）

## 4. 読み上げテキスト生成（`ttsText`）

`src/utils/ttsText.ts`。イベント種別に応じた読み上げ文を生成する。

### 主要関数

- `eewAlertToText(eew, kind)` — EEW の切り出し。`kind` は `forecast`（「地震動予報、〇〇で地震。」）／`warning`（「緊急地震速報、〇〇で地震。」）／`hypocenterUpdate`（「震源を更新、〇〇で地震。」）
- `eewIntensityToText(eew, announceUpgrade)` — EEW の予想値（予想最大震度・予想最大階級）。`announceUpgrade` が真のとき「緊急地震速報に切り替わりました。」を前置きする（真にするのは予報→警報の格上げだけ。→ §6）
- `earthquakeToText(quake, opts, isNew)` — 地震情報（`isNew:false` で更新報の言い回しになる）
- `tsunamiToText(tsunami)` / `tsunamiCancelToText(cancelReason)` — 津波。**区域や観測点を挙げる
  読み上げには、対になる「断片列」を返す関数がある**（`tsunamiToSegments` /
  `tsunamiDowngradeToSegments` / `tsunamiObservationUpdateToSegments` / `tsunamiArrivalToSegments`）。
  カードを読み上げに追従させるのに「どの語がどの区域・観測点を指すか」が必要なため
  （→ 後述「読み上げに合わせたカードの追従」）。文字列版は断片列を連結しただけで文面は同じ。
  `tsunamiCancelToText` は区域名を含まない定型文なので断片列版を持たない（追従も働かない）
- `lpgmToText(...)` — 長周期地震動
- `nankaiToText(...)` / `kohatsuToText(...)` — 南海トラフ臨時情報・後発地震
- `nankaiCommentaryToText(...)` — 南海トラフ関連解説情報。**本文は読まない**（1000 字を超えることが
  あるため）。種別（臨時解説／定例解説）と号数までを伝え、詳細は画面のバナーに委ねる

### 特殊な扱い

- **予想震度が出ない理由**: `eewNoForecastReason` が 3 通りに分ける（仮定震源要素＝単独点処理／
  深さ 150km 超の深発地震／それ以外）。**読み上げる文言と、値の確定を待つかどうかの判断が
  同じ判定を使う。** 前 2 つはその報に予想震度が載らないと判っているので待たない（→ §6）。
  待つ意味があるのは 3 つめだけ
- **仮定震源要素**: 上記のうち単独点処理のケース。震度に加えて長周期階級も句ごと省く。単独点処理では
  地域別予想が発表されないため、`eewMaxScale` / `eewMaxLpgmClass` がともに 0 を返すことによる。
  なお M・深さを隠すのはカード表示・地図マーカー側の扱いで、EEW の読み上げは元から M・深さに
  触れない（[eew-spec.md](eew-spec.md) §5）
- **震源深さ不明**: 深さ不明（負値）では**深さ句ごと省く**。`0` のみ「ごく浅い場所」と読む
- **マグニチュード不明**: 規模不明（`NaN`＝DMDATA 経路／負値＝P2PQuake 経路）ではマグニチュード句ごと省く
- 深さ・マグニチュードの判定は `formatters.ts` の共有関数 `hasDepth` / `hasMagnitude` で行う。カード表示
  （`formatDepth` / `formatMagnitude`）・色付け（`getDepthColor` / `getMagnitudeColor`）も同じ関数を使うため、
  カードが「不明」と出すものを読み上げが「ごく浅い」「M0.0」と言うような食い違いは起きない
- **地域列挙の助詞**: 階級ごとに地域を並べるとき、場所の助詞「で」は文末（述語の直前）にのみ置く。
  句ごとに付けると一文字の助詞が読点に挟まれ、読み上げが途切れて聞こえる（震度・長周期地震動階級で共通）
- **地域名・地点名の区切り**: 名前を並べるときは読点「、」で繋ぐ。中黒「・」は VOICEVOX が音にせず、
  句読点と違って合成の区切り（§3「API 呼び出し」）にもならないため、並べた名前が一続きに聞こえる
  （例:「山形県新潟県上中下越」）。**ただし読点にすれば間が入るのは、切れ目に来た句読点に間を
  補っているから。** VOICEVOX は後ろに何も続かない句読点に間を付けないため、**読点を書いただけでは
  間が入らない切れ目が 2 種類ある**。チャンクの末尾（§3「チャンク末尾の句読点には間を足す」）と、
  辞書該当語の前後で分割した切れ目（§3「分割で落ちた句読点を戻す」）で、いずれも後から補った措置。
  補う前は辞書に載っている地名の直後だけ短い間が入り（§3「辞書（読み仮名の補正）」）、載っていない
  区域名では入らないため、名前の並びが不均一に聞こえていた。
  なお津波予報区名には「伊勢・三河湾」のように**名前自体に中黒を含むものがある**
  （`tsunami-zones.json` に 9 件）。連結にも中黒を使うと、名前の一部か区切りかが区別できなくなる。
  この読点への統一により、津波の観測・到達情報で予報区名と地点名がすべて同じ読点で並ぶ
  （「佐渡、佐渡市鷲崎、小木、…」）。**どこまでが予報区でどこからが地点かは音声では区別されない**が、
  中黒では地点名同士が一続きに潰れて個々の地名すら聞き取れなかったため、こちらを採っている
- **同じ種別を 2 度目に見たとき**: 冒頭を「震度速報が更新されました。」のように言い換える。判定の
  キーは「地震を指すキー」と情報種別の組で、前者は DMDATA 経路が `eventId`、P2PQuake 経路は発生時刻＋
  震源名（`eventId` が配信されないため。[quake-spec.md](quake-spec.md) §6.1 の同一性判定と同じ事情）。
  **見た報は全部覚えること。** 直近 1 件だけ覚えていると、種別の違う報が交互に届いたときに互いの
  記憶を上書きし、2 度目の震度速報が初報のように聞こえる。種別が違えば別の報なので、震度速報の
  あとの震源情報は「震源情報。」と名乗る。記憶には 200 件の上限があり、超えると全部捨てる
  （到達しやすいのはアーカイブ再生の復元。捨てた直後の続報は初報の言い方に戻る）
- **遠地地震**: 「遠地地震に関する情報。」と名乗り、**日付から読み上げる**（発表が発生の数十分後になり日付をまたぐため）。
  津波の一文は**固定**付加文の原文（`JMAQuake.forecastText`）を優先し、無い経路では津波区分から起こす
  （付加文コードの詳細は [quake-spec.md](quake-spec.md) §3）。
  **自由付加文（`freeText`）は読み上げない。** 検潮所ごとの波高が全角スペース整形の表で入ることがあり、
  音声にできる形へ安全に切り出す規則が作れないため。画面（地震カードの詳細表示）だけに出す。
  この結果、固定付加文が変わらない続報では**画面は更新されるのに声は同じ文言になる**

### 続報は差分だけ読む

地震情報は続報のたびに観測地域が増える。**読むのは増えたところだけ**で、既に声にした地名は
繰り返さない。

> 以下の字数は 2024/1/1 能登のテストシナリオ（`public/data/test-scenarios/`）の地震電文 14 通を
> 既定の設定で読み上げ文にして数えた**概算**。変更前は合計 2,525 字で、うち 5 報はほぼ同じ
> 240 字（読み上げで 30〜40 秒）だった。最大震度が 7 に上がった報でさえ、冒頭でそれを告げた
> あと 200 字ぶん既知の地名が続いていた。シナリオは配信規約により Git 管理外のため
> （[settings-pwa-spec.md](settings-pwa-spec.md) §6）、手元にシナリオが無い環境では再現できない。

- 読むのは**初めて挙げる区域**と、**前に伝えた震度より上がった区域**。据え置き・引き下げは読まない
- **この 2 つは群に分け、上がった分を先に読む。**「新たに」は初めて挙げる区域にだけ掛かる言葉で、
  震度が上がった区域は初めて揺れた場所ではない。1 文に混ぜると、同じ階級に両方が並んだときに
  誤った説明になる（震度4の句に「新たに山形県村山、栃木県北部」と並べると、3→4 に上がった
  栃木も初出に見える）。境目に「また、」を置くと、そこで話が切り替わることが耳に伝わる

  ```
  両方ある:   〜が更新されました。最大震度7を石川県能登、震度4を栃木県北部で観測しました。
                                  また、新たに震度4を山形県村山、…で観測しました。
  上がりだけ: 〜が更新されました。最大震度7を石川県能登で観測しました。
  初出だけ:   〜が更新されました。新たに震度4を山形県村山、…で観測しました。
  ```

  - 上がった分を先に読むのは、**そちらが重い報せ**だから（状況が前の報より悪いということ）
  - 「また、」は前の群があるときだけ付く
  - **「最大」は上がりの群にだけ冠する。** 初出の群では「新たに最大震度7を」となって据わりが悪く、
    最大震度は地震全体の値なので「新たに」と並べる語ではない
  - 地域数の上限（`ttsMaxRegions`）は**群ごとに数える**。混在する報では上限の 2 倍まで伸びうるが、
    上がった区域は数件に収まることが多いと見込んでいる（実測で確かめた性質ではない）
  - **群分けと「新たに」は差分のときだけ。** 初報・別の地震・確定情報の通し読みは 1 群のまま読む
    （比べる相手がいないので「新たに」に意味が無い）。判定は記録の有無ではなく**区域を一度でも
    声にしたか**で行う ―― 記録は地震の初報でも空の状態で渡ってくるので、有無で見ると初報から
    「新たに」が付く
  - **既知の限界**: 初出か上がりかは**地域名の文字列**で引く。県内の区域が同じ階級で揃うと名前が
    「〇〇県」へまとまるため（`aggregateAreaNamesByPref`）、区域名で伝えた地震が続報で県名へ
    まとまると、記録を引けず「新たに」と読む。伝える内容（県と震度）は正しく、語の精度だけの
    問題なので直していない
- 震源要素（震源名・深さ・マグニチュード）と津波区分も、続報では**変わったものだけ**言い直す
  （「マグニチュードは7.6に更新されました。」）。震度に変化が無くても規模の更新は読む
- 変化が何も無ければ**名乗りだけを読む**（「震度速報が更新されました。」で終わる）。黙ると
  「電文が来たのに何も起きなかった」ようにしか聞こえない。内容が続かないことで、変化が
  無かったことが対比で伝わる。
  この結果、地震情報の読み上げ文は**常に非空**になる。タブの移動は読み上げ追従が担い、
  受信時要求へ落ちるのは読み上げが無効な端末だけ（→ §6）
- 記録は地震ごとに持ち、**情報種別を跨いで共有する**。震度速報で読んだ区域を震源・震度情報で
  読み直さない。前項の「同じ種別を 2 度目に見たとき」とはキーが別で、こちらは種別を含めない
- ただし**省き方は区域と震源要素で違う**。区域は種別を跨いで省くが、震源要素・津波区分は
  その種別で初めて名乗る報では通しで言う（「地震情報。〇時〇分頃、…」の形）。種別が変わる
  最初の 1 回だけ震源が読み直されるのはこのため。値の差分になるのは同じ種別の続報から
- **その地震で最初の確定情報だけは、地域も通しで読む。** 確定情報＝震源も震度も伴う電文
  （震源・震度情報／各地の震度情報）。震度速報は区域だけの速報なので、この 2 種が届いて初めて
  観測が確定した形で揃う。速報を細切れに聞いた耳へ、**確定した観測を 1 度だけまとめて示す**。
  震源要素が「その種別の初報では通しで言う」のと規則が揃う（従来は同じ報の中で震源要素は通し・
  地域は差分と割れていた）
  - **2 通目以降は差分に戻す。** 「種別ごとに 1 回」にすると、確定情報が 2 種類届く経路で
    全区域を 2 度聞くことになる
  - この記録（`authoritativeReadQuakesRef`）は**受信した時点**で進める。区域の既読（声になった
    分だけ）とは基準が違うが、通し読みが割り込みで鳴らなければその区域は既読にならず、次の報が
    差分として読み直すので情報は落ちない
- 「ほか N 地域」で省いた区域は読んでいないので記録しない。次の報で読まれる
- **震度速報を震源要素・津波区分の比較に使わない。** この電文は震源も津波区分も伝えず、値は
  センチネル（震源座標 -200・深さ -1）と「調査中」が入る。素直に比べると、震源情報で伝えた
  「津波の心配はありません」から変化したと誤検出し、続報のたびに「調査中です」と言い出す
- 「最大」を冠せるのは、その階級が**その報の最大震度と一致するとき**だけ。差分では最大震度の
  区域が据え置きで落ちることがあり、先頭の句に無条件で付けると電文が伝えていない最大震度を語る
- **まだ一度も声にしていない震源要素が残っている続報は、差分にせず初報と同じ形で言い直す。**
  未記録の理由は「初報の時点では値が不明だった」（深さ・規模は後の報で確定する）か、
  「初報の該当箇所が鳴らなかった」のどちらかで、**どちらも「更新されました」と言うのは誤り**。
  未記録を「変化なし」として省くと、その要素はその地震の続報が続く限り二度と声にならない
- ただし**待ってよいのは「声にしうる事実」だけ**。深さは震源名の句の中でしか読まれないため
  （「〇〇、深さ10キロメートルを震源とする」）、震源名が空の電文では深さが判っていても声に
  ならない。読む条件と待つ条件は同じ述語で判定すること ―― 食い違うと、記録される機会の無い
  事実を待ち続け、**その地震だけ永久に全文読みへ戻る**（差分が静かに効かなくなる）
- 階級の打ち切り（階数・下限震度）は**差分を取る前の観測**で数える。差分後の並びで数えると、
  上位の階級が据え置きだった続報で下位が繰り上がり、普段は読まない震度まで読み始める

> 差分は**遠地地震と「顕著な地震の震源要素更新のお知らせ」には効かない**。前者は付加文が本文の
> 主体で値の比較が意味を持たず、後者は「更新されたこと」自体が電文の主旨のため。どちらも稀で、
> 続報も数報にとどまる。**ただし声にした値は記録には残る**（記録しないと、後続の地震情報が
> 同じ値をもう一度「更新されました」と言い直す）。

#### 既読になるのは「声になった分」だけ

**基準は受信した内容ではなく、実際に鳴った内容。** 読み上げは割り込まれる（新しい読み上げが
始まると進行中の再生は止まる。→ §3「セッション管理」）。文を作った時点で既読にすると、
割り込みで鳴らなかった地域が**二度と読まれない**。能登の実データには、地震情報の読み上げ中に
EEW 警報が 14 通届いた報がある。割り込みは例外ではない。

判定はチャンク単位で行う。合成は再生より先へ進むので、**予約が通ったことは鳴ったことを
意味しない**（長い文では全チャンクの予約が済んだ数秒後まで、音はまだ序盤を鳴らしている）。
読み上げが終わった時点の再生時計と、各チャンクの再生開始時刻を突き合わせる。

- **鳴り始めた最後のチャンクは数えない**（最後まで鳴った場合を除く）。途中で切られた可能性が
  あり、区域名を言い終えたか判らない。数えない代償は「次の続報で 1 地域を読み直す」だけだが、
  数えてしまうとその地域は二度と読まれない
- 1 チャンクも鳴らなかったとき（合成が全滅・VOICEVOX 未起動・鳴り出す前の割り込み）は何も
  記録しない。続報は全文を読む。**失敗は「冗長に読む」側へ倒す**
- 記録は 100 地震まで。溢れたら全部捨てる（捨てた地震の続報が全文で読まれるだけ）。
  リプレイの開始・切替でも捨てる
- **読んでいる最中に届いた続報は、まだ書き戻されていない記録を見て文を組む**（記録の更新は
  読み上げの完了時のため）。重なった分は次の報で読み直しになる。ここも冗長に倒れる側
- 記録を引くキーは地震の同一性キー（[quake-spec.md](quake-spec.md) §6.1）。P2PQuake 経路で
  統合済みカードを引けなかった報はキーが変わりうるが、その場合も全文を読むだけで情報は落ちない

> EEW の既読値（→ §6）は「送り出した値」で足りている。読み上げ文が毎回**最新値から作り直される**
> （差分を語らない）ため、鳴らずに終わった値があっても次の報が読み直すから。**地震情報は差分を
> 語るので、この逃げ場が無い。** 同じ粗さを持ち込むと地名が落ちる。

### 地域名の粒度

挙げるのは**一次細分区域**（「石川県能登」「新潟県上越」など）。電文が区域を持たない経路では、
**観測点の所属区域を座標テーブル（`station-coords.json`）から逆引きする**。地図の区域塗りと同じ
関数（`lookupStationRegion`）で引くので、読み上げと地図が同じ区域を指す。

- 県内の区域が割れていなければ「〇〇県」1 件にまとめる。全区域の名前を読むより短く、位置も伝わる
  - **ただし上位の階級で区域名を出した県はまとめない。** まとめ判定は階級ごとに独立して走るので、
    上と下で粒度が食い違うと県の震度を過小に伝える。例: 震度5強で「福井県嶺北」を出したあと、
    震度4 で嶺北・嶺南が揃って「福井県」とまとめると、福井県は震度5強なのに 4 に聞こえる。
    長周期地震動の階級でも同じ扱い
  - 区域名と県名の見分けは**区域名の索引で引けるかどうか**に頼るので、多区域の県が県名と同じ表記の
    区域を持たないことが前提。奈良県だけは県名と同名の区域を持つが単一区域なので、どちらに数えても
    出力は変わらない（この前提は `stationCoords.test.ts` が検証する）
  - 数えるのは**続報で差分に落とす前**の区域（下の「続報は差分だけ読む」の打ち切りと同じ考え方で、
    実装も同じループで数えている）。落とした後で数えると、既出の区域が「今回は声にならない」ために
    県の全区域が揃って見え、続報でだけ同じ過小伝達が起きる。**差分の仕組みを持つのは地震の経路だけ**で、
    長周期は続報でも毎回すべての区域を読み直すためこの心配は無い
  - 上位に区域を出した県はその後ずっと分解されるので、下位の階級ほど地域名が増える。ただし
    読み上げの長さは次項の上限が先に効くのでほぼ変わらず、増えた分は「ほか N 地域」に吸収される
- **標準版（P2PQuake）の詳細報は区域の点を持たない**（観測点の電文と区域速報の電文が別々に届く
  API 仕様のため。→ [quake-spec.md](quake-spec.md) §4）。この経路が逆引きの主な対象
- 区域が引けない観測点（座標テーブルに無い新設観測点など）は都道府県名で読む。ただし同じ県で
  区域が 1 つでも引けていれば県名は捨てる（「〇〇県北部」と「〇〇県」が並ぶのを避ける）
- **区域の点がある電文では都道府県ロールアップ点**（DMDATA の JSON 経路が積む県別最大震度）**を
  見ない。** 電文が示した区域をそのまま使う。観測点から逆引きした経路でだけ、観測点を 1 つも
  持たない県をロールアップ点から拾う（拾わないとその県が読み上げから消える）
- 座標テーブルが**旧形式**（区域の一覧を持たない古い `station-coords.json`）だと区域を引けず、
  読み上げは全面的に都道府県粒度へ戻る。読み込んだ時点で `[stationCoords]` の警告が出る。
  配信を更新した直後、PWA が古いデータをキャッシュしたまま新しいバンドルを動かすと起きうる
- **地域名を 1 件も作れなかったときは最大震度だけを伝える**（「最大震度4を観測しました。」）。
  震度も判っていなければ何も足さない — 震度の値が欠けた文にしない。地震情報と震度速報で
  同じ一文を使う（`maxScaleOnlySentence`）。地域が丸ごと消えたことは `[tts]` の警告に残す
  （間引いて出す）
  - **続報でも伝える。ただし言い直しはしない。** 伝えた震度を `maxScaleOnly` として覚え、
    同じ震度なら黙り、震度が変われば読み直す（前項「続報は差分だけ読む」と同じ考え方）。
    観測点が座標テーブルで解決できない状態はその地震の続報でも続くので、初報の 1 回で
    打ち切ると以降の震度が伝わらない
  - **区域を一度でも読めた地震では使わない。** 判定は「区域の既読が空か」で行う（その報で
    区域を挙げられたかではない）。後者で判定すると、区域を読めている地震の据え置きの続報でも
    最大震度を言い直す
- 実装は `ttsText.ts` の `regionNamesForScale`。区域は**都道府県名と観測点名の組**で引くので、
  同名の観測点が別の県にあっても取り違えない。`pref` が空で届く経路（DMDATA）は観測点名から
  都道府県を先に補ってから引く。この補完（`buildStationPrefIndex`）は初出優先なので、同名の
  観測点が複数の県にあれば誤った県を返しうる（現在の配信データに同名は無く、その前提は
  `stationCoords.test.ts` が検証する）

> **区域粒度は県粒度より地域数が増える。** 次項の上限に届きやすくなり「ほか N 地域」への圧縮が
> 起きる場面が増える（上限を超えたときにどれを残すかは次項）。

### 地域列挙の範囲

どの階級まで・各階級で何地域まで読むかは、設定タブの 4 項目で決まる
（項目名と既定値は [settings-pwa-spec.md](settings-pwa-spec.md) §2「主な項目の補足」）。
実装では `ttsText.ts` の `TtsRegionOptions`（`intensityLevels` / `alwaysReadScale` /
`maxRegions` / `regionTolerance`）としてこの 4 項目を受け取る。

- 読む階級は「階数の範囲内」**または**「必ず読み上げる震度以上」を満たすもの
- 階数は**最大震度に加えて何階級下まで読むか**。`0` なら最大震度のみ、既定の `2` なら最大を含めて計 3 階級
- 階数で数えるのは**観測がある階級だけ**。観測 0 地域の階級は飛ばして次を数える
  （例: 階数 1 で 5 強・5 弱の観測が無ければ、6 弱 の次に読むのは 震度 4）。長周期地震動階級も同じ数え方
- 1 階級あたりの地域名は上限まで読む。ただし上限をわずかに超えるだけなら（許容超過の範囲内）省略せず
  全地域を読む。超えた場合は上限ちょうどで切り「ほか N 地域」と件数で伝える
- 上位の階級で読んだ地域名は、下位の階級では繰り返さない
- 「必ず読み上げる震度」は震度にのみ効く。長周期地震動階級（1〜4）は震度と別軸のため対象外

### 地域名の並び順

読み上げる地域名は**気象庁の標準順**（北から南。同じ県の区域が隣り合う）に並べる。震源からの距離順だと
同じ県の同じ震度でも間に他県が挟まり、聞いて位置を掴みにくいため。県内の区域も気象庁の並びに従い、
代表点の緯度では並べない（例: 新潟県は緯度と逆に 上越 → 中越 → 下越）。

- 順序の実体は座標テーブル（`station-coords.json`）の区域キー順で、生成元の気象庁 震度観測点一覧表の
  並びをそのまま引き継いでいる。索引の構築は `stationCoords.ts` の `buildRegionOrderIndex`、
  並べ替えは `ttsText.ts` の `sortByRegionOrder`
- 索引に無い地域名（震度観測点を持たない区域）は末尾へ回す。区域の一覧（`subregions.json`）でも
  これらは末尾（沖縄県の後の北方領土・埋立地）に置かれるため、標準順と矛盾しない。座標テーブルが
  未読み込みのときは並べ替えない
- **上限で切るときに残す地域は震源に近い順で選ぶ**。「どれを読むか」（選抜）と「どの順で読むか」を
  分けているのは、地理順のまま先頭から切ると震源から遠い北側の地域が枠を占め、震源直近が
  「ほか N 地域」に潰されうるため
- **震源を持たない電文では距離で選べないので、地理順に整えてから切る**（座標テーブルが読み込めて
  いれば＝北から上限まで）。震度速報がこれにあたり、震源の緯度経度には位置不明センチネル `-200` が
  入る。0 だけを「震源なし」とみなすと、この電文で地球上に無い点からの距離を測ることになる
- 長周期地震動も同じ並び。こちらは電文に震源座標が無いため、選抜は常に電文の順序のまま

この節の挙動（震源の有無による選抜の切り替え・県内の並び・上限で切ったときの並び）は
`ttsRegionOrder.test.ts` が実配信データで検証する。順序の元になる「県ごとに連続している」
「北海道から沖縄県まで通る」という座標テーブル側の前提は `stationCoords.test.ts` が受け持つ。

> **ここまでは地震情報・長周期地震動の話。** 並び順の根拠が震度観測点の並びなので、震度観測点を
> 持たない津波予報区には適用されない（索引に無い）。津波は次項の規則で並べる。

### 津波の区域の並び順

**カードの表示順に揃える**（`tsunami.ts` の `sortAreasForCardDisplay`）。カードは同じ予想波高の
グループ内を実測波高の降順に並べ替えるため、電文順（気象庁の地理順・北から南）のままにすると、
**観測が入り始めた続報で読み上げ順とカードの並びが乖離する**。津波は震源に近い区域から到達する
ので、震源が南寄りなら電文順で後ろの区域に先に実測が入り、カードでは繰り上がる。

揃えないと、読み上げに追従するスクロールが 1 チャンクごとに上下へ往復する（後述「読み上げに
合わせたカードの追従」）。地震情報とは逆に地理順を捨てているが、津波は区域数が地震の地域数より
少なく、かつ「どこに実測が出ているか」が行動に直結するため、観測の順で読む方が情報として妥当。

- 並べ替えの単位は**同じ予想波高のグループの中だけ**。グループの境界は電文順で決まる（`groupAreasByHeight`）
- **予想最大波高の文（「予想最大波高は、〇〇で 3 メートル、…」）もカードの波高見出しと同じ区切りで読む。**
  波高の文字列だけをキーにまとめると、間に別の波高の区域が挟まっていても飛び越えて 1 つの句に
  してしまい、カードの見出し分割と食い違う。追従がその間の行を跨いだ範囲を対象にし、読んでいる
  区域が画面外に残る
- 検証は `ttsText.test.ts`（観測が入ると順序が変わること・非隣接の同じ波高を分けること）と
  `tsunami.test.ts`（並べ替えそのもの）が受け持つ

#### 観測点は「選抜」と「並び」を分ける

観測情報の読み上げ（`tsunamiObservationUpdateToSegments`）は上位 `maxPoints`（5）件だけを読む。
**どれを読むかは波高の深刻な順で選び、どの順で読むかはカードの並びに従う。**

**選抜**にはカードと同じ `compareObservedHeightDesc` を使う（「○m以上」を値の大小より上に置く
規則。→ [`tsunami-spec.md`](tsunami-spec.md) §6「観測波高の「以上」」）。値の大小だけで並べると、
打ち切りに掛かって**「○m以上」の観測点が読み上げから丸ごと落ちる**。カードなら下の方にでも
残るが、音は落ちたことに気づく手段が無い。

**選抜だけでは足りない。** 「○m以上」が上限より多く出れば、そのうちの一部は依然として落ちる
（広域で複数の潮位計が同時に飽和する場面がまさにそれ）。外した地点数は「ほか○地点でも観測して
います。」の形で必ず言う（`omittedPointsSentence`）。**述語に貼り付けず独立した一文にする** ――
下記のとおり新規と更新で述語が変わるため、貼り付けると外した地点が更新扱いになる。地点数の
言い方は到達確認の読み上げ（`tsunamiArrivalToSegments`）と共有する。

**並び**は区域と同じくカードに揃える。読み上げ側は渡された並びをそのまま読む（並べ替えるのは
呼び出し側。並びの定義と、なぜ深刻な順で読んではいけないかは
[`tsunami-spec.md`](tsunami-spec.md) §9「観測点の並び順」）。

到達確認の読み上げも同じ上限で切る（`selectArrivalsToSpeak`）。**既読として記録する側も必ず同じ
関数で絞ること** ―― 上限で読まなかった観測点を既読にすると、その到達確認は二度と読まれない
（波高更新側の `selectObservationUpdatesToSpeak` と同じ約束。→ [`tsunami-spec.md`](tsunami-spec.md)
§10「読み上げた観測点の記憶は画面用と分ける」）。

#### 新規と更新を言い分ける

観測情報の続報では、**津波が新しい場所に届いたのか、既に届いた場所で波が高くなったのか**を
言い分ける。カードも新規＝緑・更新＝黄の左枠で区別しているので、音だけがその情報を落とさない。

```
津波観測情報。岩手県、大船渡で3.0メートルに更新されました。また、新たに岩手県、宮古で1.2メートルを観測しました。
```

- **境界は「前に声にした波高があるか」だけ。** 名前を聞いたことがあるかでは判定しない。到達確認
  だけ読んだ観測点（「最大波高は観測中です」まで言った地点）に初めて値が付いた場合は、波高として
  は初出なので「新たに」側に入る ―― 前値が無いのに「更新」と言えば嘘になる
- 判定に渡すのは**読み上げ用の記憶**（`spokenObsHeightRef`）。受信時に進む画面用の記憶を渡すと、
  割り込みで鳴らなかった観測点を「更新されました」と言う
- 2 群に分かれたら**深刻な波高を含む群を先に読み、後ろを「また、」で継ぐ**。最悪の値を先に伝える
  という選抜の方針を、群に割ったあとも崩さない
- **群に割っても件数上限は合計。** 群ごとに選抜し直すと上限が実質 2 倍になり、既読を記録する側と
  読み上げた集合が食い違う
- 初報は全件が初出なので「新たに…を観測しました。」の 1 文だけになる（「また、」は出ない）

### 区域名は 1 回だけ。等級ごとに「区域と波高」を 1 文で言い切る

```
大津波警報が発表されました。ただちに高台へ避難してください。岩手県、宮城県で10メートル以上、福島県で6メートルが予想されています。
また、次の地域に津波警報が発表されています。青森県太平洋沿岸、茨城県で3メートルが予想されています。
また、次の地域に津波注意報が発表されています。北海道太平洋沿岸東部で1メートルが予想されています。
```

**区域を挙げる文と波高の文を分けない。** 分けると同じ区域名を 2 回読むことになり、予報区が数十に
及ぶ大規模警報では読み上げがほぼ倍に伸びる。これは聞き心地だけの問題ではない ―― 読み上げが長引くと
優先度の低い電文が待ちの上限（`HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS` = 90 秒）に達して割り込み、
**避難行動を含む津波の読み上げが途中で切られる**。追従スクロールの側でも、2 周目は「一度出した箇所」
として追わないため、読み上げているのに画面が動かない時間になっていた。

- **等級と行動を先に言い切る。** 区域を全部読んでから避難を促すと、予報区が多いほど行動指示が遅れる
- **下位等級の波高も読む。** 最上位だけにすると、注意報の区域にいる人へ高さが伝わらない
- **等級をまたいで波高を 1 文にまとめない。** カードは等級ごとに分かれているので、まとめると
  読み上げの句がカードを跨ぎ、追従がその間の行を含んだ範囲を対象にする
- 下位等級はそれぞれ「また、次の地域に」で始める（文の切れ目が耳で分かるように）
- **予想波高が付いていない区域は別の文で挙げる**（「〇〇にも大津波警報が発表されています。」）。
  区域名を波高の文でだけ挙げる作りなので、補わないと発表されている区域を黙って省くことになる。
  数値が来ない電文は実際にある（「巨大」「高い」は DMDATA 経路で `maxHeight` ごと落ちる）ほか、
  警報が先に出て波高が後続報で付くこともある。どの区域にも波高が無ければ、区域名を直接挙げる
  従来の形に落ちる
- **数値で表せない波高（「巨大」「高い」）は語を補う**（`NON_NUMERIC_HEIGHT_PHRASE`）。そのまま
  並べると「岩手県で巨大が予想されています」と崩れる。活用が違うので表記ごとに持つ
- **波高の単位は全角・半角の両方を読み替える**（`tsunamiHeightToSpeech`）。経路によって表記が
  違い（XML 履歴は全角「ｍ」、JSON は半角「m」）、片方だけ変換すると素通りした側が「えむ」と
  読まれる。置き換えるのは**数字の直後だけ**で、大文字の M は対象にしない ―― この関数は電文の
  文章（`headline`）にも通すため、無条件に置き換えると文中の語を壊し（`50cm` など）、数字の直後の
  M はマグニチュード（「M7.6」）を指す

## 5. ウィンドウタイトル（`useAlertTitle`）

`src/hooks/useAlertTitle.ts`。情報更新時にブラウザタブ / ウィンドウのタイトルを書き換える。
AutoHotKey 等の外部監視ツールから状態を検知できる。

### タイトル表

| 状態 | タイトル |
|---|---|
| 平常時 | `リアルタイム地震ビューアー` |
| 地震情報受信 | `地震情報 <震源> 最大震度<N>` |
| 遠地地震受信 | `遠地地震 <震源> M<規模>`（国内震度がないため震度は出さない。規模不明なら省略） |
| EEW 発報 | `緊急地震速報 <震源> 最大震度<N>予想`（**予報級は `地震動予報 …`**。区分の名前は `eewKindLabel` が単一情報源） |
| 津波情報発表 | `津波情報 発表中` |
| 特別情報発表 | `南海トラフ臨時情報（<段階>）`（段階が取れなければ `発表中`）／`後発地震注意情報 発表中` |
| 揺れの候補（未確定） | `揺れの可能性` |
| 揺れ検知 | `揺れ検知` |

> **アップデート待機中のカウントダウンだけは `useAlertTitle` を経由しない。** `App.tsx` が
> `<N>秒後に再起動します — <平常時タイトル>` を直接書く。上の表のタイトルを出している間は
> **カウントダウン自体が進まない**（[`settings-pwa-spec.md`](settings-pwa-spec.md) §5「更新の検知」）。
> カウントダウンの途中で情報が届いた場合は、止まった残り秒数ではなく上の表のタイトルを出す。

> **震度を伝えない電文でタイトルの震度を消さない。** 震源情報（VXSE52）は震度を持たないため、
> そのまま出すと「最大震度不明」に落ちる。同一イベントのカードが既に震度を出しているならタイトルを
> 更新しない。**判定はその報が初報かどうかでは行わない**（種別ごとに初報になるため歯止めが効かない）。
> 既存カードが震度を持たないとき（震源情報が先に届いた・カードがまだ無い）は、出せる情報が他に
> 無いので従来どおり出す。

### タイマー管理

- `earthquake` / `eew` / `tsunami` / `specialInfo` の 4 種類のタイマーを `timersRef` に保持
- デフォルトタブへ復帰する時刻に平常時タイトルへ戻す
- 「自動復帰までの時間」を無効化していれば次の情報更新までタイトルは維持される
- 津波タイトルは既定で「発表が解除されるまで表示」（設定で「一定時間に制限」も可）

## 6. ライブイベント連動（`useLiveEventHandler`）

`src/hooks/useLiveEventHandler.ts`。イベント種別ごとに音・通知・読み上げ・タブ切替・タイトルの発火を
一元的に扱う（約 500 行以上の巨大フック）。

### 発火順序（概念）

各イベントで以下が並行 or 逐次に発火する:

1. 音（`playAlertSound(type)`）
2. ブラウザ通知（`showBrowserNotification(...)`）
3. VOICEVOX 読み上げ（`setTimeout` で遅延投入。通知音と重ならないよう種別ごとに 500〜2800ms）
4. 自動タブ切替（`setActiveTabNonRealtime(tab)` or `setActiveTabRealtimeOnUpdate()`）
5. ウィンドウタイトル変更（`useAlertTitle`）
6. カメラ自動フィット（`FitTo*GL` 経由）

読み上げの遅延は、通知音が鳴り終わってから話し始めるための待ち時間。`TTS_DELAY_MS`
（`useLiveEventHandler.ts`）が種別ごとの値を持つが、**次の 6 種はこのテーブルを通らず
呼び出し箇所に直接書かれている**。

| 種別 | 遅延 |
|---|---|
| 地震情報の取消 | 1200ms |
| EEW 誤報取消 | 1200ms |
| 津波の解除・取消・期限切れ | 1200ms |
| 長周期地震動 | 1000ms |
| 南海トラフ臨時情報・後発地震注意情報 | 1500ms |
| 南海トラフ関連解説情報 | 1500ms（`NANKAI_COMMENTARY_TTS_DELAY_MS`） |

**通知音を作り変えたら、その種別の遅延も見直すこと。** 音が長くなれば読み上げと重なる。
**残響は全系統で廃したので、音の終わり（ピーク比 −40 dB）がそのまま見積もりの起点になる。**

ここで「音の終わり」と呼ぶのは**ピーク比 −40 dB まで落ちる時刻**で、§2 の「音の種類」表が
載せている秒数（gain の自動化が 0 へ到達する時刻）とは別物。前者は聞こえなくなる時点、
後者は完全に止まる時点で、EEW 特別警報なら 1.01 秒と 1.18 秒に分かれる。

**測るのは合成後の波形で、包絡線の計算ではない。** `OfflineAudioContext` でレンダリングし、
左右の瞬時値の絶対値がピーク比 −40 dB を最後に超えた位置を取る。声部ごとの包絡線を足して
見積もると干渉による打ち消しを織り込めず、実際より 0.4 秒ほど長い値が出る。

見直しの基準は「尾がどこまで伸びたか」ではなく **読み上げが始まる瞬間に音がどれだけ
残っているか**。判断に使うのは絶対値で、ピーク比は並べて見るためのもの（下記のとおり
音量設定に依存する）。

| 種別（遅延） | 音の終わり | 読み上げが始まる瞬間の残り |
|---|---|---|
| 地震情報（1000ms） | 1.41 秒 | −29.2 dB（絶対 −43.1 dBFS） |
| 震度速報（500ms） | 0.77 秒 | −19.6 dB（絶対 −33.8 dBFS） |
| 遠地地震（1700ms） | 1.62 秒 | 無音 |
| 津波解除（1700 → 1200ms） | 0.82 秒 | 無音 |
| EEW 誤報取消（1200ms） | 1.04 秒 | −44.9 dB（絶対 −57.1 dBFS） |
| 大津波警報（2300ms） | 1.97 秒 | 無音 |
| 南海トラフ臨時（1500ms） | 1.51 秒 | −39.5 dB（絶対 −54.7 dBFS） |
| 南海トラフ解説（1500ms） | 1.26 秒 | 無音 |
| 津波観測情報の更新（800ms） | 0.84 秒 | −36.7 dB（絶対 −54.4 dBFS） |

**津波解除だけ詰めた**（1700 → 1200ms）。2 音目を観測情報の更新と同じ長さに揃えたため
音の終わりが 1.33 → 0.82 秒に動き、1200ms の時点で完全に止まっている（地震情報の取消・
EEW 誤報取消と同値）。ほかは据え置き——`decayTone` の減衰が終わる時刻は音量を下げても
動かないので、音の終わりが変わっていない。

**ピーク比は音量設定に依存する。読み上げと重なるかは絶対値で判断すること。**
`decayTone` は固定の床（0.001）へ向かって指数減衰するため、ピークが低い音ほど同じ時刻での
相対値が大きく出る（震度速報は音量 100% で −19.6 dB、30% で −15.8 dB）。**音量設計を
変えると過去のピーク比とは比べられなくなる**ので、以前の測定値はここから外した。

次に音を作り変えるときは、この表と同じ測り方で比較すること（上の数値はその時点の実測で、
音を変えれば当然変わる。**残す意味は「比較の起点」を git 履歴を掘らずに得られること**）。

#### 間を合成の時間に充てる（先行合成）

対象は**間を置く非 EEW の読み上げ**（上の表と `TTS_DELAY_MS` の経路）。EEW の発報は間を置かない
ので対象外。

**間のあいだに、最初のひと区切りの音声合成を済ませておく**（`prewarmVoicevox`）。合成は VOICEVOX へ
2 往復（`/audio_query` → `/synthesis`）するため LAN 越しで 150〜350ms かかり、待ってから合成を
始めると「音が鳴り終わってから声が出るまで」の空白になっていた（実測 244ms → 20〜33ms）。

- **進行中の読み上げには触らない。** 先行合成はセッションを確立せず、鳴っているものを止めない
  （止めると、間を置いている最中に前の読み上げが切れる）
- 使われなかった先行合成は、次の読み上げが始まるときに打ち切る。放っておくと VOICEVOX 側の
  直列処理を占有して、これから読む方が待たされる
- **ただし、これから使うものは打ち切りの対象から外すこと。** 外さないと、地震情報と長周期の
  ように電文がほぼ同時に届いたとき、**後から始まった読み上げが、先に始まった側がこれから使う
  先行合成を消す**（本番ビルドの実測で「最初の音まで」が 2.8 秒に達した回があった）
- 打ち切られていた・失敗していた場合は、再生側で合成し直す（無音にはしない）
- 間より合成が遅ければ効かない。そのときは従来どおり待つだけで、遅くはならない

#### 間が無い経路には作り置きを用意する（切り出し語）

対象は **EEW の切り出し語**——第 1 フェーズが区分を伝えるために読む頭の一句で（下記
「第 1 フェーズ（切り出し）— 区分を名前で伝える」）、「地震動予報、」「緊急地震速報、」
「震源を更新、」の 3 通りしかない（`EEW_LEAD_PHRASES`）。

EEW は間を置かずに読み始めるため、上の先行合成が使えない。その結果**最も急を要する読み上げが
最も遅い**という逆転が起きていた（2024/1/1 能登の実電文リプレイでの実測: EEW は 238〜697ms、
地震情報を切って割り込んだ場面で 479ms。同じ再生で非 EEW は先行合成が効いて 1ms だった。
上の 20〜33ms とは別の計測なので、値そのものではなく桁の違いを見ること）。

切り出し語は震源名にも予想震度にも依存しない固定句なので、**起動時と、接続先・話者を変えたときに
合成しておく**（`warmFixedPhrases`）。当たれば往復ゼロで鳴る（実測 1〜2ms）。

- **待たない。** 合成が間に合っていなければ、その場で普通に合成する。ここで合成中のものを待つ設計に
  すると、VOICEVOX が応答を返さなくなったときに**その句を使う EEW が軒並み無音になる**——外側の
  待ち合わせが上限で諦めるため、記録も残らずに消える。作り置きは「間に合っていれば速い」ための
  仕掛けであって、外れても遅くはならない
- **1 件ずつ順に投げる。** VOICEVOX は合成を直列に捌くため、まとめて投げると起動直後を占有し、
  ちょうどその窓に届いた EEW の 2 チャンク目（震源名）が後ろに並ぶ
- 失敗は覚えない。VOICEVOX を後から起動することがあるため作り直す余地を残し、実際に読み上げた
  結果でも埋め直す（合成中のものがあれば打ち切って置き換える。「登録済みなら触らない」にすると、
  応答の返らない合成が居座っている間は永久に埋まらない）
- 接続先・話者が変わったら捨て、進行中の合成も打ち切る（前の声のまま鳴らさないため）
- 起動から作り置きが揃うまでには合成 3 件ぶんの時間がかかる。その窓に EEW が届けば当たらないが、
  待たずに普通の合成へ落ちるだけなので遅くはならない

切り出し語は句読点で終わり 5 文字以上でなければ単独のチャンクにならず、**作り置きが黙って
引かれなくなる**（症状は「第 1 報の声がわずかに遅い」だけでログにも出ない）。文言と分割条件の
一致は `voicevox.test.ts` が実物どうしを突き合わせて固定している。

#### 間を置く読み上げの予約は追跡する

対象は**間を置くすべての読み上げ**（`scheduleSpeech`）。先行合成の有無を問わず、EEW の誤報取消も
含む。

予約は、画面を閉じたときとリプレイを開始したときに取り消す。取り消さないと、状態をリセットした
後に古い予約が発火し、リセット済みなので待ち合わせにも掛からずそのまま割り込む（しかも記録が
残らない）。

#### EEW の発報は間を置かない

**EEW の発報（新規・続報）だけはこの仕組みの外にある。** 速報性を優先し、音の鳴り終わりを待たず
即座に震源を読み上げる（第 1 フェーズ）。予想値の読み上げ（第 2 フェーズ）がそれに続く。
EEW の音を作り変えても、ここに調整すべき遅延値は無い。

#### 第 1 フェーズ（切り出し）— 区分を名前で伝える

| 場面 | 読み上げ |
|---|---|
| 予報級（severity=Forecast）の発報 | 「地震動予報、〇〇で地震。」 |
| 警報級（severity=Warning）の発報 | 「緊急地震速報、〇〇で地震。」 |
| 続報での震源の大幅更新 | 「震源を更新、〇〇で地震。」（区分には触れない。既に伝えてある） |

区分の判定は severity、名前は電文の名称から借りている（**電文種別と区分は 1 対 1 ではない**。
根拠と表示側の対応表は [eew-spec.md](eew-spec.md) §3）。
**読み上げ固有の理由は「音声だけで区分が判別できること」。**
予報級まで「緊急地震速報」と読むと、一般に流れるのが警報だけであることから「警報が出た」と
聞こえ、実際より重く伝わる。

なおこれは気象庁の用語法からの意図的な逸脱。気象庁は「緊急地震速報」を警報と予報の両方を含む
上位の名前として使う。ここでは耳で区別が付くことを優先している。

鳴らしている途中で誤報取消が届いたときは、そこから先を鳴らさない（下記「第 2 フェーズ」の
「鳴っている間に上がったら」以降を参照）。**第 1 フェーズが見るのは誤報取消だけ**で、
予想値の変化では打ち切らない（震源名は値ではないため）。区分の格上げだけは別扱いで、次項。

#### 予報から警報へ上がったとき — 進み具合で 3 通り

区分が上がったことは、震源を読み終えるのを待つより重い。第 1 フェーズは「日向灘」で実測 5.5 秒
（震源名の長さで変わる）あり、読み切ってから伝えると告知がそのぶん遅れる。そこで**第 1 フェーズが
どこまで進んでいるか**で伝え方を分ける。

| 第 1 フェーズの状態 | 伝え方 |
|---|---|
| まだ声になっていない | 区分は発話の直前に決めるので、そのまま「緊急地震速報、〇〇で地震。」と読む（「地震動予報、」を一度も言わずに済む） |
| 鳴っている最中 | 鳴っている音を止め、警報として頭から言い直す（「緊急地震速報、〇〇で地震。」） |
| 読み終えた | 第 2 フェーズが「緊急地震速報に切り替わりました。」と前置きする |

**どの経路でも「緊急地震速報」の語は必ず声になる。** 「切り替わりました」の有無は、格上げ
だったか初報だったかという付加情報の差にすぎない。

**言い直すのは 1 回だけ。** 続報は密集して届く（能登の本震では 0.3〜2 秒間隔）ため、予約済みで
まだ声になっていない言い直しがある間は重ねない。区分を伝えたかどうかの記録は発話の直前まで
更新されないので、これが無いと 2 通目・3 通目の続報も「まだ伝えていない」と判定し、まったく
同じ文言を積んで二重・三重に読む。

言い直しでは語の途中で音が切れるが、文の頭からやり直すので**地名を聞き違えたまま残ることはない**
（「日向灘」が「日向」で切れて終わる形は避ける）。

得られるのは**区分の告知が早まること**だけで、予想値に届く時刻はほぼ変わらない。震源名を読み直す
時間（「日向灘」で約 5.5 秒）が前置き「緊急地震速報に切り替わりました。」（約 2.5 秒）より長く、
早く切り上げたぶんを食い潰すため。**この変更の値打ちは、区分がいつ耳に入るかの一点。**

**言い直しが起きないこともある。** 発話の完了待ちには上限（`EEW_SPEECH_CHAIN_MAX_WAIT_MS`）が
あり、VOICEVOX が極端に遅いと「鳴っている最中」の記録が先に消える。そのときは読み終えた場合と
同じ扱いになり、第 2 フェーズの前置きが伝える。**区分が声にならない方には倒れない。**

**進み具合の記録は、自分が置いた分だけを消す。** 同じ EEW でも予約は積み直されるため（震源の
大幅更新は古い音を止めずに積む）、1 つの地震に複数の予約が並ぶ。無条件に消す形にすると、他の
予約が置いた記録まで落ちて二重読みや「鳴っていない相手への割り込み」になる。

**止めるのは音だけで、順番は崩さない。** 言い直しを「前の発話を待たずに投入する」形にすると、
待ち行列にいた別の EEW の予約が「前が止まったこと」で解放され、始まったばかりの言い直しを
後ろから消す（止める行為そのものが解放のスイッチになる）。1 本のチェーンで直列化する前提は
崩さないこと。代償として、別の EEW が並んでいれば言い直しはその後ろへ回る。

割り込まない場合が 2 つある。

- **震源の大幅更新と重なったとき** — 読む文面が「震源を更新、〇〇で地震。」で区分に触れないため、
  止めても警報は伝わらない（区分は続く第 2 フェーズの前置きが伝える）
- **予想値の引き上げ** — 数秒ごとに書き換わるため、そのたびに切っていると読み終わらない

判定に使うのは**読み上げた区分**で、受信した電文のレベルの上昇ではない。後者だと警報 → 特別警報
の格上げでも言い直すが、区分は既に伝えてあり「特別警報」は音声で読まない方針のため言い直す
中身が無い。

#### 第 2 フェーズ（予想値） — 安定待ち

震度・長周期階級は、値が届いてもすぐには読まない。**続報のたびに直前の値と比較し、変わって
いなければ「安定待ち時間」の経過で確定、変わっていれば待ち直す**。値が一瞬だけ跳ね上がって
すぐ訂正される事象（2024/08/08 日向灘 M7.1 の第 15 報。震度 7 が 0.8 秒だけ存在して
6 強 → 6 弱へ訂正された）で、一瞬しか存在しない値をそのまま読み上げてしまうのを防ぐ。

**震度と長周期階級は独立に安定を待つ。** 階級側の細かい変動（観測点が少なくノイジーになり
やすい）に震度の確定を巻き込ませないため。日向灘の実データで、震度自体は安定していたのに
階級の変動につられて確定が上限まで遅れる現象を確認している。

| 項目 | 安定待ち時間 |
|---|---|
| 震度の跳躍幅が小さい変化（2 段階未満） | 300ms |
| 震度の跳躍幅が大きい変化（2 段階以上） | 2000ms（急な変化ほど「まだ確定していないかもしれない」と疑う） |
| 長周期階級（跳躍幅の概念は使わない。階級は 1〜4 の 4 段階のみ） | 300ms 固定 |
| 安定待ちの上限（震度・階級とも） | 5000ms。値が変わり続けても、この時間で強制的に最新値へ確定する |

跳躍幅は気象庁震度階級の並び順（1・2・3・4・5 弱・5 強・6 弱・6 強・7）上のインデックス差で
測る。数値の差ではない——6 弱(55)→7(70) は数値差 15 だが実際は 2 段階、6 強(60)→7(70) は
数値差 10 だが 1 段階、というように数値の刻みが不均一（5 弱/5 強・6 弱/6 強だけ 5 刻み、
それ以外は 10 刻み）なため、数値差のままでは急な変化と緩やかな変化を区別できない。

**上限は「値が最初に変わった時刻」から固定でカウントし、値が変わるたびにリセットしない。**
リセットすると、続報が連投される大地震ほどいつまでも確定しなくなる（2026-08-19 に潰した
「危険な地震ほど読み上げが遅れる」問題の再発）。

##### 震度と階級の確定タイミングの同期（非対称）

| 確定の順番 | 挙動 |
|---|---|
| 震度が先に確定 | 階級を待たず即読む。階級が後で確定次第、**震度も含めて**「予想最大震度〇〇。予想最大階級〇。」と読み直す（階級だけの短い追加句にはならない） |
| 階級が先に確定 | 震度が確定するまで保留し、確定した時点で一緒に「予想最大震度〇〇。予想最大階級〇。」と読む |

震度は緊急性が高く最優先で伝えるべきだが、階級はそれ単体で急いで伝える理由が薄いため。

##### 安定待ちを経由しない特別扱い

| 場面 | 読み上げ |
|---|---|
| 初報に予想震度が無く、付かない理由がはっきりしている（単独点処理・深発地震） | 安定待ちを経由せず即座に理由付きで読む（「単独点処理のため、予想震度なし。」／「深発地震のため、予想震度なし。」）。値が付いた続報が来たら通常どおり安定待ちを経て引き上げとして言い直す |
| 初報に予想震度が無く、理由も判らない | 安定待ちではなく理由不明タイマー（3 秒、`EEW_PHASE2_MAX_WAIT_MS`）で待つ。値が付いた続報が来たらタイマーを打ち切り、通常の安定待ちへ切り替える。付かないまま 3 秒経ったら「予想震度なし。」で打ち切る |
| 待っている最中に理由が判明した | 続報で深さが 150km 超に改められた等。理由不明タイマーを打ち切って理由付きで読む（初報で判っていた場合と揃える） |
| 予報から警報への区分格上げ | その時点の震度を**安定待ちを経由せず**即座に確定・発話する。区分の格上げは震度の値の変化より重いと判断しているため（震度が据え置きのまま区分だけ上がる続報が、`updateScaleStability` の「変化なしなら何もしない」判定に埋もれるのを避ける意味もある）。予想値の手前に「緊急地震速報に切り替わりました。」を前置きする。**第 1 フェーズを読み終えていた場合だけ**で、まだ読んでいる最中なら第 1 フェーズ側が言い直す（→ 上記「予報から警報へ上がったとき」） |

区分格上げの即時確定は、日向灘のように severity の昇格と震度の急な跳躍が同一報で重なった
場合でも安定待ちを迂回する（既知の残存リスク。既存のテストで固定された意図的な設計だが、
安定待ち機構が本来防ぎたい「瞬間的な過大値をそのまま読む」ケースと重なりうる）。

**続報で震度・階級が据え置きなら、安定待ちのサイクル自体が動かない**（判定は「直前の値と
同じか」）。**確定した値より下がった続報は、新しい安定待ちサイクルには入るが、確定しても
既読の値以下なら黙る**（引き上げは追うが引き下げは追わない）。

**予想値は毎回同じ形で読み、引き上げ専用の短句は持たない。** 「震度5強に引き上げ。」のような
差分の言い方は、基準にした値を実際に発話したかどうかに依存する。読み上げは割り込みや取消で
消えることがあるため、一度も声に出していない値からの引き上げを語る事故が起きる。

**格上げは遷移の言い方で述べ、初報から警報なら述べない。** 第 1 フェーズで「地震動予報、〇〇で
地震。」と伝えてあるので、聞き手は前の区分を知っており「何から何に変わったか」が通じる。ここを
「警報。」のような区分名だけにすると、値の前に単語が挟まるだけで変化が伝わらない。逆に初報から
警報なら切り出しで既に伝えており、重ねて言う意味がない（値を読み直すだけの報にも前置きが付くと
耳に障る。初期の実装では本震の 5 発話すべてに付いていた）。一度伝えた区分は下げず、severity が
揺れ戻しても「伝え済み」として扱う。

**「特別警報」は読み上げない。** 特別警報の条件を満たしていても、格上げとして読むのは予報→警報の
ときだけ。重さは値そのもの（「予想最大震度6弱。」）で伝える。表示・ブラウザ通知・通知音は内部の
重大度区分として 2 段階を保つ。理由（気象庁が発表時にこの名称を用いないこと）は
[eew-spec.md](eew-spec.md) §4 を参照。

**待つ対象は時間ではなく、値の確定と前の発話の完了。** 時間でデバウンスすると、続報が立て続けに
届く大地震ほど読み上げが遅れる（経緯は §10 参照）。

第 2 フェーズは第 1 フェーズの再生完了を待つため、その間に誤報取消が届くことがある。
**発話の直前に対象がまだ発表中かを確認している**（取り消された地震の予想震度を読み上げないため）。

**鳴っている間に上がったら、その先は鳴らさない。** 予想震度は数秒で書き換わる（2024/1/1 能登の
本震では 5弱 → 7 まで 7.5 秒、続報の間隔は 0.3〜2 秒）。文面はその時点の最新値から作るが、合成の
往復と発話そのもので数秒かかるため、鳴り終わる前に古くなる。そこで鳴らす直前に見直し、より高い
値の続報が届いていればそのチャンク以降を鳴らさない（仕組みは §3「鳴らす直前の見直し」）。
取りこぼしにはならない: 上がった続報を受けた時点で次の第 2 フェーズが予約されており、そちらが
最新値を読む。**値が下がっただけでは止めない**（読まない方針と揃える。下がったことを理由に
止めると、代わりに読むものが無く無音で終わる）。

取消による打ち切りは**誤報取消だけ**で、自動解除（発表の終わり）では鳴っているものを止めない。
内容が誤りだったわけではなく、また自動解除には取消の読み上げが無いため、途中で止めると
尻切れのまま何も説明されない。この扱いは第 1 フェーズ（震源）と共通。

### 読み上げの優先順位

`speakWithVoicevox` は待ち行列ではなく**割り込み**（既存の再生を stop し、進行中の合成を abort する。
§3「セッション管理」）。そのため EEW の読み上げは eventId をまたいで**全体で 1 本のチェーン**に繋ぎ、
前の発話が終わってから次を話す。

- **eventId ごとにチェーンを分けてはいけない。** EEW が同時多発すると（2024/1/1 能登では約 15 分間に
  6 件）互いの発話を途中で消し合い、どちらも尻切れになる
- 予約は eventId ごとに高々 1 件に畳む。解決した時点でその瞬間の最新値を読み直すため、続報のたびに
  積む必要が無い。**これがデバウンスの代わりになる**（連投中も沈黙せず、連呼にもならない）
- 既読の値（震度・階級・区分）を更新するのは**発話の直前だけ**。予約した時点で更新すると、
  取消で捨てられた発話や割り込みで消えた発話まで既読になる
- 既読の震度は**階級と「以上」の対**で覚える（`isForecastScaleHigher` が比較する）。階級値だけを
  覚えると、同じ階級のまま上限が定まらなくなった変化（「震度4」→「震度4以上」）を据え置きと見て
  黙ってしまう。逆向き（上限が確定した）は引き下げと同じ扱いで読まない。
  「以上」そのものの扱いは [`eew-spec.md`](eew-spec.md) §4「上限を定めない予想震度の扱い」
- 直前の発話を待つ時間には上限を置く（`EEW_SPEECH_CHAIN_MAX_WAIT_MS` = 8 秒）。VOICEVOX への合成
  リクエストにタイムアウトが無く、応答が返らないと後続の EEW が永久に読まれなくなるため

#### 割り込みを許す条件

**割り込みを許すのは「自分の優先度が読み上げ中のものと同じか高いとき」だけ。** 低い側は相手が
読み終わるのを待つ。

**つまり同格どうしは新しい方が勝つ。** 震度速報の更新が古い震度速報を置き換えるのは正しい挙動で、
ここを待ち行列にすると最新の震度がいつまでも読まれない。以下の表で「同格にする／分ける」の
判断が何度も出てくるが、その拠り所はこの規則（**ただし例外がある**。後述「内容が重ならない同格は
互いに待つ（相互譲り）」）。

| 優先度 | 種別 |
|---|---|
| 最優先 | 緊急地震速報（同格どうしは上記のとおり直列化する） |
| 高 | 津波の**等級の発表**（新規・格上げ・引き下げ・解除）／南海トラフ臨時情報・後発地震注意情報 |
| 中 | 地震情報（`kind: 'quake'` の電文。震度速報・震源情報・遠地地震・取消などの**種別を問わず一律**）／長周期地震動情報／津波の**観測情報**（等級が動いていない続報） |
| 最下位 | 南海トラフ関連解説情報 |

南海トラフ臨時情報・後発地震注意情報を津波と同じ高に置いているのは、発表頻度が極端に低く、
聞き逃したときの損失が大きいため。

**津波は等級が動いたかどうかで格が変わる。** 観測点の波高更新・到達確認だけを伝える続報
（観測情報）は中に置く。高に置いていた頃は、観測点の波高が 1 つ更新されるたびに地震情報の
読み上げを途中で消していた。ただし**格を下げるだけでは向きが入れ替わるだけ**で（同格は待たずに
割り込む規則のため、こんどは地震情報が観測情報を切る）、あわせて下記「内容が重ならない同格は
互いに待つ」の対象にしている。等級が動いた報を高に残すのは、警報の引き上げを観測値の読み上げの
後ろに回さないため。

**長周期地震動情報を地震情報と同格にしているのは、長周期の方が新しい情報だから。** 同格どうしは
新しい方が勝つ規則なので、地震情報を読んでいる最中に長周期が届けば割り込んで読める。以前は
「地震のあとに出る事後情報だから軽い」として一段下に置いていたが、各地の震度（数千文字・読み切りに
2 分近く）の後ろへ回されて大幅に遅れていた。**内容が別軸（震度と長周期地震動階級）で、どちらも
その時点で最新の情報**なので、待たせるより割り込ませる方が実態に合う。

**南海トラフ関連解説情報は単独の最下位に置いている。** 臨時情報の発表期間中は解説情報が毎日
届くため、既存のどの層と同格にしても必ず何かを切ってしまう。

- 高（臨時情報と同格）にすると、同格は新しい方が勝つため、臨時情報の読み上げを追い出す
- 中（地震情報・長周期と同格）にすると、数千文字に達しうる地震情報の読み上げを毎日切る

同格を作らず最下位に置くことで「**解説情報は何も切らない**」を保証している。**待ちの上限に
達したときも、割り込まずに黙る**（他の種別は割り込む）。層で「何も切らない」と宣言していても、
上限で割り込めばその宣言はそこで破れる——各地の震度は読み切りに 2 分近く達し、上限
（`HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS` = 90 秒）を実際に超える。定型文が大半の情報なので、
諦めて一度読まないことの損失は小さい。

> **見送る判定は待ちの出口すべてに置くこと。** 出口は 2 つある——上限に達したときと、待ち直し
> （下記「待つ条件は毎周回で作り直す」）を繰り返した末に抜けたとき。片方だけに置くと、順番の
> 取り合いが続いたときに保護が素通りする。見送ったときは予約の枠から降ろす（下記「到来順を守る」の
> 「取り下げた予約は枠から降ろす」）。

#### 内容が重ならない同格は互いに待つ（相互譲り）

「同格は新しい方が勝つ」で片付かない組み合わせがある。同格の中に**逆向きの要求が同居している**。

| 関係 | 望ましい挙動 | 理由 |
|---|---|---|
| 地震情報 ↔ 同じ地震の続報 | 割り込む | 言い換えなので最新だけ読めばよい |
| 長周期地震動 ↔ 地震情報 | 割り込む | 別軸の情報で、どちらもその時点で最新 |
| 津波の観測情報 ↔ 地震情報 | **互いに待つ** | 内容が重ならず、どちらも聞きたい |
| 津波 ↔ 南海トラフ臨時情報・後発地震注意情報 | **互いに待つ** | 同上（互いの言い換えではない） |

**優先度ではこの使い分けを表せない。** 2 行目以降はどれも「別主題で同格」——優先度から見れば
同じ関係なのに、割り込むものと待つものに分かれる。優先度は一次元の尺度なので「上が下を切る」
一方向しか作れない。そこで**主題**（下記「主題」）の側で「互いに切らない」相手を宣言する
（`MUTUAL_YIELD_TOPICS`）。

- 対象は津波（等級の発表）・津波の観測情報・南海トラフ臨時情報・後発地震注意情報
- **同主題どうしは対象外。** 言い換えなので割り込む（同じ観測点の新しい波高は古い方を置き換える）
- **片方が対象なら両方向で待つ。** 地震情報は対象に入れていないが、観測情報が対象なので
  「観測情報は地震情報を切らない」と「地震情報は観測情報を切らない」の両方が成り立つ
- **上位には従来どおり切られる**（優先度差があるときはこの宣言を見ない）。津波の格上げが観測情報を
  切るのは正しい
- 待ちの上限は別に持つ（`MUTUAL_YIELD_SPEECH_MAX_WAIT_MS` = 180 秒）。90 秒では各地の震度
  （2 分近く）を待ち切れず、上限に達した側が割り込んで「互いに切らない」が破れる

**取り下げの判定には持ち込まない。** 相互譲りで塞がっているだけの予約は取り下げず、待たせる
（下記「到来順を守る」）。取り下げる理由は「後から届いた*重い*読み上げに追い越された」ことなので、
どちらも読みたい相手には当てはまらない。

**EEW が予想震度の確定を待っている間も、EEW は最優先のまま。** 初報に予想震度が無く理由も判らない
ときだけ、第 2 フェーズは最大 3 秒待つ（上の表）。この待機中を「空き」と見なすと、震源を読み終えた
直後の数秒に地震情報が滑り込み、待ち明けの第 2 フェーズに**必ず**切られる。能登 16:08 の震源情報が
これで残り 5.7 秒を残して消えていた（当時の上限は 6 秒）。

**待ちには上限を置く**（上位を待つ場合は `HIGHER_PRIORITY_SPEECH_MAX_WAIT_MS` = 90 秒、
相互譲りの相手を待つ場合は `MUTUAL_YIELD_SPEECH_MAX_WAIT_MS` = 180 秒。分けている理由は上の
「内容が重ならない同格は互いに待つ」）。90 秒でも長めなのは、津波の本文が 60 秒近くに達すること
があり、短い上限では読み上げを途中で切ってしまうため。上位を待つこの上限が効くのは VOICEVOX が
無応答のときだけで、その状況ではそもそも何も聞こえないため、長く取っても失うものは無い。

> **待つ理由が変わったら計時をやり直すこと。** 上限は理由ごとに違うので、別の理由で消費した時間を
> 持ち越すと、上限の短い相手を「もう十分待った」と誤認してその場で割り込む。相互譲りを 100 秒
> 待った直後に EEW が始まると、EEW 側の上限（90 秒）を既に超えていることになり、**始まった
> ばかりの EEW を切って読み始める**（「EEW は常に最優先」が破れる）。

**上限に達して割り込んだときは記録を残す**（優先度の高い読み上げを消す判断なので、
黙って消すと事後に追えない。VOICEVOX が落ちていると毎回起こるため間引いて出す）。

なお 90 秒は**1 回の待ち合わせあたり**の上限。下記のとおり待ち直すことがあるため、1 件の読み上げが
待つ総時間はこれを超えうる（優先度の高い読み上げが立て続けに始まった場合）。

**待つ条件は毎周回で作り直す。** 一度きりの判定にすると、待っている間に始まった読み上げを
見落とし、待ち明けに読み始めた側が進行中の読み上げを後ろから切る。読み始める直前にも見直して、
必要なら待ち直す。

#### 優先度が無かったときに起きていたこと

いずれも 2024/1/1 能登半島地震の実電文（20 分・EEW 6 件・106 報）を再生し、発話の開始時刻と
推定所要時間から重なりを数えて確認したもの。優先度を入れる前は 12 件の割り込みのうち 3 件が
「軽い方が重い方を消す」向きだった（入れた後は 0 件）。

- EEW 第 1 報が地震情報に潰されていた。16:08 の EEW 第 1 報が、その 0.36 秒後に**読み上げの
  始まった**震源情報に消された。震源情報の電文自体は EEW より先に届いており、上の表の遅延を経て
  読み上げが始まる。**割り込みは電文の到来順では決まらない**
- 大津波警報が地震情報に潰されていた。大津波警報の読み上げが、その 30 秒後に始まった地震情報に
  残り 2.9 秒を残して消された
- 長周期地震動情報が震度速報・地震情報を潰していた。2 件とも発生し、消された残りはそれぞれ
  18.9 秒・23.6 秒

**逆向き（優先度の高い側が低い側を切る）は許す。** 緊急度どおりであり、また地震情報の本文は
数千文字に達することがあって（能登本震の地震情報は読み切りに 2 分近くかかる）、その後ろに
EEW や津波を並べると致命的に遅れる。

#### 到来順を守る — 追い越されたら取り下げる

**待つのは「重いものが先に届いた」ときだけ。** 自分の予約より**後に**届いた重い読み上げに
追い越された場合は、待たずに取り下げる（`speakNonEEWDelayed`）。

| 到来順 | 扱い |
|---|---|
| 重いものが先 → 軽いものが後 | 軽い側が**待って読む**（順序どおり） |
| 軽いものが先 → 重いものが後 | 軽い側を**取り下げる**（読まない） |
| 同じ主題で同格 | 先に届いた側を**取り下げる**（新しい方が勝つ） |
| 別主題で同格・相互譲りの対象 | **どちらも読む**（取り下げず待たせる。上の「内容が重ならない同格は互いに待つ」） |

> 上の行にも例外がひとつ。待ちは上限（90 秒／相互譲りは 180 秒）で打ち切られ、そのときは割り込んで
> 読む（この節の上の「割り込みを許す条件」）。上位を待つ 90 秒は VOICEVOX が無応答のときだけ
> 起こる経路で、その状況ではどちらも聞こえていない。

待って読むと「後から来た方が先、先に来た方が後」と喋ることになり、聞いている側には順序が
入れ替わって聞こえる。**優先度に例外は設けない**ので、津波の予約が EEW に追い越された場合も
取り下げる（画面・通知音・バナーは残るので、発表そのものは伝わる）。

判定は 2 本立て。**優先度が上の相手**には `speechBlocker` を予約した瞬間と発話の直前に取って
比べる（「予約時は空いていたのに、いまは塞がっている」が追い越しの印）。**同格の相手**はこれでは
捉えられないので（`speechBlocker` は厳密不等号で見る）、到来順の連番で後先を比べる。取り下げる
ときは先行合成も破棄し、タブ追従も呼ばない（画面は追い越した側に留まる）。

同格の追い越しを見る必要があるのは、通知音との間が種別ごとに 0.5〜2.8 秒と幅があるため。**先に
届いた電文の方が遅く喋り始めることがあり**、そのとき古い側が新しい側の声を切っていた（震源情報の
1.2 秒以内に震度速報が届くと、震度速報が途中で切られる）。「同格どうしは新しい方が勝つ」が逆向きに
破れる形なので、優先度ではなく到来順で裁く。

**取り下げるのは同じ主題どうしだけ。**

同格でも**内容が重なるとは限らない**。`high` には津波・南海トラフ臨時情報・後発地震注意情報が
同居しているが、これは「聞き逃したときの損失が大きい」から同格に置いているのであって（上の
「割り込みを許す条件」）、互いの言い換えではない。主題を見ずに取り下げると、**聞き逃しを防ぐ
ために作った層でまるごと聞き逃す**（後発地震注意情報が一言も鳴らずに消える）。

そこで読み上げに主題を持たせ、**同じ主題の後発だけが先発を取り下げられる**ようにしている。

| 主題 | 束ねる範囲 |
|---|---|
| `quake:<地震のキー>` | その地震の情報（震度速報・震源情報・各地の震度・取消） |
| `lpgm:<地震のキー>` | その地震の長周期地震動情報 |
| `tsunami` / `tsunamiObs` | 津波の**等級の発表**と**観測情報**（それぞれ 1 つ。常に 1 件だけを追う作り） |
| `nankai` / `kohatsu` / `nankaiCommentary` | 種別ごとに 1 つ（同上） |

**地震と長周期はイベントごとに分ける。** 別の地震は別のイベントで内容が重ならない（同じ分に 2 つの
地震が起きることは実際にある）。種別だけでまとめると、後から処理された地震だけが読まれ、その前に
届いた別の地震が一言も鳴らずに消える。長周期を地震情報と別主題にしているのは、内容が別軸（震度と
長周期地震動階級）で互いの言い換えにならないため。

> **主題を足すときは、その主題に属する読み上げの優先度を揃えること。** 取り下げの判定は「同じ主題の
> 中では優先度が常に等しい」ことを前提に、優先度を見ずに到来順だけを比べている。同じ主題に別の
> 優先度を混ぜると、重い読み上げが軽い方の到来順だけで静かに取り下げられる。

**津波を `tsunami` と `tsunamiObs` に分けているのがこの原則の実例。** 等級の発表は高、観測情報は中で
優先度が違う（上の「割り込みを許す条件」）。まとめたままにすると、**警報の予約が、後から届いた
観測情報に「追い越された」と判定されて取り下がる**——聞き逃してはいけない側が消える。

別主題どうしの同格衝突は、相互譲りの対象でなければ従来どおり割り込みで裁くので、先発が部分的に
聞こえ、後発が最後まで読まれる（対象なら互いに待つ。上の「内容が重ならない同格は互いに待つ」）。
主題ごとに「最後に予約された連番」を持つこと。単一の枠に置くと、主題違いの予約が枠を奪った隙に
同じ主題の後先が比べられなくなり、古い報が新しい報を切れてしまう。この記憶にも 200 件の上限があり、
超えると全部捨てる（そのときは取り下げが働かず、下の「割り込みを許す条件」だけで裁かれる）。

**取り下げた予約は枠から降ろす。**

取り下げが決まった予約は、その主題の「最後に予約されたもの」から降りる。**降ろさないと取り下げが
連鎖する**——一度も喋らずに消えた予約が枠に残ると、それより前に予約されていた読み上げが「後発に
追い越された」と誤認して取り下がり、どちらも読まれない。

**「割り込まずに黙る」経路も降りる対象。** 解説情報が待ちきれずに見送ったときも一度も喋っていない
ので、取り下げと同じ後始末が要る。

逆に、**読み終わった予約は降ろさない**（意図的）。後発を聞いたあとで先発を読めば、聞いている側には
順序が入れ替わって聞こえる。この節の規則はそれを避けるためのもの。

**この規則が及ぶのは、間が明けて判定を通るまでの一度だけ。** 境目は「間が明けたときに塞がって
いたか」の一点なので、同じ順序の電文でも間の長さ（0.5〜2.8 秒）とのタイミングで挙動が変わる。

判定を通ったあとの扱いは 2 つに分かれる。**混同しないこと。**

- **まだ声が出ていない（順番待ち）**: 取り下げも割り込みも起きない。待っている間にさらに重いものが
  積まれても**待ち時間が延びるだけ**（`waitForSpeechSlot` は毎周回で条件を作り直して待つ）。
  順序そのものは守られる——先に届いた重いものの後に読まれるため
- **すでに読み始めている**: ここから割り込みの側の話になり、重い方が軽い方を切る
  （上の「逆向きは許す」）

つまり「予約した時点で既に塞がっていた」電文は、EEW の続報が連投される場面では**読まれるまで
長く待つ**ことがある。順序は入れ替わらないので取り下げていないが、待ちの上限（90 秒）まで
届けば割り込んで読む。

### 自動タブ切替の優先順位

タブの奪い合いには **3 つの駆動が併走する**（`src/utils/tabPriority.ts`）。

| 駆動源 | いつ動くか | 順序を決めるもの |
|---|---|---|
| **読み上げ追従**（`speech`） | 読み上げの発話を投入する瞬間 | 読み上げ側の待ち行列（`waitForSpeechSlot` / `chainEEWSpeech`） |
| **電文の受信**（`receipt`） | **読み上げが無効な端末**に電文が届いたとき | 下の優先度表と 15 秒の保持。ただし**EEW 続報の保持は越える**（下の判定の 4） |
| **保持機構**（`hold` / `idleRevert`） | ユーザー操作・揺れ検知・アイドル復帰、および読み上げが有効な端末で読み上げ文が空になった電文 | 下の優先度表と 15 秒の保持 |

`receipt` を分けてあるのは、**声で伝えられない電文には画面が唯一の伝え手になる**ため。読み上げが
有効な端末では同じ電文が追従で動くので、この駆動源は現れない。読み上げ文が空になった電文だけは
`hold` へ回す ―― 本来は追従で動く電文であり、越えさせると EEW を実際に読み上げている最中に画面を
奪ってしまう（振り分けは `resolveNonRealtimeTabSource`。取り違えても型では気づけないので純関数に
切り出してテストで固定してある）。

保持機構の駆動源を 2 つに分けてあるのは、**既定の状態へ戻す操作が張った保持だけは読み上げ追従に
譲る**ため（下の判定の 5）。復帰は新しい情報ではなく元の状態へ戻すだけの操作なので、そこへ
読み上げの始まる電文が届いたなら画面を合わせる方が筋。`idleRevert` を使うのは、アイドル復帰が
realtime に留まる経路と、既定タブへ戻る復帰すべて（アイドル復帰・EEW 全解除・揺れ検知終了・
揺れの可能性の失効。実装は `revertToDefaultTab` に集約してある）。

> **この譲りが実際に効くのは、EEW 発表中のアイドル復帰だけ。** 既定タブへの復帰は最低優先度（1）で
> 張るので優先度比較だけで通り、揺れ検知中の復帰（2）は揺れ検知の保持として素通りする（判定の 2）。
> 残るのが EEW 発表中の realtime 維持（4）で、そこだけが追従を弾いていた。
>
> **譲った結果、EEW の表示（realtime）へはしばらく戻らない。** 追従が画面を取ると保持の重みは
> その電文のもの（地震情報なら 1）に下がり、以後の続報は片方向抑制（判定の 3）で弾かれる。戻る
> 契機は「電文が `idleRevertSec` のあいだ途切れて次の復帰が発火する」か「新規発報・レベルアップ・
> 誤報取消」の 2 つだけで、**続報が続いている EEW ほど前者は起きにくい**（受信のたびに復帰タイマー
> が延びる）。それでも譲る方を採ったのは、EEW が通知音・タイトル・ブラウザ通知でも伝わる一方、
> いま読み上げている電文の中身はその画面にしか出ないため。

読み上げがある経路は追従で動き、**順序の判断を読み上げ側に預ける**。重い電文の読み上げ中に
届いた軽い電文は、その読み上げが終わって自分の番が来たときに初めて画面を取る。こうして声と
画面が食い違わなくなる。

**ただし待たされずに読めるなら、通知音と同じ瞬間に先出しする**（`speakNonEEWDelayed`）。
通知音と声が重ならないよう電文の種別ごとに間を置いているため（0.5〜2.8 秒）、その間ずっと画面が
前のタブに留まると「音が鳴ったのに何も変わらない」ように見える。先出しするかどうかは
「いま読み上げを始められるか」だけで決める（判定は `speechBlocker`。待ち合わせと**同じ条件を
共有する**こと。二重に書くと、片方だけ直したときに「待たされないと踏んで画面を動かしたのに、
実際には待たされる」形の食い違いになる）。

- 対象は**タブを持つ非 EEW の経路**（地震情報・津波・長周期・それぞれの取消）。EEW は受信の瞬間に
  要求しているので対象外、南海トラフ系はタブを持たないので対象外
- 先出ししたあとも、発話を投入する瞬間にもう一度同じ追従を出す。待っている間に別の情報が画面を
  取っていれば、自分の番が来た時点で取り戻せる
- **ただし揺れ検知に奪われた画面は取り返さない**（`shouldRetakeAfterPreSpeech`）。取り返すと、
  次のレベルアップでまた奪われて数秒のうちに画面が往復する。強震モニタは 1 秒ごとにフレームが
  来るので、通知音との間（地震情報系は 0.5〜1.7 秒、津波は最大 2.8 秒）にレベルアップ判定が
  入る。EEW の続報に片方向抑制を入れているのと同じ理由で、**往復の方が食い違いより悪い**
  - **見送るのは揺れ検知が張った保持だけ**（`hold` 駆動）。揺れ検知中のアイドル復帰も同じ
    優先度で張るが（`idleRevertPriority`）、そちらは `idleRevertSec`（既定 30 秒・選べる最短で
    15 秒）に 1 回しか発火しないので往復の原因にならない。駆動源を見ずに優先度だけで弾くと、順番待ちで長く待たされた読み上げが
    直前のアイドル復帰に阻まれ、**声だけ出て画面が動かない**（判定の 5 を裏から破ることになる）
  - **追従の呼び出し自体は省かない。** 省く形にすると、近接して届いた 2 つの電文が互いの先出しを
    上書きし合ったとき、後で声に出る側の画面が二度と戻らない。先出しの成否は「取れた実績」で
    しかなく、そのあと奪われたかを知らないため。呼び出しは常に行い、取り返すかどうかは
    **そのときの保持の中身**で決める
  - 見送ったときは記録を残し、畳んだパネルは開く（要求を出さない以上 `requestAutoTab` 側の
    記録も展開も走らないため、拒否の経路と手当てを揃える）
- **先出しには最小滞留時間の床を掛けない**（`preSpeechTab` と `followSpeechTab` の使い分け）。
  先出しは「これから読む予定」にすぎないので、床を消費させると後から実際に声が出る側の追従を弾く。
  実際に踏んだ形（当時の大津波警報の間は 4.2 秒。現在は 2.3 秒）: 先出し → 直後の震度速報（間 0.5 秒）が床で弾かれ、
  **声が始まっても**画面が津波タブに留まった（地震情報を読む 3.7 秒間ずっと食い違う）
- 先出しの判断が外れること（間を置いている最中に EEW や津波が割り込む）はある。**巻き戻さない。**
  割り込んだ側が自分で画面を取るため、放っておけば正しい方へ落ち着く

> **EEW だけは例外で、受信の瞬間にも要求を出す**（`setActiveTabRealtimeUrgent` /
> `setActiveTabRealtimeOnUpdate`）。予想震度が上がらない続報では読み上げが黙るため、追従だけに
> 任せると realtime を取り戻す手段が無くなる。この 2 つも駆動源は `speech` にしてあるが、それは
> 「発話の投入時に動く」という意味ではなく、**他の読み上げ追従に弾かれないための指定**。
> 冗長に見えても消さないこと（消すと EEW の続報で realtime へ戻る経路が失われる）。

読み上げが無い経路は保持機構で動く。該当するのは、強震モニタの揺れ検知（読み上げを持たない）・
読み上げが無効な端末・読み上げ文が空になる場合（長周期、観測に変化のない津波の再送）・
ユーザーの手動選択・アイドル復帰。

> **地震情報はここに来ない。** 変化が無い続報でも名乗りだけは読むため、読み上げ文は常に非空に
> なる（→ §4「続報は差分だけ読む」）。地震情報でこの経路へ落ちるのは読み上げが無効な端末だけ。

> 区域を持たない津波の続報は**観測点更新として読み上げる**ので、通常はこちらに来ない
> （[tsunami-spec.md](tsunami-spec.md) §10「等級を伝えていない電文」）。読み上げ文が空になるのは
> 観測に一切変化がない再送のときだけ。

> **読み上げが無効な端末でも、EEW 発表中に震度速報・津波警報は画面へ出る**（機序は下の判定の 4）。
> 設定の既定値は読み上げ無効なので、ここが塞がると既定のままでは EEW 中に何も画面へ出せない。
>
> **ただし新規発報・レベルアップ・誤報取消（6）が張った 15 秒は越えない。** 続報が 1 本届けば
> 4 に落ちるため窓は短いが、続報が来ないまま終わる EEW と誤報取消の直後は最大 15 秒残る。
> その間も音・通知・ウィンドウタイトルは働く。
>
> **声と画面が一致するのは読み上げが有効なときだけ**という点は変わらない。読み上げを持たない
> 経路には順序を決める仕組みが無いため、複数の電文が続けて届いたときの前後関係は優先度と保持で
> 裁くしかない。
>
> 以下は**読み上げの設定に関わらず効く**もの。
> ①EEW の続報が他の情報の画面を奪わない抑制（津波タブ表示中に続報で引き戻されなくなる）
> ②アイドル復帰が揺れ検知中に張る重み（揺れ検知のあと津波が画面を取れるようになる）
> ③揺れ検知の保持が他の移動を妨げない（揺れ検知中に地震情報が届いたら画面が移る）
> ④津波の観測点更新でも画面が移る（従来は新規発報と格上げだけだった）
> ⑤特別情報の受信でパネルを一時的に開く挙動。

| 優先度 | 契機 |
|---|---|
| 6 | EEW の新規発報・レベルアップ・誤報取消 |
| 5 | ユーザーの手動選択（ナビの選択・津波カードから地震情報へのリンク） |
| 4 | EEW の続報 |
| 3 | 津波（新規発報・grade 格上げ・観測点更新・解除／取消／失効） |
| 2 | 強震モニタの揺れ検知 |
| 1 | 地震情報・長周期地震動情報 |

揺れ検知が地震情報より重いのは「いま揺れている」を示す情報だから。津波より軽いのは、津波が
避難行動を促す情報だから。**長周期地震動を地震情報と同格にしているのは読み上げ側と揃えるため**で、
どちらも移動先は地震情報タブなのでタブの奪い合いは起きない。

#### 受け付けるかの判定（`shouldAcceptAutoTab`）

上から順に見る。

1. **保持が切れていれば通す**（`TAB_HOLD_MS` = 15 秒）
2. **揺れ検知（2）の保持は、他の移動を妨げない。** 揺れ検知のあとに地震情報や津波が届くのは
   実際に起きた順序どおりで、そこで画面が留まる方が不自然。**読み上げの有無に関わらず**通す。
   優先度の値（2）は逆向き（揺れ検知が地震情報の保持を越えて realtime を取る）で意味を持つ
3. **EEW の続報（4）は、他の情報が確保している画面を奪わない。** 「非 realtime へ移ったあとは
   続報で引き戻さない」という片方向の抑制で、優先度の仕組みを入れる前の実装にあった考え方を
   駆動源の枠組みで作り直したもの（優先度の比較だけでは続報 4 ＞ 津波 3 で通ってしまう）。
   これが無いと、津波を読み上げて画面を移した直後に続報が届いて realtime へ戻り、数秒ごとに
   往復する。realtime を EEW 自身が確保している間（保持が EEW 由来）は素通りする
4. **読み上げが無効な端末での電文の受信（`receipt`）は、EEW 続報の保持を越える。** 直上の抑制と
   対になる規則で、声で伝えられない電文には画面が唯一の伝え手になるため。画面を取ったあとは
   その直上の抑制が 15 秒守る。**越えるのは続報（4）の保持だけ**——`eewUrgent`（6）は越えない
   （誤報取消のオーバーレイ表示を無関係な地震情報で消さないため）。アイドル復帰が EEW 発表中に
   張る保持（4・`idleRevert`）もここで越える（揺れ検知中の復帰は 2 なので判定 2 が、既定タブへの
   復帰は 1 なので判定 7 が通す）。読み上げが有効な端末で読み上げ文が空になった電文は `hold` で
   出るため、ここには来ない（振り分けは `resolveNonRealtimeTabSource`）
5. **アイドル復帰の保持は、読み上げ追従を妨げない。** 復帰は「既定の状態へ戻す」操作にすぎず、
   新しい情報より重い理由がない。ユーザー操作・揺れ検知（`hold`）に対しては従来どおり優先度で
   判定する（電文の受信は直上の判定 4 が通す）
6. **追従どうしは保持を見ない。** 順序は読み上げ側が決めているので、タブ側で重ねて守ると
   「読み終えた電文の保持の残り」が次に読む電文を弾く（この二重防御が「喋っているのに画面が
   動かない」の正体だった）。
   **ここを「手動選択以外は全部突破」まで広げてはいけない**（広げると、区域を持たない津波電文で
   受信時要求に落としたフォールバックを長周期が即座に奪う）。譲らせる相手は 2・4・5 のように
   駆動源で名指しする
7. それ以外は優先度を比較する（同格以上は通す。新しい情報が勝つ）。手動選択を突破できるのは
   EEW の新規発報・レベルアップ・誤報取消（6）だけ

> **揺れ検知中に地震情報や長周期が届くと、画面は earthquake タブへ移る**（読み上げの有無に
> 関わらず）。地図の内容は表示中のタブから決まるため、リアルタイム震度の観測点・検知点・予報円は
> 一時的に見えなくなる（[map-rendering-spec.md](map-rendering-spec.md) §3）。実際に起きた順序を
> そのまま見せる方針を採った結果で、検知そのもの（判定エンジン・通知音・検知カード）はタブに
> 関わらず動き続ける。揺れがレベルアップしたり別地点で検知されれば realtime へ戻る。

#### そのほかの決めごと

- **保持は「最後に動いた理由」で上書きする**（最大値を取らない）。EEW の新規発報（6）で確保した
  直後に続報（4）で動けば、保持も 4 に下がる。最大値を取ると、その EEW が終わるまで手動選択が
  奪われ続ける
- **追従には最小滞留時間がある**（`TAB_FOLLOW_MIN_DWELL_MS` = 1.5 秒）。VOICEVOX が起動して
  いない端末では合成が 1 つも通らず発話がほぼ即座に終わるため、床を置かないと声が出ないまま
  タブだけが激しく入れ替わる。**優先度が上がる追従は床を無視する**（声が切り替わっているのに
  画面が遅れないように）。床は追従だけに掛け、受信時の要求には掛けない
- **ユーザー操作とアイドル復帰は必ず通る。** どちらも `forceTab` を通り、保持を捨ててから
  張り直す。拒否できる形にすると次の 2 つが起きる。①ユーザー操作: 「押しても切り替わらない」
  （津波タブを見ている間に地震情報へのリンクを押す経路が該当した）②アイドル復帰: タイマーは
  一発限りで再スケジュールされないため**二度と復帰しない**。とくに設定「自動復帰までの時間」の
  15 秒は保持時間と一致するため、直前の手動操作と必ず衝突する
- **アイドル復帰が realtime に留まるときの重みは、留まる理由に合わせる**（`idleRevertPriority`）。
  EEW 発表中なら続報相当（4）、揺れ検知だけなら揺れ検知（2）。揺れ検知だけのときに EEW 相当を
  張ると優先度表（揺れ検知＜津波）が逆転し、津波警報や「別地点で揺れ検知」が画面を取れなくなる。
  この重みが効くのはユーザー操作・揺れ検知（`hold`）に対してだけで、読み上げ追従は駆動源で通る
  （判定の 5）。電文の受信（`receipt`）も判定の 4 で通る
- **生のタブ切替を使わないこと。** 優先度を通らない移動は、張るべき保持を張らないまま動く。
  実装では `setActiveTab` を呼べるのは `requestAutoTab` だけという不変条件にしてある
  （配り忘れを 3 箇所作り、いずれも「画面が奪われる」「復帰しない」という形で出た）
- **駆動源には既定値を置かない。** `requestAutoTab` も `forceTab` も呼び出し側に明示させる。
  選択を誤ったときの症状は例外もログも出さずに現れる（`hold` で出せば EEW 発表中に画面が動かず、
  `receipt` で出せば読み上げ中の EEW から画面を奪う）ため、型で気づけるようにしてある
- 拒否したときもパネルの折りたたみは解除する（保持は「今見せるべきものを守る」ためで、情報を
  隠すためではない）
- **南海トラフ臨時情報・後発地震注意情報・関連解説情報はタブを持たない**ので自動タブ切替の
  対象外。地図に重ねた帯（`SpecialInfoBanner`）で伝えるため移動先が無い。代わりにパネルを
  一時的に開く挙動があり、詳細は [architecture-spec.md](architecture-spec.md) §4 が単一情報源
- **読み上げ中のアイドル復帰は別課題。** 各地の震度は読み切りに 2 分近くかかることがあり、
  その間に既定 30 秒のアイドル復帰が発火すると声と画面が食い違う。復帰を延期する変更は
  「二度と復帰しない端末」を作る危険があるため、この修正には含めていない

ログの読み方（成立・拒否はいずれも `console.debug`）。

| 文言 | 意味 |
|---|---|
| `タブ名を要求` | 判定に入る前（次の行を見るまで結果は分からない） |
| `→ タブ名 移動` | 成立して移動した（`保持切れ` か `保持中N/駆動源を突破` が続く） |
| `→ タブ名 スキップ` | 優先度・抑制の判定で拒否された（理由が括弧内に出る） |
| `→ タブ名 追従を間引き` | 最小滞留時間の床で間引かれた |

追従は呼び出し元が名前付きの記録を持たないものがあるため、結果は `requestAutoTab` 側で残している。
要求の文言を「→ …移動」と分けているのは、1 行目だけを読んで「移動した」と誤読しないため。
拒否のときは**要求側と保持側の駆動源を両方出す**こと。負けた相手の優先度だけでは、その保持を
張ったのが受信時要求か・手動選択か・復帰かを突き合わせられない。

### 読み上げに合わせたカードの追従（津波のみ）

タブを合わせても、カードが縦に長ければ読まれている区域は画面の外にある。そこで**読み上げの
進行に合わせて津波カードをスクロールさせる**（`ttsFollow.ts` ＋ `TsunamiTab`）。

**要件の中心は「動かしすぎないこと」。** 1 行ずつ寄せると細かいスクロールが連続して落ち着かない。

| 判定 | 動き |
|---|---|
| 読んでいる箇所がすべて視野内 | **動かさない**（これが主要な歯止め） |
| 視野の外 | 送る。行き先は「読んでいる箇所＋前置き＋これから読む箇所を、視野に収まる限り広げた範囲」の上端（上に余白を 24px 残す） |
| 読んでいる箇所だけで視野を超える | その上端を視野の上端に合わせる（観測点を多く抱えた区域の行） |

**収まりの判定と送り先は同じ基準で測る。** 収まりを余白抜きの高さで測ると、上に残った未読を含める
ために範囲を伸ばしすぎ、送り先ではその余白のぶん**読んでいる箇所が視野の下から出る**（送り先だけ
下げているため）。視野内かどうかの判定も同じ余白を見込む ―― 判定だけ厳しくすると、余白のぶん
足りないだけで毎チャンク送り直すことになる。

範囲の上端を視野の上端に置くのは、**最小移動で収めるとスクロールが増えるため**。下に余地を作れば
続きの箇所がそこに入り、次の数チャンクは「視野内」の判定で動かないまま済む。実測では、大津波警報の
全区域がおおむね 1 画面に収まる大きさならスクロールは 1 回で済み、パネルを狭めて収まらなくすると
等級のあいだだけでなく区域ごとに送られる（動きの量は画面の大きさと区域数で変わる）。

**区域を読むときは、その等級カードの頭を「前置き」として一緒に視野へ入れる。** 区域行だけを上端に
合わせると、どの警報の話をしているのかが画面から消えるため。ただし前置きは**読んでいる箇所とは
別に扱う**。

- 動かすかどうかの判定には**使わない**。読んでいる箇所ではないので、これが画面外にあることを
  理由に送ってはいけない
- 収まらなければ**捨てる**。区域の多い等級カードでは前置きを入れる余地が無い
- 足す順は前置き → これから読む箇所。逆にすると、続きの区域で視野が埋まって前置きが必ず落ちる

> 前置きを「読んでいる箇所」に混ぜてはいけない。**混ぜると等級ごとにしか動かなくなる**
> （理由と経緯は `ttsFollow.ts` の `planFollowScroll` の JSDoc）。

**ハイライトは作らない。** スクロールの追従だけを行う。

#### 追わない条件

| 条件 | 理由 |
|---|---|
| 津波タブが表示されていない | タブは `invisible` で隠すだけなので、非表示でもスクロールが効いてしまう（戻ると知らない位置にいる） |
| パネルが折りたたまれている | 幅または高さが 0 になり、視野の高さが取れない |
| 手で動かした直後（`INTERACTION_HOLD_SEC` = 30 秒） | 地図の自動フィットと同じ考え方・同じ定数。検知は `wheel` と `touchstart` のみ（`scroll` は自分の `scrollTo` が撒くので使えない。クリックは拾わない ―― 観測点をクリックして地図を寄せるのは正当な操作） |
| 対象の行を引き当てられていない | 区域コードや観測点名が食い違って一度も引けないことがある。受け持ったことにしないので、猶予が明ければ受信時スクロールが動く |

逆に、**読み上げが有効なときは受信時スクロール（`focusedDistrict` による「変わった区域へ寄せる」
動き）を待たせる。** 電文が届いた瞬間に区域へ寄せても、読み上げが始まるのはその 0.8〜2.8 秒後
（通知音との間隔）で、そこから追従が等級カードの頭へ引き戻す。**発表の直後に前後へ往復する動きが
見える**ため、声と画面を一致させる側へ任せる。

ただし**待ちっぱなしにはしない**（`SPEECH_FOLLOW_GRACE_MS` = 20 秒）。「有効」は端末の設定値に
すぎず、その電文で実際に読み上げが成立するかは別だからで、次はいずれも設定が有効なまま起こる。

- VOICEVOX が未起動・到達不能（`speakWithVoicevox` は無音のまま正常終了する契約）
- 区域コードや観測点名の食い違いで追従が引き当てられない

待って追従が受け持たなければ、受信時スクロールが動く。**ここを塞ぐと、これらの場面で津波カードが
一切動かなくなる**（読み上げが無効な端末では待たずに従来どおり動く）。

**そもそも待たない受信もある。** 変わった区域が特定できない受信（解除・実質変化なしの続報・
復帰による先頭戻し）は、追従の対象になる読み上げを持たない（解除の読み上げは区域名を含まない）。
待たせても追従は来ず、猶予のあいだ解除前の位置に留まるだけ。**解除で待たされるのが一番まずい。**

**他のタブから自動で連れてきたときは、カードの先頭へ戻す。** 一度スクロールしたあと別のタブへ移り、
続報やアイドル復帰で連れ戻されると、前に見ていた途中の位置から始まってしまう。動かさない条件が 2 つ:

- **ナビの手動選択で開いたとき** — 自分で開いたのだから読んでいた場所を保つ
- **手で動かした直後**（追従と同じ `INTERACTION_HOLD_SEC`）— 他の 2 駆動も同じ保持を尊重する

**「タブが実際に変わったとき」だけ**であることが重要。タブ移動の要求は「既に表示中のタブ」へも
飛ぶ（読み上げの追従は電文ごとに津波タブを要求する）ため、要求の受理だけを合図にすると
**開いたまま読み進めている最中に続報が来るたび画面が飛ぶ**。

先頭へ戻すのは**最も弱い層**で、同じ受信で受信時スクロールや追従が動くならそちらが上書きする
（先頭復帰は `useLayoutEffect`、他は `useEffect` と rAF なので必ず後になる）。

> **検知できない操作もある**（スクロールバーのドラッグ・ブラウザ内検索）。手で動かしたのに追従が
> 続く場合がある。拾えない理由は実装のコメントに残してある。

#### 「いま読んでいる箇所」の決め方

読み上げ側（`voicevox.ts`）が渡すのは**予約**で、`startAt` は AudioContext の時間軸の未来を指す
（`onChunkScheduled`）。追従側はこの予約表を持ち、`requestAnimationFrame` で `getSpeechClock()` と
突き合わせて現在位置を決める。

**チャンクごとに `setTimeout` を張る形にはしていない。** バックグラウンドのタブではタイマーが 1 秒
以上に間引かれる一方で音は実時間で鳴り終わるため、滞留したタイマーが読み上げの終了後に発火して
追従の状態が残る。`ctx.suspend()`（システムスリープ）では逆方向にずれる。rAF なら非表示中は止まり、
戻ったときに一発で正しい位置へ収束する。

**通知の例外で読み上げを壊さないこと。** `speakWithVoicevox` は「例外を投げない」契約（未起動・
通信失敗でも無音で正常終了する）で、通知から throw が抜けると再生ループが中断し、**警報の本文が
途中で切れる**。記録だけ残して続行する（`stillPlayable` と同じ方針）。

#### 対象の特定

> ここで言う参照は**津波カードの行を引くためのもの**（等級・区域・観測点）。地震情報が持つ
> `quakeRegion` / `quakeFact` は引き当てるカードを持たず、この節の対象外
> （→ §4「既読になるのは「声になった分」だけ」）。

**名前の文字列照合は使わない。** 津波予報区 69 件と観測点 213 件のあいだに包含関係が 37 組あり、
「清水 ⊂ 土佐清水」のようにオフセット一致もある。さらに読み上げが使う区域名は観測情報の
`districtName`、カードの行は `area.name` で、`matchesArea` が code を優先することからも両者が
食い違う経路が想定されている。

代わりに**読み上げ文を組むときに参照（`SpeechRef`）を持たせる**（`SpeechSegment`）。参照は 3 種
（等級・区域・観測点）。区域は code を優先し、無ければ名前で引く（`matchesArea` と同じ順序）。
等級を告げる文（「大津波警報が発表されました。」「また、次の地域に津波警報が発表されています。」）は
その等級のカードを指すので、区域名を読み始める前に画面が整う。

**引き当ての失敗は記録に残す。** 読み上げの終わりに、区域・観測点を読んだのにその行を一度も
引けていなければ警告を出す（症状は「画面が動かない」だけで、表示の不具合と区別できないため）。
**数えるのは区域・観測点だけ。** 等級のカードは全等級ぶん常に登録されていて電文の中身に依らず
必ず引けるので、これを成功に数えると（読み上げは必ず等級の宣言から始まる）**警告が二度と出なく
なり、診断が静かに死ぬ**。前置きを数えないのも同じ理由。

- **種類が混ざったチャンクでは、より具体的な方だけを対象にする**（観測点 ＞ 区域 ＞ 等級）。
  「岩手県、宮古で1.2メートル、」のように短いチャンクが結合されるが、区域の行は観測点の行を
  内側に抱えて背が高く、両方を対象にすると範囲が視野を超えて区域の先頭へ揃え直すだけになる
  （読んでいる観測点が画面に出ない）。等級のカードは区域行をすべて抱えているので同じ理由で最も弱い
- 渡すのは**津波の読み上げだけ**。地震情報の本文は数千文字（数百チャンク）で、対象を持たない通知が
  大量に流れる

#### 世代の管理

セッションには世代トークンを添える（`createSpeechFollowController`）。読み上げが続けて起きると、
**後の発話の最初の通知が前の発話の終了より先に届きうる**（割り込む側は先行合成が済んでいれば即座に
鳴り出す一方、割り込まれた側はまだ完了を待っている）。トークンが一致するときだけ状態を触る。

リプレイの開始・切替では世代を問わず打ち切る（`reset`）。`resetTracking` は鳴っている読み上げを
止めないため、追従だけを残すと切り替え後の無関係なカードを古い進行に合わせて動かし続ける。

状態を React に伝えるのは**開始と終了だけ**。チャンクごとに更新すると App から全タブが再描画される
（非表示タブの描画を 0 回に保つ設計。[architecture-spec.md](architecture-spec.md)）。途中の通知は
セッションのオブジェクトへ直接積む。

### 設定連動

- `settings.soundEnabled` — アラート音の ON/OFF
- `settings.voicevoxEnabled` — 読み上げの ON/OFF（`soundEnabled` と独立）
- **ブラウザ通知は種別ごとに 3 つの独立トグル**:
  - `settings.notifyEEW` — 緊急地震速報の発報・昇格時のブラウザ通知 ON/OFF
  - `settings.notifyTsunami` — 津波注意報以上のブラウザ通知 ON/OFF
  - `settings.notifyDetection` — 強震モニタ揺れ検知時のブラウザ通知 ON/OFF
- `settings.notifyMinScale` — 通知の最低震度
- `settings.idleRevertSec` — **操作も情報の更新もない状態が続いたとき**にデフォルトタブへ戻るまでの秒数（`0` で無効。ユーザー操作・自動のタブ切替・電文の受信のいずれでも計り直す。「最低表示時間の保証」を兼ねている理由は [`settings-pwa-spec.md`](settings-pwa-spec.md) §2）

### 既知の課題

- 5 箇所の setTimeout が未追跡・キャンセル不能で時系列逆転が起きうる

### 解消済み

- **AUD-2**: EEW キャンセル電文が P2PQuake WS と Yahoo の両方から届いた場合の二重鳴り防止。`hadKey=true`（このセッションで表示中の EEW）のみで音・通知・読み上げを発火（`useLiveEventHandler.ts`）。2 経路が重なるのは standard 版限定だが、`hadKey` ガード自体は両バリアントで働く（[`eew-spec.md`](eew-spec.md) §3）
- **AUD-4**: 新しい読み上げの開始時に旧セッションの合成リクエストを `AbortController` で打ち切るようにした。セッション ID の更新だけでは in-flight のリクエストが完走して VOICEVOX を占有し、新規発話が待たされていた
- **AUD-6**: 津波の解除/取消/期限切れの通知音を追加（`playAlertSound('tsunamiCancel')`。音の内容は §2 の表を参照）
- **自動タブ切替の優先度**: 後から来たイベントが無条件にタブを奪う問題を解消した（§6「自動タブ切替の
  優先順位」）。EEW が確保した realtime を地震情報が即座に奪い、声は EEW を守るのに画面だけ取られて
  いた。EEW 誤報取消の 10 秒オーバーレイ中に無関係な地震情報でタブが即消える問題も同時に解消
- **AUD-7**: 読み上げは常に `voicevoxEnabled` 単独で判定するように統一。`soundEnabled` はアラート音のみに影響し、`voicevoxEnabled` の可否とは独立に動く

## 7. ブラウザ通知（`notifications`）

`src/utils/notifications.ts`。`Notification` API のラッパー。

- 初回発火時に権限リクエスト
- `tag` で通知を種別ごとに識別（同一 tag は上書き）
