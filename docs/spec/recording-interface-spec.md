# 録画ツール向けインターフェース仕様書

> 本書は**アプリの外から再生を操り、中で何が起きたかを読み取るための口**（`window.__replay`）をまとめた仕様書。
> 読者は**録画・編集の自動化を書く人**を想定している。実コードと食い違う場合は実コードを正とする。
> 関連: [`settings-pwa-spec.md`](settings-pwa-spec.md) §6（再生そのものの仕組み）、
> [`audio-tts-spec.md`](audio-tts-spec.md) §6（読み上げの順番と割り込み）。

## 1. 概要

地震の記録動画を作るために、アプリを過去の時刻から再生して画面を録る。編集では
**「どこを等倍で見せ、どこを早送りし、どこをカットするか」**を決めるので、外から
「いつ何が起きたか」が読めないと判断できない。

`window.__replay` はそのための口で、ページが表示されている間は常に生えている
（`src/App.tsx`）。**設定タブの UI を叩かせないために置いてある** —— UI を経由させると、
文言やレイアウトを変えるたびに自動化が壊れ、「画面の見た目」と「外から操る口」が結びついてしまう。

| | |
|---|---|
| `now()` | 再生中のシナリオ時刻（epoch ms）。ライブ中は実時刻 |
| `offset()` | 壁時計に足しているオフセット(ms)。`null` ならライブ |
| `fetching()` | 電文を取りに行っている最中か |
| `error()` | 取得の失敗（`null` なら失敗していない） |
| `speaking()` | 読み上げの最中か |
| `start(iso)` / `stop()` | 再生の開始・停止 |
| `drainEvents()` | 溜まったイベントを汲み出す（返した分は消える） |
| `peekEvents()` | 消さずに覗く（デバッグ用） |

**`start()` が取るのは ISO 8601 の文字列。** `offset()` が返す「壁時計に足している ms」と
対になる入力に見えるが別物で、数値を渡すと 1970 年前後の時刻として解釈される。いまは
入口で弾いて取得を 1 件も投げないが、その門を置く前にこの誤りで配信元へ 576 件の
リクエストが出た。

## 2. イベントログの汲み出し

### なぜイベントログが要るか

**`speaking()` だけでは、連続して読み上げたものが 1 本に融ける。** あれが答えるのは
「いま読み上げているか」だけで、どの発話かを持たない。

2024-01-01 18:27 の実配信では、津波（観測）の読み上げ（約 36 秒）の直後に
震源・震度情報の読み上げが続き、外からは **60.3 秒の 1 本**にしか見えなかった。編集側が
頭（採用すると決めた電文）を見て丸ごと採用した結果、落とすと決めた電文の読み上げが
36.6 秒ぶん本編に入った。**音の途切れからも分けられない** —— 0.12〜0.31 秒の息継ぎが
均等に並ぶだけで、発話の境目と区別が付かない。

イベントログは**読み上げ 1 本ごとに開始と終了を出し、それぞれがどの電文のものかを指す**。

### 汲み方

```js
// CDP（Chrome DevTools Protocol）越しに数百ミリ秒おきに呼ぶ
const { events, dropped } = await page.evaluate(() => window.__replay.drainEvents())
if (dropped > 0) console.warn(`イベントを ${dropped} 件取りこぼした`)
for (const ev of events) record(ev)
```

- **返した分はバッファから消える。** 同じイベントを二度受け取ることはない
- **ポーリングの形にしてある。** 外の録画ツールは CDP 越しに関数を呼ぶだけで、ページからの
  通知は受け取れない
- **定期的に汲むこと。** 溜めておけるのは 2000 件までで、超えると古い方から捨てる
- **`peekEvents()` は消さずに覗く。** 捨てた件数も持ち越すので、覗いても汲み出しの邪魔にならない

### 取りこぼしの見分け方

捨てたことは**2 通りで分かる**。

- `dropped` —— 前回汲んでから捨てた件数。汲むと 0 へ戻る
- `seq` の飛び —— 全イベントが持つ通し番号（1 始まり・単調増加）。飛んでいれば、その間の
  イベントは失われている

**記録できなかった回も `seq` は進む。** 記録の処理が失敗しても本体は止めない設計なので、
その回は番号だけが消費される（捨てたときと同じ形で表に出る）。

## 3. イベントの共通部分

すべてのイベントが次の 3 つを持つ。

| フィールド | 意味 |
|---|---|
| `seq` | 通し番号（1 始まり・単調増加） |
| `at` | **シナリオ時刻**（epoch ms）。`now()` と同じ時間軸で、再生の速度・オフセットを掛けた後の値 |
| `wallAt` | **実時刻**（epoch ms）。突き合わせの保険 |

**編集で使うのは `at`。** 動画の中の位置はシナリオ時刻で決まる。`wallAt` は
「録画ツール側の時計とどれだけずれているか」を確かめるためのもの。

型は `src/utils/replayEventLog.ts` の `ReplayEvent`（判別可能な共用体）が単一情報源。
**値の一覧はそちらを正とする** —— 下の表は意味を説明するもので、フィールドの全列挙ではない。

## 4. イベントの種類

### 読み上げ

| `type` | 意味 |
|---|---|
| `speechStart` | 読み上げ 1 本の始まり |
| `speechEnd` | その終わり（割り込まれて途中で終わった場合も含む） |
| `speechChunk` | チャンクの再生予約 |

`speechStart` の主なフィールド:

| | |
|---|---|
| `speechId` | この読み上げの識別子。`speechEnd` / `speechChunk` が同じ値で指す |
| `channel` | `'eew'`（緊急地震速報の列）か `'other'`（それ以外）。列が別で、割り込みの規則も違う |
| `topic` | 読み上げの主題（非 EEW のみ。`quake:<鍵>` / `tsunami` / `lpgm:<eventId>` 等） |
| `eewKey` | 緊急地震速報の地震を指す鍵（EEW のみ） |
| `subject` | 画面の追従が向いている対象（どのカードを見せているか）。`topic` と重なることが多いが別の軸で、渡されていなければ `null` |
| `telegram` | **どの電文のものか**（→ §5） |
| `text` | 読み上げた文。2000 字で切り、切ったら `textTruncated` が真・`textLength` に元の長さ |

`speechEnd`:

| | |
|---|---|
| `spoke` | **1 音でも実際に鳴ったか。** 偽になるのは合成が 1 つも成功しなかった場合と、鳴り始める前に取り下げた場合 |
| `durationMs` | 開始からの経過（実時刻で測る） |

**「終わった」と「鳴った」は別物。** VOICEVOX が起動していない端末でも読み上げは正常終了するので、
`spoke` を見ないと無音の区間を「声が入っている」と読む。

`speechChunk` の `startAt` は **AudioContext の時間軸（秒）**で、`at` とは基準が違う。
2 番目以降のチャンクでは未来を指す（予約であって鳴り始めではない）。`index` は
**連番になるとは限らない**（合成に失敗したチャンクは飛ぶ）。

### 通知音

`type: 'sound'`。`sound` に種別（`eew` / `tsunami` / `kyoshin` 等）、`telegram` に持ち主。

編集側が「音の上で切っているのは声か通知音か」を判定するのに使う。**強震モニタの検知音は
電文と無関係**なので `telegram` が空になる（それが正しい）。

**設定タブの通知音テストも同じ経路を通り、`telegram` は空になる。** `playAlertSound` は
電文処理の外（テストボタンの押下）から直接呼ばれても同じ関数を通るため、kyoshin に限らず
`eew` / `tsunami` 等どの種別のボタンを試しても `telegram: null` で記録される（下の「読み上げ」
節にある設定タブの試聴と同じ扱い）。

### 電文の受信

`type: 'telegram'`。

| | |
|---|---|
| `kind` | 種別（`quake` / `tsunami` / `eew` / `lpgm` / `nankai` / …） |
| `infoType` | 電文が名乗る情報種別（「震度速報」「津波観測に関する情報」等） |
| `eventId` / `serial` | 識別子と報番号。持たない種別・持たない報では `null` |
| `cancelled` | 取消の電文か |
| `skipped` | **画面・音へ回らなかった理由**（回ったなら `null`） |

`skipped` の値:

| 値 | 意味 |
|---|---|
| `heldBack` | カードが中身を採らなかった（音・読み上げ・タイトル・タブ移動が起きない） |
| `staleSerial` | 緊急地震速報の古い報（受け入れ済みの報番号より前） |
| `testReport` | 試験報・訓練報 |
| `notDispatched` | 音も読み上げも起こさないと決めている——**種別まるごと**（地震・津波に関するお知らせ）、**種別内の特定の値**（長周期地震動観測情報の取消・階級 0。画面（長周期一覧・バッジ）には反映される）、**取得経路単位**（「もっと見る」による地震カード履歴の追加読み込みは、南海トラフ臨時情報等の帯を電文の中身を問わず一切画面へ反映しない。理由は下記「もっと見る」の段落）の 3 通りを指す |
| `silentReplayInit` | リプレイ開始時の「窓の手前」を作るサイレント注入。画面には反映されるが音・読み上げには回らない（→ `docs/spec/settings-pwa-spec.md` §6「初期状態（24 時間）では足りないものを、履歴の遡り（7 日）から補う」） |
| `notApplied` | 反映されなかった（古い報・重複配信・期限切れで棄却された）。**`notDispatched` との違いは「意図した除外か」**——こちらは受信側の事情（古さ・重複）で棄却され、状態も動かない |

**「届いたのに読まれなかった」がここで分かる。** これが無いと、編集側は電文の一覧と
読み上げの一覧を突き合わせて欠けを推測するしかない。

**サイレント注入・棄却も `telegram` として記録する。** リプレイ開始時に窓の手前（24 時間分の
初期状態）を作る電文は、そもそも `onLiveEvent` を呼ばない設計（`silentReplayInit`）なので、
記録しないと録画ツールは再生開始直後の状態を電文一覧から追えない。同様に、古い報・重複配信で
棄却された電文（`notApplied`）も記録する——サイレントかどうかとは独立の理由。

**ただし「地震・津波に関するお知らせ」（`quakeNotice`）はこの原則の唯一の例外。** この種別は
元から音・読み上げを一切起こさないと決めており（`notDispatched`。上表）、その記録自体も
「サイレント復元でないときだけ」行う設計になっている——サイレント復元では `notDispatched` も
含め `telegram` イベントが**1 件も出ない**。理由は、無条件に記録すると最大 7 日前の履歴上の
お知らせが、起動・API キー変更・リプレイの往復のたびに「いま届いた」電文としてログへ混入する
ため（他の種別のように「反映されたか」で `silentReplayInit`/`notApplied` を出し分ける形には
できない——この種別は反映の有無を問わず記録が要らないと決めているので、`silent` の真偽だけで
記録の要否そのものが決まる）。録画ツールの側で「サイレント復元中の `quakeNotice` が電文一覧に
現れない」ことを異常と誤診断しないこと。

**「もっと見る」（地震カード履歴の追加読み込み）は、南海トラフ臨時情報・南海トラフ関連解説
情報・後発地震注意情報・地震回数に関する情報を画面へ一切反映しない。** これらは画面上部の
特別情報バナー（以下「帯」。→ `architecture-spec.md` §4「特別情報バナー」）として表示される
種別で、起動時の履歴復元（24 時間・7 日。→ `settings-pwa-spec.md` §6）とは異なり、この経路は
さらに古い日を遡って既存カードの厚みを増やすためのものである。

古い日にあった帯の電文を反映すると、現在表示中の最新の帯情報を古い内容で上書きしてしまう
（帯の各 `applyXxx` は無条件に上書きする実装のため）。これが反映しない理由である。

**反映しない場合でも、電文が届いた事実は `notDispatched` として記録する**（届いたことと
反映しなかったことの両方が録画ツール側で分かるようにするため）。この場合の除外理由は電文の
内容（取消・階級等）ではなく「この取得経路自体が反映しないと決めている」ことだが、
`notApplied`（受信側の事情による棄却）にも `silentReplayInit`（画面には反映される）にも
当てはまらないため `notDispatched` へ含める。

**lpgm（長周期地震動観測情報）だけは対象外**——地震カードに紐づく情報で「もっと見る」が
増やすカードの一部なので、従来どおり画面へ反映し、キュー経路と同じ `lpgmNotifiable` の
判定で記録する。**quakeNotice は「唯一の例外」（上記）と同じ理由で記録しない。**

### 画面の変化

| `type` | 意味 |
|---|---|
| `tab` | 表示中のタブが**実際に**変わった（`tab` / `prevTab`）。同じタブへの要求は出ない。`prevTab` は型上 `string \| null` だが、既定タブで初期化されるため実際には null にならない |
| `alert` | 警報・注意報の状態が動いた |
| `overlay` | 画面の一部が**実際に**開いた・閉じた。`tab` と同じく、既に開いている（閉じている）ものへの同じ要求は出ない |

`alert` は `category`（`eew` / `tsunami`）と `change` の組:

| `change` | 意味 |
|---|---|
| `issued` | 新規の発表 |
| `upgraded` | 段階が上がった（予報 → 警報、津波注意報 → 津波警報 等） |
| `downgraded` | 段階が下がった（全部は解けていない）。**津波だけ** —— 緊急地震速報の区分は予報から警報へ上がるだけで下がらない |
| `lifted` | 解除 |
| `retracted` | 取消（誤報） |
| `expired` | 時間切れ（自動解除・有効期限） |

**続報そのものは `alert` に出ない** —— 秒ごとに届くので、出すと「状態が動いた」という問いに
答えられなくなる。続報の到来は `telegram` の側に出る。

**EEW の `retracted`（誤報取消）と `expired`（自動解除）は重複配信の扱いが違う。** P2PQuake WS と
Yahoo hypoInfo の両方から同一 EEW の消滅を検出すると、同じ状態遷移に対して複数回キャンセルが
届くことがある（音・読み上げの二重鳴り防止と同じ現象）。`retracted` は重複を問わず記録する
（ブラウザ通知と同じ基準——`hadKey=false` でも「自動解除済みの後に遅れて届いた本物の誤報取消」
がありうるため、訂正情報を握り潰さない側へ倒す）。**`expired` は初回（`hadKey=true` 相当）だけ
記録する**——最終報を複数受信すると複数キューに積まれるため、無条件に記録すると同じ自動解除が
二重・三重に並ぶ。

**区域ごとの等級変化（津波の一部解除・一部引き上げ）も出ない。** `alert` が答えるのは
「全体の等級が動いたか」で、`grade` もいちばん重い等級を指す。一部だけが動いた報では
その値が変わらないため、ここへ混ぜると「動いていない変化」として並ぶ。画面と読み上げには
出ている（気象庁は一部解除でも区域を電文から消さず、等級の降格として載せる）ので、
**そこを区間の切れ目に使いたい場合はこのログだけでは足りない。**

`overlay` の対象は `distribution`（推計震度分布図のモード）・`unreceived`（震度を入手していない
地点の一覧）・`lpgm`（長周期地震動の一覧）・`telegramText`（気象庁が書いた文）・
`specialInfoPanel`（特別情報のためのパネル展開）・`actionChecklist`（行動チェックリストの帯）。
`open` が真偽、`reason` に短い理由（「震度分布のボタン」「推計震度分布図の受信」等）。

**手で押した開閉も出る。** 自動で開いたものだけではない。

**`telegramText` は `subject` で区別すること。** この種別だけは 6 箇所（地震カードの「気象庁
からの補足」・南海トラフ臨時情報・後発地震注意情報・関連解説情報・地震回数・津波のコメント欄）
が同じ `overlay: 'telegramText'` を共有しているため、`subject`（`'lpgm:<eventId>'` / `'nankai'` /
`'kohatsu'` / `'nankaiCommentary'` / `'earthquakeCount'` / `'tsunamiComment'`）が無いと、
どの表示が開いたか区別できない。

**`distribution` / `unreceived` / `lpgm` にも `subject` が付く**（地震カードの `eventKey`、
`lpgm` だけ電文の `eventId`）。呼び出し元は 1 つ（`applyQuakeOverlay`）だが、群発地震で
複数の地震について続けて開閉したとき、`overlay` 種別だけでは「同じ地震の開閉」か
「別の地震への切り替え」かを区別できないため。

**`specialInfoPanel` / `actionChecklist` だけは `subject` が常に `null`。** どちらも
特定の地震・電文へは紐づかない画面全体の状態（特別情報のパネル・行動チェックリストの帯）。

**前の 3 つ（`distribution` / `unreceived` / `lpgm`）は排他で、切り替えると 2 件出る** ——
閉じた分と開いた分。1 件に畳むと、何が引っ込んだのかが読めない。

### 再生の制御

| `type` | 意味 |
|---|---|
| `control` | `action` が `start` / `stop`。`start` には `target`（ISO 8601）と `offset`(ms) |
| `fetch` | 電文の取得。`phase` が `start` / `done` / `error`、`target` が `main` / `prefetch`、失敗は `message` |

**シナリオ時刻のジャンプは `control` で起きる**（オフセットを変える箇所は開始と停止の 2 つだけ）。

`fetch` の `done` は成否によらず出る（終わりの印）。失敗は `error` が別に出る。

**ただし出るのは、いま再生しているぶんだけ。** アーカイブの取得は途中で止められないので、
停止して別の日時で開き直したあとに古い取得が解決することがある。その回は `done` も `error` も
出さない —— 出すと、まだ取得中なのに「終わった」が並び、外からは待ちを閉じてよいと読める
（`fetching()` も同じ規律で、古い側では下ろさない）。**`start` の次に `done` が来ない区間が
ありうる**ので、`done` だけで待ちを組まず `control` の `stop` も見ること。
**`start(iso)` が範囲外の時刻で弾かれたときも `error` が出る** —— 出ないと、外からは
「開始したのに何も起きない」としか見えない。

## 5. 読み上げの持ち主を辿る

`speechStart` と `sound` と `alert` は `telegram` を持つ。中身:

| | |
|---|---|
| `seq` | その電文の `telegram` イベントの `seq` |
| `kind` / `infoType` / `eventId` / `serial` | 電文が名乗っているもの（`telegram` イベントと同じ値） |

**`seq` で辿れるうえ、中身も冗長に持っている。** 参照先の `telegram` イベントが
バッファから溢れても、種別と識別子だけは読める。

```js
// この読み上げは採用した電文のものか
function isAdopted(speechStart, adoptedTelegramSeqs) {
  const t = speechStart.telegram
  if (!t) return false          // 持ち主を引けなかった読み上げ（下記）
  return adoptedTelegramSeqs.has(t.seq)
}
```

**`telegram` が `null` になる形は、イベントの種類で意味が違う。**

| 種類 | `null` のとき |
|---|---|
| `speechStart` | **緊急地震速報の予想値の読み上げで、鍵から持ち主を引けなかったとき。** あの発話は「値が落ち着くまで待つ」タイマーから始まるので受信処理の文脈が残っておらず、地震の鍵で引き直している。引ければ埋まる |
| `sound` | **電文と無関係に鳴る音**（強震モニタの揺れ検知・その候補・設定タブの通知音テスト）。空が正しい状態で、異常ではない |
| `alert` | 電文から起こすので、通常は埋まる |

**`speechStart` の `null` だけが「引けなかった」を意味する。** `sound` の `null` を同じ
ものとして扱うと、揺れ検知の音が毎回「持ち主不明の異常」に見える。

**紐づけの粒度は「予約した瞬間の電文」。** 読み上げは通知音との間（長いもので約 2.8 秒。
実際の長さは鳴らした音の種別で決まる）や順番待ちを経てから鳴るので、鳴っている時刻に
届いていた電文とは限らない。

## 6. 出していないもの

**高頻度で動くものは出さない。** バッファが埋まるため。

- 地図の再描画・カメラの追従
- リアルタイム震度の更新（毎秒）
- 緊急地震速報の予報円（100ms ごと）
- 画面の時計

**`telegram` に出ない電文もある。** 受信の入口より手前で落としているもののうち、
§4 の `skipped` に挙げた 4 つは記録するが、それ以外（配信元が送ってこなかった電文・
接続していない期間の電文）は当然ながら出ない。

**設定タブの試聴（声の確認）は `speech*` に出ない。** 電文の読み上げとは別の経路で鳴らして
いるため。**そのあいだ `speaking()` は真を返すのに、対応する `speechStart` が無い**ので、
音の有無だけで区間を切っていると理由の分からない空白になる。録画の最中に人が設定タブの
試聴を押すことは想定していないが、押せてしまう以上ここに書いておく。

## 7. 注意

**記録は常時行っている。** 録画モードの設定とは独立していて、切り替えても止まらない。
1 イベントは小さなオブジェクトで、溜まるのは汲む側が止まったときだけ。

**記録の失敗で本体は止まらない**（表への出方は §2「取りこぼしの見分け方」のとおり）。
握って続行する設計で、握ったことはブラウザのコンソールへ残る。

**再生を開始し直してもイベントログは消えない。** 時間軸が変わったことは `control` の
`start` で分かるので、その前後を自分で切り分けること。
