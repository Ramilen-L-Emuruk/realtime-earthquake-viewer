# 層B 律速切り分け — 検証観点まとめ

> 関連: 計画書 [webgl-rendering-migration-plan.md](webgl-rendering-migration-plan.md) §6 ／ 実行手順 [poc/README.md](../poc/README.md)
> 対象: `worktree/feat/webgl-poc` の PoC による実機（Surface Go 2）計測
> 位置づけ: 「実機で**何を見て・どう判断し・次に何を決めるか**」を一枚に集約する。手順そのものは poc/README.md。
>
> **現状（2026-07-25 実機3回計測・§1 の問いは決着）**: **律速に到達しない**。塗り面積を 4.0 倍
> （0.98M→3.91M px）・線幅を 10 倍（1.2→12）に上げ、両者を重ねた `overload` まで負荷を積んでも
> **全 19 計測が p95 16.9〜17.0ms・fps 58〜60** で vsync 天井（16.7ms）を破らなかった。
> フィルレート律速でも CPU/頂点律速でもない。**間引き廃止は描画コストの観点で青信号**。
> 1・2回目の「判定不成立」は (a) 飽和した baseline から負荷を**下げて**振っていた
> (b) zoom の劣化 33.3ms が**タイル初回読み込みの交絡**だった（3回目の `baseline-warm` 16.9ms で確定）
> の二重の誤りによる。数値・撤回した主張・経緯は末尾「付録: 実機結果」。
> **残る論点は層 B の外**: 検証項目2 の Leaflet 比較・**項目5 非加算合成（最難関）**・毎秒更新・
> EEW 複合負荷・真の実行時メモリ。

## 1. この検証が決める唯一の問い

層 B（フル解像度の線/面の描画負荷）の律速が
- **CPU（頂点処理・JS）** なのか
- **GPU フィルレート（画面を塗るピクセル速度）** なのか

を確定する。これが **MapLibre 一本化の GO/NO-GO と分岐**を決める。ここを外すと全面リライトの投資判断を誤る。

## 2. 律速判定の観点（3軸の反応で読む）

`__runLayerBSuite('surface-go2')` の各 run を **パン時の p95（フレーム時間の95%tile）** で横断比較する。

| run | baseline から変えた軸 | 期待する読み |
|---|---|---|
| `baseline` | —（full / lw1.2 / 実効DPR / 点on） | 基準。static / pan / zoom の3局面 |
| `dpr-1.0` / `dpr-0.75` | 描画バッファ解像度を下げる | **改善大 → フィルレート律速** |
| `verts-thin` | 頂点 31,646 → 9,874 | **改善 → CPU/頂点律速** ／ 不変 → フィルレート |
| `fill-lw4` | 線幅 1.2 → 4（塗り面積↑） | **悪化 → フィルレート律速** |
| `points-off` | 観測点 circle を消す | 点の描画寄与の切り分け |

**判定は単軸でなく整合で読む:**
- フィルレート律速の型 = 「DPR↓で改善 ＋ 線幅↑で悪化 ＋ 頂点↓に鈍感」
- CPU/頂点律速の型 = 「頂点↓で改善 ＋ DPRに鈍感 ＋ 線幅↑に鈍感」
- 両方効く中間型なら、**実効 DPR(1.5) での支配項**がどちらかを p95 の変化量の大小で決める。
- **飽和の型（＝判定不成立）= 「どの軸を振っても p95 が同値」**。baseline が既に vsync 上限
  （60Hz なら 16.7ms）に張り付いている場合、天井より上の余裕は原理的に測れないため、
  p95 は軸ではなく vsync を測っていることになる。どちらの律速型にも当てはめてはならない。
  → 2026-07-25 実機は **pan・zoom 双方**がこの型だった（下記「実機結果」）。
  - **【重要】飽和は「律速が無い」ことの証明ではない。検出に失敗しただけ**。「余裕で 60fps」と
    「かろうじて 60fps」を区別できないため、headroom（残り余力）は未知のまま残る。計画書 §8 は
    フィルレート律速を「GO/NO-GO を分ける前提条件」と位置づけているが、飽和した指標では
    この条件を**クリアできない**（否定も肯定もできない）。
  - **正しい対処は2つ**: ①**負荷を上げる方向**へ振って天井を破る（DPR を 2.0 へ上げる・線幅を
    大きくする・CPU スロットルを掛ける）②**vsync にクランプされない指標**を使う（GPU フレーム時間を
    Performance の GPU トラック / `chrome://tracing` で直接見る）。どちらも計画書 §6 測定方法が
    既に指定している。**負荷を下げる方向に振るのは無意味**（天井下での比較は何も測っていない）。
  - **交絡に注意**: 飽和していると、軸以外の要因（初回タイル読み込み等）の差だけが数値に出て
    軸の反応に見えてしまう。**負荷を増やした軸が「改善」したら交絡を疑う**（2026-07-25 の実例）。

## 3. 実機で観察する指標の観点

- **主指標 = フレーム時間 p95**。体感（毎フレーム落ちるか）を直接表す。FPS 平均は補助（60 に張り付くか届かないか）。
  - **vsync 上限に注意**: p95 が 16.7ms 付近なら、それは「描画コスト 16.7ms」ではなく「vsync 待ちで
    それ以上速く描けない」の意。この状態では軸を振っても数値が動かず**差の検出力がゼロ**になる。
    軸比較をする前に、まず baseline が天井を破っているか（p95 > 16.7ms か）を確認する。
  - **`max` は判定に使わない**: 単発のタイル読み込み・GC・`pixelRatio` 変更に伴う描画バッファ再確保が
    そのまま乗るため、軸と無関係に上下する。2026-07-25 実機でも DPR を下げた run の方が max が
    悪化する（42.5ms）非単調が出た。傾向は p95 と longtask で読む。
- **longtask（>50ms）件数・最大**: CPU 側の詰まり。フィルレート律速なら longtask が少なくても p95 が悪化する（GPU 待ち）— この乖離自体が判定材料。
- **メモリ**: RAM 4GB 構成での tab キル・context lost 誘因。Leaflet 版との差を意識する。
- **WebGL context lost / 描画崩れ**: 左下 `ERROR:` 表示・地図が黒くなる等。防災用途では「地震の瞬間に地図消失」が最悪の障害モードなので、出たら必ず記録する。
- **局面**: static / pan / zoom の3つ。WebGL は操作中に毎フレーム全画面を描き直すため、律速は pan/zoom で顕在化し static では出にくい。
  - **ズームは「初訪問のズームレベル」で初回コストを払う**（タイル取得＋デコード＋ジオメトリ再タイル化＋
    頂点バッファ生成）。スイート冒頭の zoom 計測にだけこれが乗ると、後続 run との差が軸の反応に
    見えてしまう（2026-07-25 の交絡）。**計測前にウォームアップパスを置く**か、末尾で baseline を
    再計測して対照を取る。

## 4. 判定後の意思決定の観点（分岐）

### A. フィルレート律速だった場合
- **間引き廃止は保留**: 形状保存の間引きを外しても増えるのは頂点数で、塗り面積はほぼ不変 → フィルレートには効かない。フル解像度化という当初目的が効果対象外になる。
- **DPR 抑制（`pixelRatio`）が本命**: 塗り面積は DPR² に比例。実効 1.5 → 1.0 で塗り面積は半分以下。精細さ（ぼやけ）とのトレードオフを実機で確認する。
- **一本化の是非は"手段"の観点で再判断**: MapLibre は `pixelRatio` で描画解像度を CSS 解像度から切り離せるが、現行 Leaflet+SVG は DPR 抑制余地がほぼ無い。「`pixelRatio` 抑制を得るために全面リライトのコストが見合うか」で決める（フィルレート律速＝自動 NO-GO ではない）。

### B. CPU/頂点律速だった場合
- **MapLibre 化 GO**。間引きを廃してフル解像度化しても GPU で軽くなる見込み。PoC 項目2以降へ進む。

### C. 飽和（どの軸も動かない）だった場合 — 2026-07-25 実機は pan・zoom 双方がこれ
当初この分岐は想定していなかったが、実機ではこれが出た。**「律速が無い」ではなく「この計測では
検出できなかった」**と読む（§2 の飽和の型）。
- **分かるのは「現行の負荷では天井を超えない」ことだけ**。フル解像度・実効 DPR のまま 60fps で
  回っているのは事実。ただし**残り余力（headroom）は不明**なので、「軽い」とは言えず
  「重くない」までしか言えない。
- **間引き廃止の障害は、少なくとも現行負荷では見えていない**（上記の限界付き）。
- **一本化の是非には中立**。一本化の根拠にも反証にも使えない。判断は残る検証項目
  （非加算合成・毎秒更新・複合負荷）へ持ち越す。
- **【誤りやすい点】「60fps 同着だから Leaflet と同等」とは言えない**。Leaflet の pan は CSS transform の
  コンポジタ合成のみで再ペイントがほぼ走らないのに対し、MapLibre は毎フレーム全ビューポートを
  塗り直す（計画書 §2.4・§8）。同じ 60fps でも仕事量は桁違いで、差はファンレス機の熱・電力、
  そして**複合負荷（項目7: flyTo＋予報円＋毎秒更新）に回せる余裕**として現れる。
  検証項目2 は Leaflet 側を実測しない限り閉じられない。
- **やるべきこと**: ①負荷を上げて天井を破る ②GPU フレーム時間を直接測る ③メモリを測る
  ④Leaflet 比較を別途行う。いずれも計画書 §6 測定方法が既に指定している。

#### C の顛末（2026-07-25 3回目で決着）

**①を実行して決着した。** 負荷を上げても天井を破れなかったため、飽和は「測定不能」から
**「余力の上界を示す積極的な結果」へ転じた**:

- 塗り面積 **4.0 倍**（0.98M→3.91M px）・線幅 **10 倍**（1.2→12）・両者同時（`overload`）でも
  p95 16.9〜17.0ms を維持 → **実配置の 1.78 倍の塗り面積を線幅 10 倍と同時に背負っても余裕がある**。
- **飽和したまま負荷を上げられたこと自体が答えになる**。「破断点を探す」必要はなく、
  「実配置に余裕があるか」に答えが出た時点で判断材料は揃う。
- **②GPU フレーム時間の必要性も下がった**。rAF が vsync でクランプされるから GPU 時間が要る、
  という理屈だったが、余力を実測で上から抑えたためこれが代替になる。
- ③メモリは `jsHeapMB` を追加して取得（38〜107MB で振動・暴走なし・context lost なし）。
  ただし JS ヒープのみなのでタスクマネージャ併用は引き続き必要。
- ④**Leaflet 比較は未実施のまま**。検証項目2 はこれ無しに閉じられない（下記「4.」も参照）。

**教訓**: 飽和を見たら「測れなかった」で止めず、**負荷を上げる方向に振り直す**。
上げても動かなければ、それは余力の下限を保証する強い結果になる。

## 5. GO 後に残る検証観点（計画書 §6 項目2–7）

律速で GO が出ても、一本化には次を順に潰す:
- **フル解像度の軽さ**: 現行 Leaflet 比で pan/zoom が同等以上に軽いか。
- **カメラ操作**: flyTo / パン / ズームの滑らかさ。
- **当たり判定**: 活断層クリックのポップアップが `queryRenderedFeatures` で線近傍（現行 tolerance 相当）に開くか。
- ~~**非加算合成（最難関）**: `KyoshinSubThreshold` の ①同レベル内は重なっても濃くならない ②レベル間は濃くなる、の二層を再現できるか。~~ → **【2026-07-25 クリア】** カスタムレイヤーの**オフスクリーン FBO 二層合成**（レベルごとに不透明描画 → opacity で over 合成）で現行と等価に再現。開発機で解析期待値と±1一致、**実機で 59〜60fps・longtask 0・追加コストは標準 circle 比で測定限界以下**。詳細は計画書 §6 結果記録（検証項目5）／[webgl-poc-review-3c2ddaf.md](webgl-poc-review-3c2ddaf.md)。
- **毎秒更新**: index 更新を feature-state / `setData` で軽く回せるか。WebGL では「毎秒1回の全画面再描画」に化けるため、フィルレート律速機で毎秒カクつかないか。
- **EEW 複合負荷**: flyTo ＋ 予報円アニメ ＋ 毎秒更新が同時に走る最悪局面（設定タブの EEW テストで再現）。

## 6. 横断リスクの観点

- **context lost からの復帰**: MapLibre の自動リストア可否・失敗時フォールバック（再初期化 / リロード誘導）。
- **実行時メモリ（4GB）**: WebGL バッファ・グリフアトラスで Leaflet 比増。バンドルサイズ（転送量）とは別軸。
- **テキスト描画**: 地方 / 県 / 区域ラベルは現状 DOM。MapLibre で GPU 描画するには日本語グリフ PBF の自前ホストが要る。少数は DOM Marker で妥協可、数千点（`IntensityPoints`）は symbol レイヤー必須。
- **バンドル / PWA 初回ロード**: MapLibre は Leaflet より重い（実行時は軽い想定・初回は要計測）。
- **2 バリアント**: 地図描画はバリアント非依存。PoC・移行は実質1系統で足りる。

## 7. 最終 GO/NO-GO の観点

- **一本化 GO の必要条件**: 律速が CPU/頂点 ＋ 実機でフル解像度が現行以上に軽い ＋ 非加算合成が再現でき ＋ context lost / メモリが許容範囲。
- **転換（NO-GO 寄り）**: フィルレート律速 → DPR 抑制路線。一本化は「`pixelRatio` を得る手段」としてコスト対効果で再評価する。

## 付録: 実機結果（2026-07-25 Surface Go 2・3回計測）

- **環境**: Surface Go 2 実機（Edge）、viewport 1272×768・**DPR 1.5**・**60Hz**、開発機の `dev:poc` へ LAN 接続。
- **描画状態**: 活断層フル解像度 31,646 頂点（間引き後は 9,874）、観測点 1,458 点（`TARGET_POINTS=1725` 狙いのサンプリング実測値）。
- **証跡**: 1回目 `perf-2026-07-25T04-0[6-8]-*`（8件・軸は pan のみ）／2回目 `perf-2026-07-25T04-4[6-8]-*`（13件・zoom 拡張）／**3回目 `perf-2026-07-25T10-5*`（19件・負荷上げ方向＋ウォームアップ＋開始zoom固定＋warm対照）**。各10秒。
- **結論は3回目で出た**（下記「3回目」）。1・2回目は判定不成立で、その経緯と撤回した主張も記録として残す。

### 1回目（8件・軸は pan のみ）

| baseline | pan | **16.9** | 59.9 | 33.3 | 0 | 1.5 | 2.20M | 31,646 | 1.2 |
| baseline | zoom | **33.3** | 54.2 | 83.1 | **6 / 85** | 1.5 | 2.20M | 31,646 | 1.2 |
| dpr-1.0 | pan | **16.9** | 59.7 | 42.5 | 0 | 1.0 | 0.98M | 31,646 | 1.2 |
| dpr-0.75 | pan | **16.9** | 59.9 | 17.2 | 0 | 0.75 | 0.55M | 31,646 | 1.2 |
| verts-thin | pan | **16.9** | 59.8 | 33.8 | 0 | 1.5 | 2.20M | 9,874 | 1.2 |

zoom だけ 33.3ms で天井を破っていたため、当初これを「唯一の信号」と読んだ。**この読みは 2回目で覆る。**

### 2回目（13件・各軸を pan/zoom 両方で計測）

pan は1回目と完全に一致（全軸 16.9ms・longtask 0）。**zoom の行だけ抜粋**:

| run | phase | p95 | fps | max | longtask 件/最大/合計 | pr | 頂点 | 線幅 | 実行順 |
|---|---|---|---|---|---|---|---|---|---|
| baseline | zoom | **33.3** | 55.5 | 66.7 | **3 / 53 / 156** | 1.5 | 31,646 | 1.2 | 3番目 |
| dpr-1.0 | zoom | **16.9** | 58.2 | 84.1 | 2 / 91 / 180 | 1.0 | 31,646 | 1.2 | 5番目 |
| dpr-0.75 | zoom | **16.9** | 59.3 | 49.9 | 1 / 62 / 62 | 0.75 | 31,646 | 1.2 | 7番目 |
| verts-thin | zoom | **16.9** | 59.7 | 33.2 | **0** | 1.5 | 9,874 | 1.2 | 9番目 |
| fill-lw4 | zoom | **16.9** | 59.7 | 33.4 | **0** | 1.5 | 31,646 | **4** | 11番目 |
| points-off | zoom | **16.9** | 59.5 | 33.4 | **0** | 1.5 | 31,646 | 1.2 | 13番目 |

### 判定: zoom の劣化はウォームアップ交絡だった（軸の反応ではない）

**決定的な矛盾**: `fill-lw4` は線幅 1.2→4 で**塗り面積を 3.3 倍に増やした**のに、baseline zoom の
33.3ms から **16.9ms へ改善**している。GPU に塗らせるピクセルを 3 倍にして速くなることは
物理的にあり得ない。負荷を減らす `points-off` と負荷を増やす `fill-lw4` が**同じ 16.9ms に着地**する
以上、33.3 → 16.9 の差は軸が作ったものではない。

**正体は初回タイル読み込み**。longtask を実行順に並べると **3 → 2 → 1 → 0 → 0 → 0** と単調減衰する
（上表「実行順」列）。baseline zoom はスイート中で最初に z4〜7 を訪れる計測で、その時点で GEBCO
ラスタタイルは未キャッシュ・ジオメトリもそのズームレベルで未タイル化。初回だけ「タイル取得＋
デコード＋再タイル化＋頂点バッファ生成」を丸ごと払っている。以降は温まった状態の再利用。
DPR を変えた 5・7 番目に longtask が残るのも、`pixelRatio` 変更が描画バッファ再確保を強制するため
筋が通る。

**結論: pan・zoom とも全軸が vsync 上限に飽和**しており、**律速切り分けは不成立**。

| 「pan が天井なら **Leaflet に負ける余地も無い**（最良でも同着）」 | Leaflet の pan は CSS transform のコンポジタ合成のみで再ペイントがほぼ走らない（計画書 §2.4・§8）。MapLibre は毎フレーム 2.2M px を塗り直す。**同じ 60fps でも仕事量は桁違い** |
| 「検証項目2 は pan について Leaflet 側を測らずとも**満たされる**」 | 上記より不成立。飽和した指標は「余裕で 60fps」と「かろうじて 60fps」を区別できない。差はファンレス機の熱・電力、そして**複合負荷（項目7）に回せる余裕**として出る |
| 「層 B の当初懸念は pan については**否定された**」 | 「現行負荷では天井を超えない」までしか言えない。**飽和は律速の不在を証明しない** |
| 「計測器の健全性は確認できた（zoom で劣化を検出しているので pan は本当に軽い）」 | 検出していたのはウォームアップで、軸に対する感度の証明にはならない |

### 計測設計の不備（計画書 §6 測定方法との対照）

計画書は既に正しい道具を指定していたが、今回の PoC は使っていなかった:

| 計画書の指定 | 今回 |
|---|---|
| DPR を 1.0 / 1.5 / **2.0** で振る | 1.5 / 1.0 / **0.75** — **下げる方向のみ**。天井下の比較は何も測っていない |
| CPU スロットル 1× / 2× / 4× を軸に振る | 未実施 |
| **GPU フレーム時間を直接見る**（Performance の GPU トラック・`chrome://tracing`） | 未実施。rAF 間隔のみ＝構造的に vsync でクランプされる |
| 比較対象は現行実装（Leaflet） | 未実施 |
| 実機ではメモリも測る（`performance.memory`・タスクマネージャ） | 未実施。`measure.ts` に項目が無い |

**`performance.memory` は JS ヒープのみ**で WebGL バッファ・テクスチャを含まないため、§6 の言うとおり
タスクマネージャ併用が要る（§8「実行時メモリ」）。

### 有効な新規知見: 初訪問ズームレベルのウォームアップコスト

交絡そのものは計測の失敗だが、**現象は実装上の論点として有効**。初訪問のズームレベルで 50〜90ms の
longtask が出る。これは MapLibre 固有ではない（GEBCO ラスタは Leaflet 版も同じものを引く）が、
WebGL 版ではジオメトリ再タイル化が上乗せされる。

**EEW の `flyTo` は「初訪問ズームレベルへ飛ぶ」動作**なので、この初回コストが最悪局面で出る懸念がある。
→ 検証項目7（EEW 複合負荷）で見るべき具体的観点として扱う。

#### 天井は破れなかった — 意図的に上げても

| 軸 | 振った範囲 | 倍率 |
|---|---|---|
| 塗り面積 | 0.98M → **3.91M px** | **4.0 倍** |

**全 19 計測が p95 16.9〜17.0ms。** これは 1・2回目の「飽和」より強い主張になる。
前 2 回は天井に張り付いた baseline から負荷を**下げて**動かなかっただけ（＝何も測っていない）。
今回は**上げて**動かなかったため、**「実配置の 1.78 倍の塗り面積を線幅 10 倍と同時に背負っても
余力がある」という上界の言明**が得られた。

#### 決着した結論

- **§1 の問い（フィルレート律速 か CPU/頂点律速 か）はどちらでもない。律速に到達しない。**
- **間引き廃止は描画コストの観点で青信号**。フル 31,646 頂点と間引き後 9,874 頂点で p95 の差が測定不能。
- **GPU フレーム時間の必要性が下がった**。`overload` で余力を実測で上から抑えたのが代替になる。
- **メモリ・安定性**: `jsHeapMB` 38〜107MB で振動（GC）・暴走なし・**context lost なし**。
  ただし JS ヒープのみのためタスクマネージャ併用は引き続き必要。

#### 残った小さな観察（律速ではない）

- **zoom だけ max 33〜50ms・fps 58〜59.6 が全 run で一定**（pan は max 約 17ms）。p95 は 16.9ms の
  ままなので 5% 未満のフレーム。軸依存でないため、連続スイープが整数ズームを跨ぐ際の
  タイルセット入れ替えが濃厚。
- **単発の longtask**（`dpr-2.0` zoom 97ms・max 100.2ms、`fill-lw12` pan 86ms）は軸と単調な関係が
  無く、`pixelRatio` 変更に伴う描画バッファ再確保が乗った公算。p50/p95 は無傷。
