## 【対応確認】フレーム計測の追加とグリフキャッシュの罠

`measure.ts` の `summarizeFrames` を `export` し、`measureLabelLayer` で rAF フレーム間隔を
収集して `frame` として結果に含める形。前レビューの提案どおりで、既存関数の再利用も適切。
`elapsedMs` を残しつつ「グリフ生成コストの指標として無情報」とコメントで明記した判断も良い。

**グリフキャッシュがページを閉じるまで消えない**ため、同一ページで `__runLabelZoomSuite` を
2 回目以降実行すると `glyphsGenerated` が動かず計測が無効化される——この発見は有用で、
README とコメントの両方に書いたのは適切。

（レビュー側は毎回 `browser_navigate` でリロードしていたため踏まずに済んでいたが、
それは意識的な回避ではなく偶然だった。明文化された価値は大きい。）

## 【HIGH・事実誤認】「レビュー環境＝実際の Chrome」は誤り

[`label.ts`](../poc/label.ts) のコメントおよび計画書 §6 に、以下の趣旨の記述がある:

> このPoCをPlaywright/Chromium(headless)で動かす開発機では〔…〕ノイズフロアが最大18.7ms程度あり
> （**レビュー環境=実際のChrome・vsync6.1ms**では17.6msのスパイクが検出された）

> 本セッションのPlaywright（Chromiumをheadless/CDP経由で駆動）は vsync が 16.7ms(60Hz) に
> 固定されるのに対し、レビュー〔…〕

**レビュー側も Playwright 経由である。** 前回・今回とも `mcp__plugin_ecc_playwright__*` で
駆動しており、「実際の Chrome」を手で操作したことは一度もない。

レビュー環境の実測:

| 項目 | 値 |
|---|---|
| `navigator.userAgent` | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) … Chrome/150.0.0.0 Safari/537.36` |
| UA に `Headless` を含むか | **含まない** |
| `navigator.webdriver` | **false** |
| `screen` | 2560x1440（実モニタ） |
| `devicePixelRatio` | 1 |

つまりレビュー側の Playwright は **headed（実ブラウザウィンドウ）** を駆動している。

**したがって分かれ目は「Playwright かどうか」ではなく「headed か headless か」である。**
Playwright は既定で headless だが headed でも動く。「Playwright ＝ headless ＝ 60Hz 固定」
という含意は誤り。記述をこの区別で書き直されたい。

なお「headless Chromium の vsync が 60Hz にエミュレートされる」こと自体は正しく、
そちらの観測（16.7ms・ノイズフロア 18.7ms）を疑うものではない。**両方とも正しい観測で、
環境が違っただけ**である。

## 【HIGH・反証】「開発機では構造的に検出できない」は成り立たない

コメントには次の一般化がある:

> この指標は非力な実機（Surface Go 2等〔…〕）でこそ意味を持つ可能性が高く、
> 開発機での「frame.maxが動かない」は「生成コストが無い」ことの証明にはならない

後半（「動かない＝コストが無い、ではない」）は**正しい**。しかし前半の
「開発機では検出できない・実機を待つべき」という含意は、**同じ開発機で反証された**。

### 実測（headed・リロードして各回1度きり実行）

**回1: ノイズフロアを 3 本連続で取ってから subregions のみ表示**

| 条件 | glyph 増分 | frame p50 | frame p95 | **frame max** |
|---|---|---|---|---|
| ノイズフロア① | 0 | 5.9 | 6.0 | **6.1** |
| ノイズフロア② | 0 | 5.9 | 6.0 | **6.1** |
| ノイズフロア③ | 0 | 5.9 | 6.0 | **6.1** |
| subregions 単独 | **+196** | 5.9 | 6.0 | **35.1** |

**回2: ノイズフロアを段の前後に挟み、小さい段（regions）と大きい段（subregions）を比較**

| 条件 | glyph 増分 | frame p50 | frame p95 | **frame max** |
|---|---|---|---|---|
| ノイズフロア（前） | 0 | 5.9 | 6.0 | **6.1** |
| regions | **+2** | 5.9 | 6.0 | **6.2** |
| ノイズフロア（中） | 0 | 5.9 | 6.0 | **6.1** |
| subregions | **+194** | 5.9 | 6.0 | **35.3** |

### 読み取れること

- **ノイズフロアは 5 本すべて 6.1ms**。18.7ms は headless 環境固有であり、
  headed では vsync 周期（5.9〜6.1ms）そのものに収まる
- **グリフ生成コストは明確に検出できる**。+194〜196 で **35.1 / 35.3ms** ＝ ノイズの **5.8 倍**。
  2 回の独立試行で **0.2ms** しか違わず、再現性は極めて高い
- **軸が効いている**。+2 → 6.2ms（ノイズと同等）、+194 → 35.3ms。
  生成量に対して単調に反応する
- **ノイズフロアを段の前後に挟んでも 6.1ms のまま**（回2）。
  その同じ区間内で 35.3ms のスパイクが出ている以上、**これをノイズと説明することはできない**

### 前回の 17.6ms も実信号だった

前回レビューの subregions 段は suite 内での累積計測で **+125 → 17.6ms** だった。
今回の単独計測は **+194 → 35.3ms**。グリフ数 1.55 倍に対し時間 2.0 倍で、おおむね比例する。
**n=1 だった前回の観測は、今回 n=2 の独立試行で裏付けられた。**

### したがって対処は

**「実機（Surface Go 2）を待つ」ではなく「headed で測る」。**
開発機のままで、この指標は十分な検出力を持つ。実機計測は依然として価値があるが、
それは「開発機では測れないから」ではなく「**遅い機体での実寸を知るため**」である。

計画書とコメントの当該記述を、この区別で書き直されたい。

## 【副産物】1グリフあたり約 0.18ms

| 試行 | glyph 数 | frame max − ノイズ | 1グリフあたり |
|---|---|---|---|
| 前回（suite 内） | 125 | 17.6 − 6.2 = 11.4 | 0.091ms |
| 回1（単独） | 196 | 35.1 − 6.1 = 29.0 | 0.148ms |
| 回2（単独） | 194 | 35.3 − 6.1 = 29.2 | 0.151ms |

単独計測 2 本では **約 0.15ms/グリフ** で安定する（suite 内の前回値が小さいのは、
累積の途中段でありフレームをまたいで分散した可能性がある——**未検証**）。

**【推測・未計測】** これを Surface Go 2 に外挿する場合、開発機比で 2〜3 倍と仮定すると
200 グリフで **60〜90ms** 程度。longtask の閾値 50ms を超える水準に入るため、
**§8 のテキスト描画は「無視できる」とは言い切れない可能性がある**。
ただしこれは外挿であり、実機で確かめるまで断定はできない。実機計測の価値はここにある。

## レビュー側での独立検証

| 確認項目 | 手段 | 結果 |
|---|---|---|
| レビュー環境が headless か | `navigator.userAgent` / `navigator.webdriver` | **headed（UA に Headless なし・webdriver false）** |
| ノイズフロアの実測 | 静止状態 620ms × 5 本 | **全本 max 6.1ms** |
| 生成コストの検出可否 | subregions 単独をリロードして 2 回 | **35.1 / 35.3ms（再現性 0.2ms）** |
| 軸の効き | regions(+2) と subregions(+194) を同一セッションで比較 | **6.2ms 対 35.3ms** |
| ノイズとの分離 | 段の前後にノイズフロアを挟む | **前後とも 6.1ms・間に 35.3ms** |

## 記録: 「環境が違う」で片付ける前に

今回、双方の観測（16.7ms / 6.1ms・18.7ms / 6.1ms）は**どちらも正しかった**。
しかし原因の特定は「Playwright か実 Chrome か」という誤った軸で行われ、
その結果「開発機では構造的に測れない」という**過剰に強い結論**が導かれた。

正しい軸は headed / headless であり、それは `navigator.userAgent` を 1 行読めば分かる。
**観測が食い違ったとき、環境差を仮定するのは正しい。だがどの環境差かを実際に確かめないと、
仮定が結論に昇格してしまう**——今回は「実機を待つしかない」という形で作業を止めかけていた。
