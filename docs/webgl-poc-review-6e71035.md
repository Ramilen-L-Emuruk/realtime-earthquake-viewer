## 【訂正】レビュー側の処方箋は使えなかった

前回わたくしはこう書いた:

> 実装は検証項目2 で作った処方箋がそのまま使える
> （`moveend` ハンドラ内で `performance.now()` の差分を取り、結果に名指しで記録する）

**これは誤りだった。** 項目2 の `moveendMs` は `startDrive` の停止関数が
`map.fire('moveend')` を**自分で呼び**、その前後の時刻差を取る方式である。
**自分で発火させるからこそ「前」の時刻が取れた。**

flyTo では `moveend` が Leaflet のアニメーション内部から自動発火するため、
**外部から「発火直前」の時刻を取る手段がない**。Leaflet の `Renderer` は map 追加時点で
`moveend` を購読しており、後から登録した計測用ハンドラより**先に**再描画が走る。
つまり計測ハンドラが呼ばれた時点では、既に再描画は終わっている。

対応側はこれを見抜き、**`MessageChannel` ブロック検出器**（`label` PoC で実証済み・vsync 非依存）に
切り替えた。飛行開始直前に検出を開始し、`moveend` 後 `LANDING_SETTLE_MS = 300` の settle を挟んでから
停止する構成で、**着地の同期再描画をメインスレッドの最長連続ブロックとして捕捉する**。

**この選択のほうが正しい。** レビュー側の指摘は「穴の所在」としては合っていたが、
「塞ぎ方」としては使えないものを提示していた。

## 【評価】計測の限界を自分で書いている

```
【厳密には】飛行開始〜settle 終了の区間内でのメインスレッド最長連続ブロックであり、
「着地由来」であることはコード上は保証しない。
```

そのうえで読み方の指針も添えられている——
「`frame.p95` が既に高い回は飛行中にもブロックがあった可能性があるので
`landingBlockTop3Ms` と `frame` を併せて読むこと（飛行中のタイル読込等が混じりうる）」。

**指標の名前が主張する内容（landing＝着地）と、実際に測っている量（区間内の最長ブロック）の
ズレを、自分で明示している。** 本日の一連で繰り返した「指標が何を測っているか」の失敗に対する
予防として機能する書き方である。

`rafId` を `moveend` 時点で止め、settle 中は rAF を回さない設計も正しい——
**`frame` 統計は「飛行中のみ」に保たれ、MapLibre 側と同じ定義のまま比較できる。**

## 【MEDIUM 1】longtask の観測窓が広がった — 第1回の値と単純比較できない

`po.disconnect()` の位置が変わっている:

| | 第1回（`0fa20f7` 時点） | **今回（`6e71035`）** |
|---|---|---|
| `PerformanceObserver` の停止 | `moveend` 直後 | **settle（+300ms）の後** |
| 観測される範囲 | 飛行中のみ | **飛行中 ＋ 着地 ＋ settle** |

**実機第1回の Leaflet 計測「longtask 0/32件」は、着地コストを観測窓に含んでいなかった。**
今回の実装では着地の longtask も捕捉されるため、**同じ機体・同じ操作でも longtask が増えうる。**

これは実装の改善によるものであり劣化ではないが、**前回値との差をエンジンの性能差と誤読しないこと。**
再計測後は「Leaflet longtask 0 → N 件」を**観測窓の変更として**説明する必要がある。

なお `elapsedMs` は `moveend` 時点のままで settle を含まないため、
**`fps` の定義は変わっておらず第1回と比較可能**である（この切り分けは適切）。

## 【MEDIUM 2】MapLibre 側に着地コストが無いという仮定が未検証

コメントの根拠:

> MapLibre 側は毎フレーム描画で着地に偏るコストが無く既存 frame 統計で全量を捉えるため、
> この指標は不要（MapLibre 側の再計測も不要）

**これは妥当な推論だが、検証されていない。** `poc/measure.ts` に `MessageChannel` は**0箇所**で、
MapLibre 側の着地時ブロックは一度も測られていない。

MapLibre も `moveend` を発火し、その時点で内部処理（タイルの pruning、シンボルの再配置など）が
走る可能性は排除できない。**「無い」ことを示すデータが無い。**

**提案**: `measureOneFly`（MapLibre 版）にも同じブロック検出器を入れる。追加コストは小さく、
入れれば「MapLibre の着地コストは 0 に近い」ことを**証跡で示せる**。
現状のままだと、Leaflet 側にだけ不利な指標を足した形にも見えてしまう。

**ただし MapLibre 側を改修すると第1回（`surface-go2-camera*` 34件）との比較条件が変わる**ため、
入れるなら MapLibre 側も再計測が要る。両者を新しい実装で揃えて測り直すのが最も明快である。

## 再計測時の注意（実機に投入する前に）

1. **Leaflet 側の longtask は第1回と比較しない**（観測窓が違う・MEDIUM 1）
2. **`landingBlockMaxMs` は `frame.p95` と併せて読む**（飛行中のブロックが混じりうる・実装コメントの指示どおり）
3. **`LANDING_SETTLE_MS = 300` の妥当性**は未確認。着地の再描画が 300ms を超えると取りこぼす。
   本番アプリの静止時計測で `frame.max` 149.9ms が出ているため PoC では十分な余裕と見られるが、
   **`landingBlockTop3Ms` の2番手・3番手が settle 端に張り付いていないか**を結果で確認されたい
