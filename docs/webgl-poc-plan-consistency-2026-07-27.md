## 3. 構造的な原因と提案

同じ事実が **§2.4/§5 の進捗メモ**・**§6 の結果記録**・**§8 のリスク一覧**・**冒頭ステータス行**の

`779a8bb` でも §6 と §8 は正しく直っているが、L695/L697/L802 の要約部分までは追随していない。
**同型の取り残しは今後も起きる。**

**提案（軽い順）**

- **(a)** 各項目の状態を**§6 の結果記録だけを正**とし、他の箇所からは「§6 参照」にリンクするだけにする。
  進捗メモに状態を書かない
- **(b)** 冒頭ステータス行の直後に**検証項目の状態一覧表**（項目 / 開発機 / 実機 / 判定）を1つ置き、
  そこだけを更新する
- (c) 現状維持で、都度すべての箇所を直す（取り残しが再発する）

レビュー側の推奨は **(b)**。表が1つあれば「何が終わって何が残っているか」を数行で確認でき、
本ドキュメントのような照合作業自体が不要になる。

## 4. 残っている検証待ち（照合後の正確な一覧）

### 判定に必須 — 比較対象が無く結論が出せない

1. **Leaflet 側のカメラ計測**（検証項目3）
   本番アプリ側に flyTo/fitBounds の計測フックを仕込み、実機で同条件計測して MapLibre 側
   （fps 28.2〜52.7・`frame.p95` 17〜83.3ms）と突き合わせる。**これが無い限り項目3 は保留のまま**。
   比較対象を作る作業が要るため、他の残件より工数が大きい
2. **Leaflet 側の実行時メモリ**（§8）
   ただし **VRAM が本手法では観測できない**問題が先にあり、
   「何をもって答えとするか」の定義から決め直す必要がある

### 実装後に必要

3. **案C（起動時グリフ事前生成）の体感確認**
   初期化処理（データ fetch・タイル取得）と競合したときの実測。未実施

### 優先度は低いが未了のまま

4. **本番ビルドでの実機再計測**（層 A 残差の実寸）
5. **CPU スロットル軸（1×/2×/4×）** — §9 付録で「未実施」
6. **GPU フレーム時間の直接計測**（Performance の GPU トラック・`chrome://tracing`） — §9 付録で「未実施」

**GPU 側は依然として vsync に隠れて観測できていない**。rAF 間隔は構造的に vsync でクランプされるため、
「GPU が間に合っているか」は本計画を通して一度も直接確認されていない。
