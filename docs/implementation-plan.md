# 機能実装計画

このアプリに追加する機能の計画と、採否の判断を 1 か所に集めたもの。**読者は開発者**（このリポジトリに手を入れる人）。

- 目的は 3 つ。**何を作るかを決める**こと、**決めた理由を残す**こと、**着手順を示す**こと
- 「面白そう」で始まった案が、なぜ採用されたか／なぜ落ちたかを後から辿れるようにする
- 実装済みの機能の仕様は書かない。それは [`docs/spec/`](spec/) の担当。**ここで計画したものが実装されたら、仕様は `docs/spec/` へ移す**

> 各項目の判定は、書いた時点の実装とデータ源の状況にもとづく。**外部 API の可用性は変わる**ため、「困難」「不可」の判定は根拠ごと読み直すこと。

## 読み方

各項目は次の 4 つのラベルと、判定欄を持つ。

| ラベル | 値 | 意味 |
|---|---|---|
| 関心 | ◎ / ○ / － / × / 済 | **実装したい強さ**。◎=実装する前提で詰めたい / ○=あってもいいが必須ではない / －=未判定 / ×=不要 / 済=実装済み |
| 実現性 | 可 / 条件付き / 困難 / 不可 | 下記 |
| 規模 | S / M / L / XL | 下記 |
| 依存 | 基盤A〜H / 項目番号 / なし | 下記 |

関心は**分析の密度を表さない**。× の項目にも他と同じ密度で難所を書いてある。落とした理由を後から辿るためで、調べ直す必要はない。

**関心 × は要否「不要」と同義**として扱う。両方に同じことを書くのは重複だが、一覧を見るだけで落としたものが分かる方が実用的なので残している。

落とした理由は各項目の **「不要と判定した理由」**、それが無ければ **「難所」** に書いてある。難所そのものが決定的だった項目には前者を置いていない。

**実現性**

| 値 | 意味 |
|---|---|
| 可 | 既存の仕組みと公開データで実装できる |
| 条件付き | 共通土台の整備、または外部要因（CORS・API 可用性）の実測確認が必要 |
| 困難 | 技術的には可能だが障壁が大きい（重い依存・レイテンシ・法的整理・サーバー必須） |
| 不可 | 現在のデータ源では原理的にできない |

**規模**

| 値 | 目安 |
|---|---|
| S | 1〜2 ファイル。新規データ源なし |
| M | 複数ファイル。新規レイヤーかパネルを 1 つ増やす |
| L | 生成スクリプトの追加、または外部データ源の新規統合を伴う |
| XL | アーキテクチャ変更、またはサーバー側の実体が必要 |

**依存の書き方**

- 基盤への依存が部分的なら `（一部）`、あってもなくてもよいなら `（任意）` を付す
- 複数の基盤に同時に依存するなら `・` で連結する（例: `基盤B・C`）
- 他の項目そのものが前提になる場合は項目番号を書く（例: `51 または 91`）
- 一覧表では接頭辞「基盤」を省いて `A`〜`H` と書く

**要否**

| 値 | 意味 | 一覧での表記 |
|---|---|---|
| 必要 | 実装する。着手待ち | `必要` |
| 不要 | 実装しない | `不要` |
| 未判定 | まだ決めていない（初期値） | `—` |
| 実装済み | 既にある | `済` |

> **ラベルの正は「一覧」の表**。各項目の見出し行はその写しで、「共通土台」「依存関係の早見」「付記」も一覧から引いた集計。ラベルを変えるときは一覧を直し、見出しと集計へ反映する。

## 採否の判断基準

92 件を判定した結果から抽出したもの。**新しい案を出すときは、まずここを読む。** 同じ議論を繰り返さないために置いている。

### 前提として置いていること

この 2 つは機能の形を直接左右する。**思いつきの段階で当てておくと、作れないものを設計せずに済む。**

- **一人が複数の端末で開く。** 同じ利用者が PC とスマートフォンで併用することを想定する。したがって**利用者が手で入力したデータを端末に溜める機能は意味を持たない** —— 記録が端末ごとに分散し、どれも不完全になる
  - これは実装から導いた事実ではなく**この文書が置く想定**。設定は `useSettings.ts` が端末ごとの `localStorage` に保存し、端末間の同期は持たない
  - **対象外になるものが 2 つある**
    - **観測データから自動で溜まるもの。** どの端末も同じ観測を見ているので同じ結果が溜まる（88 観測点の個性・89 静けさスコア）
    - **開発者が自分の端末で見るもの。** そもそも端末をまたぐ必要がない（基盤C の検知履歴・59・60）
- **地震のときに利用者に余裕はない。** 揺れている最中や直後に**手動操作を要求する機能は成立しない**。放っておいても働くか、平常時に一度設定すれば済む形にする

### 最初に決めること —— 誰のための機能か

**一般利用者向けか、開発者向けかで基準の当たり方が変わる。** 案を出したら、まずここを決める。

| 宛先 | 変わること |
|---|---|
| **一般利用者向け** | 下記の基準がすべて当たる。特に「公式データと誤認される」「災害を娯楽として扱う」に厳しい |
| **開発者向け** | 端末をまたぐ一貫性は要らない（自分の端末で見るだけ）。公式データとの紛らわしさも、置き場所を開発者向けの画面に限れば緩む。ただし**一般の画面に出すなら一般利用者向けの基準に戻る** |

基盤C（アプリ内検知履歴）とその上の 59・60 は開発者向け。**同じ題材でも宛先を変えれば通ることがある** —— 65（観測網の穴）は一般利用者向けとしては「気象庁の情報と紛らわしい」で落としたが、開発者向けに限れば 58・59 の一部として成立しうる。

**同じ題材でも、上のどれに当たるかで結論が変わる。** 判定が紛れやすい組を並べる。

| 通した方 | 落とした方 | 分かれ目 |

## 共通土台

複数の項目が同じ前提を要求する。**個別に作ると同じものを 2 度用意することになる**ため、先に土台の要否を決める方が早い。

### 基盤A. 長期震源カタログ — **整備済み**

現在のカタログは**直近 30 日**（`HEATMAP_DAYS = 30`・[useQuakeHeatmap.ts:11](../src/hooks/useQuakeHeatmap.ts:11)）。ヒートマップ用に取得したもので、統計解析には期間も件数も足りない。

- 必要になる項目: 4・9・12（任意）・15・17・20・64（7 件）

**入手経路の比較**

| 経路 | 期間 | 形式 | 認証 | 判断 |
|---|---|---|---|---|
| 気象庁「地震月報（カタログ編）」の震源データ | 1919〜2023 年 | 年別・まとめ ZIP・96 バイト固定長 | 不要 | **採用。** 全期間が揃い、小さい地震も入る |
| 気象庁「震源リスト」 | 2024-01-01〜2 日前 | 日別 HTML・固定幅の表 | 不要 | **採用。** 上の確定値の遅れを同じ粒度で埋める。再配布も同じ規約 |
| USGS FDSN event service | 1900 年頃〜 | GeoJSON | 不要・**CORS 許可済み** | 併用候補。ブラウザから直接引けるが**M2.5 以上のみ**で、b 値の推定には不足 |
| opendataapi.jp（第三者が気象庁データを CSV/JSONL 化） | 1919 年〜 | CSV / JSON | **API キーが必要** | 見送り。キー管理が増え、運営が個人。手作業での取得には便利 |
| DMDATA `gd/earthquake`（既存） | 実装上限 2000 件 | JSON | API キー | 長期には届かない（現在の 30 日はこれ） |

- **実体**: `scripts/build-hypocenter-catalog.ts` が気象庁の震源データを読み、年ごとの JSON にする。読み込みは `src/utils/hypocenterCatalog.ts`。仕様は [`data-sources-spec.md`](spec/data-sources-spec.md) §6「長期震源カタログ」へ移した

**実装で決着したこと**（当初「決めるべきこと」として挙げていたもの）

| 論点 | 決着 |
|---|---|
| 対象期間 | **1919 年〜2 日前**（108 年・約 102 万件・31MB）。確定値（地震月報カタログ編）は 2023 年までしか無いが、**同じ粒度の「震源リスト」（日別）が 2024-01-01 以降を 2 日前まで埋める**。年 ZIP を先に試し 404 なら日別へ落ちるので、確定値が公開されれば自動で入れ替わる。当初は「最新まで埋める公開データは無い」と判断して 2009〜2023 年に絞ったが、消費側の機能を具体的に検討した段で震源リストを見つけて撤回した |
| 完全性の扱い | **収録は M2.0 以上だが、M2.0 の取りこぼしが無いのは 1997 年以降だけ。** M5 以上は 1919 年から横ばいなのに M2 以上は 46 倍に増えている（増えたのは観測網）。索引が期間ごとの完全性下限（`completeness`）を持ち、件数を数える機能は `completeMinMagnitude()` で閾値を上げる |
| 更新 | **GitHub Actions で週 1 回**。気象庁側が 2 日前までなので、頻度を上げても尾は縮まらない。索引の `coveredThroughMs` が終端を持つので、消費側は「未取得」と「地震が無かった」を描き分けられる |
| M の下限 | **M2.0**。年 26,000 件（2011 年だけ 93,212 件）。b 値の推定に使える下限で、容量との折り合いもよい。この下限に絞ると**手動検測の震源が約 8 割**を占める（全体では自動処理が過半数）。**下げても情報は増えない** —— 2023 年の実測で M1 台は M2 台の 4.3 倍しかなく（グーテンベルク・リヒター則なら 10 倍）、M0 台は 1.3 倍で頭打ち。取りこぼし方が海域と陸域で違うため、混ぜると観測網の密度分布が地震活動の分布として出る |
| 96 バイト固定長のパーサ | **「難しくはない」という見立ては外れた。** 公開仕様を鵜呑みにすると 1 バイトずつずれる（実ファイルは改行区切り）。さらに**収録年を広げた段で書式が年代で変わることが判明** —— 1961〜1993 年は小数部が 1 桁少なく、素朴に読むと緯度が 78km ずれる。**生成のたびに取得経路ごとに既知の地震と照合する**（7 経路・7 地震）仕組みで担保した。踏んだ罠は [`data-sources-spec.md`](spec/data-sources-spec.md) §6 に列挙してある |

- **ライセンス**: 気象庁サイトのデータは**公共データ利用規約（第 1.0 版）**に準拠する（[気象庁のサイトポリシー](https://www.jma.go.jp/jma/kishou/info/coment.html)が明記）。この規約はデジタル庁が 2024-07-05 に定めたもので**CC BY 4.0 と互換**、複製・公衆送信・翻案が認められ商用利用もできる。条件は「出典表示」「加工した旨の記載」「国が作成したかのような態様で公表しない」の 3 つ。表記例は「出典: 気象庁ホームページ（当該ページの URL）」「気象庁『◯◯』を加工して作成」
- **USGS との併用**: 項目 50（USGS 世界地震）を実装するなら取得経路を共有できる。M2.5 以上で足りる用途（9 の余震域・20 の同一地点履歴）だけ USGS に寄せ、細かい地震が要る用途（4・15）は気象庁の ZIP に寄せる、という分け方もある

### 基盤B. onset 時刻の外部公開 — **整備する**

検知エンジンは各観測点の初動時刻を内部に持つが、外へ出していない。

- 必要になる項目: 8・59
- 実体: `kyoshinDetector` の戻り値に観測点ごとの onset 時刻を含める
- 注意: 既存の検知結果（likely/confirmed）とは粒度が違う。点単位の情報を毎秒返すことになるため、量と更新頻度の設計が要る

### 基盤C. アプリ内検知履歴 — **実装済み**

検知したイベントを端末内に永続化する。**別セッションが実装を終えて main に入った**（`src/utils/detectionDiagnostics.ts`・`src/utils/detectionDiagnosticsDb.ts`、設定タブの「診断ログ」節）。

**目的は開発者が検知精度を後から確認すること。** 一般利用者に見せるための土台ではない。この位置づけが上に乗る項目の設計を左右する。

**実装で決着したこと**（当初「判断材料」として挙げていたもの）

| 論点 | 決着 |
|---|---|
| 保存先 | **IndexedDB**（`kyoshin-diagnostics`）。1 件 150KB 前後になるため localStorage（5MB・同期・設定と同居）には置けない |
| 保持件数 | `MAX_RECORDS = 50`。超えたら古いものから捨てる |
| 記録の中身 | 検知の前後 61 秒ぶんの生の観測値（1725 観測点 × 61 文字）と**観測点の座標そのもの**。版だけを記録して後から引く形は採らなかった（旧版の観測点リストが配信され続けることに賭けられないため） |
| UI | 設定タブに件数表示・書き出し・消去。**失敗しても本体を止めない**（IndexedDB が使えない環境では警告だけ出して諦める） |

**59（根拠開示）の土台にもなる。** 検知の前後 61 秒を丸ごと持っているので、判定の再現ができる。

- 必要になる項目: 58・59・60・61・82（一部）・88・89（7 件）
- 検知エンジンの**回帰ベンチ**（`scripts/bench-kyoshin.ts`）とは別物。ベンチは**過去の窓をオフラインで流して実装を評価する**もの、履歴は**動いているアプリが自分の検知を実地で記録する**もの。**取り違えると 58 以降が「もう作られている」と誤解される**
- **乗る項目は宛先が分かれる。** 表示の置き場所（一般の画面か、開発者向けの画面か）が変わるので、実装前に決めておく

| 宛先 | 項目 |
|---|---|
| 開発者向け | 59 検知の根拠開示・60 誤検知の分類 |
| 両方に意味がある | 58 検知の成績表・61 検知ランキング・88 観測点の個性 |
| 一般利用者向け | 82 地震の解説自動生成・89 静けさスコア |

- **残る判断材料**: 気象庁発表との照合をどこで行うか（58 の成績表が要求する）

### 基盤D. 3D 描画（pitch の解禁） — **整備する**

地図の傾き（pitch）と回転（bearing）は**ユーザー操作から無効化されている**（[map-rendering-spec.md](spec/map-rendering-spec.md) §6）。

- 必要になる項目: 3・4（2 件）
- **解禁の前に直すもの**（仕様書が「有効に戻すなら何を先に直すか」として挙げている 2 点）
  1. **予報円の半径計算**（`PsWaveGL`）— 半径を「震央から東へ 1 点ずらした画面座標の x 座標差」で求めているため、回転すると `cos(bearing)` 倍に縮む（実測: 0 度 45.51px → 90 度 0px で円が消える）。傾けた場合も透視で圧縮され、地面の円と画面上の円が一致しなくなる
  2. **カメラ自動フィットの bearing 前提**（`gl/camera.ts`）— `fitBounds` 経由はユーザーの回転を無断でリセットし、`flyToBoundsSnapped` は回転を保ったまま北が上の前提で狭いズームを当てるため対象が見切れる
- **影響を受けないもの**: 円マーカー・ラベル・DOM マーカー（`rotationAlignment` の既定が viewport なので画面に正対したまま）
- **pitch を解禁しても、それだけでは 3D にならない**: 3D 地形（terrain）を使っていないため傾けても地面は平らなまま。項目 4（地下の点群）には **three.js の custom layer** が別途必要になる。項目 3（震度の押し出し）は `fill-extrusion` で足りる

### 基盤E. 静的レイヤーデータの生成 — 判断対象外（既にある手順）

`scripts/build-*.mjs` で外部データを JSON 化し、`public/data/` に置いて遅延読込する既存パターン。

**他の土台と違い、これは既にある手順。** 整備の要否を決める対象ではなく、下記の項目が同じ型で作れることの表明として置いている。判断は項目ごとに閉じる。

- 同じ型で作れる項目: 35・36・37・38・39・47（6 件）
- 判断材料は項目ごとに 2 つ。**容量**（`gzip.ts` があるので圧縮前提で見る）と**ライセンス**（政府標準利用規約なら概ね可）

### 基盤F. 全球投影 — **整備する**

現在は日本域前提。世界の地震を出すなら MapLibre の globe 投影に切り替えるか、Mercator のまま広域表示するかの判断が要る。

- 必要になる項目: 49・50
- 影響: 予報円の半径計算とカメラフィットは日本域の Mercator 前提。基盤D と同種の波及がある

### 基盤G. サーバー側の実体 — **不要が確定**

現在は静的ホスティング（GitHub Pages）のみ。端末間で状態を共有する機能はサーバーを要求する。

- これを要求していた 34・53・68 は**3 件とも不要と判定された**ため、整備する理由がなくなった
- **節を残しているのは制約の記録として**。「サーバーを持たない」は今後の項目にも同じ判断を強いる。運用コストと個人情報の扱いが発生し、**アプリの性格そのものが変わる**

### 基盤H. 配色の差し替え — **整備する**

震度・長周期地震動階級の配色は `intensity.ts` の `INTENSITY_COLORS` / `INTENSITY_BG_COLORS`（と `lpgm.ts` の対応するテーブル）に定義され、`getIntensityColor()` などの関数を通して **20 ファイルが参照している**。

- 必要になる項目: 73・77（2 件）
- **関数で一元化されているのが有利**。差し替えの仕組みは関数側に入れれば足り、参照している 20 ファイルを個別に直す必要はない
- **仕様書の記述を書き換える必要がある**: [map-rendering-spec.md](spec/map-rendering-spec.md) §15 は「気象庁の震度配色・長周期地震動階級の配色は仕様として定まっているため色そのものは変えられない」と書いている。これは法的な禁止ではなく設計判断だったため、切り替えを入れるなら同時に改める
- **既定は気象庁配色のまま置く**。震度色は防災情報として広く認知されているので、既定を変えるとテレビや他のアプリと食い違って誤読を招く。差し替えは利用者が明示的に選んだときだけ働く形にする
- **文字色は自動で追従する**: §15 の設計（塗り色から白/黒を選ぶ）があるため、パレットを変えてもコントラストは保たれる
- **注意が要る箇所**: Canvas アイコン（`gl/intensityIcons.ts`・`gl/lpgmIcons.ts`・`gl/kyoshinDetectedIcons.ts`）はキャッシュを持つのでパレット変更時に捨てる必要がある。地図レイヤーの色を式で埋めている箇所は再適用が要る。`getDepthColor`（深さの段階色）は別のパレットなので連動させない

# 揺れの伝播を見せる

## 1. 予報円と実測波面の重ね合わせ

`関心 ×` `実現性 可` `規模 M` `依存 なし` — **要否: 不要**

- **見え方**: EEW の理論 P/S 波円と、強震モニタで実際に揺れが広がっていく輪を同時に描く。予測と実測のズレが目に見える
- **データ源**: 既存のみ（`usePsWaveCalc` の予報円＋強震モニタのフレーム）
- **実装**: 実測側の「波面」をどう定義するかが設計の中心。検知エンジンの確定点の外周（凸包）か、震度が閾値を超えた点の最遠距離を半径とする円か
- **難所**: 円で近似すると異方性（不均質な地下構造による伝播の偏り）が消える。それを見せたいのに円にしては本末転倒。凸包の方が誠実だが、点が疎な海域で形が破綻する

## 2. 揺れのトレイル（残像）

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 必要**

- **見え方**: 観測点が現在値だけでなく直近数秒の減衰履歴を尾として残す。揺れが伝わると尾の向きが揃い、波面の進行が目に見える
- **データ源**: 既存の毎秒フレームのみ。追加取得なし
- **実装**: `KyoshinPointsGL` の下に第 2 レイヤーを敷く。点ごとに「過去 N 秒の最大値 × 減衰係数」をリングバッファで保持し、`circle-radius` と `circle-opacity` に反映する。点を増やすのではなく**消え残りを描く**
- **難所**:
  - MapLibre の既定 300ms トランジションの無効化が必須。過去 2 回踏んだ罠（[map-rendering-spec.md](spec/map-rendering-spec.md)）
  - 毎秒 `setData` が 2 本になる。観測点は約 1725 点なので致命的とは思えないが、負荷の実測は要る
  - 減衰計算を GPU 側の時間 uniform に寄せられないのが MapLibre の制約。CPU で毎秒回すことになる
- **派生**: 尾を「値が上がった点だけ」に絞ると、onset の広がり＝検知エンジンの L2 判定がそのまま絵になる。59 と目的が重なる

## 3. 震度の 3D 押し出し

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤D` — **要否: 必要**

- **見え方**: 区域や観測点を震度の高さに立ち上げる。日本列島が波打つ
- **データ源**: 既存
- **実装**: `fill-extrusion` は MapLibre 標準機能。**項目 4 のために基盤D（pitch 解禁）を整備すると決めたので、この項目が単独で負う追加コストは小さくなった**（4 が要する three.js もこちらには不要）
- **難所**: 震度は区域単位の階級値なので、高さの割り当てが恣意的になる。気象庁配色は変えられないため、色は震度色のまま高さだけを足す形になる
- **判断のポイント**: 基盤D のコストは 4 が引き受けた。**残るのは「立体にして意味があるか」だけ**
- **保留にしている理由**: 4 を実装して 3D の見え方を実物で確かめてから決める

## 4. 3D 震源分布

`関心 ◎` `実現性 条件付き` `規模 XL` `依存 基盤A・基盤D` — **要否: 必要**

- **見え方**: 地図を傾けて震源を深さ方向に配置する。海溝から陸へ向かって**プレートの沈み込み面が斜めに沈んでいく形が立体で見える**
- **データ源**: 30 日カタログでは点が足りない。沈み込み帯を見せるなら基盤A（長期カタログ）が必須
- **実装は 2 つの壁を越える**
  1. **pitch の解禁**（基盤D）。予報円の半径計算とカメラ自動フィットの bearing 前提を先に直す
  2. **地下を描く仕組み**。MapLibre の `fill-extrusion` は地面から上へ押し出すので地下に使えない。震源の点群は **three.js の custom layer** で描くことになる（このアプリに新しい描画エンジンが 1 つ増える）
- **決めるべきこと**: **深さ方向の誇張率**。実スケール（水平 1000km に対して深さ 100km）では薄すぎて形が読めないため、垂直方向を数倍に伸ばすのが通例。ただし伸ばしすぎると沈み込み角の印象が狂う
- **難所**: データ量。一元化震源は年間 10 万件超なので、ビルド時の間引き方（M 下限・対象期間）を決める必要がある
- **2D 断面図という選択肢もあった**: 線分を引いて「距離 × 深さ」でプロットする形。pitch も three.js も要らず規模は L に収まり、沈み込み角を定量的に測れる代わりに**形が掴めない**。形の直感を優先して 3D を採った。目的が違うので排他ではなく、後から 2D を足すこともできる

## 5. 等震度線

`関心 ◎` `実現性 可` `規模 M` `依存 なし` — **要否: 必要**

- **見え方**: 観測点の震度を補間して等高線を描く。点の集合より分布の形が直感的に読める
- **データ源**: 既存（地震情報の観測点別震度、または強震モニタ）
- **実装**: 補間（IDW か Kriging の簡易版）→ 等高線抽出（marching squares）。ライブラリなしで書けるが 200 行規模
- **難所**: 観測点が疎な海域・山間部で等高線が暴れる。震度は距離減衰だけでなく地盤で大きく変わるため、**滑らかな等高線は実態を単純化しすぎる**という批判が成り立つ。気象庁が等震度線を常用しないのはこの理由

## 6. 走時曲線グラフ

`関心 ×` `実現性 可` `規模 M` `依存 基盤B` — **要否: 不要**

- **不要と判定した理由**: 横軸に震源距離・縦軸に経過秒を取り、理論走時線に実測 onset を乗せるグラフ。理論の検証としては筋が通るが、**読み手が限られる**（走時曲線を読める人向け）。同じ「予測と実測のズレ」は 1 や 8 の方が地図上で直感的に示せる
- **記録として**: 基盤B（onset 公開）を要求する項目だったが、これが落ちても 8・59 が同じ土台を要求するため、基盤B の要否には影響しない

## 7. 矩形断層面の描画

`関心 ×` `実現性 困難` `規模 XL` `依存 基盤D・F` — **要否: 不要**

- **不要と判定した理由**:
  - 気象庁の即時電文にメカニズム解（走向・傾斜・すべり角）は載らない。CMT 解（断層の動きを解析した結果。発生から時間を置いて公表される）は別配信・月報なので**国内のリアルタイム表示は成立しない**
  - USGS 経由なら世界の M4.5+ に moment tensor が即時公開されるが、それは 50 の範囲に収まる話
  - `fill-extrusion` では傾いた面が作れないため three.js の custom layer が必要。基盤D に加えて描画エンジンをもう 1 つ抱えることになる
- **記録として**: 震源球（ビーチボール）の 2D 表示だけなら安い。項目 4 で three.js が入るので**描画側の壁は消える**が、データ側の壁（気象庁の即時電文にメカニズム解が載らない）は残るので判定は変わらない。50（USGS）を実装すれば世界の地震に対しては成立する

## 8. 揺れの進行方向（onset 勾配）

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤B` — **要否: 必要**

- **前提の訂正**: 当初案は「揺れの主軸方向（卓越方向）」だったが、**これは実現不可**。Yahoo 強震モニタの JSON は成分別データを持たず、観測点ごとの震度インデックス 1 値のみ（[kyoshin.ts:7](../src/services/kyoshin.ts:7)）。検知エンジンのコメントにある「成分」は連結成分（グラフ）で、地震計の 3 成分とは無関係
- **読み替えた内容**: 各観測点の onset 時刻を面として捉え、**勾配ベクトルの逆向き＝震源方位**を出す。震源を知らないまま震源の方向が分かる。検知エンジンの震源非依存という性格がそのまま絵になる
- **データ源**: 既存。onset 時刻は検知エンジンが内部に持っている（基盤B で外に出す）
- **実装**: 近傍 K 点で平面フィット（最小二乗）→ 勾配 → 矢印レイヤー。計算自体は 20 行程度
- **難所**: onset が 1 秒粒度。S 波 4km/s なら 1 秒 = 4km、観測点間隔は 20km 程度あるため、**5 秒ほど伝播しないと向きが定まらない**。近距離・発生直後には使えない
- **土台の共有**: 59 が同じ基盤B を要求する。**別々に設計しないこと**
- **91 を実装すれば精度を測れる**: K-NET のアーカイブは 3 成分（`.NS` / `.EW` / `.UD`）を持つので、過去地震に対しては**真の卓越方向が計算できる**。onset 勾配で出した方位と突き合わせれば、この手法がどれだけ当たるかを検証できる

## 9. 余震域の楕円近似

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤A` — **要否: 必要**

- **見え方**: 余震分布に主成分分析で楕円を当て、「北東-南西に 60km 延びている」を絵で示す。断層の延びと長さが読める
- **データ源**: 直近の余震なら 30 日カタログで足りる。過去の地震に遡って見せるなら基盤A
- **実装**: 2×2 共分散行列の固有値分解。外部ライブラリ不要で 20 行程度。楕円は GeoJSON polygon で近似
- **難所**: 本震・余震の同定ルール。群発地震（能登・和歌山）では楕円が意味を失う。**10（クラスタリング）とセットで初めて成立する**

## 10. 前震／本震／余震のクラスタ色分け

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 必要**

- **見え方**: 時空間クラスタリングで地震を群にまとめ、群ごとに色を変える。群発の構造が見える
- **データ源**: 既存 30 日カタログで成立する
- **実装**: 単連結クラスタリング（時間差と距離の閾値）か、地震学で使われる窓型宣言法（Gardner-Knopoff）。前者が安い
- **難所**: 閾値の決め方で群の切れ方が変わる。9 の前提でもあるため、**先にこちらを決める順序になる**

- **データ源**: 既存カタログのマグニチュードのみ

- **難所**: **表現の節度**。被害を娯楽化する比喩（「原爆 n 個分」等）は避ける判断が要る

## 15. b 値のライブ推定

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤A` — **要否: 必要**

- **見え方**: マグニチュード-頻度分布の傾き b（通常 0.9〜1.0）。低下すると相対的に大地震が増える傾向とされる。地域別に色分けした b 値マップ
- **データ源**: 30 日では**足りない**。地域別に出すなら領域ごと 50〜100 件が最低線で、基盤A が必須
- **実装**: Aki の最尤法で 10 行程度。本番は Mc（完全性マグニチュード）の推定
- **難所**: **Mc の決め方で b が大きく動く**。誠実に出すには推定に使った件数と Mc を必ず併記し、「参考値」と明示する必要がある
- **判断のポイント**: 科学的な正しさを保つコストが、面白さに対して見合うか

# 音

## 21. ソニフィケーション

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 必要**

- **聴こえ方**: 全観測点の震度を音に変換する。案は 3 つ
  1. 最大震度を音高、揺れている点数を音量にする（最も単純）
  2. 地域別に音を割り当てて和音にする（どこが揺れているかが分かる）
  3. 震度分布のヒストグラムをスペクトルとして加算合成する（最も情報量が多いが解読が難しい）
- **データ源**: 既存の毎秒フレーム
- **実装**: `alertSound.ts` が既に Web Audio の Oscillator / Gain / Convolver（残響）を持っている。同じ AudioContext に常時オシレータを 1 本足し、毎秒パラメータを更新する。ユーザー操作前は鳴らせない制約（unlock）の作法も既存に倣える
- **難所**:
  - 通知音との衝突。EEW の警報中はソニフィケーションを絞る（ダッキング）必要がある
  - 音量設定を既存の通知音と別系統で持つ必要がある
- **最大の価値**: **平常時に流しっぱなしにできる**こと。何も起きていない時間に意味を持たせられる。他の地震ビューアーが持っていない軸

## 22. 地域の定位（パンニング）

`関心 ×` `実現性 可` `規模 S` `依存 なし` — **要否: 不要**

- **聴こえ方**: 東で揺れたら右から鳴る。画面を見ていなくても方角が分かる
- **実装**: Web Audio の `StereoPannerNode`。経度を -1〜1 に写すだけ
- **難所**: 21 の一部として実装するのが自然。**単独では機能にならない**

## 23. 地球の脈（アンビエント）

`関心 ×` `実現性 可` `規模 S` `依存 なし` — **要否: 不要**

- **聴こえ方**: 常時微動レベルを持続音にして流し続ける
- **実装**: 21 の派生。全点の中位値を音量に写す
- **難所**: 21 との違いが曖昧。**21 の「モード」として扱うべき**

## 24. 地震波のピッチシフト再生

`関心 ×` `実現性 不可` `規模 L` `依存 51 または 91` — **要否: 不要**

- **不可の理由**: 地震波形そのものがこのアプリのデータ源に無い。リアルタイム震度は 1 秒ごとの震度相当値であって波形ではない
- **成立する条件**: 51（Raspberry Shake）または 91（K-NET アーカイブ）で波形を手に入れた場合のみ
- **記録として**: 波形が手に入った暁には安い（`decodeAudioData` に相当する処理は自前で書くが、リサンプルだけ）

## 25. チャイムの差し替え

`関心 ◎` `実現性 可` `規模 M` `依存 なし` — **要否: 必要**

- **見え方**: 設定タブで種別ごとに音源を選ぶ。プリセット数種＋ユーザーのローカルファイル
- **実装**: File API で読んで IndexedDB に ArrayBuffer で保存（localStorage には入らない）。再生は `decodeAudioData` → `BufferSource`。`alertSound.ts` の `PLAYERS` テーブルに「外部バッファ再生」の枝を足す
- **難所**:
  - **既存の制約に触る**。音の長さと `TTS_DELAY_MS` の連動（[audio-tts-spec.md](spec/audio-tts-spec.md) §6）が壊れる。外部音源は長さが不定なので、decode 後の duration から遅延を動的に決める必要がある
  - 著作権のある音源をユーザーが入れる余地。配布はしないのでアプリ側の責任は限定的だが、注意文は要る
  - IndexedDB のサイズ上限（ブラウザ依存）

## 26. 話者の使い分け

`関心 ◎` `実現性 可` `規模 S` `依存 なし` — **要否: 必要**

- **見え方**: EEW は緊迫した声、平常情報は落ち着いた声。VOICEVOX は話者とスタイルを複数持つ
- **実装**: 現在は話者 ID が 1 つ。種別ごとに ID を持たせて `voicevox.ts` の合成呼び出しへ渡す
- **難所**: 切り出し語のキャッシュ（`warmFixedPhrases`）が話者ごとに要る。話者を増やすとキャッシュが分岐する

## 27. 多言語読み上げ

`関心 ◎` `実現性 困難` `規模 L` `依存 なし` — **要否: 必要**

- **見え方**: 英・中・韓で読み上げる。訪日外国人向け
- **調査の結果、合成エンジンの選択肢が乏しかった**
  - **ブラウザ標準の Web Speech API はこのアプリの用途に合わない。** Chrome は約 15 秒（200〜250 文字）で発話を打ち切り、Chrome と Safari は**タブがフォーカスを失うと合成を止める**。地震情報の読み上げは確実にこの長さを超えるし、通知として使うなら非フォーカスで鳴らなければ意味がない。音声の種類と言語対応も端末依存
  - **VOICEVOX を採用している理由がここにある**（ローカル HTTP で音声データを取得して Web Audio で鳴らすので、上の制約を受けない）。ただし**音声合成の言語は日本語のみ**。英単語をカタカナへ変換するオプションは `voicevox_core` に要望として上がっているが**未実装**（Issue #739）で、UI の多言語化も未対応（Issue #1682）
  - **カタカナ変換という回避策の限界**: 呼び出し側で英語をカタカナに直せば「アースクエイク アーリー ウォーニング」のように読ませられる。ただしアクセントとリズムは日本語のままなので、**英語話者に通じる発音にはならない**。訪日外国人向けという目的には足りない
  - クラウドの TTS サービスはキーと費用が発生する。多言語対応のローカル TTS（Piper 等）は利用者に別のソフトを導入させることになり、VOICEVOX に加えて 2 つ目の常駐を求める形になる
- **難所（読み上げ文そのもの）**: `ttsText.ts` の文の組み立ては日本語の助詞・語順に強く依存している。翻訳ではなく**言語ごとに文を組み立て直す**ことになる。地名の訳（一次細分区域名）も全件必要
- **判断のポイント**: **表示の多言語化（UI ラベル）だけなら規模 M で成立する。** 読み上げと表示を分けて考える価値がある

## 28. 触覚通知（Vibration API）

`関心 ○` `実現性 可` `規模 S` `依存 なし` — **要否: 必要**

- **見え方**: 震度に応じてスマホが震える。震度階級をパターンの長さ・回数で表す
- **実装**: `navigator.vibrate()`。パターン配列を渡すだけ
- **難所**: iOS Safari が Vibration API を実装していない（**iPhone では動かない**）。Android 限定の機能になる

# 重ねるレイヤー

## 35. 人口メッシュ

`関心 ◎` `実現性 可` `規模 L` `依存 基盤E` — **要否: 必要**

- **見え方**: 「震度 5 弱以上を体感した推定人口 ○○万人」を地震カードに 1 行。地図では震度と人口の積を色で示す
- **データ源**: e-Stat の国勢調査メッシュ人口（政府統計・利用可）。500m メッシュで約 30 万、1km メッシュで約 8 万
- **実装**: ビルド時に「メッシュ ID → 人口」を TypedArray 化して gzip（`gzip.ts` が既にある）。既存の生成データと同じ遅延読込パターン。震度からの割り当ては一次細分区域単位の面積按分で足りる
- **難所**:
  - データ量。1km メッシュ＋gzip で 1MB 台
  - 内挿の精度。区域単位の粗い按分でも万人単位の桁は合う。**桁だけ合わせて有効数字 1 桁で出すのが誠実**
- **価値**: 報道より早く規模感が出る。この一覧で実用性が最も跳ねる項目

## 36. 鉄道路線

`関心 ◎` `実現性 可` `規模 L` `依存 基盤E` — **要否: 必要**

- **見え方**: 路線を線で描き、震度 4 以上の区域を通る路線を強調する。「止まりそうな路線」が地震発生 10 秒後に分かる

- **難所**:
  - 表示の混雑。全国の路線を出すと地図が線だらけになる。ズーム閾値（既存の「視野の実距離」方式）で新幹線→幹線→ローカル線の段階表示が必須

- **実装**: `services/usgs.ts` を足して既存の地震カード型へマップすれば、カードも地図も流用できる
- **難所**:
  - 投影。日本域前提の Mercator から全球へ広げると、予報円の半径計算とカメラフィットが影響を受ける（基盤F）
  - PAGER の死者数推定を出すことの是非。**出すなら確率分布のまま出す**（点推定にしない）
- **判断のポイント**: **フィードだけなら極めて安い**。ShakeMap・PAGER は第 2 段として分けられる

## 51. Raspberry Shake

`関心 ○` `実現性 困難` `規模 XL` `依存 なし` — **要否: 不要**

- **見え方**: 近所の市民地震計の**生波形**。このアプリが持っていない「波形」という軸が開く
- **データ源**: FDSN Web Service（国際地震観測網連盟が定めた標準 API。station で観測点一覧、dataselect で波形を取る）。**波形は miniSEED**（地震波形の標準バイナリ形式）
- **実装**: ブラウザでの miniSEED パース（`seisplotjs` 等のライブラリ）が必要
- **難所**:
  - パースが重くバンドルが膨らむ
  - **国内の台数が少なく、地域によっては 1 台も無い**
  - CORS の可否は実測しないと分からない
  - レイテンシが数秒〜数十秒で、強震モニタの 1〜2 秒に劣る
- **判断のポイント**: 価値は認めるが優先度は低い。**波形を扱う目的なら 91 の方が筋が良い**（過去データだが量と質で勝る）
- **不要と判定した理由**: **難しいので落とす。** miniSEED のパースでバンドルが膨らみ、国内の台数も少なく、レイテンシも強震モニタに劣る。**「波形」という軸は 91（K-NET アーカイブ）が開くので、この項目を失っても軸は残る**

## 52. 端末の加速度センサー

`関心 ×` `実現性 可` `規模 M` `依存 なし` — **要否: 不要**

- **見え方**: `DeviceMotion` でスマホを地震計にする。強震モニタと突き合わせると面白い
- **難所**:
  - iOS は許可プロンプトが必要（`requestPermission`）。HTTPS 必須
  - **端末が動いているだけで反応する**。歩行・車内・机の振動と地震を区別できない。誤検知の山になる
  - 端末ごとにセンサー特性が違い、計測震度への換算は成立しない
- **判断のポイント**: 「地震計にする」と称するには精度が足りない。**実験的な表示に留めるなら成立する**

## 53. 端末群の相互共有

- **難所**: 52 の誤検知問題を抱えたまま、さらにサーバー（基盤G）が必要になる。**落とすのが妥当**

## 54. SNS 震度

`関心 ○` `実現性 条件付き` `規模 L` `依存 なし` — **要否: 必要**

## 55. 停電情報

`関心 ◎` `実現性 困難` `規模 M` `依存 なし` — **要否: 必要**

- **見え方**: 停電の広がりを地図に重ねる。地震の被害規模を測る手がかりになる
- **調査の結果、「データが無い」という当初の判定は誤りだった。公式の集約 API は存在する**

  - 対象は **7 社**（北海道・東北・東京・中部・北陸・中国・沖縄）。**関西・四国・九州が入っておらず全国を覆っていない**（10 社への拡大を目指すとされている）

  - 個人がスクレイピングして JSON を配信していた非公式 API（`jp-power-outage`）は**停止している**
- **難所**: **取得経路が法人契約に限られる。** 個人開発の一般公開アプリからは手が届かない。スクレイピングは規約と安定性の両面で採れない
- **要否を「必要」に置いている理由**: 手段が存在しないのではなく、**現時点で手が届かない**だけ。API が一般に開かれれば実装できるので、落とすのではなく待つ位置づけ

## 56. 河川水位・ダム放流

`関心 ×` `実現性 条件付き` `規模 M` `依存 なし` — **要否: 不要**

- **データ源**: 国土交通省の水文水質データベースに API がある
- **難所**: 地震との関係が薄い（地震で水位は基本的に変わらない）。**このアプリの焦点から外れる**

# 検知エンジンを見せる

> この 4 項目はすべて**基盤C（アプリ内検知履歴）**の上に乗る。基盤C の状況は「共通土台」の節を参照（本文書を書いた時点では未コミット）。

## 58. 検知の成績表

`関心 ○` `実現性 可` `規模 M` `依存 基盤C` — **要否: 必要**

- **見え方**: 自前検知を後から気象庁発表と照合し、「何秒早かったか」「空振りだったか」を自動採点する
- **データ源**: 基盤C の検知履歴＋既存の地震情報カード
- **実装**: 照合ロジック（時刻差と距離の許容範囲で対応付け）＋集計表示
- **難所**:
  - 照合の基準。検知は「地域単位」、気象庁発表は「震源」なので 1 対 1 に対応しない
  - 空振りの定義。人為ノイズを検知した場合と、気象庁が発表しない微小地震を検知した場合は区別すべき（60 の担当）
- **価値**: 検知エンジンに積み上げた設計の価値が数字で出る。**開発者にとっても利用者にとっても意味がある**

## 59. 検知の根拠開示

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤B・C` — **要否: 必要**

- **見え方**: 近傍一致した点・spread 値・どのゲートで確定したかを地図上で説明する
- **データ源**: 基盤B（onset 公開）＋基盤C
- **実装**: 検知エンジンが判定の中間状態を返す形に変える。表示は地図オーバーレイ＋パネル
- **難所**:
  - 中間状態の量が多い。毎秒 1725 点ぶんの内部値をすべて外へ出すのは重いので、**何を出すかの選別が設計の本体**
  - 8 と同じ基盤B を要求する。**同時に設計すること**
- **価値**: 「なぜ検知したか」が見えると、誤検知の議論が具体的になる。60 の前提でもある

## 60. 誤検知の分類

`関心 ○` `実現性 可` `規模 M` `依存 基盤C` — **要否: 必要**

- **見え方**: 検知履歴に「人為ノイズ／欠測グリッチ／実地震」のラベルを後から付けて蓄積する
- **実装**: 自動分類（気象庁発表との照合＋パターン）＋手動ラベル付け
- **難所**: 自動分類の精度。手動を許すと「誰がラベルを付けたか」で意味が変わる
- **価値**: 蓄積すると検知パラメータの調整根拠になる。**回帰ベンチの窓データ（`scripts/kyoshin-bench/windows.json`）と役割が近い**ため、両者の関係を決める必要がある

## 61. 検知ランキング

`関心 ○` `実現性 可` `規模 S` `依存 基盤C` — **要否: 必要**

- **見え方**: 過去の地震で「何秒早く出せたか」の履歴を並べる
- **実装**: 58 の副産物。58 を作れば表示形式を変えるだけ

## 91. K-NET / KiK-net からの過去強震データ再生

`関心 ◎` `実現性 条件付き` `規模 L` `依存 なし` — **要否: 必要**

- **やりたいこと**: 防災科研の強震観測網（K-NET / KiK-net）のアーカイブから過去の地震を持ってきて、**Yahoo の保持期間より前の地震を再生できるようにする**
- **なぜ今できないか**: 強震モニタのリプレイは「Yahoo が秒ファイルを保持している期間しか遡れない」（[kyoshinSource.ts:107](../src/services/kyoshinSource.ts:107)）。2011 年の東日本大震災や 1995 年の阪神・淡路を検知エンジンに流すことは現状できない

**アプリ側の受け入れ口は既に用意されている。** `kyoshinSource.ts` のヘッダに設計意図が明記されている。

> 将来、防災科研 K-NET のアーカイブなど「フレーム列が一度に手に入る」供給元を足す場合は、KyoshinSource を実装して start() の中でフレームをまとめて enqueue すればよい（下流は変更不要）

つまり**難所はアプリ側ではなく、データの入手と変換に集約される**。

- **入手の条件（調査済み。障壁はほぼ無い）**
  - **到達性は問題ない。** 実測すると `www.kyoshin.bosai.go.jp` は 302、`www.hinet.bosai.go.jp` は 200 を返す。到達できないのは `www.kmoni.bosai.go.jp`（強震モニタ）だけで、[CLAUDE.md](../CLAUDE.md) の「防災科研へ届かない」という記録は**このホストに限った話**だった
  - 認証は **HTTP Basic**（ユーザー登録は無料）。公式ページが `wget --http-user=... --http-password=...` の例を示しており、**スクリプトからの自動取得が想定されている**。同時接続数や頻度の制限は明示されていない
  - **資格情報は取得済み**（プロジェクト所有者が保有）。置き場所は既存の `DMDATA_API_KEY` と同じ `.env.local`（Git 管理外）にして、スクリプトが環境変数から読む形にする。**値をリポジトリに入れない**。ワークツリーでは `.env.local` が引き継がれない点も既存と同じ
  - URL は階層的（`all/zip/YYYY/MM/YYYYMMDDHHMISS/` で地震を指定）。ファイル名は観測点・時刻・成分の組（例: `MYG0041103111446.NS`）
  - 形式は **K-NET ASCII / Binary / CSV**。**CSV があるので、気象庁の震源カタログのような固定長パースは要らない**
  - 提供されるのは**イベント単位の波形**（加速度時系列）で、連続データではない
- **引用の義務**: 利用したことを明示し、DOI（`10.17598/NIED.0004`）を参考文献等に記載する。論文・発表・報告書を作成した場合は写しを提出する規定がある
- **難所（変換）**:
  - 波形から強震モニタ相当の値へ換算する必要がある。**リアルタイム震度は 1 秒ごとの独自演算**であり、気象庁の計測震度（60 秒の積算）とも別物。同じ値を再現できるとは限らない
  - 観測点の対応付け。強震モニタは**防災科研由来で約 1725 点**（[kyoshin-detection-spec.md](spec/kyoshin-detection-spec.md) §1）で、K-NET と KiK-net の合計とほぼ同規模。**集合が大きく違うわけではない**のは有利だが、点が 1 対 1 に揃う保証はない（Yahoo の公開座標は小数第 1 位までしか精度が無い点があり、実観測点が同一座標に潰れる事例が確認されている）。ただし**フレームは `sitesKey` で観測点集合を識別する設計**のため、別の観測点リストを持たせることは既存の枠内で可能
  - データ量。1 地震で全国分（K-NET・KiK-net で約 1700 点）× 数分の波形は数百 MB になる
- **難所（再配布）— ここが残る最大の論点**
  - **生成物をリポジトリにコミットできるか**。DMDATA の EEW と同種の問題（[settings-pwa-spec.md](spec/settings-pwa-spec.md) §6 の規約制限）
  - 公開されている利用条件からは**再配布の可否が読み取れなかった**（明示されているのは「利用の明示」「DOI の引用」「成果物の報告」まで）。**判断するには問い合わせが必要**
  - 認証を要するデータである以上、**再配布は許されない前提で設計するのが安全**
- **副産物: 3 成分の波形が揃う**。K-NET は南北・東西・上下を別ファイルで配信している（`.NS` / `.EW` / `.UD`）。項目 8 で「Yahoo のリアルタイム震度では取れない」と書いた**卓越方向が、過去データに対しては計算できる**。8 の目的（リアルタイムに震源方位を知る）には使えないが、8 の実装を検証する材料にはなる

**現実的な落としどころ: 開発者のローカル専用にする。**

- `scripts/` で波形 → フレーム列に変換し、`.gitignore` 対象のローカルファイルとして置く
- 用途は**検知エンジンの回帰検証**。別セッションのベンチ（`scripts/kyoshin-bench/windows.json`）と同じ位置づけで、**検証窓を 2011 年以前まで広げられる**
- 一般利用者向けには配布せず、開発ツールとして持つ

- **価値**: この形なら検証に使える地震が桁違いに増える。**東日本・阪神・中越といった教科書的な地震で検知性能を測れる**ようになるのは、パラメータ調整の根拠として大きい
- **残る未知は 1 つだけ**: **波形 → リアルタイム震度相当の換算が成立するか。** 到達性・認証・データ形式はすべて解決したので、ここだけは実装して実データで比べるまで分からない。成立しなければ「別の量」として扱うことになり、検知エンジンに流す値が変わるので検証の意味づけも変わる
- **決めるべきこと**: 一般公開する機能にするか、開発ツールに留めるか。**再配布の可否が不明な間は開発ツールに留めるのが安全**
- **代替案**: 気象庁の「震度データベース検索」は**観測点ごとの最終震度**（1 地震 1 値）を提供する。時系列ではないためリプレイには使えないが、基盤A（長期カタログ）の一部としては使える
