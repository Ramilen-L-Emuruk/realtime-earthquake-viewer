# 本番アプリ 移動中ベースライン（Surface Go 2・2026-07-27）— 体感が数字になった。段階0 は移動中に効かない

> 計測機: Surface Go 2（Windows・Edge 150・**vsync 16.7ms / 60Hz**・DPR 1.5・viewport 1272x768）
> 対象: **本番アプリ（現行 v3.23.1 相当・DMDSS 版）** — PoC ではない
> 計測器: `scripts/perf/measure-moving-baseline.js`（注入型・**本番コード非改変**）/ `measure-kyoshin-static.js`
> 依頼: [webgl-production-baseline-request.md](webgl-production-baseline-request.md)
> 証跡: 24件（静止2・地震情報タブ移動4・リアルタイムタブ移動9・自動ズーム3 ほか）
>
> **結論**
> - **アプリが重いのではなく、「動かしたときだけ」重い。** 静止時は **fps 57・DOM 書き込み 31/秒**で健全
> - **移動中は fps 13〜25・計測窓の 50〜66% が停止・1秒級のブロックが毎回**
> - **段階0（差分更新化）は移動中に効かない。** DOM 書き込みが **31/秒 → 12,563/秒（405倍）** に戻る。
>   これは**段階0 改修前（10,730/秒）すら上回る**
> - **主犯は2つ**: 静的パスの再描画（観測点なしでも fps 29〜39）＋ 観測点1,725点（さらに半減）

## 2. 読み取れること

### ① 静止時は健全。問題は「動かしたとき」に限られる

静止時は **fps 57.0/57.9・`p95` 17.0ms（1フレーム）・longtask 157〜372ms**。
非力機でもほぼ理論値どおり回っている。**段階0 の成果がここに出ている。**

ユーザーの体感が「**移動中**に明らかにコマ落ちして見える」と区間を限定したものだったのは、
**正確な観察だった**。

### ② 段階0 の差分更新は移動中に効かない

| 状態 | DOM 属性書き込み |
|---|---|
| 段階0 **改修前**（静止時・旧定義） | 10,368〜10,730 /秒 |
| 段階0 **改修後**（静止時・新定義） | **31〜36 /秒** |
| **移動中（pan）** | **8,919〜10,638 /秒** |
| **移動中（zoom）** | **11,842〜12,563 /秒** |

**静止時 → 移動中で 405倍。しかもズーム時は段階0 改修前を上回る。**

**機序**: 差分更新は「値が変わった点だけ書き換える」方式だが、
**地図が動けば全点の座標が変わる**ため、全点書き換えに戻る。
**依頼書 §1④ で立てた仮説（未検証）が、実測で確認された。**

### ③ 体感の正体は「断続的な停止」であって「一様な遅さ」ではない

**全区間で `frame.p50` が 16.7〜16.8ms（1フレーム）。**
中央のフレームは正常に描けている。それでも fps が 13〜25 に落ちるのは、
**時々 1秒級で完全に止まる**ため。

| 区間 | `p50` | `blockMaxMs` |
|---|---|---|
| リアルタイム pan | 16.7〜16.8ms | **1,043〜1,173ms** |
| リアルタイム zoom | 16.7ms | 590〜910ms |

**「もっさり遅い」ではなく「カクッと引っかかる」**——
ユーザーが「コマ落ちして**いるように見える**」と表現したことと符合する。

### ④ 主犯は2つあり、片方だけでは足りない

| 状態 | fps |
|---|---|
| 地震情報タブ（観測点なし）で移動 | **29.4〜38.8** |
| リアルタイムタブ（観測点1,725点）で移動 | **16.8〜24.9** |

**観測点なしでも fps 30 前後まで落ちる。** つまり
**活断層・プレート境界・県境などの静的パスの再描画だけで、既に半分**。
そこに観測点1,725点が乗って**さらに半減**する。

**毎秒更新（層 A）だけを対策しても届かない。**

### ⑤ ズームがパンより重い

fps 13.0〜20.1（zoom）対 16.8〜24.9（pan）。DOM 書き込みも 12,563 対 10,638 でズームが上。
ズームは全点の座標に加えて**半径・スケールも変わる**ためと考えられる（**機序は未測定**）。

### ⑥ 自動ズームの平均値は誤読を招く

`fps 54.2〜56.3`・`p95 16.8ms` は一見「快適」に見えるが、
**20秒の計測窓に対し実際に動いているのは flyTo の 1秒だけ**で、
残り19秒の静止に平均が薄められている。DOM 書き込み 403/秒 × 20秒 ≈ 8,000回で、
**pan の1秒あたりとほぼ同じ**——飛行の1秒で全部書いている。

**読むべきは `blockMaxMs` 178〜364ms**（PoC の Leaflet 着地 129〜575ms と同じ帯）。
**`blockMaxMs` を入れていなければ「自動ズームは fps 54 で快適」という真逆の結論を書いていた。**

## 3. 移行判断への含意

**GO は動かない。** 一本化の根拠は検証項目2（毎フレーム全画面再描画で 9倍以上）であり、
本計測はそれを**本番の実データで裏付けた**形になる。

**加えて「安い手で埋められるか」の見通しが変わった。**

- 段階0（層 A・毎秒更新の差分化）は**静止時にしか効かない**ことが確定した
- 移動中の書き換えは **Leaflet の SVG レンダラーが座標変換のたびに全要素の属性を書き直す**構造から来ており、
  アプリ側の工夫で回避しにくい（**機序の詳細は未測定**）
- 観測点を止めても fps 30 前後止まりで、**体感の解消には届かない**

**したがって「移行せずに直せる余地」は、静止時に比べて小さいと考えられる。**
ただしこれは本計測から導いた**推論であり、代替策を実装して測ったわけではない**。

## 4. 計測の限界・未検証事項

- **手動パン/ズームは人の操作に依存する**。操作の激しさで DOM 書き込みが 2,637〜7,915/秒 と
  3倍ばらついた回がある（地震情報タブ pan）。区間内の操作量は制御していない
- **`mode` は推定値**（`pathCount > 1000 ? 'kyoshin' : 'unknown'`）で、地図モードを直接取得していない。
  実際の切り分けは `kyoshinActive` / `pathCount` で行った
- 静止時の**段階0 改修前（before）は旧定義（名目割り）のまま**であり、本文書の新定義の値と
  厳密には比較できない（改修前コードが必要なため測り直し不能）。
  ただし差が 405倍あり、定義差（数%）は結論に影響しない
- **ズームがパンより重い機序**は未測定
- 自動ズームは **n=3 でばらつきが大きい**（`blockMaxMs` 178〜364ms）

## 5. 経緯の記録（計測条件の取り違え）

初回4件は**地震情報タブ**で計測されており、観測点が乗っていなかった
（`kyoshinActive: false`・`pathCount: 0`）。ユーザーの申告により判明し、
リアルタイムタブで測り直した。

**この取り違えは結果的に有益だった**——観測点なしの対照が得られ、
上記④「主犯は2つ」の切り分けが可能になった。意図せず作られた対照実験である。

なお、この間レビュー側は**観測点が出ない原因を「強震モニタへの 403」と誤診した**。
実際には `CLAUDE.md` に「未登録秒を叩いて 403→200 の境界を捉える較正の**正常動作**」と
明記されており、**タブが違っただけ**だった。プロジェクトのドキュメントに答えがあったにもかかわらず、
目の前のエラーだけを見て「9時間の時刻ずれ」「本番の実バグの可能性」まで組み立てた。
**片方の証拠から断定する**という、本計画で繰り返し踏んでいる失敗の再発である。
