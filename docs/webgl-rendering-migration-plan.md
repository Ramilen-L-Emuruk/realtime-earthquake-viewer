## 1. 背景と目的

- 非力な PC でアプリの動作が重いという報告がある。
- 負荷軽減のため、**ビルド時に地図・活断層などの頂点を間引いている**（`scripts/build-*.mjs`）。本来はフル解像度で表示したいが、描画負荷のために削らざるを得ない状況。
- **目標**: 地図描画を GPU 基盤へ一本化し、間引きをやめてフル解像度で表示しても軽く動くようにする。見た目・挙動は現行と完全に同一を維持する。
- **一本化の意図**: 「Leaflet(CPU 土台) + WebGL オーバーレイ」の二重構造は、両者の投影・アニメを毎フレーム同期させる弱点を抱える。中途半端な二重管理を避け、地図基盤ごと単一の GPU エンジン（MapLibre GL JS）へ統一する。

## 2. 現状分析（調査結果）

### 2.1 実測（Playwright + Performance 計測）

計測環境: dev（DMDSS 版）、`devicePixelRatio=1`、viewport 1837×965。**このマシンは非力ではない**点に留意（＝定常コストが 60fps に吸収されて見えている）。

| 局面 | 平均 FPS | ロングタスク | DOM 属性更新 | メモリ |
|---|---|---|---|---|
| リアルタイムモード・静止 12 秒 | 59.2（最低 56） | 0 件 | **527 回/秒**（追加・削除 0） | 63.9→66.5MB（安定） |
| 設定タブ・静止（点描画なし） | 60 | 0 件 | 0 | 安定 |

- **静止時の定常コスト**として毎秒 527 回の属性更新が発生。高性能機では 60fps に吸収されるが、非力機では体感の重さに直結すると考えられる。
- **【注意】「527 回/秒」は計測手順が未記録**（何をどうカウントしたか不明）で、このままでは再現・比較に使えない。桁の検算にも疑義がある: Leaflet の SVG レンダラは `setStyle` で `fill`/`fill-opacity`/`fill-rule`/`stroke`、`setRadius` で `d` を毎回 `setAttribute` するため、約1,725点の無条件全点更新なら素朴には数千回/秒の属性更新になるはず。「主因 = `KyoshinPoints` の無条件全点更新」という因果づけ自体は §2.2 のコード読解と整合するが、数値は鵜呑みにせず、段階0 の再計測（§6）で計測スクリプトと数え方を記録した上で改修前（before）から測り直す。
  - **【2026-07-25 再計測済み】実際は約 10,370 回/秒**（1,725 点 × 6 属性/秒）で「527 回/秒」は桁誤りだった。属性 6 の内訳と before/after の全数値は §6「結果記録」参照。
- **CPU スロットル検証（6 倍）＋ 自動マウスドラッグ ＋ CDP セッション**の三重掛けでレンダラがクラッシュ。これは**計測器側の事故の公算が高く、アプリの欠陥とは断定しない**。PoC では倍率を 4 倍程度に緩め、操作も穏やかにする。
- **パン/ズーム操作時の実測は未取得**（上記クラッシュで中断）。PoC で取得する。

### 2.2 描画方式の現状

**強震モニタの点（`mode === 'kyoshin'`）** — 4 レイヤーすべて共有ペイン `kyoshin-points`・`interactive:false`・`pointerEvents:none`（クリック・ホバー不使用）:

| レイヤー | 対象 | 実装 | 毎秒の更新 |
|---|---|---|---|
| `KyoshinPoints` | 震度1以上（index 7+） | `L.circleMarker` 約1725点・SVG レンダラ | **全点を無条件に `setRadius`+`setStyle`（差分なし）** |
| `KyoshinSubThreshold` | 震度0以下（index 1-6） | 生 SVG `<circle>`・レベル別 `<g opacity>` で非加算合成 | **変化した点だけ**グループ付け替え（差分更新済み） |
| `KyoshinDetectedPoints` | 確定検知点 | 生 SVG・数十点 | 毎回フル作り直し（点数が少なく軽い） |
| `KyoshinMaxEffect` | 最大震度の波紋 | 生 SVG `<circle>`・rAF | 同時 0〜1 個の短命アニメ（600ms） |

- **SVG を使う理由（コード内コメント）**: 過去に canvas 実装で flyTo/ズームアニメ中に巨大バッファの再合成が重く撤退した経緯があり、SVG＋`transform` 追従に移行済み。
- 毎秒の定常コストの主因は `KyoshinPoints` の無条件全点更新（他レイヤーは差分更新・少数で軽い）。

**活断層（`ActiveFaultsLayer`）**:

- 約 580 セグメント（3,400 本超のライン）を `L.polyline`（SVG レンダラ）で描画。
- **クリックでポップアップ（地名表示）を持つ** — 可視線は `interactive:false`、当たり判定は同一形状の透明 `L.polyline`（Canvas レンダラ・tolerance 付き）に `bindPopup` して委譲。線から数 px ずれてもポップアップが開く。
- マウント時に 1 度だけ Leaflet レイヤーを構築し、以降は表示/非表示の切替のみ。

**ベースマップ（`BaseMap` / `JapanMap`）**: 背景ラスタータイル（`tile-pane` に img。GPU 合成され元々軽い）、県境・一次細分区域・海岸線・ラベル。詳細は本設計時に精査する。

### 2.3 間引きの実態と理由

- ビルド時に Douglas-Peucker で頂点を削減: `build-active-faults.mjs`（`EPSILON=0.002` 度 ≒ 220m）、`build-prefectures.mjs`、`build-subregions.mjs`、`build-tsunami-zones.mjs`。
- **理由は「描画負荷」**（データ量・転送ではない）。`ActiveFaultsLayer` のコメント（毎秒再レンダーで全本数の差分計算が重い → レイヤー数・頂点数を削減）が根拠。`build-prefectures.mjs` にも「拡大時の崩れを抑えるため詳細を残す」とあり、負荷制約下で本意でなく削っていることが読み取れる。
- 生成 JSON（`public/data/*.json`）は初回 1 回の fetch/parse のみで、継続的な負荷ではない。
- **結論**: 描画負荷が理由である以上、GPU 描画に移せば間引きをやめられる見込みが高い。

### 2.4 問題の二層構造（重要な前提）

現状の「重さ」は性質の異なる 2 つの負荷に分解できる。方式判断と PoC 設計はこの分解を前提にする。**両者を分けずに測ると、全面リライトの効果を過大評価する。**

| 層 | 症状 | 主因 | 解の粒度 |
|---|---|---|---|
| **A. 静止時の定常負荷** | 無操作でも毎秒約 10,370 回（2026-07-25 再計測・§6 結果記録）の DOM 属性更新 | `KyoshinPoints` の無条件全点 `setRadius`+`setStyle`（差分なし）。ほかに毎秒の React 再レンダー（第二成分・§6 結果記録） | **安価** — Leaflet のまま差分更新化。隣の `KyoshinSubThreshold` が既に実装済みの方式を移植するだけ（数十行）→ **実施済み（§6 結果記録）** |
| **B. フル解像度の線/面の描画負荷** | 間引きをやめると線・面が増え重くなる | 多頂点の SVG ペイント | **高価** — GPU 化（＝MapLibre）が要る。ただし律速がフィルレートなら GPU 化でも解決しない恐れ（§8） |

- **層 A は MapLibre 一本化を待たずに単独で潰せる。** 全面リライトの投資判断の前に、まず層 A を差分更新化して実機で測り、「目的（非力機の軽量化）の何割が層 A の解消で埋まるか」を把握する（→ §6 段階0）。
- **層 B こそが MapLibre 一本化の本来の動機。** ただし層 B の律速が「頂点処理・ドローコール」なら GPU 化で効くが、「フィルレート（画面を塗るピクセル速度）」なら描画 API を変えても効かない。間引き（Douglas-Peucker）は形状保存のため、廃止で増えるのは頂点数であって塗り面積はほぼ不変 — つまりフィルレート律速だと間引き廃止は効きも悪化もせず、当初目的（フル解像度化）自体が効果対象外になる。加えて描画モデルの差も逆風になりうる: Leaflet のパンは CSS transform のコンポジタ合成のみで再ペイントがほぼ走らないのに対し、WebGL 地図はカメラ操作中に毎フレーム全ビューポートを描き直す（→ §6 検証項目1 で切り分け、判明時は §6「フィルレート律速だった場合の分岐」へ）。

## 3. 方式判断の経緯

判断は 3 段階で行った。すべての経緯を記録する。

### 第 1 段階: 描画技術（canvas / WebGL / SVG 差分）

| 観点 | 自前 canvas | WebGL | 現行 SVG を差分更新 |
|---|---|---|---|
| 静止時の毎秒負荷 | 極小 | 極小 | 小（変化点のみ） |
| パン/ズーム操作時 | 軽い | 最軽 | 要素数の壁が残る |
| フル解像度の線/面 | 要素増で徐々に重い | GPU で軽い | 重い（不可に近い） |
| 依存追加 | なし | あり | なし |
| 実装量/リスク | 中 | 大 | 小 |

- **層 A（静止時負荷）** は「現行 SVG を差分更新」で十分に潰せる（§2.4）。安価なので全面リライトの前にまず実施・実測する（→ §6 段階0）。
- **層 B（フル解像度の線/面）** は canvas/SVG では要素数・ペイントの壁に当たる → GPU（**WebGL**）が要る。真の要件「**地図・活断層をフル解像度で軽く**」はこちらで、以降の一本化議論は層 B を対象とする。

### 第 2 段階: WebGL の実装形態（二本立て / 一本化）

| | MapLibre 一本化（採用） | Leaflet + deck.gl 二本立て |
|---|---|---|
| CPU/GPU 同期問題 | **消える（単一エンジン）** | 残る（要検証） |
| 間引き廃止 | 完全 | 完全 |
| 描画の軽さ | GPU で統一 | GPU（オーバーレイのみ） |
| flyTo/当たり判定 | ネイティブで綺麗 | Leaflet 流用 |
| 将来性（ベクタータイル/3D） | ◎ | △ |
| 作業量/回帰リスク | 全面リライト | オーバーレイのみ |
| バンドルサイズ | 重い（実行時は軽い） | 中 |

- 二本立ては Leaflet(CPU 投影・アニメ) と deck.gl(GPU) を毎フレーム同期させる中途半端さが残る。これを嫌い、**地図基盤ごと MapLibre GL JS へ一本化する**方針を採用。deck.gl は不要になる（MapLibre 単体で点・線・面・当たり判定・GPU 描画・flyTo が揃うため）。

### 第 3 段階: 描画バックエンド（WebGL2 / WebGPU）— ターゲット実機 Surface Go 2

- **ターゲット実機は Surface Go 2**: Pentium Gold 4425Y / Core m3-8100Y、GPU **Intel UHD Graphics 615**（2018 年世代・最下位クラスの統合 GPU）、10.5" 1920×1280・220ppi（Windows スケーリング 150% 前提で実効 DPR ≒ 1.5）、RAM 4〜8GB。**「弱い統合 GPU × 高精細画面」が負荷特性の核**。
- **WebGPU は不採用**。理由:
  1. **動作保証がない** — Chrome 113+ で既定有効だが、クラッシュ・不正描画・脆弱性のあるドライバを外す**ブロックリスト**があり、UHD 615 のような旧世代の弱 GPU は対象になりやすい。無効化されると WebGL2 フォールバックに落ちるため、**WebGPU 前提で作っても実機では WebGL2 で動く公算**が高い。
  2. **動いても効果が限定的** — UHD 615 は生の GPU 性能が低く、WebGPU の利点（ドローコール削減・計算シェーダ）の恩恵が小さい。
  3. **真の律速に効かない** — 220ppi を弱 GPU で毎フレーム塗る**フィルレート**が律速になりうる。描画 API を WebGPU に変えても解決しない（DPR 抑制など別対策の領域）。
- **採用は WebGL2（＝ MapLibre）**。UHD 615 でも枯れた WebGL2 は安定動作し、ブロックリストのリスクも WebGPU より低い。
- **将来性は MapLibre 経由で獲得する** — MapLibre の WebGPU バックエンド対応が実用化すれば、エンジン更新で自動的に恩恵を受けられる（自前 WebGPU 実装は不要）。これにより「一本化」と「将来性」を両立する。

## 4. 採用アーキテクチャ（MapLibre 一本化）

**MapLibre GL JS を唯一の地図・描画エンジンとする。** Leaflet / react-leaflet / deck.gl は廃止する。

- 背景タイル → MapLibre のラスタータイルソース（現行の地理院系タイルを移設）
- 点（強震点・観測点）→ circle レイヤー。色は index の data-driven styling、更新は feature-state または GeoJSON `setData`
- 線（活断層・海岸線）→ line レイヤー（フル解像度でも GPU で軽い）
- 面（県境・一次細分区域塗り）→ fill レイヤー
- 当たり判定（活断層ポップアップ等）→ `queryRenderedFeatures`
- カメラ操作（flyTo・パン・ズーム）→ MapLibre ネイティブ（`flyToLite` の自前実装は廃止）
- 特殊合成・アニメ（`KyoshinSubThreshold` の非加算合成、波紋、予報円拡大）→ 標準レイヤーで表現できない場合は MapLibre のカスタムレイヤー（WebGL 直書き）で実装

**投影の追い風**: MapLibre も Leaflet も Web メルカトル（EPSG:3857）。既存の `public/data/*.json` の座標はそのまま使える見込み（GeoJSON は `[lng, lat]` 順のため並び順の変換は要る）。

**React 統合**: MapLibre GL JS はバニラ JS。統合方式（`react-map-gl` を使う / `maplibre-gl` を直接 `useRef`+`useEffect` で制御）は本設計着手時に Context7 で最新事情を確認して確定する。現行レイヤーが命令的（`useMap`+`useEffect` で Leaflet API 直叩き）なので、`maplibre-gl` 直制御とも親和性はある。

## 5. 保つべき挙動（回帰防止チェックリスト）

移行後も以下を現行と同一に保つ（括弧内は MapLibre での実現手段の当たり）:

- **強震点**: 気象庁配色 / `SHINDO0_COLOR`、半径 `BASE_RADIUS(2.5) × iconScale`、index 別表示規則（0＝非表示 / 1-6＝半透明合成 / 7+＝不透明 0.85）、カメラ追従、非インタラクティブ。
- **`KyoshinSubThreshold`**: 指数カーブの不透明度（index 0→0、index 6→0.35）と二層の合成規則 — **①同一レベル内は重なっても濃くならない**（レベルごとの `<g opacity>` に circle を格納し、グループを一枚に合成してから opacity を掛ける）／**②異なるレベル間の重なりは素直に濃くなる**（別グループのため）。（→ MapLibre の circle は同一レイヤー内でも通常のアルファブレンド（over 合成）で重なりが蓄積して濃くなるため、「レベルごとに別レイヤー化＋各レイヤー内の重なりを潰す」再現が要る。標準スタイルでは不可でカスタムレイヤー行きの公算 = PoC 項目5）
- **`KyoshinDetectedPoints`**: 震度に応じた可変サイズ、確定点による上書き、低→高震度の順の重ね。
- **`KyoshinMaxEffect`**: 最大震度更新時の波紋アニメ（600ms、index 7 以上でトリガ）。
- **活断層**: 色 `#c2410c` / 太さ 1.2 / 不透明度 0.65、**クリックで地名ポップアップ**（線近傍の tolerance 相当）。（→ `queryRenderedFeatures`）
- **ベースマップ**: 背景タイル、県境・一次細分区域・海岸線・ラベルの見た目。（ラベルは現状 DOM = `L.marker`+`divIcon`。MapLibre での実現方式は §8「テキスト描画」参照）
- **その他の地図連携機能**（付録参照）: EEW 震源マーカー・予報円、津波海岸線、地震マーカー・震度集約、ヒートマップ、検知点、自動フィット（`FitToDetection`/`FitToCandidate`）、flyTo。
- 2 バリアント（standard / DMDSS）双方で成立すること。

## 6. PoC 計画（律速分解を軸に）

### 目的

全面リライトに踏み込む前に、**(a) 層 A の安価な改善でどこまで軽くなるか**・**(b) 層 B の律速が CPU かフィルレートか**を先に確定し、その上で **MapLibre 一本化の致命的リスクを薄い縦切りの PoC で潰す**。使い捨てブランチでの最小実装で本体への統合は不要（ただし段階0 の差分更新化は有効なら本採用してよい）。

### 段階0: 層 A の安価な中間改善を先に実測（全面リライトの前段）

- `KyoshinPoints` の毎秒更新を、隣の `KyoshinSubThreshold` と同じ**差分更新**（前回 index を保持し、変化した点だけ `setStyle`/`setRadius`）に書き換える。Leaflet のまま・数十行。
  - **実装注意**: 差分経路だけでは `iconScale` 変更時に index 据え置きの点が取り残される。`KyoshinSubThreshold` と同様、「indices の差分更新」と「iconScale 変更時の全点再適用」の二経路に分ける（同ファイルの drawFn コメント参照）。
- 静止時の DOM 属性更新（層 A）がどこまで下がるかを、**開発機の CPU スロットルと実機（Surface Go 2）の両方で**実測する。
  - **計測方法を記録する**: §2.1 の「527 回/秒」は手順未記録で再現できない（§2.1 注記）。改修前（before）から同一手順で測り直し、計測スクリプトと数え方を残す。
  - **主指標はフレーム時間**: DOM 属性更新回数は中間指標にとどめ、判断は体感に直結するフレーム時間の分布（p95）とロングタスクで行う。
- **判断**: 層 A の解消だけで実機の体感が十分軽くなるなら、全面リライト（層 B 対応）の緊急度は下がる。層 B が実機で明確なボトルネックだと確認できてから全面リライトへ進む。

### 検証項目（この順で潰す）

1. **律速の切り分け（最優先）**: 層 B の重さの正体が **CPU（頂点処理・JS）** か **GPU フィルレート（塗り面積）** かを分解する。ここを外すと PoC 結果を誤読する（切り分け方法は下記「測定方法」参照）。
   - **フィルレート律速だった場合、間引き廃止は効かない**（形状保存の間引きを廃止しても塗り面積はほぼ不変。§2.4）。判明した場合は下記「フィルレート律速だった場合の分岐」に従い対策を組み替える。
   - **【2026-07-25 実機3回計測・決着済み】結論: 律速に到達しない。** 塗り面積を 0.98M→**3.91M px（4.0 倍）**・線幅を 1.2→**12（10 倍）**・頂点を 9,874↔31,646 と振り、両者を重ねた `overload`（3.91M px ＋ 線幅 12）まで負荷を上げても、**全 19 計測が p95 16.9〜17.0ms・fps 58〜60** で vsync 天井（16.7ms）を破らなかった。フィルレート律速でも CPU/頂点律速でもなく、**実配置の 1.8 倍以上の負荷まで律速に届かない**（＝下記「フィルレート律速だった場合の分岐」は発動しない）。**間引き廃止は描画コストの観点で青信号**（フル 31,646 頂点と間引き後 9,874 頂点で p95 の差が測定不能）。
     - 1・2回目は**判定不成立**だった。pan・zoom とも飽和した baseline から負荷を**下げて**振っていたため何も測れておらず、さらに 1回目に zoom で見えた劣化（33.3ms）は**タイル初回読み込みのウォームアップ交絡**だった（3回目の `baseline-warm` 対照 16.9ms で確定）。経緯と撤回した主張は下記「結果記録」、スイート改訂のレビューは [webgl-poc-review-4b0517c.md](webgl-poc-review-4b0517c.md)。
     - **残る論点**（層 B の外）: 検証項目2 の Leaflet 比較（未実施）・検証項目5 非加算合成・毎秒更新・EEW 複合負荷・真の実行時メモリ。観点は [webgl-layerb-verification-points.md](webgl-layerb-verification-points.md)。
2. **フル解像度描画の軽さ**: MapLibre で 背景タイル＋県境＋**間引き前フル解像度の活断層**＋強震点を描画し、非力機相当（CPU 4 倍スロットル・実機）でも現行以上に軽い（パン/ズーム時のロングタスク減・FPS 同等以上）。
3. **カメラ操作の滑らかさ**: flyTo・パン・ズームがスロットル下・実機で滑らか。
4. **当たり判定**: 活断層クリックで `queryRenderedFeatures` によりポップアップが線近傍で開く（現行 tolerance 相当）。
5. **非加算合成の再現**: `KyoshinSubThreshold` の **①同一レベル内は重なっても濃くならない／②レベル間は素直に濃くなる** の二層挙動を再現できるか（**WebGL 共通の最難関。抜けると見た目が変わる**）。標準 circle レイヤーは同一レイヤー内でも通常のアルファブレンド（over 合成）で重なりが濃くなるため、レベルごとに別レイヤー化＋各レイヤー内の重なり潰し（ステンシル/デプス等のカスタムレイヤー）が要る公算。
6. **毎秒更新のコスト**: 強震点の index 更新を feature-state か `setData` で軽く回せるか。**注意: WebGL は 1 点の変化でも全ビューポート再描画になる**（Leaflet+SVG の静止時は変化領域のみ再ペイント）。層 A の「毎秒の属性更新」が MapLibre 化後は「毎秒 1 回の全画面描画」へ置き換わるため、フィルレート律速の実機で毎秒のカクつきとして体感されないかを確認する。
7. **EEW 発報シナリオの複合負荷**: flyTo＋予報円アニメ＋毎秒更新が同時に走る、最も性能が問われる瞬間をシナリオ化して測る（設定タブの EEW テストで再現可）。PoC 実装に EEW 系が無い段階ではカメラ操作＋点更新＋円アニメの同時実行で代替し、レイヤー移植後の回帰検証で本シナリオを必須にする。

### 測定方法

**律速の切り分け（項目1）——最初にやる**:

律速が CPU か GPU フィルレートかは、負荷の"次元"を独立に振って FPS の反応を見て分離する。以下 3 軸の反応表を作れば律速要因が一意に定まる。

- **DPR（内部解像度）を振る**: `deviceScaleFactor` を 1.0 / 1.5 / 2.0 と変える（`Emulation.setDeviceMetricsOverride`、または描画バッファ解像度）。塗る面積は DPR² に比例するので、**DPR を下げただけで FPS が大きく改善するなら GPU フィルレート律速**。
- **CPU スロットルを振る**: `Emulation.setCPUThrottlingRate` を 1×/2×/4× と変える。DPR 一定でスロットル倍率にほぼ比例して悪化するなら **CPU 律速**。
- **塗り面積 vs 頂点数を別々に振る**: 活断層の線幅・面塗り有無（＝被覆ピクセル）と、頂点密度（間引き前/後＝頂点数）を独立に変える。線幅を増やすと悪化し頂点を増やしても変わらないなら **フィルレート律速**、頂点数に比例して悪化するなら **CPU/頂点処理律速**。
- **GPU 実測**: Chrome DevTools Performance の GPU トラック、`chrome://gpu`、`chrome://tracing`（gpu カテゴリ）で GPU フレーム時間を直接確認する。

**FPS・ロングタスク**:

- Playwright + CDP。静止 / パン / ズームの 3 局面で FPS・ロングタスク（>50ms）を `PerformanceObserver` で計測。比較対象は現行実装（Leaflet）。
- マウス自動操作は穏やかに、または MapLibre のカメラ API（`panBy`/`zoomTo`/`flyTo`）で代替。CPU スロットルは rate 4（6 倍はクラッシュしたため緩和）。
- **実機ではメモリも測る**（`performance.memory`・タスクマネージャ）。RAM 4GB 構成では実行時メモリがタブキル・context lost の誘因になるため、Leaflet 版との差分を記録する。

**実機（Surface Go 2）を前倒しする**:

- CPU スロットルは CPU 性能しか模擬できず、**UHD 615 の GPU 性能・220ppi の高精細は実機でしか再現できない**。よって**律速の切り分け（項目1）は開発機では原理的に判定不能**。薄い PoC を早期に Surface Go 2 実機へ載せ、上記 3 軸を実機で振ることを **PoC 最初のマイルストーン**にする。
- PoC ビルドは GitHub Pages のブランチ、または同一 LAN の dev サーバーへ出す。実機で律速が判明して初めて下記「フィルレート律速だった場合の分岐」が引ける。ここまで通って初めて全面リライトの確信が持てる。

### フィルレート律速だった場合の分岐

律速がフィルレートと判明しても「一本化 or 別対策」の二者択一ではない。判断変数は「一本化する/しない」「間引きを廃止する/しない」「DPR を抑える/抑えない」の 3 つで、律速の正体が決めるのはこの組み合わせである。

- **間引き廃止は保留** — 間引き（Douglas-Peucker）は形状保存のため、廃止で増えるのは頂点数であり塗り面積はほぼ不変（§2.4）。フィルレート律速には効きも悪化もせず、当初目的（フル解像度化）自体が効果対象外になる。
- **DPR 抑制が本命対策** — 塗り面積は DPR² に比例するため、実効 DPR ≒ 1.5 の描画バッファを 1.0 相当へ抑えれば塗り面積は半分以下になる。見た目の精細さ（ぼやけ）とのトレードオフは実機で確認する。
- **DPR 抑制の実装手段が一本化の是非を左右する** — MapLibre はコンストラクタの `pixelRatio` オプションで描画バッファ解像度を CSS 解像度から切り離せる（API 詳細は本設計時に Context7 で裏取り）。一方、現行 Leaflet+SVG は SVG をブラウザがデバイス解像度でラスタライズするため DPR 抑制の実装余地がほぼ無い（Canvas レンダラはズームアニメ中の再合成コストで撤退済み・§2.2）。よってフィルレート律速でも一本化は自動的に NO-GO にはならず、**「`pixelRatio` 抑制の手段として全面リライトのコストに見合うか」を改めて判断する**。

- フル解像度データ生成: `build-active-faults.mjs` の `EPSILON` を 0（または大幅に小さく）にして再生成し、**間引き前後の頂点数を記録**する。

## 7. PoC 後の本設計・移行戦略

## 8. リスクと未確定事項

- **全面リライトの回帰リスク** — 地図連携の全機能（付録）を再実装・再検証する必要がある。最大のリスク。
- **非加算 opacity 合成の再現**（`KyoshinSubThreshold`）— WebGL 共通の最難関。カスタムレイヤーが必要になる可能性。PoC 項目 5。
- **非力 GPU での MapLibre 安定性** — 目的（非力機の軽量化）と逆行しないか。フォールバックの要否を検討。
- **WebGL コンテキストロストからの復帰** — GPU リセット・ドライバ再起動・メモリ逼迫（RAM 4〜8GB）でコンテキストが失われると、SVG/DOM と異なり WebGL 地図は描画ごと消える。常時表示の防災用途では「地震発生の瞬間に地図が黒画面」が最悪の障害モード。MapLibre の復帰挙動（自動リストアの可否・イベント）を PoC で確認し、復帰失敗時のフォールバック（再初期化・リロード誘導）を本設計に含める。
- **【最重要 / PoC 項目1 へ昇格】高精細 × 弱 GPU のフィルレート律速**（Surface Go 2 の 220ppi × UHD 615）— GPU 化しても「画面全体を塗る速度」が壁になりうる。**この場合、間引き廃止（フル解像度化）は効果対象外になり一本化の本来の動機が消える**うえ、WebGL 地図はカメラ操作中に毎フレーム全ビューポートを描き直すため、コンポジタ合成で済む Leaflet のパンより塗りが増える局面もある。単なるリスクではなく、全面リライトの GO/NO-GO を分ける前提条件。§6「フィルレート律速だった場合の分岐」に従い実機 PoC で最優先に見極める。
- **層 A と層 B の混同**（§2.4）— 「静止時の重さ」（層 A・安価に解消可）と「フル解像度の重さ」（層 B・GPU 化が要る）を分けずに測ると、全面リライトの効果を過大評価する。段階0 で層 A を先に潰し、残差として層 B を測る。
- **バンドルサイズ / PWA 初回ロード** — MapLibre は Leaflet より重い（実行時は GPU で軽くなる想定だが、初回ロードは要計測）。
- **実行時メモリ（RAM 4GB 実機）** — バンドルサイズ（転送量）とは別軸で、WebGL バッファ・グリフアトラス等の実行時メモリが Leaflet 比で増える。4GB 構成ではタブキル・context lost の誘因になるため、実機 PoC で計測する（§6 測定方法）。
- **投影・座標の差異** — Web メルカトルで一致する見込みだが、`[lng,lat]` 並びや境界の扱いを PoC で確認。
- **背景タイル** — 現行タイル（`TileTintLayer` 含む色調整）の MapLibre での再現。
- **テキスト描画（ラベル・ツールチップ）** — 現状のラベルは全て DOM（地方/県/区域名 = `L.marker`+`divIcon`、ヒートマップの `Tooltip` 等）。MapLibre で GPU 描画するには symbol レイヤー＋**日本語グリフ（フォント PBF）の自前生成・ホスト**（GitHub Pages）が要り、地図描画とは別種の準備物になる。少数のラベルは MapLibre の Marker（DOM）で妥協する現実解もあるが、「一本化」の定義を緩める判断のため本設計前に決める。数百〜数千規模の点（`IntensityPoints` は divIcon が重く SVG へ集約した経緯あり）は DOM 妥協が効かず、文字/アイコン付きなら symbol レイヤーが必須。
- **React 統合方式・MapLibre 最新 API** — 本設計時に Context7 で裏取り（未確定）。
- **学習コスト・工数** — Leaflet 資産を捨てるため相応の工数。
- **2 バリアントの地図描画は共通** — standard / DMDSS の差はデータソース側で、地図描画レイヤー自体はバリアント非依存の見込み。PoC・移行は実質 1 系統で足りる（要確認）。§5 の「双方で成立」は主にデータ連携部分の話。
