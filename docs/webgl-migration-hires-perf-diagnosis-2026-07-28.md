# maxload-eew劣化の原因切り分け結果（Surface Go 2・2026-07-28・v2ハーネス）

> 前提: [webgl-migration-hires-perf-surface-go2-2026-07-28.md](webgl-migration-hires-perf-surface-go2-2026-07-28.md)
> （n=3でmaxload-eewの再現性ある劣化をHIGHで確認）
> 分離シナリオ: `b9f5b95`（[レビュー](webgl-migration-review-b9f5b95.md)）・
> `2b8eabc`（[レビュー](webgl-migration-review-2b8eabc.md)）
> 証跡: `perf-2026-07-28T06-51-07-surface-go2-hires-v2.json`（リロード直後・8シナリオ）
>
> **結論: maxload-eewの劣化は「カメラ移動」単独でも「複合再描画の持続」単独でもなく、
> 両者の組み合わせ、特に【EEWテストの震源(三陸沖・最も密なリアス海岸の直近)へのカメラ移動】が
> 支配的要因である強い状況証拠を得た。**

## 2. 決定的な手がかり: `detect`が震源のロケーションを裏付けた

`maxload-eew`の`detectMid`（計測窓60%地点）と`detect`（終端）が**両方とも**、land-fill・sub-borders・
pref-borders・active-faults・kyoshin-points・eew-region-fillすべて**0**を示している
（`plate-boundaries`のみ4）。これは「終端でカメラが海上に出る」だけでなく、**計測窓のほぼ全域で
カメラが陸地の外（沖合）に留まっている**ことを意味する。

一方`eew-static`（定点固定・東北の陸を広く映す）は同じ複合負荷を抱えながら
land-fill 34・sub-borders 50・kyoshin-points 148・eew-region-fill 22と、しっかり負荷を踏んでいる
ことが確認できる。

**EEW特別警報テストの震源座標を確認したところ、`src/utils/testData.ts`の`createTestEEW`は
`hypocenter: { latitude: 38.1, longitude: 142.9 }`＝「三陸沖」だった。** この地点は、これまでの
高精細化コミット（`a455644`）のコミットメッセージで**繰り返し「三陸リアス海岸(ズーム10.5)」が
角張り解消の確認地点として言及されてきた、基図の中で最も頂点密度が高い海岸線の直近**である。

## 3. 数字が示す非加算的な悪化

| シナリオ | ブロック率 | 単独要因 |
|---|---|---|
| flyto-widezoom-quake | 3.8% | カメラ移動のみ（別ルート・密度の低い区間） |
| eew-static | 8.1% | 複合負荷のみ（カメラ静止・東北陸地の一般的な密度） |
| 単純合算なら | ~11.9% | — |
| **maxload-eew（実測）** | **24.2%** | **両方＋震源直近の最密領域を通過** |

実測（24.2%）は単純合算（~11.9%）の**約2倍**。これは「カメラ移動」と「複合負荷」が独立に足し算される
のではなく、**カメラがまさに最も密なジオメトリ領域を通過しながら同時に複合負荷を処理している**という
最悪の重なりが起きていることを示唆する。`flyto-widezoom-quake`の移動経路（`drivePan([139.5, 37.5], 7.5,
0.6, 0.25)`＝茨城〜栃木付近を移動）は三陸のリアス海岸を通らないため、この仮説と矛盾しない。

## 4. 開発機への申し送り（次の一手）

**仮説（強い状況証拠あり・完全な確定ではない）**: EEW自動カメラフィットが震源（三陸沖）周辺の
高密度ジオメトリ領域へflyToする際、カメラ移動コストと複合再描画コストが最悪の形で重なる。

**この仮説をピンポイントで検証する追加シナリオ案**:
- `flyto-sanriku-quake`（EEW/kyoshin無し・quakeモードのみで三陸沖周辺へ意図的にflyTo）を追加し、
  `flyto-widezoom-quake`（別ルート）と比較する。三陸ルートだけ突出して重ければ仮説はほぼ確定する。

**対処の方向性（原因確定後に検討）**:
- 震源周辺の高精細ジオメトリを、flyTo中は一時的に簡易表示に切り替える（本番の既存の緩和策
  「flyTo中は予報円を止める」と同種の考え方）
- 三陸沿岸に限らず、flyTo中は全レイヤーの高精細ジオメトリを簡略化表示にし、着地後に高精細へ戻す
  （MapLibreの`recalculateStyleLayers`のコスト構造次第で実現性が変わるため要調査）

## 5. 補足: 発報順序（新規/続報）の影響は結論を左右しないことを確認

`2b8eabc`適用前の8シナリオ版で追加実行された3件の証跡
（`06-41-38`・`06-43-58`・`06-46-00`。`eew-static`が先発火＝`maxload-eew`が「続報」条件）を確認したところ、
`maxload-eew`はfps 20.14〜20.97・longtask合計1,834〜2,124ms（12秒中約15〜18%）、
`eew-static`（この順序では「新規発報」）はlongtask合計905〜1,382ms（8秒中約11〜17%）だった。

**「続報」条件でも`maxload-eew`は一貫して悪く**、レビュー`webgl-migration-review-b9f5b95.md`で
懸念した発報順序の違いは、**この劣化の有無そのものには大きく影響しないと確認できた**
（`eew-static`側の値がむしろ発報順序で上下する側面はあり、細部の解釈には注意を要するが、
主要な結論——複合負荷とカメラ移動の重なりが支配的——は4回すべての証跡で一貫している）。

## 6. レビュー側での確認手段

| 確認項目 | 手段 | 結果 |
|---|---|---|
| detectMid/detectでの陸地不在の確認 | `maxload-eew`の`detectMid`・`detect`を突合 | 両方とも陸地レイヤー全0を確認 |
| 震源座標の特定 | `src/utils/testData.ts`の`createTestEEW`を検索 | `(38.1, 142.9)`＝三陸沖と確認 |
| 三陸が最密領域であることの裏付け | `a455644`のコミットメッセージを再確認 | 「三陸リアス海岸(ズーム10.5)」が高精細化の確認地点として明記されていたことを確認 |
| ブロック率の比較 | 各シナリオのlongtask合計/elapsedMsを算出 | flyto-widezoom-quake 3.8%・eew-static 8.1%・maxload-eew 24.2% |
