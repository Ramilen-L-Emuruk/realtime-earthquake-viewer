# 機能アイデア バックログ

このアプリに追加しうる機能の候補を、判定の材料ごと 1 か所に集めたもの。**読者は開発者**（このリポジトリに手を入れる人）。

- 目的は 2 つ。**要否を決める**ことと、**決めた理由を残す**こと
- 「面白そう」で始まった案が、なぜ採用されたか／なぜ落ちたかを後から辿れるようにする
- 実装済みの機能の仕様は書かない。それは [`docs/spec/`](spec/) の担当

> 各項目の判定は、書いた時点の実装とデータ源の状況にもとづく。**外部 API の可用性は変わる**ため、「困難」「不可」の判定は根拠ごと読み直すこと。

## 読み方

各項目は次の 4 つのラベルと、判定欄を持つ。

| ラベル | 値 | 意味 |
|---|---|---|
| 関心 | ◎ / ○ / － / × / 済 | **実装したい強さ**。◎=実装する前提で詰めたい / ○=あってもいいが必須ではない / －=未判定 / ×=不要 / 済=実装済み |
| 実現性 | 可 / 条件付き / 困難 / 不可 | 下記 |
| 規模 | S / M / L / XL | 下記 |
| 依存 | 基盤A〜G / 項目番号 / なし | 下記 |

関心は**分析の密度を表さない**。× の項目にも他と同じ密度で難所を書いてある。落とした理由を後から辿るためで、調べ直す必要はない。

**関心 × は要否「不要」と同義**として扱う。両方に同じことを書くのは重複だが、一覧を見るだけで落としたものが分かる方が実用的なので残している。

落とした理由は各項目の **「不要と判定した理由」**、それが無ければ **「難所」** に書いてある。難所そのものが決定的だった項目には前者を置いていない。

**実現性**

| 値 | 意味 |
|---|---|
| 可 | 既存の仕組みと公開データで実装できる |
| 条件付き | 共通土台の整備、または外部要因（CORS・API 可用性）の実測確認が必要 |
| 困難 | 技術的には可能だが障壁が大きい（重い依存・レイテンシ・法的整理・サーバー必須） |
| 不可 | 現在のデータ源では原理的にできない |

**規模**

| 値 | 目安 |
|---|---|
| S | 1〜2 ファイル。新規データ源なし |
| M | 複数ファイル。新規レイヤーかパネルを 1 つ増やす |
| L | 生成スクリプトの追加、または外部データ源の新規統合を伴う |
| XL | アーキテクチャ変更、またはサーバー側の実体が必要 |

**依存の書き方**

- 基盤への依存が部分的なら `（一部）`、あってもなくてもよいなら `（任意）` を付す
- 複数の基盤に同時に依存するなら `・` で連結する（例: `基盤B・C`）
- 他の項目そのものが前提になる場合は項目番号を書く（例: `51 または 91`）
- 一覧表では接頭辞「基盤」を省いて `A`〜`G` と書く

**要否** は各項目の見出し行に書く。`未判定` が初期値。

> **ラベルの正は「一覧」の表**。各項目の見出し行はその写しで、「共通土台」「依存関係の早見」「付記」も一覧から引いた集計。ラベルを変えるときは一覧を直し、見出しと集計へ反映する。

## 共通土台

複数の項目が同じ前提を要求する。**個別に作ると同じものを 2 度用意することになる**ため、先に土台の要否を決める方が早い。

### 基盤A. 長期震源カタログ

現在のカタログは**直近 30 日**（`HEATMAP_DAYS = 30`・[useQuakeHeatmap.ts:11](../src/hooks/useQuakeHeatmap.ts:11)）。ヒートマップ用に取得したもので、統計解析には期間も件数も足りない。

- 必要になる項目: 4・9・12（任意）・15・17・20・64（7 件）
- 実体: 気象庁の一元化震源カタログを `scripts/build-hypocenter-catalog.mjs` でビルド時に間引き（M2.0 以上など）、既存の生成データと同じ遅延読込パターンで置く
- 判断材料: 年間 10 万件超。間引き方と対象期間で容量が決まる。ライセンス確認が必要

### 基盤B. onset 時刻の外部公開

検知エンジンは各観測点の初動時刻を内部に持つが、外へ出していない。

- 必要になる項目: 8・59
- 実体: `kyoshinDetector` の戻り値に観測点ごとの onset 時刻を含める
- 注意: 既存の検知結果（likely/confirmed）とは粒度が違う。点単位の情報を毎秒返すことになるため、量と更新頻度の設計が要る

### 基盤C. アプリ内検知履歴

検知したイベントを端末内に永続化する。**別セッションで着手予定**（本文書を書いた時点では未コミットのため、リポジトリからは確認できない）。

- 必要になる項目: 58・59・60・61・82（一部）・88・89（7 件）
- 検知エンジンの**回帰ベンチ**（`scripts/bench-kyoshin.ts`）とは別物。ベンチは開発者がオフラインで実装を評価するもの、履歴はアプリが自分の検知を記録するもの。**取り違えると 58 以降が「もう作られている」と誤解される**
- 判断材料: 保存先（localStorage か IndexedDB）、保持件数の上限、気象庁発表との照合をどこで行うか

### 基盤D. 3D 描画（pitch の解禁）

地図の傾き（pitch）と回転（bearing）は**ユーザー操作から無効化されている**（[map-rendering-spec.md](spec/map-rendering-spec.md) §6）。

- 必要になる項目: 3
- 解禁すると影響を受けるもの: 予報円の半径計算、カメラの自動フィット。仕様書に「有効に戻すなら何を先に直すか」が既に書かれている
- 判断材料: 3 のためだけに解禁する価値があるか。**2D で足りる項目（4 など）を 3D 前提と混同しないこと**

### 基盤E. 静的レイヤーデータの生成

`scripts/build-*.mjs` で外部データを JSON 化し、`public/data/` に置いて遅延読込する既存パターン。**新設は不要で、倣うだけ**。

- 必要になる項目: 35・36・37・38・39・47（6 件）
- 判断材料は項目ごとに 2 つ。**容量**（`gzip.ts` があるので圧縮前提で見る）と**ライセンス**（政府標準利用規約なら概ね可）

### 基盤F. 全球投影

現在は日本域前提。世界の地震を出すなら MapLibre の globe 投影に切り替えるか、Mercator のまま広域表示するかの判断が要る。

- 必要になる項目: 49・50
- 影響: 予報円の半径計算とカメラフィットは日本域の Mercator 前提。基盤D と同種の波及がある

### 基盤G. サーバー側の実体 — **不要が確定**

現在は静的ホスティング（GitHub Pages）のみ。端末間で状態を共有する機能はサーバーを要求する。

- これを要求していた 34・53・68 は**3 件とも不要と判定された**ため、整備する理由がなくなった
- **節を残しているのは制約の記録として**。「サーバーを持たない」は今後の項目にも同じ判断を強いる。運用コストと個人情報の扱いが発生し、**アプリの性格そのものが変わる**

# 揺れの伝播を見せる

## 1. 予報円と実測波面の重ね合わせ

`関心 ×` `実現性 可` `規模 M` `依存 なし` — **要否: 不要**

- **見え方**: EEW の理論 P/S 波円と、強震モニタで実際に揺れが広がっていく輪を同時に描く。予測と実測のズレが目に見える
- **データ源**: 既存のみ（`usePsWaveCalc` の予報円＋強震モニタのフレーム）
- **実装**: 実測側の「波面」をどう定義するかが設計の中心。検知エンジンの確定点の外周（凸包）か、震度が閾値を超えた点の最遠距離を半径とする円か
- **難所**: 円で近似すると異方性（不均質な地下構造による伝播の偏り）が消える。それを見せたいのに円にしては本末転倒。凸包の方が誠実だが、点が疎な海域で形が破綻する

## 2. 揺れのトレイル（残像）

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 未判定**

- **見え方**: 観測点が現在値だけでなく直近数秒の減衰履歴を尾として残す。揺れが伝わると尾の向きが揃い、波面の進行が目に見える
- **データ源**: 既存の毎秒フレームのみ。追加取得なし
- **実装**: `KyoshinPointsGL` の下に第 2 レイヤーを敷く。点ごとに「過去 N 秒の最大値 × 減衰係数」をリングバッファで保持し、`circle-radius` と `circle-opacity` に反映する。点を増やすのではなく**消え残りを描く**
- **難所**:
  - MapLibre の既定 300ms トランジションの無効化が必須。過去 2 回踏んだ罠（[map-rendering-spec.md](spec/map-rendering-spec.md)）
  - 毎秒 `setData` が 2 本になる。観測点は約 1725 点なので致命的とは思えないが、負荷の実測は要る
  - 減衰計算を GPU 側の時間 uniform に寄せられないのが MapLibre の制約。CPU で毎秒回すことになる
- **派生**: 尾を「値が上がった点だけ」に絞ると、onset の広がり＝検知エンジンの L2 判定がそのまま絵になる。59 と目的が重なる

## 3. 震度の 3D 押し出し

`関心 ○` `実現性 条件付き` `規模 L` `依存 基盤D` — **要否: 未判定**

- **見え方**: 区域や観測点を震度の高さに立ち上げる。日本列島が波打つ
- **データ源**: 既存
- **実装**: `fill-extrusion` は MapLibre 標準機能なので描画自体は安い
- **難所**: **これは単体で安い機能ではない**。pitch がユーザー操作から無効化されているため、立体を見せるには基盤D（pitch 解禁）が前提になり、予報円の半径計算とカメラ自動フィットが前提を失う
- **判断のポイント**: この機能ひとつのために pitch を解禁する価値があるか。7 も同じ土台を要求するが、7 は別の理由で不要と判定済み。**現状、基盤D を要求するのはこの項目だけ**

## 4. 震源分布の深さ断面

`関心 ◎` `実現性 条件付き` `規模 L` `依存 基盤A` — **要否: 未判定**

- **見え方**: 地図上に 2 点を打つと、その線分に沿った帯に入る震源を「距離 × 深さ」でプロットする。海溝側から陸へ引くと**プレートの沈み込み面が斜めに並ぶ**
- **データ源**: 30 日カタログでは点が足りない。沈み込み帯を見せるなら基盤A（長期カタログ）が必須
- **実装**: 地図側は線分＋ドラッグ端点のマーカーのみ。断面は SVG の新規コンポーネント。線分への正射影は `geo.ts` の距離関数で足りる
- **難所**: データ量。一元化震源は年間 10 万件超なので、ビルド時の間引き方（マグニチュード下限・対象期間）を決める必要がある
- **注意**: **2D グラフなので基盤D（3D）とは無関係。** 3 と混同して「3D を待つ」必要はない

## 5. 等震度線

`関心 ◎` `実現性 可` `規模 M` `依存 なし` — **要否: 未判定**

- **見え方**: 観測点の震度を補間して等高線を描く。点の集合より分布の形が直感的に読める
- **データ源**: 既存（地震情報の観測点別震度、または強震モニタ）
- **実装**: 補間（IDW か Kriging の簡易版）→ 等高線抽出（marching squares）。ライブラリなしで書けるが 200 行規模
- **難所**: 観測点が疎な海域・山間部で等高線が暴れる。震度は距離減衰だけでなく地盤で大きく変わるため、**滑らかな等高線は実態を単純化しすぎる**という批判が成り立つ。気象庁が等震度線を常用しないのはこの理由

## 6. 走時曲線グラフ

`関心 ×` `実現性 可` `規模 M` `依存 基盤B` — **要否: 不要**

- **不要と判定した理由**: 横軸に震源距離・縦軸に経過秒を取り、理論走時線に実測 onset を乗せるグラフ。理論の検証としては筋が通るが、**読み手が限られる**（走時曲線を読める人向け）。同じ「予測と実測のズレ」は 1 や 8 の方が地図上で直感的に示せる
- **記録として**: 基盤B（onset 公開）を要求する項目だったが、これが落ちても 8・59 が同じ土台を要求するため、基盤B の要否には影響しない

## 7. 矩形断層面の描画

`関心 ×` `実現性 困難` `規模 XL` `依存 基盤D・F` — **要否: 不要**

- **不要と判定した理由**:
  - 気象庁の即時電文にメカニズム解（走向・傾斜・すべり角）は載らない。CMT 解（断層の動きを解析した結果。発生から時間を置いて公表される）は別配信・月報なので**国内のリアルタイム表示は成立しない**
  - USGS 経由なら世界の M4.5+ に moment tensor が即時公開されるが、それは 50 の範囲に収まる話
  - `fill-extrusion` では傾いた面が作れないため three.js の custom layer が必要。基盤D に加えて描画エンジンをもう 1 つ抱えることになる
- **記録として**: 震源球（ビーチボール）の 2D 表示だけなら安い。将来 50 を実装したときに再検討の余地がある

## 8. 揺れの進行方向（onset 勾配）

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤B` — **要否: 未判定**

- **前提の訂正**: 当初案は「揺れの主軸方向（卓越方向）」だったが、**これは実現不可**。Yahoo 強震モニタの JSON は成分別データを持たず、観測点ごとの震度インデックス 1 値のみ（[kyoshin.ts:7](../src/services/kyoshin.ts:7)）。検知エンジンのコメントにある「成分」は連結成分（グラフ）で、地震計の 3 成分とは無関係
- **読み替えた内容**: 各観測点の onset 時刻を面として捉え、**勾配ベクトルの逆向き＝震源方位**を出す。震源を知らないまま震源の方向が分かる。検知エンジンの震源非依存という性格がそのまま絵になる
- **データ源**: 既存。onset 時刻は検知エンジンが内部に持っている（基盤B で外に出す）
- **実装**: 近傍 K 点で平面フィット（最小二乗）→ 勾配 → 矢印レイヤー。計算自体は 20 行程度
- **難所**: onset が 1 秒粒度。S 波 4km/s なら 1 秒 = 4km、観測点間隔は 20km 程度あるため、**5 秒ほど伝播しないと向きが定まらない**。近距離・発生直後には使えない
- **土台の共有**: 59 が同じ基盤B を要求する。**別々に設計しないこと**

## 9. 余震域の楕円近似

`関心 ○` `実現性 条件付き` `規模 M` `依存 基盤A` — **要否: 未判定**

- **見え方**: 余震分布に主成分分析で楕円を当て、「北東-南西に 60km 延びている」を絵で示す。断層の延びと長さが読める
- **データ源**: 直近の余震なら 30 日カタログで足りる。過去の地震に遡って見せるなら基盤A
- **実装**: 2×2 共分散行列の固有値分解。外部ライブラリ不要で 20 行程度。楕円は GeoJSON polygon で近似
- **難所**: 本震・余震の同定ルール。群発地震（能登・和歌山）では楕円が意味を失う。**10（クラスタリング）とセットで初めて成立する**

## 10. 前震／本震／余震のクラスタ色分け

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 未判定**

- **データ源**: 既存 30 日カタログで成立する

- **難所**: 閾値の決め方で群の切れ方が変わる。9 の前提でもあるため、**先にこちらを決める順序になる**

# 音

## 21. ソニフィケーション

`関心 ○` `実現性 可` `規模 M` `依存 なし` — **要否: 未判定**

- **聴こえ方**: 全観測点の震度を音に変換する。案は 3 つ
  1. 最大震度を音高、揺れている点数を音量にする（最も単純）
  2. 地域別に音を割り当てて和音にする（どこが揺れているかが分かる）
  3. 震度分布のヒストグラムをスペクトルとして加算合成する（最も情報量が多いが解読が難しい）
- **データ源**: 既存の毎秒フレーム
- **実装**: `alertSound.ts` が既に Web Audio の Oscillator / Gain / Convolver（残響）を持っている。同じ AudioContext に常時オシレータを 1 本足し、毎秒パラメータを更新する。ユーザー操作前は鳴らせない制約（unlock）の作法も既存に倣える
- **難所**:
  - 通知音との衝突。EEW の警報中はソニフィケーションを絞る（ダッキング）必要がある
  - 音量設定を既存の通知音と別系統で持つ必要がある
- **最大の価値**: **平常時に流しっぱなしにできる**こと。何も起きていない時間に意味を持たせられる。他の地震ビューアーが持っていない軸

## 33. 地震図鑑

`関心 ×` `実現性 可` `規模 M` `依存 なし` — **要否: 不要**

- **見え方**: 過去の地震をカード化して一覧・収集する
- **難所**: 32 と同じ性格の懸念。ただし「図鑑」は資料性が高く、収集要素を外せば 19・20 に近い実用機能になる
- **不要と判定した理由**: **不謹慎。** 災害を収集の対象として扱うことになる（32・86・90 と同じ判断）

## 34. 安否共有

`関心 ×` `実現性 困難` `規模 XL` `依存 基盤G` — **要否: 不要**

- **見え方**: 「無事です」ボタンで共有リンクを発行する
- **難所**:
  - **サーバーが必要**（基盤G）。静的ホスティングでは成立しない
  - 個人情報を扱うことになり、このアプリの性格が変わる
  - 既存の安否確認サービス（災害用伝言板・SNS）に対する優位が無い
- **判断のポイント**: 落とすのが妥当と思われる項目

# 重ねるレイヤー

## 35. 人口メッシュ

`関心 ◎` `実現性 可` `規模 L` `依存 基盤E` — **要否: 未判定**

- **見え方**: 「震度 5 弱以上を体感した推定人口 ○○万人」を地震カードに 1 行。地図では震度と人口の積を色で示す
- **データ源**: e-Stat の国勢調査メッシュ人口（政府統計・利用可）。500m メッシュで約 30 万、1km メッシュで約 8 万
- **実装**: ビルド時に「メッシュ ID → 人口」を TypedArray 化して gzip（`gzip.ts` が既にある）。既存の生成データと同じ遅延読込パターン。震度からの割り当ては一次細分区域単位の面積按分で足りる
- **難所**:
  - データ量。1km メッシュ＋gzip で 1MB 台
  - 内挿の精度。区域単位の粗い按分でも万人単位の桁は合う。**桁だけ合わせて有効数字 1 桁で出すのが誠実**
- **価値**: 報道より早く規模感が出る。この一覧で実用性が最も跳ねる項目

## 36. 鉄道路線

`関心 ◎` `実現性 可` `規模 L` `依存 基盤E` — **要否: 未判定**

- **見え方**: 路線を線で描き、震度 4 以上の区域を通る路線を強調する。「止まりそうな路線」が地震発生 10 秒後に分かる
- **データ源**: 国土数値情報 N02（線路 2.5 万本・駅 1 万・政府標準利用規約）
- **実装**: 既存の生成スクリプトのパターンに倣う。**震度との交差はビルド時に「路線が通る区域コードの集合」を持たせる**（実行時の空間演算を避ける）
- **難所**:
  - 表示の混雑。全国の路線を出すと地図が線だらけになる。ズーム閾値（既存の「視野の実距離」方式）で新幹線→幹線→ローカル線の段階表示が必須
  - **運行情報 API が実質存在しない**。JR 各社は非公開、ODPT（公共交通オープンデータ）は関東中心＋会員登録。実測との連携は当面できず「静的な路線 × 震度」に留まる

## 37. 原発・空港・港湾

`関心 ◎` `実現性 可` `規模 S` `依存 基盤E` — **要否: 未判定**

- **見え方**: 重要施設を地図に置き、震度との突き合わせで「震度 5 弱以上の原発」を一覧する
- **データ源**: 国土数値情報（発電所 P03・空港 C28・港湾 C02）。**件数が小さい**（原発 20 サイト・空港 100 程度）
- **実装**: 静的 JSON 1 本＋symbol レイヤー。ズーム閾値は `LabelsGL` に倣う
- **難所**: ほぼない。ただし「原発が危険」という含意を持たせない中立表示（震度を出すだけ）に留める判断が要る
- **判断のポイント**: **36 より圧倒的に安く、実用価値は近い**。報道でも必ず触れる項目

## 38. ハザードマップ

`関心 ◎` `実現性 条件付き` `規模 L` `依存 基盤E` — **要否: 未判定**

- **見え方**: 津波浸水想定・液状化・土砂災害の想定区域を重ねる
- **データ源**: 国土交通省ハザードマップポータルの「重ねるハザードマップ」がタイル配信を提供している。自前で JSON 化するより**タイルを借りる方が現実的**
- **難所**:
  - タイル配信の利用条件（出典表示・アクセス頻度）の確認が必要
  - ラスタタイルなので、震度との突き合わせ（数値としての利用）はできない。**見せるだけ**になる
  - 想定区域は「その想定での話」であり、今起きた地震の被害ではない。誤読の余地がある

## 39. 避難所と経路

`関心 ◎` `実現性 条件付き` `規模 L` `依存 基盤E` — **要否: 未判定**

- **見え方**: 避難所の位置と、現在地からの経路
- **データ源**: 国土地理院の指定緊急避難場所データ（全国約 10 万件）
- **難所**:
  - 位置の表示だけなら安い。**経路探索は別世界**（道路網データ＋経路計算エンジン）で、外部サービス（OSRM 等）への依存が生じる
  - 避難所は災害種別ごとに指定が違う（地震用・津波用・洪水用）。種別を無視して出すと誤誘導になる
- **判断のポイント**: 「位置の表示だけ」に絞れば規模 M で成立する。落とすのが妥当なのは**経路探索の部分だけ**で、項目そのものは残る（下記「落とす候補」に挙げていないのはこのため）

## 40. 昼夜境界線

`関心 ◎` `実現性 可` `規模 S` `依存 なし` — **要否: 未判定**

## 41. 気象警報・雨雲レーダー

## 42. 火山情報

- **実装**: 火山の位置は静的 JSON（活火山 111）。電文パースを 1 系統足す

## 43. 地殻変動（GNSS）

`関心 ○` `実現性 困難` `規模 L` `依存 なし` — **要否: 未判定**

- **データ源**: 国土地理院の GEONET。**日次の座標値は公開されているが機械可読な API が整っていない**（F3 解はファイル配布）

- **判断のポイント**: 面白いが、このアプリの「リアルタイム」という性格から外れる

## 44. 建物被害の統計推定

- **データ源**: 35 の人口メッシュに加え、建物データ（国土数値情報の建物利用現況、または住宅・土地統計調査）

- **難所**:

  - 死傷者推定に踏み込むと表示の是非が別問題になる。**棟数までに留めるべき**
- **判断のポイント**: 35 が先。35 なしには成立しない

## 45. 津波伝播の概算シミュレーション

`関心 ○` `実現性 条件付き` `規模 L` `依存 なし` — **要否: 未判定**

# 新しいデータ源

## 49. 各国 EEW の統合

`関心 ◎` `実現性 条件付き` `規模 L` `依存 基盤F` — **要否: 未判定**

- **見え方**: 台湾・中国・メキシコ等の緊急地震速報を同じ地図に出す
- **データ源**: Wolfx の公開 WebSocket（`api.wolfx.jp`）が CENC・JMA・CWA・SCEA を中継している。無料・キー不要だが**非公式**
- **実装**: `services/wolfx.ts` を足して既存の `EEWAlert` 型へマップする。予報円・区域塗りの描画機構はそのまま使える
- **難所**:
  - **震度階級が国ごとに違う**（中国は烈度 I〜XII、台湾は 0〜7 級）。階級の翻訳層が必要
  - 非公式中継の安定性。P2PQuake と同格のリスク
  - **日本の EEW と混ざると誤認を招く**。別レイヤー・別配色・別通知系統として完全に分離する設計が必須
  - 予報円の計算は日本の 2 層速度モデル前提なので、海外では精度が落ちる
- **判断のポイント**: 50 と束ねて「世界地震」の枠にするのが自然。分離設計の手間が本体より重い

## 50. USGS 世界地震

`関心 ◎` `実現性 可` `規模 M` `依存 基盤F` — **要否: 未判定**

- **見え方**: 世界の M4.5+ を地図に。ShakeMap（推定震度分布）と PAGER（被害推定）も同じ event API から取れる
- **データ源**: USGS の GeoJSON Feed。**キー不要・CORS 許可済み・安定**
- **実装**: `services/usgs.ts` を足して既存の地震カード型へマップすれば、カードも地図も流用できる
- **難所**:
  - 投影。日本域前提の Mercator から全球へ広げると、予報円の半径計算とカメラフィットが影響を受ける（基盤F）
  - PAGER の死者数推定を出すことの是非。**出すなら確率分布のまま出す**（点推定にしない）
- **判断のポイント**: **フィードだけなら極めて安い**。ShakeMap・PAGER は第 2 段として分けられる

## 51. Raspberry Shake

`関心 ○` `実現性 困難` `規模 XL` `依存 なし` — **要否: 未判定**

- **見え方**: 近所の市民地震計の**生波形**。このアプリが持っていない「波形」という軸が開く
- **データ源**: FDSN Web Service（国際地震観測網連盟が定めた標準 API。station で観測点一覧、dataselect で波形を取る）。**波形は miniSEED**（地震波形の標準バイナリ形式）
- **実装**: ブラウザでの miniSEED パース（`seisplotjs` 等のライブラリ）が必要
- **難所**:
  - パースが重くバンドルが膨らむ
  - **国内の台数が少なく、地域によっては 1 台も無い**
  - CORS の可否は実測しないと分からない
  - レイテンシが数秒〜数十秒で、強震モニタの 1〜2 秒に劣る
- **判断のポイント**: 価値は認めるが優先度は低い。**波形を扱う目的なら 91 の方が筋が良い**（過去データだが量と質で勝る）

## 52. 端末の加速度センサー

## 58. 検知の成績表

# アーカイブ再生

## 91. K-NET / KiK-net からの過去強震データ再生

`関心 ◎` `実現性 条件付き` `規模 L` `依存 なし` — **要否: 未判定**

- **やりたいこと**: 防災科研の強震観測網（K-NET / KiK-net）のアーカイブから過去の地震を持ってきて、**Yahoo の保持期間より前の地震を再生できるようにする**
- **なぜ今できないか**: 強震モニタのリプレイは「Yahoo が秒ファイルを保持している期間しか遡れない」（[kyoshinSource.ts:107](../src/services/kyoshinSource.ts:107)）。2011 年の東日本大震災や 1995 年の阪神・淡路を検知エンジンに流すことは現状できない

**アプリ側の受け入れ口は既に用意されている。** `kyoshinSource.ts` のヘッダに設計意図が明記されている。

> 将来、防災科研 K-NET のアーカイブなど「フレーム列が一度に手に入る」供給元を足す場合は、KyoshinSource を実装して start() の中でフレームをまとめて enqueue すればよい（下流は変更不要）

つまり**難所はアプリ側ではなく、データの入手と変換に集約される**。

- **難所（入手）**:
  - ダウンロードに**ユーザー登録とログインが必要**。ブラウザから直接取得することはできない
  - **防災科研のホストへ到達できない環境がある**（[CLAUDE.md](../CLAUDE.md) に記録あり）。到達性そのものを実測で確認する必要がある
  - 提供されるのは**イベント単位の波形**（加速度時系列）で、連続データではない
- **難所（変換）**:
  - 波形から強震モニタ相当の値へ換算する必要がある。**リアルタイム震度は 1 秒ごとの独自演算**であり、気象庁の計測震度（60 秒の積算）とも別物。同じ値を再現できるとは限らない
  - 観測点の対応付け。強震モニタは**防災科研由来で約 1725 点**（[kyoshin-detection-spec.md](spec/kyoshin-detection-spec.md) §1）で、K-NET と KiK-net の合計とほぼ同規模。**集合が大きく違うわけではない**のは有利だが、点が 1 対 1 に揃う保証はない（Yahoo の公開座標は小数第 1 位までしか精度が無い点があり、実観測点が同一座標に潰れる事例が確認されている）。ただし**フレームは `sitesKey` で観測点集合を識別する設計**のため、別の観測点リストを持たせることは既存の枠内で可能
  - データ量。1 地震で全国分（K-NET・KiK-net で約 1700 点）× 数分の波形は数百 MB になる
- **難所（再配布）**:
  - **生成物をリポジトリにコミットできるか**が最大の論点。DMDATA の EEW と同種の問題（[settings-pwa-spec.md](spec/settings-pwa-spec.md) §6 の規約制限）
  - 研究利用が前提のデータを一般公開アプリに載せられるかは、利用規約の確認が必須

**現実的な落としどころ: 開発者のローカル専用にする。**

- `scripts/` で波形 → フレーム列に変換し、`.gitignore` 対象のローカルファイルとして置く
- 用途は**検知エンジンの回帰検証**。別セッションのベンチ（`scripts/kyoshin-bench/windows.json`）と同じ位置づけで、**検証窓を 2011 年以前まで広げられる**
- 一般利用者向けには配布せず、開発ツールとして持つ

- **価値**: この形なら検証に使える地震が桁違いに増える。**東日本・阪神・中越といった教科書的な地震で検知性能を測れる**ようになるのは、パラメータ調整の根拠として大きい
- **判断のポイント**:
  1. 防災科研への到達性（実測が必要）
  2. 波形 → リアルタイム震度相当の換算が成立するか（しないなら「別の量」として扱う）
  3. 一般公開する機能にするか、開発ツールに留めるか
- **代替案**: 気象庁の「震度データベース検索」は**観測点ごとの最終震度**（1 地震 1 値）を提供する。時系列ではないためリプレイには使えないが、基盤A（長期カタログ）の一部としては使える
