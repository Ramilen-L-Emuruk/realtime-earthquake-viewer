# 利用者向けの文言を決める手順

画面や音で利用者に届く文言を、足す・変えるときの進め方。**読み手はこのリポジトリで作業する人**（Claude を含む）。

**対象**は、利用者の目か耳に届く文字列のすべて。

- PWA の画面（カード・設定・地図の表示・ホバーの説明・通知・エラーの表示）と読み上げの文
- 自作地震計のホスト（ブラウザで開く管理コンソールの画面・確認の窓、画面に出る警告）
- データファイルの利用者向けの欄（`description` など）

README・仕様書（`docs/spec/`）・CLAUDE.md・コード内のコメントは対象外。あちらは CLAUDE.md の「ドキュメント客観レビュー」で見る。

**いつ諮るか・諮らなくてよい例外（バグの修正）・「足さない」が選ばれたときの扱いは、CLAUDE.md の「指摘への対応が利用者向けの文言を足すなら、実装の前に確認を取る」と「決めていないことを既決にしない」が正。** この手順書は、そこで諮る文面をどう用意し、どう記録するかを書く。

## 1. 棚卸しは機械で取る

直す範囲の文字列を、目で探さずに一覧にする。

```bash
npm run list-ui-strings -- --out <スクラッチパッド>/strings.tsv <パス…>
```

| 直すもの | 渡すパス |
|---|---|
| 管理コンソール | `seismo-host/src/admin` |
| ホストの警告（管理コンソールの稼働状況に出るもの） | `seismo-host/main.ts` `seismo-host/src/receiver` `seismo-host/src/detection` `seismo-host/src/intensity` `seismo-host/src/timebase` `seismo-host/src/protocol`（`seismo-host/src` を丸ごと渡すと管理コンソールまで混ざる） |

ホストの警告の行は、ほとんどがログの文になる。`main.ts` の文の大半は `emit(…)` へ渡すログで、印は `text` のまま出る（`emit` という名前は一般的すぎて、ログと見分ける判定に入れていない）。画面に出る警告の文を組むのは、管理コンソールの `seismo-host/src/admin/viewStatus.ts` と、`seismo-host/src/receiver/stationConfig.ts` の警告の文。ホストの警告を直すときは、管理コンソールの行と合わせて見る。
| PWA の画面 | `src/components` `src/App.tsx` |
| 読み上げの文 | `src/utils/ttsText.ts` ほか、読み上げ文を組む所。文の一覧は [`docs/spec/tts-sentence-inventory.md`](spec/tts-sentence-inventory.md) |

- 出力は 1 行 1 件の TSV（パス・行・抜き出し方の印・文字列）。印は `text`・`error`（`new Error` / `throw` の文）・`log`（`console` やログへ書く文）
- 読むのは `.ts`・`.tsx`・`.html`。テスト・型定義・`node_modules`・`dist`・リンクは読まない。ほかの拡張子のファイルがあれば、何本読まなかったかを標準エラーに出す
- **コメントは拾わない**（構文木から取るので、コメントはそもそも乗らない）
- HTML（ファイルでも、テンプレート文字列で組んだものでも）はタグと `<!-- -->` を外し、地の文と、日本語を含む属性の値を拾う（`title`・`placeholder`・`label`・`value` など）。`<style>`・`<script>` の中身を外すのは `.html` のファイルだけ
- 埋め込み式は `${…}` と表す。式の中の文字列は別の行に出る
- 渡したパスが無い・読めるソースが 1 本も無い・書き出せないときは、終了コード 2 で止まる
- 構文エラーや UTF-8 として読めない文字のあるファイルがあれば、一覧は出したうえで、そのファイルと行を標準エラーに出して終了コード 2 を返す。そのファイルの分は欠けているかもしれない
- 一覧はリポジトリに入れない（スクラッチパッドに置く）。2 の役割と、諮った結果をこの台帳へ書き足していく

**`log` と `error` の行は、そのまま対象にしない。** 画面に出るかを呼び出し元で確かめる。`console` へ書くだけの文は開発者向けで対象外。例外の文が画面のエラー欄に出るなら対象。

**拾えない形・崩れて出る形**は次のとおり。別に探す。

- 日本語を含まない文言（英語だけのボタン名など）
- JSON のデータファイルの利用者向けの欄（`description` など）
- 文字列を連結（`+`）で組んでいる箇所。断片ごとに出るので、つないで読む
- 引用符の無い属性値（`placeholder=未設定`）。HTML の実体参照（`&nbsp;` など）は復号せずそのまま出る

## 2. 役割で分けて、見せ方を決める

台帳の行ごとに、次の役割のどれかを書き足す。

| 役割 | 見せ方 |
|---|---|
| 状態・エラー（いま何が起きているか） | 常に出す |
| 隠すと、失敗の原因が辿れなくなる前提条件 | 常に出す |
| 固定の説明・凡例・用語の意味 | ホバーで出す |
| 見出し・ボタン・確認 | 短くする。ボタンには押した結果を書き、「OK」にしない |

ホバーで出す部品は、PWA なら `DescriptionTip`（`src/components/DescriptionTip`）。マウス・フォーカス・タップのどれでも開く。管理コンソールには同じ働きの部品がまだ無いので、使う前に作る。

## 3. 語の出どころを探す

**自分で言い換えを作らない。** 先に、利用者がすでに知っている語を探す。

- **地震・津波などの情報**は、気象庁の資料の語に合わせる。わざと外している語は [`docs/spec/quake-spec.md`](spec/quake-spec.md) §8「気象庁の表現からわざと外している語」に並んでいるので、先に確かめる。
- **一般の操作・状態**（確認・保存・破棄・再読み込み・読み込み中など）は、ほかのアプリの実物を見る。
  - Web 検索では実際の画面の文字列がほとんど出てこない。
  - 手元にあるアプリの言語ファイルから引く。

  ```bash
  npm run find-locale-strings -- "<言語ファイル>" <語…>
  ```

  | アプリ | 言語ファイル（Windows。Git Bash では `%USERPROFILE%` を `$USERPROFILE` と書く） |
  |---|---|
  | Chrome | `C:\Program Files\Google\Chrome\Application\<版>\Locales\ja.pak` |
  | VS Code | `%USERPROFILE%\.vscode\extensions\ms-ceintl.vscode-language-pack-ja-<版>\translations\main.i18n.json` |
  | VS Code の拡張機能 | 同じ場所の `extensions\*.i18n.json`（Git なら `vscode.git.i18n.json`） |

  - 全角と半角の違いは揃えてから突き合わせる（Chrome は「？」、VS Code は「?」を使う）。
  - 標準エラーに、当たった件数・読んだ文字列の数・そのうち日本語を含む数が出る。
  - 終了コードは、当たれば 0、日本語のファイルを読めたが当たらなければ 1、読めなかったか日本語を含む文字列が半分に満たなければ 2。**0 件を「その言い方をしていない」の根拠にできるのは 1 のときだけ。**
  - Chrome は行頭に文字列の番号が付く。別名の表から引いたものには「別名」と付く。番号は版で変わる。
  - VS Code の Git の訳は、鍵が英語の原文になっている。訳の元を確かめられる（原文が改行を含むと、1 件が複数行で出る）。
  - VS Code の日本語パックは、版の違うものが同時に入っていることがある。新しい版の方を渡す。
  - VS Code の `main.i18n.json` は大きい。読み切れないときは `NODE_OPTIONS=--max-old-space-size=4096` を付ける。
  - Edge の `ja.pak` は作りが違い、読めない（終了コード 2 で止まる）。

- **見つからなければ、見つからなかったと書いて諮る。** 作った語であることを隠さない。

2026-10-11 に引いた例:

| アプリ | 見出し・本文 | ボタン |
|---|---|---|
| Chrome 154 | 「このサイトを離れますか？」・「行った変更が保存されない可能性があります。」 | 「このページを離れる」 |
| VS Code の Git | 「'{0}' の変更を破棄しますか?」 | — |

どちらも同じ形をしている。見出しは丁寧形の問いで、2 文目で何が起きるかを言い切り、ボタンには押した結果を書く。

## 4. 調子を揃える

1 つのアプリの中で、丁寧形にするか言い切りにするかを決める。決めるのは文を書き直す前。役割ごとに分けてもよい（確認の窓は丁寧形の問い、状態は言い切り、など）。

**すでにある決まりと合わせる。** PWA の、取得の失敗・制限を知らせる通知は「主節は言い切り」と決めてある（[`docs/spec/settings-pwa-spec.md`](spec/settings-pwa-spec.md) §5.5「通知の文の形」）。

PWA とホストの調子は、並べて 1 回で決める（2026-10-12 ユーザー承認）。どちらにするかは**未決（ユーザー判断待ち）**。決まったら、この節に承認日つきで書く。

## 5. 避ける形

この節は**画面と読み上げの文言**の話。README や仕様書の書き方の話ではない。

2026-10-10 のユーザーの指摘（原文）:

> 説明しすぎ(文がAIくさい、PWAはホバーで表示なのに説明が常時表示)。

前半の「説明しすぎ」は 2 の見せ方で、後半の「常時表示」はホバーで出すことで答える。

「AI くさい」に当たる形として、2026-10-12 にユーザーが次の 4 つを選んだ。例は、その日の管理コンソールにあった文（直す前のもの）。

| 形 | 例 |
|---|---|
| 独自の言い換え語。ほかのアプリが使う語を避けて、和語で言い直している | 「届く刻みが細かく」「遡れる長さ」「作ったあとで元の記録が伸びた時」「取り戻した分」 |
| 理由や手順まで書く。状態の一言で済む所に、なぜそうなるか・次に何をするかまで続ける | 「読めない波形が N 件届いた。ホストと管理コンソールの版が食い違っている疑いがあるので、開発者へ伝えること」 |
| 括弧の補足。本文の後ろに、条件や理由を括弧で足す | 「まだ 1 枚も無い（基板から届けば、ここに出る）」「該当なし（観測点に割り当てた基板のみ）」 |
| 「〜こと」の指示書調。利用者への指示を常体の「〜こと」で結ぶ | 「保存したら元の場所へ据え直し、『鉛直を合わせる』を押し直すこと」 |

**文書の書き方を画面へ持ち込まない。**

- 文書（README・仕様書）では、前提知識の無い読み手に合わせて専門語を開いて言い換える。
- 画面では、利用者がほかのアプリで覚えた語のほうが速く伝わる。開いた言い換えは、かえって読み手を止める。
- 上の 4 つの形は、どれも文書の書き方がそのまま画面に出たもの。
- データファイルの `description` のように画面に出る欄は、画面の側として扱う。

ほかに、制作過程の漏れや内部用語も避ける（CLAUDE.md「ドキュメント客観レビュー」の「データファイル・UI文言特有の観点」）。

## 6. 諮る

諮るときの決まり（実物を見せる・「変えない」を入れる・選択の意思が読み取れない答えは決まっていない扱いにする）は、冒頭に挙げた CLAUDE.md の 2 節に従う。この手順書で足すのは次のこと。

- **AskUserQuestion は 1 回に出せる問いの数に上限がある**（2026-10 時点で 4 問）。タブや場面ごとに分けて出す。
- **長い文は選択肢の `preview` に入れる。** 選択肢のラベルは短く保つ。
- **選択肢の説明に、語の出どころを添える。** 気象庁の資料の名前、Chrome の文字列の番号など。出どころが無い案には、作った語だと書く。
- **自由記述で文面が書かれてきたら、それが答え。** そのまま使う。
- 諮った結果は、1 の台帳の行に書き足す。

## 7. 記録する

承認日の書式と、日付を添えられないものの扱いは、CLAUDE.md「決めていないことを既決にしない」に従う。この手順書で足すのは次のこと。

- 決めた文面は、承認日を添えてコミットメッセージに残す。
- 「変えない」が選ばれたものも残す。次の見直しで同じ問いを出さないため。
- 見せ方の決まり（何を常に出し、何をホバーにしたか）は、その画面を説明している資材に書く。管理コンソールは `seismo-host/README.md`。PWA は、その画面を扱う `docs/spec/` の仕様書（設定タブなら `settings-pwa-spec.md`）。

## 8. 入れた後

- **画面で確かめる。**
  - ホバーで説明が出るか。
  - タッチでも開けるか。
  - 狭い幅で折り返したときに、操作するものを覆わないか。
- **読み上げの文を変えたら、耳で確かめる。** VOICEVOX で鳴らし、[`docs/spec/tts-sentence-inventory.md`](spec/tts-sentence-inventory.md) の文の一覧も直す。
- **文言をテストで固定している箇所は、期待値を新しい文面へ直す。** テストが落ちたら、意図して変えたのか、壊したのかを分ける。
- **客観レビュー（`doc-objectivity-reviewer`）に掛ける。** レビューが文面を変えたがっても、その場で直さず 6 へ戻る。
