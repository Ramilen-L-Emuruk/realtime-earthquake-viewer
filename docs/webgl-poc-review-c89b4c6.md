## 【判断①】テキスト描画 = B案 — レビュー側の推奨は誤りだった

### 決定の理由（計画書より）

> 全面リライトで MapLibre に移行する以上ビルド時グリフパイプラインの工数は見合い、
> B は生成スパイクを**恒久的に消し**、PWA の Service Worker 事前キャッシュで**オフラインでも即座**
> ＝防災アプリで「肝心の瞬間に固まらない」保証

### レビュー側の C案推奨に何が欠けていたか

前回レビューでわたくしは C案（起動直後アイドル時に事前生成）を推し、その根拠を
**「コストは消えないが、支払うタイミングを選べる」**と書いた。

**この整理には決定的な見落としがある——「毎回払う」ことを勘定に入れていなかった。**

MapLibre のグリフキャッシュ（`glyphManager.entries`）は**ページを閉じると消える**。
これは PoC 検証中に自分で確認し、`webgl-poc-review-f5d8de5.md` にも
「同一ページで2回目以降は `glyphsGenerated` が動かない＝リロードが必要」と記録している。
**つまりリロード（＝新しいセッション）のたびに、グリフ生成は最初からやり直しになる。**

| | 初回起動 | 2回目以降の起動 | オフライン |
|---|---|---|---|
| **C案**（起動時事前生成） | 100〜260ms | **毎回 100〜260ms** | 毎回 100〜260ms |
| **B案**（PBF ホスト） | ネットワーク待ち | **HTTP/SW キャッシュで即座** | **SW 事前キャッシュで即座** |

**C案はコストを移動させるだけで、消していない。B案は恒久的に消す。**
毎日開かれる PWA では、この差は繰り返し効き続ける。

さらに、わたくしが B案の弱点として挙げた「初回コストがネットワーク待ちに変わる」も、
**PWA の Service Worker 事前キャッシュで解消される**。本アプリは PWA であり、
既にオフライン動作を前提としている。**弱点として挙げた点が、この構成では成立しなかった。**

工数の評価も見直す必要がある。わたくしは B を
「当初の見積もりに戻る＝準備物が増える」と否定的に書いたが、
**そもそも全面リライトで移行するのだから、ビルド時パイプラインを1本足す相対コストは小さい。**
既存実装を温存する前提で工数を見積もっていたのが誤りだった。

### 防災アプリという文脈

決定理由の最後にある「**肝心の瞬間に固まらない保証**」が本質である。
実機計測で見えた最悪の構造は「区域名ラベルの初出＝地震検知時の自動ズーム」だった。
C案はその確率を下げるが**保証はしない**（起動直後に地震が来れば温め切る前に踏む）。
B案は生成そのものが起きないため、**タイミングに依存しない**。

防災用途で「たいていは大丈夫」と「原理的に起きない」の差は、工数で測るものではない。

## 【判断②】実行時メモリ = 長時間稼働の安定性を答とする

VRAM が観測できない以上、バイト数の突き合わせは原理的に完結しない
（レビュー側も前回「GPU プロセスと突き合わせる」という指示が筋が悪かったと認めている）。

これに対し、**バイト計測をやめて「実機での長時間稼働の安定性（タブ kill / context lost の有無）」を
答とする**という判断は妥当である。

§8 の本来の問いは「**RAM 4GB 機で実用に耐えるか**」であって、内訳の数値ではない。
知りたいのは「落ちないか」であり、それは**タブが kill されるか・context lost が起きるか**を
長時間観測すれば直接答えが出る。**測れる量に問いを合わせるのではなく、問いに合う指標を選び直した**形。

これは本日の一連（`elapsedMs` → `frame.max` → `blockMaxMs`）で得た教訓と同型である。
`blockMaxMs` に替えた瞬間に環境差の論争が消えたのと同じく、
**指標を替えることで「原理的に答えの出ない問い」が「答えの出る問い」に変わっている。**

**【未定義・要確認】** 「長時間」の具体（何時間・どの操作を含むか・判定条件）はまだ書かれていない。
実施前に決めておかないと、結果が出たときに合否を判定できない。

## 記録: 推奨が覆されたことについて

本レビューでは指摘すべき点がない。むしろ**2件とも、レビュー側が出した案より良い**。

C案の見落とし（グリフキャッシュがセッションを越えないこと）は、
**わたくし自身が PoC 検証中に発見し、自分で綴りに書いた事実だった**。
それを対処案の比較に持ち込めていなかった——**知っていたのに使えなかった**という失敗であり、
情報が足りなかったわけではない。

対処案を比較する際、「一度きりのコストか、繰り返すコストか」は最初に確認すべき軸だった。
