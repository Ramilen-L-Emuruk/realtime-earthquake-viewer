## 【対応確認】狙った負荷を踏むようになった

日本全体のビューを固定したまま `setLayerZoomRange` で `minzoom`/`maxzoom` を外し、
`visibility` の出し入れでレイヤーを順に出す方式に変更された。レビュー側の提案 (1)(2) が
両方入っている。

### 独立再現（`__runLabelZoomSuite()` をレビュー側で実行）

| 段 | `renderedSymbols` | `glyphsGenerated`（累積） | 増分 |
|---|---|---|---|
| suite 開始前 | — | 13 | — |
| regions（地方9件） | 8 | 15 | +2 |
| prefectures（県47件） | 30 | 84 | **+69** |
| subregions（区域192件） | 67 | 209 | **+125** |
| intensity（震度ラベル） | 45 | 218 | +9 |

**単調増加が確認できた。** 前回の「全ズーム帯で 40 種のまま不変」は完全に解消されている。
`glyphsGenerated` と `renderedSymbols` が結果に含まれたことで、
**この判定がレビュー側から一目でできるようになった**点も含めて対応は妥当。

`renderedSymbols` がソース件数より少ない（区域192件に対し67）のは
`text-allow-overlap` 既定 false による衝突間引きで、コメントの説明どおり正常。

### セルフレビューでの発見を評価する

`intensity-label` が `load` 時点から常時表示だったため、suite 開始前に
そのグリフが生成済みになっており、**4件目の計測が「開始前に済んでいた」アーティファクト**に
なっていた——これを自力で見つけて `visibility: 'none'` + 手動トグルに分離したのは良い。

レビュー側が指摘したのは3レイヤーぶんの視野問題だけで、**4件目の汚染は見落としていた**。
同型の失敗を自分で探しにいく動きができている。

## 【新規 HIGH】`elapsedMs` がグリフ生成コストに反応しない

### 観測

レビュー側で、各段のグリフ生成増分と並べて**フレーム間隔も同時に収集**した
（`fitBounds` → 全レイヤー非表示 → `idle` 待ちの後、1段ずつ `visibility` を切り替え、
`idle` までの経過時間と rAF のフレーム間隔を計測）:

| 段 | グリフ生成増分 | `idleMs`（＝`elapsedMs` 相当） | frame p95 | **frame max** |
|---|---|---|---|---|
| regions | **+2** | 611.7 | 6.1 | 6.3 |
| prefectures | **+69** | 612.1 | 6.1 | 6.2 |
| subregions | **+125** | 612.4 | 6.2 | **17.6** |

**グリフ生成量が 2 → 125 と 60 倍以上変わっても、`idleMs` の差は 0.7ms**（611.7 / 612.1 / 612.4）。
約 612ms という一定値で、生成量にまったく反応していない。この 612ms が何に律速されているかは
未測定だが、**少なくともグリフ生成コストではない**ことは上記から確定する。

一方、**フレーム時間の max には明確に出ている**。125 グリフの段だけ 17.6ms で、
他の 2 段（6.2〜6.3ms）に対し **約 11.4ms の増分**。p95 は全段 6.1〜6.2 で不動であり、
**「一度きりの生成コストが max にだけ現れる」という性質と合致する**。

### したがって

`__runLabelZoomSuite` の結果に載っている `elapsedMs`（実測 608〜611.5ms）は、
**グリフ生成コストの指標として使えない**。すべての段でほぼ同値になるため、
軸を振っても動かない——層B で言うところの**飽和した指標**である。

`longTaskCount: 0` も同様に注意が要る。**これは正しい観測だが「安い」の証拠ではない**。
実測の 17.6ms は longtask の閾値 50ms を下回るので、そもそも longtask にはならない。
**17.6ms という実測値そのもののほうが、`longtask 0` より遥かに情報量がある。**

### 対処

`measureLabelLayer` にフレーム時間の集計を足す。既存の `measure.ts` に
`summarizeFrames(frameDeltas, elapsedMs)` があり、そのまま使える形になっている:

```ts
const frameDeltas: number[] = []
let last = performance.now()
let rafId = requestAnimationFrame(function loop(t) {
  frameDeltas.push(t - last); last = t; rafId = requestAnimationFrame(loop)
})
// … idle 待ち …
cancelAnimationFrame(rafId)
// 結果に frame: summarizeFrames(frameDeltas, elapsedMs) を含める
```

`elapsedMs` は「idle までの所要時間」として残してよいが、
**グリフ生成コストの指標ではないことを結果の読み手に分かる形にしておくこと**。

### この項目の失敗の系譜（4度目・ただし性質が変わった）

| 回 | 測ろうとしたもの | 実際に測っていたもの |
|---|---|---|
| 層B・項目1 | 描画負荷の律速 | vsync 天井 |
| 項目4 | 円と正方形の差 | 両者が恒等的に一致する軸 |
| §8 ラベル（前回） | 多数グリフの生成コスト | **空の視野**（負荷を踏んでいない） |
| **§8 ラベル（今回）** | 同上 | **負荷は踏んだが、反応しない指標** |

前回は「負荷が発生していなかった」、今回は「負荷は発生したが指標が拾っていない」。
**一段進んでいる。** 残るは指標の差し替えだけで、構造の作り直しは要らない。

## 【副産物】開発機の vsync は 6.1ms — 計画書の記述は誤り

上表の frame p95 は**全段で 6.1〜6.2ms** と動かない。これが開発機の vsync 周期であり、
**約 164Hz** に相当する。レビュー綴り `b5d8bae` の情報5 に記録した「開発機 170Hz」と整合する。

計画書 §6 検証項目3 の「開発機は高性能GPUのため全計測が **vsync天井16.7ms付近**」は**誤り**。
16.7ms は 60Hz の周期であり、この機体のものではない。当該記述の訂正が要る。

また subregions 段の frame max 17.6ms は、vsync 6.1ms の**約3フレーム分**（6.1 × 3 = 18.3ms）に
あたる。前レビュー HIGH2 で `estimatedVsyncMs` を入れてもらった意図がそのまま効く場面で、
**vsync 周期の実測が無ければ 17.6ms を「3フレーム落ち」と読むことすらできない**。
対応の価値がここで実証された形になる。

## 記録: 良い対応と、その一般形

今回の対応で `glyphsGenerated` / `renderedSymbols` が結果に載ったことで、
**レビュー側は3分で「負荷を踏んだか」を判定できた**。前回はグリフキャッシュを
直接覗くまで気づけなかったことを思えば、差は大きい。

一方で今回新たに見つかった問題は、**その処方箋が「負荷を踏んだか」にしか適用されておらず、
「その負荷が指標に現れるか」には適用されていなかった**ために起きている。
両方が揃って初めて計測は成立する:

1. **狙った負荷を踏んだか**（`glyphsGenerated` 等の入力側の証跡）← 今回入った
2. **その負荷が指標に現れるか**（軸を振ったとき指標が動くか）← 今回不足

(2) は「軸を2点以上振って、指標が動くことを一度確認する」だけで済む。
本レビューが 3 段のデータを並べた瞬間に分かったのも、それをやったからにすぎない。
