## 1. 分離シナリオの設計 — 的確

- **`flyto-widezoom-quake`**（EEW・kyoshin無しで広ズームのカメラパンのみ）と
  **`eew-static`**（EEWを発火させた後カメラを固定して毎秒更新・波・EEW塗りの持続コストだけを測る）の
  2本で、「カメラ移動由来か」「複合再描画の持続コスト由来か」を直交する軸で切り分けようとしている。
  これは前回レビュー（`webgl-migration-review-89188bd.md`）の「盲目的な対処を避け支配源を確定する」
  という趣旨に正しく沿っている。
- **`detectMid`**（計測窓60%地点でのdetectスナップショット）は、レビュー側が`maxload-eew`の証跡で
  実際に気づいていた問題（終端でカメラが海上へflyToし`detect`が全0になる）を正しく認識して解消している。

## 2. [MEDIUM] `eew-static`と`maxload-eew`が同一ページ内で同じテストボタンを2回発火する

新しいシナリオ順序は `... → eew-static（EEWテストボタンを発火） → maxload-eew（同じボタンを再度発火）`。

CLAUDE.mdに明記されている仕様（「異なるボタンを押すと前のEEWタイマーをキャンセルし新規発報」
「同じボタン再クリックで続報（`eewUpdate`音）」「EEWは約30秒で自動解除」）に照らすと、
`eew-static`の発火から`maxload-eew`の発火までの間隔（約12.8秒）はEEWの自動解除（約30秒）より短いため、
**`maxload-eew`側のボタンクリックは「新規発報」ではなく「続報（update）」になる**可能性が高い。

これまでの実機計測（n=3）では`maxload-eew`が計測窓内で唯一・最初のEEW発火だったため「新規発報」の
コストを測っていたが、**今回の新しい順序で実機計測すると`maxload-eew`は「続報」のコストを測ることになり、
これまでの3回の基準値と厳密には同一条件ではなくなる**。新規発報と続報で内部処理（音源選択・カード追加
vs 更新等）が異なる可能性があり、コストの違いが出るかは未検証。

**対処の提案**: 次の実機計測でこの点を認識した上で結果を解釈する（「続報」のコストとして読む）、
または`eew-static`と`maxload-eew`の間にページリロードを挟んで両方とも「新規発報」条件で測る、
のいずれかを推奨する。ブロッカーではないが、**次の実機結果を前回のn=3と直接比較する際に
注意が必要**なため記録しておく。
