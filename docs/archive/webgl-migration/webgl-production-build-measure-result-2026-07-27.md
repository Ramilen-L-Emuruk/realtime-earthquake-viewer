# 本番ビルドでの実機再計測 結果（残作業D・Surface Go 2・2026-07-27）

> 依頼: [webgl-production-build-measure-request.md](webgl-production-build-measure-request.md)
> 比較対象（dev サーバー計測）: [webgl-production-baseline-2026-07-27.md](webgl-production-baseline-2026-07-27.md)
> 証跡: `surface-go2-prod-{static,pan,zoom,autozoom}` 各3件・計12件
> 計測環境: `npm run build:dmdss` → `npm run preview:dmdss -- --host`（本番ビルド・DMDSS版・`buildMode:'production'`）
> **【既知の限界】`swControlled: false`（全件）**——実機はLAN経由のHTTP（`http://192.168.0.64:5195/...`）でアクセスしており、
> Service Worker はセキュアコンテキスト（HTTPS または localhost）でのみ有効なため、`navigator.serviceWorker` が
> `undefined`（実機コンソールで確認済み）となり登録されない。**本文書の全数値はSW非介入（キャッシュなし）の状態**。
> ただし本依頼の主目的（dev モードのオーバーヘッドを除いた本番バンドルの絶対値較正）には影響しない
> （SW はネットワーク応答の速さに効く要因であり、今回計測している rAF/DOM 書き込み/longtask はローカル描画コストのため）。
>
> **結論: 「段階0の差分更新が移動中に効かない」という核心は本番ビルドでも不変。fps・blockMaxMs は区間により
> 改善の度合いが異なり、特にズームは本番ビルドでも最悪帯（fps 15〜21・blockMaxMs 最大653ms）が残る。**

## 2. 【注意】autozoom 3件目は計測条件が異なる

3件目の証跡（`perf-2026-07-27T17-25-09`）は `kyoshinActive:false`・`mode:'unknown'`・`pathCount:0` で、
**リアルタイム震度タブから外れた状態で計測されている**。地震テストボタンは検知時の自動タブ切替を伴うため、
計測窓の途中でタブが切り替わったと考えられる（**アプリの既知の仕様**であり不具合ではない）。

**autozoom の比較は 1・2件目（n=2）を正とする。** 3件目（fps 52.74・`blockMaxMs` 368ms）は
「地震テスト後、別モードに切り替わった状態」の参考値として別枠で扱う。

## 3. 読み取れること

### ① 核心（段階0が移動中に効かない）は本番ビルドでも不変

pan・zoom とも DOM 書き込みは**数千〜1万/秒の桁のまま**（静止時 14〜31/秒の 200〜500倍）。
dev で確認した「動くと全点書き換えに戻る」という機序はビルドモードに依存しない、という
依頼書の予想どおりの結果になった。**この核心は決着のまま動かない。**

### ② fps・体感コストの改善度は区間で大きく違う——「本番なら軽くなる」は言い過ぎ

**pan は本番ビルドで明確に改善した**（fps 約2倍・`blockMaxMs` 約2.5〜3倍改善）。
これは dev モード（React development・非minify・HMR）のオーバーヘッドが実際に乗っていたことを示す。

**しかし zoom はほとんど改善しなかった**（fps 13〜20 → 15〜21、`blockMaxMs` 590〜910ms → 540〜653ms）。
**「本番ビルドなら軽くなるはず」という期待は、区間によっては成立しない。**
zoom の重さは dev のオーバーヘッドではなく、**アプリの実コスト（層A残差）そのもの**である可能性が高い。

### ③ 静止時は longtask が完全に消えた——dev のノイズが明確に除去された

dev の静止時計測では 157〜372ms の longtask が散発していたが、本番ビルドでは**3件とも 0件**。
これは dev モードの再レンダリングコストが静止時にも薄く乗っていたことの裏付けであり、
546ee9f レビューで見えた「開発機の domWrites 1041→11.6」の傾向とも整合する
（ただし実機の domWrites 自体は静止時 dev/prod でほぼ同水準——影響を受けたのは longtask 側だった）。

### ④ 「移行せずに直せる余地」は zoom について特に小さい

zoom は dev でも本番でも fps 13〜21・`blockMaxMs` 500〜900ms 台という**ほぼ同じ最悪帯**にいる。
本番ビルド化という「移行せずにできる対策」を最大限やっても、**ズーム時の重さはほぼ解消されない**。
これは検証項目3（カメラ操作）で MapLibre が着地コストで Leaflet の 5.2倍優位だった結果と符合し、
**一本化（GO）の必要性を追加で裏付ける**。

## 4. 計画書への反映

- 計画書「残る作業 (c) 本番ビルドでの実機再計測」を**完了**として記録
- **絶対値の較正**という当初目的を達成: pan は dev 由来の過大評価が判明・zoom は dev/prod でほぼ同じ実コストと判明
- GO/NO-GO は変わらず GO。むしろ zoom の重さが「移行しても直らない dev アーティファクトではない」と判明した分、
  **一本化の必要性がより明確になった**
