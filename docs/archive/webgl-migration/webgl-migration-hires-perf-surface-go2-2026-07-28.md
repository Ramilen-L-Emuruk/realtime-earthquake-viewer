## 2. コールドスタートと定常状態の切り分け

**static-quake〜pan-maxzoom-kyoshinの5シナリオは、1回目→2・3回目で軒並み大幅改善**
（静止441.5→108.8/50.4ms、パン320→58.2/95.5ms 等）。これは**高精細ジオメトリのGPUバッファ初回
アップロード・タイル初回転送という一度きりのコスト**を1回目が捉えていたためと考えられる。
**定常状態（2・3回目）ではこれらのシナリオは安定して健全域**（blockMax 41〜113ms・longtask 0〜2件）。

**ただし`maxload-eew`だけは3回中3回とも温まった状態でも劣化が残る。** blockMaxMs・longtask最大こそ
大きく改善したが（593→154.1→117.3ms、502→129→79ms）、**fps 17〜19・longtask合計1,866〜2,536ms
（12秒中約15〜21%）** という数字は3回とも一貫しており、コールドスタートでは説明できない、
**EEW発報時特有の負荷**であることが再現性をもって確認できた。

## 3. 【HIGH】maxload-eewはPoC検証項目7からの実質的な劣化

PoC検証項目7（EEW複合負荷・最悪局面）は実機2スイート・8証跡で
**「fps59.9〜60.0・longtask 0・`flyTo`区間p95 17.5〜19.5ms」**という結果だった（計画書§6）。

今回の定常状態（2・3回目・温まった状態）の`maxload-eew`は**fps17.77/19.18・longtask32/37件
（合計1,866ms/2,062ms）**——コールドスタートの影響を除いても、
**PoCで確認していた「問題なし」から明確に悪化している。3回の反復でこの劣化は安定して再現しており、
測定ノイズではない。**

**PoCとの決定的な違い**: PoCの検証項目7は、その時点の（間引きされた）ベースマップ上でEEW複合負荷を
測ったもの。今回の計測は、その後の一連の高精細化コミット（`a455644`〜`fd86e16`）で基図の頂点数が
**約8.75倍**に増えた**後**の状態で同種の負荷を測っている。**基図の高精細化が、EEW発報時のflyTo・
毎秒更新・region-fill再描画と重なったときの実コストを押し上げたと考えられる。**

これは前回レビュー（`webgl-migration-review-89188bd.md`）で「合成的なスケーリングテストと実ジオメトリの
負荷特性が異なる可能性がある」とMEDIUM/情報として留保していた懸念が、**実機計測で現実の問題として
確認された**ことを意味する。

## 4. 次のアクション（開発機への申し送り）

- **`maxload-eew`の定常状態でも残る約2秒のブロック（12秒中約15〜21%・3回とも再現）は、このアプリの
  核心機能（緊急地震速報）に直結する問題であり、優先度高く原因調査・対処を要する。**
  ただし1回目の502ms単発フリーズ・2.5秒合計ほど壊滅的ではなく、**コールドスタート分を除いた実態は
  中程度だが安定して再現する劣化**という位置付けが正確。
- 切り分けの提案:
  1. **高精細化前のコミット（`5fba87b`以前）で同じ`maxload-eew`シナリオを実機計測**し、
     本当に高精細化が原因かを確認する（原因の特定なしに対処に進むと的外れになりうる）
  2. `maxload-eew`中に具体的にどのレイヤーの再描画が支配的かを`detect`や追加の計測フックで特定する
     （region-fillのpolygon再計算か、flyToの着地コストか、毎秒更新か）
  3. **起動時のジオメトリバッファ事前ウォーム**（アプリ起動直後にアイドル時間で全レイヤーを一度
     オフスクリーンで描画しGPUバッファを転送しておく）で、コールドスタート分の劣化（1回目の数値）は
     緩和できる可能性がある——ただし`maxload-eew`の定常状態の劣化には効かない別問題である点に注意
