## 【対応確認】比較の枠組み

`poc/leaflet-main.ts`（＝本番の描画方式を再現した Leaflet PoC・検証項目2 で使用したもの）に
カメラ計測を足す方式を採っている。**本番アプリにフックを仕込まずに済ませた判断は正しい**——
本番の `JapanMap.tsx` は map インスタンスを window に露出しておらず、
外から `flyTo` を起動するには本番コードの改変が要るところだった。
加えて項目2 と同じ土俵で測れるため、**過去の結果との一貫性も保たれる**。

MapLibre 版との対応を照合した:

| 観点 | MapLibre 版（`measure.ts`） | Leaflet 版（`leaflet-measure.ts`） | 判定 |
|---|---|---|---|
| 座標順 | `[lng, lat]` | **`[lat, lng]`**（`JAPAN_BOUNDS_LATLNG`） | **正しく反転** |
| duration 単位 | `durationSec * 1000`（ms） | **`durationSec` そのまま**（秒） | **正しく使い分け** |
| `START_ZOOM` / `CAMERA_MAX_ZOOM` | 5 / 8 | **5 / 8** | 一致 |
| `LOCAL_CLUSTER_SPREAD_DEG` | 0.15 | **0.15** | 一致 |
| padding パターン | 60 / 48 / 20 巡回 | **同一** | 一致 |
| duration パターン | 0.8 / 1.0 交互 | **同一** | 一致 |
| `fps` の定義 | `frames / (elapsedMs/1000)` | **同一** | 一致 |
| `estimatedVsyncMs` | スイート先頭の `static` でキャッシュ | **同一**（`lastEstimatedVsyncMs`） | 一致 |
| `moveend` 待ち | on/off を対にしてタイムアウト付き | **同一** | 一致（過去指摘が反映） |
| ラベル形式 | `point-d{sec}` / `bounds-p{pad}-d{sec}` | **同一** | 突き合わせ可能 |

**`estimatedVsyncMs` が両エンジンに入っている点が特に効く。**
項目2 のときは「両エンジンを同一セッションで計測し vsync 天井の一致を証跡で確認」する必要があったが、
今回は証跡自体が vsync を持つため、**別セッションで測っても後から天井の一致を検証できる**。

## 【対応確認】安定性観測の合否条件

前回レビューで「『長時間』の具体（何時間・どの操作・判定条件）が未定義」と指摘した点への対応。
`poc/README.md` に運用仕様が定義された。

**特に評価すべきは「タブ kill 自体はページ消滅のため自己申告できない」という穴を自分で見つけ、
最後に届いたサンプルの `elapsedSec`/`when` で「いつまで生きていたか」を判断する設計にしたこと。**
FAIL 条件②「サンプルが意図時間より前で途切れる」がこの観測に対応しており、
**測定対象がプロセスごと消えるケースを、外部から検出可能な形に落とし込んでいる**。

「初期の立ち上がり増加（working set がタイル/テクスチャで埋まる分）は正常なので無視し、
後半で持続的・単調に増え続けるかだけを見る」という読み方の指定も適切。
ウォームアップと本質的な増加を混同しない設計になっている。

## 【MEDIUM 1】飛行先の乱数が両エンジンで独立している

`randomPointInJapan()` / `randomLocalClusterBounds()` は両実装とも実行時に乱数を引くため、
**MapLibre 側（実機取得済み・`surface-go2-camera` 34件）と Leaflet 側（これから取得）は
異なる飛行列になる。**

飛行の負荷は移動距離とズーム変化量に依存するため、**1対1のペア比較にはならない**。
MapLibre 側の実測が fps 28.2〜52.7 と 1.9 倍の幅を持つことからも、
**飛行内容のばらつきが結果に効いている**ことが分かる。

**実務上の影響は差の大きさ次第である:**

- 両者の差が大きければ（例: 項目2 の 9 倍のような差）、平均・分布の比較で十分に判定できる
- 差が小さい（例: 1.5 倍以内）場合、**乱数由来のばらつきに埋もれて判定できない恐れがある**

**推奨**: まず現状のまま計測し、**差が明確なら追加作業は不要**。
差が微妙だった場合に限り、乱数シードを固定して同一飛行列を両エンジンで再現し、
**同一実行内のペア比較**に切り替える（本日 `blockMaxMs` で確認したとおり、
ペア比較にすれば実行間の共通変動が消える）。**その場合は MapLibre 側も再計測が必要**である点に注意。

## 【MEDIUM 2】Leaflet 有利のバイアスが項目3 にも引き継がれる

レビュー綴り `webgl-poc-review-82d4d39.md` の「情報3」で記録したとおり、
**Leaflet PoC は本番より軽い**:

- 本番の `ActiveFaultsLayer.tsx` は**可視線（SVG）に加えて当たり判定用の透明 Canvas 線を重ねて持つ**が、
  Leaflet PoC は MapLibre 版に対応物が無いため**当たり判定線を省略している**（条件を揃えることを優先した判断）
- プレート境界線・津波海岸線も本番では同一パターン

**飛行中は可視線と当たり判定線の両方が再クリップ・再描画の対象になる**ため、
**本番の Leaflet は今回測る Leaflet PoC よりさらに重い可能性が高い。**

したがって結果の読み方は次のようになる:

- **Leaflet PoC が MapLibre より遅い** → 本番はさらに遅いはずなので、**結論は強まる**（安全側）
- **Leaflet PoC が MapLibre より速い** → **バイアスを差し引く必要があり、そのまま結論にできない**。
  当たり判定線を足した条件での再計測を検討すべき

**後者の場合に備えて、この注意を計測前に共有しておく。**
（`webgl-poc-surface-go2-2026-07-27.md` の項目3 節、または計画書の該当箇所に一行あると確実。）
