# センサーノードのファームウェア

**読者はこのセンサーを自分で組み立てて動かす人。** ここにあるのはマイコンへ
書き込むプログラムで、**このアプリ本体のビルドには含まれない**。

自作地震計のセンサー側。加速度センサーの生波形を LAN 内へ流し続けるだけのもので、
震度の計算はしない。値の意味と全体の設計は
[`docs/implementation-plan.md`](../docs/implementation-plan.md) の項目 93 を参照。

- `seismo-node/seismo-node.ino` — ESP32 + MPU6050 用。**なぜそう書いたかはコード中のコメントに書いてある**（冒頭だけでなく各所にある）
- `seismo-node/wifi_config.example.h` — 接続先の雛形
- `iis2iclx-probe/` と `tools/` — センサーの品種を比べたときの道具（下記「センサーの品種を比べた」）。観測には使わない

## 送るもの（パケットの形）

UDP で **1 パケット＝ヘッダ 1 行＋サンプル行**。改行区切りのテキストで、
サンプルは 1 行 1 サンプル、軸をカンマで並べる。

```
{"v":2,"mac":"020000000003","bid":"7f3a91c4","sid":"i2c0-68","st":"MPU6050","ch":["HN1","HN2","HN3"],"ug":61.0352,"fs":2,"hz":100,"t":1790185612727,"q":1085044,"c":30,"o":21,"ack":1}
-1234,5678,-90
-1230,5675,-88
（以下 c 行）
```

| 欄 | 意味 |
|---|---|
| `v` | 形式の版 |
| `mac` | 基板の識別子。**焼いても置き換えても変わらない**唯一のもの（区切りなしの 12 桁） |
| `bid` | 起動ごとの ID。**`q` は再起動で 0 へ戻る**ので、通し番号だけでは一意にならない |
| `sid` | 基板の中のどのセンサーか。バス番号とアドレスの組（`i2c0-68` など） |
| `st` | センサーの型番 |
| `ch` | 軸の名前。**ここを見れば軸数が決まる**ので、受け手は型番を知らなくてよい |
| `ug` | 1 LSB あたりの µg |
| `fs` | フルスケール（g） |
| `hz` | サンプリング周波数 |
| `t` | **先頭**サンプルの時刻（unix ミリ秒） |
| `q` | 先頭サンプルの通し番号。**起動のたびに 0 から** |
| `c` | このパケットのサンプル数 |
| `o` | FIFO があふれた累計回数 |
| `ack` | `1` なら「届いたら返事をくれ」。受け手は基板ごとに 1 秒に 1 回、送り元へ `seismo-ack <mac>` の 1 行を返す（受け手を `SEISMO_ACK=off` で動かしている間は返さない。→ 下記「届いたかをホストに訊く」）。**欄が無ければ返事は来ない**（返事を読まない古いファームのため） |

**基板が名乗るのは「焼いても動かしても変わらない事実」だけ。** 設置に由来する事実
（どの観測点か、何と呼ぶか）は受け手が持つ。名前は設置ごとに変わるのに、データを
名前で引く形にすると、基板を別の部屋へ移した日を境に同じ名前が別の場所の波形を指す
ようになる。基板の名前は状態ページと mDNS には出るが、パケットには載らない。

`ch` の命名は SEED に倣う（`HN` ＝ 100 Hz 級の加速度計、3 文字目が向き）。
**方位が確定していなければ `1/2/3`、確定したら `Z/N/E`。** いまは取り付けの向きを
測っていないので `1/2/3`。

**生のカウント値を送り、換算はしない。** `ug` を掛けるのは受け手の仕事。
基板側で物理量へ直すと、あとから係数を直せなくなる。

**`q` と `o` が受け手の頼りになる。** `q` が飛べばパケットが届かなかったこと、
`o` が増えればセンサーの中でサンプルが失われたことを意味する。
**どちらも、前後を繋いではいけない印**——失われた時間を詰めて繋ぐとそこに段差ができ、
計測震度のフィルタはそれを強い揺れとして読む。

**`t` は半サンプル分を引いてある。** FIFO の中の最新サンプルは「たった今」ではなく、
前回のサンプリングの瞬間から今までのどこかで採られている——平均すれば半サンプル分
（100 Hz なら 5 ms）だけ前。引かないと、名乗る時刻が系統的に遅れる。

### 版 1（旧形式）

```
{"n":"seismo-3","s":"MPU6050","ug":61.0352,"hz":100,"r":2,"t":1790185612727,"q":1085044,"c":30,"o":21}
```

`mac`・`bid`・`sid`・`ch` を持たず、基板の**名前**（`n`）だけで名乗っていた。
`r` が `fs`、`s` が `st` にあたる。1 枚に 1 個しか読まないので `sid` も要らなかった。

**焼き直していない基板は、いまも版 1 を送る。** このリポジトリのファームが版 2 を
送るようになったのは 2026-09-25 だが、切り替わるのは基板ごとに書き込んだ時点。

**受け手はいまも版 1 を読める**——蓄えた記録は実装より長生きするので、古い形を
読めなくすることはできない。版 1 の `t` には上の半サンプル補正が入っていないため、
**受け手は版 1 を読むときだけその分を引く**。

## 配線

4 本だけ。他のピンは使わない。

| センサー側 | ESP32 側 |
|---|---|
| VCC | **3V3** |
| GND | GND |
| SDA | **GPIO21** |
| SCL | **GPIO22** |

**`22` の隣が `21` とは限らない。** 基板によっては `TX0`・`RX0` が
あいだに入る。ピンを数えず、基板の印字を読んで挿すこと。ここを 1 つずらすと
センサーは応答しないが、USB シリアルは平然と動き続けるので気づきにくい。

**VCC は `5V` ではなく `3V3` へ。** ブレイクアウトの多くは基板上に
レギュレータを持つが、省いた個体があり、それに 5V を入れると I2C の線に 5V が
乗って ESP32 側を壊す。

配線するのは上の 4 本だけで、**残りのピンは未接続のままでよい**。AD0（I2C アドレスの
最下位ビットを選ぶピン）も繋がない —— 落としたままなら `0x68` になり、1 枚に 1 個なら
衝突しない。

### 1 枚に 3 個ぶら下げるとき

**MPU6050 のアドレスは `0x68` と `0x69` の 2 つしか取れない**（AD0 で選ぶだけ）ので、
1 本のバスには 2 個までしか載らない。ESP32 は I2C を 2 つ持つので、**バスを分ける**。

| | AD0 | SDA | SCL | 名乗る `sid` |
|---|---|---|---|---|
| 1 個目 | GND（または未接続） | GPIO21 | GPIO22 | `i2c0-68` |
| 2 個目 | **3V3** | GPIO21 | GPIO22 | `i2c0-69` |
| 3 個目 | GND（または未接続） | **GPIO16** | **GPIO17** | `i2c1-68` |

`sid` がバス番号とアドレスの組になっているのは、この形を想定しているため。
**バスが違えば同じ `0x68` で構わない**（衝突するのは同じ 2 本の線の上だけ）。

**`WHO_AM_I` は 3 個とも `0x68` を返す。** このレジスタが持つのはデバイスアドレスの
上位 6 ビットで、**AD0 で決まる最下位ビットを反映しない**。`0x69` の個体が `0x69` と
名乗ることを期待すると、2 個目が永久に「応答しない」扱いになる。誰がどこに居るかは
`WHO_AM_I` ではなく、起動時の I2C スキャン（状態ページの `i2c`）で見ること。

**3 個並べるなら、1 個目と 3 個目の AD0 も GND へ明示的に落とすほうが安全。**
ブレイクアウトの基板上のプルダウンは実装されていない個体がありうるし、浮いたピンは
電気的に不定 —— **アドレスが不定になると「たまに動く」という最悪の形で出る**。

3 個目は 16/17 でなくてもよい。避けるのは下の表のピンだけ。
**ただし `ESP32-WROVER` は GPIO16/17 が内蔵 PSRAM に配線されているので使えない**
（金属シールドの印字で見分ける。`WROOM-32` なら空いている）。

### 起動しなくなったら、まず配線を疑う

**触ってはいけないピンに触れると、ファームが起動しないままリセットを繰り返す。**
症状はシリアル（115200 bps）にしか出ないので、それを読むまで気づけない。

| シリアルに出るもの | 触れているピン |
|---|---|
| `csum err:0xXX!=0xYY`（**値が毎回変わる**） | **GPIO12**。起動時 HIGH でフラッシュ電圧が 1.8V になり、3.3V のフラッシュが不安定に読める |
| `flash read err, 988` | **GPIO6〜11**。内蔵フラッシュ専用の配線（38 ピン版では `SD_CLK` `SD_DATA0〜3` `CMD` の名前で出ている） |
| 何も出ない・COM ポートごと消える | 短絡。すぐ USB を抜く |

**切り分けは足す順で。** 電源 2 本だけ → SDA を足す → SCL を足す、と 1 本ずつ進めれば、
どの線が悪さをしているか必ず分かる。**全部挿してから悩まない。**

**`5V` の隣の `GND` に注意。** 38 ピン版はその並びの手前に `D2`（GPIO9）・`D3`（GPIO10）・
`CMD`（GPIO11）が並ぶので、1 つずれると内蔵フラッシュの線を掴む。ブレッドボードを使うなら、
**3V3 と GND をそれぞれ電源レールへ 1 本ずつ渡して、センサーはレールから取る**ほうが安全。
ESP32 のピンへ直接何本も挿すより、間違いが起きにくい。

## 接続先を書く

```bash
cp seismo-node/wifi_config.example.h seismo-node/wifi_config.h
```

複製した側に SSID・パスワード・送り先を書く。**`wifi_config.h` は
`.gitignore` で除外してある**ので、このリポジトリには入らない。

遠隔で再起動する口を使うなら `ADMIN_TOKEN` にも値を入れる（下記
「遠隔で戻す口を持つ」）。**空のままでも焼けるし、行ごと無くても焼ける** ——
その場合は口が閉じたままになる。

## ノードの名前

名前は **MAC アドレスから引く**。対応表は `wifi_config.h` の `NODE_NAMES` で、
表に無い基板は MAC の下 3 バイトを使って `seismo-xxxxxx` と名乗る。

**1 つのバイナリを全台へ焼けるので、焼き間違いという事故が起こりえない。**
ビルド時に名前を切り替える形を避けた理由は `seismo-node.ino` の
`resolveNodeName` の直前に書いてある。

基板を足すときは、起動時のシリアル出力（**115200 bps**）か状態ページに出る
MAC を対応表へ書き足す。

## 書き込む

```bash
arduino-cli compile --fqbn esp32:esp32:esp32 firmware/seismo-node
arduino-cli upload -p <ポート> --fqbn esp32:esp32:esp32 firmware/seismo-node
```

2 台目以降は OTA で更新できる。

```bash
arduino-cli upload -p seismo-1.local --protocol network --fqbn esp32:esp32:esp32 firmware/seismo-node --upload-field password=
```

**OTA は受信側の PC へ内向きの TCP 接続を張り返す。** ファイアウォールが
それを止めていると「No response from device」で失敗するので、書き込みツールへ
受信を許可する規則を足すこと。

## 動いているか見る

`http://seismo-1.local/` が JSON を返す。項目はこれで全部。

```json
{"node":"seismo-1","mac":"02:00:00:00:00:02","boot_id":"a3912b8d","sensor":"MPU6050",
 "uptime_s":80,"rssi":-48,"ip":"192.0.2.42","time_synced":true,"unix":1790339210,
 "sample_hz":100,"ug_per_lsb":61.0352,"head_truncated":0,
 "wifi_up":true,"udp_armed":1,"udp_arm_fail":0,"wifi_got_ip":1,"free_heap":203672,
 "sntp_syncs":1,"sntp_last_sync_unix":1790339135,
 "udp_open":true,"acks":72,"ack_age_s":0,"ack_foreign":0,"ack_level":0,"ack_rearms":0,"ack_reconnects":0,
 "host_probe_fail":0,"self_restarts":0,"restart_skipped":0,"reset_reason":"poweron",
 "booted_by_self_restart":false,
 "i2c":[{"bus":0,"begun":true,"found":2,"addrs":"0x68,0x69","addrs_truncated":false},
        {"bus":1,"begun":true,"found":1,"addrs":"0x68","addrs_truncated":false}],
 "sensors":[
   {"sid":"i2c0-68","ok":true,"who_am_i":"0x68","seq":7614,"packets":255,"overflow":0,
    "i2c_fail":0,"fail_streak":0,"partial":3,"partial_streak":0,
    "realign":0,"realign_streak":0,"unsent":0,"pretime":60,
    "init_tries":1,"init_fails":0,"rem_hist":[1,0,1,0,1],"last":[-92,112,15904]},
   …（センサーの数だけ）]}
```

基板そのものについて:

- `boot_id` — 起動ごとに変わる ID。パケットの `bid` と同じ値で、**再起動を
  「パケットが遅れて届いた」と取り違えないための印**
- `time_synced` — **この起動で** SNTP が時計を合わせたか。**合わせるまで 1 件も送らない**ので、
  ここが `false` のまま動かない基板は一言も波形を出していない（下記「時計が合う前は送らない」）
- `sntp_syncs` / `sntp_last_sync_unix` — この起動で SNTP が時計を合わせた回数と、最後に合わせた
  時刻（unix 秒。まだなら 0）。**15 分ごとに 1 つ増えるのが正常。** 最後に合わせた時刻が
  何十分も前のままなら、取り直しが止まっている
- `wifi_up` — いま Wi-Fi に繋がっているか
- `wifi_got_ip` — アドレスを取り直した回数。**起動したときの 1 回ぶんを含む**ので、
  1 なら起動してから一度も切れていない
- `udp_armed` — UDP のソケットを**開けた**回数（下記「Wi-Fi が繋がり直したら、
  UDP を開き直す」）。**普段は `wifi_got_ip` と同じ値になる**（2026-10-01 の実機で、
  繋ぎ直しを繰り返して差 0）。**差が出ても異常ではない** ——
  - `wifi_got_ip` のほうが大きい: アドレスの取り直しが立て続けに来て、1 回の開き直しで
    まとめて済んだ
  - `udp_armed` のほうが大きい: 1 度の接続を、繋がり具合の見張りとイベントの
    両方が拾って 2 回開いた（開きすぎは無害）。**または、繋がり直しとは別に開き直した**
    —— 返事の途絶で作り直した（`ack_rearms` が同じだけ増える）か、開き損ねたものを
    開き直した（`udp_arm_fail` が増えている）

  **送れているかどうかは、この差では判らない。** 開き損ねは次の `udp_arm_fail` に出る
- `udp_open` — UDP のソケットがいま開いているか。**`false` のままなら、その基板は返事を
  読めていない**（Wi-Fi が繋がっている間は 15 秒ごとに開き直しを試すので、続くのは
  開けない原因が消えないときだけ）。**Wi-Fi が切れている間は直前の値が残る**ので、
  `wifi_up` と併せて読む（繋がり直せば必ず開き直す）
- `udp_arm_fail` — 開こうとして**失敗した**回数。**増えていたら、開き直せるまでその基板は
  返事を読めず、送れていないこともある**（コアが送る瞬間にソケットを作り直すので、送信だけは
  通っている場合がある）。開けた回数と分けてあるのは、1 つに
  まとめると「開けたつもり」の数字になってしまうため —— `endPacket()` が真を返しながら
  1 バイトも出ていなかったのと同じ種類の乖離を、診断の側で作らないようにしている
- `free_heap` — 空きメモリ（バイト）。**繋ぎ直しのたびにソケットを開き直す作り**なので、
  放し忘れがあれば `udp_armed` が増えるぶんだけ減っていく。**状態ページを読むだけでも
  数百バイト上下する** —— 2026-10-01 の実機で、繋ぎ直しをせずに状態ページを 8 回続けて
  読んだところ 1 回ごとに約 250 バイト減り、8 回目で 1508 バイト戻った。
  **減り続けて戻らないなら漏れを疑う**
- `acks` / `ack_age_s` — ホストから「届いた」の返事を受けた数と、最後に受けてからの秒数
  （下記「届いたかをホストに訊く」）。**`ack_age_s` が 0〜1 を行き来していれば届いている。**
  一度も受けていなければ `-1`。**`acks` が 0 のままなら、その起動では立て直しが働かない**
  （ホストが返事を返さない版か、`SEISMO_ACK=off`）
- `ack_foreign` — 同じソケットへ届いた、自分宛ての返事ではないもの。**普段は 0**
- `ack_level` — 返事が途絶えたときに次に打つ手（0: UDP を作り直す・1: Wi-Fi を繋ぎ直す・
  2: 再起動）。**返事が 1 つ届けば 0 へ戻る**ので、0 でなければいま立て直しの最中。
  **ただし再起動を上限で飛ばしたときも 0 へ戻る**（作り直しからやり直すため）——
  0 だから健全とは限らないので、`ack_age_s` と `restart_skipped` も併せて見る
- `ack_rearms` / `ack_reconnects` — 返事の途絶で UDP を作り直した回数・Wi-Fi を繋ぎ直した回数
- `host_probe_fail` — 返事が途絶えたが、ホストが HTTP にも答えなかったので段を上げずに
  待った回数。**ホストを止めている間や、ホストの処理が止まっている間はこれが増える**（基板の故障ではない）
- `self_restarts` / `restart_skipped` — 返事の途絶で自分から再起動した回数（6 時間の窓の中）と、
  上限（3 回）に達していたので再起動を飛ばした回数。**`restart_skipped` が増えていたら、
  再起動では直らない何かが起きている**
- `reset_reason` / `booted_by_self_restart` — この起動の理由（`poweron`・`sw`・`panic`・
  `brownout` など）と、それが返事の途絶による自分からの再起動だったか。`/restart` や
  OTA でも理由は `sw` になるので、後者で見分ける
- `rssi` — Wi-Fi の受信強度（dBm）。弱いと送信が滞り、あふれの原因になる
- `head_truncated` — パケットのヘッダが収まらず送れなかった回数。**起こらないはず**の
  値なので、0 でなければファームの不具合
- `i2c` — **起動時にバスを舐めた結果。** 「居るのに読めない」と「そもそも居ない」を
  分けられる唯一の手掛かり。3 個ぶら下げたなら `bus0` に 2 つ・`bus1` に 1 つ出る。
  `begun` はバスを開けたかどうか、`addrs_truncated` は並びが長すぎて切れたかどうか

センサーごとに:

- `ok` — **そのセンサーを使っているかどうか。** 下がっていたら、まず `i2c` を見る。
  居るのに `false` なら初期化の失敗、居ないなら配線
- `overflow` — サンプルが失われた累計回数。受け手はこの値の変化で不連続を知る。
  **原因は 1 つではない** —— FIFO のあふれ・FIFO の読み出し中に I2C が欠けた・
  端数が続いたので作り直した（`realign`）・降格から復帰した、のいずれでも進む。
  原因が違っても「前後を繋いではいけない」という結論は同じなので、1 つの値にまとめてある
- `partial` — FIFO の件数が 6 の倍数でなかった回数。**これは `overflow` に入らない** ——
  その周期を読まずに見送るだけで、サンプルは FIFO に残る（下記「FIFO の端数は捨てない」）
- `realign` — 端数が続いたので FIFO を作り直した回数。**こちらは異常。** `overflow` の
  内訳の 1 つで、残りは `i2c_fail` と `init_tries` の増え方から読む
- `partial_streak` / `realign_streak` — いま何周期続いているか。累計ではなく**進行中の
  値**で、端数なしで読めた時点で 0 へ戻る。「たまたま 1 回目」と「まだ一度も起きていない」を
  見分けるためのもの
- `rem_hist` — 端数の内訳。**先頭が 1 バイト・末尾が 5 バイト。** 何が起きているかを
  分けるための値で、読み方は下記
- `i2c_fail` / `fail_streak` — I2C の取引が失敗した累計と、いま連続している回数
- `unsent` — 読めたのに送れなかったサンプル数。**Wi-Fi が切れているあいだも
  吸い出しは進む**ので、ここが増えていれば「センサーが死んだ」ではなく
  「送れていなかった」と分かる
- `pretime` — **時計が合う前**に読めたサンプル数。`unsent` と分けてあるのは、原因も
  手当ても違うため（あちらは Wi-Fi が繋がっていない、こちらは繋がっているが SNTP の
  応答がまだ来ていない）。**起動直後に少し増えて止まるのが正常** —— 電源を入れ直した
  実機で 60（0.6 秒ぶん）だった。増え続けているなら時刻が取れていない
- `init_tries` / `init_fails` — 初期化を試みた回数と、直近の初期化で失敗した I2C 取引の数
  （設定の書き込みと WHO_AM_I の読み取りの両方を含む）
- `last` — 最後に読んだ生の 3 軸。静止しているなら長さが 1 g 相当（約 16400）に
  なるので、**センサーが値を返しているのに配線が緩んでいる**といった形も見分けられる。
  ただし**個体差が大きい**（下記「直していないこと」）
- `uptime_s` と `seq` — 割れば実際のサンプリング周波数が出る。`sample_hz` は設定値

### FIFO の端数は捨てない

FIFO の件数（バイト数）が 6 の倍数にならないことがある。**たいていは異常ではない** ——
1 サンプル分の 6 バイトを内部で書いている最中に件数をラッチすれば端数が出る。データシート
（[MPU-6000/MPU-6050 Register Map and Descriptions](https://cdn.sparkfun.com/datasheets/Sensors/Accelerometers/RM-MPU-6000A.pdf)・
RM-MPU-6000A-00）も、件数が 1 サンプル分の倍数になるとは定めていない。**定めていないのは
「倍数になる」という保証のほうで、端数が正常だと積極的に述べた記述も無い** —— そのぶんは
下の判定と実測で埋めている。

**端数を見たら、その周期は読まずに 1 周期待つ。** 待っているあいだもサンプルは FIFO に
残るので失われない（次の周期までに溜まるのは 60 サンプル。FIFO は 170 サンプル分ある）。
増えるのは `partial` だけで `overflow` は動かないので、**受け手の区間も切れない。**

**端数が 2 周期続いたときだけ FIFO を作り直す**（`realign`）。こちらは異常のほうなので
`overflow` も進み、受け手へ切れ目が伝わる。**作り直しても直らないまま 5 回続けば、その
センサーは降格して初期化からやり直す**（下記「1 個だけ黙ったとき」）。

どちらが起きているかは `rem_hist` と続き方で読む。

| | 書き込み途中（正常） | 1 バイト失われた（異常） |
|---|---|---|
| 端数の値（`rem_hist`） | 1〜5 に散る | 5 に偏る |
| 続き方 | 1 周期で消える | 作り直すまで残る |

**`realign` が増えているなら、右側を疑うこと。** ただし**右列はまだ実機で見ていない** ——
`realign` は一度も発火していないので、設計上こうなるはずという想定にとどまる。

実測では左側だった —— 3 台 9 センサーを 46 分動かして端数 44 回が 1〜5 に散り
（1 バイトから順に 12/6/12/8/6 件）、`realign`・`overflow`・`i2c_fail` はいずれも 0。
頻度は読み出し 1 回あたり 0.053%、サンプル周期 10ms に掛ければ約 5µs の窓に当たる勘定で、
6 バイトを書く時間として辻褄が合う。

> 端数を切り捨てて残りだけ読み進める形を採っていないこと、続き方の判定に端数の値の一致を
> 使っていないことには、それぞれ理由がある。`drainSensor` のコメントを見ること。

### 1 個だけ黙ったとき

**1 個の頃は「データが来ない」がそのまま異常の合図だった。** 3 個あると残りが流れ続ける
ので、外からは正常に見える。そこで次の一巡を持たせてある。

1. **数える** — I2C の失敗・FIFO の端数・送れなかったサンプルを、種類ごとに分けて数える。
   1 つに合算すると、状態ページを見ても何が起きたか判らない
2. **降格する** — 連続 20 回（約 6 秒）失敗したセンサーは `ok` を下ろす。
   **FIFO を作り直しても端数が残る、が 5 回続いた場合も同じく下ろす**（判定に使うのは
   `fail_streak` ではなく `realign_streak`）。**あふれが続いても降格はしない**
3. **やり直す** — `ok` が下りているセンサーは 10 秒ごとに初期化をやり直す。
   **1 周期に 1 個だけ**（初期化は 150 ms の待ちを含むので、まとめて試すとそのあいだ
   OTA も状態ページも応答しない）
4. **伝える** — 復帰したら `overflow` を 1 つ進める。降格は約 6 秒の連続失敗で起きるのに
   FIFO は 1.7 秒ぶんしか持たないので、**黙っていた間サンプルは確実に失われている**

> 2 で「あふれでは降格しないのに、作り直しが続けば降格する」と扱いを分けているのには
> 理由がある。`demoteStuck` と `REALIGN_STREAK_TO_DEMOTE` のコメントを見ること。

**3 が無いまま 1・2 だけ入れると、一過性の失敗でそのセンサーが永久に死ぬ。**
逆に 2 が無いと、設定が飛んだセンサーは電源を入れ直すまで戻らない。

**4 を落とすと、受け手は空白に気づけない。** 読めていない間は通し番号も進まないので、
復帰したセンサーの波形は切れ目なく続いているように見える —— 上の「`q` と `o` が受け手の
頼りになる」で書いた段差が、**1 個のセンサーだけで起きる**形。

**`ok` は「WHO_AM_I が読めたか」では決めない。** あれは静的なレジスタなので、
スリープ解除や FIFO_EN の書き込みが落ちていても平然と応答する。**読めるが溜めない
センサーが `ok:true` のまま無言になる**のがいちばん厄介な壊れ方で、「届かない」は
気づけても「健全と名乗って届かない」は気づけない。設定の書き込みがすべて通ったことまで
見て決めている。

**USB のポート番号で基板を呼ばないこと。** シリアル番号を持たない個体があり、
挿す口を変えるたびに番号が動く。名前（`seismo-1.local`）か MAC で指すこと。

### ネットワークが黙ったとき

**同じ壊れ方が、センサーではなくネットワークの側でも起きる。** 基板は送る側なので、
繋がりが壊れても自分では気づけない —— **`endPacket()` は成功を返し、状態ページ（TCP）は
別の経路で応え続ける。**

> 2026-09-30、1 枚が 5 日間この状態だった。HTTP も ping も応え、状態ページは
> 「センサー 3 つとも正常・パケット 144 万・`unsent` 0」を名乗っていたのに、
> **UDP は 1 バイトも届いていなかった。** `endPacket()` は 144 万回とも真を返していた。
> 電源を抜くしか戻す手が無かった。

手当ては 4 つ。**`endPacket()` の戻り値を当てにしない**ことが共通の前提。

**最初の 3 つは「出ていったはず」を確かめやすくするだけで、ホストに着いたことの
確認ではない。** 上の 5 日間の形そのものを基板が自分で見つけられるのは、4 つ目
（「届いたかをホストに訊く」）だけ。

#### 時計が合う前は送らない

`configTime()` は**投げるだけで応答を待たない。** 返ってくるのは数秒後で、その間
`gettimeofday` は 1970 年を返す。そのまま送ると、受け手には
**「通し番号は続いているのに、時刻だけが 50 年以上飛んだ」**パケットとして届く。

受け手（`seismo-host`）はそれを区間の切れ目として扱うようになったが、**そもそも
送らないのが筋。** 番号が続いたまま時刻が飛ぶ形は、受け手の側では「基板が壊れた」と
「時計がいま合った」を**見分けられない**。

送らなかったサンプルは `pretime` に数える。送るかどうかと状態ページの `time_synced` は
**同じ 1 つの判定**を通る —— 別々に持つと、ページが「合っている」と名乗りながら
1 件も送っていない状態が作れてしまう。

**「合った」は時計の値ではなく「この起動で SNTP が一度合わせたか」で決める。**
ESP32 は**ソフトウェアの再起動**（OTA の書き込み後・`/restart`・返事の途絶による自分での
再起動）では時計を残したまま起き上がる。時刻の値だけを見ると、起動した瞬間に
「合っている」と判定し、**SNTP を一度も始めないまま走り続ける**。

> 2026-10-01 に実際にこうなった。3 枚の時計が 22 時間で 0.5〜1.3 秒遅れ、状態ページは
> `time_synced:true` と名乗り続けた。ホストの観測点の合成は裏付けを**データの時刻**で
> 待つので、いちばん遅れた基板を毎回欠くようになった（生データでは、それ以前の起動では
> 3 時間ごとに取り直しの跳びが見え、この起動からは 1 度も無かった）。

**時計は 15 分ごとに取り直す**（コアの既定は 3 時間）。水晶のずれは基板ごとに違い、
実機の 3 枚で約 5〜14 ppm あった（取り直しの跳びと、取り直さなかった間のずれの伸びから
測った）。3 時間置くと、いちばんずれる基板は 1 回で時計が約 136 ms 跳び（実測）、ホストは
パケットの時刻が 100 ms を超えて跳ぶと区間を切る。15 分なら跳びは約 13 ms に収まる。

**SNTP（ネットワーク越しに時刻を合わせる仕組み）の応答が永久に返らない環境では、
その基板は一言も送らない。** `time_synced` が `false` のまま・`sntp_syncs` が 0 のまま・
`pretime` が増え続けることで分かる。シリアルには SNTP を始めたときと時計が合ったときに 1 行ずつ出る。
`configTime()` の呼び直しは要らない —— **ESP32 の通信部品（lwIP）が持つ SNTP は
自分で再試行する**（間隔を倍々に伸ばしながら）。この起動で合った後は呼ばないようにしてある。

**ソフトウェアの再起動のあとも、合うまでは送らない。** 持ち越した時計のまま送る逃げ道は
置いていない —— 置けば、上の「ずれた時刻のデータが黙って流れる」状態を作り直すことになる。
代わりに、送らない間は返事の途絶も起きないので、**返事による立て直し（下記「届いたかを
ホストに訊く」）は動かない。** 一時的な不通なら SNTP の再試行で合ったところから送り始める。

> **これは気づきやすさと引き換えにした。** 以前は同期前のパケットがそのまま出ていき、
> ホストが「足場がエポックとして成り立たない」と**毎分の要約で警告していた**
> （`timebase-epoch`）。送らなくなったぶん、**ホストから見ると単に居ないだけ**になる。
> 観測点に割り当てた基板なら、ホストが 60 秒で「届いていない」と知らせる
> （[`seismo-host/README.md`](../seismo-host/README.md)「割り当てた基板が届いていないことを知らせる」）。

#### Wi-Fi が繋がり直したら、UDP を開き直す

ESP32 の `WiFiUDP` は Wi-Fi が切れるとソケットが無効になる。**それでも
`beginPacket()` / `endPacket()` は成功を返す。** だから繋がるたびに
`stop()` → `begin(0)` で開き直す（回数は `udp_armed`）。

**`loop()` の見張りだけでは足りない。** 切れてから繋がるまでが `loop()` の 1 周より
短いと、状態はずっと「繋がっている」に見えて変わり目が立たない —— そのとき
**ソケットは無効なまま残る**。つまり直そうとしている症状が、別の入口からそのまま戻る。
そこで Wi-Fi のイベント（`STA_GOT_IP`）も受けて、**いま持っている見立てを捨てる**。
立て直す処理はイベント側には書かない（別の実行の流れから同じ持ち物を触ることになる）。

**起動時に Wi-Fi を待たない。** 以前は 30 秒待って、繋がらなければ SNTP・mDNS・OTA・
状態ページ・UDP を**丸ごと飛ばしていた**。`setAutoReconnect(true)` が後で繋ぎ直すので
Wi-Fi だけは復活するが、そのとき**開いていないソケットへ UDP を投げ続け、状態ページも
出ず、OTA も立っていないので遠隔で焼き直すこともできない。**
**停電からの復帰で普通に踏む** —— ルーターが立ち上がるのに 1 分以上かかるのに、
基板は 1 秒で起きて 30 秒で諦めるため。

**ただし「一度も繋がらない」基板は、変わり目が立たないので黙る。** 待つのをやめた
ことで、かつて 30 秒後に出ていた `# wifi FAILED` の記録が失われていた。
**起動から 30 秒たっても一度も繋がらなければ、シリアルへ 1 度だけ警告を出す** ——
この場面では状態ページも OTA も立っていないので、**シリアルが唯一の診断の手段**。

**繋ぎ直しても状態ページ・mDNS・OTA は生き残る**（実機で確認。わざと切って
繋ぎ直した直後に 3 つとも応答し、OTA の書き込みも通った）。だから立て直すのは
UDP と SNTP だけでよい。

#### 遠隔で戻す口を持つ

| 口 | すること |
|---|---|
| `POST /restart` | 応答を返してから再起動する |
| `POST /wifi-reconnect` | Wi-Fi を切って繋ぎ直す。**再起動はしない**（`boot_id` が変わらない） |

どちらも **`wifi_config.h` の `ADMIN_TOKEN` を `X-Seismo-Token` ヘッダで要求する。**
状態ページ（`/`）は読むだけなので素のままだが、こちらは基板の状態を変えるので、
同じ LAN にいる誰でも落とせる形にはしない。

**断る理由ごとに別の応答を返す。**

| 応答 | 意味 |
|---|---|
| `501` | **口は閉じている**（この口を持つファームを、`ADMIN_TOKEN` を入れずに焼いた） |
| `403` | 口は開いているが、合言葉が違う |
| `404` | **この口を持つ前のファームのまま**（2026-10-01 より前に焼いた基板）。または `GET` で叩いた（`POST` 限定） |

**`POST` で叩いて 404 なら、その基板は焼き直すしかない。** 遠隔で戻す口そのものが
無いので、電源を入れ直してから OTA で焼く。

**501 と 403 を同じにしないこと。** `wifi_config.h` は `.gitignore` で各基板の手元に
残るので、ファームを新しくしても `ADMIN_TOKEN` の行が無いままのことがある。そこへ 403 を
返すと、呼んだ側は「打ち間違えた」と読んで合言葉を何度も試す —— **復旧の手が迷走する。**

```bash
curl -X POST -H "X-Seismo-Token: <token>" http://seismo-1.local/restart
curl -X POST -H "X-Seismo-Token: <token>" http://seismo-1.local/wifi-reconnect
```

**`GET` では動かない**（404）。ブラウザの先読み・履歴の復元・クローラが踏むだけで
基板が落ちる形にはしないため。

**応答を返してから落とす。** 即座に再起動すると応答が返らず、呼んだ側には
「繋がらなかった」としか見えない —— **再起動できたのか届かなかったのかが区別できない口は、
再起動を頼む口として使えない。**

> **`setAutoReconnect(true)` は当てにならない。** あれが効くのは**予期しない**切断
> （電波が届かない・AP が落ちた）に対してだけで、**こちらから呼んだ `disconnect()` は
> 「意図した切断」として扱われ、繋ぎ直されない。** 2026-10-01 に自動で戻ると思って
> `disconnect()` だけを呼び、**基板を 1 枚ネットワークから落とした**（ping も通らず、
> 電源を入れ直すまで戻らなかった）。`/wifi-reconnect` は `begin()` を自分で呼ぶ。

#### 届いたかをホストに訊く

UDP は投げたら終わりで、届いたかは送った側からは分からない。そこで**ホストに
返事をもらう。** パケットのヘッダに `"ack":1` を載せると、ホスト（`seismo-host`）は
送り元へ `seismo-ack <mac>` の 1 行を返す。基板ごとに 1 秒に 1 回まで。

**返事が 15 秒来なければ、軽い手から順に立て直す。**

| 段 | すること | 波形が止まる長さ |
|---|---|---|
| 0 | UDP のソケットを作り直す | ほとんど止まらない |
| 1 | Wi-Fi を切って繋ぎ直す（`/wifi-reconnect` と同じ道） | 数秒 |
| 2 | 再起動する | 時計合わせからやり直すので十数秒 |

**返事が 1 つ届けば段 0 へ戻る。** 段を上げるたびに 15 秒待つので、再起動まで
最短 45 秒かかる。

**15 秒は「返事を 15 回続けて落とした」にあたる。** UDP の返事が数回落ちる程度では
上がらず、本当に途絶えたときだけ上がる。計り始めるのは**返事のあとで最初に送れた
とき** —— Wi-Fi が切れている間や時計が合う前は送っていないので、返事が来ないのは
当たり前だから。

**段を上げる前に、ホストが止まっていないかを確かめる。** ホストの HTTP の口
（既定 50506。`wifi_config.h` の `HOST_HTTP_PORT` で変えられる）へ `GET /healthz` を送り、
**答えが返らなければ段を上げずに待つ**（`host_probe_fail` が増える）。待つのは
接続に 0.5 秒・答えに 0.5 秒まで —— この間は FIFO の吸い出しも止まり、吸い出しの間隔を
差し引くと待てるのは 1.4 秒なので、0.4 秒を残してその内に収めてある。開発でホストを止めるたびに基板が再起動していたら、
ホストを戻したときには基板が時計合わせの最中で、しばらく波形が来ない。
**HTTP が答えるのに UDP の返事が来ない**、が直したい形そのもの —— 5 日間黙った基板も、
HTTP には応え続けていた。

**TCP が繋がるだけでは「生きている」と見なさない。** 接続を受け付けるのは OS なので、
ホストのプロセスが止まっていても繋がる（処理を止めた node へ 6 ms で繋がり、HTTP は
時間切れになった）。かつては TCP の接続だけで確かめていて、2026-10-02 13:41 に
同じ機械で重い処理が走ってホストが約 45 秒止まったとき、基板 2 枚がホストは生きていると
読んで再起動まで段を上げた。**答えの状態コードは見ない** —— `HTTP/` で始まる答えが返れば
処理は回っている（`/healthz` を持たない古いホストも 404 で答える）。

**再起動は 6 時間に 3 回まで。** 再起動しても直らない故障で再起動を繰り返すと、
そのたびに時計合わせからやり直すので波形がほとんど出なくなる。上限に達したら
再起動だけを飛ばし（`restart_skipped` が増える）、作り直しと繋ぎ直しは続ける。
回数は再起動をまたいで残す必要があるので、電源を切るまで消えないメモリ（RTC）に
置いてある。**電源を入れ直すと 0 に戻る。** 置き場所は `RTC_NOINIT_ATTR` でなければ
ならない —— よく使われる `RTC_DATA_ATTR` が残るのは深いスリープからの復帰だけで、
`ESP.restart()` では初期値へ戻る（そこへ置くと回数が毎回 0 になり、上限が効かない）。

**返事を読んだら、読み残しを必ず捨てる**（`clear()`）。ESP32 の `parsePacket()` は
前のパケットを読み残していると、次から 0 を返し続ける。想定より長いものが 1 つ
届いただけで以後の返事が読めなくなり、基板は返事が途絶えたと取り違えて立て直しを始める。

**この起動で返事を一度も受けていなければ、段を上げない。** 返事を返さないホスト
（この仕組みより古い版、または `SEISMO_ACK=off` で動いているもの）へ繋いだ基板が、
繋ぎ直しと再起動を延々と繰り返さないため。シリアルに 1 度だけその旨が出る。
**再起動の繰り返しもここで止まる** —— 再起動した先で返事が戻らなければ、その起動では
段を上げない。引き換えに、**起動した直後から送れていない基板は自分では戻らない**
（起動したばかりならソケットも新しいので、起きにくい形と見ている）。

> **ホストを先に新しくすること。** 新しいホストは `ack` を求めない古いファームには
> 返事を返さないので、先に入れても何も起きない。逆に基板を先に焼いても、返事が
> 一度も来ないので段は上がらない（上の門）—— どちらの順でも壊れはしないが、
> 立て直しが働き始めるのは両方が揃ってから。

**返事が来ているかは状態ページで分かる。** `ack_age_s` が 0〜1 を行き来していれば
届いている。ホストの側では `GET /status` の `acks`（`sent`・`failures`・`throttled`）。

**実機で 3 通りとも確かめてある**（2026-10-01、seismo-1）。**ホストの生存を TCP の接続だけで
確かめていた版での結果**で、HTTP の答えで確かめる今の版では次の 2 つを確かめた（2026-10-02、3 枚とも）。

- **ホストを止めて立ち上げ直した**：止まっている間に `host_probe_fail` が 1〜2 増え、段は 0 のまま
- **ホストのプロセスを 50 秒一時停止した**（`NtSuspendProcess`。処理は止まるが TCP は繋がる状態）：
  返事の途絶が 45〜50 秒まで伸びる間、15 秒ごとに `host_probe_fail` だけが増え、段は 0 のまま。
  再起動も繋ぎ直しも起きず、再開すると返事が戻った（TCP だけで確かめていた版は、
  2026-10-02 13:41 にホストが約 45 秒止まったとき、2 枚が再起動まで段を上げた）

- **ホストを止めた**：15 秒ごとに `host_probe_fail` だけが増え、段は 0 のまま
- **ホストを `SEISMO_ACK=off` で動かした**：15 秒ごとに作り直し → 繋ぎ直し →
  再起動と上がり、再起動した先では `booted_by_self_restart: true`・`self_restarts: 1`。
  返事を一度も受けていないので、その起動では段がそれ以上上がらなかった（100 秒見た）
- **返事を戻した**：再起動せずに返事を受け直し、段は 0 のまま

**再起動の上限（3 回）で飛ばす経路は、まだ実機で走らせていない。** 3 回目のあとに
返事が戻り、また途絶える、を 6 時間の窓の中で繰り返さないと通らない。

**ソケットを開き損ねたら、段とは別に開き直す。** 開き損ねたままだと返事を読みに行けず、
段を上げる仕組みごと止まる（Wi-Fi が繋がっている間、15 秒ごとに試す。`udp_open` で見える）。
段を上げる話ではないので、返事を一度も受けていない起動でも、ホストが止まっていても試す。

**送り元のアドレスは確かめない。** 照合するのは返事に書かれた MAC だけ。LAN の中で
返事を偽る相手は想定していない（OTA にも認証が無いのと同じ見立て）。

## 届かなかった分を残しておく

**届かなかったことを知っているのはホストのほう。** 基板は `endPacket()` の真偽からも、
1 秒に 1 回の返事からも、どのまとまりが届いたかを知れない（返事は「生きている」を知らせる
だけ）。そこで基板は**送った分を手元に残しておき、ホストが欠けた範囲を指定して取りに来る**
（`GET /backlog`）。ホストが欠けをどう覚えて取りに行くかは
[`seismo-host/README.md`](../seismo-host/README.md)「届かなかった分を基板へ取りに行く」。

**残す場所は 2 段。**

| 置き場所 | 抱えられる長さ | いつ書くか |
|---|---|---|
| メモリの輪（300 まとまり・約 79 KB） | 直近約 30 秒（3 センサー） | 時計が合っている間に作ったまとまりを全部 |
| フラッシュの輪（データ領域 `spiffs`。既定の分割では 352 区画・約 1.4 MB） | 約 11 分 | ホストの返事が 8 秒途絶えている間だけ |

- **フラッシュへは途絶えている間だけ書く。** 常に書くと、区画の書き換え回数（1 区画あたり
  約 10 万回）を日々食い潰す。途絶えている間だけなら、輪を 1 周しても 1 区画 1 回で済む
- **8 秒待つのは、電波の弱い基板の普段の途切れを拾わないため。** RSSI −77 の基板では返事が
  数秒途切れることが珍しくなく、3 秒にしていたときは 100 秒に 5 回書き始めていた。メモリの輪が
  30 秒ぶんあるので、8 秒待っても取りこぼさない
- **書き始めるときは、最後に返事を受けた時刻の 2 秒前から写す。** 返事が来ていた間に送った分は
  届いている。輪を丸ごと写すと、数秒途切れるたびに 30 秒ぶんを書き直す（実測で 100 秒に 49 区画）
- **書き始め直すときは、前に写した位置より前へは戻らない**（同じ分で区画を食わない）
- **続けて書くのは 30 分まで。** 返事を一度も返さないホストを相手にすると、途絶えが終わらないので
  書き出しも終わらない。止めたら、**返事が一度戻るまで書き始めない**。ホストは見つけた欠けを
  20 分で諦めるので、それより長く書いても取り戻せる分は増えない
- **区画は起動 ID を持つ。** 基板が再起動しても、返事が途絶えていた間の前の起動の分を返せる
  （メモリの輪は再起動で消える）
- **区画の中身に CRC-32 を持たせる。** 起動時に全区画を読んで確かめ（352 区画で 133 ms。2026-10-02 に a0b7 で実測）、
  合わない区画は数えずに外す。書いている途中で電源が落ちた区画を「抱えている」と名乗ると、
  ホストはその範囲を訊き、返らなかった分を「上書きされた」と記録してしまう。
  返す前にももう一度確かめる
- **1 周に書く区画は 1 つまで。** 1 区画の消去と書き込みで処理が止まる（2026-10-02 に a0b7 で実測 40〜57 ms）

**`GET /backlog?sid=<センサー>&bid=<起動 ID>&from=<番号>&to=<番号>`** —— `[from, to)` に掛かる
まとまりを、**送ったときのパケットそのままの形で**並べて返す（1 回に 30 まとまりまで。
30 まとまりで約 17 KB・2026-10-02 に a0b7 で実測 0.17〜0.19 秒）。応答を作っている間は吸い出しも止まるので、
続きはホストが訊き直す。見出しに次を載せる。

- `X-Backlog-Have` —— そのセンサーで抱えている範囲 `<先頭>-<末尾の次>`。無ければ `none`。
  訊かれた範囲がこれより古ければ、その分はもう取り戻せない
- `X-Backlog-More` —— 上限で打ち切ったなら `1`
- `X-Backlog-Next` —— 返した最後のまとまりの末尾の次
- `X-Backlog-Bid` —— いまの起動 ID

訊かれた起動 ID の分がメモリにもフラッシュにも無ければ **410**、引数が読めなければ **400**、
輪を確保できなかった基板は **503**。

**状態ページに出る値**（`http://seismo-1.local/`）:

- `backlog_used` / `backlog_oldest_age_s` —— メモリの輪に入っているまとまりの数と、いちばん古いものの秒数
- `backlog_requests` / `backlog_served` / `backlog_bad` / `backlog_other_boot` —— `/backlog` を受けた回数・
  返したまとまりの数・引数が読めずに断った回数・訊かれた起動の分が無かった回数
- `flash_ok` / `flash_sectors` / `flash_valid` —— フラッシュの輪を使えているか・区画の数・中身のある区画の数
- `spilling` / `spill_starts` / `spill_lost` —— いま書き出しているか・書き始めた回数・写す前にメモリの輪が
  上書きしてしまったまとまりの数（**増えていたら書き出しが追いついていない**）
- `spill_caps` / `spill_capped` —— 30 分で止めた回数と、いま止めたままか（返事が戻れば下がる）
- `flash_writes` / `flash_fails` / `flash_max_ms` —— 区画を書いた回数・消去か書き込みに失敗した回数・
  1 区画にかかった最長の時間
- `flash_read_fails` / `flash_crc_bad` / `flash_init_ms` —— 読み出しに失敗した回数・CRC が合わずに外した
  区画の数・起動時に全区画を確かめるのにかかった時間。**書き込みの失敗と分けてある** —— 書けないのは
  区画の寿命や電源の疑い、読めないのは訊かれた分を返せなかったことで、手当てが違う

**実機で確かめた**（2026-10-03、3 枚）。ホストを 5 分 18 秒止めている間、3 枚とも書き出しを続け、
写す前に上書きされた分（`spill_lost`）は 0。起動し直したホストが止まっていた間の分をすべて
フラッシュから取り戻した（取り戻しの結果は [`seismo-host/README.md`](../seismo-host/README.md)
「届かなかった分を基板へ取りに行く」）。

**返事が来ているのに書き出しを始めないことも見る。** `spill_starts` が返事の途切れていない間に
増えるなら、途絶えの判定が狂っている。返事の時刻（`loop()` の途中で受ける）は、その周の頭で
取った時刻より後になりうるので、差を符号付きで取らないと負の差が巨大な値に化ける ——
符号無しで引いていた版では、返事が 1 秒も途切れていないのに 1 枚あたり 2 分で 8〜23 回、区画を
1 つ書いては止める空振りが起きていた。直した版では 3 枚とも 3 分で 0 回だった。

**区画の形を変えたので、前の版（"SBL1"）のファームが書いた区画は読まない。** 焼き直した直後は
`flash_valid` が 0 から始まり、輪が回ってきたら上書きされる。

## センサーの品種を比べた

**MPU6050 を使っているのは、震度 2 の上のほうから 7 まで一通り拾えるから。** 静かな揺れまで見たいなら
IIS2ICLX（ST の 2 軸傾斜計）のほうが水平で 5〜7 倍静かだが、**2 軸しか無く、寝かせた
1 枚では上下動を測れない**（上下動を測るには、別の 1 枚を立てて置く）。ただ、上下動が
無くても震度はほとんど下がらない（下記「上下動が無いと、震度はどれだけ下がるか」）。
観測にはまだ組み込んでいない。

### 静かなときのばらつき

| | 水平 | 上下 | 測定範囲・出力頻度 | 軸 |
|---|---|---|---|---|
| MPU6050 | **1.04 mg**（0.95〜1.07） | **1.53 mg**（1.39〜1.57） | ±2 g・100 Hz（61.0352 µg/LSB） | 3 |
| IIS2ICLX | **0.15〜0.20 mg** | —（Z 軸が無い） | ±500 mg・104 Hz（0.015 mg/LSB） | 2 |

1 mg = 0.980665 gal。どちらも机に置いて静止させた値（2026-09-26）。

**物差しは「1 秒ぶんの標準偏差（σ）」。** 長い区間をまとめて 1 つの σ にすると、ゆっくりした
動き（ドリフト）が乗って大きく出る。ただし**集めた量は揃っていない**:

- **MPU6050**: 3 枚・9 個・27 軸を 90 秒（2698 パケット・欠け 0）。軸ごとに 1 秒ごとの σ の
  中央値を出し、水平と上下に分けてさらに中央値を取った（括弧は軸ごとの値の幅）。個体差は目立たない
- **IIS2ICLX**: 2 枚・4 軸。下記の probe の状態ページを**1 回読んだときの** 1 秒ぶんの σ
  （起動から 344 秒、人が触れなくなってから）。**1 回きりなので、MPU6050 の値ほど確かではない**

IIS2ICLX の 2 枚は別々の I²C バス（GPIO21/22 と GPIO16/17。本体のファームと同じで、
**`ESP32-WROVER` では GPIO16/17 が使えない**のも同じ。上記「1 枚に 3 個ぶら下げるとき」）へ繋ぎ、
どちらもアドレス 0x6A。基板にはアドレスを切り替えるはんだの橋（SJ1）があり、それを切っていない
状態の値。電源は 3.3 V。

### 測れる震度の幅

| | 下限（σ の 3 倍の揺れが見える震度） | 上限（張り付く震度） |
|---|---|---|
| MPU6050 | **I=2.01**（上下は 2.35） | **I=7.63**（上下は 7.02） |
| IIS2ICLX | **I=0.33〜0.58** | **I=6.42**（傾きを引くと 6.26） |

0.5 Hz の正弦波を水平 1 軸だけに入れ、**本番と同じ計測震度の計算**へ通した値（調べた周波数の
うち、いちばん大きな震度が出るのが 0.5 Hz）。揺れが速いほど数字は下がる —— 10 Hz なら
MPU6050 は下限 I=0.58・上限 I=6.19。**振幅から直に換算していない** —— 計算の途中のフィルタは
周波数ごとに利得が違うので、直に換算すると実際より良い数字が出る。

- **上下の値も、正弦波は水平の軸へ入れて求めている。** 計算は 3 つの軸を同じ式で通してから
  合成するので、どの軸へ入れても答えは同じ。変えたのは振幅のほう（上下の σ・上下の余地）だけ
- **下限**は、ノイズと同じくらいの揺れがその震度に見えるということ。これより小さい揺れは
  ノイズと区別できない。IIS2ICLX に幅があるのは σ を 0.15〜0.20 mg の両端で計算したから
- MPU6050 の「下限」は、ほかの文書にも別の数字で出てくる。**物差しが違うので、どれも正しい**:
  - 計測震度 1.64 — [`docs/implementation-plan.md`](../docs/implementation-plan.md) 項目 93。
    公称のノイズ密度から積んだ概算
  - 計測震度 1.18 — [`seismo-host/README.md`](../seismo-host/README.md)「計測震度相当」。
    静止させた基板の記録（8 時間）を、重力を引いて計算に通した値。**ノイズそのものが示す震度**
  - I=2.01 — この節。σ の 3 倍の揺れが示す震度で、**ノイズと区別できる揺れの下限**
- **上限は「少なくともここまで測れる」の側。** 上下動を 0 と置いているので、本物の地震の
  震度はこれより高く出る
- MPU6050 の上下が先に張り付くのは、**重力 1 g が常に乗っていて、余地が片側 1 g しか無い**から
- IIS2ICLX の「傾き」は、置いた向きのわずかな傾きで片側の余地が狭まる分。実測した 4 軸の平均の
  うちいちばん大きい 87.39 mg で計算した

### 棲み分け

震度の階級は計測震度で切られている（震度 1 は 0.5〜1.5、震度 2 は 1.5〜2.5、震度 6 強は
6.0〜6.5、震度 7 は 6.5 以上）。上の表をこれに当てると:

- **MPU6050**: 計測震度 2.0 あたりから上を拾える ＝ 震度 2 の上のほうから震度 7 まで。
  **震度 1 と震度 2 の下のほうはノイズに埋もれる**
- **IIS2ICLX**: 計測震度 0.3〜0.6 あたりから上が見える ＝ 震度 1 も拾える。ただし
  **震度 6 強の途中（計測震度 6.3〜6.4）で張り付く。** それとは別に、2 軸しか無いので
  寝かせた 1 枚では上下動を測れない（震度への影響は次の節）

### 上下動が無いと、震度はどれだけ下がるか

**ほとんど下がらない。** 震度は 3 成分を合わせた長さから出すので、上下動を抜けば必ず
低く出るが、その幅は震度 1〜4 で中央値 0.01〜0.02・上位 1 割でも 0.08 以下だった。
階級が下がった点は、震度 1〜4 で 1.9〜3.4%（どれも 1 階級だけ）。

K-NET・KiK-net（地表）の実波形を、同じ記録から「3 成分で計算した値」と「上下を 0 にして
計算した値」の 2 通りに出して比べた。地震は 4 つ（2016 年熊本地震の本震・2016 年鳥取県
中部の地震・2018 年大阪府北部の地震・2018 年北海道胆振東部地震）、観測点は延べ 2305 点。
表はリアルタイム震度（`src/utils/knet/realtimeIntensity.ts`。ホストと同じ計算）の最大で、
計測震度（気象庁の方式）でもほぼ同じ数字になる（中央値の差は階級ごとに 0.02 未満）。
階級の境目はアプリと同じ表（`src/utils/measuredIntensity.ts`）から引いた。

| 3 成分での階級 | 点数 | ずれの中央値 | 上位 1 割 | 最大 | 階級が下がる割合 |
|---|---|---|---|---|---|
| 1 | 582 | 0.018 | 0.079 | 0.395 | 1.9% |
| 2 | 686 | 0.017 | 0.064 | 0.210 | 3.4% |
| 3 | 461 | 0.012 | 0.040 | 0.357 | 2.8% |
| 4 | 230 | 0.010 | 0.036 | 0.119 | 2.6% |
| 5弱 | 35 | 0.010 | 0.037 | 0.085 | 5.7% |
| 5強 | 28 | 0.005 | 0.025 | 0.039 | 3.6% |
| 6弱 | 14 | 0.014 | 0.032 | 0.049 | 0.0% |
| 6強 | 9 | 0.005 | 0.027 | 0.049 | 0.0% |
| 7 | 1 | 0.056 | 0.056 | 0.056 | 0.0% |

- **4 つとも内陸の地殻内の地震。** 海溝沿いの地震や深い地震、震源のごく近くでは上下動の
  比重が変わるので、ずれはこれより大きくなりうる。そうした地震では測っていない（震源の
  深さや震源からの距離で分けても数えていない）
- 表に載っていない 259 点は、3 成分でも震度 0 だった点
- 震度 5 弱より上は点数が少なく、割合は 1 点で大きく動く（5 弱の 5.7% は 35 点中 2 点、震度 7 は 1 点しか無い）
- **計測震度は、記録の平均を引いてから計算した。** 計測震度の計算
  （`src/utils/knet/seismicIntensity.ts` の `applyJmaFilter`）は記録をそのまま 0 で詰めて
  FFT に掛けるので、K-NET の記録に残る直流のずれが詰め目で段差になり、震度を押し上げる。
  引かずに比べると、3 成分の値のほうが 1 以上高く出る点がいくつもあった（上下動は直流の
  ずれが大きいので、上下を抜いたせいで大きく下がったように見える）。リアルタイム震度は
  計算器が最初の 1 秒の平均を引くので、この問題は無い

| 道具 | 測るもの | 動かし方 |
|---|---|---|
| `tools/udp-noise.mjs` | MPU6050 の σ | `node firmware/tools/udp-noise.mjs 90`（秒数） |
| `iis2iclx-probe/` | IIS2ICLX の σ | 焼くと毎秒の統計をシリアルと状態ページ（`GET /`）へ出す |
| `tools/sensor-range.ts` | 測れる震度の幅 | `npx tsx firmware/tools/sensor-range.ts`（リポジトリのいちばん上で） |
| `tools/horizontal-only-intensity.ts` | 上下動が無いときの震度のずれ | `npx tsx firmware/tools/horizontal-only-intensity.ts`（同上。要 NIED の登録） |

- **`udp-noise.mjs` は受け手（`seismo-host`）と同じポート 50505 で待ち受ける。** 基板は宛先の
  ポートを 1 つしか持たないので、**測る間は受け手を止める**（止めずに起動すると「受信に失敗」で
  終わる）。止めていた間の分は、受け手を戻したあと基板から取り戻される（上記「届かなかった分を
  残しておく」）
- **`horizontal-only-intensity.ts` は NIED から K-NET の記録を取る。** 認証情報
  （`NIED_KNET_USER` / `NIED_KNET_PASSWORD`）を環境変数かリポジトリ直下の `.env.local` に置く。
  **`.env.local` はワークツリーへ引き継がれない**ので、ワークツリーで走らせるときは環境変数で
  渡すか、メインの checkout からコピーする。取得は地震 1 つにつき 2 件（月ごとの一覧と ZIP）で、
  ZIP は `.claude/knet-cache/` へ控えるので 2 回目からは取得しない（ワークツリーからは
  `KNET_CACHE` でメイン側の控えを指せば取り直さずに済む）。**先に `DRY=1` を付けて回すと、
  取得せずに投げる予定の URL と件数だけを出す**
- **probe は UDP で送らない。** 受け手は 3 軸を前提にしていて、2 軸のまま送っても震度の計算から
  外れる。焼くときは `iis2iclx-probe/wifi_config.example.h` を `wifi_config.h` へ複製して書き換え、
  本体のファームと同じ手順で焼く（上記「書き込む」）。名前は `iis2iclx-probe` に決め打ちしてある:

  ```bash
  arduino-cli upload -p <ポート> --fqbn esp32:esp32:esp32 firmware/iis2iclx-probe
  arduino-cli upload -p iis2iclx-probe.local --protocol network --fqbn esp32:esp32:esp32 firmware/iis2iclx-probe --upload-field password=
  ```

  2 行目は 2 回目以降の OTA。**観測中の基板とは別の 1 枚へ焼くこと**（同じ基板へ焼くと、その基板は
  観測を止める）
- **`sensor-range.ts` の σ はファイルに直接書いてある。** 測り直したら、そこを書き換えてから流す

## 直していないこと

- **起動した直後から送れていない基板は、自分では戻らない。** 返事を一度も受けていない
  起動では段を上げないため（上記「届いたかをホストに訊く」）。`/restart` か電源の
  入れ直しで戻す。**気づく手掛かりはホストの側にある** —— 観測点に割り当ててあれば、
  ホストが「届いていない」と毎分のログと管理コンソールへ出す
  （[`seismo-host/README.md`](../seismo-host/README.md)「割り当てた基板が届いていないことを知らせる」）
- **降格と再試行を実機で発火させていない。** センサーを 1 個抜いて初めて通る経路なので、
  焼いた状態では一度も走っていない。**動いているのは「数える」ところまで**
- **`realign` は実機で 1 回だけ発火した**（2026-10-01、seismo-3 の `i2c1-68` で
  `realign=1`・`overflow=1` を状態ページで見た。いつ起きたかは分からない）。
  **FIFO の作り直しまでは走ったが、そこから降格（作り直しが 5 回続く）へ進む経路は
  まだ一度も走っていない**（上記「FIFO の端数は捨てない」）
- **個体ごとの換算のずれを補正していない。** 静止時の重力は 1 g のはずだが、手元の
  9 個では 0.68〜1.24 g 相当まで散った。生のまま送る方針は変えないので、直すなら
  受け手側
- **フラッシュの区画の CRC が合わない経路を、実機で走らせていない。** 区画をわざと壊さないと
  通らない。CRC が合う側は確かめてある —— 2026-10-02 に a0b7 を焼き直したとき、前の起動が書いた
  41 区画を新しい起動が CRC 込みで読み込み（`flash_crc_bad` 0）、前の起動 ID で訊いた `/backlog` が
  フラッシュの分を返した
- **起動時に区画の読み出しが一度失敗すると、その起動ではその区画を読み直さない**
  （`flash_read_fails` に数えるだけ）。次の起動では読み直す
- **OTA に認証が無い。** 同じ LAN にいる誰でも書き換えられる
